CATEGORY: 2 - ACTION REQUIRED (find and convert hardcoded internal hrefs)
TITLE: URL-HARDCODE-01 is now deny-by-default, portal-aware and HIGH severity -
       interpolated and portal hrefs that used to pass now fail
DATE: 2026-08-31

--------------------------------------------------------------------------------
WHY YOU ARE READING THIS
--------------------------------------------------------------------------------

After this pull, `php artisan rsx:check` reports URL-HARDCODE-01 at HIGH severity
for every href value that starts with "/" and is not produced by a Route() call.
Your next check run can go red on files that have never been flagged.

The rule used to flag a literal ONLY when the STAFF dispatcher could resolve it.
Three whole classes of href therefore sailed through:

  1. Anything interpolated. The rule took the last path segment, saw the dot in
     `<%= t.id %>`, and skipped the href as a static file.
  2. Anything in the portal. Portal routes live in their own manifest table, so
     the staff resolver returned nothing and the rule flagged nothing - even for
     a clean, uninterpolated `/messages`.
  3. Any route not registered at scan time.

That is not a gap in the implementation, it is the wrong contract: "flag it if it
resolves" can never enforce "every internal URL is generated". A hardcoded portal
href reached production and broke navigation while `rsx:check` reported the file
clean.

Find yours now:

    php artisan rsx:check
    grep -rnE 'href[^a-zA-Z]*=[^a-zA-Z]*["\x27`]/' rsx/ \
        --include=*.jqhtml --include=*.blade.php --include=*.js --include=*.php

--------------------------------------------------------------------------------
WHAT IS FLAGGED NOW
--------------------------------------------------------------------------------

    href="/contacts"                        a bare internal path
    href="/contacts/view/<%= row.id %>"     interpolated jqhtml
    href="/contacts/view/{{ $id }}"         interpolated blade
    `<a href="/contacts/view/${id}">`       a JS template literal
    '<a href="/clients/' + id + '">'        JS concatenation
    $el.attr('href', '/settings')           the attribute set from JS
    window.location.href = '/dashboard'     a navigation written as a literal

Interpolation is a POSITIVE signal, not a reason to skip: a constructed path is
exactly the job Route() exists to do.

Unchanged - still clean:

    href="#" / href="#section" / href="/"
    href="https://..." / href="//cdn..." / mailto: / tel: / javascript:
    /assets/ /css/ /js/ /images/ /img/ /fonts/ /storage/
    /_compiled/ /_vendor/ /_download/ /_download_zip/ /_inline/ /_thumbnail/
    /_preview/ /_icon_by_extension/ /_upload /_ajax/
    href="/favicon.ico"   (a known static extension, when nothing is interpolated)
    any value that is ENTIRELY a Route() call

A value inside a comment (<%-- --%>, {{-- --}}, <!-- -->, //, /* */, #) never
fires - so an illustrative href in a component doc block is safe.

--------------------------------------------------------------------------------
THE CONVERSION
--------------------------------------------------------------------------------

jqhtml (staff):

    - <a href="/contacts/view/<%= row.id %>">
    + <a href="<%= Rsx.Route('Contacts_View_Action', {id: row.id}) %>">

jqhtml (portal) - the portal helper is the one that prepends /_portal/:

    - <a href="/messages/<%= t.id %>">
    + <a href="<%= Rsx_Portal.Route('Portal_Messages_Thread_Action', {thread_id: t.id}) %>">

blade:

    - <a href="/contacts/view/{{ $id }}">
    + <a href="{{ Rsx::Route('Contacts_View_Action', ['id' => $id]) }}">
    - <a href="/login">                    (portal blade)
    + <a href="{{ Rsx_Portal::Route('Portal_Login_Controller::index') }}">

JavaScript:

    - const html = `<a href="/contacts/view/${id}">x</a>`;
    + const html = `<a href="${Rsx.Route('Contacts_View_Action', {id: id})}">x</a>`;

    - $el.attr('href', '/clients/' + id);
    + $el.attr('href', Rsx.Route('Clients_View_Action', {id: id}));

    - window.location.href = '/dashboard';
    + window.location.href = Rsx.Route('Dashboard_Index_Action');

Where the literal resolves, the finding NAMES the destination action and carries
the parameters through, so the suggested line is usually paste-ready. Where it
does not, `php artisan rsx:routes` lists what is registered.

WHY THE PORTAL CASE IS THE DANGEROUS ONE: the portal is browsed under the
/_portal/ prefix. Spa.dispatch strips that prefix to MATCH a route, but writes
the URL to history verbatim - so a bare /messages/3 stays bare and the address
bar leaves the portal. Only Rsx_Portal.Route() puts the prefix back. The rule
decides portal-ness by PATH: a file under rsx/portal/ gets the portal helper in
its suggestion, resolved against the portal route table.

--------------------------------------------------------------------------------
WHEN THE LITERAL IS LEGITIMATE
--------------------------------------------------------------------------------

Rarely, a "/" path is genuinely not a route: a path served by something mounted
beside this application, or a target that must not move with a route rename.
Declare it, on the line or the line above, WITH a rationale - a bare marker
suppresses nothing:

    <a href="/legacy-entry">   <%-- @URL-HARDCODE-01-EXCEPTION - served by the
                                   legacy mount, not by the router --%>

    // @URL-HARDCODE-01-EXCEPTION - the health probe path is fixed by the load balancer
    $el.attr('href', '/_healthz');

"I do not know the action name" is not a rationale. Neither is "it works".
