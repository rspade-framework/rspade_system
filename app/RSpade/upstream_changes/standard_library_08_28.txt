THE RSPADE STANDARD LIBRARY
Date: 2026-08-28

SUMMARY
    The framework now DECLARES a standard library: a set of PHP extensions and
    composer packages that every install is guaranteed to have and that the
    framework commits to keeping. Application code may reach for any of them
    without installing anything and without checking whether the box has it.

    Nothing you have written stops working. What changes is that some of the
    problems your app currently solves by hand now have one supported answer,
    and one of them - MONEY ARITHMETIC IN A FLOAT - is a correctness bug that
    does not announce itself. That is the action this document is about.

    Full reference: php artisan rsx:man standard_library

THE CHANGE
    PHP EXTENSIONS
        Declared in App\RSpade\Core\Health\Rsx_Php_Requirements and enforced at
        boot: a box missing one throws by name instead of failing later inside
        whatever feature touched it first. Newly declared:

            ldap     Directory authentication (Active Directory, OpenLDAP)
            imap     Reading a mailbox over IMAP/POP3
            sodium   Modern cryptography - AEAD, signing, password hashing
            zstd     Zstandard compression
            pcntl    CLI tier only - signal handling and process control

        Already required and unchanged: imagick, gd, gmp, zip, zlib, redis,
        pdo_mysql, and the base set (ctype, curl, dom, fileinfo, filter, hash,
        iconv, json, libxml, mbstring, openssl, pcre, pdo, phar, posix, session,
        simplexml, tokenizer, xml, xmlreader, xmlwriter). simplexml joins that
        base set with PhpSpreadsheet, which requires it; it is part of php-xml,
        which every install already has.

        pcntl is a CLI-ONLY guarantee. Debian/sury deliberately do not compile it
        into php-fpm, so web-tier code must never call it.

        NOT declared, and not to be assumed: exif, calendar, mysqli, sockets. They are present on a typical box but nothing promises
        them. If your app calls one, declare it in your own application-layer
        composer.json (php artisan rsx:composer require) so a box without it
        fails at install time rather than in production.

    COMPOSER PACKAGES
        Added to config('rsx.dependencies.exposed_composer') and installed in
        system/vendor - use them directly, there is nothing to require:

            phpoffice/phpspreadsheet   Real spreadsheets (xlsx/xls/ods)
            league/csv                 Streaming CSV read/write
            brick/money                Money arithmetic (with brick/math)
            endroid/qr-code            QR codes as PNG or SVG

        Joining the four already exposed and unchanged:
        giggsey/libphonenumber-for-php, ezyang/htmlpurifier, sokil/php-isocodes,
        nikic/php-parser, guzzlehttp/guzzle, laravel/framework.

        Exposure is a standing commitment: an exposed package stays available at
        a compatible major version, and any retirement or major bump ships with
        its own upstream_changes document naming the remedy.

    You receive all of this automatically with the framework submodule. There is
    nothing to install and nothing to add to your composer.json.

ACTION REQUIRED

    1. PORT MONEY ARITHMETIC TO brick/money
    -------------------------------------------------------------------------
    This is the item that matters, because it is silent. A float cannot hold
    most decimal amounts. 0.1 + 0.2 is 0.30000000000000004 in PHP as in every
    other language with doubles, and an integer past 2^53 loses its last digits
    outright. Nothing throws. The error accumulates through a line-item loop and
    surfaces as an invoice that is off by a cent nobody can account for.

    FIND IT. Run each of these over your /rsx/ tree and read every hit that
    touches an AMOUNT (price, total, budget, rate, fee, tax, balance, subtotal,
    discount, salary, cost):

        # float casts on money
        grep -rn --include="*.php" -e "(float)" -e "floatval(" rsx/

        # money rendered with number_format
        grep -rn --include="*.php" "number_format" rsx/

        # arithmetic on a model attribute that is a DECIMAL column
        grep -rnE --include="*.php" '\$[a-z_]+->(price|total|amount|budget|rate|fee|tax|balance|subtotal|cost|salary)[^;]*[-+*/]' rsx/

        # a DECIMAL column passed through untouched, then computed on later
        grep -rn --include="*.php" -e "->price =" -e "->total =" -e "->amount =" -e "->budget =" rsx/

    A hit is FINE when the value only travels (assigned to a column, put in a
    payload, compared for emptiness). A hit is a BUG when the value is added,
    multiplied, divided, summed, split or rounded as a float.

    CONVERT IT.

        // BEFORE - float arithmetic, float rounding, no currency
        $subtotal = 0.0;
        foreach ($lines as $line) {
            $subtotal += (float) $line->unit_price * $line->quantity;
        }
        $tax   = round($subtotal * 0.0825, 2);
        $total = $subtotal + $tax;

        echo '$' . number_format($total, 2);

        // AFTER - exact decimals, an explicit rounding mode, currency carried
        use Brick\Money\Money;
        use Brick\Math\RoundingMode;

        $subtotal = Money::of('0.00', 'USD');
        foreach ($lines as $line) {
            $subtotal = $subtotal->plus(
                Money::of($line->unit_price, 'USD')->multipliedBy($line->quantity)
            );
        }
        $tax   = $subtotal->multipliedBy('0.0825', RoundingMode::HalfUp);
        $total = $subtotal->plus($tax);

        echo $total->formatTo('en_US');   // "$64.92"
        // or, to keep your own presentation:
        echo '$' . $total->getAmount();   // exact decimal string, never a float

    THREE RULES THAT COME WITH IT.

        a) Money::of() takes a STRING or an int, never a float. Pass the model
           attribute straight through - a DECIMAL column arrives as a string, and
           casting it to a float on the way in throws away the precision you came
           here for.

        b) State the rounding mode on any operation that can produce more scale
           than the currency has (multipliedBy, dividedBy). brick/money THROWS
           rather than guessing, which is the point: the exception tells you a
           rounding decision was being made silently before.

        c) Two Money values of different currencies cannot be added. If that
           throws in your code, it found a real bug.

    FORMATTING FOR DISPLAY. Two options, both correct:

        $money->formatTo('en_US')          // locale decides symbol and separators
        $money->getAmount()                // exact decimal string, you format it

    Worked example - the template's own currency formatter, which keeps its
    existing output while carrying the amount as an exact decimal underneath:

        system/app/RSpade/resource/reference_app/lib/formatters.php
            (Formatters::currency)

    ... and a DECIMAL column rendered through it rather than through a float:

        system/app/RSpade/resource/reference_app/models/project_model.php
            (Project_Model::budget_formatted)

    2. AUDIT ANY EXTENSION YOU ASSUMED BUT NOBODY DECLARED
    -------------------------------------------------------------------------
    If your app calls exif, calendar, mysqli or sockets, it
    is relying on a box's happenstance. Declare the requirement in your own
    application-layer manifest:

        php artisan rsx:composer require ext-exif

    Find them with:

        grep -rnE --include="*.php" '\b(exif_|cal_days_in_month|mysqli_|socket_)' rsx/

    Do NOT keep money on bcmath just because it is now declared - convert it to
    brick/money per item 1, which needs no extension at all.

    3. OPTIONAL - ADOPT THE THREE TEMPLATE IMPROVEMENTS
    -------------------------------------------------------------------------
    Your /rsx/ is your own fork, so these do not arrive on their own. Each is a
    self-contained demonstration of one standard-library package; take the ones
    that apply to your app.

    a) SERVER-SIDE PHONE VALIDATION AND E.164 STORAGE (libphonenumber)

       A browser widget formats a phone number; it does not decide whether the
       number is usable, and it is not the thing your data has to trust. The
       template now validates every submitted phone number on the server and
       stores E.164 ("+19206145140"), so two records holding the same number
       compare equal, a search matches whatever spelling the user typed, and an
       SMS gateway gets the form it requires.

       Read: system/app/RSpade/resource/reference_app/app/frontend/contacts/contacts_controller.php
             (save() and _normalize_phone())

       The shape, for one field:

           use libphonenumber\NumberParseException;
           use libphonenumber\PhoneNumberFormat;
           use libphonenumber\PhoneNumberUtil;

           $value = trim((string) ($params['phone_work'] ?? ''));

           if ($value !== '') {
               try {
                   $proto = PhoneNumberUtil::getInstance()
                       ->parse($value, config('rsx.formatting.phone_region'));

                   if (!PhoneNumberUtil::getInstance()->isPossibleNumber($proto)) {
                       $errors['phone_work'] = 'Please enter a valid phone number';
                   } else {
                       $value = PhoneNumberUtil::getInstance()
                           ->format($proto, PhoneNumberFormat::E164);
                   }
               } catch (NumberParseException $e) {
                   $errors['phone_work'] = 'Please enter a valid phone number';
               }
           }

       THREE THINGS TO GET RIGHT.

           - isPossibleNumber(), not isValidNumber(). A number in an unassigned
             range is what is printed on somebody's business card. Rejecting it
             makes an unrelated edit to that record unsaveable.
           - A BLANK value is a value. The user clearing the field means "this
             contact has no work number" and must store null - not be skipped as
             "not submitted". A form submits every field it renders.
           - If you store E.164 you MUST also display it. A formatter that shows
             "+1 920 614-5140" where the user typed "(920) 614-5140" reads as a
             bug. The template's Formatters::phone() / Formatters.phone() now
             render a number belonging to the region's OWN country code in that
             region's national style, and only a foreign number with its country
             code. Copy both sides or neither.

       IF YOU ALREADY HAVE PHONE DATA, normalise it with a one-off migration or
       task before turning the validation on, or leave existing rows alone -
       nothing re-writes them, and the two spellings coexist harmlessly except
       when compared.

       config('rsx.formatting.phone_region') is a NEW application-layer config
       key (rsx/resource/config/rsx.php, default 'US'). Add it, or pass your
       region literally.

    b) EXPORT TO EXCEL (PhpSpreadsheet)

       CSV is text a spreadsheet guesses at; xlsx carries the types, so a phone
       number stays a phone number and a date is a date rather than whatever the
       recipient's locale decides "3/4/25" meant.

       Read: system/app/RSpade/resource/reference_app/app/frontend/clients/clients_controller.php
             (export_xlsx)
             .../reference_app/app/frontend/clients/list/clients_datagrid.js
             (export_selection_xlsx)
             .../reference_app/lib/file_download.js
             (base64_to_bytes)

       The one thing that is not obvious: an Ajax response can never BE a
       download - the transport is XHR and every response is HTTP 200 JSON. The
       CSV export gets away with returning a string. A workbook is binary, so the
       endpoint returns it base64-encoded and the client rebuilds the bytes:

           // PHP
           $handle = fopen('php://memory', 'r+');
           (new Xlsx($spreadsheet))->save($handle);
           rewind($handle);
           $bytes = stream_get_contents($handle);
           fclose($handle);

           return [
               'xlsx_base64' => base64_encode($bytes),
               'filename'    => 'clients_export_' . Rsx_Date::today() . '.xlsx',
               'count'       => $count,
           ];

           // JS
           trigger_file_download(
               base64_to_bytes(result.xlsx_base64),
               result.filename,
               'application/vnd.openxmlformats-officedocument.spreadsheetml.sheet'
           );

       Gate the endpoint the way the CSV one is gated, and mirror that gate on
       the menu item so the menu never offers what the server will refuse.

       NOTE: rsx/lib/csv_download.js was RENAMED to rsx/lib/file_download.js - it
       holds download helpers for both formats now. If you adopt this, rename
       your copy too; nothing references it by path.

    c) Formatters::currency() ON brick/money

       Covered by item 1. The output for existing callers is unchanged except in
       one case, which is the reason for the change: an amount with more digits
       than a double holds now formats to the digits it was given.
       Formatters::currency('9007199254740993') was "9,007,199,254,740,992" and
       is now "9,007,199,254,740,993".

VERIFICATION

    The framework side arrived correctly:

        php artisan rsx:health
            The dependency rows and both extension tiers report OK. A missing
            extension is its own FAIL row naming the apt package.

        php artisan rsx:composer provides
            Lists what the framework supplies here, including the four new
            packages at their installed versions.

        php artisan rsx:man standard_library
            The reference page.

    Your money conversion is correct when:

        - every grep in item 1 returns only hits where the amount TRAVELS, never
          hits where it is computed;
        - a total built from the same line items twice gives the same string
          both times, and equals the figure computed by hand;
        - a deliberately awkward case behaves - three items at 0.10 summing to
          exactly "0.30", a value split N ways summing back to the original;
        - nothing in the money path calls round(), number_format(), (float) or
          floatval() on an amount any more.

    Your phone conversion is correct when:

        - a bad number renders as a per-field form error, not a page error;
        - a good number is stored as "+1..." and is displayed back in the form
          exactly as the user typed it (open the edit screen after saving - this
          is the step that catches a half-adopted change);
        - clearing the field stores null;
        - an existing record with a placeholder area code still saves.

    Your xlsx export is correct when the downloaded file opens in Excel and its
    first row is the header. From the CLI, the endpoint's bytes must start with
    the ZIP signature (50 4B 03 04) after base64-decoding.
