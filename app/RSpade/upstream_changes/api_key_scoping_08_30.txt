API KEY SCOPING - SCOPE MANAGEMENT UI, AND THE GET-PURITY RULE
Date: 2026-08-30

SUMMARY
    An API key used to carry its holder's ENTIRE authority: an integration that
    only needed to read contacts could, with the same credential, delete every
    client its owner could delete. _api_keys.scopes is now enforced - a key may
    be narrowed to a rule set, and every existing key (scopes NULL) is
    unaffected.

    TWO THINGS REACH YOU HERE.

    1. The template app's Settings > API Keys module grew a whole scope
       management UI - a mint modal with presets, a custom-rule box and a live
       effective-access preview, a Scope column on the grid, and a read-only
       view of an existing key's rules. Your /rsx/ is your own fork, so none of
       it arrives on its own. Copy it if you want it. (Section: CHANGES
       REQUIRED.)

    2. API-GET-PURE-01, a new manifest-scan rule, ships in /system/ and applies
       to YOUR API controllers immediately. A GET #[Api_Endpoint] whose body
       writes now FAILS THE MANIFEST BUILD. (Section: ACTION REQUIRED.)

    Nothing else changes. A key with no rules behaves exactly as it did, and
    Api_Key_Model::generate() gained an optional trailing $scopes argument, so
    every existing call site is unaffected.

    Full contract: php artisan rsx:man external_api (section KEY SCOPES).

        // browser computed. The preview panel unions the same presets
        // client-side so the operator can see the result, but what is stored is
        // re-derived from config on the server: a ticked preset is a NAME, and

        // The mode is answered EXPLICITLY. Treating an unrecognised value as
        // unrestricted would mean a broken form silently mints the widest key
        // there is, which is the one failure this endpoint must not have.
        if ($access_mode !== 'unrestricted' && $access_mode !== 'scoped') {
            return response_form_error(
                'Please correct the errors below.',
                ['access_mode' => 'Choose whether this key is unrestricted or scoped.']
            );

        if ($access_mode === 'scoped') {
            $preset_names = is_array($params['presets'] ?? null) ? $params['presets'] : [];
            $preset_rules = static::_expand_scope_presets($preset_names);

            if ($preset_rules === null) {

                    'Please correct the errors below.',
                    ['presets' => 'One of those presets no longer exists. Reload the page and choose again.']
                );
            }

                return response_form_error(

            } catch (\InvalidArgumentException $e) {
                // The parser's own message names the offending line verbatim.
                return response_form_error('Please correct the errors below.', ['scopes' => $e->getMessage()]);

        /**
         * Ajax endpoint: the app's named scope presets, for the mint modal.
         */
        #[Ajax_Endpoint]
        public static function get_scope_presets(Request $request, array $params = [])
        {
            if (!Session::has_api_access()) {
                return response_unauthorized('API access is not enabled for your account');
            }

            $presets = [];

            foreach (static::_scope_presets() as $preset) {
                $presets[] = [
                    'name' => $preset['name'],
                    'description' => $preset['description'] ?? '',
                    'rules' => $preset['rules'] ?? '',
                ];
            }

            return ['presets' => $presets];
        }

        /**
         * Ajax endpoint: which endpoints would this rule text actually reach?
         *
         * A MALFORMED RULE IS A NORMAL ANSWER HERE, not a failure: the operator
         * is mid-keystroke and the panel's job is to say what is wrong with what
         * they have written so far.
         */
        #[Ajax_Endpoint]
        public static function preview_scopes(Request $request, array $params = [])
        {
            if (!Session::has_api_access()) {
                return response_unauthorized('API access is not enabled for your account');
            }

            $scopes = trim((string) ($params['scopes'] ?? ''));

            try {
                $groups = Api_Catalog::resolve_for_scopes(1, $scopes === '' ? null : $scopes);
            } catch (\InvalidArgumentException $e) {
                return ['error' => $e->getMessage(), 'unrestricted' => false, 'groups' => []];
            }

            return [
                'error' => null,
                'unrestricted' => Api_Scopes::is_unrestricted($scopes === '' ? null : $scopes),
                'groups' => static::_preview_groups($groups),
            ];
        }

        /**
         * Ajax endpoint: one key's scope rules.
         *
         * KEYS ARE IMMUTABLE AFTER MINT - there is no edit endpoint, and
         * narrowing a key means revoking it and minting a replacement. The
         * ownership rule lives in this body rather than in the #[Auth] gate: a
         * key belonging to somebody else answers exactly as one that does not
         * exist.
         */
        #[Ajax_Endpoint]
        public static function get_key_scopes(Request $request, array $params = [])
        {
            if (!Session::has_api_access()) {
                return response_unauthorized('API access is not enabled for your account');
            }

            $user = Session::get_user();
            if (!$user) {
                return response_error(Ajax::ERROR_AUTH_REQUIRED);
            }

            $key = Api_Key_Model::where('id', $params['id'] ?? null)
                ->where('user_id', $user->id)
                ->first();

            if (!$key) {
                return response_error(Ajax::ERROR_NOT_FOUND, 'API key not found');
            }

            return [
                'id' => $key->id,
                'name' => $key->name,
                'scopes' => $key->scopes,
                'unrestricted' => $key->is_unrestricted(),
            ];
        }

        /**
         * The configured presets, always as a list of arrays.
         */
        private static function _scope_presets(): array
        {
            $presets = config('rsx.api.scope_presets', []);

            return is_array($presets) ? $presets : [];
        }

        /**
         * The rule text for a set of preset NAMES, or null when one of them is
         * not configured. An unknown name is REFUSED rather than skipped:
         * silently dropping it would mint a key narrower than the operator
         * ticked, and they would find out from a 403 weeks later.
         */
        private static function _expand_scope_presets(array $names): ?string
        {
            $by_name = [];
            foreach (static::_scope_presets() as $preset) {
                $by_name[$preset['name']] = $preset['rules'] ?? '';
            }

            $lines = [];
            foreach ($names as $name) {
                if (!array_key_exists($name, $by_name)) {
                    return null;
                }
                $lines[] = $by_name[$name];
            }

            return implode("\n", $lines);
        }

        /**
         * Flatten Api_Catalog's grouped catalogue to what the preview renders.
         */
        private static function _preview_groups(array $groups): array
        {
            $out = [];

            foreach ($groups as $group) {
                $endpoints = [];

                foreach ($group['endpoints'] as $endpoint) {
                    foreach ($endpoint['methods'] as $method) {
                        $endpoints[] = ['method' => $method, 'pattern' => $endpoint['pattern']];
                    }
                }

                $out[] = ['name' => $group['name'], 'endpoints' => $endpoints];
            }

            return $out;
        }

ACTION REQUIRED

    1. AUDIT YOUR GET ENDPOINTS FOR API-GET-PURE-01 (every app with an API)

       "Read-only" is expressible in the scope language only as a GET grant, so
       the value of `Grant GET /api/v1/**` rests entirely on GET being
       side-effect free. That is now enforced at scan time.

       THE MANIFEST BUILD NOW FAILS when a GET-only #[Api_Endpoint] handler's own
       body contains any of:

           ->save(   ->delete(   ->update(   ::create(   ->raw_bulk(
           DB::statement(  DB::insert(  DB::update(  DB::delete(
           Task::dispatch(

       You will find out immediately - the build names the file, the method and
       the token it found. There is nothing to search for pre-emptively; if your
       build succeeds after the pull, you have no violations the rule can see.

       WHEN IT FIRES, there are exactly two correct answers:

         (a) MOVE THE WRITE. If the endpoint mutates anything a caller would
             consider state, it is a POST endpoint that was declared GET. Change
             methods: ['GET'] to methods: ['POST'] and tell your consumers.

         (b) DECLARE THE EXCEPTION, if the write is genuinely bookkeeping the
             caller asked for (a read receipt, a last-seen stamp):

                 /**
                  * Latest inbox messages.
                  *
                  * @API-GET-PURE-01-EXCEPTION stamps last_polled_at for the
                  * caller's own connector; no user-visible state changes.
                  */

             THE RATIONALE IS REQUIRED. A bare tag still fails the build,
             because recording that somebody wanted the rule off is not the same
             as recording a reason.

       WHAT THE RULE CANNOT SEE: only the handler's OWN body is scanned. A
       private helper it calls is not followed. That is the honest limit of a
       literal-token rule, and it is why (b) exists - if you have GET endpoints
       whose writes hide behind a helper, the rule will not catch them and a
       Grant GET rule set will be broader than it looks. Read your GET handlers
       once, now, while the list is short.

    2. NOTHING TO DO FOR EXISTING KEYS

       Every key in your database has scopes NULL and stays UNRESTRICTED. No
       credential changes behaviour, and no integration breaks. Scoping is
       opt-in, per key, at mint time.

    3. IF YOU MINT KEYS FROM A SCRIPT

       rsx:api:key:create and rsx:api:key:temp take a repeatable --scope:

           php artisan rsx:api:key:temp --user=importer@example.com \
             --scope="Grant GET /api/v1/**" --json

       A malformed rule exits non-zero with error.code scopes_invalid and mints
       nothing. Omitting --scope keeps the old behaviour exactly.

VERIFICATION

    Manifest build (the GET-purity rule):

        php artisan rsx:manifest:build      # or simply load any page

    The UI, after copying the files:

        php artisan rsx:debug /frontend/settings/api_keys --user=<your id>

    Open Generate New Key, choose Scoped, tick a preset: the Effective access
    panel lists the endpoints the rules reach. Type a broken rule
    ("Grant SNARF /api/v1/x") - the panel and the field both show the parser's
    message naming the line, and the mint is refused.

    End to end, with a real key:

        php artisan rsx:api:key:create --user=1 --name="scope test" \
          --scope="Grant GET /api/v1/me" --json

        curl -H "Authorization: Bearer <key>" https://your.host/api/v1/me
        # 200, and key.scopes echoes the rule

        curl -H "Authorization: Bearer <key>" https://your.host/api/v1/contacts
        # 403 {"error":{"code":"insufficient_scope",
        #               "required":"GET /api/v1/contacts"}}

        php artisan rsx:api:key:list --user=1     # Scope column reads "1 rule"
