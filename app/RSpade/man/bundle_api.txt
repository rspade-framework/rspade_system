
NAME
    Bundle - RSX asset compilation and management system

SYNOPSIS
    // Module Bundle (page entry point)
    use App\RSpade\Core\Bundle\Rsx_Module_Bundle_Abstract;

    class My_Bundle extends Rsx_Module_Bundle_Abstract
    {
        public static function define(): array
        {
            return [
                'include' => [
                    'bootstrap5',           // Module alias
                    'Quill_Bundle',         // Asset bundle (explicit)
                    'rsx/theme',            // Directory (auto-discovers asset bundles)
                    __DIR__,                // Module directory
                ],
            ];
        }
    }

    // Asset Bundle (dependency declaration, auto-discovered)
    use App\RSpade\Core\Bundle\Rsx_Asset_Bundle_Abstract;

    class Tom_Select_Bundle extends Rsx_Asset_Bundle_Abstract
    {
        public static function define(): array
        {
            return ['npm' => ['tom-select']];
        }
    }

    // Render in Blade
    {!! My_Bundle::render() !!}

DESCRIPTION
    RSX Bundles provide a radically simplified asset compilation system
    compared to Laravel Mix or Vite. Instead of webpack configurations,
    JSON manifests, and build scripts, you define a simple PHP class
    with an array of what to include. The framework handles everything
    else automatically.

    Unlike Laravel's approach where you configure webpack, define entry
    points, set up hot module replacement, and manage complex build
    pipelines, RSX Bundles use a single 'include' array that accepts
    any mix of directories, files, NPM packages, or other bundles.
    The system automatically determines file types, resolves dependencies,
    and compiles everything.

    The Bundle system integrates directly with the Manifest, automatically
    including JavaScript stubs for controllers and models. SCSS files are
    compiled transparently. Vendor and application code are automatically
    split for optimal caching.

    Key differences from Laravel Mix/Vite:
    - Laravel: Complex webpack.mix.js or vite.config.js files
    - RSX: Simple PHP class with an include array

    - Laravel: Manual configuration of entry points and outputs
    - RSX: Automatic detection and compilation

    - Laravel: Separate processes for JS bundling and CSS compilation
    - RSX: Unified system handles all asset types

    - Laravel: Manual versioning and cache busting setup
    - RSX: Automatic hash-based cache busting

    Benefits:
    - No JavaScript build configuration needed
    - Works immediately without npm run dev/build
    - Automatic vendor/app code splitting
    - Integrated with PHP class discovery
    - Zero configuration SCSS compilation

CREATING A BUNDLE
    CREATING A MODULE BUNDLE (page entry point):
        1. Extend Rsx_Module_Bundle_Abstract
        2. Implement define() method
        3. Return configuration array with 'include' key

        Example:
            class Dashboard_Bundle extends Rsx_Module_Bundle_Abstract
            {
                public static function define(): array
                {
                    return [
                        'include' => [
                            'bootstrap5',
                            'rsx/app/dashboard',
                        ],
                        'config' => [
                            'api_version' => '2.0',
                        ],
                    ];
                }
            }

    CREATING AN ASSET BUNDLE (dependency declaration):
        1. Extend Rsx_Asset_Bundle_Abstract
        2. Place alongside components that need the dependency
        3. Declare NPM modules, CDN assets, or direct file paths

        Example:
            class Chart_JS_Bundle extends Rsx_Asset_Bundle_Abstract
            {
                public static function define(): array
                {
                    return [
                        'cdn_assets' => [
                            'js' => [
                                ['url' => 'https://cdn.jsdelivr.net/npm/chart.js'],
                            ],
                        ],
                    ];
                }
            }

CDN ASSETS
    'cdn_assets' declares external URLs the bundle RENDERS INTO THE HEAD of
    every page it serves - a CSS framework, a global library present
    everywhere. Both 'js' and 'css' lists are accepted, each entry a map with
    at least 'url'.

    EVERY MODE MIRRORS THE ASSET. It is downloaded into
    rsx/resource/.cdn-cache/ (committed to git) on first compile and the tag
    points at /_vendor/{mirror_filename} - on a development box exactly as in a
    sealed build. Because the copy is same-origin, a cdn_asset contributes
    NOTHING to the CSP policy in any mode, and the store is where a compile
    goes for the bytes rather than the network.

    A declared 'integrity' hash is VERIFIED at download and a mismatch fails
    the compile; the attribute itself is not emitted, since the asset is served
    from our own origin. An unreachable URL fails the compile naming it.

    A sealed web request never downloads: a missing mirror file THROWS naming
    the file and rsx:build --force. In development the same miss is a 404 naming
    rsx:cdn_externals:refresh.
    See: php artisan rsx:man csp, php artisan rsx:man external_resources

    CHOOSING BETWEEN THE TWO. cdn_assets is a HEAD asset: fetched on every page
    the bundle serves, whether or not anything uses it. The external-resources
    registry is an ON-DEMAND load: nothing is fetched until code calls
    Rsx.load_external('identifier'), which is what a feature-specific library
    (a charting library, a vendor widget) should be. The registry is also the
    only one of the two that a portal/staff realm split, a readiness handshake
    or per-entry CSP extras applies to.
    See: php artisan rsx:man external_resources

BUNDLE TYPES
    RSX has two types of bundles with distinct purposes:

    MODULE BUNDLES (Rsx_Module_Bundle_Abstract)
        Top-level bundles that get compiled and rendered on pages.
        - Can scan directories via 'include' paths
        - Can explicitly include Asset Bundles by class name
        - Auto-discovers Asset Bundles in scanned directories
        - Gets built via rsx:bundle:compile
        - Cannot include other Module Bundles

        Example:
            class Frontend_Bundle extends Rsx_Module_Bundle_Abstract {
                public static function define(): array {
                    return [
                        'include' => [
                            __DIR__,          // Directory scan
                            'rsx/theme',      // Directory scan (auto-discovers asset bundles)
                            'Quill_Bundle',   // Explicit asset bundle
                        ],
                    ];
                }
            }

    ASSET BUNDLES (Rsx_Asset_Bundle_Abstract)
        Dependency declaration bundles co-located with components.
        - NO directory scanning - only direct file paths
        - Declares CDN assets, NPM modules, watch targets
        - Auto-discovered when Module Bundles scan directories
        - Never built standalone - metadata consumed by Module Bundles
        - Can include other Asset Bundles by class name

        Example:
            // /rsx/theme/components/inputs/select/Tom_Select_Bundle.php
            class Tom_Select_Bundle extends Rsx_Asset_Bundle_Abstract {
                public static function define(): array {
                    return [
                        'npm' => ['tom-select'],
                    ];
                }
            }

    AUTO-DISCOVERY
        When a Module Bundle scans a directory, Asset Bundles found within
        are automatically processed. Their CDN assets, NPM modules, and
        config are merged into the parent bundle.

        This allows components to declare their own dependencies without
        requiring explicit inclusion in every Module Bundle that uses them.

        Discovered Asset Bundles cannot have directory scan paths in their
        'include' array. If an Asset Bundle needs directory scanning, it
        must be explicitly included by class name in the parent Module Bundle.

BUNDLE PLACEMENT
    MODULE BUNDLES exist at top-level module directories:

    CORRECT:
        /rsx/app/login/login_bundle.php          - Module Bundle
        /rsx/app/frontend/frontend_bundle.php    - Module Bundle

    ASSET BUNDLES live alongside their components:

    CORRECT:
        /rsx/theme/components/inputs/select/Tom_Select_Bundle.php
        /rsx/theme/bootstrap5_src_bundle.php

    MODULE BUNDLE COVERAGE:
    Including __DIR__ in a Module Bundle automatically includes all
    files in that directory and subdirectories recursively, while
    auto-discovering any Asset Bundles found.

    Example:
        // /rsx/app/login/login_bundle.php
        class Login_Bundle extends Rsx_Module_Bundle_Abstract
        {
            public static function define(): array
            {
                return [
                    'include' => [
                        __DIR__,  // Includes ALL of /rsx/app/login/ recursively
                    ],
                ];
            }
        }

    This single bundle covers:
        /rsx/app/login/login_controller.php
        /rsx/app/login/login_index.blade.php
        /rsx/app/login/login_index.js
        /rsx/app/login/accept_invite/...
        /rsx/app/login/signup/...
        ... and all files in subdirectories

    COVERAGE IS VALIDATED AT RENDER TIME, twice: the bundle must cover the
    directory of the VIEW being rendered, and the directory of the CONTROLLER
    that dispatched the request. Both throw a YoureDoingItWrongException naming
    the bundle, the path and the include list. The point is that a page's own
    code - its Ajax stubs, its Rsx.Route() targets, its components - is actually
    in the bundle serving it.

    TWO WAIVERS, BOTH FOR FRAMEWORK-OWNED MARKUP:
        - A view under app/RSpade/ never has to be covered. Framework views are
          rendered from application routes by design.
        - When the VIEW is a framework view, the CONTROLLER check is waived too.
          The app controller then contributes nothing to the page but the route
          it is mounted on, and the bundle is framework-owned end to end, so
          there is no app-side JS for it to be missing.

    The second waiver is what lets a framework feature mounted on an application
    route ship its own bundle. The shipped case is the API reference console:
    Rsx_Api_Docs::page() renders _Apidocs_App.blade.php, which names the
    framework's _Apidocs_Bundle, from whatever route the application declared.
    An application never writes a bundle for it. See external_api(3).

ADDING CUSTOM NPM MODULES
    Application developers can include third-party npm packages in their bundles
    by creating Asset Bundles co-located with their components:

        // /rsx/theme/components/charts/Chart_JS_Bundle.php
        class Chart_JS_Bundle extends Rsx_Asset_Bundle_Abstract
        {
            public static function define(): array
            {
                return [
                    'npm' => [
                        'Chart' => "import { Chart } from 'chart.js/auto'",
                    ],
                ];
            }
        }

    The 'npm' array maps global variable names to ES module import statements.
    Each entry creates one global variable accessible in your JavaScript.

    The package is included only when Module Bundles scan that directory.
    This keeps bundle sizes smaller when components aren't used.

    For detailed npm integration documentation including import formats,
    troubleshooting, and examples, see npm(3).

INCLUDE TYPES
    Module Aliases
        Predefined in config/rsx.php:
        'jquery', 'lodash', 'bootstrap5', 'vue', 'react'

    Bundle Classes
        Reference other bundles:
        'Core_Bundle', 'Bootstrap5_Src_Bundle'

    Bundle Aliases
        Defined in config/rsx.php:
        'bootstrap5_src' => Bootstrap5_Src_Bundle::class

    Directories
        Include all files recursively:
        'rsx/app/dashboard'

    Specific Files
        Include individual files:
        'rsx/lib/utils.js'
        'rsx/theme/variables.scss'

    Overridden Framework Classes
        Whichever way a bundle reaches a framework PHP class your
        application overrides (rsx:man class_override) - directory, pattern
        or explicit file, in any bundle including the framework's own - it
        compiles your file in that file's place in the include order, once,
        and never the framework's, even when none of the bundle's includes
        covers your file's directory. Only PHP classes are overridable: a
        framework JS class, template or stylesheet a bundle includes is
        compiled as it is found, and a stylesheet of yours that styles the
        same component is compiled alongside it. An overridden MODEL
        brings its client-side class too: when your override has a JS
        class of its own (class User_Model extends Base_User_Model), the
        bundle receives that file right after the model, so every bundle
        that includes the framework's models - through Core_Bundle, every
        bundle there is - carries your override's stub and JS class
        together (rsx:man class_override, BUNDLES).

    Type-Filtered Directories
        One directory, ONE file type, in exactly two forms:

        'rsx/theme/*.scss'       that directory's own .scss files, and no
                                 subdirectory's
        'rsx/theme/**/*.scss'    that directory's .scss files and those of
                                 everything beneath it

        A directory include takes every file of every type beneath it. A
        pattern is the granularity between that and one file: it is how a
        bundle takes a theme's global stylesheets without the component
        library that lives in the theme's subdirectories.

        The grammar is those two forms and nothing else: a literal directory,
        an optional '**/' segment, and a file name that is exactly '*.<ext>'
        with one extension. There are no brace sets, no '?', no character
        classes, no exclusions and no '*' in any other position. A second
        extension or a second directory is a second entry.

        - Any other use of '*' fails the build ("Bundle include pattern is not
          one of the accepted forms"), printing the two forms.
        - A pattern that matches NO file fails the build ("Bundle include
          pattern matches no files" / "names a directory that does not
          exist"), naming the pattern and the bundle. It is never a silent
          no-op: a bundle that quietly lost its stylesheets renders a working
          page that looks wrong and reports nothing.
        - The matches join the bundle at the entry's own position in the
          include list, sorted by path - the order a directory include uses,
          identical on every checkout. A file an earlier entry already named
          keeps its earlier position, so 'rsx/theme/variables.scss' followed
          by 'rsx/theme/*.scss' leaves the variables first.
        - The recursive form passes over the directory names a directory
          include passes over (vendor, node_modules, resource, public, ...).
        - A pattern is expanded on every compile, so in development a file
          ADDED to a matched directory is in the bundle on the next request,
          exactly like a file added beneath a directory include.
        - A pattern names files, not a directory: it never satisfies the
          render-time coverage check (BUNDLE PLACEMENT above). A bundle built
          from patterns and files still lists its own module directory.
        - An Asset Bundle discovered by a scan may not declare one, for the
          same reason it may not declare a directory.

        The two forms are DIFFERENT tools. Over a theme, '**/*.scss' takes
        every component's stylesheet as well - most of the stylesheet weight,
        and the component inventory as a list of CSS class names. '*.scss'
        takes only the directory it names, so a theme whose global stylesheets
        sit at more than one depth needs one entry per directory that holds
        them. See PUBLIC-FACING BUNDLES below.

        Inside a PHP block comment the recursive form cannot be written as it
        is: the sequence '*' '/' ends the comment. Write it in a '//' comment.

    NPM Modules
        Use Asset Bundles with the 'npm' array. See npm(3) for details.

    CDN Assets
        NOT an include entry. There is no 'cdn:' include prefix - an external
        URL reaches a page one of two ways:

        - An Asset Bundle's 'cdn_assets' map, for a library the page needs in
          its HEAD on every load (see CDN ASSETS below).
        - The external-resources registry, for anything loaded ON DEMAND at
          runtime: declare it in a *.externals.php file and call
          Rsx.load_external('identifier').
          See: php artisan rsx:man external_resources

    Public Directory Assets
        Static assets from public/ directories with automatic cache-busting:
        '/public/sneat/css/core.css'
        '/public/sneat/js/helpers.js'

        These resolve to files in any public/ directory in rsx/. Resolution
        cached in Redis for performance. Generates tags with filemtime() for
        fresh cache-busting on each page render.

PUBLIC-FACING BUNDLES
    A BUNDLE TAKES ITS AUDIENCE FROM ITS LEAST PRIVILEGED PAGE. Everything a
    bundle includes is downloaded by everybody who can load any page that
    renders it. A bundle rendered by a page that needs no sign-in - a login
    page, signup, password reset, an error page, a client portal's sign-in
    pages - is served to anonymous visitors, whatever else it also serves.

    Such a bundle NEVER includes a shared directory. A directory include of a
    shared tree (the theme, the shared library, the models) publishes
    everything in it: the whole component library, every model's ORM
    definition (columns, enums, relationships) and every controller's route
    and Ajax stubs. Every endpoint stays gated; what is handed over is the map
    of the application - its endpoint surface, its domain model and its
    permission vocabulary - before the visitor has a session.

    A public-facing bundle is a MINIMUM INCLUDE SET, named by hand:

        'include' => [
            // The theme's global stylesheets, and the framework build they
            // configure. The pattern takes the theme directory's OWN
            // stylesheets; its subdirectories are the component library.
            'rsx/theme/variables.scss',
            'rsx/theme/responsive.scss',
            'Bootstrap5_Src_Bundle',
            'rsx/theme/*.scss',

            // Each component the pages render, by FILE, parent first.
            'rsx/theme/components/forms/form_field_abstract.jqhtml',
            'rsx/theme/components/forms/form_field_abstract.js',
            'rsx/theme/components/forms/form_field.jqhtml',
            'rsx/theme/components/forms/form_field.js',

            __DIR__,    // required: it covers the views the bundle serves
        ],

    The rule is "no directory from the SHARED trees", not "no directory": the
    bundle's own module directory is required by the coverage check.

    ADDING A FEATURE TO SUCH A PAGE MEANS ADDING ITS FILES TO THE BUNDLE. A
    component, model or script the page newly uses is not there until it is
    named: the component's template and class (and stylesheet), EVERY PARENT
    of it - the JS base class it extends and the template its
    <Define:X extends="Y"> names - each model its JavaScript reads, and each
    script or npm Asset Bundle it calls.

    How To Find The Set
        1. Scan the module's templates for component tags.
        2. Subtract what Core_Bundle already provides: the framework's own
           components (the form engine, the second-factor and passkey
           controls, Turnstile, the spinner) reach every bundle.
        3. Search the module's own JavaScript for model names.
        4. Include each remaining component by file - never by its directory,
           which usually holds its siblings too - and its parents.
        5. Find the theme's global stylesheets at EVERY depth they live at.
           Do not assume one.
        6. Compile, load every route the bundle serves, and LOOK at it.

    What Is Missing, And How It Fails
        a JS class                 throws when the bundle loads, naming itself
        an extends="" parent       SILENT - the child renders without the
        template                   parent's markup
        a stylesheet               SILENT - a working page that looks wrong
        a component's files        an empty element and a console WARNING
        entirely                   ("Creating X with defaults"), no error
        a model class behind a     throws when the response is unwrapped,
        {__MODEL} response         naming the model (see rsx:man model_fetch)
        a view's directory         throws at render (BUNDLE PLACEMENT)

    A CLEAN CONSOLE IS NOT EVIDENCE. Capture a screenshot of every page before
    narrowing a bundle - each state it can show, in light and dark - and
    compare after. Identical images are conclusive; nothing else catches the
    silent rows.

    The Component Shake Does Not Do This
        A sealed build drops the components a bundle never names (THE
        COMPONENT SHAKE). It drops COMPONENTS ONLY: plain JS classes, model
        and controller stubs and shared stylesheets are always kept, because
        any class may be reached by a boot-phase sweep. It never runs in
        development, which is a mode an application may be served in. The
        include list is the only control over what a bundle publishes.

    Internal Bundles Are Not Held To This
        A bundle whose every page requires a staff sign-in includes whole
        shared directories, and should: an employee reading the JavaScript of
        the application they work in is not a disclosure, and an include list
        that must be edited for every new component is a cost with nothing
        bought. The same holds for the SIGNED-IN bundle of a client portal:
        its users are outside the organisation, but they are identified, and
        the convenience of the wide bundle is worth the small exposure. What
        such a portal owes is a SEPARATE bundle for its sign-in pages, so that
        anonymous visitors do not receive the signed-in one.

    The worked examples are the reference application's sign-in bundle and
    its portal's:
        system/app/RSpade/resource/reference_app/app/login/login_bundle.php
        system/app/RSpade/resource/reference_app/portal/auth/portal_auth_bundle.php
    The recurring audit is an entry in rsx:man prelaunch_checklist.

ROUTE EXTRACTION (include_routes)
    Bundles can extract route definitions from directories without bundling
    their assets. This enables Rsx.Route() calls for controllers outside
    the bundle's include paths.

    SYNTAX
        class Frontend_Bundle extends Rsx_Module_Bundle_Abstract
        {
            public static function define(): array
            {
                return [
                    'include' => [
                        __DIR__,
                    ],
                    'include_routes' => [
                        'rsx/app/login',    // Extract routes only, no assets
                        'rsx/app/admin',
                    ],
                ];
            }
        }

    USE CASE
        The frontend module needs to generate URLs to the login module
        (e.g., logout link) but shouldn't bundle login's JavaScript/CSS.
        Using include_routes extracts route patterns and makes them
        available to Rsx.Route() without including the module's assets.

    HOW IT WORKS
        - Scans directories for PHP files extending Rsx_Controller_Abstract
        - Extracts #[Route] attribute patterns from public static methods
        - Generates Rsx._define_routes() call in compiled bundle
        - Routes become available via Rsx.Route('Controller', 'method')

    EXAMPLE
        // In frontend JavaScript (with login routes extracted)
        const logout_url = Rsx.Route('Login_Controller::logout');
        // Returns: '/logout'

ALWAYS-PUBLISHED ROUTES
    Some route targets are emitted into EVERY bundle's client route table,
    whether or not the bundle includes - or is allowed to include - the code
    that declares them. The list is config, not a bundle declaration:

        // system/config/rsx.php (an app appends in rsx/resource/config/rsx.php;
        // the merge is append-only, so the framework's entries always remain)
        'always_published_routes' => [
            '_Sys_Dashboard_Action',
        ],

    The spelling is the one Rsx::Route() takes: a bare SPA action class name,
    or 'Controller::method' for a PHP route. At compile time the bundle
    compiler resolves each target's patterns out of the manifest - the same
    lookup Rsx::Route() performs server-side - and emits them beside the
    ordinary route table. Their auth grants ship on every page in
    window.rsxapp.auth_routes_published, so Permission.can_access() answers for
    them too, in every bundle, without the opt-in auth_routes export.

    A configured target with no routes in the manifest FAILS THE COMPILE. A
    published entry that silently vanished would leave every page in the
    application linking to a placeholder URL.

    The shipped entry is the /_sys control panel's dashboard. An application
    bundle may never include app/RSpade/Sys (CONV-BUNDLE-02, critical), so the
    published entry is what makes Rsx.Route('_Sys_Dashboard_Action') resolve
    from an application page. See rsx:man sys_panel.

    This is NOT a substitute for include_routes. include_routes is a bundle
    saying "I link to that module of mine"; always_published_routes is the
    framework saying "every bundle links here".

PUBLIC ASSET INCLUDES
    Bundles can include static assets from any public/ directory with
    automatic cache-busting via filemtime().

    SYNTAX
        Prefix paths with /public/ in bundle includes:

            'include' => [
                '/public/sneat/css/core.css',
                '/public/sneat/js/helpers.js',
            ]

    RESOLUTION
        Path "sneat/css/demo.css" resolves to first match across all public/
        directories in manifest. Resolution cached in Redis indefinitely.

        Searches:
            rsx/public/sneat/css/demo.css
            rsx/app/admin/public/sneat/css/demo.css
            rsx/theme/public/sneat/css/demo.css
            ... (all public/ directories)

    OUTPUT
        CSS: <link rel="stylesheet" href="/sneat/css/demo.css?v={filemtime}">
        JS:  <script src="/sneat/js/helpers.js?v={filemtime}" defer></script>

        The filemtime() call executes on each page render, providing fresh
        cache-busting timestamps without rebuilding bundles.

    ORDERING
        Public assets output with CDN includes, before compiled bundle code.
        Order preserved as listed in bundle definition:

            1. CDN CSS assets
            2. Public directory CSS
            3. Compiled bundle CSS
            4. CDN JS assets
            5. Public directory JS
            6. Compiled bundle JS

    AMBIGUITY ERRORS
        If multiple files match the same path, compilation fails:

            Ambiguous public asset request: 'sneat/css/demo.css' exists in
            the public/ directory of more than one module: '_root', 'theme'

        The message names the modules, never absolute paths ('_root' is
        rsx/public/ itself).

        Solution: Use more specific paths or rename files to avoid conflicts.

    CACHING
        - Path resolution cached in Redis indefinitely
        - Cache validated on each use (file existence check)
        - Stale cache automatically re-scanned
        - filemtime() executes on each page render for cache-busting

    RESTRICTIONS
        - Only .js and .css files allowed
        - Must start with /public/ prefix
        - Files must exist in a public/ directory
        - No PHP files allowed (security)

BUNDLE RENDERING
    In Blade layouts/views:
        {!! Dashboard_Bundle::render() !!}

    Generates:
        <link href="/_compiled/Dashboard__vendor.abc123.css" rel="stylesheet">
        <link href="/_compiled/Dashboard__app.def456.css" rel="stylesheet">
        <script src="/_compiled/Dashboard__vendor.abc123.js"></script>
        <script src="/_compiled/Dashboard__app.def456.js"></script>
        <script src="/_field_lengths/Dashboard_Bundle__def456.js?v=<state key>" defer></script>

    The last tag is the bundle's FIELD-LENGTH SCRIPT (below); it is emitted only
    for a bundle whose compiled output carries at least one model.

    Never call from controllers - only from Blade files.

    THE FIELD-LENGTH SCRIPT. A column's max length is a fact about the DATABASE,
    so it is not compiled into a bundle: the framework serves it, per bundle, as
    one line of JavaScript -

        Rsx.__field_length_data = {"Contact_Model": {"first_name": 100, ...}, ...};

    - and Model.field_length('column') reads that object, synchronously. It lists
    exactly the models whose stubs are in the bundle's compiled app script (the
    compiler records them in build/bundle_models/<Bundle>.json, in every mode; a
    sealed build's seal covers that file), each varchar/char column with the PHP
    model's own field_length() answer, single-underscore system columns left out.
    A model whose table is not in the database yet gets an empty entry.

    The URL names the bundle's own app script hash, so the script is exactly as
    reachable as the bundle (any other name is a 404), and carries the STATE key
    as ?v= - it is served immutable for the current key and no-store for any
    other, and the key moves when a migration runs (rsx:man migrations). A
    migration therefore changes what the script answers and changes no bundle.

    A PAGE THAT PRINTS A BUNDLE'S TAGS BY HAND GETS NO FIELD LENGTHS. The tag is
    emitted by render(); a layout that writes its own <script src="/_compiled/...">
    tags instead does not load the script, and Model.field_length() throws there,
    naming the script. Render bundles with render().

    ON-DEMAND COMPILE. In development a request for a /_compiled/ file that is not
    on disk compiles the named bundle first - but only when the name is a concrete
    MODULE bundle (a manifest class extending Rsx_Bundle_Abstract, not abstract, not
    an asset bundle; AssetHandler::_is_on_demand_bundle()). The hash in the filename
    is computed BY the compile, so the requested file is served only if the compile
    produced it; any other name or hash is a 404 and compiles nothing. A compile
    failure propagates as the error it is. Sealed builds never compile on request.

VENDOR/APP SPLIT
    Files automatically split:
    - vendor/: Files containing "vendor/" in path, NPM modules
    - app/: Everything else

    Benefits:
    - Vendor files cached longer (rarely change)
    - App files rebuilt on changes
    - Smaller incremental builds

BUNDLE PROCESSORS
    Transform files during compilation.
    Configured globally in config/rsx.php.

    Built-in processors:
    - Scss_BundleProcessor: .scss -> .css
    - Jqhtml_BundleProcessor: .jqhtml -> JavaScript

    All processors receive ALL collected files,
    decide what to process based on extension.

CREATING A PROCESSOR
    class MyProcessor extends AbstractBundleProcessor
    {
        public static function get_name(): string
        {
            return 'myprocessor';
        }

        public static function get_extensions(): array
        {
            return ['myext'];  // Extensions to process
        }

        public static function process(string $file, array $options = []): ?array
        {
            $content = file_get_contents($file);

            // Transform content
            $processed = transform($content);

            return [
                'content' => $processed,
                'extension' => 'js',  // Output extension
            ];
        }
    }

    Register in config/rsx.php:
        'bundle_processors' => [
            App\RSpade\Processors\MyProcessor::class,
        ],

COMPILATION PROCESS
    1. Resolve all includes to file list
    2. Split into vendor/app buckets
    3. Check cache (skip if unchanged)
    4. Run processors on files
    5. Add JavaScript stubs from manifest
    6. Filter to JS/CSS only
    7. Compile vendor and app separately
    8. In production: concatenate into single files

    In a sealed build (debug, production) one more step runs between 1 and 2: the
    COMPONENT SHAKE, below.

THE COMPONENT SHAKE (sealed builds)
    A bundle includes directories, and a directory brings everything in it. A login
    bundle that includes the theme for its variables and form inputs also receives
    every other component the theme holds, none of which a login page can render. In
    a sealed build that is weight a visitor downloads for nothing, and a list of the
    application's component names handed to somebody who has not signed in.

    So a sealed build removes from each bundle every jqhtml COMPONENT that nothing
    the bundle serves names. Development never does: there every included file is
    in the bundle, as always.

    ONLY COMPONENTS ARE EVER REMOVED. A component is a name the bundle's files define
    as one - a .jqhtml template, or a JS class descended from Component - together
    with the files carrying that name: the template, the class, and the stylesheet
    whose single wrapper class is that name. The three are kept or removed together.
    Every other file is always kept: plain JS classes and functions, model and
    controller stubs, stylesheets that are not one component's own.

    A component is KEPT when its name appears, as a whole word, in:

        - the bundle's own 'keep' list (below);
        - a Blade file served with this bundle - one that prints it, extends a layout
          that prints it, or is included by one that does - or a Blade file served
          with no bundle at all (a partial that could be included anywhere);
        - a JS file in the bundle that is not a component;
        - a quoted string in PHP or config (a component the server chooses: a viewer
          registry, a config value);
        - the template or class of another kept component, and so on to the end.

    and also when its class defines a STATIC METHOD (it may be reached by a sweep
    over every class, with nothing naming it) or carries a @route (an SPA action is
    reached by URL).

    A mention in a comment or a string counts: keeping too much is the safe direction.
    One shape does not count - the name directly after a single period that does not
    itself follow a word character, as in $('.My_Component') or ".My_Component", which
    is a CSS class selector and not a use of the component.

    WHAT IT CANNOT SEE: a name assembled at run time.

        const name = 'Select_' + kind + '_Input';     // named nowhere
        $el.component(name);

    Declare those in the bundle - the one escape hatch:

        return [
            'include' => [...],
            'keep' => ['Select_Country_Input', 'Select_State_Input'],
        ];

    A 'keep' entry that names no component in the bundle is refused at build time.

    A WRONG REMOVAL SHOWS ONLY IN A SEALED BUILD, so reproduce it in debug mode
    (php artisan rsx:mode:set debug). A debug build carries the names it removed and
    registers each as a component that fails on creation with:

        Component X is not in My_Bundle: the sealed build removed it, because nothing
        the bundle serves names it. If it is built from a name assembled at run time,
        list it in My_Bundle::define() under 'keep' and rebuild ...

    A PRODUCTION build carries no such list - the names are what is being withheld -
    so there a removed component renders as an empty element, with the runtime's
    "no template or class defined" console warning and nothing else.

    Reading the decision, in any mode, without building:

        php artisan rsx:bundle:shake:report                 every bundle: counts, sizes,
                                                            the dropped names
        php artisan rsx:bundle:shake:report My_Bundle --kept    each kept component and
                                                            the reason it was kept
        php artisan rsx:bundle:shake:report My_Bundle --why=Some_Component
                                                            its reason, traced back to
                                                            the file that started it
        php artisan rsx:bundle:shake:report --json

    A sealed build also writes each bundle's decision to build/bundle_shake/<Bundle>.json.

    The decision is a function of the bundle's file list and the manifest, so two boxes
    building the same tree remove the same components.

NODE WORK RUNS IN ONE DAEMON, NOT ON COMMAND LINES
    Every node step of a compile runs over ONE persistent RPC service on ONE
    unix socket - babel, jqhtml, minification, SCSS compilation and
    concatenation alike, each a subsystem of it, each loaded on first use. The
    service is spawned on demand, reused, and reaped by rsx:clean and by
    maintenance mode; there is nothing to start and nothing to install. See
    Core/JsParsers/README.md for the architecture and the full roster.

    THE RULE THAT PRODUCED IT: a request that grows with the size of the
    application must never travel as command-line arguments. Linux caps a
    SINGLE argument at MAX_ARG_STRLEN (32 pages = 131072 bytes) - not the
    getconf ARG_MAX total, not raised by ulimit - and the cap behaves as a
    cliff: one byte under builds, one byte over fails every build from then on.
    Concatenation used to name every bundled file on one command line and hit
    that ceiling in a large application at ~1,300 JavaScript files, taking every
    route to a 500 and blaming the file whose addition tipped it over. The file
    list now travels in a socket payload, which has no such ceiling.

    exec_safe() refuses an over-limit command with a legible message naming the
    byte count and the limit. That is a diagnosis aid for whatever is left, not
    permission to build long argument lists.

JAVASCRIPT STUBS
    Controllers with Ajax_Endpoint methods get stubs:
        // Automatically included in bundles
        class User_Controller {
            static async get_profile(...args) {
                return Ajax.call(Rsx.Route('User_Controller', 'get_profile'), args);
            }
        }

    Note: Rsx.Route() generates type-safe URLs like /_ajax/User_Controller/get_profile

    Models with fetch() methods get stubs:
        class User_Model {
            static async fetch(id) {
                return Ajax.model_fetch('User_Model', id);
            }
        }

    A stub is generated from the model's CODE alone - enums, relationships,
    declared text types, derived properties. It carries no column lengths:
    field_length() is one inherited method that reads the page's field-length
    script (BUNDLE RENDERING, above).

    A MODEL STUB FOLLOWS THE CLASS THAT EXTENDS IT. A generated model stub is
    emitted at the include position of the PHP model file, AND behind every JS
    model class in the bundle that extends it - a hand-written X_Model.js
    declares `extends Base_X_Model`, and that clause is what pulls Base_X_Model
    in. This matters because a JS model class reaches a bundle by CLASS
    REFERENCE from anything that names it (a framework core component naming
    File_Attachment_Model reaches every bundle), which the bundle's include list
    never mentions. So a model's client-side layer is complete wherever its
    class is used - in a login bundle that includes no models directory, and in
    a framework-owned bundle that by convention includes no rsx/ path at all -
    and it does not matter WHERE the PHP model file lives, an overridden model
    sitting in rsx/models included. Without this the bundle evaluates
    `class X_Model extends Base_X_Model` against an undefined base and throws an
    uncaught ReferenceError during bundle evaluation, which aborts the script:
    no client component in that bundle boots.

CONFIGURATION
    Bundle config added to window.rsxapp:
        'config' => [
            'feature_flags' => ['new_ui'],
            'api_version' => '2.0',
        ]

    Access in JavaScript:
        if (window.rsxapp.config.feature_flags.includes('new_ui')) {
            // New UI code
        }

    'config' is for STATIC values only. The config block is also baked into
    the compiled JavaScript artifact at compile time, so a dynamic per-request
    value placed there would exist in two copies with one stale. For
    request-time lookups, use the load_rsxapp_data() hook below.

LOAD_RSXAPP_DATA HOOK
    A bundle may declare an optional public static load_rsxapp_data() method.
    If present on the bundle class being rendered, the framework calls it just
    prior to generating the bundle HTML and merges the returned key/value
    pairs into PageData, so they are printed inside window.rsxapp.page_data:

        class Frontend_Bundle extends Rsx_Module_Bundle_Abstract
        {
            public static function define(): array { ... }

            public static function load_rsxapp_data(): array
            {
                if (!Session::is_logged_in()) {
                    return [];
                }

                return [
                    'unread_notification_count' =>
                        Notification_Model::where('user_id', Session::get_user_id())
                            ->where('is_read', false)
                            ->count(),
                ];
            }
        }

    Access in JavaScript:
        const count = window.rsxapp.page_data.unread_notification_count;

    This is the sanctioned channel for shipping request-time data with the
    initial page load - for example, an unread-notification count the header
    widget can paint immediately instead of waiting on an Ajax round trip.

    Contract:
    - The method MUST return an array (empty array is fine). Any other
      return type throws.
    - It runs on every full page load, after dispatch - Session (or
      Portal_Session on portal pages) is fully established, so auth checks
      and user-scoped queries work normally.
    - Only the RENDERED bundle's method is called (the Module Bundle whose
      render() the layout invokes). load_rsxapp_data() on included or
      auto-discovered bundles is NOT called.
    - Returned pairs merge into window.rsxapp.page_data alongside any values
      added via PageData::add() / @rsx_page_data during the request; on a key
      collision the later add wins.
    - SPA navigations do not re-render the bundle, so this is boot-time data.
      A widget needing live values afterward still refreshes via Ajax or a
      realtime subscription; the hook only seeds the first paint.
    - The hook blocks page render - keep lookups cheap (indexed counts,
      cached values). Do not put heavy queries here.
    - On an FPC-cached route the printed value is cached with the page like
      all rsxapp data; do not return per-user data on FPC routes.

WATCH TARGETS
    The 'watch' key declares CACHE-INVALIDATION INPUTS: files that can change a
    compiled artifact without being compiled into it. The canonical case is a
    vendored SCSS entry point in 'include' that @imports a first-party partial
    which is not itself an include.

        class Bootstrap5_Src_Bundle extends Rsx_Asset_Bundle_Abstract {
            public static function define(): array {
                return [
                    'include' => ['rsx/theme/vendor/bootstrap_custom.scss'],
                    'watch' => [
                        'rsx/theme/vendor/bootstrap5/scss',  // Directory
                        'rsx/theme/variables.scss',          // File
                    ],
                ];
            }
        }

    ACCEPTED PATHS
        A watch entry takes the same kinds of path as an include entry: an
        existing FILE or an existing DIRECTORY, relative to base_path(). A
        directory is scanned recursively (honouring config
        rsx.manifest.excluded_dirs); a file is registered directly.

        A watch entry is NEVER compiled into any artifact. It contributes only
        its content hash to the cache key.

    MUST EXIST - FAIL LOUD
        A target that is neither an existing file nor an existing directory
        throws a RuntimeException naming the declaring bundle class and the
        path. A typo, or a path deleted since the definition was written, is a
        build failure and not a silent no-op:

            Bundle 'watch' target does not exist.

            Bundle: Rsx\Theme\Bootstrap5_Src_Bundle
            Watch target: rsx/theme/varables.scss
            ...

        Rationale: a watch list that silently watches nothing is
        indistinguishable from a correct one from the build output. The bundle
        compiles, reports success, and serves a stale artifact.

    BUCKET MEMBERSHIP FOLLOWS THE DECLARING BUNDLE
        Each artifact is cached per bucket ('vendor' / 'app') and keyed on
        bundle_files[bucket] + watch_files[bucket]. A watch target is registered
        under the bucket(s) the DECLARING BUNDLE contributes compiled files to -
        never inferred from the watched path.

        So a watch target of a vendor-bucket bundle invalidates the VENDOR
        artifact no matter where the watched file lives. This is what makes the
        normal shape of "compile a third-party source tree, parameterised by
        first-party configuration" work: the knobs deliberately live in
        application space while the vendor tree stays pristine.

        A bundle that contributes no compiled files of its own (watch-only,
        cdn-only, or a module bundle whose includes are all sub-bundles)
        registers its watch targets into BOTH buckets. Over-invalidation costs a
        rebuild; under-invalidation is a stale artifact.

        REGISTRATION IS ADDITIVE. One path may be a watch target of one bucket
        and a direct include of the other at the same time; both facts are kept
        and one edit invalidates both artifacts. A path is never moved between
        buckets, and the same path appearing in both is a correct state.

        The asymmetry with 'include' is deliberate. An include entry IS the
        bytes of exactly one artifact, so its bucket is a property of the file's
        own path. A watch entry feeds an artifact it is not part of, so its
        bucket is a property of the bundle that declared it. (Include entries
        must stay path-derived: a module bundle's include is normally a
        directory scan sweeping first-party sources and vendored trees in one
        pass - rsx/theme contains rsx/theme/vendor/ - so attributing every
        scanned file to the declaring bundle would drain the vendor bucket.)

CACHING
    Development:
        - Vendor files cached until dependencies change
        - App files rebuilt on any change
        - Cache keys based on file hashes, per bucket, over
          bundle_files[bucket] + watch_files[bucket] (see WATCH TARGETS)

    Production:
        - All files concatenated and minified
        - Cache forever with hash in filename
        - Rebuild only via rsx:bundle:compile

EXAMPLES
    // Kitchen sink bundle
    class App_Bundle extends Rsx_Bundle_Abstract
    {
        public static function define(): array
        {
            return [
                'include' => [
                    // Required modules
                    'jquery',
                    'lodash',
                    'bootstrap5',

                    // Other bundles
                    'Core_Bundle',

                    // Application code
                    'rsx/app',
                    'rsx/lib',

                    // Specific overrides
                    'rsx/theme/variables.scss',

                    // NPM packages
                    'npm:axios',
                    'npm:chart.js',
                ],
                'config' => [
                    'app_name' => 'MyApp',
                    'version' => '1.0.0',
                ],
            ];
        }
    }

    // Module-specific bundle
    class Admin_Bundle extends Rsx_Bundle_Abstract
    {
        public static function define(): array
        {
            return [
                'include' => [
                    __DIR__,  // Include bundle's directory
                    'rsx/lib/admin',
                ],
            ];
        }
    }

    Framework detects and prevents circular includes:

TROUBLESHOOTING
    A component renders as an empty element in debug or production only:
        The component shake removed it (THE COMPONENT SHAKE above). Switch to debug
        mode, where creating it names the cause; add it to the bundle's 'keep'.
        php artisan rsx:bundle:shake:report My_Bundle --why=The_Component

    Bundle not updating:
        php artisan rsx:bundle:compile My_Bundle --clean

    Missing files:
        Check paths are relative to project root.
        Verify files exist in manifest.

    "Bundle include pattern is not one of the accepted forms":
        An include entry contains '*' and is neither '<directory>/*.<ext>'
        nor '<directory>/**/*.<ext>'. See INCLUDE TYPES.

    "Bundle include pattern matches no files":
        The directory holds no file of that type at the depth the form
        covers. '*.scss' does not descend; '**/*.scss' does.

    A page on a hand-listed bundle looks wrong with a clean console:
        A stylesheet or an extends="" parent template is missing from the
        include list. Neither is an error. See PUBLIC-FACING BUNDLES.

    Processor not running:
        Check processor registered in config.
        Verify file extension matches.
