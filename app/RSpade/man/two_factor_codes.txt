TWO_FACTOR_CODES(1)              RSpade Manual              TWO_FACTOR_CODES(1)

NAME
    two_factor_codes - emailed six-digit sign-in codes and their sign-in
    links: the recipe, for staff and the client portal

SYNOPSIS
    # 1. The login function: the password passed, and this sign-in owes a code
    Rsx_Two_Factor::begin_challenge($login_user, [
        Rsx_Two_Factor::ANSWER_ISSUED_CODE,     // an emailed code
        Rsx_Two_Factor::ANSWER_PASSKEY,         // or any factor the user holds
        Rsx_Two_Factor::ANSWER_TOTP,
        Rsx_Two_Factor::ANSWER_RECOVERY_CODE,
    ]);
    return redirect(Rsx::Route('Login_Controller::verify'));

    # 2. The send endpoint - mint a code and its link, deliver both in one email
    #[Ajax_Endpoint]
    public static function send_code(Request $request, array $params = [])
    {
        $code = Rsx_Two_Factor::issue_code();
        $link = Rsx_Two_Factor::issued_link(Rsx::Route('Login_Controller::verify'));
        (new Sign_In_Code_Email($code, $link))->to(Rsx_Two_Factor::pending_identity()->email)->send();
        return null;
    }

    # 3. The email - SECURITY reaches a block-listed address, ignores opt-out
    class Sign_In_Code_Email extends Rsx_Email_Abstract { const CATEGORY = self::SECURITY; ... }

    # 4. The screen
    <Two_Factor_Challenge $controller="Login_Controller" $method="verify_2fa"
                          $send_controller="Login_Controller" $send_method="send_code" />

    # 5. The verification endpoint - unchanged from any other challenge; the
    #    screen posts {code} or, from the link, {email_link}
    $login_user = Rsx_Two_Factor::verify_challenge($params);

DESCRIPTION
    An emailed sign-in code is a second step that needs nothing enrolled:
    the user typed their password, the site emails six digits - and a link
    - to the account's address, and typing the digits or opening the link
    in the same browser completes the sign-in. It is how a
    site requires a second step of EVERYBODY - every client on a portal, say
    - without asking each of them to install an authenticator app first.

    It is not a framework feature that an application switches on. It is a
    policy the application writes, from primitives the framework owns:

        THE FRAMEWORK (Rsx_Two_Factor / Rsx_Portal_Two_Factor)
            mints the code (random_int), keeps ONE live code per identity
            (encrypted, beside the identity's failure budget), re-sends those
            same digits on a resend until the code expires, mints the
            browser-bound link that travels with them and serves the page it
            opens, verifies either answer under the login throttle and the
            two attempt caps, records the outcome, marks the address
            verified, and signs the identity in. It enforces which kinds of
            answer a challenge accepts.

        THE APPLICATION
            decides which sign-ins owe a code, which other answers it will
            take instead, delivers the code (its own email class, an SMS,
            anything), words it, and caps how many it will send.

    Nothing in the framework asks whether a site uses emailed codes, so
    nothing can make a site use them, and every variation - codes for the
    portal only, codes only for users without an authenticator, a
    remember-this-device cookie - is a change to the application's own login
    function and nothing else.

    WHO IT SUITS. An emailed code proves the person at the keyboard can read
    the account's mailbox. That is weaker than an authenticator app or a
    passkey - the mailbox is also where a password reset goes - and much
    stronger than a password alone. Offer a passkey beside it and a user who
    registers one never waits for an email again (PASSKEYS SKIP IT).

THE FLOW
    1. The login function verifies the password, exactly as for any second
       factor (rsx:man two_factor, THE SECOND-FACTOR LOGIN FLOW): nothing
       recorded, nothing stamped.
    2. It decides the sign-in owes a code and calls
       begin_challenge($identity, $accepts) with ANSWER_ISSUED_CODE in the
       list. The identity is parked; the session is SIGNED OUT.
    3. It redirects to the challenge page, which renders
       <Two_Factor_Challenge> with a send endpoint.
    4. The component sees the challenge accepts an issued code and none has
       been issued, and calls the send endpoint itself. The endpoint calls
       issue_code() and emails the digits to pending_identity().
    5. The user types the code - or opens the link from the email in the
       same browser, which lands back on this page and posts the link's
       token for them (THE EMAIL LINK). The component posts the answer to
       the verification endpoint, which calls verify_challenge() - the same
       call as for a TOTP code - and answers {redirect}.
    6. "Resend code" calls the send endpoint again. While the code is live,
       issue_code() returns the SAME digits, so every message the user holds
       carries the one code that works; after it expires the next send mints
       a new one (LIFETIME).

WHAT A CHALLENGE ACCEPTS
    begin_challenge()'s $accepts is the policy, enforced:

        ANSWER_ISSUED_CODE     the identity's live code from issue_code()
        ANSWER_TOTP            an authenticator app code
        ANSWER_PASSKEY         one of the identity's passkeys
        ANSWER_RECOVERY_CODE   an unspent recovery code

    verify_challenge() tries only the accepted kinds, and an answer of
    another kind is a WRONG answer even when it is correct. Listing a factor
    the identity does not hold is harmless (it is simply not offered); a list
    the identity cannot answer at all throws before the sign-out, and an
    issued code is always answerable.

    Common shapes:

        everybody gets a code, and may use a factor they hold instead
            [ISSUED_CODE, TOTP, PASSKEY, RECOVERY_CODE]

        a code only for identities with no factor of their own
            Rsx_Two_Factor::is_enabled($identity)
                ? null                                  // their factors
                : [Rsx_Two_Factor::ANSWER_ISSUED_CODE]  // an emailed code

        a code and nothing else
            [ISSUED_CODE]

THE SEND ENDPOINT
    The application's. Public (#[Auth('public')]), because the session is
    deliberately signed out between the password and the code. It acts only
    on the challenge parked on the caller's own session, and the address is
    the pending identity's own, read server-side - nothing the browser sends
    chooses where a code goes.

        #[Ajax_Endpoint]
        public static function send_code(Request $request, array $params = [])
        {
            $pending = Rsx_Portal_Two_Factor::challenge_pending();
            $portal_user = Rsx_Portal_Two_Factor::pending_identity();

            if ($pending === null || $portal_user === null) {
                return response_error(Ajax::ERROR_VALIDATION, 'Your verification window has expired. Please sign in again.');
            }

            if ($pending['codes_issued'] >= 5) {
                return response_error(Ajax::ERROR_VALIDATION, 'Too many codes have been sent. Please sign in again.');
            }

            $code = Rsx_Portal_Two_Factor::issue_code();
            $link = Rsx_Portal_Two_Factor::issued_link(Rsx_Portal::Route('Portal_Login_Controller::verify'));
            (new Portal_Sign_In_Code_Email($portal_user, $code, $link))
                ->to($portal_user->email)->send();

            return null;
        }

    THE RESEND CAP IS THE APPLICATION'S. Guessing is bounded by the
    framework's attempt caps (rsx.two_factor.challenge_max_failures wrong
    answers per challenge, identity_max_failures per identity) whatever the
    resend count; a resend cap only keeps one sign-in from mailing an inbox
    without limit. challenge_pending()['codes_issued'] is the count, and it
    counts SENDS: a resend that re-sends the live code still counts.

    ONE MESSAGE FOR EVERY SEND. A resend carries the same code and the same
    link, and every issue_code() restarts their clock (and the challenge's),
    so the email needs no "here it is again" variant: it is word for word the
    original and states the configured window,
    rsx.two_factor.challenge_window_minutes, true of every copy.
    issued_code_expires_at() still answers when the live code stops working,
    or null when it has none.

    A user-safe rejection renders inline on the challenge screen.

THE EMAIL
    One class in rsx/emails/, like any email (rsx:man email), declared
    CATEGORY = SECURITY:

        class Portal_Sign_In_Code_Email extends Rsx_Email_Abstract
        {
            const CATEGORY = self::SECURITY;

            public function __construct(
                public Portal_User_Model $portal_user,
                public string $code,
                public string $link
            ) {}

            public function subject(): string { return 'Your sign-in code: ' . $this->code; }

            public function data(): array
            {
                return [
                    'code' => $this->code,
                    'link' => $this->link,      // after the code; it works in this browser only
                    'expiry_minutes' => max(1, (int) config('rsx.two_factor.challenge_window_minutes')),
                ];
            }

            public static function sample(): static { ... }
        }

    WHY SECURITY. The site block list stops correspondence the SITE starts;
    the recipient opt-out records what a recipient no longer wants. Neither
    describes a code the recipient asked for a second ago, without which
    they cannot reach their own account - so a SECURITY email passes both,
    and carries no unsubscribe link. The dev-site recipient gate and
    rsx.mail.delivery still apply.

    THE CODE IS IN THE QUEUE ROW. data() is frozen into _email_queue for as
    long as the row is retained. That is acceptable for a code that dies
    within minutes - and the link dies with it; never put a long-lived
    secret in an email's data().

THE EMAIL LINK
    issued_link($return_url) answers the link that goes in the same message
    as the code. The two are one answer delivered twice: the link answers
    the challenge as ANSWER_ISSUED_CODE, a correct answer of either kind
    consumes both, and the link stops working the moment the code does.

    THE CONTRACT
        call it after issue_code(), in the same send   with no live code it
                                                       throws - a link nobody
                                                       was sent a code with
                                                       would be a second,
                                                       unannounced secret
        $return_url                                    the challenge page
                                                       (Rsx::Route() /
                                                       Rsx_Portal::Route()),
                                                       no fragment
        a resend                                       the same link (it is
                                                       derived from the
                                                       challenge and the code;
                                                       the first $return_url
                                                       is kept)
        a fresh sign-in                                a new link for the new
                                                       challenge

    The URL is absolute, on the realm's own host (the portal's under its
    prefix), and signed for that host (Rsx_Signed_Url), so a staff link is
    refused on the portal's host and the reverse.

    BOUND TO THE BROWSER THAT SIGNED IN. The link belongs to the challenge
    parked on the browser that typed the password. The route /_email_link/
    :token answers:

        that browser           a redirect to $return_url with the token in
                               the fragment (#rsx_email_link=...), where
                               <Two_Factor_Challenge> posts it as
                               {email_link} to the verification endpoint -
                               no change to the endpoint, which hands
                               $params to verify_challenge() as always
        any other browser      a notice (409): "This sign-in was started in a
                               different browser. Enter the 6-digit code from
                               the email in the browser where you signed
                               in." Not an attempt; the code stays live
        expired, used, forged  a notice (410): "This link has expired or was
                               already used. Sign in again."

    Both notices are the error-page funnel (rsx:man error_pages), so an
    application's /error/generic page dresses them; they carry
    Referrer-Policy: no-referrer and Cache-Control: no-store.

    WHY OTHER BROWSERS ARE REFUSED. A link that signed in whatever browser
    opened it would sign in whoever reads the mailbox, from anywhere, with
    no password - the password typed a moment ago would protect nothing.
    Bound to the browser that proved the password, the link is exactly as
    strong as the code: the password AND the mailbox. On a phone reading
    the mail of a desktop sign-in, the code is the way through, and the
    notice says so.

    MAIL SCANNERS. Security gateways and link previewers fetch every URL in
    a message before the recipient sees it. The route only READS: nothing
    is consumed, counted or signed in by a GET. The answer is an ordinary
    Ajax POST from the challenge page, under the CSRF check, the throttle
    and the attempt caps - and the token reaches it in the fragment, which
    a browser never sends to a server, so it appears in no access log after
    the first request.

    A WRONG OR DEAD LINK posted as {email_link} - one minted for another
    challenge, or whose code was replaced - is a wrong answer, counted like
    a wrong code.

    OTHER TABS. The challenge screen left open where the password was typed
    swaps itself for "You have signed in using the email link." and
    Continue when the link completes the sign-in in another tab of the same
    browser (rsx:man two_factor, <Two_Factor_Challenge>). Nothing to wire;
    the host's challenge page need only send a signed-in visitor onward.

    STORAGE. Nothing secret is stored. The token is an HMAC (under a key
    derived from app.key) of the challenge and the code's expiry; the
    store keeps its SHA-256 bound to {challenge, browser session, identity,
    code expiry, return URL}, beside the code, expiring with the code.

A PASSED EMAILED ANSWER VERIFIES THE ADDRESS
    When an issued code - typed, or its link - answers a challenge,
    verify_challenge() sets is_verified = 1 on the identity (login_users for
    staff, portal_users for the portal) before the realm signs it in. The
    answer proved the person at the keyboard reads that mailbox, which is
    all is_verified records. Consequences:

        an emailed code doubles as address verification, so a signup flow
        can verify by challenge (begin_challenge($identity,
        [ANSWER_ISSUED_CODE])) with nothing of its own - the reference
        application's self-signup does exactly that, switched off as shipped
        (system/app/RSpade/resource/reference_app/app/login/signup/)

        a portal user with is_verified = 0 is admitted by can_login() on the
        strength of the very answer that verified them - provided the
        application's own login function let them reach the challenge

        the address stays verified even when the realm then refuses the
        sign-in (no enabled membership, an inactive account): the mailbox
        was proved either way


DELIVERY MUST BE LIVE
    rsx.mail.delivery defaults to 'suppressed': every message is rendered and
    recorded, Status Suppressed, and NOTHING LEAVES. That is what a fresh
    install needs - and it means a site requiring emailed codes with delivery
    suppressed is a site nobody can sign in to. Before switching emailed codes
    on anywhere a real person signs in, set delivery to 'live' and prove it
    with rsx:mail:test. During development the code can be read from the
    /_sys mail history, or from the dev catcher with delivery 'aiosmtpd'.

    That is why the reference application ships the feature switched OFF.

    And a deploy-time decision does not survive mail breaking, or being switched off,
    AFTER the feature is on. The login function asks, every time:

        if (!Rsx_Mail::deliverable_to($identity->email, Rsx_Mail::SECURITY)) {
            // nobody would receive the code: degrade (skip the step, or offer
            // another factor) rather than lock the account
        }

    deliverable_to() answers for the delivery mode (live or the development catcher), the
    block list and the opt-out together, with SECURITY's exemptions (rsx:man email, WILL IT ARRIVE?).
    Skipping the step or refusing the sign-in is the application's policy.

PASSKEYS SKIP IT
    A passwordless passkey sign-in (verify_passkey_login(), rsx:man
    two_factor, PASSWORDLESS SIGN-IN) owes nothing further - the passkey is
    two factors on its own. So a site that requires emailed codes and also
    offers <Passkey_Sign_In> and <Passkey_Register> lets any user trade the
    email for a passkey, by their own choice, with no application code
    deciding it.

FEDERATED SIGN-IN
    A Google or Microsoft sign-in reaches the same challenge only if the
    application says so: the framework drives that ceremony, so it asks the
    sso.two_factor.accepts resolve hook (portal.sso.two_factor.accepts on the
    portal). Return the same $accepts the password login computes - from the
    same function, so the two doors cannot drift - or null for the default
    (rsx:man sso).

THE CLIENT PORTAL
    Identical, on Rsx_Portal_Two_Factor and Portal_Session, with a portal
    route for the challenge page. The two realms' challenges are separate
    session values: a staff challenge and a portal challenge pending in one
    browser never see each other.

THE REFERENCE IMPLEMENTATION
    The reference application implements this for the portal, behind
    rsx.portal.emailed_sign_in_codes in rsx/resource/config/rsx.php (OFF):

        rsx/portal/auth/Portal_Login_Controller.php
            challenge_accepts() - the policy, in one place; index() - the
            password stage; send_code() - issue and email, capped at
            MAX_CODES_PER_SIGN_IN
        rsx/portal/auth/portal_login_verify.blade.php
            <Two_Factor_Challenge> with the send endpoint
        rsx/emails/portal_sign_in_code_email.php (+ .blade.php)
            the SECURITY email
        rsx/handlers/Portal_Sso_Handlers.php
            portal.sso.two_factor.accepts, asking challenge_accepts()

    Downstream these are at system/app/RSpade/resource/reference_app/. The
    staff login is the same code against Rsx_Two_Factor.

TRUSTING THE BROWSER
    A site that emails a code on every sign-in can let a browser that passed
    one skip the next for a while: set the realm's
    rsx.two_factor.trusted_device_days, call trust_this_device() in the verify
    endpoint after verify_challenge(), and ask device_is_trusted() in the
    login function before begin_challenge(). Off by default, per realm, and
    entirely the application's call (rsx:man two_factor, TRUSTED BROWSERS).

LIFETIME
    A code belongs to the IDENTITY, not to the challenge or the browser, and
    lives rsx.two_factor.challenge_window_minutes (15) from its LAST issue:

        a resend while it lives        the same digits and the same link, with a
                                       full window again (the pending challenge
                                       too); the wrong-answer caps do not reset
        a new sign-in, another browser the same digits (a fresh session cannot
                                       mint a parallel code)
        after it expires               the next issue_code() mints a new one
        a correct answer               consumes it, and its link (any accepted
                                       answer - the sign-in it was sent for
                                       is over)
        the link opened by a GET       nothing: the route only reads
        a spent challenge, or the      destroys it; the next sign-in mints new
        identity locked
        Cancel (abandon_challenge())   leaves it: another browser of the same
                                       identity may be answering it

    So a resend can never keep a code alive past its first fifteen minutes,
    and nothing but its expiry or its use retires it. The challenge has its
    own window of the same length from the password, and both are SECURITY
    windows, not timeouts - they bound how long a proven password and a
    delivered code stay redeemable, and expiry is a working outcome ("Your
    verification window has expired. Please sign in again.").

    STORAGE. The code is kept in the transient-counter store (Redis, beside
    the identity's failure count), ENCRYPTED with the application key - not
    hashed, because re-sending the same digits means reading them back. A
    copy of the store alone does not reveal a code without app.key. What
    this gives up against a keyed hash is the case of an attacker holding
    the application key and live read access to the store at once; that
    exposure is bounded by the code's absolute life, and the password it
    would complete still has to be known. The session's challenge holds
    only which identity is pending and how many codes were sent.

RSX VS LARAVEL
    Laravel: Fortify ships TOTP only; an emailed code is a hand-written
    notification, a code column or cache key, a verify route, and a
    throttle the author must remember to add - each app re-solving storage,
    expiry and brute-force protection.
    RSX: the code, its encrypted storage, its expiry, its attempt caps and the
    sign-in belong to the challenge every second factor already uses; the
    application writes only its policy (begin_challenge's $accepts), one send
    endpoint and one email class.

TROUBLESHOOTING
    "...does not accept an issued code"
        issue_code() was called for a challenge begun without
        ANSWER_ISSUED_CODE in $accepts - the login function and the send
        endpoint disagree about the policy. Compute $accepts in one function.

    No email arrives
        rsx.mail.delivery is not 'live' (DELIVERY MUST BE LIVE), or the
        recipient is outside the .dev. whitelist on a development host. The
        queue row in /_sys says which.

    The link says "This sign-in was started in a different browser."
        It was opened somewhere other than the browser that typed the
        password - a phone, another browser, a private window. Type the code
        from the same email in the browser that signed in; the visit spent
        nothing.

    "...issued_link() was called with no live issued code"
        The send endpoint asked for the link before issue_code(). Issue the
        code first, then the link, and put both in one message.

    "That code is not valid." for a code just received
        The code expired (LIFETIME - fifteen minutes from the FIRST send, not
        the latest), or it was destroyed by a spent challenge or a locked
        identity; a send after that mints a new one, and older messages
        carry the dead code.
