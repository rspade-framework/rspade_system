NAME
       task_commands - giving a #[Task] its own artisan command with #[Command]

SYNOPSIS
       #[Task('<task description>')]
       #[Command('<prefix:name>', '<command description>')]
       public static function do_work(Task_Instance $task, array $params = []) { }

       php artisan <prefix:name> [--key=value ...] [-q]

DESCRIPTION
       An application does not write artisan command classes. It writes tasks, and
       annotates the ones that deserve a name:

           #[Task('Import the nightly vendor feed')]
           #[Command('myapp:import', 'Import the nightly vendor feed')]
           public static function import(Task_Instance $task, array $params = [])
           {
               $task->status('Fetching');
               $rows = Vendor_Feed::fetch($params['since'] ?? null);
               $task->status('Importing');
               $task->stdout(count($rows) . ' rows');
               return null;
           }

       That declaration IS the command. There is no class to write, no file to place, no
       Kernel to edit, and no registration call anywhere in the application. The manifest
       discovers the attribute at build time; the framework registers one thin command per
       declaration at console boot.

           $ php artisan myapp:import --since=2026-08-01
           Fetching                                                   <- stderr
           Importing                                                  <- stderr
           1500 rows                                                  <- stdout
           $ echo $?
           0

       A command declared this way is EXACTLY

           php artisan rsx:task:run <Service> <method> [--key=value ...]

       under a friendlier name: the same argv parsing, the same output contract, the same
       exit codes, the same code path. Nothing about how a task behaves changes because it
       acquired a name, and a task never learns that it has one.

       An application therefore has one way to write CLI-invocable work, not two. Anything
       reachable from cron, from a deploy script or from an operator's shell is a #[Task],
       which means it is also dispatchable in the background, schedulable with #[Schedule],
       and recorded as a run like every other: a console run is an INLINE run with its own
       _tasks row (Task_Run_Model), its reports and its output, visible in /_sys/tasks.

THE ATTRIBUTE
       #[Command(string $name, string $description)]

       $name         The artisan command name. MUST contain a 'prefix:name' segment and
                     MUST NOT begin 'rsx:'. Both halves are non-empty.
       $description  The line `php artisan list` prints beside the command. Required.

       Named arguments work: #[Command(name: 'myapp:import', description: 'Import')].

       #[Command] is meaningful ONLY on a method that also carries #[Task]. It may be
       repeated to give one task two names, though there is rarely a reason to.

       Attributes here are reflection-only: never define a Command attribute class.

WHAT IS REGISTERED
       One Task_Alias_Command per declaration - Task_Run_Command with the service and the
       method already decided. Its signature is the bare name, plus the same free-form
       --key=value argv parsing rsx:task:run has, so every option an invocation passes
       arrives in the task's $params (--user and --site too: only rsx:task:run reads those
       as who the run acts as - ACTING AS A USER). Laravel's own built-ins (--help, --quiet, --verbose,
       --version, --ansi, --no-ansi, --no-interaction, --env) and the maintenance gate's
       --force never do. A JSON value is decoded: --data='{"a":1}' arrives as an array. A
       bare --flag arrives as boolean true.

       The command appears in `php artisan list` under its own prefix, with its
       description, and in `php artisan rsx:task:list` in the COMMAND column beside the
       task that declares it ('-' for a task that declares none).

OUTPUT CONTRACT
       Shared verbatim with rsx:task:run.

       STDOUT is the task's stdout: every $task->stdout() line and everything the task
       echoes or prints, written live. Nothing else is ever written there - no banner, no
       envelope, no summary. A task whose output is meant to be piped writes exactly that
       to stdout.

       STDERR is the task's stderr: every $task->stderr() line, every CHANGED status()
       (one line each, as the status text), and the "Task failed: <error>" line of a run
       that fails, written live and flushed immediately. Operator lines (a stop or kill
       performed on the run) are recorded on the run but never echoed to the command's
       stderr.

       EXIT CODE is the run's return code (rsx:man tasks, THE RETURN CONTRACT): 0 when the
       task returned null, true or 0; the integer it returned for a failure, clamped to
       1..255 (a negative or oversized code exits 1); 1 for false, any other return value,
       or a throw. A task that THROWS prints its failure line to stderr and exits 1; the
       exception is recorded on the run's error.

       WHILE THE TASK SYSTEM IS OFF (php artisan rsx:tasks:disable; rsx:man tasks, TURNING
       THE TASK SYSTEM OFF AND ON) a command does not run and does not fail: its run is
       queued, one line on stderr says it is waiting for `php artisan rsx:tasks:enable`,
       and it waits - with no limit - until the system is back on. It then runs and exits
       with its code as above. A command ended while it waits leaves its run queued for a
       worker; a run cancelled from the queue, or killed under the worker that ran it,
       exits 1.

           php artisan myapp:import | wc -l          # stdout to the pipe, stderr to the
                                                     # terminal
           php artisan myapp:import 2>/dev/null      # discard stderr
           php artisan myapp:import -q               # stderr is never produced
           php artisan myapp:import 2>&1 | tee log   # both, interleaved

       -q / --quiet silences stderr and NEVER stdout.

       Everything a console run writes is ALSO recorded on its run, exactly as a worker
       run's would be: the _task_output lines (stdout, stderr), the reports, the summary.
       A console transcript and the run's output in /_sys read the same.

       THE STREAMS ARE THE RUNNER'S, NOT THE TASK'S. The command attaches its stdout and
       stderr through Task::internal()'s fourth argument, and nothing else does.
       Application code calling Task::internal() from a web request or from another task
       passes three arguments and prints to nobody's console; a queued or scheduled run
       writes its lines to the database only. A task's own code cannot tell the
       difference and must not try to.

       A console run executes in the command's VIRTUAL session (rsx:man session): it acts
       as nobody until somebody is declared - rsx:task:run's --user (ACTING AS A USER), or
       the task itself (Session::set_login_user_id(), set_site_id()) - get_session_id() and
       get_audit_session_id() answer null, and session values throw. A task's writes
       therefore record no audit session.

       A #[Command] run is an inline run, so #[Exclusive]/#[Debounce] hold: a
       single-instance task waits for a running instance of its identity to finish before
       it starts. Being inline, it is never killed for time: the silence limit applies
       only to runs a pool worker executes (rsx:man tasks THE SILENCE LIMIT).

ACTING AS A USER
       php artisan rsx:task:run <Service> <method> --user=<id|email> [--site=<id>] [...]

       rsx:task:run (never an alias) takes the two flags rsx:ajax takes, with the same
       meaning - one resolution serves both (Rsx_Cli_Actor), so they cannot drift:

       --user  a login identity: its login_users id, or its email address. Must exist.
       --site  a site id. Must exist. With --user, REQUIRED when the identity has users
               rows on several sites (or on none); with exactly one, that site is used.

       A disabled membership or site (User_Model::is_active()) is refused before anything
       runs, exit 1, as a sign-in and a #[Run_As_Dispatcher] worker refuse it.

       Before the task runs, Session::impersonate() declares the site, the login identity
       and its users row on that site (null when it has none there). No sign-in is
       created: get_session_id(), get_user_session_id() and get_audit_session_id() stay
       null. The run's dispatched_by names the user, and its writes, revisions and
       created_by/updated_by pairs are attributed to them. --site alone declares a site
       and nobody acting on it. Neither flag ever reaches the task's $params.

       The flags work for ANY task. A #[Run_As_Dispatcher] task (rsx:man tasks, RUNNING AS
       THE DISPATCHER) NEEDS them - it runs as a person - and without --user it is refused
       before anything runs or is recorded, exit 1:

           [ERROR] Bulk_Service::set_status runs as the user who dispatched it
           (#[Run_As_Dispatcher]). From the command line, say who it acts as:
           --user=<id|email> --site=<id>

       With them it runs inline as that person - an operator's re-run of a person's
       request, attributed to them:

           php artisan rsx:task:run Bulk_Service set_status --user=ann@example.com --site=1

       A flag that names nothing exits 1 with rsx:ajax's message on stderr ("[ERROR] User
       not found: ...", "[ERROR] Site ID not found: ...", "[ERROR] Login user 7 has users
       rows on sites 1, 4; pass --site=<id> to choose one").

       A #[Command] alias does NOT take the pair: every option an alias is given is the
       task's own parameter, --user and --site included. #[Command] beside
       #[Run_As_Dispatcher] is a build FATAL (TASK-RUN-AS-01).

BUILD-TIME RULES
       Every rule is enforced by Task_Command_ManifestSupport during the manifest build and
       fails as a RuntimeException naming the file and the method. A violating declaration
       breaks the build until it is fixed - there is no warning tier.

       #[Command] on a method with no #[Task]
             "#[Command] may only annotate a #[Task] method"
             There is nothing for the command to run. Add #[Task('...')], or remove the
             #[Command].

       A name with no prefix segment
             "A command name needs a 'prefix:name' segment"
             'import' squats on artisan's root namespace and collides with whatever
             Laravel adds next. Use 'myapp:import'.

       A name beginning 'rsx:'
             "The 'rsx:' prefix belongs to the framework"
             Name the command after the application.

       #[Command] beside #[Run_As_Dispatcher]
             TASK-RUN-AS-01, reported by the code-quality rule at manifest build. A task
             that runs as the user who dispatched it has no user on an alias's command
             line (an alias takes no --user). Remove the #[Command], or the
             #[Run_As_Dispatcher]; rsx:task:run --user runs such a task by hand.

       A name already taken
             "One command name names exactly one task" (another #[Command]), or
             "That name is already a framework command" (the first token of a $signature
             under app/RSpade/Commands or app/Console/Commands, read from source at build
             time). Choose another name; a #[Command] never shadows one.

       A missing or empty description
             "The second argument is the description and is required"
             It is the line `php artisan list` prints. A command nobody can identify in a
             listing is not finished.

       The table these produce is manifest data['task_commands'], read back with
       Manifest::get_task_commands(). A tree whose manifest has never been built has no
       table, so nothing is registered and artisan boots normally - the aliases appear with
       the first build, like everything else the manifest provides.

WHEN NOT TO
       Not every task wants a name. Add #[Command] when a HUMAN or a SCRIPT invokes the
       work directly - a maintenance chore, an import, a report, a one-off repair.

       Leave it off when:

       - the task is only ever dispatched by application code. It is already reachable as
         `rsx:task:run <Service> <method>` when somebody needs to poke it by hand.
       - the task is purely #[Schedule]d. The cron tick runs it; a name in `artisan list`
         invites a hand-run of something that is nobody's business to run by hand.
       - what you actually want is FRAMEWORK plumbing - something that must work on a tree
         too broken to boot, or before the manifest exists. That is a hand-written command
         in app/RSpade/Commands (see rsx:man artisan_commands), and it is the framework's
         to write, not an application's.

       A task is not made better by having a command. It is made reachable.
