NAME
    breadcrumb_origins - an alternate breadcrumb parent for a page reached from
    somewhere other than its home (the reserved _via parameter)

TAGS
    spa, ui

SYNOPSIS
    The link that starts the detour pushes an origin:

        Rsx.navigate(Rsx.Route('Billing_Invoice_Builder_Action', {
            engagement_id: 156,
            _via: Spa.via_push('engagement', 156),
        }));

    The page where the trail splits accepts it, and VERIFIES it:

        class Billing_Invoice_View_Action extends Spa_Action {
            static breadcrumb_via = ['engagement'];

            async breadcrumb_parent_via(via) {      // via = {type: 'engagement', id: '156'}
                await this.await_loaded();
                if (this.data.invoice.engagement_id !== int(via.id)) return null;
                return Rsx.Route('Engagements_View_Action', via.id) + '#tab=billing';
            }

            async breadcrumb_parent() {             // unchanged: the home parent
                return Rsx.Route('Billing_Invoices_Action');
            }
        }

    Reading, opting out, and continuing a detour:

        Spa.via()                              // [{type: 'engagement', id: '156'}, ...]
        Rsx.navigate(url, {via: 'drop'})       // never carry the current origin
        Rsx.redirect(url, {via: 'drop'})
        Rsx.navigate(url, {via: 'continue'})   // a create page handing over to the
                                               // record it created keeps the origin

DESCRIPTION
    Breadcrumbs are location-based: every action names ONE parent in
    breadcrumb_parent(), and the resolver follows those parents up to a root
    (rsx:man primary_secondary_nav_breadcrumbs). That is right for most pages
    and wrong for a page that legitimately lives in two places.

    The worked example. On an engagement's Billing tab
    (/engagements/156#tab=billing) a user clicks New Invoice. The invoice
    builder lives under Billing (/billing/invoices/new?engagement_id=156), so
    its trail is Billing > Invoices > New Invoice and the sidebar lights
    Billing. After Save, the invoice page (/billing/invoices/123) crumbs to the
    invoice list too, and so does its Edit Draft page. The user's only way
    back to the engagement is the browser's Back button. The same invoice is
    also reached from Billing > Invoices, where the invoice list IS the right
    parent - so the parent depends on where the user came from, and that has
    to be carried by the navigation.

    An ORIGIN is that fact, carried in the URL as a CLAIM and VERIFIED by the
    page that consumes it. It is deliberately not a history trail: it never
    shows more than the claim the user's own click made, it applies to one
    subtree (every page beneath the page that accepts it), and it removes
    itself the moment the user leaves that subtree. With an origin, the
    builder, the invoice page and Edit Draft all crumb
    Engagements > Engagement 156 > Invoice ..., and the sidebar lights
    Engagements.

    An origin URL (return_to=/...) is rejected by design: it is an injectable
    parent, the destination cannot verify it, and it loops. An app-invented
    parameter (from=, parent_id=) solves one hop and never reaches the pages
    beneath it.

THE PARAMETER
    _via is a framework-reserved query parameter. Its value is an ordered,
    comma-separated list of origin tokens, nearest origin first:

        _via=<token>[,<token>...]          token = <type>[.<id>]
        type = [a-z][a-z0-9_]*             id    = [A-Za-z0-9_-]+

        _via=engagement.156
        _via=engagement.156,contact.42
        _via=billing_dashboard             (an origin that is a place, not a record)

    At most 4 tokens. Past that, tokens are dropped from the END (the oldest
    origins), with a console_debug note, and the address bar is rewritten to
    the kept 4.

    A malformed value is ignored as a whole and stripped from the address bar,
    with a console_debug note naming it. It never throws: a URL is user input.

    Rsx.Route() (JS) and Rsx::Route() (PHP) pass _via through like any query
    argument. Nothing server-side interprets it. _via never reaches an
    action's this.args (Spa strips it before matching), so it never changes a
    component's cache key either.

DECLARING A DECIDER
    A page that can stand under an alternate parent declares the origin types
    it accepts, and one hook that turns an origin into a parent URL:

        static breadcrumb_via = ['engagement', 'contact'];
        async breadcrumb_parent_via(via) { ... }     // via = {type, id}

    - The two are ONE declaration. A class declaring either declares both,
      in the same class (manifest-build FATAL SPA-VIA-01 otherwise). Both are
      inherited the way any JavaScript static and method are, so a subclass
      inherits the pair, and a subclass that re-declares one re-declares the
      other.
    - breadcrumb_via is an array LITERAL of strings, each a valid type
      (FATAL otherwise), so the build can check it.
    - The hook VERIFIES the claim against the page's own data and returns
      null to decline. A declined origin is treated exactly as if the page did
      not accept that type. Verification is what makes a pasted or tampered
      _via harmless: it produces a trail that is true, or it is ignored.
    - The parent URL may carry a #fragment (#tab=billing). The crumb keeps it;
      matching ignores it.
    - The parent URL may carry a _via of its own - origins this page can
      DERIVE from its data (see NESTING).

    Spa_Action declares the empty pair (breadcrumb_via = [], a hook returning
    null), so every action has both.

RESOLUTION
    Rsx_Breadcrumb_Resolver walks from the current page upward with the
    current URL's tokens as PENDING:

    1. At each page, if a token is pending and the page's class lists the
       first pending token's type in breadcrumb_via, breadcrumb_parent_via()
       is called with that token.
       - A URL: this page CONSUMES the token. Its parent is the returned URL,
         and the REST of the list rides on that URL as its _via.
       - null: step 2.
    2. Otherwise breadcrumb_parent() names the parent, and the WHOLE pending
       list rides on it, so a page further up can consume it.
    3. Tokens a parent URL already carries go in FRONT of what rides on it
       (capped at 4). The parent is loaded detached, and the walk continues.

    The page that consumes the URL's FIRST token is the DECIDER, identified as
    '<Action_Class>@<its URL without _via or fragment>'.

    A parent URL already in the trail ends the walk there, with a console
    warning (a loop), and so does a trail 20 pages deep.

    Worked chain, from /billing/invoices/123/edit?_via=engagement.156:

        Invoice_Edit (no via types)   -> breadcrumb_parent() =
                                         /billing/invoices/123, carrying
                                         _via=engagement.156
        Invoice_View (accepts it)     -> breadcrumb_parent_via() =
                                         /engagements/156#tab=billing
                                         DECIDER Invoice_View@/billing/invoices/123
        Engagement_View               -> breadcrumb_parent() = /engagements
        Engagements_Index             -> root

        Engagements > Engagement 156 > Invoice 123 > Edit Draft

    Each crumb's link is the URL in the chain, so the Invoice 123 crumb links
    to /billing/invoices/123?_via=engagement.156 and keeps the trail.

CARRYING AND STRIPPING
    Carrying. When the current URL has a _via and an in-app navigation's
    target names none, the framework copies the current _via onto the target:
    Rsx.navigate(), Rsx.redirect() and intercepted link clicks, which all go
    through the one navigation door (rsx:man navigation). A target that names
    its own _via keeps it (explicit wins). Only a target that is a route this
    bundle knows on this host is carried onto - a page of this SPA, or one
    reached by a full page load (another SPA bootstrap, the SPA disabled, or
    {load: 'full'}).

    Across a full page load. Before the load the door writes a one-use
    hand-off to session storage (the target URL, how its _via arrived, and
    the decider of the page being left); the next SPA document reads it at
    boot, so the origin is judged exactly as an in-app navigation would
    judge it. Without the hand-off - a reload, a pasted URL, a new tab - the
    first page of a document is judged as explicit.

    The {via} option of Rsx.navigate() / Rsx.redirect() says how:

        'carry'      the default (the option absent): copied, arrival carried
        'drop'       not carried
        'continue'   copied, arrival EXPLICIT - this navigation continues the
                     same detour
        anything else throws, naming the three; 'continue' with
        {load: 'none'} throws too (nothing loads, so no page judges the claim)

    The create-page hand-off. A create page reached from another record has
    no record of its own, so it is its own decider: New Invoice
    (/billing/invoices/new?engagement_id=156&_via=engagement.156) declares
    breadcrumb_via = ['engagement'] and checks the claim against its
    engagement_id. After Save it moves to the invoice it created. A plain
    carried hop would strip the origin there, because the invoice view is a
    different decider - right for a move between sibling records, wrong for
    this one. So the save hands over with 'continue':

        const result = await Invoice_Controller.create(values);
        Rsx.navigate(Rsx.Route('Invoice_View_Action', result.invoice_id),
                     {via: 'continue'});

    A create page built on Rsx_Form needs no code of its own: the endpoint
    answers redirect_via beside its redirect, and the form follows it with
    Rsx.navigate(result.redirect, {via: result.redirect_via || 'carry'}):

        return [
            'redirect' => Rsx::Route('Invoice_View_Action', $invoice->id),
            'redirect_via' => 'continue',
        ];

    and the invoice view ALSO declares the origin and verifies it against
    the record it shows:

        static breadcrumb_via = ['engagement'];

        async breadcrumb_parent_via(via) {
            await this.await_loaded();
            if (str(this.data.invoice.engagement_id) !== via.id) return null;
            return Rsx.Route('Engagement_View_Action', via.id, {tab: 'billing'});
        }

    Without that declaration the origin is stripped, exactly as before:
    'continue' only changes how the claim is judged, never whether a page
    must verify it. It is an option on the navigation, not a page
    declaration, because only the code that just saved knows the next page is
    the same detour; a page that accepted carried origins from any decider
    would keep them across unrelated sibling hops too.

    Navigation does not know whether the origin applies to the target - it
    carries unconditionally, and the walk decides afterwards. Every navigation
    remembers how its _via arrived:

        explicit   the target URL named it; also the first page of a document
                   (a reload, a pasted URL, a new tab) not reached through
                   the full-load hand-off
        carried    copied by the framework
        restored   Back/Forward onto an entry

    Keep or strip, after the walk (Rsx_Breadcrumb_Resolver.settle_via(), once
    per page, whether or not a layout renders breadcrumbs):

        _via arrived as       walk result                          outcome
        -------------------   ----------------------------------   -------
        explicit              a page accepted the first token       keep
        carried               the SAME decider as the page left     keep
        carried               a DIFFERENT page accepted it          strip
        restored              the decider the entry recorded        keep
                              (no record: judged as explicit)
        any                   no page accepted it (no breadcrumbs,  strip
                              a root, no page declares the type,
                              every hook declined)

    Strip means: _via is removed from the address bar with
    history.replaceState() - never a new history entry - and the plain trail
    is shown. Keep writes the decider into the entry's state
    (history.state.via_decider), which is what Back and Forward compare
    against.

    No flicker: when the URL carries a _via, the resolver emits no chain
    until the decision is made (the previous crumbs stay on screen), and the
    session cache is keyed by the full URL, so a grafted and a plain chain
    never stand in for each other.

    The carried hop in the worked example: the invoice page (decider
    Invoice_View@/billing/invoices/123) -> Edit Draft, carried. Edit Draft's
    walk reaches the same invoice page: same decider, kept. A link from there
    to invoice 124, carried: invoice 124 accepts the token too, but it is a
    different decider - stripped, and invoice 124 shows its plain trail.

NEW TABS
    A tab opened from a link reads the link's href, and a raw href carries no
    origin. So before the browser reads it - on mousedown (any button),
    auxclick, contextmenu, and Enter on a focused link - the SPA link handler
    writes the current _via into an in-app link's href. It applies only to a
    link to a known SPA route of this host that does not name its own _via.

    The rewritten href stays: wherever the origin does not apply, the page it
    opens strips it, and "Copy link" keeps the context too. A new tab has no
    previous entry, so it is judged as explicit. A rewritten link is marked
    (data-spa-via-carried); a left click on it still navigates as a CARRIED
    hop, and the mark lets the href follow the current origin, or lose it.

NESTING
    The list form is the whole nesting mechanism.

    Origins the user traversed. Contact 42 -> engagement 156 -> invoice, each
    link built with Spa.via_push(), produces _via=engagement.156,contact.42 on
    the invoice. Walking up, the invoice page consumes engagement.156; its
    parent, the engagement page, receives _via=contact.42, consumes it and
    crumbs to contact 42:

        Contacts > Contact 42 > Engagement 156 > Invoice 123

    Origins a decider derives. A hook may return a parent URL carrying its own
    _via - say the engagement's own client - and those tokens are put in front
    of whatever is still pending. The current URL only ever holds what the
    user's clicks established.

    Keep/strip is judged on the FIRST token's decider only, and stripping
    removes the whole list. A token nobody consumes rides up to the root crumb
    and is stripped wherever that crumb leads.

SIDEBAR
    A grafted page should light the section its trail starts in (Engagements),
    not the one its URL is under (Billing).

    The resolver's callbacks carry meta:

        on_chain(chain, meta), on_complete(chain, meta)
        meta = {grafted: bool, root_url: string, decider: string|null}

    grafted - an origin replaced a parent somewhere in the trail; root_url -
    the URL the trail starts at; decider - as above, or null.

    The layout hook. When a trail completes, every layout in the chain
    receives

        on_breadcrumb_complete(chain, meta)      // Spa_Layout, empty by default

    whichever layout streamed it - so a layout that owns a sidebar but not the
    breadcrumbs still learns the root. The template's Sidebar_Nav takes the
    meta in follow_trail(meta): when meta.grafted is true it matches its items
    against meta.root_url first, and falls back to the current URL when none
    matches. The plain case is unchanged. An application with its own sidebar
    does the same from its layout's on_breadcrumb_complete().

API
    static breadcrumb_via = ['type', ...]       Spa_Action; the types this page
                                                consumes
    async breadcrumb_parent_via(via)            Spa_Action; verify, return a
                                                parent URL or null
    Spa.via()                                   the current origins, parsed:
                                                [{type, id}, ...], [] when none
    Spa.via_push(type, id = null)               a _via VALUE with this origin
                                                in front of the current list,
                                                capped at 4; throws on a type
                                                or id outside the grammar
    Rsx.navigate(url, {via: 'carry'|'drop'|'continue'})
    Rsx.redirect(url, {via: ...})               'carry' (default) copies the
                                                current _via; 'drop' does
                                                not; 'continue' copies it as
                                                an explicit claim; anything
                                                else throws
    Spa_Layout.on_breadcrumb_complete(chain, meta)
    Rsx_Breadcrumb_Resolver.settle_via(action, url, navigation)
    Spa.return_url(url)                         the URL returning to url in the
                                                state it was left in on this
                                                trail, else url (RETURNING TO
                                                THE STATE YOU LEFT)
    Rsx.HASH_SCROLL_KEY                         '_scroll', the one-time scroll
                                                hash key

    Deliberately absent: a setter for the current URL's _via (an origin is
    something a LINK carries, never something a page asserts about itself),
    and any reading of this.args._via (FATAL). There is no PHP twin of
    via_push(): server-rendered links rarely establish origins.

WHEN NOT TO USE IT
    - A page with one true parent. breadcrumb_parent() is the whole answer.
    - Pre-filling a form. engagement_id on New Invoice is DATA and stays its
      own argument; _via only steers the trail. A link that starts a detour
      usually carries both.
    - "Remember my filters". That belongs to the list (its own URL state),
      and returning to it is the journal's job (RETURNING TO THE STATE YOU
      LEFT).

COMMON PITFALLS
    - Verifying nothing in the hook. The claim arrived in a URL; anyone can
      type it. Check it against the page's own data and return null when it
      does not hold.
    - Setting _via on a link that does not ESTABLISH an origin. Carrying is
      automatic; a hand-copied _via is an explicit claim, which defeats the
      different-decider strip. The same goes for {via: 'continue'} on a
      navigation that is not a create page's hand-off.
    - {via: 'continue'} on the save call alone. The record page must also
      declare the origin type and verify it, or the origin is stripped.
    - Reading this.args._via. It is never there (FATAL SPA-VIA-01). The hook
      receives its token; a layout reads Spa.via().
    - Returning a parent that points back into the subtree. The walk stops at
      the repeat with a warning.
    - Expecting _via to survive into an unrelated page. It is stripped there,
      by design.
    - Navigating to the page already showing, minus its _via. From a page
      with an origin, Rsx.navigate() to the same path carries the origin back
      on, which makes it exactly the URL on screen - a reload. Pass
      {via: 'drop'} to show the page without its origin.

RETURNING TO THE STATE YOU LEFT
    A crumb's href is the bare route of its page, so following one opens
    that page fresh - a list with its default sort, no filters, page 1, at
    the top - while Back returns to the exact entry. So the SPA keeps a
    per-tab JOURNAL of the history entries the user moved through, and a
    crumb leads to the page the user actually came through, in the state
    they left it in - and only when they really came through it.

    The journal records, per history entry (keyed by the spa_run/spa_index
    stamp the SPA keeps in history.state, which survives a reload):

        url     the entry's URL with its fragment, followed as the page
                rewrites it in place (Rsx.url_hash_set(), a {load: 'none'}
                replace, a stripped _via)
        scroll  where the page was scrolled when the entry was LEFT
        from    the entry the user was on when they moved FORWARD to this
                one (a link, Rsx.navigate(), a form's redirect, a full load
                through the navigation door). Back, Forward and a reload
                never change it; Rsx.redirect() inherits the replaced
                entry's
        trail   the crumbs the page's trail showed (recorded by the walk)

    THE RULE. For a crumb URL T, walk `from` back from the page on screen.
    T inherits the state of the NEAREST entry in that chain whose URL
    (without fragment and _via) is T's, provided every entry passed on the
    way showed T in its own trail. Otherwise the crumb is the bare route.
    In words: the saved state is used only while the user never left that
    page's branch of the trail.

        Journey                                         Crumb      Result
        List (sorted, scrolled) -> record -> Edit ->    List       restored
          Save -> record
        List -> record A -> sub-record B                List       restored
        List -> record -> another section -> its        List       bare
          record -> record 2
        Dashboard -> record                             List       bare
        A new tab opened from an email link -> record   List       bare
        List -> record -> List (re-sorted) -> record 2  List       the newer
                                                                   state
        any of the above, then a reload                 as before

    Origins (_via) decide WHICH pages are on the trail; the journal decides
    whether a crumb carries saved state. Nothing here changes which crumbs
    appear.

    THE HREF. A stateful crumb links to T's path and query (its _via
    included) with the fragment of the entry found, plus the one-time
    scroll key when that entry was left scrolled:

        /clients#Clients_DataGrid_sort=name&Clients_DataGrid_page=3&_scroll=840

    The state is in the href itself, so ctrl/middle-click opens the same
    state in a new tab (whose own journal starts empty). The `at` anchor is
    left out when a position is carried.

    THE SCROLL KEY. Rsx.HASH_SCROLL_KEY ('_scroll') is a reserved hash key:
    _scroll=<y> or _scroll=<x>,<y>, never written by scrolling - only
    placed on a link (by the rule above, or by an application link that
    wants to land at a position). The SPA removes it from the URL before
    the history entry is written (or rewrites the address in place on a
    first load), so a copied URL or a reload never jumps again, and applies
    it through the same scroll restoration as Back: it follows a page that
    grows while it loads, and yields to the user's own wheel, touch, key
    or scrollbar. A recorded position (Back/Forward, a reload) outranks it;
    an `at` anchor outranks both. An application must not use the key for
    its own state.

    WHERE THE RESOLVER PUTS IT. Every chain item the resolver emits
    (on_chain, on_complete, on_breadcrumb_complete) carries

        url    the page's identity - match, cache and compare on it
        href   the link to render: Spa.return_url(url) for a crumb above
               the current page, url for the active one

    A layout renders href. The href is computed at every emission and is
    never in the breadcrumb cache: the cache is per page, the href per
    journey.

    OTHER LINKS BACK. A Back or Cancel button, or a deleted record's exit,
    to a page on the trail uses the same answer:

        Spa.return_url(Rsx.Route('Clients_Index_Action'))

    It is synchronous and returns the URL unchanged when the rule does not
    hold. The template's Record_Page_Actions applies it to its Back href;
    its edit pages' Cancel links and its delete exits call it.

    A list's state must live under a STABLE fragment key for this to
    work: a key derived from a component id (which depends on mount order)
    is not read back by the grid of the next visit. The template's
    DataGrid_Abstract keys its state by the component name ($hash_ns to
    override), and its first load leaves the scroll position alone.

    STORAGE. The journal is session storage (Rsx_Storage): per tab, kept
    across reloads and full page loads, empty in a new tab, cleared with
    the framework's other keys when the session, user, site or build
    changes, and capped at the 100 most recently written entries. When
    session storage is unavailable (a locked-down browser, quota) every
    crumb is the bare route; nothing fails.

MANIFEST-BUILD FATALS (SPA-VIA-01)
    - A route declaring a :_via parameter (#[Route], #[Portal_Route], @route).
    - JavaScript reading _via from an args object (this.args._via,
      args['_via'], const {_via} = this.args).
    - static breadcrumb_via without an instance breadcrumb_parent_via() in the
      same class, or the reverse.
    - A breadcrumb_via that is not an array literal of strings, or an entry
      that is not [a-z][a-z0-9_]*.

RSX VS LARAVEL
    Laravel has no client-side breadcrumb chain. Packages such as
    diglactic/laravel-breadcrumbs are server-side and location-only; an
    alternate parent there is a second route or a hand-passed parameter.
