NAME
    framework_pull_mechanics - how a release is built, delivered and applied

SYNOPSIS
    A framework-developer page. For USING the update, see rsx:man rsx_upstream.

DESCRIPTION
    Three repositories, one direction of travel:

        rspade_framework_dev    the monorepo. system/ is the authored source.
              |  bin/publish
              v
        rspade_system           the distribution. What a downstream tracks.
              |  git submodule
              v
        rspade (the starter)    what a new project clones. system/ is a
                                submodule pinned at a rspade_system revision.

    ALL OF system/ IS FRAMEWORK PROPERTY AND IS OVERWRITTEN ON EVERY UPDATE.
    Nothing downstream may edit it, nothing downstream is preserved across an
    update, and the framework does not ask.

PUBLISHING A RELEASE
    bin/publish, run from the monorepo. Pre-flight: rsx:check clean, git tree
    clean.

    rspade_system
        The finalized system/ tree - development files stripped, bin/*.dist
        renamed to their live names, terminology normalized. Committed by the
        RSpade Release Bot with no attribution trailers, and pushed to BOTH
        the internal remote and github.com/rspade-framework/rspade_system.

        A failed GitHub push is fatal, never skipped: that repository is what
        every downstream pull fetches from, so a release nobody can obtain is
        not a release.

    rspade (the starter)
        The application template, with system/ recorded as a GITLINK at the
        rspade_system revision this run just pushed. The revision is captured
        immediately after that push, because that is the moment it becomes
        fetchable - a gitlink the world cannot reach produces a starter that
        clones and then cannot initialise its own framework.

        .gitmodules is written directly rather than by `git submodule add`,
        which would clone hundreds of megabytes on every publish to produce
        two artifacts we can write ourselves. It carries:

            ignore = dirty

        which is load-bearing, not tidiness: the manifest build renames
        .php <-> .php.upstream inside system/ to apply class overrides, and
        without it every `git status` in every downstream project reports
        ` M system` forever for churn that regenerates itself. It hides
        DIRTINESS only - a moved revision still shows.

        STAGING EXCLUDES system/. The gitlink is staged deliberately, and the
        worktree there is an empty mount point; `git add -A` reading that
        directory would see nothing and drop the gitlink straight back out,
        publishing a starter with no framework at all.

    (There is no third repository. The reference application used to ship
    standalone as rspade_template_app; it now rides inside rspade_system at
    app/RSpade/resource/reference_app - see template_app(3).)

WHAT A DOWNSTREAM UPDATE DOES
    See rsx:man rsx_upstream for the full sequence. In summary: reset the
    submodule hard, fetch, check out the tip, commit the gitlink, rebuild.

    THE RANGE RUNS FROM THE RECORDED GITLINK, NOT FROM THE CHECKOUT. The
    changelog and the commit count describe what the application's history
    moved, so a pull interrupted between the checkout and the pointer commit is
    completed by the next pull with the full changelog - the checkout sitting
    ahead of the record is the recovery case, never an up-to-date one.

    The updater COPIES ITSELF TO /tmp AND RE-EXECS before touching anything.
    It lives at system/bin/framework-pull-upstream.sh, inside the tree it is
    about to replace, and git offers no guarantee that a checkout leaves a
    running script's inode intact. The vendored-era updater survived this by
    accident, because rsync writes a temp file and renames.

THE UPDATER SELF-DELIVERS
    The live bin/framework-pull-upstream.sh is GENERATED from the authoritative
    bin/framework-pull-upstream.sh.dist by the interception in system/artisan.
    EDIT THE .dist ONLY.

    It ships in the submodule like everything else, so improvements land
    automatically - on the pull AFTER the one that delivers them (one-pull
    lag). That lag is why durable "make the environment correct" behaviour
    belongs in bin/environment_updates/ rather than in the updater: those run
    from the freshly-synced copy, so they take effect on the same pull.

THE MAINTENANCE WINDOW
    ONE implementation, bin/maintenance-mode.sh - the same script
    rsx:maintenance:enable runs. It owns the service list; nothing else
    repeats it.

    Raised before anything is touched and lifted on every exit path, Ctrl-C
    included. An operator's existing window is left exactly as they raised it:
    the services it stopped are already stopped, and lowering ours on the way
    out would restart them mid-surgery.

    A stale window left by a previous updater run IS adopted, identified by
    the flag's reason line, so an interrupted update cannot leave a box 503ing
    until somebody finds the file.

TROUBLESHOOTING A RELEASE
    Starter clones but system/ is empty
        The clone did not recurse. That is the user's fix
        (git submodule update --init --recursive), but check the README says
        --recurse-submodules.

    Starter's gitlink names an unreachable revision
        The rspade_system push failed or was skipped. Publish is fail-loud on
        that push precisely to prevent this.

    Downstream reports ` M system` constantly
        ignore = dirty is missing from .gitmodules. Publish writes it into the
        starter and the vendored -> submodule conversion sets it (git submodule
        add writes path/url/branch only), so this is a project converted before
        that landed. The environment update
        bin/environment_updates/080_submodule_ignore_dirty.sh heals it, as does
        `php artisan rsx:heal submodule-ignore-dirty`; commit the .gitmodules
        change, it is tracked.

    A framework update lands with no trace in status, diff or the commit
        A repo-wide `[diff] ignoreSubmodules = all` in the app's .git/config -
        the usual answer to the noise above - suppresses submodule reporting
        entirely, the recorded pointer included. `dirty` is the only value that
        shows a moved pointer while hiding the build's churn, and it belongs
        per-submodule in the tracked .gitmodules. The same 080 update unsets the
        blanket key; the "Submodule Visibility" rsx:health row reports both.
