    model_indexes - Database index analysis and recommendation system

SYNOPSIS
    php artisan rsx:db:check_indexes [--show-details] [--generate-migration]

    Reports the indexes the application's model queries and relationships need
    and the database does not have, and writes a reviewed migration for them.

DESCRIPTION
    The advisor reads two things:

    1. Model relationships - every relationship each model declares
    2. Query patterns - the model query chains in the application's source
       (rsx/), read from the PHP syntax tree

    From each it derives a REQUIREMENT: the columns a query filters on, on one
    table, split into equality columns, at most one range column, and sort
    columns. It compares every requirement with the indexes the table already
    has, and recommends an index only where none serves it.

    It is advice, never automation: nothing is created until you generate the
    migration, read it, and run migrate.

COMMAND USAGE
    php artisan rsx:db:check_indexes
        The report: sources read, what could not be read, the indexes to
        create (and auto-generated ones to drop), then the low-value ones.

    --show-details
        Every call site behind each recommendation, every excluded source
        file, every chain that could not be analyzed, and the list behind
        each [WARNING] count.

    --generate-migration
        Writes the migration(s) - see MIGRATION GENERATION.

    --include-low-value
        Puts the low-value recommendations in the generated migration too.

    --include-system
        Also analyzes framework tables (see WHAT IS ANALYZED).

    --include-dev
        Also counts development-only sources (rsx/app/dev and seeders).

    --table=<name>
        Reports only this table.

    --format=json
        The same analysis as one JSON document.

    --no-relationships / --no-queries
        Skips one of the two analyses.

    --show-all
        Shows every recommendation even past the per-table quota.

WHAT IS ANALYZED
    Sources:
        Every PHP class file under rsx/ in the manifest, except:
        - tests: any path with a tests/ directory segment (always excluded);
        - dev: rsx/app/dev, the developer-only screens;
        - seeders: a path with a sample_data/, seeders/ or seeds/ directory
          segment, a class extending a *Seeder class, or a class whose every
          #[Command] is named with a last segment beginning "seed"
          (rsx_app:seed). Code that runs once to populate a database is not
          a query workload.
        --include-dev counts dev screens and seeders again.

    Tables:
        Framework tables are left out by default: a table whose name begins
        with an underscore, and a table whose NAME is declared by framework
        source - a core model, or an application class that extends a core
        model's base without redeclaring $table (users, login_users, sites).
        Their indexes ship with the framework; the summary line counts the
        requirements left out. --include-system analyzes them.

    Nothing unread is silent:
        A source file that does not parse and a relationship that cannot be
        introspected are counted in a [WARNING] line, and listed under
        --show-details. Their requirements are unknown, not absent.

RELATIONSHIP REQUIREMENTS
    - hasMany / hasOne: the foreign key on the related table, plus site_id
      when the related model is site-scoped (the relation query carries its
      global scope)
    - morphMany / morphOne: the {relation}_type + {relation}_id pair on the
      related table (plus site_id, as above)
    - belongsToMany: each pivot key, on its own (a pivot is joined, never
      queried through a model's scope)
    - belongsTo / morphTo: nothing - they resolve through the target's
      primary key

    Each is attributed to the file and line that declares the relationship.

QUERY REQUIREMENTS
    A CHAIN is a fluent expression rooted at a static call on a model class:
    Client_Model::where(...)->...  (self:: and static:: inside a model are
    that model). A chain built on a variable, a relation method or a closure
    result is not read.

    Equality columns (a SET - order does not matter):
        where('col', $v)   where('col', '=', $v)   where(['a' => 1, 'b' => 2])
        whereIn('col', [...])   whereNull('col')

    Range column (the first one only - an index cannot range past it):
        where('col', '<' | '>' | '<=' | '>=', $v)   whereBetween('col', [...])
        whereNotNull('col')   where('col', 'LIKE', 'prefix%')
        (IS NOT NULL reads every non-null key: a range for index use)

    Sort columns (kept only when there is no range column):
        orderBy('col')   orderByDesc('col')   latest()   oldest()
        (latest() / oldest() with no argument sort by created_at)

    Never a requirement:
        - where('col', 'LIKE', '%...'): a leading wildcard reads every row
          (a pattern whose literal start is % or _, including "%{$term}%")
        - where('col', '!=', ...), and an operator that is not a literal
        - a TEXT / MEDIUMTEXT / LONGTEXT / BLOB / JSON column
        - a column the table does not have
        - conditions inside where(function ($q) { ... }) groups

    Abandoned chains (nothing recorded; listed under --show-details):
        - a column name that is not a literal: where($column, ...)
        - any orWhere...(): no single composite index serves an OR

    Column qualifiers:
        - 'clients.name' on Client_Model is the model's own column;
        - a column qualified with a joined table (or its alias, 'tasks as t')
          that is a known model table is a requirement on THAT table - with
          no implicit site_id, because the global scope filters the root
          model only;
        - a column qualified with anything else is dropped;
        - in a chain with a join, an unqualified column is kept only when the
          root table has it and no joined table does (a join to a table that
          is not a literal makes every unqualified column ambiguous).

    Site scope:
        A site-scoped model (Rsx_Site_Model_Abstract, or Site_Scoped) filters
        every query by site_id, so its requirements carry site_id among their
        equality columns - unless the chain calls withoutGlobalScope(s), or
        runs inside Model::without_site_scope(fn) on a model that shares its
        scope flag (every model under Rsx_Site_Model_Abstract shares one).

    The primary key:
        InnoDB clusters every table on its primary key and appends it to
        every secondary index. An equality set holding the whole primary key
        is a primary-key lookup and needs nothing; a range or sort on the
        primary key is dropped - (a) already orders and ranges by id within a.

MATCHING AND RECOMMENDING
    Selective and low-cardinality columns:
        A column is LOW-CARDINALITY when it is a boolean (TINYINT(1)), a MySQL
        ENUM, a declared model enum ($columns 'enum'), or is named like a flag
        or status: is_*, has_*, status, *_status, status_id. Every other column
        except site_id is SELECTIVE.

    Served:
        An existing index - the primary key and unique keys included, any
        name - serves a requirement when either:
        - its LEADING columns are exactly the requirement's equality set, in
          any order; or
        - its leading columns are all in the equality set and include at least
          one selective column. A selective column already narrows the read to
          a few rows, which the remaining conditions filter cheaply: one
          client's rows all sit in one site, so (client_id) serves
          {site_id, client_id}.
        Whatever follows the matched columns (the range or sort column, or
        nothing) is optional. A requirement with no equality column is served
        by an index leading with its range column.

        Requirement {site_id, client_id} is served by (site_id, client_id), by
        (client_id, site_id, name) and by (client_id); not by (site_id) alone.
        Requirement {site_id, status_id, client_id} is not served by
        (status_id) alone: an enum narrows by a fraction.

    Recommended shape:
        equality columns (site_id first, then alphabetical), then the range
        column, or the sort columns when there is no range column.

    Aggregation:
        Identical requirements from different call sites are one
        recommendation, reported with how many distinct call sites need it.
        A recommendation also absorbs every other requirement whose equality
        set is its leading columns, so one index carries several call sites.

    Low value:
        A requirement whose only columns besides site_id are equality on
        low-cardinality columns narrows a read by a constant fraction at best
        (its sort columns are not considered). It is
        listed separately and left out of the migration unless
        --include-low-value. One that a normal recommendation also serves is
        folded into it instead.

    Nearly served:
        When an existing index's leading columns are all but one of a
        recommendation's equality columns, the report names it and the
        columns it leads with. Such an index holds only site_id and
        low-cardinality columns (else it would serve), and the column it lacks
        is the selective one. An index that is exactly those columns is
        preferred and marked "extend it" - adding the column to it is often
        better than adding another index:
            nearly served by idx_x, which leads with (site_id, status_id): missing invoice_id - extend it

    Auto-generated indexes:
        An index named idx_auto_* that no analyzed requirement uses is listed
        to drop. Indexes with any other name are never dropped.

    Quota:
        At most 32 recommendations per table (fewer when the table already
        has many hand-written indexes; MySQL allows 64). Past it, relationship
        indexes are kept first, then multi-column query indexes, then
        single-column ones; --show-all lists everything.

MIGRATION GENERATION
    php artisan rsx:db:check_indexes --generate-migration

    Each file is created by make:migration:safe (so it is recorded in its
    directory's .migration_whitelist) and then given one ALTER TABLE ... ADD
    INDEX / DROP INDEX statement per change, each create preceded by the call
    sites it serves:

    - application tables -> rsx/resource/migrations/
    - framework tables (--include-system) -> system/database/migrations/,
      on a framework-developer tree only. Elsewhere system/ is replaced by
      every framework update, so the command prints an [ERROR] naming the
      tables instead: send them to RSpade as a change request.

    When both appear, two files are written. Index names are
    idx_auto_<columns>, shortened with a hash suffix past MySQL's
    64-character limit. Review the file, then run php artisan migrate.

LIMITATIONS
    Static analysis sees only what the source states literally. Not analyzed:
    dynamic column names, whereRaw / whereHas / whereColumn / whereDate,
    conditions inside where(function ...) groups, chains with orWhere, queries
    built on a variable or a relation method, the relationship kinds other
    than those above (hasManyThrough), and anything decided at run time.

    It also cannot see data: a requirement on a column holding three distinct
    values is recommended unless it is recognisably a flag, status or enum.
    Verify critical queries with EXPLAIN against production-sized data.

WORKFLOW
    1. php artisan rsx:db:check_indexes
    2. Read each recommendation and its call sites (--show-details)
    3. php artisan rsx:db:check_indexes --generate-migration
    4. Review the migration; delete what you do not want
    5. php artisan migrate

    Hand-written indexes: name them idx_<table>_<purpose>; never use the
    idx_auto_ prefix, which marks indexes the advisor may propose dropping.
