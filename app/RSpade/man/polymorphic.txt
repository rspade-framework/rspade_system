POLYMORPHIC(7)                 RSX Framework Manual                POLYMORPHIC(7)

NAME
    polymorphic - Polymorphic relationships with type references

SYNOPSIS
    Model definition:

        class Activity_Model extends Rsx_Model_Abstract
        {
            protected static $type_ref_columns = ['eventable_type'];

            #[Relationship]
            public function eventable()
            {
                return $this->morphTo();
            }
        }

    Usage:

        $activity->eventable_type = 'Contact_Model';  // Stores integer in DB
        $activity->eventable_id = 123;
        $activity->save();

        echo $activity->eventable_type;  // Returns "Contact_Model"
        $activity->eventable;            // The Contact_Model row (property, not call)

    Form handling:

        $eventable = Polymorphic_Field_Helper::parse($params['eventable'], [
            Contact_Model::class,
            Project_Model::class,
        ]);

THE PAIR STANDARD
    A polymorphic reference is ALWAYS a pair, both columns BIGINT:

        {relation}_type   the type-ref discriminator, declared in the owning
                          model's $type_ref_columns
        {relation}_id     the row id

    Two parallel nullable FK columns ("either project_id or client_id is set")
    is the forbidden shape - if a reference can point at more than one table it
    is a pair. A reference that can only ever point at ONE table is a plain FK,
    not a polymorphic reference.

    The `_type` suffix is the across-the-board standard. It is exactly what
    Eloquent derives by default, so `morphTo('eventable')` and
    `morphMany(X::class, 'eventable')` need no explicit column arguments.

    Note the shape of the audit columns: created_by_type / created_by_id and
    updated_by_type / updated_by_id. They are the standard pair, not a special
    case - the `_id` suffix on the id column is what makes them one. They are
    declared on Rsx_Model_Abstract (so every model casts them) and stamped
    automatically by save(); see model_normalization(7), AUDIT AUTHORSHIP.

    Do not confuse a `*_type` type ref with a `type_id` ENUM column. `type_id`
    is an integer enum defined in $enums (see enum(7)); it names a case, not a
    table. Nothing in this page applies to it.

    POLY-01 (a manifest-build-FATAL code-quality rule) enforces the standard:
    see CODE QUALITY RULE below.

DESCRIPTION
    Polymorphic relationships allow a single database column pair to reference
    multiple model types. For example, an Activity can be related to either a
    Contact or a Project using eventable_type and eventable_id columns.

    RSX uses a type reference system that stores integers in the database but
    transparently converts to/from class name strings in PHP. This provides:

    - Efficient integer storage instead of VARCHAR class names
    - Automatic type discovery - no manual mapping required
    - Transparent conversion - you work with class names, never see integers
    - STOCK Eloquent morph relations, unchanged, over the integer column

TYPE REFERENCE SYSTEM
    How It Works

        RSX maintains a _type_refs table that maps class names to integer IDs:

            id | class_name      | table_name
            1  | Contact_Model   | contacts
            2  | Project_Model   | projects
            3  | Task_Model      | tasks

        When you set a type_ref column to a class name, RSX:
        1. Checks if the class exists in _type_refs
        2. If not, validates it's a valid Rsx_Model subclass and creates entry
        3. Stores the integer ID in the database

        When you read a type_ref column, RSX:
        1. Looks up the integer ID in _type_refs
        2. Returns the class name string

    Defining Type Reference Columns

        Declare which columns are type references in your model:

            class File_Attachment_Model extends Rsx_Model_Abstract
            {
                protected static $type_ref_columns = ['fileable_type'];

                #[Relationship]
                public function fileable()
                {
                    return $this->morphTo();
                }
            }

        The cast is automatically applied - no manual $casts definition needed.
        The declaration is the ENTIRE setup: with it in place, every stock
        Eloquent morph relation works over the column (see LARAVEL MORPH MAP
        INTEGRATION). Without it you have Laravel's string morph, which POLY-01
        fatals at build time.

    Database Schema

        Type reference columns must be BIGINT, not VARCHAR:

            fileable_type BIGINT NULL,
            fileable_id BIGINT NULL,

        The _type_refs table is created automatically by framework migrations.

    Auto-Discovery

        When storing a new class name that isn't in _type_refs yet:

            $attachment->fileable_type = 'Custom_Model';
            $attachment->save();

        RSX will:
        1. Verify Custom_Model exists and extends Rsx_Model_Abstract
        2. Create a new _type_refs entry with the next available ID
        3. Store that ID in the fileable_type column

        This means any model can be used in polymorphic relationships without
        pre-registration. The system is fully automatic.

    Caching

        The type refs map is cached:
        1. In Redis (if available) - refreshed when entries are added
        2. In PHP memory - loaded once per request

        The map is typically small (< 100 entries), so full-map caching is used.

    Validation

        On write: Throws exception if value is not a valid Rsx_Model subclass
        On read: Throws exception if ID doesn't exist in _type_refs table
        Null values: Allowed if the database column is nullable

        A DEREFERENCE fails loud; the mere EXISTENCE of a registry row for a
        vanished class does not. See BOUNDARIES.

LARAVEL MORPH MAP INTEGRATION
    Type_Ref_Registry::register_morph_map() runs during framework boot and
    registers EVERY type ref under TWO aliases pointing at the same class:

        'Contact_Model' => Rsx\Models\Contact_Model::class
        '4'             => Rsx\Models\Contact_Model::class

    That second alias is the whole mechanism. morphTo() reads the RAW attribute
    (it bypasses the cast, so it sees the integer 4) and resolves it through
    Relation::getMorphedModel() - a plain morph-map lookup. Registering the id
    AS an alias therefore turns the raw integer into the right class with no
    framework workaround at all. PHP coerces a numeric-string array key to an
    int, so `4` and `"4"` both hit the entry.

    ALIAS ORDER IS LOAD-BEARING. Model::getMorphClass() answers with the FIRST
    morph-map key that maps to the class, and that value is what a WRITE puts in
    the type column (morphTo()->associate(), morphMany()'s own constraint,
    whereMorphedTo()). It must be the CLASS-NAME alias, which Rsx_Type_Ref_Cast
    then converts to the integer. Class-name aliases are therefore always
    inserted before integer aliases. Changing that order silently breaks every
    polymorphic write in the application.

    What works, unchanged:

        $attachment->fileable;                          // morphTo, lazy read
        $attachment->fileable()->withTrashed()->first();// the relation object
        $attachment->fileable()->associate($contact);   // write
        $attachment->fileable()->dissociate();          // clear the pair
        $contact->morphMany(File_Attachment_Model::class, 'fileable');
        $contact->morphOne(File_Attachment_Model::class, 'fileable');
        Activity_Model::whereMorphedTo('eventable', $contact);
        Activity_Model::whereHasMorph('eventable', [Contact_Model::class]);

    Reading a relation as a PROPERTY ($attachment->fileable) requires the method
    to carry #[Relationship] - RSX only treats attributed methods as relations
    (see Rsx_Model_Abstract::isRelation). Calling it as a method returns the
    relation object, which is what you want for withTrashed() and friends.

    The morph map uses simple class names (e.g., "Contact_Model") not fully
    qualified names, matching how RSX models work throughout the framework.

BOUNDARIES
    Eager loading is forbidden framework-wide.
        `->with('eventable')` throws, like every other eager load in RSX. The
        morph dictionary Laravel builds for eager loading reads through the
        ACCESSOR (class names) and would work; the restriction is policy, not a
        type-ref limitation.

    A half-set pair is a data defect and fails loud.
        `{relation}_type` NULL with `{relation}_id` set makes Eloquent build a
        degenerate query and throw. Write both columns together, or neither.
        (Both NULL reads as null; a valid type with a missing row reads as null.)

    A _type_refs row whose class is gone is INERT, PERMANENT, and SILENT.
        If a model class is renamed or deleted, its _type_refs row remains. The
        framework does NOT report it - not at boot, not in rsx:debug, not in
        rsx:health - and offers no way to delete it. That is deliberate:

          - The row is HARMLESS. Nothing is wrong with a registry entry that no
            data points at.
          - DELETING it is what causes harm. Any row anywhere still holding that
            integer loses the only record of what the integer meant. So there is
            no prune command, and writing your own is a mistake.

        The row stays a valid, named type ref for reading purposes. What still
        fails loud is a DEREFERENCE - code that must produce a class and cannot:

        - REGISTRATION registers the retired id in the morph map under a POISON
          alias (Retired_Type_Ref) whose instantiation throws. Boot itself never
          throws and never warns.
        - morphTo() over such a column throws at `new $class` - the exact frame
          that used to say "Class name must be a valid object or a string" -
          with: Type ref 3 ("Event_Model") names a model class that no longer
          exists in the codebase.
        - THE CAST (reading $model->parent_type) throws the same message.
          id_to_class() verifies the class still resolves; it never hands back a
          class name that names nothing.
        - class_to_id() REFUSES a retired class, on the cached path too, so no
          NEW references can accrue. The refusal is about the WRITE, never about
          the row.
        - whereHasMorph($relation, '*') - which plucks distinct stored values
          and instantiates each - hits the poison alias and produces that same
          named error instead of a Laravel fatal. An explicit type list is still
          preferable to '*'.

    WHICH ROWS POINT AT A VANISHED MODEL
        The one thing worth knowing is the opposite direction: which DATA still
        holds a type id that no longer resolves. Those rows throw at the point of
        use, and they are yours to repoint or delete.

            php artisan rsx:type_refs:orphans [--json]

        A REPORT and only a report. It counts, it prints, it executes nothing it
        prints, and it always exits 0 - orphaned rows are information, not a
        failed command. No rows are ever loaded into memory: every number is a
        COUNT(*) ... GROUP BY, and the SELECT is text.

        A row is an ORPHAN when its type-ref column holds a non-null value that
        is not a resolvable registry id. One definition, both shapes: an id whose
        _type_refs row names a vanished class, and an id with no _type_refs row
        at all (hand-written SQL, a restore from another environment, a registry
        row somebody deleted).

        The column inventory is the manifest's: every model's _type_ref_columns()
        - its own $type_ref_columns declaration UNIONed with the framework audit
        pairs (created_by_type / updated_by_type / deleted_by_type, type refs on
        every table) - intersected with the columns each table actually has.

        Sample output:

            $ php artisan rsx:type_refs:orphans

            shared_items.item_type - 4 rows
              SELECT * FROM shared_items WHERE item_type IN (12, 19)  -- Event_Model, Forum_Thread_Model

            4 rows across 1 column. Repoint or delete them (or restore the
            class). Never delete the _type_refs row - it is what keeps the id
            readable.

        An id with no registry row prints as `19 (no _type_refs row)` in the
        trailing comment. With nothing to report:

            [OK] No polymorphic rows point at a vanished model.

        --json emits a list of
        {table, column, count, type_ids: {id: class_name|null}, select}.

        Engine: Type_Ref_Orphan_Report (scan(), type_ref_columns_by_table(),
        format_select()).

    RETIRING A MODEL - the checklist:
          1. Delete the model class as usual. Leave the _type_refs row alone;
             it is not debris and there is nothing to clean up.
          2. `php artisan rsx:type_refs:orphans` - the rows still pointing at it.
          3. Repoint or delete those rows. A cleanup MIGRATION does this in raw
             SQL, with the class name as a string literal - it may not reference
             the registry at all (MIGRATION-MODEL-01):

                 UPDATE shared_items SET item_type = NULL, item_id = NULL
                  WHERE item_type = (SELECT id FROM _type_refs
                                      WHERE class_name = 'Old_Model')

             Outside a migration, Type_Ref_Registry::find_id_by_class_name(
             'Old_Model') is the one lookup that does NOT auto-create and does
             NOT require the class to still exist (class_to_id() throws for
             exactly these classes).

    A TABLE RENAME FOLLOWS ITSELF INTO _type_refs.
        _type_refs stores class_name AND table_name, so renaming a table would
        strand the registry row. The migrate pipeline handles it: every statement
        `migrate` executes passes through one macro, which recognises

            RENAME TABLE a TO b            (multi-rename lists included)
            ALTER TABLE a RENAME [TO|AS] b

        and, in the SAME migrate run, updates _type_refs.table_name, printing one
        line per registry row it moved:

            Type ref Widget_Model: table old_widgets -> new_widgets

        RENAME COLUMN / RENAME INDEX / RENAME KEY are not table renames and are
        not matched. A migration writes the plain rename and nothing else - it
        must not (and by MIGRATION-MODEL-01 may not) touch the registry itself.
        Implementation: Type_Ref_Table_Rename.

    Pivot-table morphs (morphToMany / morphedByMany) are not supported.
        Their discriminator lives on a pivot table that no model owns, so no
        $type_ref_columns declaration can apply to it and the column would be a
        VARCHAR class name. Model the join table as a real model with its own
        {relation}_type / {relation}_id pair. POLY-01 flags these.

CODE QUALITY RULE
    MIGRATION-MODEL-01 - No Application Code In A Migration
    (CodeQuality/Rules/Database/MigrationModelReference_CodeQualityRule.php)

        An rsx:check rule (severity high). A migration may not name a model
        class or Type_Ref_Registry: it must replay from scratch forever, and
        those symbols are current code that gets renamed and deleted. Resolve a
        type-ref id with the get-or-create closure shown under CONVERTING
        EXISTING COLUMNS. A class name as a STRING is never flagged. Full
        contract: rsx:man migrations.

    POLY-01 - Polymorphic Type-Ref Declaration
    (CodeQuality/Rules/Manifest/MorphStringPattern_CodeQualityRule.php)

        Manifest-build FATAL, AST-based, cross-file. It flags Laravel's
        string-morph pattern:

        - morphTo() whose type column is not in the DECLARING model's
          $type_ref_columns
        - morphOne() / morphMany() whose type column is not in the RELATED
          model's $type_ref_columns (the related model owns that table)
        - morphToMany() / morphedByMany() - always (see BOUNDARIES)
        - a morph type column whose name does not end in `_type`

        It does NOT fire on a call whose owning model cannot be resolved
        statically (a variable class name): the rule is fatal, so an unprovable
        case is skipped rather than guessed at.

        Migrations are not covered - the manifest does not scan migration
        directories and column definitions live inside raw SQL strings. A
        VARCHAR `*_type` column is caught at the model that relates over it.

        Escape hatch, for a genuinely external table whose discriminator is not
        yours to change: @POLY-01-EXCEPTION - <rationale>, on the method
        docblock/line or anywhere in the file.

QUERY BUILDER INTEGRATION
    Transparent WHERE Clauses

        The query builder automatically converts type_ref columns in WHERE
        clauses. You can use class name strings directly:

            // All of these work - class names auto-converted to IDs
            File_Attachment_Model::where('fileable_type', 'Contact_Model')->get();
            File_Attachment_Model::where('fileable_type', '=', 'Contact_Model')->get();
            File_Attachment_Model::where(['fileable_type' => 'Contact_Model'])->get();

            // whereIn also works
            File_Attachment_Model::whereIn('fileable_type', [
                'Contact_Model',
                'Project_Model'
            ])->get();

            // Integer IDs still work (pass-through)
            File_Attachment_Model::where('fileable_type', 42)->get();

        Supported methods: where(), orWhere(), whereNot(), orWhereNot(),
        whereIn(), orWhereIn(), whereNotIn(), orWhereNotIn()

        A table-qualified spelling of the model's OWN column
        ('file_attachments.fileable_type') converts too, and the clause stays
        qualified in the emitted SQL. A qualifier naming a DIFFERENT table is
        deliberately left alone - that column belongs to the joined table's
        model and cannot be resolved here (convert explicitly with
        Type_Ref_Registry::class_to_id()).

        A value that is neither null nor an integer and does not resolve in
        the registry THROWS, naming the model, column and value - it is never
        bound as a string (MySQL would coerce it to 0 against the BIGINT
        column and the clause would silently match nothing).

    Polymorphic Join Helpers

        Join tables with polymorphic columns using dedicated helpers:

            // Get contacts that have attachments (INNER JOIN)
            Contact_Model::query()
                ->joinMorph('file_attachments', 'fileable')
                ->select('contacts.*', 'file_attachments.filename')
                ->get();

            // Get all contacts, with attachments if they exist (LEFT JOIN)
            Contact_Model::query()
                ->leftJoinMorph('file_attachments', 'fileable')
                ->get();

            // RIGHT JOIN
            Contact_Model::query()
                ->rightJoinMorph('file_attachments', 'fileable')
                ->get();

        Parameters:
            $table      - Table with polymorphic columns (e.g., 'file_attachments')
            $morphName  - Column prefix (e.g., 'fileable' for fileable_type/fileable_id)
            $morphClass - Optional class name (defaults to current model)

        Explicit class (when querying from a different model context):

            SomeModel::query()
                ->leftJoinMorph('file_attachments', 'fileable', Contact_Model::class)
                ->get();

        The generated SQL is equivalent to:

            LEFT JOIN file_attachments
                ON file_attachments.fileable_id = contacts.id
                AND file_attachments.fileable_type = <type_ref_id>

FORM HANDLING
    Client-Side Format

        Polymorphic fields are submitted as JSON-encoded values:

            eventable={"model":"Contact_Model","id":123}

        This single-field approach simplifies form handling compared to
        separate type and id fields.

    Polymorphic_Field_Helper

        Server-side parsing with security validation:

            use App\RSpade\Core\Polymorphic_Field_Helper;

            $eventable = Polymorphic_Field_Helper::parse($params['eventable'], [
                Contact_Model::class,
                Project_Model::class,
            ]);

            // Validation
            if ($error = $eventable->validate('Please select an entity')) {
                $errors['eventable'] = $error;
            }

            // Access values
            $model->eventable_type = $eventable->model;  // "Contact_Model"
            $model->eventable_id = $eventable->id;       // 123

        The whitelist ensures only allowed model types are accepted.

    Validation Methods

        Required field:
            if ($error = $field->validate('Please select')) {
                $errors['field'] = $error;
            }

        Optional field:
            if ($error = $field->validate_optional('Invalid type')) {
                $errors['field'] = $error;
            }

    State Checking

        $field->is_empty()    // No value provided
        $field->is_valid()    // Value provided and model type allowed
        $field->is_invalid()  // Value provided but model type not allowed

CLIENT-SIDE IMPLEMENTATION
    Building a Polymorphic Picker Component

        To create a picker for polymorphic fields, build a component that:

        1. Maintains a hidden input with the JSON-encoded value
        2. Implements val() to get/set as {model: 'Model_Name', id: number}
        3. Syncs the hidden input on every change
        4. Handles pre-load value setting (value set before options loaded)

    Hidden Input Pattern

        The component template should include a hidden input:

            <input type="hidden" $sid="hidden_value" name="<%= this.args.name %>" />

        On value change, sync to hidden input as JSON:

            _sync_hidden_value() {
                const $hidden = this.$sid('hidden_value');
                if (this._value && this._value.model && this._value.id) {
                    $hidden.val(JSON.stringify(this._value));
                } else {
                    $hidden.val('');
                }
            }

    val() Implementation

        The val() method should work before and after component loads:

            val(value) {
                if (arguments.length === 0) {
                    // Getter
                    return this._value || this._pending_value || null;
                }

                // Setter
                const parsed = value ? {model: value.model, id: parseInt(value.id)} : null;

                if (this.data.loading) {
                    this._pending_value = parsed;
                    this._value = parsed;
                    this._sync_hidden_value();
                } else {
                    this._value = parsed;
                    this._apply_to_ui();
                    this._sync_hidden_value();
                }
            }

    Using Tom Select

        For searchable dropdowns, use Tom Select with a compound value format:

            // Compound value: "Model_Name:id"
            valueField: 'compound_value',

            onChange: function(compound_value) {
                if (!compound_value) {
                    that._value = null;
                } else {
                    const parts = compound_value.split(':');
                    that._value = {model: parts[0], id: parseInt(parts[1])};
                }
                that._sync_hidden_value();
            }

        Add options with the compound format:

            all_options.push({
                compound_value: 'Contact_Model:' + contact.id,
                model: 'Contact_Model',
                id: contact.id,
                name: contact.name,
            });

COMPLETE EXAMPLE
    Model Definition

        class Activity_Model extends Rsx_Model_Abstract
        {
            protected static $type_ref_columns = ['eventable_type'];

            public static $enums = [];
            public static $rel = [];

            protected $table = 'activities';

            #[Relationship]
            public function eventable()
            {
                return $this->morphTo();
            }
        }

    Controller

        use App\RSpade\Core\Polymorphic_Field_Helper;

        #[Ajax_Endpoint]
        public static function save(Request $request, array $params = [])
        {
            $eventable = Polymorphic_Field_Helper::parse($params['eventable'] ?? null, [
                Contact_Model::class,
                Project_Model::class,
            ]);

            $errors = [];

            if ($error = $eventable->validate('Please select an entity')) {
                $errors['eventable'] = $error;
            }

            if (!empty($errors)) {
                return response_form_error('Please correct errors', $errors);
            }

            $activity = new Activity_Model();
            $activity->eventable_type = $eventable->model;
            $activity->eventable_id = $eventable->id;
            $activity->save();

            return ['success' => true];
        }

            CREATE TABLE activities (

                site_id BIGINT NOT NULL,
                created_at TIMESTAMP(3) DEFAULT CURRENT_TIMESTAMP(3),
                updated_at TIMESTAMP(3) DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
                created_by_id BIGINT NULL,
                created_by_type BIGINT NULL,

        ");

RSX VS LARAVEL
    Laravel Default

        - Stores full class name as VARCHAR: "App\\Models\\Contact"
        - Requires manual morph map configuration for aliases
        - No automatic discovery of new types

    RSX Approach

        - Stores integer ID in BIGINT column
        - Automatic class name to ID mapping via _type_refs table
        - Auto-discovery creates new entries on first use
        - Morph map auto-registers BOTH the class name and the integer id, so
          stock Eloquent morph relations work over the integer column unchanged
        - Simple class names: "Contact_Model" not "App\\Models\\Contact"

    Benefits

        - Smaller database storage (BIGINT vs VARCHAR)
        - Faster queries (integer comparison vs string comparison)
        - Indexable without concerns about string length
        - Consistent with RSX simple class name conventions
        - Zero configuration - just declare $type_ref_columns

CONVERTING EXISTING COLUMNS
    To convert a VARCHAR polymorphic column to a type ref:

    1. Migration: seed the registry, map the data, widen the column
    2. Model: declare the column in $type_ref_columns
    3. Model: the relation becomes a plain morphTo()/morphMany()

    With data to preserve:

        // 1. Every class the column names needs a _type_refs row BEFORE the
        //    mapping UPDATE. A migration may not call the registry to make one
        //    (MIGRATION-MODEL-01 - the registry validates against the LIVE
        //    manifest, so a retired class breaks every future replay). Get-or-
        //    create the row directly, class name as a STRING, table name
        //    hardcoded - one call per distinct class stored in the column:
        $type_ref_id = function (string $class_name, string $table_name): int {
            $existing = DB::select(
                "SELECT id FROM _type_refs WHERE class_name = ?", [$class_name]
            );
            if (!empty($existing)) {
                return (int) $existing[0]->id;
            }
            DB::statement(
                "INSERT INTO _type_refs (class_name, table_name, created_at, updated_at)
                 VALUES (?, ?, NOW(3), NOW(3))",
                [$class_name, $table_name]
            );
            return (int) DB::getPdo()->lastInsertId();
        };

        $type_ref_id('Contact_Model', 'contacts');
        $type_ref_id('Project_Model', 'projects');

        // 2. Map the stored class names to their ids IN PLACE. Values still
        //    holding a Laravel FQCN need the basename first:
        //      SET entity_type = SUBSTRING_INDEX(entity_type, '\\\\', -1)
        DB::statement("
            UPDATE my_table t
            JOIN _type_refs r ON r.class_name = t.entity_type
            SET t.entity_type = r.id
        ");

        // 3. Any row whose class no longer exists did not map. Decide
        //    EXPLICITLY - a value the registry cannot resolve throws on read:
        DB::statement("
            UPDATE my_table SET entity_type = NULL, entity_id = NULL
            WHERE entity_type IS NOT NULL AND entity_type NOT REGEXP '^[0-9]+$'
        ");

        // 4. Widen the column. Both halves of the pair are BIGINT.
        DB::statement("ALTER TABLE my_table MODIFY entity_type BIGINT NULL");

    For a fresh table with no data to preserve, step 4 alone is enough.

SECURITY CONSIDERATIONS
    Model Type Validation

        CRITICAL: Always validate that submitted model types are in the allowed
        list. Attackers could submit arbitrary model names to exploit the
        polymorphic relationship.

        The Polymorphic_Field_Helper enforces this automatically:

            // Only Contact_Model and Project_Model are accepted
            $eventable = Polymorphic_Field_Helper::parse($params['eventable'], [
                Contact_Model::class,
                Project_Model::class,
            ]);

            // Submitting {"model":"User_Model","id":1} will fail validation
            $eventable->is_valid();  // false

    Type Ref Auto-Creation

        The type_refs system validates that any new class name is a valid
        Rsx_Model subclass before creating an entry. This prevents attackers
        from polluting the _type_refs table with invalid class names.

    Use Model::class, Not Strings

        Always use the ::class constant to specify allowed models:

            // CORRECT - uses class constant
            Polymorphic_Field_Helper::parse($value, [Contact_Model::class]);

            // WRONG - hardcoded string
            Polymorphic_Field_Helper::parse($value, ['Contact_Model']);

        Using ::class ensures:
        - IDE autocompletion and refactoring support
        - Compile-time error if class doesn't exist
        - Consistent naming with actual class names
