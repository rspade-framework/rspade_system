TIME(7)                     RSpade Framework Manual                    TIME(7)

NAME
       Rsx_Time, Rsx_Date - Date and datetime handling for RSpade applications

TAGS
       time, stdlib, models, api

SYNOPSIS
       PHP Datetime:
           use App\RSpade\Core\Time\Rsx_Time;

           $now = Rsx_Time::now();
           $iso = Rsx_Time::to_iso($datetime);
           $localized = Rsx_Time::to_user_timezone($datetime);
           $formatted = Rsx_Time::format_timestamp($datetime);
           $in_its_zone = Rsx_Time::format_timestamp($entry->started_at, $entry->timezone);
           $relative = Rsx_Time::relative($datetime);

       PHP Date:
           use App\RSpade\Core\Time\Rsx_Date;

           $today = Rsx_Date::today();
           $formatted = Rsx_Date::format($date);
           $relative = Rsx_Date::relative($date);
           $is_past = Rsx_Date::is_past($date);
           $next_week = Rsx_Date::add_days($date, 7);
           $monday = Rsx_Date::start_of_week($date);
           $month_name = Rsx_Date::month_human($date);

       JavaScript Datetime:
           const now = Rsx_Time.now();
           const iso = Rsx_Time.to_iso(datetime);
           const formatted = Rsx_Time.format_timestamp(datetime);
           const relative = Rsx_Time.relative(datetime);

       JavaScript Date:
           const today = Rsx_Date.today();
           const formatted = Rsx_Date.format(date);
           const relative = Rsx_Date.relative(date);
           const is_past = Rsx_Date.is_past(date);
           const next_week = Rsx_Date.add_days(date, 7);
           const monday = Rsx_Date.start_of_week(date);

DESCRIPTION
       RSpade provides two separate classes for handling temporal values:

       Rsx_Time - Datetimes (moments in time)
           Represents specific moments. Always has time component. Timezone-aware.
           Stored in UTC, displayed in user's timezone.
           Format: ISO 8601 "2024-12-24T15:30:45.123Z"

       Rsx_Date - Dates (calendar dates)
           Represents calendar dates without time. Timezone-agnostic.
           "December 24, 2025" is the same day everywhere.
           Format: Always "YYYY-MM-DD" (e.g., "2024-12-24")

   STRINGS, NOT OBJECTS
       All external-facing APIs return STRINGS, not Carbon or Date objects:

           $model->created_at      // "2024-12-24T15:30:45.123Z" (string)
           $model->due_date        // "2024-12-24" (string)
           Rsx_Time::now_iso()     // "2024-12-24T15:30:45.123Z" (string)
           Rsx_Time::to_iso($x)    // "2024-12-24T15:30:45.123Z" (string)
           Rsx_Time::add($x, 60)   // "2024-12-24T15:31:45.123Z" (string)

       This design keeps PHP and JavaScript in sync - identical string formats
       on both sides, no serialization surprises.

       Carbon is used internally for calculations and rarely exposed. In PHP the
       methods returning Carbon are parse(), now(), to_timezone(), and
       to_user_timezone(); everything else returns strings:

           $carbon = Rsx_Time::parse($time);  // Carbon for calculations
           $result = Rsx_Time::to_iso($carbon);  // Back to string for output

   CRITICAL: Type Separation
       Date functions THROW if passed a datetime.
       Datetime functions THROW if passed a date-only string.

       This is intentional. Mixing dates and datetimes causes bugs:
       - "2024-12-24" as datetime would become midnight UTC, wrong in other timezones
       - "2024-12-24T00:00:00Z" as date loses the time information

       Examples of errors:
           Rsx_Time::parse('2024-12-24')
           // THROWS: "Use Rsx_Date::parse() for dates without time components"

           Rsx_Date::parse('2024-12-24T15:30:00Z')
           // THROWS: "Use Rsx_Time::parse() for datetimes with time components"

DATE VS DATETIME
       Use DATE when:
           - Due dates (the task is due on this calendar day)
           - Birth dates (born on this day, no time)
           - Anniversaries, holidays
           - Any value where time of day is irrelevant

       Use DATETIME when:
           - Event start/end times
           - Created/updated timestamps
           - Scheduled appointments
           - Any value where the exact moment matters

       Database columns:
           DATE        - For date-only fields
           DATETIME(3) - For datetime fields (millisecond precision)

RSX_DATE CLASS
       All functions work with "YYYY-MM-DD" format strings.

   Parsing & Validation
       parse($input)
           Returns "YYYY-MM-DD" string or null.
           THROWS on datetime input.

       is_date($input)
           Returns true if input is valid date string.

   Current Date
       today()
           Returns today's date as "YYYY-MM-DD" in user's timezone.
           PHP: $today = Rsx_Date::today();
           JS:  const today = Rsx_Date.today();

       now()
           Alias for today(). Provided for consistency with Rsx_Time::now().

   Formatting
       format($date)
           Display format: "Dec 24, 2025"

       format_iso($date)
           Ensures "YYYY-MM-DD" format.

       relative($date)
           Human-readable relative date.
           "Today", "Yesterday", "Tomorrow", "3 days ago", "in 5 days"

   Comparison
       is_today($date)     True if date is today
       is_past($date)      True if date is before today
       is_future($date)    True if date is after today
       diff_days($d1, $d2) Days between dates (positive if d2 > d1)

   Arithmetic
       add_days($date, $days)
           Add (or subtract with negative) days from date.
           Returns "YYYY-MM-DD" or null if invalid input.

   Week/Month Boundaries
       start_of_week($date)    Monday of the week containing date
       end_of_week($date)      Sunday of the week containing date
       start_of_month($date)   First day of month (YYYY-MM-01)
       end_of_month($date)     Last day of month

       is_weekend($date)       True if Saturday or Sunday
       is_weekday($date)       True if Monday-Friday

   Component Extractors
       All extractors return null for invalid input.

       day($date)              Day of month (1-31)
       dow($date)              Day of week integer (0=Sunday, 6=Saturday)
       dow_human($date)        Full day name ("Monday", "Tuesday", etc.)
       dow_short($date)        Short day name ("Mon", "Tue", etc.)
       month($date)            Month number (1-12)
       month_human($date)      Full month name ("January", "February")
       month_human_short($date) Short month name ("Jan", "Feb")
       year($date)             Four-digit year (e.g., 2025)

   Database
       to_database($date)
           Returns "YYYY-MM-DD" for database storage (same as ISO format).

RSX_TIME CLASS
       All functions accept ISO 8601 datetime strings or Carbon/Date objects.
       All functions RETURN strings (except parse(), now(), to_timezone(), and
       to_user_timezone(), which return Carbon in PHP).

   Parsing & Validation
       parse($input)
           Returns Carbon (PHP) or Date (JS) in UTC.
           Used for internal calculations, not for output.
           THROWS on date-only string input.

       is_datetime($input)
           Returns true if input is valid datetime (not date-only).

   Current Time
       now()           Returns current time as Carbon/Date (for calculations)
       now_iso()       Returns current time as ISO 8601 string (preferred)
       now_ms()        Returns current time as Unix milliseconds

   Timezone Handling
       get_user_timezone()
           Returns the IANA zone this request displays in (e.g.
           "America/Chicago") - see TIMEZONE INITIALIZATION.

       local_date($time, $zone) / local_clock($time, $zone)
       combine_date_and_time($date, $clock, $zone)
       day_start_utc($date, $zone) / day_after_utc($date, $zone)
           A day and a wall clock in a NAMED zone - the day an instant falls on
           there, the instant a date + clock typed there mean, the bounds of a
           date window. See rsx:man time_value_design.

       encode_for_output($field, $value)  (PHP only)
           One timestamp as an external API carries it: the UTC value plus
           $field__localized and $field__localized_tz - see EXTERNAL API.

       to_timezone($time, $tz)           (PHP only)
           Convert datetime to specific timezone. Returns Carbon.

       to_user_timezone($time)           (PHP only)
           Convert datetime to user's timezone. Returns Carbon.

       get_timezone_abbr($time, $tz)
           The zone's abbreviation at that instant - "CST" in January, "CDT" in
           July, "IST", "AEDT" - from the tz database, the same string in both
           languages (FORMATTING). A zone whose tz name is only a number prints
           as "UTC-3" / "UTC+5:30".

       get_user_timezone_source()        (PHP only)
           Where get_user_timezone() came from: explicit | browser | site |
           server (Rsx_Time::TIMEZONE_SOURCE_*) - see RECORDED ZONES.

   Serialization
       to_iso($time)
           Returns ISO 8601 UTC string: "2024-12-24T15:30:45.123Z"

       to_ms($time)
           Returns Unix timestamp in milliseconds.

       to_database($time)   (PHP only)
           Returns MySQL format: "2024-12-24 15:30:45.123"

   Formatting
       Every formatter prints the SAME STRING in PHP and in JavaScript - one
       engine per language over one committed zone-name table (FORMATTING).
       $tz is the zone to print in; omitted, the viewer's (get_user_timezone()).
       null or an unparseable value prints ''; a date-only value throws.

       format_timestamp($time, $tz)      "Oct 9, 2026 2:30 PM"
                                         "Oct 9, 2026 2:30 PM IST" (a zone not yours)
       format_timestamp_short($time, $tz)
                                         "10-09 2:30p", "10-09-25 2:30p" (another year)
       format_time_range($start, $end, $tz, $short)
                                         "Oct 9, 2026 2:30 - 4:00 PM"
       format_date($time, $tz)           "Oct 9, 2026"
       format_time($time, $tz)           "2:30 PM"

   Duration & Relative
       diff_seconds($start, $end)
           Seconds between two datetimes.

       seconds_until($time)
           Seconds until future time (negative if in past).

       seconds_since($time)
           Seconds since past time (negative if in future).

       duration_to_human($seconds, $short)
           Long:  "2 hours and 30 minutes"
           Short: "2h 30m"

       relative($time)
           "2 hours ago", "in 3 days", "just now"

   Arithmetic
       add($time, $seconds)
           Add seconds to time. Returns ISO 8601 string.

       subtract($time, $seconds)
           Subtract seconds from time. Returns ISO 8601 string.

   Comparison
       is_past($time)      True if datetime is in the past
       is_future($time)    True if datetime is in the future
       is_today($time)     True if datetime is today (in user's timezone)

   Component Extractors
       Extract date/time components from a datetime. All require timezone
       parameter ($tz) or use user's timezone if omitted.
       Return null for invalid input.

       day($time, $tz)             Day of month (1-31)
       dow($time, $tz)             Day of week integer (0=Sunday, 6=Saturday)
       dow_human($time, $tz)       Full day name ("Monday", "Tuesday", etc.)
       dow_short($time, $tz)       Short day name ("Mon", "Tue", etc.)
       month($time, $tz)           Month number (1-12)
       month_human($time, $tz)     Full month name ("January", "February")
       month_human_short($time, $tz) Short month name ("Jan", "Feb")
       year($time, $tz)            Four-digit year (e.g., 2025)
       hour($time, $tz)            Hour (0-23)
       minute($time, $tz)          Minute (0-59)

   Live Updates (JavaScript only)
       countdown($element, target_time, options)
           Live countdown to future time. Updates every second.

           const ctrl = Rsx_Time.countdown($('#timer'), deadline, {
               short: true,
               on_complete: () => alert('Done!')
           });
           ctrl.stop();  // Stop the countdown

       countup($element, start_time, options)
           Live elapsed time since past time.

           Rsx_Time.countup($('.elapsed'), started_at, { short: true });

FORMATTING
       One moment, one string, in both languages. Rsx_Time's formatters run on
       one engine per language - Rsx_Timestamp_Format in PHP, its twin in the
       vendor bundle in JavaScript - implementing the same algorithm over the
       same committed zone-name table, so a server-built label and one drawn in
       the browser are byte-identical.

   The Zone Suffix
       " <ABBR>" is appended ONLY when the zone printed differs from the
       viewer's at that instant, judged by BOTH the UTC offset and the
       abbreviation:

           printing in the viewer's own zone          no suffix
           America/Winnipeg for an America/Chicago    no suffix (same offset,
             viewer                                    same name)
           Asia/Kolkata for an America/Chicago viewer " IST"
           America/Los_Angeles in July for an         " PDT" (same offset,
             America/Phoenix viewer                    another name)

       Standard vs daylight is the instant's own, for both zones. The common
       use: a time a person ENTERED in their own day (an activity's start and
       end) is printed in the zone it was entered in, and says so when that is
       not the reader's (rsx:man time_value_design):

           Rsx_Time::format_time_range($entry->started_at, $entry->ended_at, $entry->timezone)

   The Abbreviations
       Taken from the tz database: per zone, each offset it has used since 1970,
       named by its most recent transition; a numeric tz name ("-03", "+0530")
       prints as "UTC-3" / "UTC+5:30"; an offset the table does not know prints
       the same way. Duplicate names across zones (IST is India, Ireland and
       Israel) are kept as they are. The table is a committed file both
       languages read (Core/Time/vendor/rsx_timezone_abbreviations.js),
       regenerated by the framework's maintainers with rsx:time:abbreviations.

   The Three Forms
       format_timestamp() - the LONG form, the application's house style:
           rsx.datetime.display.date + ' ' + rsx.datetime.display.time
           (default "M j, Y" and "g:i A": "Oct 9, 2026 2:30 PM").

       format_timestamp_short() - the DENSE form, for grid cells, logs and
           history rows. Fixed, not configurable: month and day zero-padded, the
           hour not, a/p lowercase with no space; the year only when it is not
           the current year, both judged in the zone printed:
               "10-09 2:30p"   "10-09-25 2:30p"   "10-09 2:30p IST"

       format_time_range($start, $end, $tz = null, $short = false):
           same local day     "Oct 9, 2026 2:30 - 4:00 PM" (a shared meridiem
                              once), "Oct 9, 2026 11:30 AM - 1:00 PM"
                              short: "10-09 2:30-4:00p", "10-09 11:30a-1:00p"
           different days     "Oct 9, 2026 11:00 PM - Oct 10, 2026 1:00 AM"
                              short: "10-09 11:00p - 10-10 1:00a"
           null $end          the start alone, as format_timestamp() prints it
           The separator is an en dash. The suffix comes once, at the end, judged
           at the start. A time pattern with no A / a prints both clocks in full.

       format_date() / format_time() print the date and the clock pattern alone.

   Patterns
       rsx.datetime.display.date / .time take a CLOSED subset of PHP date()
       letters, implemented identically in both languages:

           d j m n M F y Y D l g G h H i s A a

       plus literal punctuation and spaces; a backslash makes a letter literal.
       Any other letter is refused when the configuration is read - loudly,
       naming the letter - because a letter one language implements and the
       other does not is exactly the drift the engine exists to remove.

TIMEZONE INITIALIZATION
       Every timestamp is STORED and TRANSPORTED in UTC. A timezone is used for
       three things only: printing a time in the viewer's zone (server-side
       formatting, Blade renders, the browser's conversions), the localized
       companions on external API timestamps (EXTERNAL API below), and reading
       #[Schedule] wall-clock times - which always use the SERVER timezone.

       Which zone a request displays in is resolved PER REQUEST by
       Rsx_Time::get_user_timezone(). Each tier is skipped when its value is
       absent or not an IANA identifier, so the answer is always a real zone:

           1. a signed-in staff user's EXPLICIT timezone - login_users.timezone
              when it is not NULL (NULL means automatic)
           2. the browser's own zone - the rsx_tz cookie (THE BROWSER COOKIE)
           3. the site's timezone (sites.timezone)
           4. the server timezone (SERVER TIMEZONE below)
           5. UTC

       The explicit zone outranks the cookie because the cookie can be stale on
       the first request after the preference changed in another browser.

       Nothing ever writes a browser's zone to the account. Two browsers in two
       zones on one account each render in their own, and a headless browser
       (rsx:debug) changes nobody's preference.

       On a PORTAL request tier 1 does not exist: portal_users has no timezone
       column, so a portal page starts at the browser's cookie, then the PORTAL's
       site (the one its URL serves, Portal_Session::get_site_id()), never the
       staff session's.

       No cookie outside a browser: an external API request, a task, a command
       and a #[Run_As_Dispatcher] run resolve 1 -> 3 -> 4 -> 5. An automatic
       user's emails and task output therefore render in the SITE zone.

       The resolution is cached per request and invalidated when the
       experience, the user, the site or the cookie changes; a write through
       Rsx_Time::set_user_timezone() clears it explicitly. An invalid stored
       value is never an exception here - it falls through.

   The Browser Cookie
       rsx_tz holds the browser's IANA identifier
       (Intl.DateTimeFormat().resolvedOptions().timeZone): Path=/,
       SameSite=Lax, Secure on https, NOT HttpOnly (JavaScript writes it),
       Max-Age one year. When the browser cannot report a usable zone it holds
       error_reading_browser_timezone for one day, so a browser that failed
       once tries again later; that value is never read as a zone. A staff host
       and a separate portal host each write their own.

       An older spelling a browser reports (Chromium: Asia/Calcutta) that PHP's
       zone database lacks is mapped through ICU to the equivalent PHP knows
       (Asia/Kolkata) - Rsx_Time::normalize_timezone().

       Core/Js/Rsx_Timezone_Cookie.js keeps it current:

           Every page, at core init (before the first Ajax call): signed out, a
           portal page, or an AUTOMATIC user - write the browser's current zone;
           a user with an EXPLICIT zone - clear the cookie. It also strips the
           interstitial's ?_rsx_tz=1 marker from the address.

           An SPA page also WATCHES (started by Spa's router initialization),
           because it may stay open across a zone change. There is no browser
           event for one, so the zone is re-read every minute and on
           visibilitychange / focus. On a change the cookie is updated at once,
           Spa.disable() makes the next link a full page load (the destination
           renders wholly in the new zone), and Rsx_Time stops adopting the zone
           from Ajax envelopes - the current page keeps one zone until that load.
           An explicit-zone user is never watched.

   The First Visit
       A browser's first page view arrives with no cookie, so it cannot be
       rendered in its own zone. The page dispatcher calls
       Rsx_Time::ensure_timezone($request) for every matched page route, after
       its gates:

           false     not concerned: anything but a GET document navigation that
                     wants HTML (Ajax, the external API, a task or a command, a
                     POST, a download, a JSON route, a webhook), a signed-in user
                     with an explicit zone, the cookie's error value, or the
                     reload marker present with still no cookie (the browser
                     refuses cookies: the page renders down the remaining tiers
                     rather than loop)
           true      the cookie holds a zone
           Response  no cookie yet: a minimal page whose one CSP-nonced script
                     writes rsx_tz and reloads the same URL with ?_rsx_tz=1; a
                     <noscript> meta refresh does the same for a client that runs
                     no script (curl sends Accept */* and never sees it)

       The cost is one extra round trip on a browser's first visit. An anonymous
       full-page-cached route (#[FPC]) is never asked: its output is shared.

   Page Load
       On page load, window.rsxapp includes:
           server_time               - ISO 8601 UTC timestamp from server
           user_timezone             - the zone this page was RENDERED in
           user_timezone_preference  - the signed-in staff user's explicit zone,
                                       or null (automatic, a portal page, or
                                       nobody signed in)

       Rsx_Time._on_framework_core_init() reads these automatically.

   AJAX Sync
       Every AJAX response includes _server_time and _user_timezone, and its
       timestamps travel as UTC ISO 8601 - the browser converts.
       Rsx_Time.sync_from_ajax() is called automatically to:
           - Update the user timezone if changed (not once this page detected a
             zone change - see The Browser Cookie)
           - Sync server time offset on first request or timezone change

       This corrects for client clock skew. Rsx_Time.now() returns
       server-adjusted time.

TIMEZONE PREFERENCE
       login_users.timezone holds a staff user's EXPLICIT choice, or NULL for
       AUTOMATIC (each browser's own zone). It is read and written through
       Rsx_Time; nothing else writes it.

   The Standard: A Timezone Belongs To The Person
       The timezone lives on the LOGIN IDENTITY (login_users), never on a site
       membership (users), and there is no setting that moves it. A person who
       works in several tenants is in one place, so one zone reaches every site
       they use - per-site zones would move every clock on the screen when they
       switch sites. The general rule it follows: a preference about the PERSON
       (timezone, dark mode) is a column on login_users; a preference about
       their role in ONE tenant (what they are notified about there) belongs to
       users. A tenant's own need is the SITE zone (sites.timezone - the tier
       after the browser's, and what a scheduled report keys on), and a record
       whose author's zone matters stores that zone on the row
       (rsx:man time_value_design).

       So ONLY THE PERSON sets it - their own Preferences screen, through
       Rsx_Timezone_Controller. A site administrator never edits another user's
       timezone: being global, the change would move the clocks that person sees
       in every OTHER tenant too.

   Reading
       Rsx_Time::get_user_timezone()
           The RESOLVED zone for this request (the chain above). This is what
           every formatter uses when no explicit timezone is passed.

       Rsx_Time::explicit_user_timezone(): ?string
           The signed-in staff user's explicit zone; null when automatic, on a
           portal request, or with nobody signed in.

       Rsx_Time::browser_timezone(): ?string
           The cookie's zone; null when absent, the error value or anything not
           a zone, and always on an external API request.

       Rsx_Time::get_site_timezone()
           The SITE's zone, skipping the user and browser tiers:
           sites.timezone -> the server timezone. Use it for anything that belongs to the tenant
           rather than to the viewer (a scheduled report's day boundary, a
           site-wide business-hours calculation). The site is resolved by the
           EXPERIENCE of the request, exactly as get_user_timezone() resolves it.

   Writing
       Rsx_Time::set_user_timezone(?string $timezone): bool

           Writes login_users.timezone - an identifier, or null for automatic -
           by explicit assignment + save(), then clears the resolution cache so
           the rest of THIS request - including the _user_timezone field on the
           Ajax envelope that carries the response - sees the new zone.

           Returns whether the RESOLVED zone moved: what tells a client its page
           is now in the wrong zone.

           Refusals:
               - Unknown IANA identifier -> InvalidArgumentException (the one
                 refusal driven by user-supplied data; a controller turns it into
                 a validation error).
               - Portal request, or no signed-in login user -> shouldnt_happen().
                 Both are broken assumptions: a portal account has no personal
                 zone to set.

       A NEW login identity whose creator set no zone starts at
       rsx.datetime.default_user_timezone (CONFIGURATION), applied once, when the
       row is created.

       Rsx_Time::timezone_options(): array
           Every IANA identifier mapped to a selectable label carrying its
           CURRENT UTC offset, sorted by identifier:

               'America/Chicago' => 'America/Chicago (UTC-05:00)'

           Offsets are computed at call time, so labels are DST-honest for the
           moment the list is requested (Chicago reads -06:00 in January).

   Rsx_Timezone_Controller (framework-core, staff realm)
       Core/Time/Rsx_Timezone_Controller.php, class-level #[Auth('is_logged_in')].
       Callable from JavaScript like any Ajax controller; the application does not
       wrap it in a pass-through endpoint of its own.

           await Rsx_Timezone_Controller.timezone_options();
               -> [{value: 'America/Chicago', label: 'America/Chicago (UTC-05:00)'}, ...]
                  (Select_Input-native shape)

           await Rsx_Timezone_Controller.get_settings();
               -> {timezone, resolved_timezone}
                  timezone is the stored preference (null = automatic);
                  resolved_timezone is what this request renders in.

           await Rsx_Timezone_Controller.set_timezone({timezone});
               -> {changed, timezone}
                  timezone null or '' = automatic. changed = the RESOLVED zone
                  moved. An unknown identifier returns ERROR_VALIDATION keyed on
                  'timezone'.

   The settings surface
       The template app's user-settings screen
       (/rsx/app/frontend/settings/user_settings/) is the worked example: one
       Select_Input whose first option ('') is "Automatic - follow my browser",
       followed by timezone_options(), saving straight to
       Rsx_Timezone_Controller; on {changed: true} it calls Spa.disable() so the
       next navigation renders in the new zone.

RECORDED ZONES
       Since an automatic user's zone exists only in the browser's cookie for the
       length of a request, the framework RECORDS the zone in effect wherever it
       records who did something, so "what time was it for them?" stays
       answerable:

           _audit_sessions       part of the acting context's KEY - a browser
                                 that changes zone mid-sign-in starts a new audit
                                 session (rsx:man session, AUDIT SESSIONS)
           login history rows    the zone the IDENTITY resolves to: its explicit
                                 zone, else the browser's, else the server's
                                 (a staff identity signs in before any site)
           site sign-in rows     the zone at the moment the sign-in entered the
                                 site (rsx:man session, SITE SIGN-IN HISTORY)

       Each is a pair: timezone (an IANA identifier) and timezone_source:

           explicit   login_users.timezone - the person's own choice
           browser    the rsx_tz cookie - where their browser said it was
           site       neither: the site's zone
           server     nothing better: the server's

       site and server mean the framework did NOT know where the person was. A
       reader must never present such a zone as their location. Nothing is ever
       written to login_users. Reached through the readers each table publishes
       (Session::get_audit_session(), Audit_Session::join(), the histories'
       get_history_for_user() / list_page()) - never the tables.

EXTERNAL API
       An external API response carries, beside each DATETIME/TIMESTAMP value:

           <field>                 UTC ISO 8601, unchanged
                                   2026-10-29T10:13:03.000Z
           <field>__localized      the same instant in the key holder's zone,
                                   ISO 8601 with its offset
                                   2026-10-29T05:13:03.000-05:00
           <field>__localized_tz   that zone's identifier - America/Chicago

       The zone is the chain above with no cookie: the key holder's explicit
       timezone, else the site's, the server's, UTC. A NULL timestamp gets
       three nulls. A DATE column gets NO companions: a calendar date has no
       zone, and converting one moves it a day for an evening value west of UTC.
       Ajax responses carry neither.

       The model serializer (toArray(), which the API's response builder uses)
       adds them for every DATETIME/TIMESTAMP column of an API response, so an
       endpoint returning models needs nothing. A HAND-BUILT payload uses the
       same encoder for each timestamp it writes, so an API response is never
       half-localized:

           return [
               'id' => $file->id,
               ...Rsx_Time::encode_for_output('uploaded_at', $file->created_at),
           ];

INPUT COMPONENTS
       There is NO date-picker or datetime-picker component in RSX, and none is
       planned. Date and time entry is an ordinary Text_Input rendered with a
       native HTML input type; the browser supplies the picker UI and RSX stores
       the string it produces unchanged.

           <Text_Input $name="start_date" $type="date" $max_length=-1 />

       Value formats produced and accepted by the native controls:

           type="date"            "YYYY-MM-DD"    - exactly an Rsx_Date string,
                                                    exactly what a DATE column
                                                    casts to. No conversion.
           type="time"            "HH:MM" (the control also accepts "HH:MM:SS",
                                  which is what a TIME column reads back as).
           type="datetime-local"  "YYYY-MM-DDTHH:MM" - LOCAL wall time, NO
                                  timezone offset, NO seconds. This is NOT an
                                  Rsx_Time string and must not be fed to
                                  Rsx_Time or written to a DATETIME column
                                  unmodified; interpret it in the user's resolved
                                  zone on the server first. Prefer separate date
                                  and time fields.

       A cleared native input submits "", not null - convert it before writing a
       nullable column. A custom widget, if a project ever needs one, extends
       Form_Input_Abstract and implements val() (see form_input(7)).

       Full treatment: php artisan rsx:man datetime_inputs.

DATA FLOW
       Date Field (e.g., due_date)

           Database: DATE column, value "2025-12-24"
                |
           PHP Model: $task->due_date = "2025-12-24" (string)
                | (Rsx_Date_Cast returns YYYY-MM-DD strings, NOT Carbon)
                |
           JSON Response: {"due_date": "2025-12-24"}
                |
           JS Model: task.due_date = "2025-12-24" (string)
                |
           Native <input type="date">: value "2025-12-24"
                |
           Form Submit: {"due_date": "2025-12-24"}
                |
           PHP Controller: Rsx_Date::parse($params['due_date'])
                |
           Database: "2025-12-24"

       Datetime Field (e.g., scheduled_at)

           Database: DATETIME(3), value "2025-12-24 15:30:45.123" (UTC)
                |
           PHP Model: $event->scheduled_at = "2025-12-24T15:30:45.123Z" (string)
                | (Rsx_DateTime_Cast converts MySQL format to ISO 8601)
                |
           JSON Serialize: {"scheduled_at": "2025-12-24T15:30:45.123Z"}
                |
           JS Model: event.scheduled_at = "2025-12-24T15:30:45.123Z" (string)
                |
           Display: Rsx_Time.format_timestamp(...) -> "Dec 24, 2025 9:30 AM"
                |
           EDITING has no picker component. A native datetime-local input emits
           "2025-12-24T10:00" - LOCAL wall time, no offset - so the server must
           interpret it in the viewer's resolved zone before storing (see
           INPUT COMPONENTS and rsx:man datetime_inputs). Values that are already
           ISO 8601 round-trip unchanged.
                |
           Form Submit: {"scheduled_at": "2025-12-24T16:00:00.000Z"}
                |
           PHP Controller: $event->scheduled_at = $params['scheduled_at'];
                | (the cast normalizes to UTC on write - parse() only when the
                |  value needs calculation)
                |
           Database: "2025-12-24 16:00:00.000"

EXAMPLES
       PHP - Date handling:
           $due_date = Rsx_Date::parse($params['due_date']);  // "2025-12-24"

           if (Rsx_Date::is_past($due_date)) {
               return response_error(Ajax::ERROR_VALIDATION, [
                   'due_date' => 'Due date cannot be in the past'
               ]);
           }

           $task->due_date = Rsx_Date::to_database($due_date);
           $task->save();

       PHP - Datetime handling:
           $event_time = Rsx_Time::parse($params['event_time']);

           return [
               'id' => $event->id,
               'event_time' => Rsx_Time::to_iso($event_time),
               'formatted' => Rsx_Time::format_timestamp($event_time),
               'is_past' => Rsx_Time::is_past($event_time),
           ];

       JavaScript - Date display:
           const due = this.data.task.due_date;  // "2025-12-24"
           this.$sid('due').text(Rsx_Date.format(due));  // "Dec 24, 2025"

           if (Rsx_Date.is_past(due)) {
               this.$sid('due').addClass('text-danger');
           }

       JavaScript - Datetime display with countdown:
           const event_time = this.data.event.scheduled_at;  // ISO string

           this.$sid('time').text(Rsx_Time.format_timestamp(event_time));
           this.$sid('relative').text(Rsx_Time.relative(event_time));

           if (Rsx_Time.is_future(event_time)) {
               this._countdown = Rsx_Time.countdown(
                   this.$sid('countdown'),
                   event_time,
                   { short: true, on_complete: () => this.reload() }
               );
           }

ERROR HANDLING
       Wrong type errors are thrown immediately:

           // PHP
           try {
               Rsx_Time::parse('2025-12-24');
           } catch (\InvalidArgumentException $e) {
               // "Rsx_Time::parse() received date-only string..."
           }

           // JavaScript
           try {
               Rsx_Time.parse('2025-12-24');
           } catch (e) {
               // "Rsx_Time.parse() received date-only string..."
           }

       These errors indicate a programming mistake - the wrong function is
       being used. Fix the code rather than catching the exception.

CONFIGURATION
       system/config/rsx.php:
           'datetime' => [
               'server_timezone' => env('RSX_SERVER_TIMEZONE') ?: 'UTC',
               'default_user_timezone' => 'automatic',
               'display' => [
                   'date' => 'M j, Y',     // format_timestamp() and format_date()
                   'time' => 'g:i A',      // format_timestamp(), format_time(), ranges
               ],
           ],

       display is the application's house format for a moment (FORMATTING,
       Patterns), set in rsx/resource/config/rsx.php; the browser receives the
       same values in window.rsxapp.datetime_display.

       default_user_timezone is application behaviour, so it has no .env key: an
       application sets it in rsx/resource/config/rsx.php
       ('datetime' => ['default_user_timezone' => 'site']).

       default_user_timezone is the zone a NEW login identity starts with when
       its creator set none, applied once at creation and never on a later save:

           automatic       NULL - each browser's own zone (the default)
           site            the creating site's timezone, COPIED as an identifier
           server          server_timezone, COPIED as an identifier
           <IANA id>       that identifier (e.g. America/Chicago)

       site and server are snapshots: a later change to the site's or the
       server's zone does not reach an account created before it. Anything else
       throws when a login identity is created.

       User timezone stored in login_users.timezone column (staff only - a portal
       account has no personal timezone); NULL is automatic. See TIMEZONE
       PREFERENCE.
       Site timezone stored in sites.timezone column; a site created through
       the model without one takes the server timezone (the column's own
       database default, 'America/Chicago', covers only a row inserted beneath
       the model).

SERVER TIMEZONE
       Every RSpade process RUNS in UTC, whatever the host's clock is set to:
       PHP's default zone is UTC (config/app.php) and every MySQL connection
       sets its session time_zone to +00:00, so TIMESTAMP columns,
       CURRENT_TIMESTAMP defaults and NOW() agree with the UTC strings PHP
       writes. Nothing an application stores or sends is in any other zone.

       RSX_SERVER_TIMEZONE in .env names the server's zone (an IANA
       identifier; blank or absent = UTC; an unknown one throws). It is
       read through Rsx_Time::get_server_timezone() and used in three places:

           #[Schedule]     wall-clock times are read in it - "daily at 2am"
                           with America/Chicago is 2am Chicago time
                           (rsx:man tasks, SCHEDULES AND TIMEZONES)
           new sites       Site_Model fills sites.timezone with it when a new
                           record was not given one
           display         the tier after the site's in the resolution chain above

       Rsx_Time::get_system_timezone() is a different thing: the OPERATING
       SYSTEM's zone (TZ, the /etc/localtime link, /etc/timezone; UTC when
       none is set). Only log timestamps use it - laravel.log is stamped in the
       host's own clock, so it agrees with `date` and the host's other logs.
       In a container, that is the container's zone.

MODEL CASTING
       Model date/datetime columns are automatically cast to strings via custom
       Eloquent casts. No configuration needed - columns are detected from the
       database schema.

       Rsx_DateTime_Cast (for DATETIME/TIMESTAMP columns)
           - Database read: "2024-12-24 15:30:45" -> "2024-12-24T15:30:45.000Z"
           - Database write: "2024-12-24T15:30:45.000Z" -> "2024-12-24 15:30:45"
           - Accepts: ISO 8601 strings (any offset - normalized to UTC), MySQL
             datetime strings (taken as already UTC), Unix timestamps in seconds
             or milliseconds, and a Carbon object; "" and null become NULL
           - Rejects: any other shape, with an InvalidArgumentException naming
             the column - a bad value here is a programming error, not a
             validation failure

       Rsx_Date_Cast (for DATE columns)
           - Database read: "2024-12-24" -> "2024-12-24"
           - Database write: "2024-12-24" -> "2024-12-24"
           - Accepts: YYYY-MM-DD strings only
           - Rejects: Carbon objects, datetime strings

       Why strings instead of Carbon?
           1. Prevents timezone bugs - dates have no timezone, Carbon assumes one
           2. PHP/JS parity - identical formats on both sides
           3. No serialization surprises - what you see is what you get
           4. Simpler mental model - just strings everywhere

       Casts are AUTOMATIC and are not overridden.
           The cast for a column follows from its database type. Declaring
           $casts with 'date' / 'datetime' / 'timestamp' re-introduces Carbon and
           is a MODEL-CARBON-01 violation (rsx:check) - there is no supported way
           to opt a column back onto Laravel's default. If a column needs
           different behavior, the column's TYPE is what is wrong.

       Writing is plain assignment.
           Rsx_DateTime_Cast::set() accepts an ISO 8601 string (any offset - it
           normalizes to UTC), a MySQL "Y-m-d H:i:s" string (taken as already
           UTC), a Unix timestamp in seconds or milliseconds, or a Carbon object,
           and turns "" or null into NULL. Anything else throws. So:

               $event->scheduled_at = $params['scheduled_at'];  // ISO in, UTC stored
               $event->save();

           Rsx_Time::to_database() still exists for the cases that want the MySQL
           string explicitly (a raw DB::statement(), a query binding), but it is
           NOT required to assign a model attribute.
