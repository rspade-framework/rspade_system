NAME
    form_input - The Form_Input_Abstract contract: one named value, buffered,
    announced

SYNOPSIS
    class My_Custom_Input extends Form_Input_Abstract {
        _get_value()      { return this.$sid('input').val(); }
        _set_value(value) { this.$sid('input').val(value ?? ''); }

        on_render() {
            this._mark_ready();

            const that = this;
            this.$sid('input').on('input', function () {
                that._notify_input(that._get_value());
            });
        }
    }

DESCRIPTION
    An input is a component that owns ONE named value. Form_Input_Abstract
    (framework core, Core/Forms/Form_Input_Abstract.js) owns the whole value
    contract - buffering, the val() getter/setter, events, the data-name
    attribute - so a concrete input only describes how its value maps to its DOM.

    An application never carries a copy of the base class; it reaches every
    bundle through Core_Bundle.

    Unlike an ordinary jqhtml component:
        - an input has NO on_load(), so this.data is always {}
        - its template renders EMPTY - no value attribute, ever; the form writes
          the value through val() after render
        - .Form_Input_Abstract is stamped automatically; never add a marker class

    Where the value goes once it exists is form_conventions(3).

THE FOUR MEMBERS

    _get_value()          REQUIRED - read the current value from the DOM/library
    _set_value(value)     REQUIRED - write a value to the DOM/library
    _mark_ready()         call at the earliest moment a _set_value() would stick
    _notify_input(value)  call when the USER changed the value through the UI

    _validate(value)      OPTIONAL and almost never used - see THE _validate()
                          EXCEPTION

    NEVER OVERRIDE val(). It is where buffering and events live; different
    read/write behaviour is expressed through _get_value()/_set_value(). An
    unimplemented pair throws by name:

        My_Custom_Input must implement _get_value()
        My_Custom_Input must implement _set_value()

    A concrete class that overrides on_create() MUST call super.on_create() -
    that is where buffering state is initialized and data-name is stamped.

BUFFERING: SETTABLE BEFORE READY, ALWAYS

    val(v) may be called at ANY point in the component's life - before an option
    list has been fetched, before the underlying library has instantiated, before
    the DOM exists. The value is buffered and applied at _mark_ready().

    THE CONTRACT IS TIMING INDIFFERENCE. val(value) produces identical results
    whether called before initialization, after it, or at any point between. If a
    caller needs await component.ready() or a timing trick to make val() work,
    THE COMPONENT IS BROKEN - and so is a _set_value() whose behaviour depends on
    initialization state.

    The pending slot is tracked with a BOOLEAN flag, so null, 0, false and '' all
    buffer faithfully. null is a legitimate value (most nullable columns), never
    a sentinel; do not reintroduce a null test as "no value".

    While a value is pending, val() as a GETTER returns it - so a form serialized
    before every input finished initializing still reports what was set.

LIFECYCLE: EDITABLE AS SOON AS POSSIBLE

    Initialize in on_render() whenever the input's DOM is self-contained; the
    input becomes editable as early as possible. Use on_ready() only when
    initialization genuinely depends on child components or an async library.

    Call _mark_ready() at the earliest moment a programmatic _set_value() would
    stick:

        plain text input        on_render()
        TomSelect-backed input  after the library instantiates
        server-fed select       after the options arrive
        Quill editor            inside the library's ready callback

    class Wysiwyg_Input extends Form_Input_Abstract {
        on_ready() {
            const that = this;
            quill_ready(function () {
                that._initialize_quill();
                that._mark_ready();          // AFTER the library is usable
            });
        }
    }

    Renders REBUILD the DOM. An input that draws its own rows in JavaScript
    therefore draws them from STATE in on_render(), and every user edit writes
    back to that state - anything drawn once imperatively vanishes on the next
    render. Worked example:
    system/app/RSpade/resource/reference_app/theme/components/inputs/tag_list/
    tag_list_input.js

EVENTS

    'input'   the USER changed the value through the UI
    'val'     the value changed, by any path (user or programmatic val(v))

    'input' is fired ONLY through _notify_input(value), which fires 'input' then
    'val', in that order. Hand-triggering the pair is a defect: the ordering and
    the pairing belong to the base class, and a call site that fires only one of
    them silently breaks every listener expecting the other.

    _mark_ready() applying a buffered value fires 'val' - the value did change.
    With nothing buffered it fires NOTHING: readiness is not a value change, and
    listeners wired to "on change" must not fire on load.

    Because jqhtml replays an already-fired event to a late .on(), a 'val'
    listener registered after the fact fires immediately with the current value
    and then on every subsequent change:

        this.sid('country').on('input', (c, v) => this.reload_states(v));  // user only
        this.sid('amount').on('val',  (c, v) => this.update_total(v));     // all changes

    From a form, reach one input with form.input(name) rather than a selector.

NAMING

    $name is required on every input that participates in a form. The base class
    stamps it as data-name on the component root; that attribute is how Rsx_Form
    discovers inputs and how the error renderer targets them. data-name is a LIVE
    CONTRACT ATTRIBUTE, not a debug attribute - never hand-write it, never strip
    it.

    $name goes on the INPUT, never on Form_Field. A Form_Field reads its child's
    data-name for accessibility wiring and shouldnt_happen()s without one:

        Form_Field_Abstract child input has no data-name attribute.

THE _validate() EXCEPTION

    Validation lives on the server, once. A client check that duplicates a server
    rule MASKS the absence of the server rule: blank never reaches the endpoint,
    the missing server validator is never exercised, and the gap surfaces only
    when an API caller or a script hits the endpoint directly - silently, in
    production. Full reasoning: form_conventions(3).

    _validate(value) returns null (valid) or a user-facing message string, and
    exists SOLELY for a constraint whose invalid state cannot even be EXPRESSED
    to the server: a pick-at-most-two multiselect where a third selection is
    unrepresentable in the payload, a structured value that cannot serialize when
    malformed. Its message renders through the same pipeline as a server error,
    so there is no second styling path.

    NEVER for required, format, length or range. And even where it is legitimate,
    prefer interaction design: the best pick-at-most-two multiselect simply
    refuses the third click and needs no message at all. Almost every input keeps
    the inherited no-op forever.

VALUE COERCION

    An input must accept both string and numeric values: a select whose option
    values are "3", "5", "9" must work with val(3) and val('3') alike.

        selects / discrete values   convert to string before comparing
        text inputs                 jQuery's .val() handles it
        checkboxes                  accept 1, '1' and true as checked

    class Checkbox_Input extends Form_Input_Abstract {
        on_create() {
            super.on_create();
            this.checked_value = this.args.checked_value || '1';
            this.unchecked_value = this.args.unchecked_value || '0';
        }
        _get_value() {
            return this.$sid('input').prop('checked')
                ? this.checked_value : this.unchecked_value;
        }
        _set_value(value) {
            this.$sid('input').prop('checked',
                value === this.checked_value || value === '1' || value === 1 || value === true);
        }
    }

EXTENDING ANOTHER INPUT

    class Select_Ajax_Input extends Select_Input {
        async on_load() {
            this.data.select_values = await Controller.get_options();
        }
        on_ready() {
            super.on_ready();   // parent instantiates TomSelect and _mark_ready()s
        }
        // _get_value() / _set_value() inherited
    }

    Overriding a parent's _set_value() to add behaviour calls super._set_value();
    it never becomes a val() override.

BUILT-IN INPUTS

    The inputs themselves are APPLICATION components (the template ships a full
    set under theme/components/inputs/); only the base class is framework core.

    Text_Input
        text, email, url, tel, number, date, textarea.
        $max_length is REQUIRED - a positive number sets the HTML maxlength, -1
        means unlimited, and omitting it is a console error.

            <Text_Input $name="email" $max_length=User_Model.field_length('email') />
            <Text_Input $name="notes" $type="textarea" $rows=5 $max_length=-1 />

        field_length('column') is generated from the database schema and returns
        null for a non-varchar column. Subclasses (Phone_Text_Input,
        Currency_Input) are exempt from the requirement - they have intrinsic
        limits.

    Select_Input                  dropdown with a static options array (TomSelect)
    Select_With_Description_Input dropdown with a description line per option
    Select_Ajax_Input             dropdown whose options load from a controller
    Select_Country_Input          country picker
    Select_State_Input            state picker
    Checkbox_Input                single checkbox, configurable checked value
    Checkbox_Multiselect_Input    checkbox group whose value is an array
    Hidden_Input                  hidden value, no Form_Field wrapper
    Tag_List_Input                a list of short strings as one array value
    Pin_Input                     fixed-length code entry
    Profile_Photo_Input           photo upload and crop
    Repeater_Simple_Input         repeating simple values
    Wysiwyg_Input                 rich text (Quill), async initialization

    $disabled=true renders the control disabled but the input STILL SERIALIZES -
    useful for a value the user may not change but the endpoint still receives.

CREATING A CUSTOM INPUT

    1. A jqhtml template rendering EMPTY elements, no class="Widget".
    2. A class extending Form_Input_Abstract.
    3. _get_value() and _set_value().
    4. _mark_ready() at the earliest writable moment.
    5. User interaction wired to _notify_input(value).

        <Define:My_Custom_Input>
            <input type="text" $sid="input" class="form-control" />
        </Define:My_Custom_Input>

    A value in the template - value="<%= this.data.value %>" - is wrong twice
    over: inputs have no this.data, and the form is what supplies values.

COMMON MISTAKES

    Overriding val()
        Implement _get_value()/_set_value(). The base class owns buffering and
        events.

    Forgetting _mark_ready()
        A buffered value is never applied, and the field silently stays empty.

    Calling _mark_ready() too early
        For async initialization, wait until the library or option list is
        actually usable.

    Hand-triggering 'input' + 'val'
        Call _notify_input(value).

    Overriding on_create() without super.on_create()
        Buffering state and data-name never initialize.

    Using this.data
        Inputs have no on_load(); this.data is always {}.

    Writing a required/format/length check
        That rule is the server's. See THE _validate() EXCEPTION.

    Treating null as "no value"
        The buffer tracks presence with a boolean; val(null) buffers and applies
        null.

TROUBLESHOOTING

    Value not appearing
        _mark_ready() missing or called before the input can accept a write;
        _set_value() not actually touching the DOM; $sid mismatch.

    Value lost on re-render
        The input draws from a handle instead of from state - redraw in
        on_render().

    Form does not see the input
        No $name (so no data-name), or the input does not extend
        Form_Input_Abstract, or it sits inside a composite input (serialization
        is shallow, and that is correct - the composite owns it).

    A listener fires on page load
        It is on 'val', which is every change including the seed. Use 'input' for
        user-only reactions.
