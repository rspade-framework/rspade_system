RSX TASK SYSTEM
================

NAME
    Tasks - background and scheduled work: one recorded run per execution, structured
    reports, gated lifecycle control and the widgets that show a run live

SYNOPSIS
    Define a task (a public static Service method with #[Task]):
    -----------------------------------------------------------
    #[Task('Generate report')]
    public static function generate_report(Task_Instance $task, array $params = [])
    {
        $task->status('Loading rows');
        $task->progress_count(120, 480);
        $task->stdout('wrote report.csv');
        $task->attach_file('report', $path);
        $task->summary('480 rows exported.');
        return null;                          // null, true or 0 = success
    }

    Run it now, in this process (CLI):
        php artisan rsx:task:run Service_Name generate_report --param=value

    Run it in the background (returns the run's id):
        $id  = Task::dispatch('Service_Name', 'generate_report', $params);
        $run = Task_Run_Model::find($id);     // status_id, status_text(), progress_percent(), ...

    Run it on a schedule:
        #[Task('Nightly cleanup')]
        #[Schedule('daily at 3am')]           // or standard cron '0 3 * * *'
        public static function cleanup(Task_Instance $task, array $params = []) { ... }

    Act on a run:
        $run->request_stop();                 // graceful: the task stops at its next check
        $run->force_stop(30);                 // ask, then kill after 30 s
        $run->force_kill();                   // kill now
        $run->cancel();                       // a pending run never runs
        $new_id = $run->rerun();              // a finished run, again

    Show a run in a page (Core widgets, every bundle):
        <Task_Status_Badge $task_id=this.args.id />
        <Task_Report $task_id=this.args.id $kind="progress" $bar=true />
        <Task_Output $task_id=this.args.id />
        <Task_Report_Browser $task_id=this.args.id />

DESCRIPTION
    RSX runs background work as static Service methods marked #[Task]. Unlike Laravel
    queues (job classes, a queue driver, queue:work daemons, Horizon), there is nothing to
    write but the annotated method: the framework owns the durable queue (MySQL), three
    worker pools accounted by the rsx-lockd daemon, the schedule, and the recovery of work
    whose worker died. Redis plays no part in running tasks.

    EVERY EXECUTION IS A RUN, AND EVERY RUN IS A _tasks ROW (Task_Run_Model): a dispatched
    run, each run of a #[Schedule], and every inline run - Task::internal(), rsx:task:run
    and a #[Command] alias included. The row carries the lifecycle, who started it and for
    which site, the worker that ran it, and the task's small live reports; the larger
    reports, the output lines, the messages and the attached files live in side tables
    keyed to it. A task WRITES all of it through its Task_Instance; outside code READS it
    through Task_Run_Model and acts on the run through the lifecycle methods.

    THE ONE KEY POINT: TASKS RUN CONCURRENTLY AND UNGUARDED
    -------------------------------------------------------
    NOTHING takes a global application lock - not artisan, not task workers, and not web
    requests. Multiple workers run at the same time, and a task shares the database with
    concurrent web requests and other tasks. Therefore:

      * A #[Task] method MUST NOT assume it is the only writer, or that only one kind of
        task runs at a time. If a critical section cannot tolerate a concurrent writer,
        the task acquires its own lock (RsxLocks, see LOCKS).
      * #[Exclusive] / #[Debounce] guarantee single-instance for ONE identity - they do
        NOT protect a shared table from OTHER tasks or from web writers. Use a named or
        per-site lock for that.

RUNS

    Origins (origin_id):
        Dispatched   Task::dispatch(), and a rerun - claimed by a pool worker
        Scheduled    a due #[Schedule] - its run row is created by the scheduled-pool
                     worker that claims it, linked by schedule_id
        Inline       Task::internal(), rsx:task:run, a #[Command] alias and
                     rsx:task:process --once - run in the calling process

    Status (status_id), with the Task_Run_Model constants:
        1 Pending    STATUS_PENDING     queued; scheduled_for says when it is due
        2 Running    STATUS_RUNNING     claimed; worker_pid / worker_host say where
        3 Completed  STATUS_COMPLETED   the task returned success
        4 Failed     STATUS_FAILED      a failure return, a throw, or an abandonment
                                        that is not retried
        5 Stopped    STATUS_STOPPED     the task returned success after a stop was
                                        requested: it stopped early, at a clean point
        6 Killed     STATUS_KILLED      a kill worker killed it (force stop, force
                                        kill, timeout, rsx:tasks:kill-all)
        7 Cancelled  STATUS_CANCELLED   taken off the queue before it ran

    Pending and Running are LIVE (Task_Run_Model::LIVE_STATUSES, is_live()); the other
    five are terminal (is_terminal()). A terminal run never changes again, except that a
    rerun creates a NEW run.

    Each row records dispatched_by (a type-ref pair: the User_Model, Portal_User_Model or
    Login_User_Model signed in when the run was created, null for a schedule, a worker or
    the CLI) and site_id (the current site, 0 when there is none). Those two columns are
    what an application's view gate keys on (GATES AND THE BROWSER API).

REPORTING (Task_Instance)

    The $task handle passed to every task method. Every report is optional; a task uses
    whichever describe its work.

        $task->heartbeat()                     "still alive" - stamps last_heartbeat_at
        $task->status(string $text)            one line of status, replacing the last; a
                                               CHANGED status is also written to stderr,
                                               so the output reads as a narrative.
                                               Newlines become spaces; cut to 1000 chars.
        $task->progress(float $percent)        0-100, two decimals, clamped
        $task->progress_count(int $done, int $total)   "3 of 257"
        $task->eta(int $seconds)               seconds from now; stored as the moment
                                               (eta_at), so a viewer counts down alone
        $task->state(array|object $state)      a JSON state object, replacing the last
        $task->queue_push(string|array $item)  THE QUEUE - the items the task has ahead of
        $task->queue_push_many(array $items)   it, one stored row per item, advanced as
        $task->queue_pop()                     the work advances. See THE QUEUE below
        $task->queue_remove(string|array $item)
        $task->queue_clear()
        $task->queue_depth(): int
        $task->message(string $text)           a message for whoever is watching; kept,
                                               in order, for as long as the run is
        $task->stdout(string $text)            output lines, one row per line
        $task->stderr(string $text)
        $task->attach_file(string $name, string $path, ?string $file_name = null,
                           ?string $mime_type = null)
        $task->attach_bytes(string $name, string $bytes, string $file_name,
                            ?string $mime_type = null)
                                               a named file for the run's initiator
                                               (ATTACHMENTS below); the bytes become a
                                               temp file (rsx:man temp_files) and the
                                               same name again replaces the file
        $task->summary(string $text)           the completion summary
        $task->flush()                         write every held report now

    ECHO IS STDOUT. Everything the task prints (echo, print, var_dump) is captured line by
    line as stdout, wherever the run executes - a worker, an inline run, a console run -
    and passed through unchanged, so a console runner still shows it. Output the task
    buffers itself (ob_start around a rendered view) is its own and is never recorded.

    WRITE RATE, NOT A TIMEOUT. A task may report on every item of a long loop, and writing
    each report would cost a database write and a realtime frame per item. Reports are held
    in memory and written together: the first report after a quiet spell is written at
    once, and further reports within Task_Instance::FLUSH_INTERVAL (0.25 s) of the last
    write wait for the first reporting call or is_stop_requested() after the interval, a
    flush() or the end of the run. is_stop_requested() reads the run's row on every call,
    so a stop is seen at once, but writes nothing more often than this rate - which is
    what makes a stop check and a heartbeat on every item of a loop cheap. A task about to
    go quiet for a long step calls flush() first so its watchers see
    where it is. Attachments are written immediately. REPORT ON EVERY ITEM: holding
    reports back is the framework's job, and a task that batches its own reports - the
    queue every 25th item, say - only makes its watchers that much staler. The heartbeat plays no part in worker
    liveness (THE WORKER POOLS): a task may run for hours without reporting anything.

    THE QUEUE. A percentage and a counter cannot tell a run that is stuck from one working
    through something large. The queue can: the same items sitting at its head for ten
    minutes is a stall, and a head that keeps moving is simply a big job. That signal
    exists only when the queue is advanced as the work advances, so it is built to be
    advanced on EVERY item - each item is its own row, a push is one row appended, a pop
    one row removed, and the rows in between are never rewritten.

        queue_push($item)         append one item to the tail: a string, or an array
                                  (recorded as JSON)
        queue_push_many($items)   append a list of items, in order
        queue_pop()               remove the head - the oldest item: "the head is done".
                                  Nothing on an empty queue
        queue_remove($item)       remove ONE item equal to $item, the earliest: work
                                  finished out of order. The match is the exact value
                                  that was pushed - case-sensitive, never a substring -
                                  and a queue holding duplicates loses one of them.
                                  Nothing when no item matches
        queue_clear()             empty the queue
        queue_depth()             how many items it holds

    queue_clear() followed by queue_push_many() DECLARES the queue: whatever it held, it
    now holds exactly those items. Use that at the start of a phase, and whenever the task
    would rather restate the truth than adjust it.

    A list of a few hundred items is pushed whole and popped as each finishes; the widget
    shows the head and counts the rest. For a list too large to push, slide a WINDOW:

        $task->queue_clear();
        $task->queue_push_many(array_slice($labels, 0, 100));

        foreach ($work as $i => $item) {
            // ... the work for this item ...

            $task->queue_pop();                          // the head is done
            if (isset($labels[$i + 100])) {
                $task->queue_push($labels[$i + 100]);    // one more comes into view
            }
        }

    IT IS A REPORT, NOT A WORK QUEUE. The task's real work list is its own array or query;
    the queue describes it to a watcher. queue_pop() returns nothing, and a task never
    drives itself from what it reported.

    The report comes into being with its first ITEM. queue_clear() and queue_pop() on a
    queue that has never held one record nothing, and the run has no queue report; once it
    has held one, an emptied queue reads as an empty queue.

    The queue calls are held and written at the rate described above like every other
    report, in the order they were made - a slide of the window is one small DELETE and one
    small INSERT however many items it covered. queue_remove() alone is written at once,
    because which row it removes depends on what the queue holds.

    Stop check (cooperative - see LIFECYCLE CONTROL):
        $task->is_stop_requested()             reads the row (every call); held reports
                                               are written at the usual rate

    Identity and scratch space:
        $task->get_id(), get_class(), get_method(), get_params()
        $dir = $task->get_temp_dir()           tmp/tasks/task_<id>/, removed when the
                                               run ends

    A console runner (rsx:task:run, a #[Command]) also hands the instance its own stdout
    and stderr, and output lines are echoed there live. Nothing else does: a task run from
    a web request or a worker prints to nobody's console. A task cannot tell which is
    happening and must not try to.

DESIGNING A TASK'S REPORTING

    Every task is written with its watchers in mind. A run is shown live in the
    developer console (/_sys/tasks) and, through the application's gates, to the users
    who started it; what the task reports is all anyone can see of it. When writing a
    task, decide which reports describe ITS work and use those - every one that applies,
    and none that does not:

        status()            what it is doing now ("Importing contacts", "Sending batch
                            4"). Almost every task that does more than one thing has
                            one; each change is also a stderr line, so the output
                            reads as a narrative.
        stdout() / stderr() the narrative itself: what was done (stdout), and what
                            went wrong but did not stop the run - a skipped record, a
                            retried call (stderr). See SAY WHAT THE RUN DID below.
        progress indicator  ONE of progress() or progress_count() - see below.
        eta()               when the task can estimate its finish.
        state()             the task's working state worth inspecting - counters, the
                            current batch.
        the queue           what is still ahead, advanced per item (THE QUEUE above):
                            the one report that shows whether a run is moving or stuck.
                            Any task working through a list of nameable things has one.
        message()           events a watcher should notice (a milestone reached).
        summary()           what the run did, in a sentence, at the end.

    SAY WHAT THE RUN DID - AND SAY SO WHEN IT DID NOTHING. A run's output is shown live
    and kept with the run, so it is read by somebody asking "what did this do?" Write it
    to answer that:

      - NAME EACH THING THE RUN ACTS ON, as it acts, with the outcome on the same line -
        the id, what a person would call it, and what happened:

            Sent #4812 to dana@example.com "Your invoice for March" (<message-id>)
            Server error #4813 to lee@example.com "Welcome" attempt 2/3: 451 try later
            Destroyed attachment #77 "contract.pdf" (1.4 MB), deleted 2026-09-01

        A line that only counts ("Sent 2 messages") cannot answer "was mine one of them?"

      - AN IDLE RUN SAYS IT WAS IDLE. "No mail was due." "No sessions are past their idle
        window; nothing deleted." A scheduled run with no output is indistinguishable from
        one that never looked, and every run is its own record, so the line costs nothing.

      - A RUN THAT SKIPS SAYS WHY ("Log rotation is disabled ...; nothing was done."), and
        a run that was STOPPED says how far it got.

      - END WITH THE OUTCOME in one line - the totals, after the items.

      - DO NOT FLOOD. Name items when there are few enough to read, or when each one
        matters (a message sent, a file destroyed). For bulk housekeeping - ten thousand
        expired rows - one line with the count is the whole story. A task that might list
        thousands of items lists the first couple of hundred and counts the rest.

    The summary() is not a substitute: it is the one sentence a reader is shown ABOUT the
    run, and a task normally writes the closing line and the summary both.

    ONE PROGRESS INDICATOR, AND ONLY WHERE PROGRESS IS A THING THE TASK HAS. A task that
    works through a measurable amount of work reports it with exactly one indicator:
    progress_count($done, $total) when it counts items (the percentage is derived from
    it), or progress($percent) when its measure is not a count (bytes, weighted phases).
    Never both, and never two percentages for two halves of one run. A task whose only
    honest values are 0% and 100% - one document converted, one remote call made - has
    no progress to report and reports none: status() and the run's own lifecycle already
    say "working" and "done".

    A TASK THAT LOOPS - over a queue, a list of records, a set of steps - calls two
    things on every item or step:

        $done = 0;
        foreach ($records as $record) {
            if ($task->is_stop_requested()) {     // cooperative stop (LIFECYCLE CONTROL)
                $task->summary("Stopped after {$done} of {$total} records.");
                return null;                       // settles STOPPED
            }
            $task->heartbeat();                    // "still alive", for its watchers

            // ... the work for this item ...

            $done++;
            $task->progress_count($done, $total);
        }

    is_stop_requested() is what makes the run stoppable at all: without it a graceful
    stop is never answered and only a kill ends the run. Check it where stopping leaves
    the data coherent - between items, never in the middle of one - and return success
    (null) so the run settles STOPPED with whatever it finished. heartbeat() lets a
    watcher tell a slow item from a stuck one. Both are cheap: reports are written at a
    rate (REPORTING, WRITE RATE, NOT A TIMEOUT), not per call. A task with a single long step
    and no loop needs neither, beyond one flush() before it goes quiet.

ATTACHMENTS: A FILE FOR THE RUN'S INITIATOR

    attach_file() / attach_bytes() exist for ONE shape of task: a one-time run started
    by a user action, which produces a file the initiator is WAITING FOR - the caller
    polls (or watches) the run and takes the file when it completes. An export is the
    archetype: "Export to CSV" dispatches a task, the page shows its progress, and the
    finished CSV is downloaded from the run. The attachment saves that task from building
    a storage table, a download endpoint and a cleanup of its own for a file that only
    one person, once, will fetch. A run may also attach an advanced DEBUG artifact of
    itself (a trace, a dump of what it saw) for a developer reading the run later.

    It is NOT how a task delivers results. A task whose work belongs to the application
    - a document converted, records imported, a report built for everyone to read -
    writes the result into the application's own tables and files, where the application
    reads it, keeps it and authorizes it. A task attachment is a TEMP FILE
    (Rsx_Temp_Files; rsx:man temp_files) - its own bytes under uploads/_temp, never a
    shared blob - deleted with the run's output after
    rsx.tasks.retention.output_truncate_after_minutes (RETENTION), with the temp file's
    own expiry a day later as the backstop. It is readable only through the task gates
    and belongs to a run, not to any record. (The
    framework's own document conversion is the example of the other shape: it writes
    its renditions to the blob it converted, and has no attachment.)

    Use an attachment only when the ordinary pattern - store the result, then let the
    initiator fetch it - would be needless machinery for a one-time run whose whole
    output is a file for the person who asked for it.

THE RETURN CONTRACT

    A task's return value is its RETURN CODE (Task_Run_Outcome, decided in one place):

        null, true, 0        success          (compared with ===; 0 is never "false")
        false                failure, return code 1
        any other integer    failure, that return code
        anything else        failure, return code 1, with an error naming the contract
        a throw              failure, return code 1, the exception recorded as the error

    A task reports DATA with summary(), state(), the queue or (for a file its
    initiator is waiting for) an attachment - never through its return value; returning an array is a failed run. Any Throwable counts as
    a throw: a TypeError settles exactly like an Exception.

    A successful run settles COMPLETED, or STOPPED when a stop had been requested; a
    failed run settles FAILED, with a "Task failed: <error>" line written to its stderr.
    The settle matches only a row still RUNNING, so a run a kill worker already settled
    KILLED keeps that verdict.

STARTING A RUN

    1. Background: Task::dispatch($service, $method, $params = [], $options = []): int
       Inserts a PENDING row and, when it is due now, spawns a detached worker if a pool
       has room (on_demand first, then scheduled). Returns the run's id. With both pools
       full nothing is spawned: a busy worker reaches the row when it finishes its current
       one, and the cron tick covers the rest. A process that called
       Task::spawn_workers(false) - and every test, unless it opted in - ENQUEUES ONLY (see
       SPAWNING OFF and TESTING).

       $options (any other key throws):
         'scheduled_for'  earliest run time. A FUTURE value is the only thing that defers a
                          run (the cron tick or a later spawn picks it up once due). Refused
                          (throws) for an #[Exclusive]/#[Debounce] task, whose timing is the
                          coalesced pending row's (CONCURRENCY).
         'timeout'        the run's execution cap in seconds (EXECUTION TIMEOUT)

       For an #[Exclusive]/#[Debounce] task the id returned is THE pending run of its
       identity - the existing one, or the one just created.

    2. Inline: Task::internal($service, $method, $params = []): Task_Run_Model
       Runs the task in THIS process and returns its settled row. The run is recorded like
       any other (origin Inline): its row, its reports, its output, its revision unit of
       work. A task that THROWS is settled FAILED and the exception is rethrown; a failure
       return is settled FAILED and returned (read status_id and return_code). An
       #[Exclusive]/#[Debounce] task first takes its identity's run lock, waiting for a
       running instance to finish. A fatal error that ends the process mid-run settles the
       row FAILED from a shutdown function, so it is never left RUNNING.

    3. Console: php artisan rsx:task:run <Service> <method> [--key=value ...]
       Task::internal() with the command's own stdout and stderr attached: the task's
       stdout is the command's stdout, its stderr (every status() change and the failure
       line included) is the command's stderr, and the exit code is the run's return code.
       A task worth invoking by hand gets its own artisan command by adding
       #[Command('myapp:name', 'Description')] beside its #[Task] - that alias IS this
       line under a friendlier name. Full treatment: rsx:man task_commands.

    4. Schedule: #[Schedule('<cron-or-phrase>')] on the method (SCHEDULES).

    A service may override Rsx_Service_Abstract::pre_task($task, $params), which runs
    before every run of its tasks; a non-null return ends the run with that value as the
    task's return.

CONCURRENCY: SINGLE-IDENTITY GUARDS (#[Exclusive] / #[Debounce])

    Two mutually-exclusive markers; declaring both fails rsx:check (TASK-CONCURRENCY-01):

        #[Task('Send pending email')]
        #[Exclusive]                     // at most one instance runs at a time
        #[Schedule('every 5 minutes')]
        public static function drain(Task_Instance $task, array $params = []) { ... }

        #[Task('Rebuild search index')]
        #[Debounce(30)]                  // single-instance; the coalesced follow-up runs
        public static function reindex(Task_Instance $task, array $params = []) { ... }
                                         // 30 s after the previous run COMPLETED

    Both guarantee, per IDENTITY, AT MOST ONE RUNNING + AT MOST ONE PENDING run - a
    distributed translation of the JS debounce(). #[Exclusive] has no delay. The
    identity differs:

        #[Exclusive]   the method - class::method, whatever the params
        #[Debounce]    the method AND its parameter set - class::method + params_hash
                       (sha256 of the params' JSON with every object's keys sorted), so
                       two different parameter sets are debounced independently

    The guarantee holds however the task runs: dispatch() coalesces onto the identity's
    pending run and returns its id; a worker claims a run only while holding the
    identity's run lock (a non-blocking try - a run whose identity is busy is passed over);
    a schedule tick whose identity is already running is coalesced into that run (its
    next_run_at advances and nothing runs); an inline run waits for the run lock. When a
    run settles, a coalesced pending run is re-anchored to now + the debounce delay. State
    is durable (_tasks rows) and cluster-safe (Task_Lock, a named RsxLocks lock).

    IMPORTANT: these guard ONE identity against ITSELF. They do NOT stop a different task
    (or a web request) from writing the same table concurrently. For that, lock.

LOCKS: PROTECTING CRITICAL SECTIONS

    Because tasks are unguarded and concurrent, a task that must serialize a critical
    section acquires its own lock. RsxLocks provides cluster reader/writer locks served by
    the rsx-lockd daemon. Every acquire returns a token; release it with
    RsxLocks::release_lock($token) in a finally.

        $token = RsxLocks::named_write_lock('rebuild_report_cache');   // exclusive
        try {
            // ... critical section ...
        } finally {
            RsxLocks::release_lock($token);
        }

        $token = RsxLocks::site_write_lock($site_id);   // exclusive for one tenant

    A lock is held until it is released or until the holder DIES - there is no lease, no
    TTL and no renewal. $timeout on an acquire is a WAIT budget only and defaults to wait
    forever. RsxLocks::system_lock($name) is the this-box-only flock kind.

    YOUR LOCKS ARE RELEASED WHEN THE TASK ENDS. A worker is one long-lived process running
    many unrelated tasks, so it checkpoints the lock state before each task and releases
    everything acquired during it. A task that ends still holding a lock has it released
    AND named on its stderr and in a [WORKER] log warning - that is a defect in the task.
    An inline run keeps its caller's locks.

    THE AUTOMATIC PER-TENANT WRITE LOCK IS CURRENTLY DISABLED (backlog B-87). A task that
    wants tenant-wide exclusivity asks for RsxLocks::site_write_lock($site_id) - and for a
    long sync, import or reindex, holding it blocks every web write to that tenant for the
    whole run. Backlog B-85 tracks making that choice an explicit declaration.

    SPAWNING artisan from inside a task goes through Rsx_Artisan, never
    passthru/exec_safe - a subprocess is a different lock connection and would queue
    behind locks this task holds, forever. Full contract: rsx:man locks.

THE WORKER POOLS

    Three pools, each capped on its own in rsx.tasks.pools (every cap at least 1, or boot
    throws):

        on_demand  runs dispatched work                       default 2
                                                              (RSX_TASK_MAX_WORKERS)
        scheduled  runs #[Schedule] work - and claims queued  default 1
                   dispatched work FIRST
        kill       the kill workers that carry out force      default 10
                   stops and kills (LIFECYCLE CONTROL)

    The ONE count of workers is kept by the rsx-lockd daemon (Task_Pool; rsx:man locks,
    THE RSX LOCKD DAEMON) - not by counting rows, and not by anything with a clock on it.
    Each pool is named per environment (tasks:<pool>:<scope>), so two environments sharing
    a daemon never share a pool.

    MEMBERSHIP IS A CONNECTION. Each worker opens one pool connection to rsx-lockd and holds
    it for its whole life. A worker that exits, crashes or is SIGKILLed stops being counted
    the instant its socket closes - on any host, with no heartbeat, no lease, no TTL and no
    reservation anywhere. Joining answers a worker id (wid) and the daemon's GENERATION (a
    random integer picked once at daemon startup); a claim records both on the run, with
    the worker's host and pid.

    THE WORKER'S LOOP (rsx:task:worker --pool=on_demand|scheduled). Every pool step runs
    under that pool's POOL LOCK, a FIFO mutex in the daemon:

        1. Take the pool lock. If the cap's worth of OTHER workers are members, release it
           and exit 0. Otherwise join.
        2. Still under the lock, claim the next run: the oldest due PENDING run (both
           pools); in the scheduled pool only, when none is due, the earliest due schedule,
           whose run row is created here (origin Scheduled) in the same transaction that
           advances its next_run_at. Release the lock.
        3. Run the task, holding no pool lock.
        4. Take the lock, settle the run, and claim again (back to 2). When nothing is
           claimable, or --max-time (300 s) has passed, leave the pool and exit.

    Two pools claim the same pending rows and each holds only its own lock, so EVERY CLAIM
    IS A GUARDED WRITE (WHERE the row is still PENDING) that must affect exactly one row; a
    worker that loses the race claims again.

    THE RULE: while holding a pool lock a process runs only pool ops and reads/writes of the
    task tables (plus a non-blocking try or a release of an identity run lock). No other
    blocking lock, no subprocess, no outbound call - realtime frames are held back and sent
    after the unlock. A process holds at most one pool's lock at a time. THE RULE governs
    framework code only: a task never runs under a pool lock.

    A lost pool connection ends the worker. Lost after a claim and before the run: the
    claim is handed back (a dispatched run returns to PENDING; a scheduled run's row is
    deleted and that tick is lost), "[WORKER] Lost the task pool connection after claiming
    task ..." is logged and the worker exits 1. Lost while the task ran: the run's outcome
    is recorded, the loss is logged and the worker exits 1.

    SPAWNING. Every spawn - dispatch(), a force stop or kill, the cron tick - goes through
    Task::spawn_worker($pool), which starts a detached rsx:task:worker (or rsx:task:killer
    for the kill pool) only when all four hold:

        - this process spawns workers at all (SPAWNING OFF);
        - maintenance mode is not up;
        - fewer than the pool's cap of the workers THIS process spawned into it are still
          running (read from /proc, no daemon round trip);
        - the pool, counted by rsx-lockd under its lock (released BEFORE the process is
          started), is below the cap. A worker whose own task dispatches counts itself.

    These checks only avoid starting a process that is doomed to exit; the worker's own
    admission in step 1 is what enforces the cap. rsx-lockd is a hard dependency: when it
    cannot be reached, a dispatch() that would spawn THROWS (after its row is written, so
    the work is queued), and the cron tick throws.

SPAWNING OFF: LONG-RUNNING SCRIPTS

    Every dispatch() that finds room in a pool starts a worker, and ordinary code
    dispatches: a model save whose hooks queue a task, a mail send, an upload. A script that
    writes thousands of rows turns that off for the rest of the process:

        Task::spawn_workers(false);

    dispatch() still writes every row and returns its id; it starts no worker. The cron
    tick spawns the workers that drain the queue. Task::spawning_workers() reports the
    setting. The switch governs THIS process only. See rsx:man scripting.

SCHEDULES

    #[Schedule('<expression>')] registers a recurring task. Standard 5-field cron works:
        '0 3 * * *'      Daily at 3am
        '0 9 * * 1-5'    Weekdays at 9am

    Human-readable phrases are also accepted (normalized to cron). PREFER THESE - they
    contain no asterisk-slash step token, which is unsafe to write in a block comment (the
    pair terminates a /* */ or /** */ comment and corrupts the file):
        'every minute'                 'every 5 minutes'        'every 6 hours'
        'hourly'                       'daily' / 'daily at 2am' / 'daily at 14:30'
        'weekly' / 'weekly on monday at 9:30am'                'monthly'

    Each declaration is one _task_schedules row (Task_Schedule_Model): its class, method,
    cron expression, next_run_at, and its run statistics - last_task_id, last_success_at,
    last_error_at, last_error, consecutive_failures. EACH RUN of a schedule is a run row of
    its own (origin Scheduled, schedule_id set), so a schedule has a full run history.

    rsx:task:process reconciles the table every tick: a new declaration is registered at
    its next cadence; a changed expression is re-registered with next_run_at recomputed
    (statistics kept), so an old cadence never lingers; a removed declaration's row is
    deleted (its past runs keep their rows, schedule_id cleared). A scheduled-pool worker
    advances next_run_at BEFORE running, so the cadence holds across a slow or crashed run.

    A scheduled task that fails does not stop its schedule: the run is FAILED, the schedule
    counts the failure (consecutive_failures + 1, last_error, last_error_at) and runs again
    at its next cadence. A success resets the streak. Visibility:

        php artisan rsx:tasks:list     the Schedules table: next run, last success,
                                       consecutive failures, the last error
        php artisan rsx:health         Task Schedule Failures WARNs once a schedule
                                       reaches rsx.tasks.failing_schedule_warn_after (3)
                                       consecutive failures

LIFECYCLE CONTROL

    Five operations on a Task_Run_Model. Each appends an OPERATOR line to the run's output
    naming who did it (the signed-in identity's printed name, else "the command line" or
    "an anonymous request") and the explanation when one is given; operator lines show as
    stderr. None is gated in PHP: an endpoint acting for a user asks
    Task_Gates::can_control() first. Each answers false when it no longer applies.

        request_stop(?string $explanation = null): bool
            GRACEFUL STOP. Sets stop_requested_at and does nothing else - nothing is ever
            killed. A live run only.
        force_stop(?int $grace_seconds = null, ?string $explanation = null): bool
            Sets stop_requested_at, then a kill worker kills the run's worker if it is
            still running after the grace (default rsx.tasks.stop_grace_seconds, 60). A
            PENDING run is cancelled instead.
        force_kill(?string $explanation = null): bool
            A kill worker kills the run's worker now. A PENDING run is cancelled instead.
        cancel(?string $explanation = null): bool
            PENDING only: CANCELLED, never runs.
        rerun(): int
            A finished run only (a live run throws): Task::dispatch() of the same service,
            method and params, returning the new run's id (an already-pending run's, for a
            coalesced task). The original is untouched.

    A STOP IS COOPERATIVE. A task that can be stopped calls $task->is_stop_requested()
    between units of work - every batch, every page, every file - and when it answers true
    finishes cleanly (leaves its data consistent, says what it did) and returns; the run
    then settles STOPPED. A task that never asks runs to completion - unless it was force
    stopped, and then it is killed when the grace ends. A pending run that was asked to stop
    sees the request at its first check.

        #[Task('Reindex documents')]
        public static function reindex(Task_Instance $task, array $params = [])
        {
            $done = 0;
            foreach (Document_Model::query()->result_set() as $document) {
                if ($task->is_stop_requested()) {
                    $task->summary("Stopped on request after {$done} documents.");
                    return null;
                }
                $document->reindex();
                $task->progress_count(++$done, $total);
            }
            $task->summary("Indexed {$done} documents.");
            return null;
        }

    KILL WORKERS. A kill never happens inside the request that asked for it. force_stop()
    and force_kill() record a _task_kill_requests row (Task_Kill_Request_Model) bound to the
    HOST that runs the target's worker - a pid names a process on one machine only - and,
    when that is this host, spawn a kill worker (rsx:task:killer, the kill pool). Every
    host's rsx:task:process tick spawns kill workers for its own pending requests, so a
    request made on another host, or left when the kill pool was full, is carried out
    within a minute. A kill worker:

        1. claims one request (a guarded write), earliest due first;
        2. re-reads the run every second until the request is due - a run that ended on its
           own, or whose worker is no longer the one the request names, makes the request
           MOOT. The force-stop grace is the window a cooperative task gets to finish
           cleanly; the poll is a condition check, not a deadline;
        3. sends SIGKILL to the worker's pid on this host (the grace period is the polite
           window, so there is no SIGTERM step) and waits for the process to be gone;
        4. settles the run KILLED with the explanation as status_reason and an operator
           line; a scheduled run counts as a failure on its schedule.

    An INLINE run inside a WEB REQUEST is never signalled - its pid is a php-fpm worker that
    serves other requests. Its kill request is settled moot with an operator line saying
    only a graceful stop applies. An inline run in an artisan process (rsx:task:run, a
    #[Command]) is killed like a worker.

    Nothing else needs releasing after a kill: an identity run lock and a pool membership
    both belong to the dead process's rsx-lockd connections. A kill request whose kill
    worker died mid-wait is handed back to the queue by the next tick on its host.

READING A RUN (Task_Run_Model)

    Lifecycle: status_id (+ status_id__label), origin_id, pool_id, is_live(),
    is_terminal(), task_name() ("Service::method"), service_name(), scheduled_for,
    started_at, completed_at, stop_requested_at, status_reason, error, return_code,
    schedule (relationship), dispatched_by (relationship).

    Reports:
        status_text()                 the last status line, or null
        progress_percent()            0-100, derived from the count when only a count
                                      was reported; null when neither
        progress_count()              ['done' => int, 'total' => int] or null
        eta_at()                      ISO moment or null
        state(), summary()
        queue(?int $limit = null)     the queue's items, oldest first - only the first
                                      $limit when given (the head); null when the run's
                                      queue has never held an item
        queue_depth()                 how many items the queue holds
        available_reports()           the report names this run has actually set:
                                      state_json, queue, status_text, progress,
                                      progress_count, eta, heartbeat, messages, summary,
                                      return_code
        output_after(?int $after_id, array $streams = ['stdout','stderr','operator'],
                     int $limit = 1000)  [{id, stream, line, at}], oldest first
        messages_after(?int $after_id, int $limit = 1000)  [{id, body, at}]
        attachments(), attachment($name)  Task_Attachment_Model rows; read the bytes with
                                      read_bytes() / read_stream() / download_response()
        to_status_array()             the JSON shape the endpoints and widgets read

    The output and message readers are cursor reads: pass the last id seen for the next
    page. A task attachment is a temp file (rsx:man temp_files) named under the run - it
    is not a File_Attachment_Model: no owner, no file gates and no deletion window; the
    task's view gate is who may read it, and an application serves one through its own
    gated endpoint with download_response().

    SEARCH. Task_Run_Model::search_query(array $filter) returns a Builder; an unknown key
    throws. Keys: id, ids, class (simple name or FQCN), method, params (an EXACT parameter
    set, matched by its hash), params_contains (JSON_CONTAINS - pair it with class/method),
    status (name or id, or a list), live (bool), origin, schedule_id, site_id,
    dispatched_by (['type' => 'User_Model', 'id' => 5]), and
    {scheduled,started,completed}_{after,before} (ISO moments, inclusive).

        Task_Run_Model::find_first_1000($filter)          newest first, capped by its name
        Task_Run_Model::find_page($filter, $cursor = null, $page_size = 1000)
                                          ['tasks' => [...], 'next_cursor' => ?string],
                                          keyset on id, newest first

    These are ungated server-side reads like any model read. An endpoint showing runs to a
    user narrows the query with Task_Gates::scope_viewable() first.

GATES AND THE BROWSER API

    A run's params, reports, output and files are operator data, and stopping or rerunning
    one is an operator act, so the APPLICATION decides who may do either - through event
    handlers in /rsx/handlers/. WITH NO HANDLER, NOBODY MAY (deny by default, in both
    realms). Task_Gates is the single seam every task endpoint, topic and widget asks:

        staff realm                        portal realm
        task.view.authorize    (gate)      portal.task.view.authorize    (gate)
        task.view.scope        (filter)    portal.task.view.scope        (filter)
        task.control.authorize (gate)      portal.task.control.authorize (gate)

      - the view GATE answers for one run: data {task, user}; return true to allow;
      - the view SCOPE narrows a list query to the runs the viewer may see: each handler
        receives the Task_Run_Model builder and returns it narrowed. Keep the gate and the
        scope the same rule;
      - the control GATE answers for one action on one run: data {task, user, action},
        action one of stop, force_stop, force_kill, cancel, rerun.

    `user` is the realm's identity (Session::get_user() on staff, the portal user on a
    portal request). A DEVELOPER (Session::is_developer(), staff realm) passes every gate
    with no handler asked - the /_sys console shows and controls every run.
    PHP: Task_Gates::can_view($run), scope_viewable($query), can_control($run, $action).

        // Only these tasks, only these actions, only on the viewer's own runs.
        const USER_TASKS = ['Contact_Export_Service::export' => ['stop', 'cancel']];

        #[OnEvent('task.view.authorize', priority: 10)]
        public static function view_own_runs($data)
        {
            $task = $data['task'];

            return $task->dispatched_by_type === 'User_Model'
                && (int) $task->dispatched_by_id === Session::get_user_id()
                && isset(self::USER_TASKS[class_basename($task->class) . '::' . $task->method]);
        }

    LEAST PRIVILEGE - THE POLICY.JSON POSTURE. Write the handlers the way an AWS IAM
    policy is written: grant only what the application's own screens were built to do, and
    nothing because it might be useful. Each grant names three things:

        WHO      the user type (the realm, and within it User_Model / Portal_User_Model,
                 a role or ACL check if only some users may), and normally OWNERSHIP - the
                 run's dispatched_by is the viewer;
        WHAT     the specific tasks - 'Service::method' - that a screen shows those users;
                 never "every task", never a pattern;
        ACTIONS  per task, only the actions that screen offers (a progress panel needs
                 view and nothing else; a Stop button needs stop). force_kill belongs to
                 developers in /_sys and is almost never granted.

    A task not granted stays invisible to users - even one they started - and is seen by
    developers in /_sys. EVERY NEW TASK, and every task whose behaviour changes, is checked
    against the handlers in the same change: a task users should see gets its own grant, a
    task that changed gets its grant re-checked, and a task users need not see gets none.
    The view gate and the view scope must express the same grant (one run vs a list).

    Worked example: system/app/RSpade/resource/reference_app/handlers/Task_Gate_Handlers.php
    - a USER_TASKS map of 'Service::method' => [actions], granted to staff users on the runs
    they started; the scope narrows to the same owner AND the same listed tasks.

    ENDPOINTS. Rsx_Task_Controller (#[Auth('public')], #[Auth_Realm('any')] - the gates
    decide): get, report, output, messages, find, page, stop, force_stop, force_kill, cancel,
    rerun. A run the viewer may not see answers "not found", exactly like a missing one.
    The read endpoints are #[Portal_Impersonation_Readable]; the lifecycle ones are not, so
    View as Client can watch a run and never stop one. get() answers to_status_array() plus
    `can`: which actions the viewer may take.

    JS: Rsx_Task.
        await Rsx_Task.get(id)                        {status, progress_percent, can, ...}
        await Rsx_Task.report(id, kind, limit)        {kind, value, total, status}
                                                      limit (queue only): the first,
                                                      oldest N items; total = the
                                                      queue's depth (null otherwise)
        await Rsx_Task.output_after(id, after_id, streams)   {lines, last_id, more, is_live}
        await Rsx_Task.messages_after(id, after_id)   {messages, last_id, more}
        await Rsx_Task.find(filter)                   {tasks} (newest, at most 1000)
        await Rsx_Task.page(filter, cursor, page_size)  {tasks, next_cursor}
        await Rsx_Task.stop(id, explanation) / force_stop(id, grace, explanation) /
              force_kill(id, explanation) / cancel(id, explanation)
        await Rsx_Task.rerun(id)                      {task_id}
        await Rsx_Task.watch(id, cb) / watch_output(id, cb) / watch_list(cb)
                                                      {stop(), established}
        await Rsx_Task.watch_task(class_name, method, cb)
                                                      runs of ONE task, by name (method
                                                      null: every task of the service)
        await Rsx_Task.live_runs(class_name, method)  its pending + running runs

    IS A TASK RUNNING? A page that must know whether a task is running - a button to
    disable while an import runs, a banner while a sync is in flight - watches the task BY
    NAME and asks on each frame. The watch fires once on subscribe (the resync), so the
    first answer needs no separate call:

        await Rsx_Task.watch_task('Import_Service', 'run', async () => {
            const runs = await Rsx_Task.live_runs('Import_Service', 'run');
            show_import_busy(runs.length > 0);
        });

    The frame says only "a run of this task changed"; live_runs() is the gated search
    (find({class, method, live: true})), so a viewer sees only runs their view scope
    admits. class_name is the service's simple name (Import_Service), as in every filter.

    TOPICS. Frames are notification-only; refetch on each (rsx:man realtime):

        Task_Changed_Topic {id}       lifecycle, reports, messages, attachments
        Task_Output_Topic {id}        output lines (the busy feed, only a console needs it)
        Task_List_Changed_Topic {class, method}
                                      a run entered, left or changed lifecycle state.
                                      The frame names the run's task (simple service
                                      name); filters match shallowly, so {} hears every
                                      run, {class} every run of one service, {class,
                                      method} every run of one task

    can_subscribe() is Task_Gates: the run's view gate for the two {id} topics; for the
    list topic, a developer or a signed-in viewer in a realm whose view scope has a
    handler. A frame is published only to the sites holding a matching subscription, and
    not at all when nobody watches. Inside a component prefer
    this.subscribe('Task_Changed_Topic', {id}, () => this.refresh()).

THE SAMPLE TASK

EXECUTION TIMEOUT

    A run a POOL WORKER executes is capped by its timeout (a dispatch() option), else
    rsx.tasks.default_timeout (1800 s; 0 on both = no cap). An INLINE run (Task::internal(),
    rsx:task:run, a #[Command]) is never capped: it belongs to the process that started it,
    and how long it takes is that caller's business.

    Enforcement lives in the cron tick: a RUNNING pool-worker run whose worker is STILL ALIVE
    on the host the tick runs on, past its cap, gets a force-kill request ("timed out after Ns
    (cap Ms)"), carried out by a kill worker and settled KILLED; one [TASK TIMEOUT] line is
    logged. Granularity is the cron tick (one minute). This reaper cap is framework
    infrastructure - you never add a timeout to your own task.

FAILURE AND ABANDONMENT

    A task that fails (a failure return or a throw) settles FAILED and is NEVER retried -
    there is no retry for a failure and no opt-in. A failed dispatched run stays failed
    until something dispatches it again (rerun()); a schedule runs again at its cadence.

    A RUNNING run whose worker is gone is ABANDONED - the task never reported an outcome -
    and the cron tick settles it, with NO grace period: every verdict is evidence, never an
    age. Each host's tick asks rsx-lockd about every RUNNING run carrying a worker_id, one
    members_alive round trip per pool, under that pool's lock:

        the daemon's own generation     not alive -> abandoned, whatever host ran it.
                                        Alive -> running.
        an older generation, THIS host  the daemon restarted since the claim and cannot
                                        know; the pid decides.
        an older generation, ANOTHER    left alone for that host's own tick; rsx:health's
        host                            Task Worker Pools row WARNs while any remains.
        no worker_id (inline)           the pid on its own host decides.

    Settling an abandoned run:

        Dispatched   back to PENDING with scheduled_for = now +
                     rsx.tasks.retry.base_seconds * 2^(n-1), n = this abandonment's number
                     (abandon_count): 600 s, 1200 s, 2400 s, 4800 s at the defaults. The
                     rsx.tasks.retry.attempts-th abandonment (5) FAILS it for good. So a
                     dispatched task's body may run more than once when a worker dies under
                     it - write it to be safe to re-run from the start.
        Scheduled    FAILED; the schedule counts the failure and runs at its next cadence.
        Inline       FAILED; its caller is gone.

    Each settle writes status_reason and an operator line naming the reason.

    A daemon restart therefore never reaps live work: every running worker is then of an
    older generation and is judged by its own pid. A worker of the CURRENT generation whose
    connection dropped while its process lives on is reaped at once; if it then finishes,
    its own settle no longer matches (the row is no longer RUNNING under it).

RETENTION

    Task_Retention_Service::sweep (#[Exclusive], every 30 minutes) keeps history to the
    size rsx.tasks.retention allows, over FINISHED runs only, walking each set by keyset:

        output_truncate_after_minutes (10080 = 7 days) after a run finished, its output is
            cut to its last output_keep_lines (150) lines and its attachments are unlinked
            - each blob released once nothing else references it; the run is stamped
            output_truncated_at and never visited again;
        purge_after_minutes (30240 = 21 days) after it finished, the run is deleted - its
            reports, output and messages with it;
        a task temp directory that outlived its run is removed.

MAINTENANCE MODE

    While maintenance mode is up (rsx:maintenance:enable, or the window rsx:framework:pull
    raises) the CLI gate refuses the automation:

        rsx:task:process   REFUSED (exit 75). Cron keeps calling it; every call exits.
        rsx:task:worker    REFUSED (exit 75). Task::spawn_worker() starts nothing for any
                           pool while the window is up, so a dispatch made during it leaves
                           its row PENDING for the first tick after the window.
        rsx:task:run       REFUSED unless --force. --force is consumed by the gate and
                           never reaches the task's parameters.

    Enabling maintenance first runs rsx:tasks:kill-all, which force-kills this host's
    running runs synchronously, in its own process (no kill worker can be spawned in the
    window): each is SIGKILLed and settled KILLED with the explanation. See
    rsx:man maintenance_mode.

COMMANDS

    php artisan rsx:task:run Service method [--key=value]    Run inline (rsx:man task_commands)
    php artisan rsx:task:list                                Discovered tasks, with the
                                                             #[Command] each is reachable
                                                             as (or '-')
    php artisan rsx:tasks:list                               Pools (workers of cap), running
                                                             runs with worker PIDs, the
                                                             queued count, every schedule
    php artisan rsx:tasks:stop <id> [--force [--grace=N]] [--kill] [--explanation="..."]
                                                             Graceful stop; --force = force
                                                             stop; --kill = force kill
    php artisan rsx:tasks:cancel <id> [--explanation="..."]  Cancel a pending run
    php artisan rsx:tasks:kill-all --explanation="..."       Force-kill every running run:
                                                             this host's at once, another
                                                             host's queued for its kill
                                                             workers
    php artisan rsx:task:process [--once] [--force-scheduled]  The cron tick (below)
    php artisan rsx:task:worker [--pool=on_demand|scheduled] [--max-time=300]
    php artisan rsx:task:killer                              A kill worker (spawned for you)

    rsx:task:process is the scheduler/dispatcher tick. Install it in cron:

        * * * * * cd /var/www/html && php artisan rsx:task:process

    Each tick it: (1) settles abandoned runs and requests force kills for timed-out ones;
    (2) hands back kill requests whose kill worker died; (3) reconciles _task_schedules
    from the manifest; (4) tries ONE spawn per pool with due work - on_demand (else
    scheduled) for due dispatched runs, scheduled for due schedules, kill for this host's
    pending kill requests. It never becomes a worker, and is silent on an idle tick.
    --once runs one due dispatched run inline in the tick's process (testing);
    --force-scheduled makes every schedule due now.

CONFIGURATION (config/rsx.php 'tasks')

    'tasks' => [
        'pools' => [
            'on_demand' => ['max_workers' => env('RSX_TASK_MAX_WORKERS', 2)],
            'scheduled' => ['max_workers' => 1],
            'kill'      => ['max_workers' => 10],
        ],
        'default_timeout'             => 1800,  // execution cap (0 = none); EXECUTION TIMEOUT
        'stop_grace_seconds'          => 60,    // force_stop()'s default grace
        'failing_schedule_warn_after' => 3,     // rsx:health threshold
        'retry' => [
            'base_seconds' => 600,              // first re-run of an ABANDONED dispatched run
            'attempts'     => 5,                // the abandonment that FAILS it
        ],
        'retention' => [
            'output_truncate_after_minutes' => 10080,
            'output_keep_lines'             => 150,
            'purge_after_minutes'           => 30240,
        ],
    ],

    stop_grace_seconds is owner-set: the window a cooperative task gets to finish cleanly,
    not a bound on any operation. 'retry' is pacing for work a dead worker ABANDONED, never
    a timeout, and never applied to a task that failed.

DATABASE SCHEMA

    _tasks (Task_Run_Model) - one row per run:
        class, method, params (JSON), params_hash, origin_id, schedule_id, pool_id,
        site_id, dispatched_by_id + dispatched_by_type,
        status_id, status_reason, error, return_code,
        scheduled_for, started_at, completed_at, stop_requested_at, abandon_count, timeout,
        status_text, progress_percent, progress_done, progress_total, eta_at,
        last_heartbeat_at, last_report_at,
        worker_pid, worker_id, worker_generation, worker_host  (written together by a claim,
            cleared together wherever a run is handed back),
        output_truncated_at, created_at, updated_at
    _task_reports      (task_id, kind_id) unique: state JSON, state list, summary
    _task_output       one row per line; stream_id 1 stdout, 2 stderr, 3 operator
    _task_messages     one row per message
    _task_attachments  (task_id, name) unique; temp_file_id -> _temp_files (cascade)
    _task_schedules    one row per #[Schedule] (SCHEDULES)
    _task_kill_requests  force stops and kills waiting for a kill worker

    The side tables cascade from _tasks. All are framework system tables - read them
    through the models and the readers above.

TESTING

    Under the test suite spawning is OFF by default: Task::dispatch() writes its row and
    returns, and a tick a test runs spawns nothing either. A test drives queued work itself:

        Task::internal('My_Service', 'my_task', $params);       // a real inline run
        Artisan::call('rsx:task:worker');                       // drain in-process

    A test whose SUBJECT is the spawn calls Task::spawn_workers(true); the runner resets it
    at every class boundary and waits there for every detached process the class started
    (rsx:man testing). Rsx_Test_Abstract::__run_task_method($class, $method, $params) calls
    a task method directly as a real inline run (no pre_task(), no run lock, no capture),
    settles it, and returns what it reported with state().

    An in-process worker is a real pool member: it needs rsx-lockd, joins under the pool
    lock and leaves before Artisan::call() returns. Pools are named by the connection
    scope, so the test database's pools are never the developer database's.

TROUBLESHOOTING

    A dispatched run stays Pending
        - Are the pools full? rsx:health "Task Worker Pools" shows each pool's members
          against its cap; /_sys/workers shows what they are running. A busy worker
          reaches the row when it finishes.
        - Did this process call Task::spawn_workers(false), or is it a test? Then the cron
          tick drains it.
        - A future 'scheduled_for', a retry backoff after an abandonment (status_reason
          says so), or an #[Exclusive]/#[Debounce] identity whose run is still running.
        - Cron is the backstop: * * * * * php artisan rsx:task:process

    A stop did nothing
        - A graceful stop is cooperative: the task must call is_stop_requested(). Use
          force_stop() (rsx:tasks:stop <id> --force) to kill it after a grace period.
        - A run inside a web request is never signalled; only a graceful stop applies.

    A force stop or kill has not happened
        - The kill worker runs on the TARGET's host. /_sys/workers lists pending kill
          requests; that host's next rsx:task:process tick spawns its kill workers.

    A run reports "Unavailable" / "Task not found" in a widget
        - The viewer fails the view gate. With no task.view.authorize handler, nobody but
          a developer sees any run (GATES AND THE BROWSER API).

    Two tasks corrupt shared data
        - Tasks are unguarded and concurrent. Guard the critical section with a named or
          per-site lock. #[Exclusive]/#[Debounce] only guard ONE identity.

    "Cannot reach rsx-lockd ..." from Task::dispatch() or rsx:task:process
        - The daemon is down (rsx:health "Lock Server"; rsx:man locks). A dispatch() that
          would spawn throws AFTER writing its row, so the work is queued. Running workers
          finish their current task, record its outcome, log "[WORKER] Lost the task pool
          connection ..." and exit 1; the next tick spawns fresh ones.

    Task Worker Pools WARN: more members than rsx.tasks.pools.<pool>.max_workers
        - The cap was lowered under running workers (they drain as they finish), or two
          configurations share one database and host.

    Task Worker Pools WARN: running task(s) from a previous rsx-lockd generation on host(s)
        - Runs claimed before the daemon last restarted, on other hosts. Each host's tick
          settles its own by pid; for a host that is gone, settle them with
          rsx:tasks:stop <id> --kill --explanation="...".

    A schedule runs but never succeeds
        - rsx:tasks:list (Schedules table) and /_sys/tasks (Schedules tab) show the streak
          and the last error; the schedule keeps running regardless.
