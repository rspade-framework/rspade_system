RSX TASK SYSTEM
================

NAME
    Tasks - Unified background task execution with scheduling and queueing

SYNOPSIS
    Define a task (a public static Service method with #[Task]):
    -----------------------------------------------------------
    #[Task('Generate report')]
    public static function generate_report(Task_Instance $task, array $params = [])
    {
        $task->info('Starting');
        $task->update_progress(50, 'halfway');
        return ['status' => 'complete'];   // stored as JSON result
    }

    Run it now (synchronous CLI):
        php artisan rsx:task:run Service_Name generate_report --param=value

    Run it in the background (returns a pollable id, runs in ~1s):
        $id = Task::dispatch('Service_Name', 'generate_report', $params);
        $status = Task::status($id);   // array; ['status'] => pending|running|completed|failed

    Run on a schedule (recurring):
        #[Task('Nightly cleanup')]
        #[Schedule('daily at 3am')]        // or standard cron '0 3 * * *'
        public static function cleanup(Task_Instance $task, array $params = []) { ... }

DESCRIPTION
    RSX runs background work as static Service methods marked #[Task]. There is one
    durable queue (the _tasks table) and one shared pool of generic worker processes.
    You never write a worker loop or a queue driver - the framework spawns, caps, and
    reaps workers, and reconciles schedules, automatically.

    Unlike Laravel queues (job classes, a queue driver, `queue:work` daemons, Horizon),
    RSX tasks are just annotated methods; dispatch/scheduling/worker-management are
    built in. MySQL backs the durable queue; the rsx-lockd daemon backs every lock a task
    takes and is the one count of the worker pool (see THE WORKER POOL). Redis plays no
    part in running tasks.

    THE ONE KEY POINT: TASKS RUN CONCURRENTLY AND UNGUARDED
    -------------------------------------------------------
    NOTHING takes a global application lock - not artisan, not task workers, and not web
    requests (a read-only request now takes no lock at all). Multiple workers run at the
    same time, and a task shares the database with concurrent web requests and other tasks.
    Therefore:

      * A #[Task] method MUST NOT assume it is the only writer, or that only one kind of
        task runs at a time. If a critical section cannot tolerate a concurrent writer,
        the task acquires its own lock (RsxLocks, see LOCKS).
      * #[Exclusive] / #[Debounce] guarantee single-instance for ONE identity
        (class::method) - they do NOT protect a shared table from OTHER tasks or from web
        writers. Use a named or per-site lock for that.

EXECUTION MODES

    1. Immediate (synchronous)
       php artisan rsx:task:run Service_Name task_name --param=value
       Runs in-process, no queue row, no timeout. STDOUT is the return value as JSON and
       nothing else; STDERR carries the task's log lines live (-q silences them, never the
       value) - see OUTPUT CONTRACT in rsx:man task_commands. Also available in code as
       Task::internal($service, $task, $params), which returns the task's value and, called
       from application code, prints nothing anywhere.

       A task worth invoking by hand gets its own artisan command by adding
       #[Command('myapp:name', 'Description')] beside its #[Task]. That alias IS this line
       under a friendlier name - same params, same output, same exit codes. Full treatment:
       rsx:man task_commands.

    2. Background (async)
       $id = Task::dispatch($service, $task, $params, $options);
       Inserts a pending row AND, when the task is due now and the pool has room,
       spawns a detached worker so it runs within ~1 second (at the cap nothing is spawned:
       a busy worker reaches the row when it finishes its current task, and the cron tick
       covers the rest). A process that called Task::spawn_workers(false) - and every test,
       unless it opted in - ENQUEUES ONLY; see SPAWNING OFF and TESTING below.
       Returns the pollable task id (for #[Exclusive]/#[Debounce]
       identities that coalesce onto an already-pending run, returns that pending row's id).
       $options: 'queue', 'timeout' (the execution cap enforced by the cron tick's reaper -
       see EXECUTION TIMEOUT below), and 'scheduled_for' - a FUTURE 'scheduled_for' is the
       only thing that defers the run (that row waits and the cron tick runs it when due).

    3. Scheduled (recurring)
       #[Schedule('<cron-or-phrase>')] on the task method. The cron tick keeps one
       persistent tracker row per scheduled task and runs it when due.

TASK_INSTANCE API

    The $task object passed to every task method:

    Logging (appends a timestamped line; persisted for queued/scheduled tasks):
        $task->info($message)
        $task->error($message)
        $task->debug($message)
    (There is no warning() level.)

    Progress and result:
        $task->update_progress(int $percent, ?string $message = null)  // 0-100, logged
                                                    // logs as "[45%] message", or "[45%]"
        $task->set_result($value)                                      // JSON result, mid-run
    (There is no set_status() / progress() method.)

    Progress stamp for long runs:
        $task->heartbeat()
    Records last_heartbeat_at on the row, which the task screens display. Optional: it
    plays no part in worker liveness. A worker is counted alive for exactly as long as its
    rsx-lockd connection is open (THE WORKER POOL), so a task may run for hours without
    calling anything.

    Temp workspace (auto-deleted on completion/failure):
        $dir = $task->get_temp_dir()    // tmp/tasks/task_<id>/

    Misc: $task->get_id(), get_status(), get_params(), get_queue().

DISPATCH & STATUS

    $id = Task::dispatch($service, $task, $params, $opts);  // enqueue + run now, returns id

    Task::status($id) returns an ARRAY (or null if unknown):
        [
            'id', 'class', 'method', 'queue', 'status',   // status: pending|running|completed|failed|killed
            'params'  => array,
            'result'  => array|null,                      // the task's return value when completed
            'logs'    => string[],                        // one entry per logged line
            'error'   => string|null,
            'scheduled_for', 'started_at', 'completed_at', 'created_at', 'updated_at',
        ]

    Example:
        $s = Task::status($id);
        if ($s['status'] === 'completed') {
            $out = $s['result']['output_path'];
        }

SCHEDULING

    #[Schedule('<expression>')] registers a recurring task. Standard 5-field cron is
    accepted:
        '0 3 * * *'      Daily at 3am
        '0 */6 * * *'    Every 6 hours
        '0 9 * * 1-5'    Weekdays at 9am

    Human-readable phrases are also accepted (normalized to cron). PREFER THESE - they
    contain no asterisk-slash step token, which is unsafe to write in a block comment (the
    asterisk-slash pair terminates a /* */ or /** */ comment and corrupts the file):
        'every minute'                 'every 5 minutes'        'every 6 hours'
        'hourly'                       'daily' / 'daily at 2am' / 'daily at 14:30'
        'weekly' / 'weekly on monday at 9:30am'                'monthly'

    Schedule edits take effect within one cron tick: the processor compares the manifest
    expression to the stored one and regenerates the tracker (recomputing next_run_at)
    when they differ, so an old cadence never lingers.

CONCURRENCY: SINGLE-IDENTITY GUARDS (#[Exclusive] / #[Debounce])

    Two mutually-exclusive markers control concurrency for ONE identity (class::method);
    declaring both fails rsx:check (TASK-CONCURRENCY-01):

        #[Task('Send pending email')]
        #[Exclusive]                     // at most one instance runs at a time
        #[Schedule('every 5 minutes')]
        public static function drain(Task_Instance $task, array $params = []) { ... }

        #[Task('Rebuild search index')]
        #[Debounce(30)]                  // single-instance; follow-up waits 30s after the
        public static function reindex(Task_Instance $task, array $params = []) { ... }
                                         // previous run COMPLETED

    Both guarantee AT MOST ONE RUNNING + AT MOST ONE PENDING per identity (a distributed
    translation of the JS debounce()). #[Exclusive] == #[Debounce(0)].
    State is durable (_tasks rows) + cluster-safe (Task_Lock, a named RsxLocks lock). Tasks with
    neither marker may run concurrently with copies of themselves.

    IMPORTANT: these guard ONE identity against ITSELF. They do NOT stop a different task
    (or a web request) from writing the same table concurrently. For that, lock.

LOCKS: PROTECTING CRITICAL SECTIONS

    Because tasks are unguarded and concurrent, a task that must serialize a critical
    section acquires its own lock. RsxLocks provides web-cluster reader/writer locks (many
    concurrent readers; exclusive writers) served by the rsx-lockd daemon, which must be
    running. Every acquire returns a token; release it with RsxLocks::release_lock($token)
    (use try/finally).

    A lock is held until it is released or until the holder DIES - there is no lease, no
    TTL and no renewal, so a task that holds a lock for six hours still holds it at the end,
    and a task killed with SIGKILL frees its lock instantly. This matters most for exactly
    the work tasks do: long syncs, big imports, whole-table rebuilds.

    Custom named lock (guard a named resource):
        use App\RSpade\Core\Locks\RsxLocks;

        $token = RsxLocks::named_write_lock('rebuild_report_cache');   // exclusive
        try {
            // ... critical section; no other writer of this name runs concurrently ...
        } finally {
            RsxLocks::release_lock($token);
        }

        $token = RsxLocks::named_read_lock('rebuild_report_cache');    // shared reader

    Per-site (tenant) lock - the SAME lock the framework takes automatically for a web
    request that mutates a tenant's data. Use it when a task performs a multi-step
    mutation of one site that must be atomic against those web writers and other tasks:

        $token = RsxLocks::site_write_lock($site_id);   // exclusive for this tenant
        try {
            // ... mutate site $site_id atomically ...
        } finally {
            RsxLocks::release_lock($token);
        }

        $token = RsxLocks::site_read_lock($site_id);    // shared reader for this tenant

    All four accept an optional $timeout, which is a WAIT budget and NEVER a limit on how
    long the lock is held. It defaults to NULL = wait forever; pass a number only when the
    task genuinely has something better to do than wait, and it throws when that number
    elapses. Grants are FIFO, and a request that would close a wait-for cycle is refused
    immediately (with the cycle described) rather than parked forever.

    release_lock() returns a BOOL: false means the lock daemon restarted while the task
    held the lock, so mutual exclusion was not in force for the whole critical section (it
    is logged as an error either way). A long task that can act on that news should check it.

    RsxLocks::system_lock($name) is the other kind: THIS BOX ONLY, exclusive only, backed
    by flock. Use it only when the contended resource is local to the machine - a task
    coordinating with other servers wants the cluster locks above.

    YOUR LOCKS ARE RELEASED WHEN THE TASK ENDS. A worker is one long-lived process
    running many unrelated tasks, but an ordinary application lock is held until the
    PROCESS exits - so without a boundary the first task to write to a tenant would hold
    that tenant against the whole cluster for the worker's entire life. The worker takes a
    checkpoint before each task and releases anything acquired during it; locks the WORKER
    itself holds are unaffected. Still release your own in a finally: a task that ends
    holding one is released AND named in a [WORKER] warning, because that is a defect in
    the task.

    THE AUTOMATIC PER-TENANT WRITE LOCK IS CURRENTLY DISABLED (backlog B-87). A save()
    against a site-scoped model no longer takes cluster:SITE_<id> by itself, so a task that
    wants tenant-wide exclusivity must ask for it: RsxLocks::site_write_lock($site_id).
    Think before you do - for a long-running task (an external sync, a bulk import, a
    reindex) holding it blocks every web request that writes to that tenant for the whole
    run, and such a task is usually better written to tolerate concurrent writers. Backlog
    B-85 tracks making that choice an explicit declaration.

    SPAWNING artisan from inside a task goes through Rsx_Artisan, never passthru/exec_safe
    - a subprocess is a different lock connection and would otherwise queue behind locks
    this task holds, forever. See rsx:man locks (LOCK GROUPS AND SUBPROCESSES).

    See rsx:man locks for the full contract. Task_Lock, which holds the #[Exclusive] /
    #[Debounce] identity locks, is a thin object over an RsxLocks named lock - there is no
    second lock mechanism behind it.

THE WORKER POOL

    One shared pool of generic workers drains the queue. Concurrency is capped by
    rsx.tasks.global_max_workers, and the ONE count of workers is kept by the rsx-lockd
    daemon (Task_Pool; rsx:man locks, THE RSX LOCKD DAEMON) - NOT by counting rows, and not
    by anything with a clock on it.

    MEMBERSHIP IS A CONNECTION. Each worker opens one pool connection to rsx-lockd and holds
    it for its whole life. Joining the pool is a membership on that connection, so a worker
    that exits, crashes or is SIGKILLed stops being counted the instant its socket closes -
    on any host, with no heartbeat, no lease, no TTL and no reservation anywhere. A Redis
    flush changes nothing about the pool.

    THE WORKER'S LOOP. Every pool step runs under the POOL LOCK, a FIFO mutex the daemon
    holds per pool:

        1. Take the pool lock. If global_max_workers OTHER workers are already members,
           release it and exit 0 - the pool is full. Otherwise join.
        2. Still under the lock, claim the next row by the priority order below and mark it
           RUNNING with this worker's worker_pid and worker_member_key. Release the lock.
        3. Run the task, holding no pool lock.
        4. Take the pool lock, record the outcome on the row, and claim again (back to 2).
           When nothing is claimable, or --max-time has passed, leave the pool, release the
           lock and exit.

    The worker ADMITS ITSELF in step 1 - that is where the cap is enforced. Every pool call
    waits for the daemon's acknowledgement, so no worker sends a pool command and moves on
    (or exits) before the accountant has applied it.

    THE RULE: while holding the pool lock a process runs only pool ops and reads/writes of
    _tasks rows (plus a non-blocking try or a release of an #[Exclusive]/#[Debounce] run
    lock). No other blocking lock, no subprocess, no outbound call. Pool waits are invisible
    to the daemon's deadlock detector, and THE RULE is what makes that safe. It governs
    framework code only - a task itself never runs under the pool lock.

    SPAWNING. Every spawn - Task::dispatch() and the cron tick alike - goes through
    Task::spawn_worker(), which starts a detached `rsx:task:worker` only when all three hold:

        - this process spawns workers at all (see SPAWNING OFF below);
        - fewer than global_max_workers of the workers THIS process spawned are still
          running (read from /proc, no daemon round trip). This is what caps a script that
          dispatches on every write: once its own spawns fill the cap, each further dispatch
          returns at once until one of them exits;
        - the pool, counted by rsx-lockd under the pool lock (released again BEFORE the
          process is started), is below the cap. A worker whose own task dispatches counts
          itself as one of the members.

    These checks only avoid starting a process that is doomed to exit; two spawners racing
    can both see room, and the loser's worker finds the pool full in step 1 and exits.
    A worker run by hand is admitted exactly the same way.

    Priority order (a single order, no per-queue routing): a worker claims run-now tasks
    first (dispatched, FIFO by enqueue time), then due scheduled tasks (by next_run_at).
    The `queue` column is a label only; it does not isolate workers.

    rsx-lockd is a hard dependency, exactly as it is for locks: when the daemon cannot be
    reached, a dispatch() that would spawn THROWS (after its row is written, so the work is
    queued), and the cron tick throws. Neither ever spawns around an admission count it
    could not read. See TROUBLESHOOTING.

SPAWNING OFF: LONG-RUNNING SCRIPTS

    Every dispatch() that finds room in the pool starts a worker, and a lot of ordinary code
    dispatches: a model save whose hooks queue a task, a mail send, an upload. A script that
    writes thousands of rows can therefore start a process per write for as long as the pool
    has room. Turn that off for the rest of the process:

        Task::spawn_workers(false);

    dispatch() still writes every row exactly as before and returns its id; it starts no
    worker. The cron tick (rsx:task:process, every minute) spawns the workers that drain the
    queue, so the work runs on the pool's own schedule instead of competing with the script
    for the CPU. Task::spawning_workers() reports the current setting. The switch governs
    THIS process only - web requests, the cron tick and the workers themselves are
    unaffected. It is the same switch the test suite uses (see TESTING).

    Neither `supervisorctl stop tasks` nor rsx:maintenance:enable is the answer: the
    supervisor program only runs the cron tick, and maintenance mode stops rsx-lockd and
    Redis, which the script needs. See rsx:man scripting.

CONFIGURATION (config/rsx.php 'tasks')

    'tasks' => [
        'global_max_workers'   => env('RSX_TASK_MAX_WORKERS', 3),  // pool size (fixed per env)
        'default_timeout'      => 1800,   // execution cap for a row carrying no timeout (0 = none)
        'cleanup_stuck_after'  => 1800,   // dead-worker recovery grace (STUCK TASK RECOVERY)
        'task_retention_days'  => 30,     // how long completed/failed rows are kept
        'failing_schedule_warn_after' => 3,  // consecutive failed runs before rsx:health WARNs
    ],

    #[Task('...', queue: 'reports')] sets a per-task queue LABEL. NOTE: 'timeout' is NOT a
    #[Task] argument - it is a Task::dispatch() option and a _tasks column.

EXECUTION TIMEOUT

    A running task is capped by its own _tasks.timeout, or by rsx.tasks.default_timeout when
    the row carries none. With both absent (or 0) the task runs unbounded.

    Enforcement lives in the cron tick's reaper (rsx:task:process -> detect_stuck_tasks): a
    RUNNING row whose worker is STILL ALIVE - a pool member, with its pid running on the host
    the tick runs on - past its cap is killed through Task_Killer -
    SIGTERM, 5s grace, SIGKILL - exactly as rsx:tasks:kill does, then settled KILLED with a
    "timed out after Ns (cap Ms)" status_reason. A recurring cron TRACKER row is recycled to
    PENDING instead, so a timeout never silently stops a schedule. One [TASK TIMEOUT] line is
    logged per kill.

    Granularity is the cron tick interval (one minute), not the second: a task may overrun its
    cap by up to a tick before the reaper sees it. The kill signals a pid, so it acts only on a
    worker running on the host where the tick runs. The separate dead-worker sweep (STUCK TASK
    RECOVERY) handles the other case - a RUNNING row whose worker is GONE.

COMMANDS

    php artisan rsx:task:run Service method [--param=value]   Run synchronously (CLI)
    php artisan rsx:task:list                                 List discovered tasks, with
                                                              the #[Command] each is
                                                              reachable as (or '-')
    php artisan rsx:tasks:list                                Running instances + every schedule
    php artisan rsx:task:process [--once] [--force-scheduled] The cron tick (below)
    php artisan rsx:task:worker  [--max-time=300]             A pool worker (spawned for you)

    rsx:task:process is the scheduler/dispatcher tick. Install it in cron:

        * * * * * cd /var/www/html && php artisan rsx:task:process

    Each tick it: (1) recovers stuck tasks (STUCK TASK RECOVERY) and enforces timeouts;
    (2) revives any cron tracker found sitting in a terminal state (see FAILURE BEHAVIOR);
    (3) reconciles #[Schedule] tracker rows from the manifest; (4) if there is pending work,
    spawns detached workers until Task::spawn_worker() declines. It does NOT itself become a
    worker. --once claims one task under the pool lock and runs it inline without joining
    the pool (testing); --force-scheduled marks all schedules due now.

    You rarely run rsx:task:worker by hand - the processor and Task::dispatch() spawn
    them. A worker admits itself to the pool under the pool lock (exiting at once when it
    is full), drains by the priority order until empty (or --max-time, checked between
    tasks), then leaves the pool and exits - see THE WORKER POOL.

MAINTENANCE MODE

    While maintenance mode is up (rsx:maintenance:enable, or the window rsx:framework:pull
    raises for an update) the CLI gate is allow-most-deny-some, and the task commands are
    exactly the "some":

        rsx:task:process   REFUSED (exit 75) - the cron tick must not fire into a stopped
                           environment. Cron keeps calling it; every call exits immediately.
        rsx:task:worker    REFUSED (exit 75) - and so a dispatch made during the window
                           simply leaves its row PENDING until the window lifts.
        rsx:task:run       REFUSED unless --force. A human may insist; --force is consumed
                           by the gate and never reaches the task's parameters.

    Enabling maintenance also runs rsx:tasks:kill-all (see KILLING RUNNING TASKS) so nothing
    is mid-write when the services stop. Nothing is lost: on-demand rows go terminal KILLED
    with the explanation, cron trackers recycle to PENDING and keep their schedule.

    See `rsx:man maintenance_mode`.

TASK DATABASE SCHEMA (_tasks)

    id, class, method, queue, status,   // status: pending|running|completed|failed|killed
    params (JSON), result (JSON), logs (TEXT), error (TEXT),
    status_reason (TEXT; one-line explanation for a KILLED, kill-recycled or failure-recycled
      transition; NULL otherwise),
    consecutive_failures (INT; runs that threw since the last success; 0 after a success),
    last_error_at (TIMESTAMP; when the last failure was recorded; NULL if none),
    scheduled_for (run no earlier than), next_run_at (recurring tracker; NULL on one-shots),
    cron_expression (stored schedule for tracker rows; NULL otherwise),
    started_at, completed_at, last_heartbeat_at,
    timeout, worker_pid, worker_member_key (the worker's rsx-lockd pool member id while the
      row is RUNNING; NULL otherwise, and NULL on a row run inline by --once),
    lock_key, created_at, updated_at

    On a TRACKER row, completed_at means LAST SUCCESSFUL RUN (the row is never terminal, so
    nothing else records it). On a one-shot it means what it always did: when the row settled.

FAILURE BEHAVIOR

    A SCHEDULED task that throws does not stop its schedule. The tracker row is recycled to
    PENDING in the SAME update that records the failure, so it fires again at its next
    cadence - exactly like cron itself, where one bad night is not an unsubscribe. Recorded
    on the row: error (full text), status_reason ("failed (recycled): <first line>"),
    last_error_at, and consecutive_failures + 1. completed_at is NOT touched, so it still
    names the last run that actually worked. The row never passes THROUGH a terminal status
    on its way back to pending - one atomic write - so a worker SIGKILLed mid-settle cannot
    strand the schedule.

    A ONE-SHOT (dispatched) task that throws goes terminal FAILED with completed_at and
    last_error_at set, as always. There is NO retry mechanism anywhere in the task system: a
    failed one-shot stays failed until something dispatches it again.

    Any Throwable counts. A TypeError inside a task settles and records its message exactly
    like an Exception.

    A success resets consecutive_failures to 0 and stamps completed_at.

    THE INVARIANT: A CRON TRACKER IS NEVER PERMANENTLY TERMINAL. One tracker row exists per
    #[Schedule] and IS that schedule - park it in FAILED or KILLED and the schedule stops
    forever, silently, while the row still looks registered. Every settle path (failure,
    kill, timeout, dead-worker recovery) therefore recycles a tracker instead of failing it,
    and rsx:task:process ENFORCES the rule each tick: a tracker found in any terminal state
    is revived to pending, loudly ([STRANDED SCHEDULE], logged), with its failure record
    preserved. That sweep should never fire - it exists for strands the settle paths cannot
    reach: rows written by hand in SQL, and rows carried in from a pre-fix release by a
    framework update.

    VISIBILITY. A recycled tracker looks PENDING like every healthy one, so status says
    nothing about health - the failure columns do:

        php artisan rsx:tasks:list     Schedules table: next run, last success, consecutive
                                       failures, and the last error for any failing schedule
        php artisan rsx:health         WARNs once a tracker reaches
                                       rsx.tasks.failing_schedule_warn_after (3) consecutive
                                       failures, naming each offender and its reason

KILLING RUNNING TASKS

    Force-kill running task instances (distinct from the stuck-task reaper, which only acts
    after cleanup_stuck_after). Used by rsx:framework:pull to quiesce work before an update.

        php artisan rsx:tasks:list                                  Running instances (+ schedules)
        php artisan rsx:tasks:kill <id> --explanation="..."          Kill one running task
        php artisan rsx:tasks:kill-all --explanation="..."           Kill every running task

    Each kill sends SIGTERM, waits 5 seconds, then SIGKILL to the row's worker_pid. --explanation
    is REQUIRED and recorded on status_reason. An ON-DEMAND task becomes terminal KILLED; a
    recurring CRON TRACKER row is RECYCLED to pending instead (a terminal status would silently
    stop its schedule). Nothing else needs releasing: an #[Exclusive]/#[Debounce] run lock and
    the worker's pool membership both belong to the worker's rsx-lockd connections, which the
    daemon drops the moment the process dies. The kill signals a pid, so it reaches a worker
    running on the host where the command runs.

    A recurring schedule keeps exactly ONE tracker row (next_run_at + cron_expression). When
    due, a worker advances next_run_at (so the cadence holds even if the run is slow or
    crashes), runs the task, then recycles the row back to pending.

    Atomic dequeue: the task pool lock plus SELECT ... FOR UPDATE guard task selection;
    per-identity run-locks (lock_key) enforce #[Exclusive]/#[Debounce].

STUCK TASK RECOVERY

    A RUNNING row whose worker is gone and whose start predates cleanup_stuck_after is
    recovered by the cron tick: an on-demand row is marked failed; a cron tracker row is
    recycled to pending (its next_run_at is already advanced), so the schedule survives -
    the same rule FAILURE BEHAVIOR states, applied to a row that will never settle itself.

    "Gone" is rsx-lockd's answer. Under the pool lock the tick asks whether the row's
    worker_member_key is still a member of the pool (member_alive), which is false the
    moment the worker's connection closed, on whatever host it ran. The verdicts and the
    settle writes happen under that one lock, so they are one consistent view of the pool
    and the rows.

    The cleanup_stuck_after grace still applies to every verdict. A restart of rsx-lockd
    ends every membership while the workers keep running their current tasks, so without
    the grace a daemon restart would reap live work; with it, only a row that has also
    outlived the grace is settled. (Such a worker notices the lost connection when it next
    takes the pool lock, records its own row's outcome, logs the loss and exits.)

    A row with NO worker_member_key - run inline by rsx:task:process --once, which is not a
    pool member - is judged by the local pid probe instead, a verdict that is only
    meaningful on the host that ran it.

EXAMPLES

    Concurrent-safe scheduled task using a per-site lock:
        use App\RSpade\Core\Locks\RsxLocks;

        #[Task('Recompute a tenant balance sheet')]
        public static function recompute(Task_Instance $task, array $params = [])
        {
            $site_id = (int) $params['site_id'];
            $token = RsxLocks::site_write_lock($site_id);   // exclude concurrent site writers
            try {
                $task->info("Recomputing site {$site_id}");
                // ... multi-step mutation that must be atomic ...
                return ['recomputed' => true];
            } finally {
                RsxLocks::release_lock($token);
            }
        }

    Dispatch + poll from a controller:
        #[Ajax_Endpoint]
        public static function start_export(Request $request, array $params = [])
        {
            $id = Task::dispatch('Export_Service', 'generate', ['kind' => 'clients']);
            return ['task_id' => $id];
        }

        #[Ajax_Endpoint]
        public static function export_status(Request $request, array $params = [])
        {
            $s = Task::status((int) $params['task_id']);
            return ['status' => $s['status'], 'result' => $s['result']];
        }

TESTING

    Under the test suite (rsx:test, Rsx_Test_Abstract::suite_is_running()) spawning is OFF
    by default - Task::spawning_workers() is false: Task::dispatch() writes its row and
    returns, and an rsx:task:process tick a test runs spawns nothing either. A detached
    worker would be a whole PHP boot racing the test that queued it. A test that asserts on
    queued work drives it itself:

        Task::internal('My_Service', 'my_task', $params);    // run the task in-process
        Artisan::call('rsx:task:worker');                     // drain the queue in-process

    A test whose SUBJECT is the spawn opts in for its class:

        Task::spawn_workers(true);

    The runner calls Task::spawn_workers(false) at every class boundary, and the harness
    waits at that boundary for every detached process the class started (rsx:man testing,
    CLASS BOUNDARIES AND DETACHED PROCESSES).

    An in-process worker is a real pool member: it needs rsx-lockd, joins under the pool
    lock and leaves before Artisan::call() returns (a throw closes its pool connection, so
    the test process is never left a member). The pool is named by the connection scope,
    so the test database's pool is never the developer database's pool.

TROUBLESHOOTING

    Dispatched task stays 'pending'
        - Is the pool at global_max_workers? rsx:health "Task Worker Pool" shows the
          members against the cap, whether the pool lock is held and how many wait for it;
          `node system/bin/rsx-lockd/lockd.js dump` names every member's host and pid.
          A full pool is normal: a busy worker reaches the row when it finishes.
        - Did this process call Task::spawn_workers(false)? Then the cron tick drains it.
        - Inside a test? dispatch() spawns nothing under the suite (see TESTING).
        - Did you pass a future 'scheduled_for'? Then it waits until due.
        - Cron is the backstop for due rows: * * * * * php artisan rsx:task:process

    Two tasks corrupt shared data
        - Tasks are unguarded and concurrent. Guard the critical section with a named or
          per-site lock (see LOCKS). #[Exclusive]/#[Debounce] only guard ONE identity.

    Scheduled task not running
        - Confirm the tracker row exists (next_run_at, cron_expression) after one tick.
        - A changed #[Schedule] is picked up within one tick; force with --force-scheduled.

    "Cannot reach rsx-lockd ..." from Task::dispatch() or rsx:task:process
        - The daemon is down or unreachable (rsx:health "Lock Server"; rsx:man locks). A
          dispatch() that would spawn throws AFTER writing its row, so the work is queued
          and runs once the daemon is back. The cron tick throws before recovering or
          spawning anything.
        - Running workers keep running their current task. Their memberships ended with
          their connections, so when each next takes the pool lock it records its row's
          outcome, logs "[WORKER] Lost the task pool connection ..." and exits 1; the next
          tick spawns fresh workers. The cleanup_stuck_after grace keeps the reaper off
          tasks that are still running (STUCK TASK RECOVERY).

    Task Worker Pool WARN: more members than global_max_workers
        - Admission happens under the pool lock, so this means the cap was lowered under
          running workers (they drain as they finish), or two configurations share one
          database and host.

    Scheduled task runs but never succeeds
        - php artisan rsx:tasks:list - the Schedules table shows consecutive failures and
          the last error; the schedule keeps retrying regardless (see FAILURE BEHAVIOR).
        - php artisan rsx:health WARNs once the streak reaches failing_schedule_warn_after.
