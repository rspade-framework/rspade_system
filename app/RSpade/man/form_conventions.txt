FORM_CONVENTIONS(3)             RSX Framework Manual             FORM_CONVENTIONS(3)

NAME
    Form Conventions - The Rsx_Form contract: declaration, submission,
    validation ownership, server-driven questions, resubmission, loading and
    dirty protection

SYNOPSIS
    <Rsx_Form $controller="Frontend_Tasks_Controller" $method="save"
              $data=this.data.form_data>

        <Form_Errors />

        <Form_Field $label="Title" $required=true>
            <Text_Input $name="title" $max_length=Task_Model.field_length('title') />
        </Form_Field>

        <button type="submit" class="btn btn-primary">Save</button>
    </Rsx_Form>

    #[Ajax_Endpoint]
    #[Auth('can_manage_tasks')]        // #[Auth] is MANDATORY - rsx:man auth_gates
    #[Writer]                          // it saves: the site's write lock (rsx:man site_locks)
    public static function save(Request $request, array $params = [])
    {
        $errors = [];
        if (trim($params['title'] ?? '') === '') {
            $errors['title'] = 'Title is required';
        }
        if ($errors) {
            return response_form_error('Please correct the errors below.', $errors);
        }
        // ... persist ...
        return ['redirect' => Rsx::Route('Tasks_View_Action', $task->id)];
    }

DESCRIPTION

        project was forked from (rsx/, your code), not in the framework (system/).
        Your copy may have changed contract, behaviour or shape since - or been
        removed. The current truth is the living file beside the code:

            rsx/theme/components/forms/CLAUDE.md
            rsx/theme/components/inputs/CLAUDE.md
            app skill: form-components

        Read it before relying on anything below; where it records a DIVERGENCE,
        it wins. This page remains the reference for how the feature was designed
        to work and the conventions it was built to - the shape RSpade expects
        application code to keep.

        This page is MIXED. The framework half - Rsx_Form, Form_Errors and
        Form_Utils (skill rspade:form-engine) - is not subject to this notice.
        The template half - Form_Field, Rsx_Tabs and the input roster - is.

    Rsx_Form is the ONE form engine in RSpade, and it lives in framework core
    (Core/Forms/). An application never carries a copy of it, of
    Form_Input_Abstract, or of Form_Errors; they reach every bundle through
    Core_Bundle with no per-bundle wiring.

    Three words, used exactly:

        Form    Rsx_Form - value state, dirty tracking, submission, error
                rendering. One pipeline, no exceptions.
        Field   Form_Field (application-owned) - label, required asterisk, help
                text. Purely presentational; it validates nothing and renders no
                error markup of its own.
        Input   A Form_Input_Abstract subclass - ONE named value, val(), events.
                See form_input(3).

    Everything else is chrome. Modal.form() is a dialog that hosts a form and
    drives THAT form's submit(); it has no pipeline of its own. See rsx:man modals.

    Contract summary in code: the class docblock of
    system/app/RSpade/Core/Forms/Rsx_Form.js.

THE DECLARATION

    Arguments on the <Rsx_Form> tag:

        $controller   REQUIRED - controller class name
        $method       REQUIRED - Ajax endpoint method on that controller
        $data         OPTIONAL - seed values for an edit form; omit for a
                      pristine create form

    $controller + $method is the ONLY place an endpoint is ever named. Modals do
    not repeat it, buttons do not repeat it, JavaScript does not repeat it. A
    submit() with either missing throws:

        Rsx_Form: $controller and $method are required on the <Rsx_Form> tag -
        the form declaration is the only place the endpoint is named.

    $data seeds an EDIT form (typically the record's fetch() payload, always a
    plain serializable object - never a model instance). Values bind by matching
    each input's $name to a key. $name belongs on the INPUT, never on Form_Field,
    and an input NEVER carries $value - the form writes it.

    Inputs still initializing when the seed lands receive their values through
    Form_Input_Abstract's pending buffer, so ordering is never the author's
    problem.

    Every form contains exactly one <Form_Errors />, placed where the LAYOUT
    wants failure feedback - inside the first section, above a two-column grid,
    under a heading - so the form's own structural containers give the alert
    their spacing. The engine never invents a position. A form without one throws
    at the moment feedback is needed:

        Rsx_Form: no <Form_Errors /> in this form. Every <Rsx_Form> places
        exactly one <Form_Errors /> where the layout wants its failure feedback.

THE SUBMISSION PIPELINE

    form.submit() is the only submission path. A button of type="submit" inside
    the form is auto-wired to it; the form element's OWN submit event is bound to
    it, so the browser's implicit submission - Enter in a single-line text input,
    with no button involved - submits the form rather than navigating the page; a
    modal's primary button calls it; programmatic callers call it. It returns a
    promise resolving with the server result on success and false on ANY failure
    (client _validate(), server validation, transport, or a before_submit abort).

    Stages, in order:

        1.  Re-entrancy guard - a second submit while one is in flight returns
            false immediately.
        2.  Loading guard - a form wearing the loading overlay refuses (see
            LOADING below).
        3.  Clear rendered errors (inline marks, messages, alert, tab badges).
        4.  Client _validate() pass - the architectural exception only, see
            VALIDATION.
        5.  Serialize - vals() collects EVERY descendant input plus the native
            hidden inputs the form owns (see HIDDEN FIELDS OUTSIDE THE FORM).
        6.  before_submit hook, when the host installed one.
        7.  Submit affordance - Button_Utils animates the submit buttons and
            makes them inert.
        8.  Ajax POST to /_ajax/{controller}/{method}, carrying the form's
            _request_ref (see RESUBMITTING).
        9a. Success: touched and parked values cleared, the reference kept
            (used) or replaced, the inputs re-baselined ('dirty' flips to
            false), 'submitted' fired with the result - and 'replayed' when the
            request history answered - result.redirect followed through Rsx.navigate()
            with {via: result.redirect_via || 'carry'} (the affordance
            deliberately stays until the page goes), result resolved.
        9b. Failure: errors rendered, 'submit_error' fired, false resolved. The
            form stays on screen with the user's values intact.

    THE BEFORE_SUBMIT HOOK

        Installed by the host (Modal.form's before_submit option, or a page
        action assigning form.before_submit). It receives (values, form) and may:

            return an object   the adjusted payload is submitted
            return false       ABORT SILENTLY - the seam for interaction guards,
                               because an "are you sure?" the user declined is
                               not an error and must not render as one
            throw {f: msg}     rendered as validation on those fields
            throw an Error     rendered as a single alert

        A field shown but not to be written is REMOVED here. The worked case is
        a model DERIVED COLUMN with an editable source column (rsx:man
        derived_columns, ONE VALUE, TWO COLUMNS): while a rule supplies the
        value, the page disables the source column's input and shows the
        derived value in it, and its before_submit deletes that field from the
        payload; the endpoint writes the source column only when the key is
        present, so the stored choice survives. A derived column itself is never
        a form field - Form_Edit::set() of one throws.

    EVENTS

        'submitted'     (result)   a successful submit; the payload is exactly
                                   what the endpoint returned
        'submit_error'  (error)    a failed submit, after the errors rendered
        'replayed'      ({result, completed_at})
                                   the success was answered from the request
                                   history (fires after 'submitted'); see
                                   RESUBMITTING
        'input'         (name, v)  the user changed a field, by name

VALIDATION LIVES ON THE SERVER, ONCE

    The form performs NO client-side validation of server-checkable rules. No
    required checks, no formats, no lengths, no ranges - anywhere: not in the
    form, not in an input, not in a modal wrapper.

    WHY, because this departs from common wisdom: a client check that duplicates
    a server rule MASKS the absence of the server rule. Blank never reaches the
    endpoint, the missing server validator is never exercised, every manual test
    looks green, and the gap surfaces only when an API caller or a script hits
    the endpoint directly - silently, in production.

    Secondary reasons: one rule, one home (duplicated validation drifts across
    two languages, and the server's copy is the one every caller shares); and
    the round trip is not a cost - a server answers a validation submit as fast
    as a keystroke handler, so pressing Submit and rendering the server's message
    IS the responsive UX.

    $required on Form_Field is PRESENTATION - the asterisk telling the user a
    server rule exists. It enforces nothing. An asterisk with no server rule
    behind it is a lie the framework cannot detect; the pairing is the author's.

    THE _validate() EXCEPTION

        An input may implement _validate(value), returning null or a message
        string. It exists solely for a constraint whose invalid state cannot even
        be EXPRESSED to the server: a pick-at-most-two multiselect where a third
        selection is unrepresentable in the payload, a structured value that
        cannot serialize when malformed. It renders through the same pipeline as
        a server error, so there is no second styling path.

        It is NEVER for required, format, length or range. And even where it is
        legitimate, prefer interaction design - the widget refusing the third
        click needs no message at all. Almost every input keeps the inherited
        no-op forever.

THE ENDPOINT CONTRACT

    BLANK IS A VALUE; ABSENT MEANS UNTOUCHED

        The form serializes every input on every submit, so a blank field always
        arrives as '' - blank is something the user DID, never an omission. The
        endpoint contract follows:

            absent key            leave it untouched (a partial update; widget
                                  callers and the external API legitimately omit
                                  fields)
            present but blank     MUST validate - a required field rejects it
                                  identically on create and on edit; an optional
                                  field SAVES it

        "Keep the old value when blank" is FORBIDDEN server-side. It makes a
        failed clear look like a success: the user emptied the field, pressed
        save, and the server silently ignored them.

    VALIDATION FAILURES

        return response_form_error('Please correct the errors below.', [
            'title' => 'Title is required',
            'email' => 'Invalid email format',
        ]);

        The first argument is the SUMMARY MESSAGE and the second is the field
        map. response_error(Ajax::ERROR_VALIDATION, 'a string') carries the
        message and no field map: the top alert shows it and no field is
        marked. When the failure is about one input, name it - the message is
        then pinned where the user has to act.

        Each key is matched to the input whose $name it names, and the message is
        pinned under that field. An unmatched key is legitimate (a rule about no
        single field) and renders in the top alert instead.

        THE TOP ALERT ALWAYS RENDERS on a failed submit, even when every message
        matched a field inline - a failure is never silent at the top of a form.
        The server's summary wins; absent one, the engine writes "Please correct
        the error(s) highlighted below." The form then scrolls its feedback into
        view, walking to the nearest scrollable ancestor and clearing sticky
        headers.

        When the form contains Rsx_Tabs, tab badges update and the first erroring
        tab activates.

    OTHER FAILURES

        not_found, unauthorized, generic and transport failures render as a
        single alert in <Form_Errors />. Nothing to write: submit() resolves
        false and the form has already rendered it. Never wrap a submit in
        try/catch to "handle" a validation error - swallowing it before the
        renderer sees it is exactly how a failed save comes to look like a
        successful one.

    SUCCESS

        Return whatever the caller needs; ['redirect' => Rsx::Route(...)] makes
        the form navigate, through Rsx.navigate() (rsx:man navigation).
        Flash_Alert::success(...) before returning is the normal companion to
        a redirect. A CREATE answers with somewhere to go - the redirect, or
        the new record's id: that answer is what a resubmission is replayed
        with and what the resubmit dialog's "View it" uses (RESUBMITTING). A create endpoint whose page was reached from another
        record adds 'redirect_via' => 'continue', so the record it created
        keeps that breadcrumb origin (rsx:man breadcrumb_origins); 'carry' is
        the default and 'drop' the third value, anything else throws in the
        browser.

QUESTIONS (SERVER-DRIVEN CONFIRMATION)

    A submission sometimes needs to ask the user something before it can finish:
    "a contact with this email already exists - create anyway?", "this group
    still has 12 members - remove it anyway?". That is not a validation error
    (nothing the user typed is wrong) and not a success (nothing was written).
    It is a QUESTION, and the framework carries it through the same pipeline.

    WHY THE SERVER ASKS

        The trigger is server knowledge: whether an address is already in use,
        whether a group has members, whether an invoice has payments. Asking
        from the client would mean re-implementing each of those rules in
        JavaScript, where it drifts from the rule it mirrors - the same reason
        validation lives on the server, once (see VALIDATION LIVES ON THE
        SERVER, ONCE). So the question originates exactly where a validation
        error originates: in the endpoint, after validation, before the write.

    THE PROTOCOL

        1. The endpoint returns response_form_question($key, $question).
        2. The form engine calls the application's registered question handler
           with $question verbatim and receives an answer.
        3. The engine calls the endpoint AGAIN with the same values plus
           _answers: {$key: answer}.
        4. The endpoint re-runs from scratch, reads the answer, and writes.

        One question per response. The framework holds no state between rounds.

    VALIDATE -> ASK -> WRITE

        An endpoint validates first, then asks the FIRST question that is still
        unanswered, then writes. Nothing - no row, no file, no email - happens
        before every question has been answered, because the resubmission
        re-runs the whole endpoint. That is also what makes it stateless: if the
        world changed between rounds and a question is due again, it is simply
        asked again.

            $answer = Form_Questions::answer($params, 'duplicate_email');

            if ($answer === null) {
                return response_form_question('duplicate_email', [
                    'kind' => 'confirm',
                    'title' => 'A contact with this email already exists',
                    'body' => "Richard Browne (Acme Corp) already uses {$email}."
                            . "\n\nCreate a second contact with the same email?",
                    'confirm_label' => 'Create anyway',
                    'cancel_label' => 'Open the existing contact',
                ]);
            }

            if ($answer === false) {
                return ['redirect' => Rsx::Route('Contacts_View_Action', $existing->id)];
            }

            // true: fall through and create

        NULL MEANS NOT ASKED YET. Every other value, FALSE INCLUDED, is an
        answer the user gave and the endpoint acts on.

            Form_Questions::answer($params, $key)     mixed; null when unanswered
            Form_Questions::answered($params, $key)   bool

        $question is OPAQUE to the framework. No field of it is read on the way
        to the handler; the recommended shapes below are documentation.

    REGISTERING THE HANDLER

        Once per application, from a static on_app_modules_define() on the class
        that owns the presentation - the modal facade, typically. There is no
        init file and none is needed.

            static on_app_modules_define() {
                Rsx_Form.set_question_handler(async (question, context) => {
                    // present it however this application presents questions
                    return answer;   // or Rsx_Form.CANCELLED
                });
            }

            context: {form, key, attempt, answers}
                     answers = those already given during THIS submission

        A FORM may override it - <Rsx_Form $question_handler=this.ask_inline>,
        or form.question_handler = fn - with the same signature, for a form that
        wants its question asked inline rather than in the usual dialog.

        NO HANDLER ANYWHERE IS AN ERROR. The submit throws, naming
        Rsx_Form.set_question_handler(). A question reaching a client that
        cannot ask it is a configuration fault, never a silent skip.

    CANCEL IS NOT AN ANSWER

            Rsx_Form.CANCELLED          a frozen sentinel object
            Rsx_Form.is_cancelled(v)    identity test

        Returning CANCELLED stops the submit exactly like before_submit
        returning false: no error rendered, no 'submit_error' fired, unsaved changes
        and parking intact, the form still open with the user's values. It is
        what the dialog's Back button, its X, Escape and a backdrop click mean.

        FALSE IS AN ANSWER. "No" reaches the endpoint and the endpoint acts on
        it. CANCELLED never reaches the endpoint at all. The sentinel is an
        OBJECT and never a boolean precisely so the two can never collide - a
        dialog whose "No" button resolves with a bare false is indistinguishable
        from a dismissal, so give "No" a distinct token and map it.

    A RE-ASK IS THE DEFECT, NOT A ROUND COUNT

        A submission may go through any number of question rounds, as long as
        each round asks a key not yet answered in it - a form's own questions
        plus one per uploaded file (the duplicate-upload question) is ordinary.
        Every prior answer is carried forward, so an endpoint asking a key the
        submission has ALREADY answered is ignoring _answers, and the loop it
        started is infinite. That re-ask ends the submission with a rendered
        error naming the endpoint and the key, instead of a tab that posts
        forever:

            Controller::method asked 'some_key' again after it was answered,
            so the submission cannot finish. ...

        The same message follows a question handler that answered null or
        undefined: the server reads either as not answered (THE NULL RULE in
        Form_Questions) and asks again. An endpoint that must ask about
        something new keys the new question differently (Form_Edit keys its
        conflict question on the version it is about).

    WHAT THE FRAMEWORK WILL NOT DO

        - Define question kinds. 'confirm', 'select' and 'prompt' below are a
          RECOMMENDED contract; an application may invent kind: 'portal_invite'
          and mount its own component.
        - Render anything, ship a default dialog, or fall back to
          window.confirm.
        - Hold state between rounds, or support more than one question per
          response.
        - Close, hide or re-render the form's host. A form inside a modal stays
          exactly where it is while the question is asked over it; how a
          question stacks over an open dialog is the application's decision.

    THE RECOMMENDED QUESTION CONTRACT

        { kind: 'confirm', title, body, confirm_label, cancel_label, back_label }
            answer: true | false        (Back / X -> Rsx_Form.CANCELLED)
            back_label (optional) labels the button that answers nothing and
            stops the call ("Back" when absent). The duplicate-upload question
            is a confirm: Cancel Upload / Skip This File / Upload Again
            (rsx:man file_upload, DUPLICATE UPLOADS).

        { kind: 'select', title, body, options: [{value, label}], default }
            answer: the chosen value

        { kind: 'prompt', title, body, default, multiline }
            answer: the string

        { kind: 'field_conflict', title, body, confirm_label, cancel_label,
          record, view_url, editors, fields }
            asked by Form_Edit (EDITING A RECORD, WHEN IT ASKS). answer: true
            overwrites; false keeps the other editors' values and writes the rest.

            record      {type, id}: the record being saved
            view_url    where its current version can be seen (the endpoint's
                        run(..., $view_url)), or null
            editors     each person who saved a listed field since the form loaded,
                        once, in the order of their first change: {type, id}, or
                        null for a write nobody signed in made (a task, a script)
            fields      one row per field this submission would overwrite:
                field     the form field, named as the input is
                kind      value | enum | reference | formatted_text | structured |
                          secret - what the values below can be
                record    {type, id}: the record the field is stored on - the
                          record being saved, or a coupled record (EDITING A
                          RECORD, COUPLED RECORDS)
                groups    the labels of the fact groups the changes came
                          through, [] for none (EDITING A RECORD, FACT GROUPS)
                loaded    the value the form was opened with
                current   the value saved now, which saving overwrites
                yours     the value this submission writes
                changes   [{by, at, record, column, group, from, to}], every
                          save since the form loaded that changed the field,
                          oldest first, one per column it changed: by as in
                          editors, at ISO 8601, record {type, id} and column
                          where it was saved, group that column's fact group
                          label or null, from/to that COLUMN's values

            A reference is {type, id}: type is the actor's class name, whatever the
            stamp matrix named - a site's User_Model, a Portal_User_Model, a
            Login_User_Model for a cross-site write, a Companion_Actor_Model, or an
            application's own actor class. NOTHING in the payload is display text for
            a person or a time: the application shows editors with its own components
            and times with its own formatters.

            Values are display text by kind: an enum's label, a referenced record's
            name, a formatted text's plain text, the value itself; a secret and a
            structured value (an array, a JSON document) carry null - say only that it
            changed. A field stored in several columns, or changed through another
            column of its fact group, is structured: loaded, current and yours are
            null, and each change's from/to show the column it names.
            form.label_for(field) names a field as the form does.

            THE EXPECTED DIALOG lists the rows saving overwrites, each with the value
            it overwrites and the one it writes, and confirms. One editor is named in
            the notice ("Jane Smith changed this record while you were editing");
            several are counted there and named per row. Buttons: Back (the form stays
            open, nothing written) and Overwrite; a link opens view_url in a new
            window. An application may add anything: a per-row choice of mine or
            theirs (answer false keeps theirs for every listed row), its own person
            and record widgets. The template's version is Modal._field_conflict_body()
            in system/app/RSpade/resource/reference_app/lib/modal/modal.js.

        { kind: '<application-defined>', ... }
            answer: whatever the application's handler returns

        title and body are PLAIN TEXT; \n\n is a paragraph break, as in the
        dialog facades.

    A CALLER THAT IS NOT A FORM

        A widget calling Controller.method() directly, or an API bridge, sees
        the question as a distinct response code:

            error.code === Ajax.ERROR_QUESTION
            error.metadata.key, error.metadata.question

        Rsx_Form.ask(question, {key}) runs the registered handler for such a
        caller, so the question looks identical wherever it came from; the
        caller then decides what to do with the answer.

        Rsx_Form.call_answering(url, params) is that whole loop for a caller
        that simply wants the endpoint answered: it calls, asks each question
        through Rsx_Form.ask(), resends with every answer so far in _answers,
        and resolves with the endpoint's value - or Rsx_Form.CANCELLED when a
        question was cancelled (the endpoint is not called again).

            const result = await Rsx_Form.call_answering(Tasks_Controller.attachments_add, { id, keys });
            if (Rsx_Form.is_cancelled(result)) return;

        The rule is the form's (A RE-ASK IS THE DEFECT, NOT A ROUND COUNT), one
        implementation for both: any number of distinct keys, and an endpoint
        asking a key it was already answered throws, naming the endpoint and
        the key. In PHP, an in-process
        Ajax::internal() raises AjaxQuestionException, carrying get_key() and
        get_question() - which is what a PHP test and rsx:ajax see.

    THE WORKED EXAMPLE

        system/app/RSpade/resource/reference_app/lib/modal/modal.js
            the registered handler: three kinds, a three-button confirm, and
            the distinct "No" token that keeps cancel and No apart.

        system/app/RSpade/resource/reference_app/app/frontend/contacts/contacts_controller.php
            save(): validate, ask about the duplicate email, then write.

RESUBMITTING (THE REQUEST REFERENCE)

    A submission can commit while its answer never reaches the user - a dropped
    connection, a proxy 502, a lock or database outage after the commit - and the
    user presses Save again. Or they create a record, press Back, and submit the
    create form again. Either way the write must not happen twice. The form
    sends a _request_ref with every call submit() makes, and a writer endpoint
    answers a reference it has already succeeded under from the request history
    (rsx:man request_history) instead of running again. Endpoints and forms
    write nothing for it.

    THE REFERENCE LIFECYCLE

        A form holds ONE reference: a random UUID (Ajax.request_ref()), unique
        across page loads because the server keeps it with its _transactions
        row for good. It is sent on every call of a submission, question
        rounds included (_answers, _changed and _loaded_updated_at are outside
        the fingerprint).

        KEPT while submissions fail: a transport failure, a 5xx, an answer
        missing the call, a validation error the user fixes, a question. A
        validation error or a question records nothing, so the corrected resend
        simply runs.

        BOUND TO THE HISTORY ENTRY. The reference belongs to the form's
        identity - controller|method|record id or 'new', the parking key - on
        the browser history entry the form is on, kept in that entry's state.
        The form reached again by Back is a new instance, and still sends the
        same reference; so does the form on a reload of that entry. This holds
        on an SPA page and a Blade page alike.

        After a SUCCESS:
            the success navigates away (result.redirect)
                -> the reference stays on the entry, marked used. Coming
                   Back and submitting again replays (same values) or is
                   refused as reused (changed values) - never a second record
            the form stays on screen (an inline add form, an edit form that
            remains open, a dialog its host keeps open)
                -> a new reference: the next submission is a new act

        A FORM IN A DIALOG (inside <dialog>, or an element with role="dialog"
        or role="alertdialog") is bound to its INSTANCE, not the entry: the
        reference dies with the dialog, and reopening it is a new act. KNOWN
        LIMIT: a user who closes the dialog after a lost answer and starts over
        in a new dialog is not protected.

        TWO LIVE FORMS WITH ONE IDENTITY on a page (two "add note" forms posting
        to one endpoint) cannot be told apart on Back: the first to submit
        holds the entry's reference and the other is bound to its instance.

        form.already_submitted() is true once this entry's reference has
        succeeded - a create form reached by Back after it saved - so a host
        may say so before the user types.

    WHAT THE USER SEES

        A REPLAYED SUCCESS IS A SUCCESS. The success path runs with the stored
        result - dirty and parking cleared, 'submitted' fired, result.redirect
        followed - and additionally 'replayed' fires and the application's
        REPLAY NOTICE is called. For the Back case on a create form, this lands
        the user on the record that was created, told why. Side channels of the
        original answer (a Flash_Alert the endpoint queued) are not replayed.

        A REUSED REFUSAL IS A QUESTION. request_ref_reused on the form's own
        endpoint means "this form, on this entry, already succeeded, and the
        values changed". request_response_expired means the earlier submission
        is older than the server keeps answers. Both go to the application's
        RESUBMIT HANDLER, which answers:

            Rsx_Form.RESUBMIT_AS_NEW ('new')
                a fresh reference, and the current values submitted - in the
                same submit() call
            Rsx_Form.CANCELLED
                stop: nothing rendered, no 'submit_error', the form open with
                its values (exactly as a cancelled question). A handler that
                navigates to the earlier result itself ("View it") returns this

        Any other answer throws, naming the two. A request_ref_reused on ANOTHER
        endpoint is a client defect and renders as an ordinary error.

    REGISTERING THE HANDLERS

        Once per application, from the same static on_app_modules_define() that
        registers the question handler:

            Rsx_Form.set_replay_notice((result, context) => { ... });
                context: {form, completed_at}. Presentation only (a flash);
                NOT awaited. completed_at is the ORIGINAL completion, ISO UTC

            Rsx_Form.set_resubmit_handler(async (context) => answer);
                context: {form, completed_at, original, expired}
                original   the earlier submission's result while the server
                           still keeps it (its redirect, its id), else null
                expired    true for request_response_expired

        A form may override either - $replay_notice= / $resubmit_handler= on
        the tag, or form.replay_notice / form.resubmit_handler.

        NEITHER IS REQUIRED. With no replay notice a replay is a silent
        success. With no resubmit handler the refusal renders in <Form_Errors />
        ("This form was already submitted on <time>, so nothing was saved this
        time. Submit it again to save it as a new submission.") and the
        reference is replaced, so the user's next submit runs as new - never a
        silent skip, and never a form that refuses forever on that entry.

        The framework defines the protocol and ships no dialog. The template's
        version is Modal._on_form_replayed() / Modal._on_form_resubmitted() in
        system/app/RSpade/resource/reference_app/lib/modal/modal.js: a flash
        "This was already saved on <time>.", and a dialog "You already submitted
        this form on <time>." with Cancel, Submit again as new, and View it
        (when original.redirect names somewhere to go).

    WHAT A SAVE ENDPOINT OWES (nothing new to build)

        - be a writer: #[Writer], or #[Manual_Lock] that takes a site write
          lock. A reader, or a manual endpoint that takes no write lock,
          records nothing and is not protected;
        - answer a create with somewhere to go (redirect, or the new id) - the
          replay returns it and "View it" uses it;
        - keep every effect inside the transaction (queue rows, never an inline
          send) - already the writer rule (rsx:man site_locks);
        - a coded failure (response_form_error(), a question) records no
          reference, so the corrected resend runs - unchanged.

        A signed-in actor is what a reference is kept under: a form nobody is
        signed in to (a sign-in or accept-invitation form) sends one, and it is
        echoed, never honoured - the form behaves exactly as without it.

    A CALLER THAT IS NOT A FORM

        A writer called straight from a stub has the same lost-answer problem:
        Ajax.action() keeps a reference per user action and endpoint across
        that action's retries (rsx:man request_history, BROWSER CALLERS).

EDITING A RECORD
    A form that edits a record saves through Form_Edit. Two things go wrong without it:
    two people with one record open overwrite each other, and a submission that
    changed one field rewrites all of them.

    THE FORM. Rsx_Form adds two keys to every submission, beside all the values:

        _changed             the fields that differ from what the form was given
        _loaded_updated_at   the version it was given: $data.updated_at

    So the seed MUST carry the record's updated_at. A seed built by hand adds it:

        this.data.form_data = { updated_at: client.updated_at, id: client.id, ... };

    _changed is wider than dirty(): a value a page wrote with val() is not unsaved work,
    but the record does not hold it, so it is reported. So is one a before_submit hook
    altered. A form that stays open after saving moves to the updated_at in the result.

    THE ENDPOINT is a #[Writer] (an Ajax endpoint is a reader unless it says so, and a
    reader that saves fails). Validate first, as ever: every field still arrives, so
    required and cross-field rules see the whole form. Then:

        $client = $params['id'] ? Client_Model::find($params['id']) : new Client_Model();
        if (!$client) {
            return response_error(Ajax::ERROR_NOT_FOUND, 'Client not found');
        }

        return Form_Edit::run($client, $params, function (Form_Edit $edit) use ($client, $params) {
            $edit->set('name', $params['name']);
            $edit->set('email', $params['email'] ?? null);
            $client->save();

            Action_Log::record(Action_Log_Model::TYPE_CLIENT_UPDATED, $client);

            return ['id' => $client->id, 'redirect' => Rsx::Route('Clients_View_Action', $client->id)];
        }, $client->exists ? Rsx::Route('Clients_View_Action', $client->id) : null);

    Form_Edit::run($record, $params, $write, $view_url = null, $coupled = [], $fields = [])
        Opens a transaction, takes a row lock, refreshes $record, settles any conflict,
        then calls $write. A throw rolls everything back. It adds updated_at to an array
        result. A new record has no conflict to settle and writes every set().
        A record deleted meanwhile answers ERROR_NOT_FOUND. $view_url is where the
        record's current version can be seen, carried on the question for its link:
        pass the view page's Rsx::Route() for an existing record.

    $edit->set($field, $value)
        Assigns the value if this submission writes that field. Same explicit, one
        field at a time assignment as `$record->field = $value`, so a transformed value
        goes straight in. The column is the one fields: stores the field in, else the
        column of the field's name. A field fields: stores in several columns, or in a
        column shared with other fields, throws: the callback composes those columns
        itself, guarded by changed().

    $edit->changed($field)
        Is this submission writing $field? For what set() cannot do: a pivot, a
        detail-table field, a value composed from several fields.

    REQUIRED: the model declares `public static $revisions = true`. Form_Edit reads
    what the other person changed from revision history and throws naming the model
    when there is none. A framework model is extended to declare it (rsx:man
    class_override).

    NEVER inside your own DB::transaction(): run() holds the transaction, and a snapshot
    taken before its lock is granted would hide the save it waited for.

    INSIDE A #[Writer] that warning does not apply. The writer's transaction is the
    framework's, opened AFTER the site's write lock was granted, so its snapshot is
    current and nothing else writes the site meanwhile; run() nests in it as a
    savepoint, and the writer commits once at the end. The same holds inside a
    Site_Lock::write() section. A coded result the endpoint RETURNS
    (response_form_error(), response_form_question()) commits what it wrote before
    answering; a thrown one rolls the request back -
    throw new Rollback_Response(response_form_error(...)) answers the same
    envelope and undoes the write (rsx:man site_locks, HOLDING A LOCK WELL).

    WHEN IT ASKS. Only when another save changed a field this submission also changed,
    to a value other than the one this submission writes. A save that touched other
    fields is no conflict: this submission writes only its own, both stand, and nobody
    is asked; nor is a field both people set to the same value. An overlap asks the
    'field_conflict' question (QUESTIONS): true overwrites, false keeps the other
    editors' values and writes the rest, and Back leaves the form open and writes
    nothing. A further save between rounds is a new question.

    A write that recorded no revision - raw_bulk(), raw SQL, or only excluded columns -
    moves updated_at without saying what changed. That asks a plain 'confirm': "No"
    writes nothing. So a column that moves on its own (a last-seen stamp) belongs in a
    write that does not touch updated_at, or the people editing that record are asked.

    COVERS the record's own columns, and the columns of every COUPLED record. A pivot or
    detail-table field is written only when changed, but is not checked for a conflict.

    COLUMNS AND FIELDS. Revisions name COLUMNS; a submission names FORM FIELDS. A record's
    own column is the form field of the same name, unless fields: maps it:

        Form_Edit::run($entry, $params, $write, $view_url, fields: [
            'entry_date' => 'activity_date',                    // the form names it otherwise
            'parent_type' => 'parent', 'parent_id' => 'parent', // several columns, one field
            'starts_at' => ['start_time', 'start_day'],         // one column, several fields
        ]);

    A column stored from one field under another name is matched through the map; a field
    stored in several columns (a polymorphic pair edited as one picker) conflicts with a
    change to any of them and is always asked about - there is no one value to compare; a
    column that feeds several fields is a change to each. An unmapped column keeps its own
    name. A field a map places (here or in a coupled map) is never also the record's own
    column of that name. The same three forms work in a coupled record's map.

    WITHOUT the map a renamed or split field matches no column: another editor's change to
    it is overwritten with no question. Check every run() call for a field the form names
    differently from its column.

    FACT GROUPS. A model declares the columns that hold one fact (rsx:man model, FACT
    GROUPS):

        public static $fact_groups = [
            'when' => ['label' => 'Date and time', 'columns' => ['date_start', 'date_end', 'time_start', 'time_end']],
        ];

    A revision that changed ANY column of a group is a change to every form field stored in
    ANY column of it - on the record, and on each coupled record through that record's map
    and its own model's declaration. So a form that sends the day as a field stored in
    date_start conflicts with another editor's re-date saved in time_start. Such a change is
    always asked about (one submitted value cannot be compared with the group): the row is
    structured, its groups name the group by label, and each change carries the column it
    changed with that column's before and after. A field stored in one column and changed
    only in that column is compared as any other field. A model with no groups and a call
    with no fields: behave as they always did.

    COUPLED RECORDS. Some edits write two records as one: the form belongs to one, but
    some of its fields are stored on another (an entry edited together with its
    activity). A save of the other record through its own screen moves neither the
    record's updated_at nor its revisions, so without this it would be overwritten with
    no question. Name the other record, with a map from its columns to the form's
    field names:

        return Form_Edit::run($entry, $params, function (Form_Edit $edit) use ($entry, $activity, $params) {
            $edit->set('qty', $params['qty']);
            $entry->save();

            if ($edit->changed('activity_type')) {
                $activity->type_id = $params['activity_type'];
            }
            if ($edit->changed('activity_time')) {
                $activity->time_start = $params['activity_time'];
            }
            $activity->save();

            return ['id' => $entry->id];
        }, $view_url, coupled: [
            [$activity, ['type_id' => 'activity_type', 'time_start' => 'activity_time']],
        ]);

    With coupled records:

    - THE VERSION IS THE COMPOSITE: the newest updated_at among the record and its
      coupled records. Every read that a later edit is compared against - the form's
      $data seed (updated_at), an API payload, a delete's precondition - publishes
      Form_Edit::version_of($entry, $activity), so the version a caller sends back
      covers what it saw of BOTH. (Seeded with the record's own updated_at, a save of
      the activity before the read would be reported as a conflict.) The result's
      updated_at is the composite too.

    - A coupled record's revisions are read through its map: a change to a mapped
      column is a change to its form field, and conflicts like any other field. A
      column outside the map (and outside the fact group of a mapped column) is never
      a conflict, nor is a mapped field this submission does not send. The map takes
      the forms fields: does (COLUMNS AND FIELDS). A form field the map gives to a
      coupled record is never the record's own column of the same name; a field
      stored on both (fields: on the record and a coupled map) is stored in several
      columns.

    - Each question row names the record its field is stored on (fields[].record).

    - The record is row-locked first, then each coupled record in the order given,
      each refreshed under its lock; a coupled record deleted meanwhile answers
      ERROR_NOT_FOUND. A coupled record that moved with no revision recorded asks the
      plain 'confirm', as the record does.

    - set() writes the record only. The callback writes a coupled record's columns
      itself, guarded by $edit->changed('<form field>') - so "keep theirs" keeps them
      too - and saves the coupled record instance it passed.

    Every coupled record's model declares $revisions = true, and each is a saved record;
    run() throws naming it otherwise.

    Form_Edit::version_of($record, ...$coupled): string
        The newest updated_at among the records, in database format. One record is its
        own updated_at.

    See system/app/RSpade/resource/reference_app/app/frontend/clients/clients_controller.php
    (one record), projects/projects_controller.php (pivots) and party/party_controller.php
    (detail tables). tasks/tasks_controller.php maps the task's parent picker onto its
    taskable pair, which Task_Model declares a fact group. Tests: rsx:test --framework
    Form_Edit_Test Form_Edit_Coupled_Test Form_Edit_Fact_Groups_Test.

HIDDEN FIELDS OUTSIDE THE FORM

    <Rsx_Form> renders a real <form> element, so the browser's own form
    association applies: give the form an id, and a native hidden input
    anywhere in the document carrying form="<that id>" belongs to it.
    vals() reads form.elements, which is exactly that set - the form's
    descendants plus the inputs associated by id, minus a descendant that
    names another form.

    The intended use is the human-verification widget, Turnstile_Input,
    placed outside the form - below a sign-in card, say - and still posting
    with it (rsx:man turnstile, OUTSIDE ITS FORM):

        <Rsx_Form id="create-account-form" $controller="Accept_Invite_Controller"
                  $method="create_account_submit">
            ...
        </Rsx_Form>

        <Turnstile_Input $form="create-account-form" />

    Only a native hidden input is reached this way. An input COMPONENT
    (anything extending Form_Input_Abstract) belongs to the form it renders
    inside, always.

VALUES AND INPUT ACCESS

    form.vals()             serialize - {name: value} for every descendant input
                            (shallow: inputs inside a composite input belong to
                            that composite) plus the native hidden inputs the
                            form owns - its descendants, and any hidden input
                            elsewhere whose HTML form attribute names its id
    form.vals(object)       apply - sets each named input present in the object,
                            SKIPPING touched names (see KEYSTROKES WIN); never
                            makes the form dirty
    form.dirty()            true while any input holds a value the user changed
                            (see UNSAVED CHANGES)
    form.input(name)        the input component with that $name, or null - the
                            sanctioned way to wire one input:
                            form.input('due_date').on('val', cb)
    form.populate(promise)  the async edit procedure, see LOADING
    form.set_loading(bool)  the overlay primitive
    form.render_error(err)  render a failure the host caught itself

    To programmatically overwrite a field the user has touched, address the input
    directly: form.input(name).val(v). vals(object) will not do it, by design.

    Events on the form: 'input' (name, value) for every user edit, 'dirty'
    (dirty) when dirty() flips, 'submitted' (result), 'submit_error' (errors).

THE PAGE PATTERN (SPA add/edit action)

    A dual-@route action loads its record in on_load() and hands it to the form
    as $data, and declares @spinner_until_ready('always'): the action is hidden
    behind the application's spinner on EVERY visit until it is ready, so the
    form is never seen - or typed into - before its record has been applied,
    a cached revisit included. No loading overlay, no "settled" flag and no
    re-seeding of the form in on_ready() is written by hand.

    Worked example, complete and current:
        system/app/RSpade/resource/reference_app/app/frontend/tasks/edit/
            Tasks_Edit_Action.js
            Tasks_Edit_Action.jqhtml

        @route('/tasks/add')
        @route('/tasks/edit/:id')
        ...
        @spinner_until_ready('always')
        class Tasks_Edit_Action extends Spa_Action {
            on_create() {
                this.data.is_edit = !!this.args.id;
                this.data.form_data = { title: '', status: Task_Model.STATUS_PENDING };
            }

            async on_load() {
                if (!this.data.is_edit) return;
                const task = await Task_Model.fetch(this.args.id);
                this.data.form_data = { id: task.id, title: task.title || '' };
            }
        }

        <Rsx_Form $data=this.data.form_data $controller="Tasks_Controller" $method="save">

    The template renders the REAL form, never a "loading..." placeholder branch:
    the spinner is what the user waits behind. A LOAD FAILURE is different - an
    error page branch is correct, because there is no form to wait for. The
    decorator and its 'uncached' mode for view pages: rsx:man spa, SPINNER
    UNTIL READY.

THE MODAL PATTERN

    A modal is chrome. The dialog opens immediately, the body component mounts
    inside it, and the primary button drives the hosted form's submit(). The
    common case needs NO JavaScript class on the body component at all:

        system/app/RSpade/resource/reference_app/app/frontend/settings/api_keys/
            add_api_key_modal_form.jqhtml     (template only - no JS class)

    An EDIT modal's body loads its record in on_load() and binds it as the
    form's $data, exactly as a page does, and the dialog is opened with
    spinner_until_ready: 'always' - the body is hidden behind the spinner until
    it is ready, and the primary button does nothing meanwhile:

        system/app/RSpade/resource/reference_app/app/frontend/settings/
            user_management/edit_user/edit_user_modal_form.js

        async on_load() {
            try { this.data.record = await Controller.get_user_for_edit({...}); }
            catch (e) { this.data.error_data = e; }
        }
        on_ready() {
            if (this.data.error_data) this.sid('form').render_error(this.data.error_data);
        }

        Modal.form({ title: 'Edit User', component: 'Edit_User_Modal_Form',
                     component_args: { user_id }, spinner_until_ready: 'always' });

    The Modal library and its options are template-application code: app skill
    modals.

LOADING

    The overlay is STATE (_loading), not a DOM operation. set_loading() flips it
    and syncs immediately; on_render() re-syncs, because renders rebuild the DOM
    and an imperatively-appended overlay would silently die on the next render.
    The DOM itself is the bookkeeping - there is no stale handle to go wrong.

    While loading, submit() REFUSES. The overlay blocks clicks; the guard blocks
    the Enter key and programmatic callers. This is not politeness: blank is a
    value, so a submit racing the fetch would VALIDLY clear every field the data
    had not reached yet.

    populate(data) is the procedure: overlay on, await, vals(), overlay off in a
    finally - so it cannot leak on success or on rejection. set_loading() is the
    primitive for an irregular load sequence. Both are for a form whose values
    arrive AFTER it is shown (a field filled on demand, a form re-seeded in
    place); a page or dialog that loads its record before anything is shown
    uses spinner_until_ready instead (THE PAGE PATTERN).

    CLEARING IS EXPLICIT, owned by whoever set it - never automatic. Both
    auto-clear candidates were examined and rejected: an on_ready() auto-clear is
    wrong BY DEFINITION (ready means "loaded and children ready", which is
    precisely when a loader must already be gone, and an externally-loaded form
    reaches ready before its data), and a data-set auto-clear misfires on partial
    programmatic vals() writes during load. The failure modes settle it: a
    forgotten clear is a permanently overlaid form - loud, fixed in minutes; a
    wrong auto-clear is a briefly-blank EDITABLE form - the silent kind of bug
    this contract exists to kill.

    THE VEIL COLOUR

        Core/Forms/Rsx_Form.scss reads ONE colour, --rsx-form-veil, and the
        application owns it: core has no palette and cannot know whether the
        surface behind the overlay is light or dark. Core declares it once on
        :root as a light-surface veil, so a form works before an app declares
        anything; the app's theme redeclares it, and a dark theme that does
        not declare the dark value flashes white.

            :root          { --rsx-form-veil: rgba(255, 255, 255, 0.65); }
            html.rsx-dark  { --rsx-form-veil: rgba(16, 21, 27, 0.7); }

        It is a VEIL, not a curtain - the translucency is what tells the user the
        form underneath is real and coming.

THE SPINNER REGISTRY

    Documented here because the form loading overlay is its principal consumer;
    the registry itself is general and available anywhere.

        Rsx.set_default_spinner('App_Spinner')   register, once, at app init
        Rsx.get_default_spinner()                the registered component name
        <Spinner />                              template entry point
        $(el).component(Rsx.get_default_spinner())    the JS equivalent

    The framework default is Rsx_Default_Spinner, a small rotating circle drawn
    at a fixed size (24px), centered in its host, in currentColor - so a fresh
    RSpade app has a working spinner before it has designed one. An application
    registers its own once, from a static on_app_modules_define() - the first
    boot phase; the first SPA page draws its spinners before app_init and
    app_ready, so a registration made there is not in force for that page:

        class App_Spinner extends Component {
            static on_app_modules_define() { Rsx.set_default_spinner('App_Spinner'); }
        }

    THE HOST OWNS THE BOX, and the box is a CENTERING STAGE - not a scale target.
    <Spinner /> defaults to 60x60; the form overlay hosts one at 150px; ordinary
    CSS sets any other context. The REGISTERED component decides whether it fills
    that box or draws at a fixed size centred inside it. There are no size
    arguments anywhere, and spinner markup is never hand-rolled.

UNSAVED CHANGES

    form.dirty() is true while any input holds a value the USER changed from
    what the form was given, and the form fires 'dirty' each time that answer
    flips:

        form.on('dirty', (form, dirty) => (dirty ? Rsx.set_navigation_guard() : Rsx.clear_navigation_guard()));

    CHANGED, NOT TOUCHED. Each input compares its current value with a BASELINE
    (Form_Input_Abstract.is_changed(); rsx:man form_input, CHANGED). A value
    typed and typed back is clean again, and the event flips back to false.

    The baseline is taken - and so none of these ever makes a form dirty - from:
        the $data seed, when the form is ready
        populate()
        every programmatic write: vals(object), form.input(name).val(v)
        a successful submit (the event flips to false before 'submitted')

    Inputs implement nothing for this. It relies on the input contract that
    already stands: once an input is ready, _get_value() reports the same value
    until the user or val() changes it.

    A form restoring PARKED values (KEYSTROKES WIN) is dirty from its own
    on_ready(). A host that wires 'dirty' in on_render() hears that flip; one
    wiring later reads form.dirty() once as it wires.

    A use beside the navigation guard: a Save button disabled until the form is
    dirty, enabled from the same event.

KEYSTROKES WIN

    The invariant: DATA FILLS FIELDS THE USER HAS NOT TOUCHED; THE USER'S
    KEYSTROKES ALWAYS WIN.

    Every user 'input' marks that name TOUCHED. Applying data - vals(object),
    populate() - skips touched names, so a revalidation re-render updates
    untouched fields and leaves in-progress edits alone. (Touched is not
    dirty: a field typed into and typed back is still touched, and still
    protected from data.)

    Across component RE-CREATION (an SPA action re-rendering on fresh data
    rebuilds the form component) touched values are PARKED on the live SPA
    action and restored to the successor instance after its seed - so they
    still win over $data, and the successor reads them as changes. Parking is
    engine-internal and silent, cleared on a successful submit, and dies with
    the action on navigation.

    Leaving the page altogether is a different seam: Rsx's navigation guard, a
    toggle the PAGE drives from the form's 'dirty' event, which has the browser
    ask before the user leaves. The form never sets or clears it. See rsx:man
    spa, THE NAVIGATION GUARD.

    The parking key is computed ONCE, in on_create(), from
    controller|method|record-id ('new' for a create form). It must not be
    re-derived later: the record id comes from the seed values, so an edit form
    that starts empty and is filled by populate() would park under one key and
    clear under another, leaving a stale slot to re-apply itself forever.

FORM SEEDS LIVE IN this.state, NEVER this.data

    this.data is the maybe-cached result of on_load(), frozen outside
    on_create()/on_load() (the framework throws), and possibly served stale on a
    repeat invocation. A form seed is neither a load result nor cacheable.

FIELD ALIGNMENT

    Keep the load endpoint (or the model fetch) and save() in the same
    controller. Adding a field touches four places, all findable by searching the
    field name: the load payload, save()'s parameter handling, the template's
    Form_Field, and on_create()'s defaults for add mode.

        // Load and save share one gate, declared once at class level - the pair
        // is one permission, so it should read as one declaration.
        #[Auth('can_manage_projects')]
        class Project_Controller extends Rsx_Controller_Abstract { ... }

REPEATER FIELDS

    A repeater is one input holding an array.

        // Array of ids
        form_data.client_ids = [1, 5, 12];
        $project->clients()->sync($params['client_ids'] ?? []);

        // Array of objects
        form_data.team_members = [{user_id: 1, role_id: 2}, ...];
        $project->team()->detach();
        foreach ($params['team_members'] ?? [] as $member) {
            $project->team()->attach($member['user_id'], ['role_id' => $member['role_id']]);
        }

    Serialization is SHALLOW, so the inputs a composite input renders inside
    itself belong to that composite, not to the form.

COMMON MISTAKES

    Naming the endpoint anywhere but the tag
        A modal that calls the controller itself, a button that posts, a
        wrapper's on_submit. There is one pipeline: form.submit().

    A client-side required check
        Deleted, always. Add the SERVER rule the asterisk promised instead.

    response_error(Ajax::ERROR_VALIDATION, 'a message')
        The second argument is metadata. Use response_form_error().

    "Keep the old value when blank" in save()
        Forbidden. Blank is a value; validate it or save it.

    A "loading..." placeholder branch instead of the form
        The overlay is the loading state; the form renders unconditionally
        underneath it.

    Writing before asking
        A question asked after the row is created is a question with no
        effect. Validate, ask, THEN write - the resubmission re-runs the
        endpoint from scratch.

    Re-implementing a question's trigger on the client
        Whether the address is already taken is server knowledge. A JavaScript
        copy of that query drifts from it, silently, exactly as a client-side
        required check masks a missing server rule.

    Treating a `false` answer as a cancel
        false is an ANSWER the endpoint acts on ("No"). Rsx_Form.CANCELLED is
        the cancel, and it never reaches the endpoint.

    Creating a record without saying where it is
        A create endpoint answering only {ok: true} replays that to a user who
        pressed Back and saved again - and the resubmit dialog has nothing to
        show. Answer redirect (or the new id).

    Asking two questions in one response
        One question per response. Return the FIRST unanswered one; the next
        round asks the next.

    Non-serializable form_data
        Extract a plain object; never assign a model instance.

    Field name mismatch
        $name and the form_data key are one string. The value silently stays
        empty when they differ.
