NAME
    session - RSX session management: the browser, who is signed in on it, and
    the record of what they did

SYNOPSIS
    if (Session::is_logged_in()) {
        $user = Session::get_user();          // site-scoped User_Model
        $site_id = Session::get_site_id();
    }

    RsxAuth::login($login_user);              // sign in on this browser
    Session::logout();                        // sign the staff account out

    Session::put_value('wizard.step', 3);     // a value on this browser
    $step = Session::get_value('wizard.step', 1);

    $log->audit_session_id = Session::get_audit_session_id();   // who did it, from where

DESCRIPTION
    Session is a static facade. Unlike Laravel's session() store or Auth guard,
    RSX has no key/value session bag and no "remember me": a browser holds one
    long-lived cookie, and the framework answers who is signed in on it through
    typed accessors. Portal_Session is the same facade for the client portal
    (rsx:man portal).

    This page has two parts.

    PART ONE - BASIC is the programmer contract: what to call, what it returns,
    and the handful of rules application code must respect. Most applications
    never need more.

    PART TWO - ADVANCED is the reference for application developers building
    session screens, background work or authentication flows, and for framework
    maintainers: the three records behind a session, token rotation, the sign-out
    reasons, lifetimes and cleanup, the machine sessions (commands, tasks, the
    test harness, API keys), audit sessions, tasks that run as their dispatcher,
    and which methods own what.

    Key differences from Laravel:
    - Laravel: Auth::login($user), session()->put('k', 'v'), Auth::user()
    - RSX: RsxAuth::login($login_user), Session::put_value('k', 'v'),
      Session::get_user()
    - Laravel starts a session on every request; RSX creates one only when
      something asks for it.

==============================================================================
PART ONE - BASIC
==============================================================================

THE SESSION IN ONE PARAGRAPH
    A SESSION is a browser. It is created the first time something asks for one
    and kept for as long as the browser keeps using it. Any number of accounts
    may sign in and out on it over its life; at any moment it carries at most
    one staff sign-in and one portal sign-in. Who is signed in, on which site,
    is read through the accessors below. A command and a task have no browser,
    so they have no session of their own (COMMANDS AND TASKS below).

get_session_id() AND has_session()
    Session::get_session_id(): ?int
        The id of this browser's session, CREATING it if the browser has none
        yet. Call it only when you want a session to exist - for a guest it
        mints a row and sets a cookie. It answers NULL where there is no
        browser: in a command, in a task, and in a test. In a task declared
        #[Run_As_Dispatcher] it answers the id of the browser whose request
        dispatched the task. On an external API request it answers the API
        key's own session.

    Session::has_session(): bool
        Whether a session exists. Creates nothing. Ask this when you only want
        to know.

        // WRONG for a guest - creates the session you were asking about
        if (Session::get_session_id() === null) { ... }

        // RIGHT
        if (!Session::has_session()) { return; }

    A table of yours that stores get_session_id() makes the column NULLABLE,
    and a screen that shows it tolerates null: a row written by a command or a
    task has no browser to name. A record of what somebody DID stores
    get_audit_session_id() instead (AUDIT SESSIONS in part two).

WHO IS SIGNED IN
    None of these create a session.

        Session::is_logged_in(): bool
        Session::get_login_user_id(): ?int      the identity (login_users.id),
                                                one across every site
        Session::get_login_user(): ?Login_User_Model
        Session::get_user_id(): ?int            the membership on the current
                                                site (users.id)
        Session::get_user(): ?User_Model
        Session::get_site_id(): int             0 when none
        Session::get_site(): ?Site_Model
        Session::is_impersonating(): bool
        Session::is_developer(): bool           login_users.is_developer
        Session::has_api_access(): bool         users.is_api_access_enabled

    On a portal request the portal identity is Portal_Session's to answer
    (get_portal_user_id(), get_user(), get_site_id()) - rsx:man portal.

SIGNING IN AND OUT
    RsxAuth::login($login_user)
        THE way into a session: signs the identity in on this browser
        (Session::set_login_user_id() underneath). A login function checks
        the password with RsxAuth::verify_credentials() first; whatever else
        the sign-in owes (a second factor, an account question of your own)
        runs between the two, with the visitor still signed out. rsx:man auth.

    Session::logout()
        Sign the staff account out of this browser. The browser keeps its
        session (and any portal sign-in on it); the staff realm's session
        values are cleared. Portal_Session::logout() is the portal twin.

    Session::set_site_id(int $site_id)
        Move the staff sign-in to another site (a site switch keeps the
        sign-in's clocks). With nobody signed in it declares the tenant for
        this request only and writes nothing.

    Session::set_temporary_site_id(int) / clear_temporary_site_id()
        Declare the tenant for the rest of this script, writing nothing
        anywhere - for a first-run request, a webhook that names its tenant,
        a script. Outranks everything but an API identity.

    Session::begin_impersonation($login_user_id) / stop_impersonation()
        "Sign in as this user" from the current staff sign-in, and back.
        IMPERSONATION in part two.

    Every sign-in and sign-out gives the browser a new session token and CSRF
    token. A page that signed in through an Ajax call is handed the new CSRF
    token in that call's envelope; nothing else needs doing.

SESSION VALUES
    Small values that belong to this browser rather than to a user or a record:
    a parked second-factor challenge, a half-finished wizard, a dismissed
    banner.

        Session::put_value(string $key, $value, ?string $expires_at = null,
                           ?string $realm = null): void
        Session::get_value(string $key, $default = null, ?string $realm = null)
        Session::forget_value(string $key, ?string $realm = null): void

    put_value() is a writer (it creates the session for a guest); the other two
    create nothing. Values are JSON-encoded, so types round-trip.

    EVERY VALUE HAS A REALM, and the realm decides when it is cleared:

        'staff'    cleared when this browser's staff sign-in ends
        'portal'   cleared when this browser's portal sign-in ends
        'guest'    the browser's own - kept through every sign-out

    Null (the default) is the realm of the request: 'portal' on a portal
    request, 'staff' otherwise. Read and forget in the realm you wrote.
    Portal_Session::put_value() / get_value() / forget_value() are these in the
    'portal' realm.

    THEY ARE NOT STORAGE. A value lasts no longer than the sign-in it belongs
    to, and the framework's own uses are second-factor challenges and small
    guest preferences. Real per-browser data belongs in a table of your own
    keyed on get_session_id() (with the foreign key in SYSTEM TABLES ARE
    PRIVATE), and anything a user should still have on another device belongs
    on the user (rsx:man user_preference_variables).

    put_value() THROWS where there is no browser - a command, a task, an API
    request - and every one of the three throws inside a #[Run_As_Dispatcher]
    task. get_value() answers the default where there is no browser.

HOW SESSIONS TIME OUT
    A SIGN-IN has two limits, per realm, in config('rsx.sessions'):

        staff.max_length_minutes    10080 (7 days)   from the sign-in
        staff.max_idle_minutes        480 (8 hours)  from the last page view
        portal.*                    the same two, for a portal sign-in
        0                           no limit

    A page view is a rendered page or an SPA navigation - never an Ajax or
    API call, so a tab that polls does not keep a sign-in alive. The limits
    are checked on every request: a page navigation past a limit signs out and
    redirects to the sign-in screen saying why; an Ajax call keeps working for
    ajax_grace_minutes (120) past the limit so an open form can still save,
    then answers the session_expired envelope. The hourly cleanup task signs
    out the sign-ins whose browser never comes back.

    A BROWSER unused for unused_session_days (30) is made inactive: whatever
    was signed in on it is signed out, and its next visit starts a new
    session. A guest browser nobody ever signed in on is deleted after
    guest_expiry_minutes (30 days).

    Set the limits in rsx/resource/config/rsx.php. Never implement "remember
    me" or a timeout of your own. The application's one job is the dialog the
    page shows when its sign-in is gone:

        // from a static on_app_modules_define()
        Rsx.set_session_expired_handler(function (info) { ... });

    Unregistered, the page reloads. Worked example:
    system/app/RSpade/resource/reference_app/lib/modal/modal.js
    (_on_session_expired).

LISTING AND ENDING SESSIONS
    Session::get_sessions_for_user($login_user_id = null) answers "where is this
    account signed in": one entry per browser and site the account has signed in
    on, signed in or recently signed out, most recently active first - never
    another account's sign-ins on the same browser. Each entry's `id` is a USER
    SESSION id, which is what terminate_session() (your own, on another
    browser), terminate_all_other_sessions() ("sign out everywhere else"),
    terminate_session_for_user() and terminate_all_sessions_for_user() (an
    administrator's, authorized by role - a refusal THROWS) take. A screen
    shows the entries active within a bounded window (the template: 3 months,
    rsx/lib/sessions/session_listing.php). Portal_Session has the same family
    for portal accounts. SESSION MANAGEMENT in part two has the whole contract.

CSRF
    Every internal transport (Ajax, uploads, @csrf forms) checks the CSRF token
    for you, portal included - rsx:man csrf. Session::get_csrf_token() and
    verify_csrf_token($token) exist for a hand-built form; get_csrf_token()
    answers null for a guest who has no session yet and creates nothing.

COMMANDS AND TASKS
    A command, a task and a test have no browser. Their session is VIRTUAL:
    no row is written, get_session_id() and get_audit_session_id() answer null,
    and session values throw. A command that acts as somebody declares it:

        Session::set_login_user_id($login_user_id);    // writes nothing
        Session::set_site_id($site_id);

    and every accessor then answers that identity. A task worker starts every
    run blank. A task that is a person's request moved off the request thread
    declares #[Run_As_Dispatcher] and runs as that person - TASKS RUN AS THEIR
    DISPATCHER in part two, and rsx:man tasks.

RSX VS LARAVEL
    Laravel                             RSX
    session()->put('k', 'v')            Session::put_value('k', 'v')
    Auth::login($user)                  RsxAuth::login($login_user)
    Auth::logout()                      Session::logout()
    Auth::user() / Auth::id()           Session::get_user() / get_user_id()
    Auth::check()                       Session::is_logged_in()
    a session on every request          a session only when asked for
    remember-me option                  one long-lived cookie; the sign-in
                                        limits end a sign-in
    @csrf + middleware                  the same, and every Ajax call too

    get_login_user_id() is the cross-site identity (login_users.id);
    get_user_id() is the membership on the current site (users.id).

TROUBLESHOOTING
    A guest gets a session row on every visit
        Something calls get_session_id(), get_session() or put_value() for
        every visitor. Ask has_session() instead, and never put either in a
        layout.

    "session values belong to a browser" thrown from a command or task
        Session values have no home there. Pass what the work needs as
        parameters, or keep it in a table of your own.

    "this task runs as the user who dispatched it" thrown from a task
        A #[Run_As_Dispatcher] task tried to change who it acts as, or to touch
        session values. Pass what it needs in its params.

    A column storing get_session_id() fails NOT NULL from a task
        Make it nullable; a task has no browser. If the row records an act,
        store get_audit_session_id() instead.

    Signed out unexpectedly
        The sign-in passed a limit (rsx.sessions.staff / .portal - 8 hours
        idle and 7 days by default), was ended from another browser or by an
        administrator, the membership or site was disabled, or another account
        signed in on the same browser. get_sessions_for_user() shows the
        reason on the signed-out entry.

    A value written before begin_challenge() is gone
        Starting a second-factor challenge signs the realm out first, which
        clears the realm's values. Write the value after begin_challenge(), or
        in the 'guest' realm.

    CSRF check fails after signing in
        The CSRF token changes at every sign-in and sign-out. A page holding a
        token from before the change must reload; an Ajax sign-in is handed
        the new one automatically.

PART TWO - ADVANCED
==============================================================================

THE THREE RECORDS
    A session is three kinds of row, each answering a different question. All
    three are framework tables (SYSTEM TABLES ARE PRIVATE).

    _sessions - THE BROWSER
        One row per browser (one cookie jar). It holds the session token (the
        cookie) and the CSRF token, the session values, its type, when it was
        last used, whether it is active, the hash of the token it last
        replaced, when anybody first signed in on it (first_signed_in_at; null
        = a guest that never signed in) and two POINTERS:

            staff_user_session_id    the staff sign-in current on it, or null
            portal_user_session_id   the portal sign-in current on it, or null

        Which pointer a request consults is decided by the REQUEST's experience
        (Rsx_Portal::is_portal_request()). Both set at once is normal: the same
        person, in the same browser, in the staff app and the client portal.
        get_session_id() is this row's id.

    _user_sessions - "WHERE YOU'RE SIGNED IN"
        One row per browser x realm x account x site x impersonator. Its
        identity never changes: a staff user session is a login identity (with
        its membership) on one site, optionally with an impersonator behind it;
        a portal one is a portal user on its site, optionally with a staff
        member viewing as them; an API one is an API key's owner (API KEY
        SESSIONS). The same account signing in again on the same browser and
        site REUSES its row. It records first_signed_in_at, signed_in_at (this
        sign-in), started_at (when it last became current), last_page_view_at,
        last_active_at, sign_in_count, and signed_out_at + sign_out_reason_id
        once it ends. The sign-in limits are measured on it.
        get_user_session_id() is the current one's id, and get_sessions_for_user()
        lists them.

    _audit_sessions - THE ACTING CONTEXT
        One row per user session x site x client address x user agent (a
        guest's act: per browser). Immutable apart from last_seen_at, minted
        when something asks for it, never deleted. What a record of an act
        points at (AUDIT SESSIONS).

    Nothing about a past sign-in is deleted: a browser that has ever had a
    sign-in is made inactive when it goes unused, never removed, because its
    user sessions are the history of where an account signed in.

ONE BROWSER, THREE SIGN-INS
    The model, walked through. One browser; accounts A and B; staff realm.

    1. A guest visits. Nothing asks for a session: no row. The first thing that
       needs one for the visitor - put_value(), a flash alert, get_session_id(),
       a sign-in - mints the _sessions row (TYPE_WEB, both pointers null) and
       sets the cookie.

    2. A signs in. The user session (browser, A, site 1) is created,
       sign_in_count 1; the staff pointer names it; the browser's tokens
       rotate; first_signed_in_at is stamped. get_sessions_for_user(A) lists
       one entry, signed in.

    3. A signs out. The user session is stamped signed_out_at, reason
       SIGN_OUT_SIGNED_OUT; the pointer is cleared; the staff values are
       cleared; the tokens rotate. The browser is a guest again - same row.

    4. B signs in. A different tuple, so a NEW user session (browser, B, site
       1). get_sessions_for_user(A) still lists only A's entry (signed out);
       get_sessions_for_user(B) lists only B's.

    5. B signs out, then A signs in again. A's ORIGINAL user session is reused:
       sign_in_count 2, signed_in_at and the clocks restart, the sign-out is
       cleared. Still one _sessions row; two user sessions; the token differed
       at every step.

    Had A signed in at step 4 without B signing out first, B's user session
    would have been signed out with SIGN_OUT_REPLACED and the staff values
    cleared - another account taking a browser over ends what was there.

    A site switch moves the pointer to the user session for the new site (one
    is created or reused) and signs the old one out with SIGN_OUT_SITE_SWITCHED,
    carrying the sign-in's clocks: switching site never restarts the session
    lifetime and never rotates the token.

TOKEN ROTATION
    Every sign-in and every sign-out on the browser making the request gives
    its row a NEW session token and CSRF token, in place, and the response
    carries the new cookie. The token the browser presented may be held by
    somebody else too - a copied cookie, or one planted before the visitor
    signed in - and after a rotation it matches nothing: the row, its values,
    its trust and its other realm's sign-in carry on under a token nobody else
    has seen. The address and user agent on the row are refreshed with it.

    A rotation is skipped when this request minted the row or has already
    rotated it (that token has not left the server), and never happens on an
    API request or in a virtual session (no cookie).

    THE REPLACED TOKEN. The row keeps the hash of the token it last replaced
    (previous_token_hash). A request carrying that token was in flight when the
    rotation happened:

        - an Ajax call or a sub-resource (an image, a download, an iframe) is
          REFUSED - the Ajax call with the session_expired envelope
          (metadata.cause 'rotated'), a sub-resource with 401 - and no session
          cookie is sent with the answer, so it can never overwrite the cookie
          the rotation just sent;
        - a PAGE NAVIGATION carrying it is an ordinary guest, so a browser that
          missed its new cookie recovers on its next page load.

    Any older token matches nothing and is an ordinary guest.

    WHAT DOES NOT ROTATE. A site switch, an impersonation starting or stopping,
    and View as Client - nobody re-authenticated. Ending a sign-in on ANOTHER
    browser (an administrator, the session cap, "sign out everywhere else", the
    cleanup sweeps) stamps the user session and moves that browser's pointer,
    and leaves its token alone: the row now grants nothing it would not grant a
    guest, and its next sign-in rotates it.

SIGN-OUT REASONS
    A user session that ends is stamped signed_out_at and one reason
    (Session::SIGN_OUT_*). get_sessions_for_user() answers the label;
    Session::sign_out_reason_label($id) answers it for any id.

        SIGN_OUT_SIGNED_OUT            Signed out             logout()
        SIGN_OUT_TIMED_OUT_LENGTH      Sign-in expired        max_length_minutes
        SIGN_OUT_TIMED_OUT_IDLE        Signed out after       max_idle_minutes
                                       inactivity
        SIGN_OUT_ENDED_BY_USER         Ended from another     terminate_session(),
                                       device                 terminate_all_other_sessions()
        SIGN_OUT_ENDED_BY_ADMIN        Ended by an            the admin and developer
                                       administrator          terminate functions
        SIGN_OUT_ENDED_BY_SYSTEM       Ended by the system    _deactivate_sessions_for_user()
                                                              (rsx:users:password:set)
        SIGN_OUT_SESSION_CAP           Too many sessions      max_web_sessions_per_user
        SIGN_OUT_REPLACED              Another account        another account signed in
                                       signed in              on the browser
        SIGN_OUT_SITE_SWITCHED         Switched site          set_site_id()
        SIGN_OUT_MEMBERSHIP_DISABLED   Membership disabled    enforce_enabled_membership()
        SIGN_OUT_IMPERSONATION_ENDED   Impersonation ended    stop_impersonation(), the
                                                              impersonation age limit
        SIGN_OUT_SESSION_RESET         Session reset          reset()
        SIGN_OUT_API_KEY_REVOKED       API key revoked        the key was revoked
        SIGN_OUT_API_KEY_EXPIRED       API key expired        the key passed expires_at
        SIGN_OUT_BROWSER_UNUSED        Browser unused for     unused_session_days
                                       N days

    Every sign-out runs through one path (Session::_sign_out_user_sessions()),
    so the rules hold everywhere: a staff sign-in that ends takes the
    impersonations riding it on the same browser with it; every browser
    pointer naming an ended user session moves (back to the impersonator's own
    sign-in when an impersonation ended, otherwise to null); a realm left
    signed out on a browser - or taken over by another account - loses that
    realm's session values; and each browser touched gets a realtime refresh
    push for that realm (except the cap and the unused-browser retirement).

SESSION VALUES, IN FULL
    _session_values, one row per (browser, realm, key), UNIQUE on the three, ON
    DELETE CASCADE from _sessions. put_value() is an upsert.

    THE REALM AT SIGN-IN. Null resolves to the request's experience whether or
    not anybody is signed in yet, so a value a signed-out visitor parks before
    signing in - across a second-factor challenge - is still there after the
    sign-in, and goes when that sign-in ends. A site switch and an impersonation
    starting or ending keep the realm's values (the same person); another
    account signing in over the realm clears them (SIGN_OUT_REPLACED).

    THE ORDER WITH A CHALLENGE. Rsx_Two_Factor::begin_challenge() signs the
    realm out FIRST and parks its pending identity after - so a value written
    before begin_challenge() is cleared by that sign-out whenever somebody was
    still signed in. Write a value that must ride the challenge after
    begin_challenge() (the template's login controller parks its invite code
    that way), or in the 'guest' realm.

    EXPIRY IS OPTIONAL. $expires_at null means "as long as the realm keeps it".
    An expired value reads as absent the instant it expires (the read filters
    on it); Session_Values_Cleanup_Service (hourly) only reclaims the space.

    WHERE THEY THROW. put_value() throws in a virtual session and on an API
    request ("session values belong to a browser"); all three throw inside a
    #[Run_As_Dispatcher] task, whose browser is not the request the run stands
    for. A test whose subject is a value acts as a browser
    (Rsx_Test_Abstract::__as_browser()).

    reset() clears every value of every realm.

LIFETIMES, CLEANUP AND DEACTIVATION
    config('rsx.sessions'), every key app-overridable in
    rsx/resource/config/rsx.php:

        staff.max_length_minutes     10080   sign-in limit, from the sign-in
        staff.max_idle_minutes         480   idle limit, from the last page view
        portal.max_length_minutes    10080
        portal.max_idle_minutes        480
        ajax_grace_minutes             120   how long past a limit a non-page
                                             request still works
        unused_session_days             30   a browser unused this long is made
                                             inactive; also how long a
                                             signed-out user session stays in
                                             get_sessions_for_user()
        guest_expiry_minutes         43200   a never-signed-in browser unused
                                             this long is deleted
        impersonation_max_days           7   an impersonation older than this
                                             is ended
        max_web_sessions_per_user       25   signed-in browsers per account,
                                             per realm
        login_history_retention_days   365   rows kept in the login histories

    A limit of 0 turns that limit off.

    AT REQUEST TIME. Session::enforce_timeouts($strict) and
    Portal_Session::enforce_timeouts($strict), called by the dispatcher (a
    page: strict) and the Ajax entry point (not strict: the grace applies),
    ahead of the #[Auth] gates. A sign-in past a limit is signed out
    (SIGN_OUT_TIMED_OUT_LENGTH / _IDLE - the earlier expiry wins; a staff
    impersonation takes the impersonator's own sign-in with it, since it ran
    on the impersonator's clocks) and the tokens rotate; the request continues
    signed out and its channel answers - the sign-in redirect with a flash for
    a page ("Your session has expired. Please sign in again." / "You were
    signed out after a period of inactivity. Please sign in again."), the
    session_expired envelope for an Ajax call. An SPA navigation is judged as
    a page. The two realms are judged independently, each on its own requests.

    PAGE VIEWS. Session::touch_page_view() / Portal_Session::touch_page_view(),
    called by a bundle render and by the SPA's navigation report
    (Rsx_Session_Controller::page_view), stamp the current user session's
    last_page_view_at at most once a minute, with the account's last_seen
    (not while impersonating). An application whose page renders no bundle may
    call them.

    LOOKUP. init() loads the row the cookie names only while it is ACTIVE. A
    row whose last_active is older than unused_session_days is retired there
    and treated as absent: nothing is minted until something asks for a
    session again. last_active (the row) and last_active_at (its current user
    sessions) are written at most once a minute.

    THE CLEANUP TASKS (Session_Cleanup_Service; each needs the rsx:task:process
    cron tick - rsx:man tasks):

        cleanup_sessions              hourly. DELETES guest browsers -
                                      first_signed_in_at null, TYPE_WEB - unused
                                      for guest_expiry_minutes, with their
                                      values; signs out the CURRENT sign-ins
                                      past a limit PLUS ajax_grace_minutes
                                      (a request would not end them sooner, and
                                      an open form may still save), under the
                                      reason a request would record; signs out
                                      the user sessions of expired API keys.
        deactivate_unused_sessions    daily maintenance. Signs out everything
                                      still signed in on a browser unused for
                                      unused_session_days
                                      (SIGN_OUT_BROWSER_UNUSED) and makes it
                                      inactive. Never an API key's row.
        end_stale_impersonations      daily maintenance. impersonation_max_days.
        cleanup_trusted_devices       daily maintenance. Expired 2FA trust.
        cleanup_session_links         hourly. Expired View as Client handshake
                                      codes.
        cleanup_login_history         hourly. login_history_retention_days.
        cleanup_user_agents           weekly maintenance. User-agent strings
                                      nothing names.

    A sign-in suspended behind an impersonation is not judged by the sweep: its
    clocks are not running (the impersonation's are), and it is judged when the
    browser returns to it. Every sweep is chunked and #[Exclusive]; nothing but
    a guest browser is ever deleted.

SESSION TYPES
    _sessions.type_id is stamped by the writer that creates the row and never
    inferred afterwards (a user-agent string is attacker-influenced):

        Session::TYPE_WEB          a browser
        Session::TYPE_PLAYWRIGHT   the rsx:debug / Playwright harness
                                   (HARNESS SESSIONS)
        Session::TYPE_API          an API key's own row (API KEY SESSIONS)
        Session::TYPE_CLI          names no row: a command or a task runs a
                                   virtual session. Kept in the enum because
                                   older audit sessions carry it.

VIRTUAL SESSIONS (COMMANDS, TASKS, TESTS)
    Every CLI process - an artisan command, a task worker, the test runner -
    runs a VIRTUAL session from boot to exit: no _sessions row, no user
    session, no audit session, no cookie. Detected from php_sapi_name().

        get_session_id(), get_user_session_id()   null
        get_audit_session_id()                    null
        has_session()                             true once an identity or a
                                                  site is declared
        set_login_user_id(), set_site_id(),
        impersonate(), begin_impersonation()      write in-memory statics only;
                                                  never a row, never last_login
        put_value()                               throws
        get_client_ip()                           null

    Session::impersonate($site_id, $login_user_id, $user_id) and
    reset_impersonation() are the CLI/test pair that declare a whole context in
    one call; Rsx_Test_Abstract::__acting_as_user() uses them. They are
    unrelated to web impersonation.

    THE TASK RUNNER'S BOUNDARY. A worker runs unrelated tasks back to back, so
    Task_Runner::execute() starts every run it executes outside its caller's
    process (a worker, rsx:task:process --once) with Session::_begin_virtual()
    - a blank context, or the frozen one of a #[Run_As_Dispatcher] task - and
    ends it with Session::_end_virtual(), which blanks the identity, site,
    impersonation, declared tenant, portal identity, declared audit session,
    request realm, and every resolution keyed on them (the timezone cache, the
    dark-mode memo, the second factors passed). Nothing one run was reaches the
    next. Task::internal() runs in its caller's context and SAVES and RESTORES
    it around the call (Session::_snapshot_context() / _restore_context()), so
    the caller gets back exactly what it had.

    TESTS ACTING AS A BROWSER. A test whose subject belongs to a browser
    (session values, two-factor trust, a challenge between two calls) calls
    Rsx_Test_Abstract::__as_browser(), which inserts a browser row and makes
    get_session_id(), has_session(), the session values and get_session()
    answer it; protected static $acts_as_browser = true does it before every
    test method. Identity stays the virtual session's. rsx:man testing.

HARNESS SESSIONS (rsx:debug / Playwright)
    rsx:debug signs in through signed dev-auth headers on its first request
    (Dispatcher::__handle_dev_auth()). The harness keeps ONE TYPE_PLAYWRIGHT
    row per staff account and site (per portal user and site), shared by every
    run:

        - the browser's cookie already names a harness row signed in as that
          identity (the run's own later requests): kept;
        - otherwise an active harness row signed in as that identity is
          REUSED - the cookie is pointed at it - provided its sign-in is within
          the realm's ordinary limits and the row within unused_session_days;
          a candidate past a limit is signed out with that reason and passed
          over;
        - otherwise a new harness row is minted.

    A harness row is never listed with an account's sessions, never counted by
    the session cap, never deleted by the guest cleanup, and its traffic
    records no audit session. Nothing purges harness rows when a run ends: the
    next run reuses them.

API KEY SESSIONS
    A request authenticated by `Authorization: Bearer rsx_...`
    (Rsx_Api_Bearer, rsx:man external_api) runs as the key's owner through
    Session::_set_api_identity(), which installs an immutable identity for the
    request - no cookie read, no Set-Cookie, and every identity setter throws.

    ONE SESSION ROW PER KEY. The key's first call mints a _sessions row of
    TYPE_API (api_key_id, unique) and a user session for the owner in the API
    realm (REALM_API); every later call reuses both, stamping them at most once
    a minute with the caller's address and user agent. So:

        - get_session_id() answers the key's row; get_user_session_id() its
          user session; has_session() answers false (it is not a browser);
        - the owner's get_sessions_for_user() lists the key's use as one entry
          (is_api); the terminate functions do not end it - the key is the
          credential;
        - each new caller address or user agent is a new audit session;
        - revoking the key signs its user session out (SIGN_OUT_API_KEY_REVOKED);
          a key past expires_at is refused and its user session signed out
          (SIGN_OUT_API_KEY_EXPIRED), by the refused call or the hourly sweep;
        - deleting the key deletes its row and user session (ON DELETE CASCADE).

    An identity installed with no key (Api_Tester_Key asking which endpoints a
    user's gates admit) writes nothing and answers get_session_id() null.

AUDIT SESSIONS
    A record of something somebody DID - an activity log row, an export record,
    a revision - has to say who did it and from where, for as long as the record
    exists. A _sessions row cannot: it is the browser, whoever is signed in on
    it changes, and a guest's is deleted. Store an audit session:

        $log->audit_session_id = Session::get_audit_session_id();

    TWO IDS, TWO JOBS - never one for the other:

        get_session_id()         the browser. For state that BELONGS TO THE
                                 BROWSER and should die with it.
        get_audit_session_id()   a permanent row describing the acting context.
                                 For the historical record of an act.

    Session::get_audit_session_id(): ?int
        The id of the _audit_sessions row for the act happening now, minted on
        first use. The key:

            the acting user session (a guest: the browser row, or nothing for a
            visitor with no row) x the site acted on x client address x user
            agent

        The user session is the request realm's (staff, or portal on a portal
        request); an API call's is the key owner's REALM_API one. The site is
        part of the key because a declared tenant (set_temporary_site_id()) can
        differ from the user session's. When any of them changes - a sign-in, a
        site switch, an impersonation, a new address - the next act belongs to a
        new row. The row also DESCRIBES the context: the acting realm's identity,
        site and impersonator, the address and user agent, the browser
        (session_id), the user session and the session type.

        NULL in a command, a task and the rsx:debug harness - a context with no
        person in it has nothing to attribute - EXCEPT a #[Run_As_Dispatcher]
        task, whose runner declares the dispatching request's audit session, so
        the run's writes count under the requester's own context.

        One resolution per context per process; last_seen_at advances at most
        once a minute. A failure to record is loud. Two requests minting the
        same context at once get the same id (one statement on a unique key).

    _audit_sessions IS NEVER DELETED. session_id and user_session_id on it are
    CORRELATION NUMBERS, not foreign keys: "every act from this browser" and
    "every act of this sign-in" are equality tests among audit rows that keep
    working whatever happens to the sessions. The session token is never
    stored.

    Reading back:

        Session::get_audit_session(int $id): ?array
            {id, site_id, login_user_id, portal_user_id, portal_site_id,
             impersonator_login_user_id, impersonator_user_id, ip_address,
             user_agent, session_id, user_session_id, session_type_id,
             first_seen_at, last_seen_at} - null for no such row.

        Audit_Session::list_page_for_user_session([
            'user_session_id' => $id,       // required: a get_sessions_for_user() id
            'filter' => '203.0.113',        // IP address or user agent
            'sort' => 'last_seen_at',       // last_seen_at | first_seen_at | ip_address
            'order' => 'desc',
            'offset' => 0,
            'limit' => 25,                  // 1..200
        ])
            One page of the audit sessions of ONE user session - the addresses
            and user agents that sign-in acted from - for a "where was this
            sign-in used" detail screen. {rows, total, offset, limit}; each row
            is get_audit_session()'s shape plus device_summary. Ungated: the
            calling endpoint first decides whether the caller may see that user
            session (normally: the id is one of the entries it lists). An audit
            session is minted when something asks for the acting context - a
            revision-recorded write, a dispatched task - so browsing alone adds
            nothing here.

        Audit_Session::join($query, 'table.audit_session_id')
        Audit_Session::column(string $name)
            Join every published field onto a query of your own as audit_<name>
            (a LEFT join), and spell a condition or ordering on one, without
            naming a system table:

                $query = Action_Log_Model::query();
                Audit_Session::join($query, 'action_logs.audit_session_id');
                $query->where(Audit_Session::column('ip_address'), 'like', $like);

    The framework stamps every recorded unit of work itself
    (_transactions.audit_session_id, nullable - rsx:man revisions). Skill
    rspade:audit-session.

    User agents and addresses. Each distinct user-agent string is stored once
    in _user_agents and each client address once in _ip_addresses; _sessions,
    _audit_sessions and the login histories hold their ids. The strings come
    back wherever the framework answers one (`user_agent` / `ip_address` in the
    session listings, the login histories and get_audit_session();
    `$session->user_agent` / `$session->ip_address` on a Session row). A
    user-agent string nothing names any more is deleted weekly
    (cleanup_user_agents) once it has gone a day unseen; an address row is
    never deleted (rsx:man ip_addresses).

TASKS RUN AS THEIR DISPATCHER
    A task declared #[Run_As_Dispatcher] is the asynchronous stand-in for a
    user's Ajax endpoint: moving the request off the request thread changes
    WHEN it runs, never WHO did it. Step by step:

    1. DISPATCH. Task::dispatch() (and every other insert, through
       Task_Runner::insert_row()) stamps the run with the requester's user
       session (_tasks.user_session_id = get_user_session_id() - a staff or
       portal sign-in, or an API key's) and audit session, and the claim tier
       PRIORITY_RUN_AS_DISPATCHER. Dispatched where there is no sign-in - a
       guest, a command, a plain task - it is refused with an exception.

    2. CLAIM. Workers claim dispatcher runs first, then other on-demand runs,
       then scheduled ones, oldest first within a tier, and tick no schedule
       while an on-demand run is due (rsx:man tasks).

    3. RUN. Task_Dispatcher_Context::begin() loads the user session and starts
       a FROZEN, BOUND virtual session from it:

           identity, site, realm    the user session's - a staff sign-in's login
                                    identity, membership and site; a portal
                                    sign-in's portal user and site (portal
                                    realm); an API key's owner - even if that
                                    browser has signed out since or signed into
                                    another account
           impersonation            the impersonator, when the user session had
                                    one
           get_session_id()         the dispatching browser's row
           get_user_session_id()    the user session
           get_audit_session_id()   the dispatch's audit session, so the run's
                                    revisions and logs count under it
           timezone                 the dispatcher's (Rsx_Time's cache is
                                    cleared on the way in and out)

       FROZEN: set_login_user_id(), logout(), set_site_id(),
       set_temporary_site_id(), begin/stop_impersonation(), impersonate(),
       reset(), the portal setters, and all three session-value calls THROW
       ("this task runs as the user who dispatched it ...").

    4. REFUSAL. Before anything executes, the dispatcher must still be allowed
       to act: the login identity exists and, on a site, the membership is
       active (users.is_enabled and sites.is_enabled); a portal user exists,
       may sign in and its site is active; the user session still exists.
       Otherwise the run FAILS with the reason as its error and the method
       never runs. Account statuses your application defines are yours to
       check in the task.

    5. RESET. However the run ended, Session::_end_virtual() blanks the process
       (VIRTUAL SESSIONS).

    A #[Run_As_Dispatcher] task cannot be started by hand: rsx:task:run (and a
    #[Command] alias, which the build already refuses - TASK-RUN-AS-01) exits 1
    with a message saying it must be dispatched from a request; #[Schedule] on
    it is a build FATAL too. Inline in a request, Task::internal() runs it in
    the request's own context. ANY TASK THAT IS THE ASYNCHRONOUS STAND-IN FOR A
    USER'S AJAX ENDPOINT MUST CARRY IT: without it the run acts as nobody, its
    writes are attributed to nobody and its site scope is empty. rsx:man tasks,
    RUNNING AS THE DISPATCHER.

REALTIME SESSION REFRESH AND THE SESSION HASH
    Realtime connections are stamped with the browser's _sessions id and the
    realm of the page that opened them. A sign-in, a sign-out, a site switch,
    an impersonation starting or ending, and every sign-out of another
    browser's user session push a targeted "reload" to the live connections of
    that browser in that realm (Realtime::push_session_refresh($realm,
    $session_id)), so an open tab never sits on a page for an identity that is
    gone. No-op when realtime is off. rsx:man realtime, SESSION REFRESH PUSH.

    window.rsxapp.session_hash is an HMAC of the session token the page was
    rendered with (Session::_client_session_hash() - the token itself never
    reaches the page). Rsx.validate_session(), run after every SPA navigation,
    compares it with the server's current one and reloads on a difference -
    how a page notices a rotation that happened in another tab without
    realtime.

TRUSTED BROWSERS (TWO-FACTOR)
    A browser that passed a second factor may be trusted for a window
    (rsx.two_factor.trusted_device_days) so the next sign-in on it is excused.
    The trust is keyed on the BROWSER row (_two_factor_trusted_devices.session_id),
    so it survives every sign-in and sign-out on that browser and is lost with
    its cookie, or when the browser goes unused long enough to be made
    inactive. A password change, removing a factor, and
    terminate_all_other_sessions() forget it. rsx:man two_factor.

VIEW AS CLIENT ACROSS HOSTS
    Staff "View as Client" (Portal_Session::begin_impersonation_from_staff())
    is a PORTAL user session on the staff member's own browser - the portal
    user, its site, and the staff users.id as impersonator - that the browser's
    portal pointer names while it lasts; the browser's own portal sign-in, if
    any, stays signed in behind it. Nothing rotates.

    A portal on its OWN host (PORTAL_URL) is reached through a separate cookie
    jar, so the browser holds a session cookie per host, each ordinarily naming
    its own row. View as Client joins them: the linked-session handshake
    (Session_Link; one-time codes in _session_links, URLs signed by
    Rsx_Signed_Url) proves both hosts are the same browser, applies the
    impersonation to the staff host's row, and points the portal host's cookie
    at that SAME row (Session::_clone_session_to_this_host(), which makes the
    portal host's previous row inactive). Ending the view signs that user
    session out (SIGN_OUT_IMPERSONATION_ENDED) and the portal pointer falls
    back. The session token never appears in a URL. rsx:man portal.

CONCURRENT SESSION CAP
    rsx.sessions.max_web_sessions_per_user (default 25; 0 or null = off) is the
    most browsers one account may be signed in on at once, per realm. At every
    sign-in - the only moment the count grows - the account's signed-in user
    sessions beyond that number, least recently active first, are signed out
    (SIGN_OUT_SESSION_CAP). Only TYPE_WEB browsers count and are evicted (a
    harness run never signs a developer out), impersonations of the account
    are not counted, and only that realm's sign-in on an evicted browser ends.
    Capacity management, not termination: no event, no refresh push - the
    evicted browser learns at its next request.

SESSION MANAGEMENT
    Listing - where an account is signed in:

        Session::get_sessions_for_user(?int $login_user_id = null,
                                       ?int $site_id = null,
                                       bool $include_impersonations = false): array
        Portal_Session::get_sessions_for_user(?int $portal_user_id = null,
                                              bool $include_impersonations = false): array

        The account's USER SESSIONS, most recently active first: every one
        still signed in, plus those signed out within unused_session_days
        (every signed-out one when that is 0), so a screen can show "signed out
        2 days ago". Never another account's, never a harness browser's. The
        staff listing includes each API key of the account that has been used,
        as one entry (is_api). $site_id narrows to one site - a tenant's view
        of an identity that may belong to several. The whole set is returned:
        a user cannot end a session they were not shown.

        An IMPERSONATION is somebody else acting as the user from somebody
        else's browser, and is left out unless $include_impersonations asks for
        it - an administrator's view, where is_impersonation labels it.

        Each entry: id (the user session - what the terminate functions take),
        session_id (the browser), site_id, user_id, ip_address, user_agent,
        user_agent_parsed, device_summary, location, last_active, created_at,
        signed_in_at, first_seen, signed_out_at, sign_out_reason (a label or
        null), is_signed_in, is_current, is_impersonation, impersonator_id,
        impersonation_started_at, sign_in_count, type_id (the browser's),
        is_api. The address and user agent are the browser's, refreshed at
        every sign-in on it.

        RECOMMENDED: a screen lists the entries active within a bounded window
        rather than everything answered - the template keeps 3 months and
        decides which rows offer "Sign out" in one place
        (system/app/RSpade/resource/reference_app/lib/sessions/session_listing.php).
        A detail screen per entry pages its audit sessions
        (Audit_Session::list_page_for_user_session()).

        Session::get_current_session_info(): ?array
            The current staff sign-in, shaped like an entry; null when none.

        Session::get_user_session_id(): ?int
            The user session this request is signed in through (staff, or the
            portal one on a portal request; an API key's on an API request).
            Null when signed out and in a virtual session (a
            #[Run_As_Dispatcher] task answers the one it is bound to). What a
            dispatched task binds to; a screen marking "this device" compares
            against an entry's is_current instead.

    Ending - pick by WHOSE sign-ins and WHO is asking. Every function takes
    USER SESSION ids and ends only signed-in user sessions; the other realm's
    sign-in on the same browser is never touched.

        // SELF, one sign-in on another browser. Fail-closed (the owning
        // account is part of the lookup); anything on this browser is refused
        // - that is logout()'s job.
        $ok = Session::terminate_session($user_session_id);

        // SELF, everything else - "sign out everywhere else". Also forgets
        // every other browser's two-factor trust.
        $count = Session::terminate_all_other_sessions();

        // ANOTHER USER, one sign-in - the ADMIN primitive. Authorized first.
        $ok = Session::terminate_session_for_user($login_user_id, $user_session_id);

        // ANOTHER USER, everything, optionally sparing one user session.
        $count = Session::terminate_all_sessions_for_user($login_user_id, $except_id);

        // ANY IDENTITY - the DEVELOPER primitive for an install-wide operator
        // screen (/_sys). Authorized by Session::is_developer() alone; null
        // ends every sign-in but those on the caller's own browser.
        $count = Session::developer_terminate_sessions($login_user_id, $user_session_id);

        // FRAMEWORK-INTERNAL, NO AUTHORIZATION - a caller with no acting user
        // (CLI maintenance), or an app flow that has already authorized and is
        // executing the consequence. Reason SIGN_OUT_ENDED_BY_SYSTEM.
        $count = Session::_deactivate_sessions_for_user($login_user_id);

        Portal twins: Portal_Session::terminate_session($user_session_id),
        terminate_all_other_sessions(), terminate_all_sessions_for_user(
        $portal_user_id, $except_user_session_id) - the last unguarded, for an
        admin action or a password change the caller has authorized.

    The authorization rule (the cross-user staff functions). Two ways to be
    authorized, and only two:

        1. THE TARGET IS THE ACTOR. Managing your own sign-ins needs no role.
        2. THE ACTOR'S ROLE MAY ADMINISTER THE TARGET'S -
           Permission::can_admin_role() against the target's users.role_id on
           the ACTING site. That list is equal-or-lower (rsx:man acls), so a
           superior is refused by construction and a peer is permitted.

        A target with no users row on the acting site is refused; no acting
        identity is refused. The rule is framework vocabulary only (core never
        names an #[Auth_Check]); the SURFACE gate stays yours.

    REFUSAL THROWS; ABSENCE RETURNS FALSE:

            refused                      AjaxUnauthorizedException (403 on Ajax)
            no such signed-in user       false / 0 - wrong id, wrong owner,
            session                      already signed out
            on the actor's own browser   false - an admin screen never signs
                                         the operator out of the browser they
                                         are working in

        The shape exists because a single overloaded false once hid an admin
        "terminate" button that never worked: an exception surfaces a wiring
        bug the day it is written.

    SINGLE-TENANT ASSUMPTION. A sign-in belongs to a login identity, which is
    cross-site; a role lives on a per-site users row. The guard resolves the
    target's role on the actor's own site and ends sign-ins on any site. On a
    one-site deployment that is exactly right; on a genuinely multi-tenant one
    the target may hold a higher role elsewhere. The multi-tenant model is
    BACKLOG B-92 and is deliberately not approximated here.

    What every ended user session triggers: the realtime refresh push to its
    browser (SIGN-OUT REASONS) and, for a staff user session ended by a
    terminate function, the audit event once per user session:

        Rsx::trigger_action('session.terminated', [
            'actor_login_user_id'  => ?int,   // null on the internal path
            'target_login_user_id' => int,
            'user_session_id'      => int,
            'session_id'           => int,    // the browser
            'scope'                => 'self' | 'admin' | 'internal',
        ]);

        The event stream is NOT a record of every sign-out - the cap, the
        lifetimes and the sweeps fire none. The user sessions themselves are
        that record (signed_out_at + reason).

USER MANAGEMENT PAGES
    THE DECISION RULE, FIRST: your TENANCY MODEL determines what a user
    management page is permitted to do.

    SINGLE-TENANT (one site - the firm administers real accounts):
        The page legitimately carries the user's sessions (get_sessions_for_user()
        for this site) with per-session and all-sessions sign-out
        (terminate_session_for_user, terminate_all_sessions_for_user), each
        entry's detail of audit sessions, login history and the windowed
        failed-attempt count, role editing, and enable/disable
        (users.is_enabled). The framework refuses a superior target underneath
        your own #[Auth] gate. Worked example:
        system/app/RSpade/resource/reference_app/app/frontend/settings/user_management/

    MULTI-TENANT SaaS (accounts are self-managed):
        An admin's only control is WHO MAY JOIN THEIR SITE - invitation and
        membership revocation. Session termination, password mechanics, email
        changes and account deletion belong to the ACCOUNT HOLDER, whose
        identity spans tenants your admin cannot see. Show membership, role
        within this site and last activity; nothing that reaches the identity
        itself (and see SINGLE-TENANT ASSUMPTION, B-92).

CONTROLLER AUTHENTICATION
    Authorization is DECLARATIVE, and pre_dispatch() is not where it happens.
    Every dispatchable surface carries an #[Auth(...)] gate list, evaluated by
    the framework before any application code; a surface with no gate fails the
    manifest build. Full treatment: rsx:man auth_gates.

        // Class-level gates apply to every surface method in the class;
        // a method-level #[Auth] is ADDITIVE (gates only narrow).
        #[Auth('is_logged_in')]
        class Admin_Controller extends Rsx_Controller_Abstract
        {
            #[Route('/admin/users')]
            #[Auth('can_manage_users')]
            public static function users(Request $request, array $params = [])
            {
                // Guaranteed: logged in AND can_manage_users
            }
        }

    The check names are marked (#[Auth_Check]) methods on the app's Permission
    class, so gate logic reads Session state through the same accessors
    documented on this page:

        #[Auth_Check]
        public static function can_manage_users(): bool
        {
            return static::has_permission(User_Model::PERM_MANAGE_SITE_USERS);
        }

    pre_dispatch() (controller and Main_Abstract alike) remains for NON-AUTH
    middleware concerns - tenant setup, interstitials, redirects. Putting an
    authorization check there is now a defect: it duplicates the declaration
    the gates already carry, and link visibility (Permission::can_access())
    cannot see it.

    Session accessors keep their inline role in the RECORD layer - "which rows
    may this caller touch" (ownership, membership scoping) stays inside the
    function body, where Session::get_user_id() and friends belong.

ACCOUNT STATE (WHO MAY LOG IN AT ALL)
    THE DOCTRINE (owner rulings 2026-08-12, 2026-09-17): the framework
    authenticates AND enforces SITE MEMBERSHIP; the APPLICATION decides what an
    account's IDENTITY state means.

    RsxAuth::verify_credentials() checks exactly four things: the address resolves to a live
    login identity, the password matches, the identity holds at least one
    ACTIVE site membership (enabled, on an enabled site), and the identity is not
    waiting on a password reset (PASSWORD RESET REQUIRED below). It does NOT read
    login_users.status_id, is_activated
    or is_verified, and it never will. Those three columns are APPLICATION
    vocabulary - they ship with the template as a starting point, they are meant to
    be overridden, and "suspended" means whatever your product says it means. A
    framework that guessed would either lock out an app that uses the column
    differently or quietly authenticate one that expected it to be enforced.

    users.is_enabled and sites.is_enabled are the other case entirely. They are
    written by the framework's own management surfaces and read by the framework
    wherever an identity is established, so their meaning is fixed and the
    framework enforces them. AN APPLICATION DELETES ITS OWN is_enabled CHECKS: repeating one adds nothing, and
    a listing that filters on it while the framework enforces it elsewhere is how
    the two drift.

    The columns and their owners:

        users.is_enabled        FRAMEWORK. The per-site membership switch -
                                "this person no longer works here". Enforced at
                                login and at every request; see SITE MEMBERSHIP
                                below. The ->enabled() scope reads this column
                                alone; User_Model::is_active() and the ->active()
                                scope read it together with sites.is_enabled.
        sites.is_enabled        FRAMEWORK. The per-site switch - "this whole
                                workspace is switched off". A membership on a
                                disabled (or deleted) site is unusable, exactly as
                                if it were disabled itself. The Default site
                                (id 0) can never be disabled: the save throws.
        login_users.status_id   APPLICATION. Along with is_activated /
        (+ is_activated,        is_verified, the account-level state of the
           is_verified)         cross-site identity. Yours to define and yours to
                                enforce.
        login_users.password_reset_required  FRAMEWORK. Refuses a PASSWORD sign-in
                                until the password changes; see PASSWORD RESET
                                REQUIRED below. portal_users carries the same
                                column for the portal realm.
        login_users.is_developer  FRAMEWORK. Whether this identity is a developer
                                of the installation. It gates nothing about logging
                                in; it is here because it is the one piece of
                                account state a person sets by hand.

    THE DEVELOPER FLAG

    A developer is login_users.is_developer, and nothing else. Read it with
    Session::is_developer() in PHP, and with window.rsxapp.is_developer in
    JavaScript - where the key is PRESENT ONLY WHEN TRUE, so client code asks it as
    a truthiness question and an absent key means false. It is never a role (a role
    says what somebody may do inside one site's records; this says who builds the
    software, across every site they belong to) and it is never a hostname (a box is
    not trusted because of what it is called).

    IT IS SET BY A PERSON, BY HAND, IN THE DATABASE:

        UPDATE login_users SET is_developer = 1 WHERE email = 'someone@example.com';

    There is no UI for it, no endpoint that writes it, no configuration key and no
    environment variable - and there will not be one. Whoever can open a database
    client against the production database already has de facto developer access to
    everything the application can reach, so the flag grants nothing that possession
    of that client did not already grant; and being able to open one is exactly the
    competence bar for holding it. Any lesser channel would hand the flag to people
    who could not otherwise have taken it.

    The initial user - login_users id 1, the account the first-run screen or the
    RSPADE_DEFAULT_* post-migrate step creates - is a developer, because the first
    account on an installation belongs to whoever is building it.

    The headless API tier is never a developer tier: a bearer key is a machine
    credential, and Session::is_developer() answers false for it and for an
    anonymous caller.

    A soft-deleted identity is refused for free and needs no code: Login_User_Model
    uses SoftDeletes, so the global scope hides trashed rows from
    verify_credentials()'s lookup and a deleted account is classified NOT_FOUND - the same answer a
    stranger's address gets, which is the right answer to give a stranger. Its
    API keys die with it: a bearer key whose login identity is soft-deleted is
    refused like an unknown key (rsx:man external_api).

    SITE MEMBERSHIP (users.is_enabled, sites.is_enabled) - THE FRAMEWORK'S OWN
    ENFORCEMENT

    A membership is ACTIVE when both switches are on: the users row is enabled and
    not deleted, and its site is enabled and not deleted. That is one definition,
    in two spellings - User_Model::is_active() for a row, the ->active() scope for
    a query - and every rule below asks it. A site picker lists and accepts with
    ->active() too, so it never offers a site the framework would refuse:

        User_Model::where('login_user_id', $id)->active()->get();

    Two rules, and an application writes neither of them.

    AT LOGIN. An identity holding no active membership on ANY site fails exactly
    the way a wrong password fails: verify_credentials() answers null and the
    caller cannot tell the two apart. The audit trail keeps the distinction the caller is denied
    - Login_History::record_failure() with STATUS_FAILED_DISABLED. The predicate is
    public, for the rare caller that has to ask it directly:

        RsxAuth::has_enabled_membership($login_user): bool

    Every other door runs through RsxAuth::login(), which asks the same question
    and RETURNS FALSE without touching the session when the answer is no - so a
    second factor answered correctly (Rsx_Two_Factor::verify_challenge), a
    federated sign-in the provider verified (Rsx_Sso), and the development
    harness's signed dev-auth headers are all refused too. The framework's callers
    record STATUS_FAILED_DISABLED and then fail in their own vocabulary: the
    challenge answers "That code is not valid.", SSO answers the same message its
    sso.login.authorize denial answers, and the harness renders anonymous.

    AT REQUEST TIME. A session that was legitimate five minutes ago must not
    outlive the membership behind it:

        Session::enforce_enabled_membership(): bool

    When the session names a login user and a site, and the users row for that pair
    is MISSING or not active (its is_enabled is false, or the SITE is disabled or
    deleted), the staff sign-in is SIGNED OUT (SIGN_OUT_MEMBERSHIP_DISABLED) and false
    is returned. The staff dispatcher calls it once per request immediately before the
    #[Auth] gates, and the Ajax channel calls it for every call before its gates;
    both then answer response_auth_required() through their ordinary channel - a
    redirect to login with the intended URL captured for a page, the auth_required
    envelope for an Ajax call. Disabling an account therefore ends the sign-ins
    that were already open, and disabling a site ends every sign-in serving it -
    which is the only reading of "disabled" worth having. An identity's
    memberships on OTHER sites are unaffected: it still signs in to those.

    The EFFECTIVE identity is what is checked. Under impersonation the browser's
    user session is the target's, so disabling an account ends an impersonation of
    it exactly as it ends that account's own sign-ins.

    The external API tier is enforced separately and earlier - Rsx_Api_Bearer
    refuses a key whose membership is not active (User_Model::is_active(), so a
    disabled site's keys stop working too) before it installs an identity - and a
    command or a task has no browser to enforce against (a #[Run_As_Dispatcher]
    task is refused at run time instead - TASKS RUN AS THEIR DISPATCHER).

    STAFF ONLY. The portal realm does not read either switch: a portal's site is
    the application's own declaration (Portal_Session::set_site_id(), rsx:man
    portal), and its sign-in and per-request rules are the application's.

    PASSWORD RESET REQUIRED (login_users.password_reset_required) - SET BY YOU,
    ENFORCED AND CLEARED BY THE FRAMEWORK

    A state of the identity that refuses a PASSWORD sign-in until the password
    has been changed: a credential believed compromised, a temporary password an
    operator issued. TINYINT, default 0, on login_users and on portal_users.

        $login_user->require_password_reset();     // sets the flag; does not save
        $login_user->save();
        $login_user->is_password_reset_required(); // bool

        php artisan rsx:users:force_password_reset --user=<id|email> [--clear] [--json]
        php artisan rsx:users:force_password_reset --portal-user=<id> [--clear]
        php artisan rsx:users:force_password_reset --portal-user=<email> --site=<id>

    The command is the operator's switch and its --clear the recovery for a
    wrongly flagged account. It sends no email, ends no session and changes no
    password - the reset workflow (a forgot-password link, a support call) is the
    application's, and a session already open stays open (rsx:users:password:set
    ends sessions when the password must go now).

    THE REFUSAL. verify_credentials() asks the flag LAST - after the password
    matched and an active membership was found - and THROWS:

        App\RSpade\Core\Auth\Auth_Password_Reset_Required_Exception
            ->getMessage()   'Your password must be reset before you can sign in.'
            ->identity       the Login_User_Model the credentials proved (NOT signed in)

    Nothing about the flag reaches a caller that has not proved the password, and
    an identity the installation would refuse anyway (no active membership) still
    answers the indistinguishable null. It is the second thrown refusal beside
    Auth_Throttled_Exception, and a login function catches both, rendering the
    message and the way to a new password:

        try {
            $login_user = RsxAuth::verify_credentials($credentials, record: false);
        } catch (Auth_Throttled_Exception $e) {
            return $form_with_error($e->getMessage());
        } catch (Auth_Password_Reset_Required_Exception $e) {
            return $form_with_error($e->getMessage() . ' Use "Forgot your password?".');
        }

    A login function that does not catch it lets a flagged account's sign-in
    surface as an error page; nothing sets the flag but the application and the
    command, so an install that never flags anybody never sees it.

    RECORDED, AS A ROW, WHATEVER record SAYS: STATUS_FAILED_PASSWORD_RESET_REQUIRED
    through Login_History::record_refusal() (LOGIN HISTORY below). record: false
    defers a SUCCESS the caller will know better; this outcome is already final.
    It is not a failure in the throttle's sense - nothing is counted, since the
    caller holds the password.

    THE PASSWORD DOOR ONLY. A passkey sign-in and a federated sign-in never
    present the password the flag distrusts, so neither consults it. No
    second-factor challenge begins for a flagged identity's password either: the
    check before it has already thrown.

    CLEARED BY THE FRAMEWORK when the password changes: both models' booted()
    zero the flag in the same save that writes a new password hash (one UPDATE,
    no second save). A save that assigns the flag ITSELF beside a new password
    keeps what it assigned - an operator issuing a temporary password that must
    be replaced writes both at once:

        $login_user->password = Login_User_Model::hash_password($temporary);
        $login_user->require_password_reset();
        $login_user->save();

    Only a model save clears it; a write that bypasses the model (raw SQL,
    ->raw_bulk()) does not.

    THE PORTAL. Portal_Auth::verify_credentials() (rsx:man portal, SIGNING IN)
    applies the same flag on portal_users, throws the same exception carrying the
    Portal_User_Model, and records into Portal_Login_History.

    Enforce your own IDENTITY statuses in TWO places, and understand why both
    (site membership needs neither - the framework does it):

    1. AT THE LOGIN GATE - your own login function, BETWEEN
       RsxAuth::verify_credentials() and RsxAuth::login(). The password has been
       checked and nobody is signed in yet, so a refusal is just an error: there
       is no session to undo. Record the outcome yourself, in the shared
       vocabulary:

           // record: false - whether this is a SUCCESS is not known until your
           // own question has been answered.
           $login_user = RsxAuth::verify_credentials($credentials, record: false);

           if ($login_user === null) {
               Login_History::record_failure($params['email'], Login_History::STATUS_FAILED_PASSWORD);

               return response_form_error('Invalid credentials');
           }

           if ($login_user->status_id !== Login_User_Model::STATUS_ACTIVE) {
               // STATUS_FAILED_LOCKED is the app-owned outcome; the framework
               // writes STATUS_FAILED_DISABLED itself for site membership.
               Login_History::record_failure(
                   $params['email'],
                   Login_History::STATUS_FAILED_LOCKED,
                   'status_id = ' . $login_user->status_id,
                   $login_user->id
               );

               return response_form_error('This account is not active.');
           }

           RsxAuth::login($login_user);
           Login_History::record_success((int) $login_user->id, $params['email']);

    2. MID-SESSION - because the gate only runs at login, and a sign-in lives
       for days. An account suspended at 10am must not keep working until its
       owner next signs in. The hook is Main::pre_dispatch(), which HALTS
       dispatch when it returns non-null:

           // rsx/main.php
           public static function pre_dispatch(Request $request, array $params)
           {
               if (!Session::is_logged_in()) {
                   return null;
               }

               $login_user = Session::get_login_user();

               if ($login_user->status_id === Login_User_Model::STATUS_SUSPENDED) {
                   // A bearer-key request has no browser session to end: any
                   // non-null return refuses it (403 account_refused).
                   if (Session::is_api_request()) {
                       return false;
                   }

                   Session::logout();

                   return redirect(Rsx::Route('Login_Controller::index',
                                              ['reason' => 'suspended']));
               }

               return null;      // continue dispatch
           }

       EVERY SURFACE MEANS EVERY SURFACE: the hook runs for a routed page, an SPA
       bootstrap, an external API call (/api/vN, after the bearer identity
       and the gates - rsx:man external_api), and a bearer key on one of the
       file-serving routes (/_download, /_inline, /_download_zip, /_thumbnail/*,
       /_preview/*), whose identity is established before the gates and before
       this hook. An API client cannot follow a redirect, so for any bearer
       identity a non-null return is answered as 403 account_refused;
       and the session writers are unavailable to a headless API identity, which
       is why the example branches on Session::is_api_request() before logout().

       It also runs for every Ajax CALL, once per call (batched or not), with
       $params['controller'] and $params['action'] naming the endpoint. A
       non-null return refuses that call: a coded result keeps its code and
       reason (return response_unauthorized('Your account is suspended.')
       for an Ajax call to show that message), and any other value - the
       redirect above included - answers 'unauthorized' "This request was
       refused.". It is never rendered as a page (rsx:man
       ajax_error_handling, TRANSPORT).

       Return an interstitial instead of a logout when the state is meant to be
       RESOLVED rather than punished (unverified email, terms not accepted,
       payment overdue): redirect to the screen that fixes it, and let the user
       keep their session. Because the hook also runs for each Ajax call, an
       interstitial that answers every request refuses the fixing screen's own
       calls too: decide on the channel (Rsx_Request_Channel::current() ===
       Rsx_Request_Channel::AJAX) or on $params['controller'] /
       $params['action'].

       NOT init(). Main::init() is a BOOTSTRAP hook - it runs once as the
       framework provider boots, in EVERY process including artisan commands and
       task workers, there is no request in scope, and its return value is
       discarded. It cannot eject anybody. init() is where you set things up;
       pre_dispatch() is where you can say no. (Portal code uses
       Portal_Main::pre_dispatch(), which has the same contract.)

    A per-USER (not per-request) check belongs in a gate instead: an
    #[Auth_Check] named for the state (is_account_active) makes it declarative,
    reusable and visible to Permission::can_access(). Use pre_dispatch when the
    answer must apply to EVERY surface, gates when it narrows specific ones.

    Session termination is the other half of enforcement FOR YOUR OWN STATUSES:
    an app-defined suspension leaves existing sessions alive until the next
    pre_dispatch runs, so an app that wants the browser signed out NOW calls
    Session::terminate_all_sessions_for_user() (SESSION MANAGEMENT below).
    users.is_enabled needs none of that - enforce_enabled_membership() ends such a
    session on its very next request.

SECURITY
    Session tokens and CSRF tokens are 64-character random hex, compared in
    constant time, and both rotate at every sign-in and sign-out (TOKEN
    ROTATION). A sign-in has a maximum length and a maximum idle time, checked
    on every request (LIFETIMES, CLEANUP AND DEACTIVATION).

    Cookie Settings:
        - Name: `__Host-rsx` whenever the cookie is Secure - every request in
          debug and production, and every https request in development. The
          plain name `rsx` is used ONLY on a development-mode request over plain
          http (where a browser would refuse a `__Host-` cookie outright). The
          two are never read interchangeably: a secure request reads only
          `__Host-rsx`, so a plain `rsx` cookie planted beside it is invisible.
          Rsx_Session_Cookie::name() is the one place the name is spelled.
        - HttpOnly: true (no JavaScript access)
        - Secure: true - unconditionally in debug and production mode. In
          DEVELOPMENT mode only, the flag follows the request scheme, so the
          plain-http loopback harness (rsx:debug, Playwright) can hold a
          session at all. The one cookie's attributes come from one helper,
          App\RSpade\Core\Session\Rsx_Session_Cookie.
        - SameSite: Lax (CSRF protection)
        - Path: /
        - Expires: 365 days, sliding - the same token cookie is re-emitted on
          every response. The cookie outlives every server-side limit on
          purpose: the server decides when a sign-in ends.

    Session Fixation:
        Planting a token in a victim's browser gains nothing: the victim's
        sign-in rotates the token, and the planted one then matches nothing.
        The cookie NAME is the second line. A browser accepts a `__Host-`
        cookie only when it is Secure, has Path=/, carries NO Domain attribute
        and arrives from a secure origin - so a sibling subdomain, a narrower
        path and a plain-http response all cannot set or shadow it. Do not
        serve a session-bearing page over plain http outside development, and
        never relax the cookie's attributes in a class override of
        Rsx_Session_Cookie - each one is load-bearing.

        Renaming the cookie signs every browser out once: a cookie under the
        previous name is never read.

    Choosing the limits:
        max_idle_minutes ends a sign-in nobody is using. It does NOT bound
        somebody who has taken over a sign-in - they are never idle.
        max_length_minutes is the limit that does: with it at 8 hours, a copied
        cookie is useful for at most 8 hours from the real person's sign-in,
        and ends sooner if they sign in again on that browser (the rotation).
        An application that holds sensitive records sets both to hours and
        turns on a second factor, so every re-entry is a full
        re-authentication:

            'sessions' => [
                'staff' => ['max_length_minutes' => 480, 'max_idle_minutes' => 60],
            ],

    Logout:
        GET /logout is BLESSED (owner ruling 2026-08-12): the template's logout
        route answers GET, deliberately. The worst a forged logout link can do
        is sign somebody out - nothing is disclosed or destroyed. This is the
        ONE sanctioned mutating GET in the auth surface; everything else
        follows the usual rule (conformance audit get_routes_write_nothing).

        logout() ends the realm's sign-in and keeps the browser's row active;
        Session::reset() is the invalidation primitive - every sign-in on the
        browser signed out (SIGN_OUT_SESSION_RESET), every value cleared, the
        row made inactive and the cookie expired, so the browser starts over as
        a stranger.

IMPERSONATION
    Staff "Sign in as this user" - a staff account assuming another login
    identity to see what that user sees. Full read/write: core exposes
    is_impersonating() and nothing else, and restricting anything is the
    application's call. (The portal's View as Client is read-only by framework
    mandate - rsx:man portal.)

    An impersonation is a USER SESSION of its own on the impersonator's
    browser: the target's login identity, the current site, and
    impersonator_login_user_id = the impersonator. The browser points at it
    while it lasts; the impersonator's own sign-in stays signed in behind it,
    SUSPENDED (not current, its clocks not running).

    Methods:
        Session::begin_impersonation(int $target_login_user_id): void
            From the CURRENT staff sign-in. The user session (this browser, the
            target, the current site, the impersonator) is found or created
            and made current. It runs on the impersonator's clocks
            (signed_in_at and last_page_view_at carried over) - nobody
            re-authenticated, so nothing rotates and the target's last_login
            is untouched. Throws when nobody is signed in, when already
            impersonating (one level only), and for the current identity
            itself.

        Session::stop_impersonation(): bool
            Signs the impersonation out (SIGN_OUT_IMPERSONATION_ENDED) and
            points the browser back at the impersonator's own sign-in, which
            takes over the impersonation's last page view. Nothing rotates.
            False (no-op) when not impersonating.

        Session::is_impersonating(): bool
        Session::get_impersonator_login_user_id(): ?int
        Session::get_impersonator_login_user(): ?Login_User_Model
        Session::get_impersonation_started_at(): ?string
        Session::cli_set_impersonator_login_user_id(?int): void
            (test seeding; a virtual session's raw setter)

    Semantics:
        - logout() is the hard exit: it signs out the impersonation AND the
          impersonator's own sign-in behind it. A sign-in limit passing does
          the same, since the impersonation ran on the impersonator's clocks.
        - Another account signing in on the browser ends both, too.
        - A site switch while impersonating moves the impersonation to that
          site and keeps the impersonator's sign-in behind it.
        - The impersonator's own sign-in signing out (from another browser, an
          administrator) takes the impersonations riding it with it.
        - rsx.sessions.impersonation_max_days (7; 0 = never): the daily
          end_stale_impersonations task signs out impersonations older than
          that, with the impersonator's own sign-in; a View as Client is
          signed out alone. The audit record is permanent either way.
        - get_user() resolves the target's membership on the current site; a
          target with no membership there answers null, so validate before
          beginning.
        - get_sessions_for_user() leaves an impersonation out of the target's
          own list ($include_impersonations shows it to an administrator), and
          the target's terminate_all_other_sessions() still ends it.

    Client exposure:
        window.rsxapp.impersonation = {impersonator_login_user_id,
        impersonator_email, started_at} while impersonating, null otherwise;
        window.rsxapp.user is the EFFECTIVE (target) user.

    The system panel's entry and exit:
        The framework's own caller is the /_sys panel's "Sign in as this user"
        on a Users detail (rsx:man sys_panel, IMPERSONATION) - developers only,
        never onto a developer, onto one of the identity's ACTIVE memberships.
        It stores the developer's current site as a session value
        ('sys.impersonation.return_site'), calls set_site_id(<chosen site>)
        and then begin_impersonation(), and loads `/`. GET
        /_sys/stop-impersonating (Rsx.Route('_Sys_Impersonation_Controller::stop'),
        published into every bundle) requires the IMPERSONATOR to be a
        developer, calls stop_impersonation(), restores and forgets the stored
        site, and lands on /_sys/users/<id>. It is the one panel route gated
        is_logged_in rather than is_sysadmin, since the effective identity is
        not a developer while impersonating.

        THE APP'S SITE DECLARATION WINS. A Main::init() that calls
        set_site_id() on every request (the single-tenant template's
        Session::set_site_id(1)) moves the impersonation to that site on the
        very next request, and enforce_enabled_membership() then checks the
        target on it: an active membership continues the impersonation there;
        none signs it out together with the developer's own sign-in.

    Usage - authorization (who may impersonate) is the APPLICATION's:

            #[Ajax_Endpoint]
            #[Auth('can_impersonate_staff')]     // an #[Auth_Check] you declare
            public static function impersonate(Request $request, array $params = [])
            {
                $target = User_Model::find($params['user_id']);
                if (!$target) {
                    return response_not_found();
                }

                Session::begin_impersonation($target->login_user_id);
                return ['redirect' => Rsx::Route('Dashboard_Index_Action')];
            }

        Render the banner from window.rsxapp.impersonation with an exit control
        that calls stop_impersonation(). The template's Impersonation_Banner
        links the panel's stop route, because the panel began it there.

LOGIN HISTORY
    Class: App\RSpade\Core\Session\Login_History (staff, `_login_history`)
           App\RSpade\Core\Session\Portal_Login_History (client portal,
           `_portal_login_history`)

    TWO STORES, ON PURPOSE. Outcomes only a credential holder can cause are
    database rows; failures are ephemeral counters plus a log line. This is the
    whole design, and everything below follows from it.

    ONE API, TWO REALMS. Both classes are Login_History_Abstract bound to their own
    table and identity: the same methods, the same STATUS_* constants (spelled the
    same through either class), the same throttle. Everything below is written for
    Login_History; PORTAL LOGIN HISTORY at the end of this section says what the
    portal binding does differently.

    RECORDING IS AUTOMATIC:
        RsxAuth::verify_credentials() records every outcome it classifies. You do not call
        Login_History from an ordinary login flow, and if you do you will
        double-record:

            SUCCESS              authenticated
            FAILED_NOT_FOUND     no such address (soft-deleted identities
                                 included - see ACCOUNT STATE)
            FAILED_PASSWORD      hash mismatch, with the login_user_id
            FAILED_DISABLED      no active site membership
            FAILED_PASSWORD_RESET_REQUIRED
                                 correct password, identity flagged (a ROW,
                                 recorded even with record: false - ACCOUNT
                                 STATE, PASSWORD RESET REQUIRED)

        verify_credentials() is the only place that can tell those apart before
        collapsing them, which is why it is the place that records them - a
        caller never has to repeat the lookup to find out what just happened.
        Malformed input (missing email or password) records nothing: nobody
        offered a credential pair, so there was no attempt to classify.

        Opt out with verify_credentials($credentials, record: false) when the
        check is not yet a login - a sign-in that still owes a second factor or
        an account question of your own, a fixture, a harness. The dev-auth
        harness never reaches verify_credentials() at all, so rsx:debug logins
        are already excluded.

    SUCCESSES AND POST-PASSWORD REFUSALS ARE ROWS:
        record_success(), record_refusal() and record_passkey_enrollment() are
        the only things that write `_login_history`. record_refusal($id, $email,
        $status, $reason = null) records a sign-in refused AFTER its credentials
        were proven - the framework's producer is the password-reset refusal; an
        app may record its own post-password refusal there (STATUS_FAILED_LOCKED)
        when it wants it in the history rather than the counters - and feeds no
        counter. record_passkey_enrollment() records the outcome of a
        signed-in identity's passkey enrollment ceremony (begun, enrolled,
        failed, abandoned - rsx:man two_factor, PASSKEY ENROLLMENT OUTCOMES);
        it is written only for an authenticated identity acting on itself.
        Each needs a credential to cause, so the tables grow with real use
        rather than with attack volume,
        and is pruned by Session_Cleanup_Service::cleanup_login_history (hourly,
        chunked) past rsx.sessions.login_history_retention_days (default 365; 0
        or null disables the prune).

    FAILURES ARE EPHEMERAL - NO ROW AT ALL:
        record_failure() writes NO database row. It increments two counters - one
        keyed by email (hashed and normalized, so casing or stray whitespace
        cannot open a fresh window), one by client IP - both expiring on
        rsx.sessions.login_throttle.window_minutes (default 15), and it emits ONE
        Log::warning('Login failure', [...]) carrying email, IP, status and
        reason. That log line is the forensic record; the counters exist only to
        answer "how many failures in the window".

        WHY (2026-08-12 CR): /login is anonymous-reachable, so a persisted
        failure row was an UNAUTHENTICATED INSERT - any bot could grow the table
        without limit - and the only consumers of those rows were the two
        short-window counts below. Persisting them bought unbounded growth in
        exchange for a number a TTL'd counter answers exactly.

    THE WINDOW IS THE HORIZON:
        $count = Login_History::get_failed_attempts_count($email, $minutes = 15);
        $count = Login_History::get_failed_attempts_count_by_ip($ip, $minutes = 15);

        BOTH ANSWERS ARE BOUNDED BY THE CONFIGURED WINDOW. $minutes is retained so
        existing call sites keep working, but asking for a larger window returns
        the window's count, not a longer history: a 30-day failed-attempt count
        is no longer answerable from this API, and a "Failed logins (30d)" stat
        must shrink to the window rather than display a number that cannot mean
        what it says. Anything longer comes from the log.

        The window is FIXED, not sliding - it runs from the first failure, then
        the counter disappears and the next failure opens a new one. A sliding
        window would let a slow attacker hold a counter alive forever.

        THESE COUNTS ARE A STATISTIC, NOT THE ENFORCEMENT. Brute-force
        enforcement is the framework's own, in Login_Throttle (next section),
        which keeps its own per-IP counter. Nothing enforces the per-email count;
        read it, display it, alert on it - do not build a second throttle on it.

    STATUS CONSTANTS:
        Login_History::STATUS_SUCCESS          - produced by verify_credentials()
        Login_History::STATUS_FAILED_PASSWORD  - produced by verify_credentials()
        Login_History::STATUS_FAILED_NOT_FOUND - produced by verify_credentials()
        Login_History::STATUS_FAILED_2FA       - produced by
                                                 Rsx_Two_Factor::verify_challenge()
        Login_History::STATUS_FAILED_SSO       - produced by
                                                 Rsx_Sso::handle_callback()
                                                 (rsx:man sso)
        Login_History::STATUS_FAILED_PASSKEY   - produced by
                                                 Rsx_Two_Factor::verify_passkey_login()
        Login_History::STATUS_FAILED_DISABLED  - produced wherever the framework
                                                 refuses an identity with no active
                                                 membership (verify_credentials(),
                                                 the challenge, passkey and SSO doors)
        Login_History::STATUS_FAILED_PASSWORD_RESET_REQUIRED
                                               - produced by verify_credentials(),
                                                 a ROW (record_refusal())
        Login_History::STATUS_FAILED_LOCKED    - no framework producer

        Passkey enrollment ceremony rows (record_passkey_enrollment(), written
        by Rsx_Two_Factor - rows, not log lines, and never fed to the throttle):
        Login_History::STATUS_PASSKEY_ENROLL_BEGUN
        Login_History::STATUS_PASSKEY_ENROLLED
        Login_History::STATUS_PASSKEY_ENROLL_FAILED
        Login_History::STATUS_PASSKEY_ENROLL_ABANDONED

        FAILED_2FA is written by the framework's own second-factor challenge
        (rsx:man two_factor) - an app that runs the challenge through
        Rsx_Two_Factor does NOT record it itself. FAILED_LOCKED has no producer
        because account state is APPLICATION vocabulary (ACCOUNT STATE above):
        the app records that outcome itself through record_failure() (or
        record_refusal()). It is kept here so every app spells the same outcome
        the same way. Since failures are not rows, a FAILED_* status recorded
        through record_failure() describes the LOG line, not a column;
        FAILED_PASSWORD_RESET_REQUIRED is the one framework FAILED_* status that
        is a row.

    READING IT BACK:
        $history = Login_History::get_history_for_user($login_user_id, $limit = 10);

        // One PAGE for a grid: column sort, search, numbered pager
        $page = Login_History::list_page([
            'login_user_id' => $login_user_id,   // required
            'filter' => 'firefox',               // attempted email, IP, user agent
            'sort' => 'created_at',              // created_at | email | ip_address | status
            'order' => 'desc',
            'offset' => 0,
            'limit' => 25,                       // 1..200
        ]);
        // ['rows' => [...same row shape...], 'total' => int, 'offset' => 0, 'limit' => 25]
        // Invalid input throws InvalidArgumentException. There is no site scope:
        // a sign-in authenticates the identity before any site is chosen. The
        // shape is the framework's standard display-page reader - rsx:man
        // database_schema_architecture, READERS OVER SYSTEM TABLES.

        Successes, post-password refusals and passkey enrollment outcomes, most
        recent first. Each record: id, email, ip_address, user_agent,
        user_agent_parsed, location (null until geo-IP is wired), status,
        status_label, failure_reason, created_at. status tells a sign-in from a
        refusal or an enrollment row; an app may also record its own outcomes
        through record_success() / record_refusal().

    PORTAL LOGIN HISTORY:
        Portal_Login_History is the same API over `_portal_login_history`, every
        id a portal_users id. Its framework producers are
        Portal_Auth::verify_credentials() (the password door, rsx:man portal),
        Rsx_Portal_Two_Factor (the challenge, passwordless passkey sign-in,
        passkey enrollment) and Rsx_Portal_Sso (federated sign-in) - the same
        outcomes, the same statuses, written to the portal table. FAILED_DISABLED
        there means the portal refused the identity (Portal_User_Model::can_login()
        or another site's portal user). What differs:

            - a row also carries the portal user's site_id, read from the portal
              user itself;
            - list_page() requires 'portal_user_id' (not 'login_user_id');
            - the per-email/per-IP STATISTICS are kept under their own keys
              ('portal_login_failures:...'), so get_failed_attempts_count*() on
              each class reads its own realm - while Login_Throttle, the
              enforcement, is ONE per-IP budget across both realms;
            - location is always null (the portal table has no location columns);
            - rows cascade with their portal user (a FOREIGN KEY ... ON DELETE
              CASCADE, like the other portal-user-keyed system tables).

        The same retention sweep and window prune both tables.
        `_portal_login_history` is a system table: application code reads it
        through Portal_Login_History and nothing else.

    APP RECIPE - CUSTOM STATUSES:
        Record the outcomes the framework cannot see, in the shared vocabulary
        (the ACCOUNT STATE section shows this inside a login function):

            Login_History::record_failure(
                $email,
                Login_History::STATUS_FAILED_DISABLED,
                'status_id = ' . $login_user->status_id,   // optional detail
                $login_user->id                            // optional, if known
            );

        This increments the same throttle counters a password failure does, which
        is usually what you want. Never pass a secret - the password is
        deliberately not a parameter.

    APP RECIPE - TWO-FACTOR:
        The second step is the FRAMEWORK'S (Rsx_Two_Factor - TOTP, passkeys and
        recovery codes; full treatment in rsx:man two_factor). What an app owns
        is the login function around it, and the shape below is the whole of it.

        CHECK THE PASSWORD, THEN RUN THE SECOND STEP, THEN SIGN IN - in that
        order, as three separate acts. verify_credentials() signs nobody in, so
        the visitor stays signed out for the whole of the second step, and a
        request that dies part-way leaves them out. Do not record at the password
        stage either, so a recorded SUCCESS always means FULL authentication:

            $login_user = RsxAuth::verify_credentials($credentials, record: false);

            if ($login_user === null) {
                Login_History::record_failure($email, Login_History::STATUS_FAILED_PASSWORD);
                return response_form_error('Invalid credentials');
            }

            if (Rsx_Two_Factor::is_enabled($login_user)) {
                // Parks the pending identity on the session. Nobody is signed in,
                // and nobody will be until the factor passes.
                Rsx_Two_Factor::begin_challenge($login_user);

                return redirect(Rsx::Route('Login_Controller::verify'));
            }

            // No second factor: this IS the login.
            RsxAuth::login($login_user);                          // stamps last_login
            Login_History::record_success($login_user->id, $email);

        The challenge is answered by YOUR endpoint, because where a signed-in
        user lands is application logic. verify_challenge() signs them in,
        stamps last_login, writes the success row, and records the FAILED_2FA
        row on a wrong answer - so the endpoint records nothing itself:

            try {
                $login_user = Rsx_Two_Factor::verify_challenge($params);   // {code}|{assertion}
            } catch (Auth_Throttled_Exception $e) {
                return response_error(Ajax::ERROR_VALIDATION, $e->getMessage());
            } catch (Two_Factor_Failed_Exception $e) {
                return response_error(Ajax::ERROR_VALIDATION, $e->getMessage());
            }

            return ['redirect' => $destination];

        Worked example:
        system/app/RSpade/resource/reference_app/app/login/login_controller.php

    CLI NEVER STAMPS last_login:
        Session::set_login_user_id()'s CLI branch declares the identity override
        and returns before the stamp, whatever $touch_last_login says. So a
        command, task or test that "logs in" leaves last_login alone, and the flag
        can only be observed over HTTP.

LOGIN THROTTLE (BRUTE FORCE)
    The authentication surface is rate-limited by the framework, not by each app.
    An unthrottled login endpoint is an unlimited password (and second-factor)
    guessing oracle, so the protection is ON by default and an app inherits it
    without writing anything.

    THE CONTRACT:
        App\RSpade\Core\Auth\Login_Throttle

        require_not_throttled(?string $ip = null): void
            Throws Auth_Throttled_Exception when this client IP is locked out.
            RsxAuth::verify_credentials() and Portal_Auth::verify_credentials()
            call it as their FIRST statement, before the lookup - a locked-out
            address cannot even probe which addresses exist. Call it yourself
            only on a path that goes through neither.

        record_failure(?string $ip = null): void
            Counts one failure against the IP and locks the address out when the
            budget is spent. Login_History::record_failure() and
            Portal_Login_History::record_failure() call it, so every recorded
            failure feeds the throttle - password misses, unknown addresses, and
            the outcomes an APP records itself (a bad second factor, a disabled
            account). One budget per IP covers both realms. Call it directly only
            where you record through neither.

        retry_after_seconds(?string $ip = null): int
            Seconds left on the lockout; 0 when the address is free. For a
            Retry-After header or an operator log line.

        reset(?string $ip = null): void
            Clears the counter and the lockout - a test, or an operator
            releasing a customer.

        $ip defaults to Session::get_client_ip() (THE CLIENT ADDRESS below).

    WHERE THE COUNTERS LIVE:
        Rsx_Counter (App\RSpade\Core\Cache\Rsx_Counter), redis database 3 -
        the transient-counter store, NOT the cache. Two keys per address: a
        failure counter opened by the first failure, and a lockout marker
        holding the UNIX time the lockout expires. Login_History's per-email
        and per-IP failure counts are the same store.

        Counters are deliberately not in the cache database: RsxCache::clear()
        runs on every database transaction rollback, so a counter kept there
        would have a rolled-back request silently zero a throttle budget. They
        are also not build-scoped - a counter measures real time and must
        survive a manifest rebuild, or an attacker could clear their budget by
        waiting for a deploy. See `rsx:man caching`.

    WHAT IS COUNTED - FAILURES, NOT REQUESTS, PER IP:
        A request that authenticates costs nothing, so a real user signing in
        fifty times a day never approaches the budget; only wrong answers
        accumulate. The key is the CLIENT IP and not the email because the
        attacker chooses the email: spraying one password across a thousand
        addresses would never trip a per-email budget, while the address it is
        sprayed FROM is the one thing the attacker must keep using.

        The counter window is FIXED, not sliding - it runs from the first failure,
        then the counter disappears and the next failure opens a new one.

    THE CLIENT ADDRESS:
        Session::get_client_ip() is $request->ip(), resolved once by the
        TrustProxies middleware, and it is the ONE client-address reader - the
        login throttle, the second-factor throttle, login history, session rows,
        the API request log and revision records all use it. X-Forwarded-For is
        honoured only when the immediate peer (REMOTE_ADDR) is a trusted proxy,
        and is then walked right to left skipping trusted hops, so an entry a
        client wrote itself is never the answer. X-Real-IP is not read, and
        X-Forwarded-Host/-Port/-Prefix are never trusted.

        Trusted: loopback (127.0.0.1, ::1 - the framework's own nginx -> FPC
        proxy -> nginx hops) plus config('rsx.http.trusted_proxies'), empty by
        default. A box behind a load balancer, TLS terminator or CDN MUST list
        that device's addresses or CIDRs in TRUSTED_PROXIES in .env; until it does, every request
        appears to come from the device and the per-IP throttle counts every
        visitor as one (rsx:man prod, rsx:man launch_checklist).

    A CALLER WITH NO CLIENT IP IS NEVER THROTTLED:
        Session::get_client_ip() answers null outside a request - CLI, tasks,
        programmatic work - and there is no remote party to throttle there. A
        command that authenticates a thousand fixtures is not an attack, and
        throttling it would collapse every such process onto one shared bucket.
        The web request is the surface being defended, and it always has an
        address.

    CONFIGURATION - rsx.sessions.login_throttle:
        enabled          true   count and enforce at all
        attempts         10     failures from one IP inside the window
        window_minutes   15     how long the failure counter lives
        lockout_minutes  15     how long the address is refused afterwards

        window_minutes is ALSO the window bounding Login_History's per-email and
        per-IP counts (there is one window, not two). A non-positive value in any
        of the three numbers is a broken deployment and fails loud.

        'enabled' => false turns the whole feature off for a deployment that
        throttles at the edge instead. There is no per-endpoint switch.

    THE MESSAGE AND THE THROW:
        Auth_Throttled_Exception carries exactly "You're doing that too fast" and
        a retry_after_seconds property. It THROWS rather than returning false
        because "we did not check" is not the same answer as "those credentials
        are wrong" - a false there would report an invalid password to a user
        whose password may be perfectly correct. The message says nothing about
        which accounts exist, how many attempts remain, or when to try again;
        retry_after_seconds is for YOUR logs and headers, not for the attacker.

    APP RECIPE - A LOGIN FUNCTION:
        Catch it around the check and render the message as the form error
        (the template app's rsx/app/login/login_controller.php does exactly this;
        an Ajax login answers response_form_error($e->getMessage())):

            try {
                $login_user = RsxAuth::verify_credentials($credentials);
            } catch (Auth_Throttled_Exception $e) {
                $error = $e->getMessage();
            }

    APP RECIPE - A SECOND FACTOR:
        A 6-digit code is a million guesses inside a 30-second window, so the
        challenge step needs the same protection the password step gets. THE
        FRAMEWORK'S OWN CHALLENGE ALREADY DOES THIS - Rsx_Two_Factor::
        verify_challenge() opens with require_not_throttled() and records its
        failure as STATUS_FAILED_2FA - so an app running that challenge writes
        none of it, and only catches the throw:

            try {
                $login_user = Rsx_Two_Factor::verify_challenge($params);
            } catch (Auth_Throttled_Exception $e) {
                return response_error(Ajax::ERROR_VALIDATION, $e->getMessage());
            }

        The shape it implements, for any OTHER factor an app verifies itself -
        refuse first, then let the recorded failure do the counting:

            Login_Throttle::require_not_throttled();     // may throw - catch it

            if (!$factor_verified) {
                Login_History::record_failure($email, Login_History::STATUS_FAILED_2FA,
                                              null, $login_user->id);
                return response_form_error('That code is not valid');
            }

        record_failure() there already feeds the throttle; do NOT also call
        Login_Throttle::record_failure() or the failure counts twice.

    APP RECIPE - A PATH THAT VERIFIES A SECRET OF ITS OWN:
        A password belongs to RsxAuth::verify_credentials() (staff) or
        Portal_Auth::verify_credentials() (portal), which do all of this already.
        A flow that checks some OTHER guessable secret (a PIN, an access code)
        and records to neither history does BOTH halves itself:

            try {
                Login_Throttle::require_not_throttled();
            } catch (Auth_Throttled_Exception $e) {
                return $this_form_with_error($e->getMessage());
            }

            if (!hash_equals($expected_pin, $offered_pin)) {
                Login_Throttle::record_failure();
                $error = 'That PIN is not right.';
            }

    FAIL CLOSED, WITH ONE TOLERATED DEGRADATION:
        Nothing in Login_Throttle catches a cache error: a redis failure
        propagates and the login fails LOUD rather than proceeding unthrottled.
        The single exception is MAINTENANCE MODE, where redis is deliberately
        stopped and RsxCache answers 0/false without touching it - the throttle is
        then inert, which costs nothing because the web tier is answering 503 to
        every request anyway.

    STORAGE:
        Two redis keys per address, both in the persistent RsxCache namespace:
        a failure counter carrying the window as its TTL, and a lockout marker
        holding the instant the lockout expires. Both disappear on their own; the
        THROTTLE never writes a database row.

USER AGENT PARSING
    The User_Agent class parses user agent strings into human-readable

    Class: App\RSpade\Core\Session\User_Agent

    Basic Usage:
        use App\RSpade\Core\Session\User_Agent;

        $parsed = User_Agent::parse($user_agent_string);
        // Returns:
        // [
        //     'browser' => 'Chrome',
        //     'os' => 'Windows',
        //     'device' => 'Desktop',
        //     'summary' => 'Chrome on Windows'
        // ]

        // Quick summary only
        $summary = User_Agent::get_summary($user_agent_string);
        // Returns: "Chrome on Windows"

    Detected Browsers:
        Chrome, Firefox, Safari, Edge, Opera, Brave, Vivaldi, Internet Explorer

    Detected Operating Systems:
        Windows, macOS, iOS, iPadOS, Android, Linux, Chrome OS, Ubuntu, Fedora

    Detected Device Types:
        Desktop, Mobile, Tablet

    Notes:

        - Not intended for feature detection or security decisions
        - For comprehensive parsing, use a dedicated library like WhichBrowser
        - Location fields are placeholders for future geo-IP integration

LOCATION (GEOCODING)
    Where an address is located is recorded once per address, on its
    _ip_addresses row: city, state, country, latitude, longitude
    (rsx:man ip_addresses). The framework does not ship a geocoder yet, so
    those fields are null today; a resolver that fills them is coming, and
    Ip_Address::describe() and Ip_Address::join() answer its results when it
    lands.

    The `location` key of a login-history record (Login_History) is read from
    _login_history.location_city / location_region / location_country, which
    nothing populates; it answers null.

SYSTEM TABLES ARE PRIVATE
    _sessions, _user_sessions, _audit_sessions, _session_values, _session_links,
    _user_agents, _ip_addresses and the login histories are framework tables.
    Application code never queries one, joins one or depends on a column of
    one; a system table's schema is not a contract. Reach what they hold
    through the interfaces on this page: get_sessions_for_user(),
    get_current_session_info(), get_user_session_id(), get_audit_session(),
    Audit_Session::list_page_for_user_session(), Audit_Session::join(),
    Login_History.

    The one reference an application makes is a constraint, not a query: a
    table of BROWSER-scoped state of your own (a preference for this browser, a
    half-finished import) declares

        FOREIGN KEY (session_id) REFERENCES _sessions (id) ON DELETE CASCADE

    with session_id NULLABLE when anything but a browser request may write the
    row. A browser that has had a sign-in is never deleted (only made inactive),
    so the cascade reaches a guest's rows and the rows of a key's deleted API
    session. When an interface does not answer what you need, ask for it to be
    extended (rsx:man database_schema_architecture).
