NAME
    rsx:framework:pull - update the RSpade framework

SYNOPSIS
    php artisan rsx:framework:pull [options]
    php artisan rsx:framework:status [--fetch]

    Options:
      --diff                  Preview the incoming changelog; change nothing.
      --no-rebuild            Sync only; print the rebuild commands to run.
      --no-commit             Update the submodule, leave the pointer uncommitted.
      --no-service-control    Do not raise the maintenance window.
      --upstream-url=<url>    Pull from elsewhere, THIS RUN ONLY.
      --branch=<name>         Track another branch, THIS RUN ONLY.

DESCRIPTION
    system/ is a GIT SUBMODULE tracking the framework distribution:

        https://github.com/rspade-framework/rspade_system.git

    ALL OF system/ IS FRAMEWORK PROPERTY AND IS OVERWRITTEN ON EVERY UPDATE.

    There are no owned zones, no protected sub-paths, no merge and no
    reconciliation. The update runs `git reset --hard` inside the submodule,
    `git clean -fdx` to remove untracked files, and checks out the upstream
    tip. Local changes there are discarded without being reported, because
    there is nothing worth reporting: the tree is a checkout of somebody
    else's repository, and a modification to it is drift, not work.

    Customize the framework with a CLASS OVERRIDE in rsx/ - copy the class
    into rsx/ under the same name (rsx:man class_override). That is the
    supported path, it survives every update, and it is the reason none of
    this needs a merge.

    WHY A SUBMODULE. When system/ was vendored - ordinary tracked files in the
    application's own repository - the framework and the application shared
    one index, and everything that followed was an attempt to reconstruct a
    boundary git could not see: a per-file release inventory to detect
    tampering, a tamper gate, an owned-zone rsync, a three-way merge for the
    remainder, a mutation ledger to tell the build's own churn from a
    developer's edits, a pre-commit hook to keep system/ out of app commits,
    and a release-reconciliation phase for merges. A submodule makes that
    boundary structural. What is left is: reset, fetch, checkout, record.

THE UPDATE, IN FULL
    1.  Resolve context and paths, then COPY THIS SCRIPT TO /tmp AND RE-EXEC.
        The updater lives at system/bin/framework-pull-upstream.sh, inside the
        tree it is about to replace; git offers no guarantee that a checkout
        leaves a running script's inode intact.

    2.  Raise the maintenance window - the same one rsx:maintenance:enable
        raises (web 503, automated task runners refused). Lifted on every exit
        path, Ctrl-C included. An operator's existing window is left exactly
        as they raised it: the services it stopped are already stopped, and
        lowering ours on the way out would restart them mid-surgery.

    3.  Establish that system/ is a submodule. See CONVERSION below.

    4.  git reset --hard + git clean -fdx inside the submodule.
        Unconditional. No checks, no report, no prompt.

    5.  Fetch and check out the upstream tip.

    6.  Commit the new submodule pointer - one commit changing one gitlink,
        with the concatenated upstream changelog as its body and two
        machine-readable trailers. The full changelog is also appended to
        rsx/resource/framework_update_history.dat, which is committed with it.

    7.  Rebuild: rsx:env:heal, rsx:clean, rsx:manifest:build --force,
        migrate --framework-only, rsx:bundle:compile,
        rsx:framework:post_update.

    8.  Lower the maintenance window.

    9.  Report pending migrations and pending upstream_changes documents.

    THE POINTER IS COMMITTED BEFORE THE REBUILD. A rebuild that fails
    therefore costs only the build: fix what it reports and rebuild. NEVER
    re-pull to fix a failed rebuild. Under the old commit-after-rebuild order
    a release whose own validator failed deterministically left the tree
    synced-but-uncommitted, and the next app commit reverted it - a deadlock,
    since the migration that fixes the build needs app commits.

REFUSALS
    The update refuses outright in four situations. Each is a separate
    condition with its own message.

    IS_FRAMEWORK_DEVELOPER=true
        The framework monorepo, where system/ IS the authored source. This is
        a safety interlock rather than a policy: without it the run reaches
        the conversion path, which begins by deleting system/.

    .rspade-forked-framework present (project root or system/)
        The developer has taken ownership of the framework tree. An update
        overwrites all of system/, which is exactly what a fork prevents.
        See rsx:man framework_fork.

    APP_ENV=production
        Framework updates are reviewed in development and deployed, never
        pulled into a live deployment.

    RSX_MODE is not development
        Stricter than the APP_ENV check, which misses a sealed DEBUG build.
        debug and production are compiled once and then immutable; replacing
        the framework under one leaves it serving assets that no longer match
        what it was built from. Absent RSX_MODE means development.

    Both .env paths are consulted: system/.env is normally a symlink to the
    project-root file, but they are two files in a fixture or on a checkout
    whose link has not been healed.

WHERE IT PULLS FROM
    THE SUBMODULE'S OWN CONFIGURATION IS THE AUTHORITY. Pointing system/ at a
    fork or an internal mirror is supported, and the updater's job is to
    update from wherever the project actually tracks. Nothing in the update
    writes a remote, a URL or a branch.

    Resolution, most specific first:

      1. --upstream-url= / --branch=      one-off override for this run
      2. the submodule's `origin` remote  what a bare `git fetch` would use
      3. .gitmodules                      the recorded URL/branch
      4. the hardcoded default            only reachable when creating it

    The hardcoded default therefore applies at exactly one moment: the initial
    `git submodule add` during conversion. From the next run onwards the
    project's own configuration decides.

CONVERSION FROM THE VENDORED TREE
    Projects created before the submodule model carry system/ as ordinary
    tracked files. The update converts them, in two commits: remove the
    vendored tree, then add the submodule.

    INSIDE THE RSPADE CONTAINER this happens automatically. OUTSIDE IT the
    update REFUSES and prints the exact commands - converting rewrites the
    application's history, and that is not something to do to somebody's
    machine unasked.

    Reachability is proven before anything is deleted, and a failed submodule
    add rolls the removal commit back, so an interrupted conversion cannot
    leave an application with no framework.

THE COMMIT
    Subject:

        Framework update <old12> -> <new12> (N upstream commits)

    The commit count separates a routine update from an eight-release
    catch-up, which is the difference between skimming and reading carefully.

    Body: the byte-faithful OLD..NEW changelog, capped at 64KB with a line
    saying what was dropped and where the rest is. bin/publish embeds every
    underlying monorepo commit's full message into each release commit's body,
    so one distribution commit's body is the complete rationale for everything
    in that release.

    Trailers:

        Framework-Update-Range: <old>..<new>
        Committed-By: rsx:framework:pull

    `git log --grep=Framework-Update-Range` finds every framework update in an
    application's history without pattern-matching a subject line.

    The commit spans the gitlink and the history file, and nothing else.

UPDATE HISTORY FILE
    rsx/resource/framework_update_history.dat is a LOG, not state. Nothing
    reads it - git decides what is installed - and corrupting, garbling or
    deleting it changes nothing about an update except that the file is
    recreated.

    Sections are appended, never rewritten:

        ## RSPADE-UPDATE <iso8601> from=<sha> to=<sha>
        Date: <human>

        Changelog (<old12>..<new12>):
        <the full changelog>

        Files changed:
        <diffstat>

    A conversion records from=BASELINE. An update that moved nothing writes
    nothing.

STATUS
    php artisan rsx:framework:status

    Reports the two revisions that matter - what system/ is CHECKED OUT at and
    what the project RECORDS - and exits 1 when they disagree. Local changes
    under system/ are reported as build churn, because that is what they are.

    --fetch additionally contacts the remote and reports whether a newer
    release is available. It is opt-in: a status command should not require a
    network.

WHEN THE TWO REVISIONS DISAGREE
    A plain `git pull` updates the RECORDED revision without checking the
    submodule out, so the framework executing is not the one the project
    claims to use. Nothing fails and nothing is printed.

    Three things address this, in depth order:

      * The git proxy (rsx:man rsx_git) syncs the submodule after any
        operation that can move the recorded revision. Nobody has to remember
        --recurse-submodules.
      * bootstrap/rsx_submodule_sync.php REFUSES TO BOOT on a mismatch,
        whatever caused it - an IDE's git, /usr/bin/git directly, a script
        that never heard of the proxy.
      * git submodule update --init --recursive fixes it by hand.

    The guard is the correctness and the proxy is the convenience, which is
    why the proxy is allowed to be small.

CLONING A PROJECT
    git clone --recurse-submodules <your-app>
    git submodule update --init --recursive     # after the fact

    An empty system/ is a missing submodule, not a broken framework. That is
    the first thing to check when a fresh clone cannot find artisan.

ENVIRONMENT UPDATES
    A successful update runs system/bin/post-update.sh, which executes every
    self-detecting, idempotent script in system/bin/environment_updates/ - the
    Claude Code status line and git guard, the knowledge-tree wiring. They are
    silent when already applied, container-gated, and can never fail a build.
    See system/bin/environment_updates/CLAUDE.md.

TROUBLESHOOTING
    "This command is disabled for framework developers"
        You are in the monorepo. Use ordinary git.

    "Framework updates require development mode"
        A sealed build. Pull in development, then rsx:prod:refresh.

    "system/ is not a git submodule, and this is not the RSpade container"
        A project that predates the submodule model. Convert it in the
        container, or run the printed commands by hand.

    "The git index stayed LOCKED through all 3 attempts"
        Another process holds .git/index.lock, or one died mid-write and left
        it. The message names the holder-finding commands and the recovery.

    "This project records framework release X, but system/ is checked out at Y"
        The pre-boot guard. Run git submodule update --init --recursive.

    A failed rebuild
        The release is already in history. Fix what the rebuild reported and
        rebuild. Do not re-pull.

FOR FRAMEWORK DEVELOPERS
    This command is disabled in the monorepo. The distribution is produced by
    bin/publish; see rsx:man framework_pull_mechanics for how a release is
    assembled and what a downstream receives.
