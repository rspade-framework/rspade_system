NAME
    rsx:git - the git proxy that keeps the framework submodule in step

SYNOPSIS
    php artisan rsx:git <any git command>

    Inside the RSpade container /usr/local/bin/git routes here automatically,
    so `git` means this without anyone having to type it.

DESCRIPTION
    IT DOES EXACTLY ONE THING. After any git operation that can move the
    RECORDED revision of the system/ submodule, it makes the submodule agree
    with it. Everything else is passthrough - same output, same exit code,
    same argv, nothing announced.

    THE PROBLEM. system/ is a git submodule. When a colleague updates the
    framework and you pull their commit, git updates the recorded revision and
    does not touch the submodule's working tree. Nothing fails, nothing is
    printed, and you are now running a framework version your project does not
    claim to use. `git status` shows ` M system` and `git submodule status`
    prefixes a `+`, but nobody reads either before every command.

    The usual answer is to tell everyone to type `git pull --recurse-submodules`
    forever. A rule everybody has to remember is not a solution; this is.

WHAT IT DOES WHEN THE REVISIONS DISAGREE
        maintenance window up
          -> reset the submodule hard, discard untracked files
          -> fetch, if the recorded revision is not in the local object store
          -> check out the recorded revision
          -> rsx:clean --_no-system-reset (caches)
          -> rebuild (manifest + bundles)
        maintenance window down
        -> report pending migrations

    The window matters: replacing the framework under a live php-fpm is
    exactly the situation maintenance mode exists for.

    IT COMES DOWN ON EVERY EXIT PATH, Ctrl-C included, and it comes down
    WHETHER OR NOT THE WORK INSIDE IT SUCCEEDED. The window exists to hold the
    moving parts still while the framework is replaced, not to keep a broken
    site off the air: when the task is over the services go back, and a site
    whose code is broken then boots and REPORTS its error, which is strictly
    more useful than a dark box whose only symptom is a 502 from nginx - a
    symptom that reads as a broken application rather than a stopped php-fpm.
    An unresolved merge conflict is reported and the services start anyway.

    Should lowering the window fail anyway, that is now printed rather than
    swallowed: the proxy names the state the box is in and repeats what the
    maintenance script said, so a stopped box is never silent.

    A FAILED REBUILD is reported the same way, after the window is down: the
    box is UP, but the manifest still describes the framework that was replaced,
    and it stays that way until `rsx:manifest:build --force` succeeds. A failed
    build is a reason to print the error, never a reason to leave the box down.

    The submodule reset is performed DIRECTLY, not through rsx:clean. rsx:clean
    does the same thing and is still called for the caches, but it needs
    artisan to boot - and the checkout must not depend on that. A developer
    whose tree is too broken to run php is the developer most likely to be
    pulling a fix.

    rsx:clean runs AFTER the checkout, never between the reset and it: artisan
    refuses to boot while the recorded revision and the checkout disagree (the
    pre-boot guard, below), and in that gap they always disagree. Its failure,
    should it fail, is reported with the exit code and the command's own
    output; the sync continues either way, because a stale cache is a rebuild
    away and an unsynced framework is not.

IT NEVER RECURSES INTO system/
    The proxied command runs with recursion scoped off:

        git -c fetch.recurseSubmodules=no -c submodule.recurse=false ...

    The reconciliation above IS the design: it wants exactly ONE object, the
    revision recorded at the new HEAD, and fetches it on demand. Git's default
    (fetch.recurseSubmodules=on-demand) pre-empts that by fetching the
    submodule once per INTERMEDIATE gitlink across the pulled range - strictly
    more data, for trees the checkout that follows immediately discards. And
    once the framework's history has been rewritten upstream, those
    intermediate gitlinks name revisions the remote no longer has: upload-pack
    answers `not our ref`, git aborts the whole operation, and the code that
    would have handled it correctly never runs. A container several commits
    behind then cannot pull at all, on any retry.

    -c, not repo config: nothing persistent is written to your clone.

    THE ESCAPE HATCH. `git pull --recurse-submodules` still recurses - a flag
    on the command line overrides -c. `clone` is not wrapped at all, so
    first-time population of the submodule is untouched.

WHICH SUBCOMMANDS TRIGGER IT
        pull merge rebase cherry-pick revert checkout switch restore reset stash

    THE LIST IS THE WHOLE POLICY: these are the operations that rewrite what
    HEAD points at, and therefore the gitlink recorded for system/. Anything
    else execs git immediately.

    `restore` and `checkout` are included because they CAN move it. When they
    do not, the before/after comparison costs one rev-parse and does nothing.

    The classifier steps past git's global options: `git -C x -c k=v
    --no-pager pull` is a pull, not a `-C`.

WHERE IT GETS OUT OF THE WAY
    Four conditions, each of which makes it exactly git:

      * The framework monorepo (IS_FRAMEWORK_DEVELOPER=true). There system/
        IS the work being done, not a checkout of it.
      * No git, or not a git repository.
      * system/ is not a submodule - a project not yet converted.
      * The subcommand is not in the list above.

    FAIL-OPEN. This wraps every git call for every downstream app, so a bug
    here must never brick git. Anything unexpected falls through to plain git
    with the original argv.

THE TWO FILES IT MERGES FOR YOU
    After a MERGING operation returns - pull, merge, rebase, cherry-pick,
    revert, stash - and before anything else looks at the tree, the proxy
    settles every unmerged path whose basename is one of:

        .migration_whitelist            key-union of the `migrations` maps
        framework_update_history.dat    line-union of the log's sections

    Both conflict for exactly one reason - both sides appended to the end of
    them - and git's line merge cannot settle either, because it does not know
    the whitelist's closing brace belongs to both sides. The markers it leaves
    are out of all proportion to the cause: a whitelist that is not JSON makes
    `migrate` read an EMPTY map and declare every migration in the tree
    unauthorized, under a message that names make:migration and never mentions
    the file.

    They are safe to merge mechanically because neither holds anything two
    sides can legitimately disagree about. The whitelist's keys are migration
    filenames, unique by construction (a YYYY_MM_DD_HHMMSS_ timestamp plus a
    slug, minted by make:migration:safe), and its values are provenance stamps
    written once at mint and never edited - so a key on both sides came from
    the shared ancestor with identical values. Both sides only append; should
    one ever drop a key, the union keeps it and the worst case is an entry for
    a file that is gone, which the checker ignores. The history log is
    append-only sections that delimit themselves. A key-union is therefore not
    a heuristic: it is the only correct result, and a developer resolving it by
    hand can only reproduce it or get it wrong.

    Each resolved path is written, staged, and announced on one line:

        [NOTE] rsx/resource/migrations/.migration_whitelist merged (ours 264 + theirs 266 -> 267 entries)
        [NOTE] rsx/resource/framework_update_history.dat merged (union)

    WHEN THEY WERE THE ONLY CONFLICTS, the pull or merge is CARRIED TO
    COMPLETION - the merge is committed with git's own prepared message, a
    rebase is continued (once per stopping commit), the proxy's exit code
    becomes 0, and the submodule sync and environment updates run as they would
    after a clean pull. Resolving the files and leaving the merge half-finished
    would be the worst of both: the developer still needs the incantation, and
    now has staged changes they did not make.

    ANYTHING ELSE STILL UNMERGED STOPS IT. The two files are resolved and
    staged either way, but the operation is left exactly as git left it and
    git's exit code stands. The same is true when a stage does not parse - that
    is unreachable for a machine-written file, and it is reported rather than
    guessed at:

        [NOTE] <path> could not be merged automatically: <reason>

    checkout, switch, restore and reset are NOT included: they are in the
    subcommand list because they can move the gitlink, not because they can
    conflict, so an unmerged whitelist while one of them runs belongs to a
    merge somebody is already in the middle of.

    The whitelist merge is performed by bin/lib/merge_migration_whitelist.php,
    plain PHP with no framework boot, because the proxy is boot-free by
    contract. `git merge-file --union` does the log.

A CONFLICTED REVISION IS REPORTED, NEVER RESOLVED
    When both sides of a merge moved the recorded revision, git cannot choose
    and neither does this. Which framework release to run is a decision with
    consequences - a release can carry migrations - so the proxy prints the
    three commands that resolve it and changes nothing:

        git checkout --theirs -- system    # take the incoming revision
        git checkout --ours   -- system    # keep yours
        git add system

    Then COMMIT THE MERGE. The next `php artisan rsx:git pull` - or any other
    proxied operation that moves HEAD - checks system/ out at the revision you
    just recorded, which is this proxy's one job.

    rsx:framework:pull is a DIFFERENT operation: it fetches the tip of the
    branch system/ tracks and moves onto THAT, so it advances to the latest
    release rather than to the revision you chose. Run it only when advancing
    is what you want.

    The vendored-era proxy tried to settle the gitlink automatically by
    comparing the two sides' release markers. That cleverness is what a
    submodule makes unnecessary; the marker itself is retired.

IT DOES NOT HAVE TO BE EXHAUSTIVE
    bootstrap/rsx_submodule_sync.php refuses to boot when the recorded
    revision and the checkout disagree, whatever caused it - an IDE's git,
    /usr/bin/git directly, a script that never heard of this proxy.

    So the proxy is the CONVENIENCE and the guard is the CORRECTNESS. That is
    why the proxy is allowed to be 300 lines you can read rather than 1,500
    you have to trust.

THE THREE LAYERS
    /usr/local/bin/git          the shim. Bails to /usr/bin/git on
                                re-entrancy, outside-the-project, or no-PHP.
                                Otherwise execs `php artisan rsx:git`.
    php artisan rsx:git         intercepted PRE-BOOT in system/artisan, so it
                                never loads Laravel and works on a tree too
                                broken to boot.
    system/bin/rsx-git.sh       the proxy itself.

CWD FIDELITY
    system/artisan does chdir(__DIR__), so by the time the proxy runs, php has
    destroyed the directory every relative pathspec was written against.

    The shim exports RSX_GIT_CWD before php can do that, and the proxy
    restores it. Without the shim the anchor is the project root - what a
    human's relative pathspec is written against - and only the artisan chdir
    is undone: a cwd the caller genuinely chose is left alone.

    The failure this prevents is the worst shape there is: `rsx:git log --
    rsx/foo.php` matching nothing and exiting 0, an audit command answering
    "no history" for a file that has history.

WHAT IT NO LONGER DOES
    Under the vendored model this script was 1,553 lines. It excluded system/
    from status/diff/add with pathspecs, unstaged system/ paths out of
    commits, rewrote `commit -a`, and ran a release-reconciliation phase over
    both sides of a merge.

    A submodule makes all of that structural: the framework contributes ONE
    gitlink to the application's index, and `ignore = dirty` in .gitmodules
    hides the build's own churn without anyone hand-rolling a pathspec.

    `dirty` hides the CHURN and not the POINTER: a framework update stays
    visible in status, diff and `show --stat`, which is the one thing about
    system/ anybody reviews. Do not add a repo-wide
    `[diff] ignoreSubmodules = all` to .git/config - it hides the pointer too,
    and every other gitlink with it. The 080 environment update unsets it and
    the "Submodule Visibility" rsx:health row reports it.
