===================

OVERVIEW

    RSpade implements a standardized Ajax error handling architecture that:
    - Returns HTTP 200 for ALL Ajax responses (success and errors)
    - Encodes success/failure in response body via _success field
    - Differentiates between business logic errors and fatal PHP errors
    - Provides consistent error display across dev and production modes
    - Uses ONE browser transport in every mode (POST /_ajax/_batch, see
      TRANSPORT) and ONE core (Ajax::execute()) building ONE envelope, so the
      same endpoint outcome is the same wire shape however it was called

RESPONSE FORMATS

    All Ajax endpoints return HTTP 200 with one of these formats:

    Every envelope also carries "_server_time" and "_user_timezone" (the
    client syncs its clock from them), "console_debug" when there are debug
    messages, and "flash_alerts" when flash messages are pending.

    Success Response
    ----------------
    {
        "_success": true,
        "_ajax_return_value": { /* developer's return value */ },
        "console_debug": [ /* optional debug messages */ ]
    }

    Business Logic Errors (Validation, Auth)
    -----------------------------------------
    {
        "_success": false,
        "error_code": "validation|not_found|unauthorized|auth_required|session_expired|question|generic",
        "reason": "User-friendly message",
        "metadata": { /* optional, e.g., field-specific validation errors */ },
        "console_debug": [ /* optional debug messages */ ]
    }

    The code is the same whether the endpoint RETURNED the coded response or
    THREW the coded exception: AjaxUnauthorizedException (what
    Permission::require_permission() and the guarded Session::terminate_*()
    throw) is "unauthorized", AjaxNotFoundException "not_found",
    AjaxFormErrorException "validation", AjaxQuestionException "question",
    AjaxAuthRequiredException "auth_required". An abort() inside an endpoint is
    the envelope too, never an HTML page: 404 is "not_found", 403
    "unauthorized", 401 "auth_required", any other status "generic" with the
    abort's message.

    "session_expired" is the framework's own: the sign-in outlived
    rsx.sessions.* and was just ended (metadata.cause is "length" or "idle"), or
    the call carried the token of a session row that has since been replaced
    (metadata.cause "retired").
    Nothing in an application returns or handles it per call. The client
    announces it - and "auth_required" on a page that was rendered signed in -
    once per page to the handler registered with
    Rsx.set_session_expired_handler(), or reloads the page when there is none.
    See rsx:man session (SESSION LIFETIME).

    Fatal PHP Errors (Uncaught Exceptions)
    ---------------------------------------
    {
        "_success": false,
        "error_code": "fatal",
        "reason": "The exception message (a developer caller) or a generic sentence",
        "metadata": {},
        "error": {
            "file": "path/to/file.php",
            "line": 123,
            "error": "Full exception message with SQL/context",
            "backtrace": [
                {
                    "file": "path/to/file.php",
                    "line": 456,
                    "function": "methodName",
                    "class": "ClassName",
                    "type": "->"
                },
                /* ... up to 10 frames */
            ]
        },
        "console_debug": [ /* optional debug messages */ ]
    }

    Network/Infrastructure Errors
    ------------------------------
    No JSON answer - the request failed as a whole. The client rejects
    EVERY call the request carried with one error: HTTP 5xx is
    'server_error' (also logged through Debugger.log_error), status 0 is
    'network_error', any other HTTP failure 'generic'.

HTTP STATUS CODE STRATEGY

    ALL Ajax Responses: HTTP 200
    ----------------------------
    - Success: HTTP 200 with _success: true
    - Validation errors: HTTP 200 with _success: false
    - Fatal PHP errors: HTTP 200 with _success: false
    - Auth errors: HTTP 200 with _success: false

    Non-200 Responses
    -----------------
    Only when the request never reached a PHP answer (nginx crashed,
    PHP-FPM dead, network failure, a 5xx from the web server), and the HTTP
    400 that refuses a malformed batch (see TRANSPORT).

    Rationale
    ---------
    - Batch requests need uniform status codes (some succeed, some fail)
    - Always get parseable response body
    - Simpler client handling - check _success field, not HTTP status
    - Non-200 only means "couldn't reach PHP at all"

ERROR TYPES

    All error responses use the unified response_error() function with constants:

    Ajax::ERROR_FATAL
    -----------------
    Uncaught PHP exceptions, database errors, bugs in code.
    Dev mode: Shows file/line/error/backtrace
    Prod mode: Generic "An error occurred" message

    Ajax::ERROR_VALIDATION
    ----------------------
    Validation failures with field-specific details.
    Used via: return response_error(Ajax::ERROR_VALIDATION, $field_errors);
    Example:
        return response_error(Ajax::ERROR_VALIDATION, [
            'email' => 'Email address is required',
            'phone' => 'Invalid phone number format'
        ]);

    Ajax::ERROR_AUTH_REQUIRED
    -------------------------
    User not logged in, needs authentication.
    Used via: return response_error(Ajax::ERROR_AUTH_REQUIRED);

    Ajax::ERROR_UNAUTHORIZED
    ------------------------
    User logged in but lacks permission for this action.
    Used via: return response_error(Ajax::ERROR_UNAUTHORIZED);

    Ajax::ERROR_NOT_FOUND
    ---------------------
    Resource not found.
    Used via: return response_error(Ajax::ERROR_NOT_FOUND, 'Project not found');

    Ajax::ERROR_QUESTION
    --------------------
    NOT A FAILURE: the endpoint is asking the user something it cannot
    decide for itself, and has written nothing. Sent by
    response_form_question($key, $question); metadata is {key, question}.

        return response_form_question('duplicate_email', [
            'kind' => 'confirm', 'title' => '...', 'body' => '...',
        ]);

    The form engine answers it through the application's registered question
    handler and calls the endpoint again with _answers attached. A caller that
    is NOT a form reads error.metadata.key and error.metadata.question and
    decides for itself (Rsx_Form.ask() runs the same handler). An IN-PROCESS
    Ajax::call() raises AjaxQuestionException, carrying get_key() and
    get_question(), which is what a PHP test and rsx:ajax see.

    Full protocol: rsx:man form_conventions, the QUESTIONS section.

    server_error / network_error (client-side only)
    -----------------------------------------------
    network_error: server unreachable (xhr.status === 0). server_error: an
    HTTP 5xx, or an answer that does not carry the call (see TRANSPORT).

SERVER-SIDE IMPLEMENTATION

    Ajax Endpoints Return Plain Data
    ---------------------------------
    Endpoint methods return plain arrays/objects. Framework wraps:

    // Your endpoint
    #[Ajax_Endpoint]
    public static function get_user(Request $request, array $params = []): array
    {
        $user = User::find($params['id']);

        if (!$user) {
            return response_error(Ajax::ERROR_NOT_FOUND, 'User not found');
        }

        return [
            'id' => $user->id,
            'name' => $user->name,
            'email' => $user->email
        ];
    }

    // Framework wraps response:
    {
        "_success": true,
        "_ajax_return_value": {
            "id": 123,
            "name": "John Doe",
            "email": "john@example.com"
        }
    }

    Never Return _success Field Manually
    -------------------------------------
    The _success field is RESERVED for framework wrapping. If your endpoint
    returns an array with a boolean _success key, the framework throws an error:

    // - WRONG - Framework throws exception
    return ['_success' => true, 'data' => $user];

    // + CORRECT - Let framework wrap
    return ['data' => $user];

    Exception Handling - Let It Bubble
    -----------------------------------
    Don't wrap database/framework operations in try/catch. Let exceptions
    bubble to the global handler which formats them properly.

    // - WRONG
    try {
        $user->save();
    } catch (Exception $e) {
        return ['_success' => false, 'message' => $e->getMessage()];
    }

    // + CORRECT
    $user->save();  // Let it throw - framework catches and formats

    When Try/Catch IS Appropriate
    ------------------------------
    Use try/catch for EXPECTED failures:
    - File uploads (may fail validation)
    - External API calls (network issues expected)
    - User input parsing (malformed data expected)

    Don't use for:
    - Database operations (schema errors are bugs)
    - Framework operations (let global handler catch)
    - "Just in case" wrapping

CLIENT-SIDE IMPLEMENTATION

    Ajax.js Automatically Unwraps Responses
    ----------------------------------------
    When you call an Ajax endpoint, Ajax.js:
    1. Makes HTTP request
    2. Receives 200 response with JSON body
    3. Checks _success field:
       - _success: true -> Resolve promise with _ajax_return_value
       - _success: false -> Reject promise with Error object
    4. Network errors also reject with Error object

    Exception-Driven Pattern
    ------------------------
    Ajax calls work like any async operation:
    - Success: Promise resolves with unwrapped value
    - Failure: Promise rejects with Error object

    try {
        const user = await User_Controller.get_user(123);
        // user is the _ajax_return_value, already unwrapped
        console.log(user.name);
    } catch (error) {
        // error is standard Error object with extra properties
        console.error(error.message); // User-displayable message
    }

    Error Object Structure
    ----------------------
    Rejected promises receive standard Error objects with additional properties:

        error.code       - 'validation'|'not_found'|'unauthorized'|
                           'auth_required'|'session_expired'|'question'|
                           'generic'|'fatal', or one the client raises
                           itself: 'php_exception' (a fatal carrying
                           file/line, for a developer caller),
                           'server_error', 'network_error'
        error.message    - User-displayable message
        error.metadata   - Additional error data from server
                           (for validation: field-specific errors)
                           (for fatal: file/line/backtrace)

    Constants available on both server and client:
        PHP:  Ajax::ERROR_VALIDATION, Ajax::ERROR_NOT_FOUND, etc.
        JS:   Ajax.ERROR_VALIDATION, Ajax.ERROR_NOT_FOUND, etc.

    Automatic Error Handling
    ------------------------
    Uncaught Ajax errors automatically display via Modal.error():

    // No try/catch - error shows in modal automatically
    const user = await User_Controller.get_user(123);

    Global unhandled rejection handler detects uncaught Ajax errors and
    shows red danger modal with error details. This prevents silent failures.
    It recognises an Ajax error by the marker every one carries
    (error.__rsx_ajax_error === true), so it covers an error whatever promise
    chain carried it - a generated stub, Model.fetch(), an application's own
    async wrapper that let it propagate.

    Rsx_Form Error Handling
    -----------------------
    A form renders its own failures - there is nothing to write and nothing to
    catch. The endpoint is named on the <Rsx_Form> tag, form.submit() runs the
    one pipeline, and a failed submit resolves false with the messages already
    on screen:

    const result = await Modal.form({
        title: 'Add User',
        component: 'Add_User_Modal_Form',
    });

    if (result) { /* saved */ }

    Rsx_Form.render_error() is what it uses, and a host that caught an error
    itself (an edit modal whose record fetch rejected) may call it directly:
    - validation: inline field errors, plus the top alert, which ALWAYS renders
    - fatal/network/auth: a single alert in the form's <Form_Errors />

    NEVER try/catch a submit to "handle" a validation error - swallowing it
    before the renderer sees it is how a failed save comes to look successful.
    See form_conventions(3).

    Form_Utils Error Display
    ------------------------
    For non-Rsx_Form forms, use Form_Utils.apply_form_errors():

    try {
        const result = await Controller.save_user(form_data);
        await Modal.alert('User saved!');
    } catch (error) {
        if (error.code === Ajax.ERROR_VALIDATION) {
            await Form_Utils.apply_form_errors($form, error.metadata);
        } else {
            Rsx.render_error(error, '#error_container');
        }
    }

    Form_Utils.apply_form_errors() automatically:
    - Matches errors to fields by name attribute
    - Adds .is-invalid class and inline error text
    - Shows alert ONLY for errors that couldn't match to fields
    - No duplicate alerts for matched fields

    Generic Error Display
    ---------------------
    Rsx.render_error() displays errors in any container:

    // Display in specific container
    Rsx.render_error(error, '#error_container');

    // Display in form's error container (for Rsx_Form use form.render_error())
    Rsx.render_error(error, this.$sid('error'));

    Handles all error types:
    - fatal: Shows file:line and full message
    - validation: Shows bulleted list of unmatched validation errors
    - auth/network: Shows user-friendly message
    - generic: Shows error message in danger alert

    Modal Error Display
    -------------------
    For critical errors that need immediate attention:

    await Modal.error(error, 'Critical Error');

    - Shows red danger modal
    - Can stack over other open modals
    - Used automatically for uncaught Ajax errors
    - Displays error message in monospace pre format

WHO SEES FATAL-ERROR DETAIL

    The redaction is SERVER-SIDE, keyed on the CALLER, never on the mode alone:
    Rsx_Diagnostics::caller_sees_detail() is true only in development or debug mode
    AND for a caller that is a signed-in developer (login_users.is_developer), a
    request carrying a valid rsx:debug credential, or a loopback caller (the peer and
    every forwarded hop are local). A development-mode site may be public, so an
    anonymous caller is redacted there too. Strict production redacts for everybody.
    (The client's Modal display choice is a separate, additional gate.)

    The same predicate governs every channel: the Ajax and batch envelopes, the
    external API's internal_error, the full-page error screen and the Ignition debug
    page (rsx:man error_pages).

    Developer caller (development or debug mode)
    --------------------------------------------
    Fatal errors show:
    - Full exception message
    - File path and line number
    - SQL queries with parameter values
    - Stack trace (up to 10 frames)
    - Console debug messages

    Example display:
        Fatal Error

        SQLSTATE[23000]: Integrity constraint violation: 1048
        Column 'login_user_id' cannot be null (Connection: mysql,
        SQL: insert into `users` ...)

        vendor/laravel/framework/src/Illuminate/Database/Connection.php:829

    Everybody else
    --------------
    Fatal errors show:
    - Generic message: "An unexpected error occurred. Please try again."
    - An error_id (16 hex characters): error.error_id in the envelope
    - No file paths, SQL, backtrace, or exception message in the response body
    The full detail is logged server-side as "[error_id=<id>] ..." so a user's
    reference finds the trace.

    Not an endpoint
    ---------------
    A target that is no class, not a controller, or not an #[Ajax_Endpoint] fails
    with ONE message for a non-developer caller ("<Controller>::<action> is not an
    Ajax endpoint"), so the channel cannot be used to probe which class names exist.
    A developer caller gets the specific reason. It is a CODED not_found, never a
    reported server fault.

    Validation/auth errors show the same user-friendly messages to every caller.

TRANSPORT

    One Browser Transport, Every Mode
    ---------------------------------
    The client sends EVERY call to POST /_ajax/_batch - a lone call as a
    batch of one - with a JSON body batch_calls, an array of {call_id,
    controller, action, params}. Development, debug and production behave
    identically.

    config('rsx.ajax.batching') (default true; window.rsxapp.ajax_batching
    in every mode) decides only how many calls share one request:

        true    calls made in one synchronous turn share a request, at most
                20 per request (Ajax.MAX_BATCH_SIZE)
        false   every call is its own /_ajax/_batch request, answered the
                same way - each call is its own entry in the browser's
                network panel

    The response is a MAP keyed "C_<call_id>", each value being exactly the
    envelope for that call:

    {
        "C_0": {"_success": true, "_ajax_return_value": {...}, "_server_time": "..."},
        "C_1": {"_success": false, "error_code": "not_found", "reason": "...", "metadata": {...}, ...},
        "C_2": {"_success": false, "error_code": "fatal", "reason": "...", "metadata": {}, "error": {...}, ...}
    }

    HTTP status: Always 200
    Each result: Has own _success field, and its own error_code
    Client: Settles each call from its own key

    No Merging
    ----------
    Two identical calls are two calls. Every Ajax call is a POST and the
    transport cannot know that an endpoint is a read, so it never sends one
    call for two callers. Reads that are safe to share are coalesced where
    they are known to be reads: the ORM fetch (overlapping fetch() of the same
    model and id - rsx:man model_fetch) and jqhtml's load coordinator (the
    same component with the same args loading at the same time).

    Every Call Is Settled
    ---------------------
    A call always resolves or rejects - never stays pending:
    - an answer that does not carry the call rejects it with 'server_error';
    - a request that fails as a whole rejects every call it carried (HTTP
      5xx 'server_error', status 0 'network_error', otherwise 'generic');
    - a failure turning one call's value into models (a record whose class
      the bundle lacks) rejects THAT call, never the page or its siblings.
    A failure that refuses the whole REQUEST on the server - a CSRF mismatch,
    a fault outside any call - is answered with the same envelope under
    every call_id the batch named (side channels included), so each caller
    receives it.

    The Direct URL
    --------------
    POST /_ajax/<Controller>/<action> is answered with the bare envelope,
    for a request made by hand (curl, a shell test). It is a batch of one
    through the same per-call path. Its params are the request body exactly
    - the JSON object, or the form fields - with nothing added or removed
    and no query string merged.

    Per-Call Checks
    ---------------
    Each call, alone or batched, runs on the REAL request - the caller's
    address, headers, cookies and session - with only that call's params as
    its input, and request() and the Request facade answer that call's
    request while it runs. In order, for each call:

        1. Session lifetime (rsx.sessions.*). Once a call answers
           session_expired, every later call in the request answers the
           same envelope. A cookie naming a replaced session row answers
           session_expired with metadata.cause "retired".
        2. Staff site membership: a disabled membership ends the session
           and the call answers auth_required.
        3. The realm's Main::pre_dispatch (Portal_Main on the portal), once
           PER CALL, with $request the call's request and $params:

               controller   the endpoint's controller
               action       the endpoint's method
               _route       '/_ajax/:controller/:action'
               _method      'POST'
               _handler     the Ajax class

           A non-null answer refuses THAT call and no other. A coded result
           keeps its code and reason - return
           response_unauthorized('Account suspended') and the call rejects
           with 'unauthorized' and that message; any other non-null value
           (a redirect or page from a hook written for pages) answers
           'unauthorized' "This request was refused.". Nothing is ever
           rendered as a page.
        4. The endpoint: its realm and #[Auth] gates, the controller's
           pre_dispatch, the action.

    A gate denial answers 'auth_required' when nobody is signed in in the
    request's realm and 'unauthorized' when somebody is - the same split the
    page channel makes, so a page whose sign-in ended elsewhere gets the
    session-ended handling. Ajax::internal() throws AjaxAuthRequiredException
    / AjaxUnauthorizedException correspondingly.

    Each call is its own unit: its own Turnstile verification and its own
    revision transaction.

    What An Endpoint May Not Do
    ---------------------------
    - Return an HTTP response. A redirect(), view(), download or any other
      Symfony Response, View, Responsable or Renderable returned by the
      action or by its controller's pre_dispatch is a FAULT (fatal
      envelope), never a success. A controller pre_dispatch that redirects
      its pages returns null for an Ajax call or answers a coded result.
    - Leave a database transaction open. It is rolled back - whatever the
      call wrote inside it is gone - and the call answers a fault naming the
      endpoint. DB::transaction(fn) commits or rolls back for you.

    Flash And Console
    -----------------
    Pending flash alerts are read once, after the last call of a request,
    and ride on the LAST call's envelope; console_debug messages ride on the
    call that produced them.

    Refused Batches
    ---------------
    A batch is REFUSED WHOLE with HTTP 400 {"error": "..."} - nothing in it
    runs - when:
    - it carries more calls than config('rsx.ajax.batch_max_calls')
      (default 100; the error names the key);
    - it is not a non-empty array of calls;
    - a call has no call_id, one that is not a non-negative integer, or one
      repeated in the batch;
    - a call has no controller or action, or one that is not a PHP
      identifier, or params that are not an object.
    The client never sends such a batch.

TESTING

    Test Success Response
    ---------------------
    php artisan rsx:ajax Controller action --args='{"id":1}'

    Run as a user
    -------------
    php artisan rsx:ajax Controller action --user=<id|email> [--site=<id>]

    --user establishes the WHOLE identity the endpoint will see - the login
    identity, the site, and the site user (users.id) resolved for that login
    identity on that site - through Session::impersonate(). With no --site the
    site is the one the login identity has a users row on; a login identity with
    rows on several sites, or on none, is refused with error_type site_required
    until --site chooses. A login identity with no users row on the chosen site
    is a real state and runs with Session::get_user_id() null; --show-context
    prints all three parts, that null included, so a user-scoped endpoint that
    answers "nothing" is never a silent surprise.

    Test Validation Error
    ---------------------
    php artisan rsx:ajax Controller action --args='{"id":""}'

    Test Fatal Error
    ----------------
    Trigger exception in endpoint (e.g., invalid SQL, missing file)

    Test Network Error
    ------------------
    Stop PHP-FPM/nginx, try Ajax call from browser

CONSOLE DEBUG MESSAGES

    Add debug output to Ajax responses:

    console_debug('channel', $var1, $var2);

    In response:
    {
        "_success": true,
        "_ajax_return_value": {...},
        "console_debug": [
            ["channel", [arg1, arg2]],
            ["log", ["message"]]
        ]
    }

    JavaScript automatically logs these to browser console.

COMMON PATTERNS

    Simple Data Retrieval
    ----------------------
    #[Ajax_Endpoint]
    public static function get_data(Request $request, array $params = []): array
    {
        return ['items' => Item::all()->toArray()];
    }

    Validation with Response Helper
    --------------------------------
    #[Ajax_Endpoint]
    public static function save(Request $request, array $params = []): array
    {
        if (empty($params['email'])) {
            return response_error(Ajax::ERROR_VALIDATION, [
                'email' => 'Email is required'
            ]);
        }

        $user = User::create($params);
        return ['id' => $user->id];
    }

    Let Database Errors Bubble
    ---------------------------
    #[Ajax_Endpoint]
    public static function save(Request $request, array $params = []): array
    {
        $user = new User();
        $user->name = $params['name'];
        $user->save();  // If this fails, exception bubbles naturally

        return ['id' => $user->id];
    }
