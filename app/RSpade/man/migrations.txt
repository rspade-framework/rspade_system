MIGRATIONS(7)                    RSX Framework Manual                    MIGRATIONS(7)

NAME
       migrations - Database migration system with raw SQL enforcement

SYNOPSIS
       php artisan make:migration:safe <name>
       php artisan migrate
       php artisan migrate:status
       php artisan rsx:db:rebuild_provision_cache_snapshot
       php artisan rsx:database_and_storage_reset --yes [--force] [--no-migrate]

DESCRIPTION
       The RSX framework enforces a forward-only migration strategy using raw SQL
       statements. Laravel's Schema builder is prohibited to ensure clarity,
       auditability, and prevent hidden behaviors.

       The migrate command automatically handles snapshot protection wherever that
       protection can actually be performed - no manual steps required. See SNAPSHOT
       PROTECTION for the three conditions, and for what happens where they do not
       hold.

PHILOSOPHY
       1. Forward-only migrations - No rollbacks, no down() methods
       2. Raw SQL only - Direct MySQL statements, no abstractions
       3. Fail loud - Migrations must succeed or fail with clear errors
       4. Automatic safety - a snapshot is taken wherever one can be taken, and the
          run says out loud when one cannot

MIGRATION RULES

   Schema Builder Prohibition
       All migrations MUST use DB::statement() with raw SQL. The following are prohibited:

       - Schema::create()
       - Schema::table()
       - Schema::drop()
       - Schema::dropIfExists()
       - Schema::rename()
       - Blueprint class usage
       - $table-> method chains

       The migration validator automatically checks for these patterns and will prevent
       migrations from running if violations are found.

   Required Table Structure
       ALL tables MUST have:

           id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY

       This is non-negotiable. Every table needs this exact ID column (SIGNED for
       easier future migrations).

   Data Type Standards - What You Need to Know
       The framework automatically normalizes data types during migration, so you can
       use simpler types and let the system handle optimization:

       What You Can Use (System Auto-Converts):
       - INT -> automatically becomes BIGINT
       - TEXT -> automatically becomes LONGTEXT
       - FLOAT -> automatically becomes DOUBLE
       - Any charset -> automatically becomes UTF8MB4
       - created_at/updated_at -> automatically added with proper defaults
       - created_by_id/_type, updated_by_id/_type -> automatically added
       - deleted_by_id/_type -> automatically added for soft-delete tables

       What You MUST Be Careful About:
       - Foreign key columns - Must match the referenced column type exactly
         Example: If users.id is BIGINT, then orders.user_id must be BIGINT
       - TINYINT(1) - Preserved for boolean values, won't be converted
       - Column names ending in _id are assumed to be foreign keys

       Recommended for Simplicity:
       - Just use INT for integers (becomes BIGINT automatically)
       - Just use TEXT for long content (becomes LONGTEXT automatically)
       - Just use FLOAT for decimals (becomes DOUBLE automatically)
       - Don't add created_at/updated_at (added automatically)
       - Don't add created_by_id/_type or updated_by_id/_type (added automatically)

   No Application Code (MIGRATION-MODEL-01)
       A migration is a FORWARD-ONLY HISTORICAL RECORD that must replay cleanly from
       scratch forever. A model class is CURRENT CODE that gets renamed and deleted.
       Naming one couples the two, and the day that class is retired a from-scratch
       replay of the whole chain hard-fails at a file nobody has touched in a year.

       A migration therefore contains no model class, no Type_Ref_Registry, and no
       service - only raw SQL and plain PHP. Prohibited:

       - use imports of a *_Model class or of Type_Ref_Registry
       - Type_Ref_Registry:: anything (class_to_id() is the offender in the field:
         it validates the name against the LIVE MANIFEST and refuses a class that no
         longer exists)
       - a static call, new, instanceof or ::class on a *_Model symbol

       A class name written as a STRING is data, not a symbol, and is never flagged -
       that is what makes the resilient pattern work. Resolve a polymorphic type-ref
       id with a get-or-create against _type_refs, class name as a string, table name
       hardcoded:

           $type_ref_id = function (string $class_name, string $table_name): int {
               $existing = DB::select(
                   "SELECT id FROM _type_refs WHERE class_name = ?", [$class_name]
               );
               if (!empty($existing)) {
                   return (int) $existing[0]->id;
               }
               DB::statement(
                   "INSERT INTO _type_refs (class_name, table_name, created_at, updated_at)
                    VALUES (?, ?, NOW(3), NOW(3))",
                   [$class_name, $table_name]
               );
               return (int) DB::getPdo()->lastInsertId();
           };

           $contact_id = $type_ref_id('Contact_Model', 'contacts');
           DB::statement("
               UPDATE activities SET eventable_type = {$contact_id}
               WHERE eventable_type = 'Contact_Model'
           ");

       Ids are still never hardcoded: the closure resolves or creates the row at
       replay time, so it is correct on a fresh install and in every environment.

       THE ONE EXCEPTION is data seeding that genuinely needs model BEHAVIOUR raw SQL
       cannot reproduce - a file pipeline, an encryption cast, a factory with side
       effects. That migration is knowingly coupled to code that may be deleted, and
       says so in its docblock:

           /**
            * @MIGRATION-MODEL-01-EXCEPTION <why raw SQL cannot do this>
            */

       The rationale is REQUIRED - a bare marker is itself a violation of the rule.
       Schema work and type-ref lookups are never the exception; convert those.

       Enforced by php artisan rsx:check, severity high. The rule reads the migration
       runner's own file list, so every migration directory and nested subdirectory is
       covered. Detection is over the PHP token stream: a class name in a comment or a
       string literal is never a violation.

   down() Method Removal
       The migration system automatically removes down() methods from migration files.
       Migrations are forward-only - database changes should never be reversed.

AUTOMATIC NORMALIZATION

   What migrate:normalize_schema Does For You
       After migrations run, the normalize_schema command automatically:

       1. Type Conversions:
          - INT columns -> BIGINT (except TINYINT(1) for booleans)
          - BIGINT UNSIGNED -> BIGINT SIGNED
          - TEXT -> LONGTEXT
          - FLOAT -> DOUBLE
          - All text columns -> UTF8MB4 character set

       2. Required Columns Added:
          - created_at TIMESTAMP(3) DEFAULT CURRENT_TIMESTAMP(3)
          - updated_at TIMESTAMP(3) DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE
          - created_by_id BIGINT NULL / created_by_type BIGINT NULL
          - updated_by_id BIGINT NULL / updated_by_type BIGINT NULL
          - deleted_by_id BIGINT NULL / deleted_by_type BIGINT NULL
            (only for soft-delete tables - a hard delete leaves no row)

       3. Indexes Added:
          - INDEX on created_at
          - INDEX on updated_at
          - INDEX on site_id (for models extending Rsx_Site_Model_Abstract)
          - INDEX on id+version (for Versionable models)

       4. Model-Specific Columns:
          - site_id BIGINT - for models extending Rsx_Site_Model_Abstract
          - version INT(11) DEFAULT 1 - for Versionable/Ajaxable models

       5. Precision Upgrades:
          - All DATETIME/TIMESTAMP columns -> precision (3) for milliseconds

       This means you can write simpler migrations and let the system handle the
       optimization and standardization. The only time you need to be explicit about
       types is when creating foreign key columns that must match their referenced
       column exactly.

   POST-NORMALIZATION APP STEPS
       normalize_schema runs TWICE in a migrate - once after each individual
       migration, and once at the end over the whole schema. The app hook hangs off
       the SECOND one, the POST-migration pass: when that pass succeeds, migrate
       fires the action event

           migrate.normalize_schema.complete

       with no payload, from Maint_Migrate::execute_migrations(), before the initial
       user and before the revision dictionary. The schema is therefore at its final
       framework-normalized tip, and the run is still inside the migration window -
       where a snapshot was taken, it still covers whatever a handler does, so a
       handler that throws rolls the whole migration back.

       An application uses it for its own "columns every table of mine must have"
       pass, computed instead of listed. A hand-maintained per-table migration list
       stops being complete the moment somebody adds a table, and nothing reports it.

       Example - stamping import provenance on every application table, so an
       importer has an idempotency key and every imported row records where it came
       from:

           namespace Rsx\Handlers;

           use Illuminate\Support\Facades\DB;

           class Schema_Normalize_Handlers
           {
               #[OnEvent('migrate.normalize_schema.complete')]
               public static function ensure_import_columns(): void
               {
                   $database = DB::connection()->getDatabaseName();

                   $tables = DB::select(
                       "SELECT table_name AS name
                          FROM information_schema.tables
                         WHERE table_schema = ? AND table_type = 'BASE TABLE'",
                       [$database]
                   );

                   foreach ($tables as $table) {
                       $name = $table->name;

                       // A leading underscore marks a SYSTEM table - framework
                       // property, never an application's to alter. The same
                       // convention governs columns: a _-prefixed COLUMN is a system
                       // column. See rsx:man database_schema_architecture.
                       if (str_starts_with($name, '_')) {
                           continue;
                       }

                       $existing = DB::select(
                           "SELECT column_name AS name
                              FROM information_schema.columns
                             WHERE table_schema = ? AND table_name = ?
                               AND column_name IN ('ext_src', 'ext_ref')",
                           [$database, $name]
                       );
                       $have = array_column($existing, 'name');

                       $clauses = [];
                       if (!in_array('ext_src', $have, true)) {
                           $clauses[] = "ADD COLUMN ext_src VARCHAR(64) NULL";
                       }
                       if (!in_array('ext_ref', $have, true)) {
                           $clauses[] = "ADD COLUMN ext_ref VARCHAR(64) NULL";
                       }
                       if (!$clauses) {
                           continue;
                       }

                       // The index rides along with the columns, in the same ALTER,
                       // so it exists exactly when they do.
                       $clauses[] = "ADD INDEX idx_ext_ref (ext_ref, ext_src)";

                       DB::statement("ALTER TABLE `{$name}` " . implode(', ', $clauses));
                   }
               }
           }

       The example is illustrative. The hook enforces nothing about column names or
       shapes - the columns above are unprefixed because they are the APPLICATION's
       columns, and an application names its own.

       Rules for a handler on this event:

       - IDEMPOTENT BY CONSTRUCTION. It runs on every migrate, including a run with
         nothing to migrate. Read what is already there (information_schema, raw SQL)
         and emit only the difference; never assume a previous run's state.
       - ONE ALTER TABLE per table. Collect every clause for a table and issue them
         together - a table rebuild is expensive and there is no reason to pay for it
         more than once per table per run.
       - NEVER touch a table whose name begins with an underscore. That prefix marks
         framework-owned system tables, and the same convention makes a _-prefixed
         COLUMN a system column (rsx:man database_schema_architecture).
       - LET IT THROW. Nothing catches the handler; on the snapshot-protected path a
         throw rolls the migration back, which is the correct outcome for a schema
         step that could not be completed.
       - Handlers run INLINE in the migrate process. Long work makes every migrate
         long; that is the handler's own cost to own.

       When at least one handler is registered, migrate prints one line naming the
       count. With none, it says nothing. The full event entry, with the position
       contract, is rsx:man event_hooks (FRAMEWORK EVENT CATALOG, Migrate Events).

VALIDATION SYSTEM

   Automatic Validation
       When running migrations in development mode, the system automatically:

       1. Validates all pending migrations for Schema builder usage
       2. Removes down() methods if present
       3. Reports violations with colored output and remediation advice
       4. Stops at the first violation to allow correction

   Validation Output
       When a violation is detected, you'll see:

           [ERROR] Migration Validation Failed

           File: 2025_09_30_create_example_table.php
           Line: 28

           Violation: Found forbidden Schema builder usage: Schema::create

           Code Preview:
           ----------------------------------------
           Schema::create('users', function (Blueprint $table) {
               $table->id();
               $table->string('name');
           });
           ----------------------------------------

           Remediation: Use DB::statement("CREATE TABLE...") instead

           Example:
             DB::statement('CREATE TABLE users (
                 id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
                 name VARCHAR(255),
                 created_at TIMESTAMP NULL DEFAULT NULL
             )');

   Code-Quality Validation
       The automatic validator above runs at migrate time and covers the Schema
       builder and down(). The self-containment rule is a code-quality rule instead:

           MIGRATION-MODEL-01   no model class, no Type_Ref_Registry
                                (php artisan rsx:check - see MIGRATION RULES)

       It is checked by rsx:check rather than by the runner because a coupled
       migration runs FINE today - it fails years later, on a replay, after the class
       it names has been deleted. Catching it at authoring time is the only moment
       the fix is cheap.

MIGRATION LOCATIONS AND ORDERING

       Migrations live under two base directories:

           database/migrations         Framework and system migrations
           rsx/resource/migrations     Application migrations

       Files are discovered RECURSIVELY beneath each base directory, so a nested
       subdirectory (for example database/migrations/rspade/ for app-specific
       framework migrations) is included automatically.

       Across ALL directories, the complete set of migration files is ordered by
       the migration's TIMESTAMP BASENAME (the filename), not by directory. A
       migration in one directory therefore runs before/after a migration in
       another directory purely according to its timestamp. This is what lets a
       migration that adds a foreign key reference an earlier-timestamped table
       that lives in a different migration directory.

       Laravel records (and the .migration_whitelist tracks) migrations by
       basename, so the basename is the single canonical identity used for
       ordering, de-duplication, and "already ran" checks. Basenames must be
       unique across all migration directories.

MIGRATION WORKFLOW

   Development Mode (RSX_MODE=development)
       Simply run:

           php artisan migrate

       In the RSpade DEVELOPMENT container, against a local database, the command
       automatically:
       1. Creates a database snapshot before running migrations
       2. Runs all pending migrations with validation
       3. Runs schema quality checks
       4. On success: commits changes, regenerates constants, recompiles bundles
       5. On failure: automatically rolls back to snapshot

       Failed migrations restore the database to its pre-migration state. Fix your
       migration files and run "php artisan migrate" again.

       Development mode OUTSIDE any RSpade container is REFUSED, with the container
       invocation printed. Development mode inside a PRODUCTION-target container, or
       pointed at an external database host, runs bare - see SNAPSHOT PROTECTION.

   Debug/Production Mode (RSX_MODE=debug or production)
       Run:

           php artisan migrate

       In these modes:
       - No snapshot protection and no automatic rollback
       - Migrations run directly against the database
       - Schema normalization still runs
       - Constants and bundles are NOT regenerated (already done in development)

       Ensure migrations are thoroughly tested in development before running in
       debug/production modes.

   Framework-Only Migrations
       To run only framework migrations (system/database/migrations):

           php artisan migrate --framework-only

       This skips snapshot protection regardless of mode.

SNAPSHOT PROTECTION

       Snapshot protection is PHYSICAL, not logical. It stops the local supervised
       mysqld, copies /var/lib/mysql, and - when a migration fails - wipes that
       directory and copies the snapshot back. It is performed ONLY where all three
       of these hold:

       1. RSX_MODE=development.
       2. The RSpade DEVELOPMENT container - /.rspade_container_dev, not merely
          /.rspade_container. The PRODUCTION container carries the latter but ships
          mysql-client ONLY: there is no mysqld to stop and no data directory to
          copy, and `supervisorctl status mysql` there answers "no such process".
       3. A LOCAL database host - localhost, 127.0.0.1, ::1, or a configured unix
          socket. Pointed at an external database, /var/lib/mysql is not the
          database being migrated at all.

       Two further things suppress the snapshot for a given RUN even where the
       mechanism is available: --framework-only (a schema-only subset used by
       tooling) and the framework-internal --_no-snapshot (a caller that already
       holds a full dump, e.g. rsx:db:rebuild_provision_cache_snapshot).

       ANYWHERE ELSE THE RUN PROCEEDS BARE, and prints every reason protection is
       off, so an operator can tell WHICH condition disabled the undo:

           [WARNING]  Running WITHOUT snapshot protection - a failed migration will
           NOT be rolled back.
              - this is a production-target RSpade container (/.rspade_container_dev
                absent), which ships mysql-client only - there is no local mysqld to
                stop and no datadir to copy

       WHY THE PRODUCTION CONTAINER NO LONGER SNAPSHOTS. It never could: that image
       has no mysqld. The dangerous half was never the snapshot but the ROLLBACK - a
       restore into a /var/lib/mysql that is not the live database would report a
       successful rollback while the real database stayed broken. A false rollback is
       worse than no rollback, so a rollback that cannot be performed is neither
       attempted nor advertised.

       php artisan migrate:restore, which performs that same restore by hand after an
       INTERRUPTED migrate, applies the identical predicate and refuses - naming the
       condition, and leaving the migration flag and any snapshot untouched - wherever
       protection is unavailable.

THE SCHEMA CACHE

       A fresh install replays every migration ever written to arrive at a schema
       that is, by definition, already known. The schema cache records that known
       end state once, so an empty database RESTORES it and then applies only the
       migrations newer than the cache.

   The two artifacts

           rsx/resource/db/schema_cache.sql.gz    a gzipped mysqldump of a database
                                                  migrated from zero. NO user rows -
                                                  the first-run screen creates user 1
                                                  after the restore.
           rsx/resource/db/uploads_cache.tar.gz   the content-addressed blob store's
                                                  contents at that same point (what
                                                  the data-seed migrations wrote).
                                                  Relative paths inside the archive,
                                                  so it extracts into any blob root.
           rsx/resource/db/README.md              regenerated with them.

       resource/ is manifest-invisible and SHIPS with the application, so the cache
       travels with the code whose migrations produced it.

   Building it - php artisan rsx:db:rebuild_provision_cache_snapshot

       DEVELOPMENT MODE ONLY. It refuses in debug and production: a sealed build's
       source tree is immutable and its services are serving traffic, and neither
       the wipe nor the rewritten artifacts belong there.

       The build runs against an EMPTY database and an EMPTY blob store, which are
       this developer's own - so it backs them up first:

           [1/7]  Enter maintenance mode (reason "schema cache build"). The real
                  mechanism: task workers are killed, then realtime, fpc-proxy,
                  php-fpm, rsx-lockd and redis stop. MySQL deliberately does not.
           [2/7]  Dump the live database to
                  storage/rsx-tmp/db_cache/live_db.sql.gz, and MOVE the blob store
                  to its sibling <blob_root>_tmp, leaving an empty store behind.
           [3/7]  DROP and CREATE the database.
           [4/7]  migrate, with --_no-initial-user (the cache carries no account)
                  and --_no-snapshot (see below).
           [5/7]  Write the two artifacts (and the README) into rsx/resource/db.
           [6/7]  DROP and CREATE again; empty the cache-build blob store.
           [7/7]  Restore the live database from the dump, move <blob_root>_tmp
                  back, DELETE THE DUMP LAST, and lower maintenance.

       migrate's own .migrating flag is NOT raised: it belongs to the datadir
       snapshot path, which step 4 skips, and the maintenance window already
       provides everything it would buy.

       WHY NO DATADIR SNAPSHOT. The snapshot exists to make a bad migration
       undoable. Step 4 migrates a database created empty one step earlier, and the
       only data worth protecting is already in the live dump - so the snapshot
       would stop MySQL and copy the whole datadir to protect nothing.

   The safety rules

       THE BACKUP IS COMPLETE BEFORE ANYTHING IS DESTROYED. The dump is written to
       a .partial and renamed on success; the blob store is MOVED (a rename), not
       copied. No destructive step runs until its own backup is in place, so an
       interrupt before that point has nothing to recover.

       THE BACKUP IS DELETED LAST. Every restore action is idempotent and
       re-runnable for exactly as long as the dump is still on disk.

       EXISTING BACKUPS ARE NEVER OVERWRITTEN. A backup already sitting in
       storage/rsx-tmp/db_cache/ was left by an interrupted run and holds the LIVE
       data; whatever is in the database and blob store now is that run's build
       residue. So the command prints that it found them, uses them as the restore
       source, and takes only the MISSING half - the two halves are independent.

       CTRL-C AND EXCEPTIONS RUN THE SAME RECOVERY. A SIGINT/SIGTERM handler turns
       the interrupt into a throw; the recovery recreates the database, restores the
       dump, clears the build store, moves the backup back, and only then deletes
       the dump. If recovery itself fails it leaves the backups in place, names
       them, keeps the maintenance window UP, and tells you that re-running
       rsx:db:rebuild_provision_cache_snapshot completes the restore from exactly those backups.

       MAINTENANCE MODE STAYS DOWN WHILE A BACKUP EXISTS. php artisan
       rsx:maintenance:disable REFUSES while storage/rsx-tmp/db_cache/live_db.sql.gz
       or the blob backup named by storage/rsx-tmp/db_cache/.in_progress is present -
       bringing php-fpm up over cache-build scratch data would serve an application
       that has lost its data. Step 7 deletes the backups BEFORE it lowers the
       window, so the refusal is already false on the happy path and no override
       token exists. --force is the deliberate operator override. See
       rsx:man maintenance_mode.

   Restoring it - the initial provision

       php artisan migrate restores the cache when BOTH are true:

           - the database has NO TABLES AT ALL (not "no migrations table", not "no
             rows" - zero tables), which is precisely the fresh-clone state, and
           - rsx/resource/db/schema_cache.sql.gz exists.

       It streams the dump back (progress visible via bin/mysqlpv), extracts the
       uploads archive OVER the blob root - never clearing it first, because the
       store is content-addressed and identical hashes cannot collide - and then
       CONTINUES with the ordinary run: pending migrations newer than the cache
       apply, both normalize passes run, and the initial user is created as usual.

       Any other state is exactly the historic behaviour. A non-empty database is
       never restored over. A missing cache is not an error - it is every
       application that has never run the dump command.

       --framework-only is excluded: it migrates a schema-only subset for tooling,
       and the cache is the whole application's schema.

   When to regenerate

       RARELY, AND ONLY WHEN THE OPERATOR ASKS FOR IT BY NAME. Every few months is
       the expected cadence.

       A STALE CACHE IS NOT A BUG. Migrations newer than the cache apply on top of
       it, which is the designed behaviour - the cache is a speed optimisation, never
       a correctness requirement. "The cache is out of date" is not a reason to
       rebuild it, and rebuilding is never a step inside some other task.

       Two reasons it is deliberate rather than routine: the build takes the
       application down, drops and recreates the developer's database and empties the
       blob store (restoring both afterwards); and each run rewrites roughly half a
       megabyte of committed binary, so casual regeneration churns history for no
       benefit.

       AI AGENTS: do not run rsx:db:rebuild_provision_cache_snapshot, and do not propose it as a step. See
       app/RSpade/Commands/CLAUDE.md.

RESETTING THE DATA

       php artisan rsx:database_and_storage_reset --yes [--force] [--no-migrate]

       Returns the application to the FRESH-INSTALL STATE: every table in the
       application database dropped, every file under the three configured storage
       roots deleted, then migrate. It exists for iterating on a bulk import, where
       the same import is run, inspected, corrected and re-run until it is right and
       every cycle needs a zero state to run against.

       NOT rsx:clean, which resets the system/ tree. This resets the DATA. The names
       are deliberately dissimilar so an operator reaching for one cannot land on the
       other.

   The two-flag gate

       --yes            required always. Without it the command prints the whole
                        consequence in plain language, exits 1, and destroys nothing.
       --force          required ADDITIONALLY when the box is running a sealed
                        production build - the same escape hatch, in the same shape,
                        as the guard on rsx:clean.
       --no-migrate     leave the schema dropped instead of re-migrating, for an
                        operator who intends to restore a dump.

       Nothing makes the command inaccessible: a command an operator cannot run is a
       command they work around. What stands between them and the wipe is that the
       refusal makes them READ WHAT THEY ARE AGREEING TO first. It names every table,
       every business record and every user account and login; the actual uploaded
       bytes under each root; that there is no undo from inside the application; and
       the flag spelled exactly as it must be typed. The refusal goes to stderr and
       exits 1.

   What it touches, and what it does not

       Dropped:   every table in the application database - not truncated, DROPPED,
                  so the re-migrate rebuilds the schema rather than leaving it at
                  whatever shape the last run produced.
       Emptied:   the three roots Rsx_File_Paths resolves - the content-addressed blob
                  store (storage/uploads), the thumbnail cache and the rendition
                  cache. The DIRECTORIES and their permissions survive; the contents
                  do not.
       Untouched: everything else. Never storage/logs, never the framework's own
                  storage, never system/, never .env.

   Where it lands

       A database with NO TABLES AT ALL is exactly the state that makes migrate take
       the fresh-install path (see THE SCHEMA CACHE): it restores the shipped cache
       and then applies whatever migrations are newer. So the landing point is the
       fresh-install state, not "empty" - and user 1 arrives the way it always does,
       from RSPADE_DEFAULT_* or the first-run screen.

       The child migrate is spawned with the internal no-snapshot flag: the reset owns
       the snapshot, and a second one would copy a datadir already copied and delete
       the copy the reset is still relying on.

   The snapshot protects the OPERATION, not your data

       Where the datadir snapshot can be taken at all (SNAPSHOT PROTECTION - the same
       three conditions, the same predicate), the reset takes it before the drop. A
       failed wipe or a failed migrate rolls the DATABASE back and the command exits
       1, exactly as migrate does; an interrupt (SIGINT/SIGTERM) takes the same path.
       Where it cannot be taken, the run says so and names every reason.

       IT IS NOT AN UNDO. A SUCCESSFUL reset commits - which is to say deletes - the
       snapshot, and the deleted FILES were never in it: there is no filesystem
       snapshot, so a file this command removes is gone at the moment it is removed,
       failure or success. After a successful reset the only route back is a database
       backup and a copy of the file store that you took BEFORE running it.

   The run

       The command raises the REAL maintenance window for its duration (reason: data
       reset) and lowers it on every exit path, so web traffic gets a 503 and
       automated task runners are refused while the database underneath them is being
       replaced. It refuses to be invoked through $this->call() from another command,
       for the same reason rsx:clean does: it drops the database the calling process
       is connected to.

       It ends with the blast radius in one line, because a destructive command owes
       the operator a record of what it destroyed:

           [OK] Dropped 62 tables, removed 1743 files (4.21 GB freed); migrated to
                the fresh-install state.

POST-MIGRATE STEPS

       Once the migrations themselves have run, migrate performs these steps IN THIS
       ORDER. All of them run on both paths - snapshot-protected and bare - and all
       of them run before the snapshot is committed, so a failure in any of them
       rolls the run back where a snapshot was taken.

       1. THE POST-MIGRATION NORMALIZE PASS - migrate:normalize_schema over the whole
          schema, adding the framework's required columns and indexes to tables the
          run just created. A failure here is a migration failure.

       2. migrate.normalize_schema.complete - the action event an application hooks
          for its own schema steps, fired with no payload. See POST-NORMALIZATION APP
          STEPS above and rsx:man event_hooks. One line when handlers exist, silence
          otherwise.

       3. THE INITIAL USER - create_initial_user_if_needed() creates the application's
          first account from RSPADE_DEFAULT_* when the database has none, firing
          user.initial.created (source post_migrate). Deliberately NOT a migration: it
          runs model and application handler code, which only works against the
          current schema, so it belongs at the tip rather than at a fixed point in
          history. See rsx:man initial_user.

       4. THE REVISION DICTIONARY - a new revision-history compression dictionary when
          the current one is missing or older than
          config('rsx.revisions.dictionary_max_age_days') - silent inside that
          cadence, one [OK] Revision dictionary N built (T tokens) line when it builds
          - because the dictionary is derived from the finished schema's column names
          and the models' enum labels and is only correct once the schema is at its
          tip. Skipped on a --framework-only run, which migrates a schema-only subset
          with none of the application's tables in it.

       5. THE CACHE CLEAR - every successful run, snapshot-protected or bare, ends by
          clearing the build-scoped cache (and so does php artisan migrate:restore,
          whose restore leaves the cache describing a schema that no longer exists).

MIGRATION EXAMPLES

   Creating a Table (Simple Version - Recommended)
       public function up()
       {
           // You can write this simple version - system auto-normalizes types
           DB::statement("
               CREATE TABLE products (
                   id INT NOT NULL AUTO_INCREMENT PRIMARY KEY,  -- becomes BIGINT
                   name VARCHAR(255) NOT NULL,
                   description TEXT,                             -- becomes LONGTEXT
                   price DECIMAL(10,2) NOT NULL DEFAULT 0.00,
                   stock_quantity INT NOT NULL DEFAULT 0,        -- becomes BIGINT
                   is_active TINYINT(1) NOT NULL DEFAULT 1,      -- stays TINYINT(1)
                   category_id INT NULL,                         -- becomes BIGINT
                   INDEX idx_category (category_id),
                   INDEX idx_active (is_active)
                   -- No need for created_at/updated_at - added automatically
               )
           ");
       }

   Creating a Table (Explicit Version - If You Prefer)
       public function up()
       {
           // Or be explicit about types if you prefer
           DB::statement("
               CREATE TABLE products (
                   id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
                   name VARCHAR(255) NOT NULL,
                   description LONGTEXT,
                   price DECIMAL(10,2) NOT NULL DEFAULT 0.00,
                   stock_quantity BIGINT NOT NULL DEFAULT 0,
                   is_active TINYINT(1) NOT NULL DEFAULT 1,
                   category_id BIGINT NULL,
                   created_at TIMESTAMP NULL DEFAULT NULL,
                   updated_at TIMESTAMP NULL DEFAULT NULL,
                   INDEX idx_category (category_id),
                   INDEX idx_active (is_active),
                   INDEX idx_created (created_at)
               ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
           ");
       }

   Adding Columns
       public function up()
       {
           DB::statement("ALTER TABLE users ADD COLUMN age BIGINT NULL AFTER email");
           DB::statement("ALTER TABLE users ADD INDEX idx_age (age)");
       }

   Modifying Columns
       public function up()
       {
           // Change column type
           DB::statement("ALTER TABLE products MODIFY COLUMN price DECIMAL(12,2)");

           // Rename column
           DB::statement("ALTER TABLE users CHANGE COLUMN username user_name VARCHAR(100)");

           // Add default value
           DB::statement("ALTER TABLE posts ALTER COLUMN status SET DEFAULT 'draft'");
       }

   Managing Indexes
       public function up()
       {
           // Add index
           DB::statement("CREATE INDEX idx_email ON users (email)");

           // Add unique index
           DB::statement("CREATE UNIQUE INDEX idx_unique_slug ON posts (slug)");

           // Add composite index
           DB::statement("CREATE INDEX idx_user_status ON orders (user_id, status)");

           // Drop index
           DB::statement("DROP INDEX idx_old_index ON table_name");
       }

   Foreign Keys (IMPORTANT - Match Types Exactly)
       public function up()
       {
           // CRITICAL: Foreign key columns must match referenced column type
           // If users.id is BIGINT, orders.user_id must also be BIGINT

           // First, ensure the column has correct type (if not already created)
           DB::statement("ALTER TABLE orders ADD COLUMN user_id BIGINT NULL");

           // Then add the foreign key constraint
           DB::statement("
               ALTER TABLE orders
               ADD CONSTRAINT orders_user_fk
               FOREIGN KEY (user_id) REFERENCES users(id)
               ON DELETE CASCADE
           ");

           // To drop a foreign key
           DB::statement("ALTER TABLE orders DROP FOREIGN KEY orders_user_fk");
       }

       // Note: After normalization, all id columns are BIGINT, so foreign keys
       // should always use BIGINT to avoid type mismatches

   Data Migrations
       public function up()
       {
           // Simple update
           DB::statement("UPDATE users SET role = 'member' WHERE role IS NULL");

           // Complex migration with temporary column
           DB::statement("ALTER TABLE orders ADD COLUMN total_new DECIMAL(10,2)");
           DB::statement("UPDATE orders SET total_new = quantity * price");
           DB::statement("ALTER TABLE orders DROP COLUMN total");
           DB::statement("ALTER TABLE orders CHANGE total_new total DECIMAL(10,2)");
       }

ERROR MESSAGES

   "Migration validation failed: Schema builder usage detected"
       Your migration uses Laravel's Schema builder. Rewrite using DB::statement()
       with raw SQL.

   "Unauthorized migrations detected!"
       Migration files exist that weren't created via make:migration:safe.
       Recreate them using the proper command.

   "Development-mode migrations run inside the RSpade container."
       You're in development mode but not in an RSpade container. The refusal prints
       the exact docker compose invocation to use instead. A deployed application
       migrates in place normally; this refusal is development mode only.

   "Snapshot restore is not available here: <reason>"
       migrate:restore found an interrupted migration but this environment cannot
       perform the restore (see SNAPSHOT PROTECTION). The migration flag and the
       snapshot are left exactly as they are.

AUTOMATIC ROLLBACK

   Where snapshot protection is engaged (see SNAPSHOT PROTECTION), if a migration
   fails:
   1. The error is displayed
   2. Database is automatically restored to pre-migration state
   3. You can fix the migration and run "php artisan migrate" again

   This happens automatically - no manual intervention required.

   Where protection is NOT engaged, there is no rollback of any kind, and the run
   says so before it starts.

SECURITY CONSIDERATIONS

   SQL Injection
       When using dynamic values in migrations, always use parameter binding:

       CORRECT:
       DB::statement("UPDATE users SET status = ? WHERE created_at < ?", ['active', '2025-01-01']);

       WRONG:
       DB::statement("UPDATE users SET status = '$status' WHERE created_at < '$date'");

   Production Safety
       - Always test migrations in development first
       - Keep migrations small and focused
       - Never reference models or services in migrations
       - Migrations must be self-contained and idempotent where possible

DEBUGGING

   Viewing Pending Migrations
       php artisan migrate:status

   Testing a Migration
       In development mode, just run:
           php artisan migrate

       If it fails, the database is automatically restored. Fix the migration
       and try again.

   Common Issues
       - "Class not found" - Don't reference models in migrations
       - "Syntax error" - Check your SQL syntax, test in MySQL client first
       - "Foreign key constraint" - Ensure referenced table/column exists
       - "Duplicate column" - Check if column already exists before adding
