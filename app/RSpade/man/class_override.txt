# Class Override System

## NAME

class_override - Replace a framework class with an application-specific one

## SYNOPSIS

A CORE MODEL is EXTENDED. Every framework model is an abstract base carrying its
whole implementation plus a concrete shell that declares nothing; the override
declares only what it changes:

    # rsx/models/user_model.php
    namespace Rsx\Models;

    class User_Model extends User_Model_Abstract
    {
        // only the members this application changes
    }

ANY OTHER framework class is COPIED under the same class name:

    cp system/app/RSpade/Core/Files/File_Attachment_Icons.php \
       rsx/lib/file_attachment_icons.php
    # then change the namespace and customize the copy

Either way the framework file stays exactly where it is, SHADOWED: the manifest
takes it out of the live index, and the rsx/ class answers for the framework
class name - simple name and fully-qualified name alike - from then on.

    php artisan rsx:overrides:list     # every override in force

## DESCRIPTION

An application customizes framework behavior without editing system/, and an
override writes nothing under system/ either. When a class of the same simple
name exists in both rsx/ and app/RSpade/, the manifest:

1. Records the framework file as SHADOWED in its override map. The file is not
   moved, renamed or edited; it leaves the live index and is never loaded.
2. Uses the rsx/ version as the authoritative class.
3. Hands the map to the class override loader, which answers the framework
   FQCN with the rsx/ class in every process (HOW REFERENCES KEEP RESOLVING).

Unlike Laravel, where replacing a vendor class means a container binding that
only reaches code resolving through the container, an RSX override replaces the
class for every reference in the tree: a `use` import, a type hint, an inline
FQCN, a static call and `new` all reach the application's class.

WHICH RECIPE APPLIES IS DECIDED BY THE CLASS, NOT BY PREFERENCE.

    A core MODEL - every *_Model under system/app/RSpade whose file is a shell
    beside a *_Model_Abstract of the same stem. The override EXTENDS that base.
    A copy of the framework file is REFUSED at manifest build.

    Everything else - controllers, services, components, libraries, the
    permission classes. The override is a COPY under the same class name, and it
    holds the whole implementation.

The split exists because a copy is frozen the moment it is taken while the
framework's own class keeps moving. A downstream field report records both halves
of what that costs: a hook the framework only INVOKES never ran, so a background
queue enqueued nothing for months and looked healthy doing it; and a framework
controller called a method the loaded class did not define, so one document type
answered 500. An override that EXTENDS a base cannot have either failure - it
inherits every member the base has now and every member it gains later - so the
classes an application most often customizes are shaped that way.

Session is not a model in this sense and is not split: it is a static facade,
called as Session:: everywhere, and replacing it is not a supported concept.

THE 28 SPLIT CORE MODELS

    Api_Key_Model                         Api_Request_Log_Model
    Country_Model                         Email_Attachment_Model
    Email_Blocked_Address_Model           Email_Queue_Model
    Email_Recipient_Model                 File_Attachment_Model
    File_Storage_Model                    Flash_Alert_Model
    Login_User_Model                      Portal_Notification_Model
    Portal_Sso_Identity_Model             Portal_Two_Factor_Credential_Model
    Portal_User_Model                     Region_Model
    Revision_Model                        Search_Index_Model
    Site_Model                            Sms_Queue_Model
    Sms_Recipient_Model                   Sso_Identity_Model
    Transaction_Model                     Two_Factor_Credential_Model

Each base sits beside its shell in the same directory - for example
system/app/RSpade/Core/Models/User_Model_Abstract.php beside
system/app/RSpade/Core/Models/User_Model.php.

A SPLIT MODEL OVER A SYSTEM TABLE IS STILL OVERRIDABLE, and the table is still
the framework's. Email_Queue_Model, Email_Recipient_Model,
Email_Attachment_Model, Sms_Queue_Model, Sms_Recipient_Model,
File_Storage_Model, File_Attachment_Model, Flash_Alert_Model,
Search_Index_Model and the rest read `_`-prefixed tables that the framework
creates, writes and sweeps. Extend the base to add a scope, a relation or an
accessor; do not migrate those tables, and do not write their rows around the
model.

## HOW IT WORKS

Every manifest build derives THE OVERRIDE MAP from scratch, over the whole tree.
A name declared by exactly one rsx/ file and by a framework file is an
override, and every framework file declaring it is shadowed:

    Framework file: app/RSpade/Core/Models/User_Model.php
    Override file:  rsx/models/user_model.php

    Result:
    - app/RSpade/Core/Models/User_Model.php stays in place, shadowed
    - rsx/models/user_model.php becomes the active class
    - App\RSpade\Core\Models\User_Model is an alias of Rsx\Models\User_Model

A shadowed file is out of everything the live index feeds - the class maps,
routes, the attribute index, the code-quality pass, every bundle - but it is
still a file of the tree: it stays in the build key by path and content, so a
framework update to it is seen like any other change, and the drift analysis
reads it where it lies (DRIFT, below).

The PHP half of the map is also written to build/manifest/class_overrides.php,
the file the class override loader reads at the start of every process. It is a
build artifact: a sealed build carries it and the seal covers it.

Because the map is derived in full every build, there is no state to repair: an
override added, edited or deleted is reflected by the next build, and an
override never makes a build restart.

FOR A SPLIT MODEL the shadowed file is the three-line shell, and the base is
untouched: it stays in the build, it stays framework property, and the override
keeps inheriting it. Everything the framework adds to the base after the override
was written is present on the application's class the day it arrives.

WHAT THE BASE CARRIES, AND THEREFORE WHAT AN OVERRIDE INHERITS: $table, $enums,
$type_ref_columns, $revisions, $realtime, $appends, $detail_tables, the
constants, the traits, the relationships, fetch()/portal_fetch(), the hooks, and
the _AUTO_GENERATED_ codegen regions. An override declares NONE of them unless it
is changing them.

    MODEL-TABLE-01 and MODEL-ENUMS-01 walk the lineage. A $table declared by an
    ancestor satisfies the rule, so an override that does not change the table
    declares no $table. Redeclaring one is how two answers to "which table" get
    into a tree.

    php artisan rsx:constants:regenerate writes the docblock and the enum
    constants into the class that DECLARES $table / $enums - the base for a
    framework model, the override's own file when the override redeclares them.

    The generated JS stub and the model index take their staleness key from the
    WHOLE lineage (Model_Lineage_Fingerprint), so a change to a base regenerates
    the stub of every model under it.

    #[Ajax_Endpoint_Model_Fetch] and the #[Auth] gates on it are resolved by
    lineage too (Model_Fetch_Lineage): a fetch() declared on the base is the
    concrete's fetch surface, and an override that redeclares fetch() replaces it -
    so the redeclaration carries #[Ajax_Endpoint_Model_Fetch] and its #[Auth] itself.
    Redeclaring fetch() or a fetchable relationship without the attribute fails the
    manifest build (UNMARKED FETCH OVERRIDE, rsx:man auth_gates).

    $neverExport is a PHP property, so an override that declares its own REPLACES
    the base's list rather than adding to it. Include the base's columns in yours:
    User_Model_Abstract withholds invite_code (a bearer credential for claiming a
    pending account), invite_accepted_at and invite_expires_at.

        protected $neverExport = ['invite_code', 'invite_accepted_at',
                                  'invite_expires_at', 'my_private_column'];

WHICH MEMBERS AN OVERRIDE MAY REPLACE OUTRIGHT. PHP-PARENT-CHAIN-01 (a
manifest-build FATAL) requires every override of an inherited method to call
parent::<same-method>(). The exception is a member the base marks #[Replaceable],
which is the framework saying "this is where the application states policy":

    fetch()                 the model's own read gate
    portal_fetch()          its portal twin
    portal_can_read()       the portal record rule
    get_printed_name()      how an actor's name renders
    get_view_profile_url()  where an actor's profile screen is
    determine_file_type()   attachment classification

on the models that carry them. Everything else chains, and that chaining IS the
drift protection: the base keeps moving and the override keeps inheriting it.

Overriding a MODEL does not change which bundles its generated Base_ stub
reaches: the stub follows the JS model class that extends it, so moving the PHP
class into rsx/models leaves every bundle that names the class complete (see
rsx:man bundle_api, JAVASCRIPT STUBS). The __MODEL name and the Base_*_Model.js
stub names are the CONCRETE's, unchanged by the split, so nothing moves in
JavaScript.

## JAVASCRIPT CLASSES, TEMPLATES AND STYLESHEETS

The same mechanism covers the three browser-side file kinds. Each is matched by
the NAME IT DECLARES - never by its file name or its directory - and each file
is its own override:

    .js       its class name (.js, .jsx, .ts and .tsx alike). An rsx/ JS class
              with the name of a framework JS class shadows the framework's
              file.
    .jqhtml   its component, <Define:Name>. An rsx/ template with the name of a
              framework template shadows the framework's .jqhtml file.
    .scss     the ONE class the whole stylesheet is wrapped in (.Name { ... }).
              An rsx/ stylesheet wrapped in the same class as a framework
              stylesheet shadows the framework's .scss file.

So rsx/theme/components/inputs/code/code_input.scss, wrapped in .Code_Input,
overrides system/app/RSpade/Core/Forms/Code_Input.scss, and nothing about the
two paths has to agree.

PER FILE, NOT PER COMPONENT. A jqhtml component is usually three files of one
name, and an application takes over as many of them as it supplies. Overriding
only the template leaves the framework's class and stylesheet for that component
in the build; overriding only the stylesheet restyles the framework's component.
What you did not override keeps arriving with framework updates - and keeps
changing under the files you did, so a template you copied is yours to keep in
step with the framework's class.

A stylesheet with no single wrapper class (variables only, or several top-level
rules) declares no name: it neither overrides nor can be overridden.

Two files of one name in rsx/ are refused at manifest build, whatever the kind -
nothing could choose between them (WHEN THE BUILD REFUSES). Two templates of one
component name inside the framework are a duplicate, not an override, and stop
the build ("Duplicate jqhtml component name detected").

Shadowing and its end work exactly as for PHP: the build prints one line naming
the framework file and the rsx/ file that shadows it, and deleting the rsx/ file
makes the framework file live again on the next build. Each file is released on
its own - removing your stylesheet brings the framework's stylesheet back and
leaves your template override standing.

## BUNDLES

Whichever way a bundle reaches a shadowed framework file - a directory include,
a type pattern or the file named explicitly - it compiles the rsx/ file that
overrides it instead, in the framework file's place in the include order (a
stylesheet cascades, a script sorts, where the framework's would have), and only
once when the bundle also includes the rsx/ file itself. The shadowed file is
never compiled.

That holds for EVERY bundle, the framework's own included: Core_Bundle and the
/_sys and /apidocs bundles receive your component, template or stylesheet
wherever they name the framework's. Those bundles still name no rsx/ path
(CONV-BUNDLE-04 reads what a bundle declares, which is unchanged); the
substitution happens below the declaration. Overriding a component the panel
uses (a form input, say) therefore changes it in the panel too.

    php artisan rsx:bundle:show <Bundle>

lists a substituted include as "<framework file> -> <rsx file> (override)".
rsx:man bundle_api has the include rules.

## WHAT THE BUILD PRINTS

A framework file leaving the live tree is never silent. The build that first
shadows it prints one line naming the framework file and the rsx/ file that
shadows it, and stays silent on every build after:

    [Manifest] Override: User_Model - the framework php file
    app/RSpade/Core/Models/User_Model.php is shadowed by
    rsx/models/user_model.php

The build that ends an override prints:

    [Manifest] Override removed: the framework file
    app/RSpade/Core/Models/User_Model.php is live again

A framework class can therefore never leave the build without a line naming it,
and rsx:overrides:list shows every override in force at any time.

## WHEN THE BUILD REFUSES

The override pass stops the build with a FATAL when an override cannot work, and
declines to shadow anything in two situations where its own input cannot be
trusted. Each FATAL names the files involved and, where there is a pattern to
follow, ends with "See: php artisan rsx:man class_override".

FATAL - THE OVERRIDE EXTENDS THE CLASS IT REPLACES

    An rsx/ class named X that declares `extends X` cannot exist: RSX enforces
    unique simple class names, so the two are the same name and the inheritance
    is a cycle. The message names the correct pattern for the class at hand - for
    a split model, extending the BASE:

        Fatal: Invalid class override pattern for 'User_Model'.

        The file rsx/models/user_model.php extends the framework class
        User_Model, but RSX requires unique class names - you cannot have two
        classes with the same name, even if one extends the other.

        CORRECT OVERRIDE PATTERN FOR A SPLIT FRAMEWORK CLASS:
          The framework carries every member of User_Model on the abstract
          base User_Model_Abstract, and ships User_Model as an empty shell so an
          application can replace it. Extend the BASE, not the shell:

             class User_Model extends User_Model_Abstract
             {
                 // only the members this application changes
             }

          Your class then overrides User_Model for the whole tree
          (app/RSpade/Core/Models/User_Model.php is shadowed and never loaded),
          still inheriting everything the framework adds to the base from now on.

    For a non-split class the same failure prints the copy recipe instead.

FATAL - AN OVERRIDE OF A SPLIT MODEL THAT DOES NOT EXTEND ITS BASE

    A copy of the framework file, or a class extending anything other than
    X_Model_Abstract, is a SECOND IMPLEMENTATION of a class the framework keeps
    developing. That is the exact failure the split ends, so it is refused rather
    than reported:

        Fatal: Invalid override of the split framework class 'File_Attachment_Model'.

          Override: rsx/models/file_attachment_model.php (extends Rsx_Site_Model_Abstract)
          Required: extends File_Attachment_Model_Abstract

        File_Attachment_Model is a SPLIT framework class:
        app/RSpade/Core/Files/File_Attachment_Model.php declares nothing but
        `class File_Attachment_Model extends File_Attachment_Model_Abstract`, and
        every member lives on the base. The shell exists so an application can
        replace it WITHOUT holding a copy of the implementation.

        REWRITE THE OVERRIDE AS:

             class File_Attachment_Model extends File_Attachment_Model_Abstract
             {
                 // only what this application changes
             }

        A copy of the framework file is a second implementation of a class the
        framework keeps developing: every member added to
        File_Attachment_Model_Abstract after the copy was taken is missing from
        it, and framework code calls those members on this class regardless.

    "extends nothing" appears in the Override line when the override declares no
    parent at all.

FATAL - TWO APPLICATION FILES DECLARE ONE NAME

    Any kind - a PHP class, a JS class, a jqhtml component, a stylesheet wrapper
    class. Nothing can choose between them, so neither overrides anything:

        Fatal: Duplicate jqhtml component 'Code_Input' declared by more than
        one application file:
          - rsx/theme/components/inputs/code/code_input.jqhtml
          - rsx/app/frontend/settings/code_input.jqhtml

        Component names (<Define:Code_Input>) must be unique across the
        application.
        (When one of them overrides a framework jqhtml file, the override must
        be exactly one application file - see rsx:man class_override.)

FATAL - THE CLASS CANNOT BE OVERRIDDEN

    Some framework classes exist before an override could answer for their
    name, or are never seen by the override pass at all. An rsx/ class named
    like one of them is refused:

        Fatal: 'Rsx' cannot be overridden.

          Application class: rsx/lib/rsx.php
          Framework class:   App\RSpade\Core\Rsx

        App\RSpade\Core\Rsx is declared while the framework boots or while the
        manifest is being built - before an override could answer for its
        name - so no application class can replace it.

        Rename the application class. Framework classes that boot the
        framework or build the manifest, and framework classes in directories
        the manifest does not index, cannot be replaced by an override.

    The middle paragraph names which of three reasons applies:

    - a BOOT CLASS (Class_Override_Boot_Set): the framework declares it while
      it boots or while the manifest is being built - the autoloader, the
      manifest, the paths and naming classes, the kernels, Laravel integration,
      the service providers and *_BundleIntegration / *_ManifestModule classes,
      and a measured list of single classes;
    - a class ALREADY DECLARED in the building process ("... was already
      declared in this process (as ...) before the override map was settled");
    - a class in a framework directory the manifest DOES NOT INDEX ("... lives
      in a framework directory the manifest does not index"): the unscanned
      app/RSpade subtrees (Commands, Ide, ...), the resource/, public/ and
      hidden directories inside the scanned ones, and system/app/{Console,
      Database, Exceptions, Http, Notifications, Providers}. Such a file can
      never be shadowed, and RSX resolves classes by simple name, so the two
      cannot coexist either.

FATAL - A SPLIT BASE NAMES ITS OWN SHELL IN A SIGNATURE

    A framework rule the build enforces on the framework itself, reported here
    because an override is what it protects:

        Fatal: User_Permission_Model_Abstract::grant() names its own
        overridable class User_Permission_Model in its signature.

    An override of X redeclares methods of X_Abstract. PHP compares a
    redeclared method's signature with its parent's while the override is
    still being declared - before the framework name X can be its alias - so a
    parameter or return type spelled X in the base could never link. The base
    spells such a type X_Abstract, or `static`. On a released framework this
    never fires; it exists so the framework cannot ship the defect.

FATAL - TWO FILES DECLARE ONE FQCN

    An override declares its class in the namespace its rsx/ path gives it,
    never in the framework's. An rsx/ file that keeps the framework namespace
    is a duplicate of the framework class, not an override of it
    ("Fatal: Duplicate PHP class name ... Both declare ...").

DECLINED - THE rsx/ FILE IS NOT ON DISK

    The index names an override that has since been deleted. The stale entry is
    dropped and nothing is shadowed:

        [Manifest] Override pass: ignoring stale index entry for User_Model -
        rsx/models/user_model.php is in the file list but not on disk.
        Nothing is shadowed; the entry is dropped.

DECLINED - THE BUILD ALREADY MARKED ITS OWN MANIFEST BAD

    A build that has hit a manifest-fatal has declared its file list
    untrustworthy. It shadows nothing; the two declarations stay in the tree and
    the class maps report the duplicate:

        [Manifest] Override pass: NOT shadowing the framework php file of
        User_Model - this build already marked its manifest bad, so its file
        list is not evidence of anything. The next build decides.

    An override that is genuinely present is shadowed on the next build, with
    the ordinary notice above.

## LISTING THE OVERRIDES IN FORCE

    php artisan rsx:overrides:list [--json]

One row per shadowed framework file, read off the manifest's override map: the kind
(php, js, jqhtml, scss), the declared name, the application file that overrides it
and the framework file it shadows, paths relative to the project root. A PHP row also
carries the drift verdict described below - "current", "N missing" (the members are
named under the table) or "extends base" for a split model, which has nothing to
drift; the three asset kinds are not analysed. "No class overrides." when there are
none. Read-only, exit 0, and it works in every mode, sealed builds included. --json
prints {"overrides": [{kind, name, override_file, framework_file, fqcn, by_fqcn,
drift: {status: current|missing|extends_base, missing: [...]} | null}]}.

THE EDITOR. The VS Code extension reads the same map through the IDE bridge
(/_ide/service/overrides). A shadowed framework file is badged in the explorer
and carries a CodeLens that opens its override, and go-to-definition on the
class name lands on the override, never on the shadowed file.

## DRIFT: AN OVERRIDE THAT STOPS CARRYING WHAT UPSTREAM DECLARES

A COPY is frozen the moment it is taken. The framework file it replaced stays in
place, shadowed, and keeps moving with every rsx:framework:pull. Nothing in PHP
relates the two files afterwards, so when the framework adds a member to that
class and then CALLS it, the call lands on the application's older copy, which
never had that member.

    CLASS-OVERRIDE-DRIFT-01 (rsx:check)

The analysis pairs each PHP override with the framework file it shadows, read
where it lies - so it always compares against the framework code currently
installed. It names every PUBLIC or PROTECTED member the framework file declares
and the
override does not - methods static and instance, declared properties, and
`use Trait;` adoptions (dropping one drops every member the trait supplied). One
finding per member, naming the class, the member, both file paths, and the
remedy. Alongside it the finding prints the override's OWN additions as INFO
context, because the reader's next move is a re-clone and a re-clone has to carry
every one of them forward.

It is HIGH, and deliberately NOT a manifest-build fatal. The drift arrives on a
PULL, not on anything the developer just typed, and the site it appears on is
running: taking that site down until somebody finds time to re-clone would turn a
latent defect into an immediate outage. The finding is the alarm; the developer
schedules the work. Suppress a deliberate divergence with
`@CLASS-OVERRIDE-DRIFT-01-EXCEPTION` in the OVERRIDE file.

Two things it cannot see. A member present in both files whose BODY has diverged
is indistinguishable from a deliberate override, so it is never reported. And a
member the override adds is never a violation - that is the work the override
exists to hold.

    Class Override Drift (rsx:health)

The same analysis as an operator row: WARN, never FAIL, one row per drifting
override, counting the missing members and pointing at rsx:check. It exists
because the moment drift appears is a framework pull, which is exactly when
somebody is looking at rsx:health and not at the linter.

Drift is analysed for PHP classes only. A JS class, template or stylesheet you
override is listed by rsx:overrides:list with no drift verdict; keeping it in
step with the framework's version is a manual diff (FRAMEWORK UPDATES).

A SPLIT MODEL HAS NO DRIFT SURFACE AND IS REPORTED ON BY NEITHER. The shadowed
file declares nothing but `class X extends X_Abstract`, and the override extends
that same base, so there is no frozen copy to measure: the pair reports nothing
rather than naming the base's members as absent from a class that has them. An
override of a split model that does NOT extend the base never reaches the drift
analysis - the override pass refuses it by name, above.

DISCIPLINE FOR LIVING WITH AN OVERRIDE

PREFER A SEAM OVER AN OVERRIDE. Most customizations attach POLICY, not logic, and
policy has framework seams that hold no copy and shadow no file:

    can_view() / scope_can_view()   Staff_Authorizable  - staff row visibility,
                                    per row and per set (rsx:man file_upload)
    portal_can_read()               Portal_Authorizable - the portal twin
                                    (rsx:man portal)
    fetch()                         the model's own read gate (rsx:man model_fetch)
    #[OnEvent] handlers             behaviour interception (rsx:man event_hooks)

The reference app is the worked example of choosing the hook: the one answer the
framework's User_Model cannot give - where a staff user's profile screen is - is
asked through the resolve hook `user.view_profile_url`, and the app answers it in
resource/reference_app/handlers/User_Profile_Url_Handlers.php. The template ships
no core-model override at all.

WHEN YOU DO COPY A NON-MODEL CLASS, ENUMERATE THE ADDITIONS IN A BANNER at the
top of the override - one line per item, in the order they appear. A re-clone
then becomes mechanical: copy the framework file over the override, fix the
namespace, re-apply the list. Without the banner, every re-clone is a diff of a
file nobody wrote most of.

RE-CLONE ON THE FINDING, NOT ON A SCHEDULE. The rule fires when the framework has
actually moved. That is the moment the diff is smallest and the reason is known.

## CREATING AN OVERRIDE

RECIPE 1 - A CORE MODEL (extend the base)

1. Write rsx/models/<thing>_model.php declaring the same simple name, extending
   the base:

        <?php

        namespace Rsx\Models;

        class User_Model extends User_Model_Abstract
        {
        }

2. Declare ONLY the members this application changes. No $table, no $enums, no
   constants, no relationships that the base already has.

3. For each method: replace it outright when the base marks it #[Replaceable];
   otherwise call parent::<same-method>() inside it (PHP-PARENT-CHAIN-01).

4. Load any page; the build prints the "Override:" line (WHAT THE BUILD
   PRINTS).

5. Verify the override is active:

        php artisan rsx:overrides:list
        # php  User_Model  rsx/models/user_model.php
        #      system/app/RSpade/Core/Models/User_Model.php  extends base

RECIPE 2 - ANY OTHER FRAMEWORK CLASS (copy it)

1. Copy the framework file into rsx/ under the same class name:

        cp system/app/RSpade/Core/Files/File_Attachment_Icons.php \
           rsx/lib/file_attachment_icons.php

2. Update the namespace in the copy:

        namespace Rsx\Lib;   // was: namespace App\RSpade\Core\Files;

3. Customize it, and record every addition in a banner at the top of the file.

4. Build, and verify as in recipe 1. From here the copy is yours to keep current:
   CLASS-OVERRIDE-DRIFT-01 names what upstream gains that it lacks.

## EXAMPLE: OVERRIDING USER_MODEL

    <?php

    namespace Rsx\Models;

    /**
     * User_Model - this application's staff user.
     *
     * Extends the framework base; declares only what this application changes.
     */
    class User_Model extends User_Model_Abstract
    {
        /**
         * The base marks this #[Replaceable] - it is where the application
         * states how a staff user's name renders. No parent:: call.
         */
        public function get_printed_name(): string
        {
            return trim($this->last_name . ', ' . $this->first_name);
        }

        /**
         * Not #[Replaceable], so the parent call is mandatory
         * (PHP-PARENT-CHAIN-01, a manifest-build fatal without it). The base
         * decides what "active" means for the framework; this narrows it.
         */
        public function is_active()
        {
            return parent::is_active() && $this->contract_signed_at !== null;
        }

        /**
         * An addition of this application's own - a relationship the framework
         * knows nothing about.
         */
        public function projects()
        {
            return $this->hasMany(Project_Model::class, 'owner_id');
        }
    }

Everything else - $table = 'users', the role enums and their constants, the ACL
resolution, fetch() and its gates, the authorship stamping - is inherited from
User_Model_Abstract and stays current with the framework.

### WHEN YOUR COPY OF THE TABLE IS SITE-SCOPED AND THE FRAMEWORK'S IS NOT

The override must extend the framework base DIRECTLY - an intermediate class
does not satisfy the check - so the base's own parent is fixed, and PHP has no
second inheritance slot to reach Rsx_Site_Model_Abstract with. That matters when
an application adds site_id to a framework table in its own migration as part of
a tenant sweep: the model needs the tenant boundary and cannot inherit it.

Adopt the trait. It is the same implementation Rsx_Site_Model_Abstract itself
adopts, not a copy of it:

    namespace Rsx\Models;

    use App\RSpade\Core\Database\Models\Site_Scoped;

    class User_Profile_Model extends User_Profile_Model_Abstract
    {
        use Site_Scoped;
    }

That installs the read scope, the create stamp, the cross-site save refusal and
the retrieved cross-check - and keeps taking framework changes to them, which a
hand-rolled bridge in the override would not. Re-implementing site scoping in an
override is the cloned-machinery drift the split exists to end; the trait is the
sanctioned way to say "this one is site-scoped too".

Your migration declares the site_id column - schema normalization adds that one
for nobody (rsx:man model). Full contract: rsx:man model, SITE SCOPING AS AN
ADOPTABLE TRAIT.

## FRAMEWORK UPDATES

An override leaves nothing under system/ for `php artisan rsx:framework:pull`
to deal with:

1. The update replaces system/ with the new revision. The framework file your
   override shadows arrives in its new version, in place, like every other.
2. Your rsx/ override remains unchanged (rsx/ is never touched by an update).
3. The next manifest build derives the override map again and the override is
   in force exactly as before. A shadowed file that changed moves the build key
   like any other change.
4. For a PHP copy, CLASS-OVERRIDE-DRIFT-01 and the "Class Override Drift"
   health row now compare against the new framework file.

See rsx:man rsx_upstream for the full update contract.

For a MODEL override there is nothing to compare after an update: the base
arrived with the pull and the override already inherits it. For a COPY - and
for every JS class, template and stylesheet you override - see what the
framework version gained with a plain diff against the file in place:

    diff rsx/lib/file_attachment_icons.php \
         system/app/RSpade/Core/Files/File_Attachment_Icons.php

rsx:overrides:list names the framework file of every override.

## REMOVING AN OVERRIDE

Delete the override file:

    rm rsx/models/user_model.php

The next build derives a map without it, prints "Override removed: the
framework file app/RSpade/Core/Models/User_Model.php is live again", and the
framework class answers for its own name from then on. There is nothing to
restore: the framework file never left. The same holds for a .js, .jqhtml or
.scss override, each judged on its own: the framework file is live again when no
rsx/ file of the same kind declares its name.

## HOW REFERENCES KEEP RESOLVING

The framework file stays on disk, and code all over the framework still names
the ORIGINAL class - by simple name, by `use` import, by inline FQCN, in a type
hint. Every one of those reaches your override, in every mode, sealed builds
included, through one mechanism: THE CLASS OVERRIDE LOADER.

IT IS PREPENDED, AHEAD OF COMPOSER

    Composer maps every framework class twice over (its optimised classmap and
    the App\ => app/ PSR-4 rule), and the framework file is still there, so
    composer would load it the moment it was asked. The override loader is
    therefore registered IN FRONT of composer, from a composer `files` entry
    (system/app/RSpade/autoload_overrides.php) - the earliest point artisan,
    the web front controller, system/script.php and every spawned script share.
    It reads build/manifest/class_overrides.php and is moved back to the front
    once the framework has booted, behind nothing that prepended itself since.

IT ANSWERS EXACT KEYS ONLY

    The loader answers for an exact framework FQCN in the override map and for
    nothing else: one array lookup, then it declines. Asked for
    App\RSpade\Core\Models\User_Model, it includes rsx/models/user_model.php and
    makes the framework FQCN a class_alias() of Rsx\Models\User_Model. Every
    other class - framework, vendor or application - loads exactly as it would
    with no override. (The RSX simple-name autoloader stays behind composer:
    placed in front, it would answer any vendor class whose simple name matches
    an application class.)

THE ALIAS EXISTS FROM THE MOMENT YOUR CLASS DOES

    A run-time type check never autoloads: a framework method typed
    `User_Model $user` handed an Rsx\Models\User_Model throws a TypeError
    unless the framework name is ALREADY an alias. So the alias is made twice
    over: the moment an override's file is included (by any loader), and
    eagerly for every override when the framework boots. instanceof, catch and
    is_a() against the framework name hold before anything has asked for it.

COMPOSER IS DISARMED, IN MEMORY

    For each overridden name, composer's live classmap entry is pointed at a
    trip-wire file (system/app/RSpade/autoload_overrides_tripwire.php), in
    memory only - nothing under vendor/ is written. Composer is only ever asked
    for such a name when the loader order has been broken, and then the request
    throws, naming the class, instead of silently loading the framework file
    (TROUBLESHOOTING). Including a shadowed framework file by path is refused
    the same way.

THE SIGNATURE CHECK AUTOLOADS

    PHP's signature-compatibility check - run when a class that redeclares an
    inherited method is declared - DOES autoload the classes the two signatures
    name. So a framework class whose inherited signature says User_Model, under
    its own unmodified `use App\RSpade\Core\Models\User_Model` import, links
    against your override: the check asks for the framework name and the
    loader answers with the alias. No framework file is ever rewritten to make
    an override work.

    The one case it cannot serve is a split base naming its OWN shell. Declaring
    your User_Model, which redeclares a method of User_Model_Abstract, makes the
    check ask for User_Model while your class is still being declared - before
    the alias can exist. That is why a framework base spells such a type as
    X_Abstract or `static`, and why the build refuses a base that does not
    (WHEN THE BUILD REFUSES). If the same thing happens through some other
    framework ancestor, the loader throws "... cannot be resolved while ... is
    still being declared"; spell the type in your override exactly as the
    framework does.

UN-OVERRIDABLE CLASSES, AND WHY

    An alias can only be made for a name nothing has declared yet. A class the
    framework declares before the override loader can answer - required by
    path while the framework boots, or loaded by the manifest build before the
    override map is settled - can never become one in that process, and a class
    in a directory the manifest does not index can never be shadowed at all.
    The build refuses an override of any of them (WHEN THE BUILD REFUSES).

A SPLIT MODEL's base is never overridden, so its own FQCN
(App\RSpade\Core\Models\User_Model_Abstract) is stable and every framework
import of it resolves to the framework base. Your file needs no import for it:
the RSX autoloader resolves the parent by simple name when the class is loaded.

## HYGIENE INVARIANT

NOTHING UNDER system/ IS EVER WRITTEN FOR AN OVERRIDE. Not by the build, not by
the fixer, not by the loader: the framework file is not renamed, no framework
import is rewritten, and composer's files are not touched (its classmap is
disarmed in memory). The override map lives in build/, the override in rsx/. A
framework file's `use` import, inline FQCN or type hint naming an overridden
class is correct as written and resolves to your override. A sealed build of a
tree with overrides leaves system/app and system/config exactly as git checked
them out, and that is asserted by the framework's production-mode acceptance
test.

A sealed build does run `composer dump-autoload`, which writes
system/vendor/composer/ on its own account; that dump knows nothing about
overrides and is neither caused nor needed by one (rsx:man prod).

A second invariant belongs to the split: a member of a core model is DECLARED ON
THE BASE. The shell is never where a member goes - the framework's own change to
a model edits x_model_abstract.php, and Core_Model_Split_Test
(rsx:test --framework --group=class_override) fails the build's own suite when a
shell declares anything or a base ships without exactly one concrete.

## LIMITATIONS

- Only works for files in rsx/ overriding framework files the manifest indexes
- Both files must declare the same name (class, component or wrapper class)
- Cannot override multiple framework classes with one file
- A core MODEL cannot be overridden by copying - the override must extend
  <Name>_Model_Abstract, and a copy is refused at manifest build
- The ABSTRACT BASE of a split model is not overridable: an rsx/ class named
  X_Model_Abstract would shadow the base itself, which is the implementation.
  Override the concrete, which is what the shell is for
- A JS class, a jqhtml template and a stylesheet are each overridden by name,
  file by file (JAVASCRIPT CLASSES, TEMPLATES AND STYLESHEETS above), and every
  bundle - the framework's own included - compiles the replacement (BUNDLES)
- An overridden PHP class is global: the /_sys panel, the framework's commands
  and every task run your class, exactly as the application does
- Classes the framework declares while it boots or while the manifest builds,
  and classes in directories the manifest does not index, cannot be overridden
  (WHEN THE BUILD REFUSES)
- Framework ARTISAN COMMANDS are not overridable, by design. An application
  writes no command classes at all (rsx:man task_commands - a named command is
  a #[Command] on a #[Task]), and a Laravel command needs an instance handle()
  that MANIFEST-INST-01 refuses under rsx/. A defect in a framework command is a
  framework change request, never a local copy

## TROUBLESHOOTING

### Override not detected

Run php artisan rsx:overrides:list. A missing row means the two files do not
declare the same name; check them:

    grep -r "^class " rsx/models/user_model.php
    grep -r "^class " system/app/RSpade/Core/Models/User_Model.php

If the build printed either of the DECLINED lines under WHEN THE BUILD REFUSES,
it is telling you why: a stale-entry line means the rsx/ file it names is not
where the index thinks it is; a bad-manifest line means an earlier failure in
the same build has to be fixed first. The map is derived in full on every
build, so a clean build cannot change the answer.

### "Invalid override of the split framework class"

The override of a core model is a copy, or extends the wrong parent. Rewrite it
as `class X_Model extends X_Model_Abstract` carrying only the members it changes;
the message names both the file and the required base. See WHEN THE BUILD REFUSES.

### "'X' cannot be overridden"

The framework class is a boot class, was already declared while the manifest
was building, or lives in a directory the manifest does not index. No override
of it can work; rename the application class. If the behaviour you need lives
in such a class, that is a framework change request (rsx:man
framework_debug_and_contrib).

### "... is overridden by ..., but composer was asked for it before the class override loader"

The trip-wire. The override loader must be first on the autoload stack, and in
this process something answered ahead of it: an autoloader registered with
prepend after the framework booted, or a process that loaded composer's
ClassLoader without its `files` entries. Composer would have loaded the
framework class and bypassed your override, so the request throws instead. Find
the spl_autoload_register(..., true, true) call or the entrypoint that loads
the class loader by hand.

### "... was already declared as ... before the override could answer for it"

The framework class was declared under its own name before the loader could
alias it - something required the framework file by path, or loaded it before
the override map was read. In this process no alias can ever be made. A
framework file included by path while it is shadowed is refused outright
("Refusing to include ...: it declares ..., which the application overrides").

### "... cannot be resolved while ... is still being declared"

Your override redeclares a method whose signature in a framework ancestor names
the very class you override. PHP's signature check autoloads that name while
your class is still being declared, before it can be the alias (HOW REFERENCES
KEEP RESOLVING, THE SIGNATURE CHECK AUTOLOADS). A framework split base never
does this, and the build refuses one that does; for any other ancestor, spell
the type in your override exactly as the framework does.

### "must call parent::" after rewriting an override onto the base

PHP-PARENT-CHAIN-01. The member is not #[Replaceable], so the override extends
the base's behavior rather than replacing it: call parent::<same-method>() inside
it. If the intent really is to replace, the base's member is the wrong seam and
the change belongs upstream - a framework change request (rsx:man
framework_debug_and_contrib), not an escape hatch.

### Missing methods after overriding a non-model class

A copy replaces the entire class. Copy the missing functionality from the
framework file it shadows (rsx:overrides:list names it). If the member exists
upstream and not in the copy, CLASS-OVERRIDE-DRIFT-01 already named it - see
DRIFT above. A model override does not have this failure mode: it inherits.

### A framework class disappeared and nothing explains it

It was not this system. Every shadowing prints a line naming both files; search
the build output for "Override:", or run rsx:overrides:list. An absent row
means the class left some other way.
