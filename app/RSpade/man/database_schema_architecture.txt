============================

OVERVIEW
--------
This document describes the RSpade database schema organization and the architectural
principles governing how framework and application data is stored.

Date: 2024-11-18
Status: Active framework architecture documentation

TABLE NAMING CONVENTIONS
-------------------------
RSpade uses table name prefixes to distinguish between different layers of the system:

1. SYSTEM TABLES (underscore prefix: _tablename)
   - Internal framework infrastructure
   - Managed entirely by framework subsystems
   - PRIVATE to the framework - see SYSTEM TABLES ARE PRIVATE below
   - Framework code may use direct DB::table() queries (exempt from the
     ORM requirement)
   - Implementation details hidden from application layer

2. CORE TABLES (no prefix: tablename)
   - Built-in application infrastructure
   - Provided by framework but application-facing
   - Developers query, extend, and build upon these
   - MUST use ORM models (DB::table() prohibited)
   - Part of the developer-facing API

3. APPLICATION TABLES (no prefix: tablename)
   - Created by developers for their specific application
   - Business domain entities
   - MUST use ORM models (DB::table() prohibited)
   - Not shipped with framework (starter template only)

COLUMN NAMING CONVENTION (the same prefix, one level down)
----------------------------------------------------------
A single leading underscore on a COLUMN means what it means on a table: this is
framework SYSTEM state, not application data.

  _columnname
    - Owned by a framework subsystem, on a table the application otherwise owns
    - Stripped from every payload by Rsx_Model_Abstract::toArray(), so the
      client never receives it
    - Skipped in the generated JS model stub's field_length() map (the client
      cannot hold the column, so it can never need its length)
    - Excluded from every revision diff (rsx:man revisions)

  __columnname
    NOT a system column. Double underscore is the framework KEY prefix that
    toArray() itself adds - __MODEL, __details - and is the payload's contract
    with the JavaScript ORM. Nothing strips it.

  columnname
    Ordinary application/core data. Reaches the browser, appears in diffs.

Consequence for both directions: when a framework feature needs per-record
state on an application table it names the column `_foo` and needs no
exclusion list, no config and no cooperation from the app; and an
application-facing column must NEVER be given a leading underscore, because it
will silently never reach the browser.

SYSTEM TABLES ARE PRIVATE
--------------------------
A table whose name begins with an underscore belongs to the RSpade core, and
so does its schema. Application code under rsx/ never reads or writes one
directly:

    - no DB::table('_sessions'), DB::select() or raw SQL that names one
    - no join onto one, and no query that depends on one of its columns
    - no reading its rows to learn something the framework has a call for

An application reaches what those tables hold through the interfaces the
framework publishes for it - the facade functions and the documented methods
of framework classes:

    who is signed in where        Session::get_sessions_for_user()
    sign-in history               Login_History::list_page() (a grid page),
                                  get_history_for_user() (the newest few)
    who performed a logged act    Session::get_audit_session()
    a record's change history     $record->revisions(), Revision_Model::diff()
    background runs               Task_Run_Model::find_page(), Rsx_Task
    files                         File_Attachment_Model and its documented
                                  methods (rsx:man file_upload)
    disk the blob store holds     File_Storage_Model::usage_report()

Each feature's man page names its interface.

THE SCHEMA OF A SYSTEM TABLE IS NOT A CONTRACT. Columns are renamed, split
into other tables and dropped between releases with no notice and no
breaking_changes document - the published interfaces are what stay stable,
and they are the only thing an application may build on. Code that reads a
system table directly works until the next framework update and then fails
at run time, with nothing at build time to say so.

WHEN THE INTERFACE IS NOT ENOUGH, the answer is a change request to RSpade
to extend it - a new accessor, another field in an answer, a filter - never
a query of your own against the table. The data is the framework's to
expose.

The same holds one level down: a `_`-prefixed COLUMN on any table is the
framework's (COLUMN NAMING CONVENTION above).

READERS OVER SYSTEM TABLES
---------------------------
Since an application cannot query a system table, the framework publishes
READERS. There are three kinds, each with one shape. A new reader is written
to the shape of its kind; a reader of a kind this section does not describe
is a design decision to record here first.

1. A DISPLAY PAGE - list_page(array $query)

   For putting rows in front of a person: a grid with column sorting, a
   search box and a numbered pager ("page 3 of 80").

       Login_History::list_page([
           'login_user_id' => 12,       // scope keys the reader declares
           'filter' => 'firefox',       // free text
           'sort'   => 'created_at',    // a name the reader publishes
           'order'  => 'desc',          // 'asc' | 'desc'
           'offset' => 50,              // rows to skip
           'limit'  => 25,              // rows to return
       ]);

       => ['rows' => [...], 'total' => 1930, 'offset' => 50, 'limit' => 25]

   - ONE array argument. Every key is optional except the scope keys the
     reader requires; a key the reader does not declare is an error.
   - `total` is the number of matching rows BEFORE the page is cut - what a
     pager needs, and what a cursor cannot give.
   - OFFSET paging, because "jump to page 5" has no other answer.
   - `filter` is a string. The READER decides which columns it searches; the
     caller never names a column. It runs in the query, so it searches the
     whole set and not the page.
   - `sort` is a NAME from a list the reader publishes, mapped by the reader
     to a column. It is not a column name and never reaches SQL as written.

   VALIDATION BELONGS TO THE READER. A reader turns strings from a request
   into a query, so it trusts none of them: an unpublished sort, an order
   other than asc/desc, a limit outside 1..the reader's maximum, a negative or
   non-integer offset, a missing scope and an unknown key each THROW
   InvalidArgumentException. There is no silent fallback - a fallback is what
   hides the day a column was renamed. A scope that bounds what the caller may
   see (whose history, which site) is REQUIRED, never defaulted to
   "everything".

   Readers are UNGATED, like any model method: whether this caller may see
   this identity's rows is the calling endpoint's question.

   Implemented with App\RSpade\Core\Database\Rsx_Page_Query, which every
   display-page reader uses - parse() for the validation, result() for the
   answer - so the contract is one piece of code and not a convention.

2. A WALK - find_page(array $filter, ?string $cursor)

   For visiting EVERY matching row: an export, a sweep, a report. Keyset
   paging - pass the returned cursor back for the next page, null means done.
   No total, no caller-chosen sort (the order is the key's), and no skipped
   or repeated row while the table changes underneath, which offset paging
   cannot promise. Task_Run_Model::find_page() is this kind, and
   Rsx_Result_Set is the same idea for an application's own models.

   A numbered pager cannot be built on a walk, and a whole-table export should
   not be built on a display page. They are different jobs; pick by the job.

3. A BOUNDED SET - returns everything

   Where the framework itself caps the set, a pager is ceremony.
   Session::get_sessions_for_user() answers every signed-in device because
   rsx.sessions.max_web_sessions_per_user bounds them, and a screen that hid
   one could not offer to sign it out. A "newest N" convenience
   (Login_History::get_history_for_user($id, $limit)) is the same kind: the
   cap is in its signature.

An AGGREGATE - a count, a sum, a usage figure - is none of these: it is a
function that answers the number (File_Storage_Model::usage_report()),
computed in the database. Loading rows through a reader to add them up in PHP
is the unbounded read the readers exist to prevent.

DATABASE ACCESS RULES
----------------------
The underscore prefix has enforcement implications:

SYSTEM TABLES (_tablename) - FRAMEWORK CODE ONLY:
  - Direct queries allowed: DB::table('_tasks')->where(...)->get()
  - No ORM model required
  - Code quality checker (PHP-DB-01) automatically skips these
  - Framework code optimizes for performance over abstraction

CORE & APPLICATION TABLES (tablename):
  - Direct queries PROHIBITED
  - ORM model REQUIRED
  - Code quality checker enforces this rule
  - Example: Client_Model::where(...)->get()

CURRENT SYSTEM TABLES
----------------------

_migrations
  Purpose: Laravel migration tracking system
  Managed by: Laravel framework migration subsystem
  Records: Migration batch history, execution timestamps

_tasks
  Purpose: Background work - ONE ROW PER RUN (dispatched, scheduled or inline)
  Managed by: RSpade Task system (Task, Task_Runner, Task_Instance)
  Records: The run's lifecycle, origin, who dispatched it and for which site,
           the worker that ran it, and its small live reports (status text,
           progress, ETA, heartbeat)
  Developer API: Task_Run_Model (readers, search, lifecycle operations)
  Side tables (each cascades from _tasks): _task_reports (state JSON, state
           list, summary), _task_output (stdout / stderr / operator lines),
           _task_messages, _task_attachments (a declared blob reference),
           _task_kill_requests (force stops and kills for the kill workers)

_task_schedules
  Purpose: One row per #[Schedule] declaration - cadence, next run and the
           schedule's run statistics (each run is a _tasks row)
  Managed by: rsx:task:process (reconciled from the manifest every tick)

_file_storage
  Purpose: Content-addressable blob storage backend
  Managed by: RSpade File attachment system
  Records: Deduplicated file blobs indexed by SHA-256 hash
  Implementation: Single-instance storage pattern - multiple attachments can
                  reference the same blob. Developers never access this directly.

_file_attachments
  Purpose: Polymorphic file attachment tracking
  Managed by: RSpade File attachment API
  Records: Attachment metadata, relationships, dimensions, upload audit
  Schema: key (64-hex), file_storage_id (FK), fileable_type/id (polymorphic),
          fileable_category, site_id, created_by_ip_address
  Developer API: Attachment methods, not direct table access

_flash_alerts
  Purpose: Transient flash message queue
  Managed by: Flash_Alert system
  Records: Session-scoped UI messages (success, error, warning, info)
  Lifecycle: Created on one request, displayed on next, then deleted. Read-path
             expiry at 1 minute; an hourly sweep deletes anything past 30 minutes
             (Flash_Alert_Cleanup_Service).
  Schema: session_id, type_id, message, timestamps
  Notes: session_id is the ONLY session FK in the schema (-> _sessions, ON DELETE
         CASCADE). It carries the realm too: portal sessions are rows in the same
         table, and ids are globally unique, so no realm column exists.

_email_queue
  Purpose: Outbound email queue - one row per message
  Managed by: Rsx_Mail, Rsx_Mail_Builder, Mail_Queue_Service
  Records: Envelope, frozen subject and template data, both rendered bodies, the
           delivery state machine and what the transport answered
  Developer API: Email_Queue_Model and the rsx:mail:* commands, not the table

_email_recipients
  Purpose: Per-address opt-out and delivery counters
  Managed by: Rsx_Mail (is_blocked / block / unblock / block_all)
  Records: One row per site_id + address
  Note: The consent record behind every non-transactional send

_email_attachments
  Purpose: The files and inline images belonging to a queued message
  Managed by: Rsx_Email_Abstract attach()/embed(), the builder
  Records: Filename, mime, attachment-vs-inline, cid and order; the bytes are in
           _file_storage
  Implementation: A row here PINS its blob against File_Disposal_Service, and
                  cascades away with its _email_queue row at retention time

_sms_queue
  Purpose: Outbound SMS queue - the deliberate mirror of _email_queue
  Managed by: Rsx_Sms and the SMS drain
  Records: Number, body, category and the same delivery state machine

_sms_recipients
  Purpose: Per-number opt-out (STOP) and delivery counters
  Managed by: Rsx_Sms
  Records: One row per site_id + number

_search_indexes
  Purpose: Full-text search index storage
  Managed by: RSpade Search system
  Records: Extracted searchable content from polymorphic entities
  Schema: indexable_type/id (polymorphic), content (full-text), metadata (JSON),
          extraction_method, language, site_id
  Implementation: Automatic extraction from models, search API queries this

CURRENT CORE TABLES
--------------------

sites
  Purpose: Multi-tenancy root table
  Managed by: Multi-tenant subsystem
  Records: Tenant organizations, each with isolated data space
  Usage: Developers query to show "available sites", build tenant switchers
  Schema: name, domain, settings, active status

users
  Purpose: User account storage
  Managed by: Authentication subsystem
  Records: User credentials, profile data, authentication state
  Usage: Developers extend with additional fields, query for user listings
  Schema: email, password_hash, name, site_id (FK), active status

login_users
  Purpose: Authentication identity tracking
  Managed by: Session system
  Records: Login credentials with 365-day session persistence
  Usage: Developers query via Session::get_login_user()
  Schema: email, password_hash, display_name, last_login, is_active

user_profiles
  Purpose: Extended user profile information
  Managed by: User management system
  Records: Additional user data beyond core authentication
  Usage: Developers customize profile fields for their application
  Schema: user_id (FK), bio, avatar, preferences (JSON), custom fields

file_attachments (DEPRECATED - will become _file_attachments)
  See SYSTEM TABLES section above. Currently core, moving to system.

CURRENT APPLICATION TABLES
---------------------------
These tables are part of the starter template demonstration application.
Developers typically replace these with their own domain entities.

clients
  Purpose: Demo business entity - client/customer records
  Business domain: B2B SaaS starter template
  Schema: name, email, phone, address, site_id (FK), status

client_departments
  Purpose: Demo organizational structure
  Business domain: Client organization hierarchy
  Schema: client_id (FK), name, parent_id (FK for nested structure)

contacts
  Purpose: Demo contact management
  Business domain: People associated with clients
  Schema: client_id (FK), name, email, phone, title, site_id (FK)

projects
  Purpose: Demo project tracking
  Business domain: Client projects/engagements
  Schema: client_id (FK), name, description, status, priority, due_date

tasks (NOTE: Confusing name - different from _tasks!)
  Purpose: Demo user TODO/task list
  Business domain: User task management
  Schema: title, description, taskable_type/id (polymorphic), status, priority,
          assigned_to_user_id (FK), due_date, site_id (FK)
  WARNING: Name collision with _tasks (background jobs). Consider renaming to
           user_tasks or todo_items in future versions.

demo_products
  Purpose: Demo product catalog
  Business domain: Product/service offerings
  Schema: name, description, price, sku, category, active status

countries
  Purpose: Geographic reference data
  Business domain: International address support
  Records: ISO country codes and names
  Note: Reference data table, could be considered infrastructure

regions
  Purpose: Geographic subdivision reference data
  Business domain: State/province/region for addresses
  Records: Country subdivisions
  Note: Reference data table, could be considered infrastructure

THE FRAMEWORK CONTRACT ON APPLICATION TABLES
-------------------------------------------
An application-owned table - one with no leading underscore - may be altered by
the application that owns it. Seven of them are nonetheless MODELLED BY THE
FRAMEWORK, which reads and writes named columns on them, joins them, and in six
places points a foreign key from one of its own `_`-prefixed tables into them:

  users, login_users, sites, portal_users, user_profiles, countries, regions

Examples of what the framework reads by name: users.login_user_id and
users.site_id (Session::get_user(), the Site_Scoped global scope),
users.is_api_access_enabled (the sole external-API predicate),
login_users.email and login_users.password (every sign-in),
login_users.dark_mode and .timezone (the per-identity preferences),
and sites.id 0 (the sessionless site).

The six foreign keys INTO application-owned tables are the contract at its
strongest, because the framework's own storage cannot be written at all if the
target is gone: _file_attachments.site_id -> sites.id,
_sessions.portal_user_id -> portal_users.id,
_sso_identities.login_user_id -> login_users.id,
_two_factor_credentials.login_user_id -> login_users.id,
_user_permissions.user_id -> users.id and
_portal_notifications.portal_user_id -> portal_users.id.

THE DECLARATION is App\RSpade\Core\Database\Schema_Contract: one map, per
table, of the required columns - each naming the framework code that reads or
writes it - the unique indexes the framework relies on, the foreign keys, the
rows it assumes (sites id 0, the configured default site, and the initial user
pair when the database has been seeded at all), and the semantic probes.

THE CHECK is the "Schema Contract" row of rsx:health (rsx:man health), in every
mode: one row per table, plus foreign keys, rows and semantics. A missing table,
column, unique index, foreign key or row is a FAIL naming the consumer that will
break; a semantic finding is a WARN.

WHAT IS NOT IN THE CONTRACT, and why:

  - The audit pairs (created_by_id/_type, updated_by_id/_type,
    deleted_by_id/_type) and created_at/updated_at. migrate:normalize_schema
    adds them to every table on every migrate, so a finding could only duplicate
    a repair that has already happened.
  - deleted_at is the exception: normalization never adds it, and losing it
    fatals every query a soft-deleting model issues, so it IS required on users,
    login_users, portal_users and sites.
  - Column types, nullability and defaults. Presence is what the framework
    depends on and what an ALTER realistically removes.
  - Columns the framework only declares on a model and never reads.

AN APPLICATION THAT ALTERS ONE OF THESE TABLES KEEPS THE CONTRACT. Adding
columns, indexes and relations of its own is expected; removing or renaming one
of the contracted columns is not, and rsx:health is where that is discovered
rather than in a stack trace on a request. The same rule extends the map in the
other direction: a new framework read of an application-owned table adds its
column to Schema_Contract in the same commit.

ARCHITECTURAL PRINCIPLES
-------------------------

1. SEPARATION OF CONCERNS
   System tables implement framework features invisibly. Core tables provide
   developer-facing infrastructure. Application tables express business domain.

2. ABSTRACTION BOUNDARIES
   System table schemas are implementation details. Core table schemas are API
   contracts. System tables can change without migration pain if APIs remain stable.

3. PERFORMANCE VS CONSISTENCY
   System tables prioritize performance (direct queries, denormalization OK).
   Core/Application tables prioritize data integrity (ORM, relationships, validation).

4. MIGRATION STRATEGY
   All migrations run chronologically when `php artisan migrate` is executed,
   regardless of whether they affect system, core, or application tables.

   System tables: Migrations written and shipped by framework developers
   Core tables: Migrations written and shipped by framework developers
   Application tables: Migrations written by application developers

   When a framework update (rsx:framework:pull) delivers new framework
   migrations, they run alongside application migrations in date order when
   migrate is executed (the updater itself runs migrate --framework-only).

5. DOCUMENTATION LEVEL
   System tables: Internal documentation only
   Core tables: Full API documentation required
   Application tables: Developer-documented

FUTURE CONSIDERATIONS
---------------------

Planned Changes:
- Rename 'migrations' to '_migrations' (Laravel supports configuring this)
- Move 'file_attachments' to '_file_attachments' (pure system implementation detail)
- Consider renaming 'tasks' to 'user_tasks' or 'todo_items' to avoid confusion with '_tasks'

Potential System Tables:
- _cache (if implementing database cache driver)
- _jobs (if using database queue driver - currently using '_tasks')
- _notifications (if implementing notification queue)
- _websocket_connections (if implementing WebSocket presence tracking)

MIGRATION MECHANICS
-------------------

When renaming a table to add underscore prefix:

1. Create migration to rename table
2. Update all Model classes: protected $table = '_newtablename';
3. Update direct queries in framework code
4. Update foreign key references in other tables (if any)
5. Update seeders, factories, tests
6. Run code quality checker to find missed references
7. Test all affected subsystems

Example migration:
  Schema::rename('file_storage', '_file_storage');

The underscore prefix is purely a naming convention - database engines treat
these identically to non-prefixed tables. The convention exists for developer
clarity and code quality enforcement.

DEVELOPER GUIDANCE
------------------

When creating new tables, ask:

Q: Will application developers query this directly?
   YES -> Core/Application table (no prefix)
   NO -> System table (underscore prefix)

Q: Is this an implementation detail of a framework subsystem?
   YES -> System table (underscore prefix)
   NO -> Core/Application table (no prefix)

Q: Would changing the schema break the developer-facing API?
   YES -> Core table (no prefix) - schema is part of the API contract
   NO -> System table (underscore prefix) - implementation detail

Examples:
- User login sessions? System (_login_sessions) - API is Session:: methods
- User accounts? Core (users) - developers extend and query this
- Search index? System (_search_indexes) - API is Search::query()
- Client records? Application (clients) - business domain entity

Column kinds the MODEL declares (the migration carries only the storage type):
- An enum: BIGINT column, mapped by public static $enums (rsx:man enums).
- A polymorphic reference: a BIGINT {relation}_type + {relation}_id pair,
  declared in $type_ref_columns (rsx:man polymorphic).
- Rich text or a custom notation: a TEXT column, typed by public static
  $text_types so the encoding is stated once and every print, edit, export
  and index asks the value (rsx:man text_types).

CONCLUSION
----------

The underscore prefix system creates a clear architectural boundary between
framework implementation details and developer-facing data structures. This
enables the framework to optimize system tables for performance while maintaining
API stability, and helps developers understand which tables are theirs to use
versus which are managed by framework subsystems.
