NAME
    login_requirements - what a signed-in user must still do before the site
    is theirs: enroll a second factor, accept terms, set a profile picture,
    connect an account - staff and the client portal

SYNOPSIS
    # One class per requirement, anywhere under rsx/ - the manifest finds it
    class Terms_Requirement extends Login_Requirement_Abstract
    {
        const REALM = 'staff';          // or 'portal'
        const ORDER = 10;               // the sequence; default 100

        public static function is_satisfied(Rsx_Model_Abstract $user): bool
        {
            return $user->terms_accepted_at !== null;   // the truth, nothing else
        }

        public static function screen(): string
        {
            return 'Terms_Controller::index';           // where the user is sent
        }

        public static function surfaces(): array
        {
            return ['Terms_Controller::accept'];        // all else it may reach
        }
    }

    # The requirement's endpoint does the work, then asks where to go next
    $user->terms_accepted_at = Rsx_Time::now_iso();
    $user->save();
    return redirect(Login_Requirements::recheck() ?? Rsx::Route('Dashboard_Index_Action'));

    # Policy changed for people already signed in
    Login_Requirements::recheck_user($user);

DESCRIPTION
    Some applications need more than a correct password before a user may
    use them: an administrator requires a second factor, the terms of service
    changed, the account must be connected to a storage provider, a profile
    is incomplete. Other systems call these "required actions" (Keycloak),
    "post-login actions" or "interstitials". RSpade calls them LOGIN
    REQUIREMENTS: things a SIGNED-IN identity must do before it is ADMITTED.

    While a requirement applies and is unmet, the identity is on the session
    - it signed in, and its requirement's own pages act on it - but every
    identity reader answers NOT LOGGED IN, everywhere except the surfaces
    that requirement lists. Every page, Ajax endpoint, model fetch, realtime
    subscription and file read treats the user as anonymous. They can do the
    requirement and nothing else, and the moment it is met the next request
    lets them in.

    THIS IS A SECURITY BOUNDARY, not a redirect. A redirect on page load is a
    nudge: Ajax endpoints and model fetches would keep answering, so a user
    told to enroll a second factor could use the whole application from the
    browser console. Here, a surface nobody listed sees an anonymous caller
    and refuses it - the boundary fails CLOSED.

TWO STAGES, KEPT APART
    AUTHENTICATION answers "who are you?": a password, a federated sign-in, a
    passkey, and ANSWERING a second-factor challenge (rsx:man two_factor). The
    identity is not proven yet, so it is represented as SIGNED OUT with the
    identity parked as inert data - nothing about the account is reachable.

    LOGIN REQUIREMENTS answer "you have proven who you are - is your account
    fit to use the site?": ENROLLING a second factor, accepting terms, a
    profile picture, connecting an account. The identity IS proven, and the
    steps reuse ordinary features that need it - the upload endpoint, an OAuth
    callback that writes to the user's row, a form that saves the profile.
    Signing out would leave those features nobody to act on, so the identity
    stays signed in and the READERS conceal it instead.

    Answering a second factor is stage one; being required to set one up is
    stage two.

HOW IT WORKS
    THE READERS. Session::is_logged_in(), get_login_user_id(),
    get_login_user(), get_user() and the Portal_Session twins answer as if
    signed out while the realm has requirements outstanding - unless the
    request is being served by the screen() or a surfaces() entry of one of
    them. Concealment is in the readers, not the surfaces, so there is no
    flag a surface can forget to check.

    THE SURFACE. The dispatch seams record what the request is for: the page
    dispatcher the matched route ('Controller::method'), Ajax::execute() each
    endpoint call (a batch binds and restores per call). Before a surface is
    known - early boot, CSRF, transport checks - a pending identity is
    concealed.

    THE LIST. Computed when an identity signs in (Session::
    set_login_user_id(), Portal_Session::set_portal_user_id()) and when the
    staff site changes (Session::set_site_id() - staff requirements are
    evaluated per site membership), cleared on sign-out, and stored on the
    session row (_sessions.login_requirements). A request reads it with the
    row it already loaded. A requirement class deleted since the list was
    computed is passed over.

    RE-EVALUATION IS AUTOMATIC. When a pending identity asks for a surface its
    requirements do not list, every requirement is evaluated again before it
    is refused - once per request. So doing what was asked is enough: the next
    request for anything lets the user in, and a requirement's endpoint never
    has to announce completion. recheck() exists to tell an endpoint where to
    send the user next.

    STEERING. A pending identity refused by a PAGE'S gates is redirected to
    the first outstanding requirement's screen, never to the login page. One
    refused by an AJAX endpoint gets error_code requirement_pending with
    metadata.destination, and the JS Ajax layer navigates there on its own
    (rsx:man ajax_error_handling). A PUBLIC surface is served to it as to any
    anonymous visitor - including the login page.

    ORDER. Outstanding requirements are taken by ORDER, then class name; the
    destination is always the first one's screen.

    NOT SUBJECT:
        - a bearer-key API call - its identity is the key's, never the
          session's;
        - the CLI - a script acting as a user is not a browser signing in;
        - an impersonation, unless the requirement says
          applies_while_impersonating() (default false): the person viewing
          the account signed in as themselves, and cannot enroll a factor for
          its owner anyway.

    With no requirement classes declared, none of this exists and nothing is
    read.

THE CLASS
    Extends App\RSpade\Core\Login\Login_Requirement_Abstract. Lives anywhere
    under rsx/ - beside its screen is the natural place.

    const REALM (required)
        'staff' or 'portal'. No default: a requirement read against the wrong
        realm's user is one nobody can satisfy. A missing or invalid REALM
        throws, naming the class, and fails the rsx:health row.

    const ORDER (default 100)
        Where it comes in the sequence.

    is_satisfied(Rsx_Model_Abstract $user): bool (required)
        THE TRUTH and the only completion signal - there is no "mark done".
        $user is the site User_Model for 'staff' (so a requirement may differ
        per site), the Portal_User_Model for 'portal'. Read state from $user,
        not from Session: the session is what this answer decides about.
        Evaluated at sign-in, on a site switch, on recheck(), and on every
        refused request of a pending identity - keep it cheap.

    screen(): string (required)
        The route target ('Controller::method') that does the requirement, in
        the requirement's realm: #[Route] for staff, #[Portal_Route] for the
        portal. Reachable while the requirement is outstanding without being
        listed in surfaces(). A Blade route is the simple choice: a SPA
        bootstrap would expose a whole module's client side to a user who can
        call none of its endpoints.

    surfaces(): array
        Every other route and Ajax endpoint the screen needs, framework ones
        included ('Rsx_Two_Factor_Controller::totp_begin',
        'File_Attachment_Controller::upload'). In one place, so the whole of
        what a not-yet-admitted user can reach reads in one file. A listed
        surface's #[Auth] gates still run - it simply sees the user.
        A model fetch is not a listable surface; a screen that needs data
        uses its own endpoint.

    applies_while_impersonating(): bool (default false)

    Logout: a #[Auth('public')] logout route needs no listing - it runs for
    an anonymous caller, and signing out reads the session itself. A logout
    gated is_logged_in must be listed by every requirement.

THE API (App\RSpade\Core\Login\Login_Requirements)
    outstanding(?string $realm = null): array
        The unmet requirements' class names, in order. $realm defaults to the
        realm of the request.
    is_pending(?string $realm = null): bool
    destination(?string $realm = null): ?string
        The first outstanding requirement's screen URL, or null.
    recheck(?string $realm = null): ?string
        Evaluate now; the next destination, or null when the identity is
        admitted. What a requirement's endpoint calls after doing its work.
    recheck_user(Rsx_Model_Abstract $user): void
        Re-evaluate every live session of a User_Model (that site's sessions)
        or a Portal_User_Model. For a policy changed mid-session - "every
        administrator must now enroll a factor" - so it reaches people already
        signed in on their next request.
    all(string $realm): array
        Every declared requirement class for a realm, in order.

    Everything prefixed with an underscore is the framework's own seam.

EXAMPLES
    An administrator-required second factor (the reference application):

        class Two_Factor_Enrollment_Requirement extends Login_Requirement_Abstract
        {
            const REALM = 'staff';

            public static function is_satisfied(Rsx_Model_Abstract $user): bool
            {
                return !$user->is_2fa_required || Rsx_Two_Factor::is_enabled((int) $user->login_user_id);
            }

            public static function screen(): string
            {
                return 'Login_Controller::two_factor_setup';
            }

            public static function surfaces(): array
            {
                return [
                    'Rsx_Two_Factor_Controller::totp_begin',
                    'Rsx_Two_Factor_Controller::totp_confirm',
                    'Rsx_Two_Factor_Controller::passkey_register_begin',
                    'Rsx_Two_Factor_Controller::passkey_register_confirm',
                ];
            }
        }

    The screen mounts <Totp_Enrollment> or <Passkey_Register>; on 'enrolled'
    or 'registered' it navigates to '/', which re-evaluates and admits.

    A profile picture: screen() is the upload page, surfaces() lists
    'File_Attachment_Controller::upload' and the endpoint that claims the
    upload onto the user; is_satisfied() checks the user has one.

    Connect a storage account: screen() explains and starts the OAuth trip,
    surfaces() lists the begin route and the provider's callback route (the
    callback must see the user to store the tokens on them); is_satisfied()
    checks a connection row exists.

    Accept terms: screen() shows them; surfaces() lists the accept endpoint,
    which stamps the user and returns recheck()'s destination.

THE REFERENCE IMPLEMENTATION
    rsx/app/login/two_factor_enrollment_requirement.php - the requirement
    rsx/app/login/login_controller.php - two_factor_setup(), its screen
    rsx/app/login/login_two_factor_setup.blade.php / .js - the screen
    Downstream: system/app/RSpade/resource/reference_app/.

HEALTH
    rsx:health "Login Requirements" FAILs on a requirement with no valid
    REALM, a screen() that is not a route in its realm, or a surfaces() entry
    that names no route or endpoint - each of which would otherwise surface
    only when a user signed in and was sent somewhere that is not there.

RSX VS LARAVEL
    Laravel: a middleware that redirects ("must verify email",
    "must accept terms"), attached route by route. Every route and API
    endpoint left out of the group - and every Ajax call, which a redirect
    does not stop - is a way around it.
    RSX: one class per requirement; the framework conceals the identity from
    every reader except the surfaces that requirement lists, so a forgotten
    route is refused rather than open, and re-evaluates on the next request
    so completion needs no bookkeeping.

TROUBLESHOOTING
    A user loops back to the requirement screen after completing it
        is_satisfied() still answers false - it is the only completion signal.
        Check what it reads was actually written.

    The requirement screen itself redirects to the login page
        The screen is gated by something besides is_logged_in that fails for
        this user, or the route target in screen() is not the one served
        (check the rsx:health row).

    A step on the screen fails with "Please finish signing in to continue"
        An endpoint the screen calls is not in surfaces().

    Login requirement X must declare const REALM
        Add const REALM = 'staff' or 'portal'.
