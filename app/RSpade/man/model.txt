OVERVIEW

All RSX models must extend Rsx_Model_Abstract, which provides:
- Column declarations: one $columns property says what each column holds
  (enum, text type, type ref, money, secret, revision exclusion, derived value)
- Mass assignment prevention (explicit field assignment only)
- Eager loading prevention (explicit queries only)
- Ajax ORM fetch() system
- Automatic boolean casting for TINYINT(1) columns
- Relationship management via #[Relationship] attribute
- Fact groups: columns that hold one fact, for edit conflict detection

The how-to, including a checklist for choosing a column's kind, is skill
rspade:models.

COLUMN DECLARATIONS

A model declares what KIND of value each of its columns holds in ONE static
property, one entry per column:

    public static $columns = [
        'status_id'     => ['enum' => [
            1 => ['constant' => 'STATUS_ACTIVE', 'label' => 'Active'],
            2 => ['constant' => 'STATUS_ARCHIVED', 'label' => 'Archived', 'selectable' => false],
        ]],
        'description'   => ['text_type' => Rich_Text::class],
        'fileable_type' => ['type_ref' => true],
        'budget'        => ['money' => true],
        'api_secret'    => ['never_export' => true],
        'view_count'    => ['revision_exclude' => true],
        'project_id'    => ['derived' => 'derive_project_id', 'from' => ['parent_type', 'parent_id']],
    ];

Keys of an entry (anything else is an error):

    enum              integer-keyed map of value => properties (ENUM COLUMNS)
    text_type         class name of an Rsx_Text_Abstract subclass (TEXT TYPE COLUMNS)
    type_ref          true - the _type column of a polymorphic pair (TYPE REF COLUMNS)
    money             true - a DECIMAL(p,2) amount read as Rsx_Money (MONEY COLUMNS)
    never_export      true - never sent in any payload (NEVER EXPORT COLUMNS)
    revision_exclude  true - not recorded in revision history (REVISION EXCLUDED COLUMNS)
    derived, from     derive method + this record's source columns (DERIVED COLUMNS)

Rules of the grammar:
- A flag is the literal true or absent; false is an error.
- At most one of enum, text_type, type_ref, money per column. never_export
  combines with anything; revision_exclude with anything except derived (a
  derived column is never recorded already). A derived column may also be an
  enum, text type, type ref or money: its computed value is assigned through
  setAttribute(), so the kind applies.
- derived and from appear together.
- 'column' => [] declares an explicitly plain column.
- A model with nothing to declare declares nothing: no empty $columns.

Every declared column, and every column a from list names, must be a column
of the model's table. rsx:check reports one that is not (MODEL-ENUM-01), and
the write side throws the first time it asks - a save of a model with derived
columns, rederive(), Form_Edit::run():

    X_Model::$columns declares 'col', which is not a column of the model's
    table. Add the column with a migration, or correct the declaration.

A model READ never checks, so a model read during a migration that has not
yet added a declared column still works.

The framework reads column declarations from $columns ONLY. A model class
declaring a static $enums, $text_types, $type_ref_columns, $neverExport or
$revision_exclude property fails the manifest build - such a property would
declare nothing, and a secret listed there would be sent to every browser.

   Inheritance
       The effective declaration overlays every class from Rsx_Model_Abstract
       down to the model, base first. A class's entry for a column REPLACES its
       parent's entry for that column wholesale; entries are never merged key by
       key, so an override that changes one key of an inherited entry restates
       the rest. A replacing entry may never drop a protection: one replacing an
       entry that carries never_export carries it too, and the audit type
       columns Rsx_Model_Abstract declares type_ref (created_by_type,
       updated_by_type, deleted_by_type) keep type_ref. A class override of a
       core model declares only the columns it adds or changes
       (rsx:man class_override).

   Enforcement
       MODEL-COLUMNS-01 (manifest build, FATAL): unknown keys, non-true flags,
       two kinds on one column, malformed enum maps and text types, derived
       without from (or the reverse), a derive method that is not a public,
       non-static method of the class taking no required argument, a from list
       naming the column itself, derived beside revision_exclude, derived
       columns depending on each other in a cycle, a replacing entry dropping
       never_export or an audit type_ref, a $casts entry on a money column,
       and the property names above.
       MODEL-COLUMNS-02 (rsx:check): a direct Model::$columns read.
       MODEL-DERIVED-01 (rsx:check): an assignment of a derived column.
       MODEL-ENUM-01 (rsx:check): a declared or from column missing from the
       table.
       MODEL-MONEY-01 (rsx:check): a money column that is not DECIMAL(p,2)
       with p at most 18.
       MODEL-DECIMAL-01 (rsx:check): a DECIMAL, FLOAT or DOUBLE column of the
       model's table with no $columns entry (money, or [] for not money).

   Reading the declaration
       Model::$columns answers ONE class's declaration and misses everything
       inherited; it is never read directly (MODEL-COLUMNS-02). Read:

       columns()                     every effective entry, overlaid
       enum_columns()                column => value map, every enum column
       enum_values('col')            one column's value map; throws
                                     "X_Model::col is not an enum column"
                                     for any other column
       text_type_columns()           column => text type class
       text_type_or_null('col')      the column's text type, or null
       type_ref_columns()            every type-ref column, audit ones included
       money_columns()               every money column
       is_money_column('col')        whether the column is declared money
       never_exported_columns()      every never_export column
       revision_excluded_columns()   revision_exclude columns plus every
                                     derived column
       derived_columns()             column => ['method' => ..., 'from' => [...]],
                                     in dependency order

       All are static and memoized per class. JavaScript: the enum helpers
       below, Model.is_derived_column('col') and Model.is_money_column('col').

   Not declared in $columns
       Dates, datetimes and TINYINT(1) booleans are read from the live schema
       (AUTOMATIC BOOLEAN CASTING; dates stay ISO strings). Relationships are
       #[Relationship] methods. A computed value that is not stored is an
       APPENDED PROPERTY. One fact stored in several columns is $fact_groups.
       Per-type fields are $detail_tables (rsx:man detail_tables). The audit
       authorship pairs are stamped by save() and never declared
       (rsx:man actors). A `_`-prefixed column is a framework system column
       (rsx:man database_schema_architecture).

   The generated header
       rsx:constants:regenerate (run by migrate in development) rewrites each
       model's _AUTO_GENERATED_ docblock and enum constants from the live table
       and $columns; never edit them by hand. Each @property line states the
       type a read returns and the column's kind:

       * @property int $status enum: STATUS_PENDING, STATUS_DONE (also $status__label and the other $status__* properties)
       * @property \Rsx\Lib\TextTypes\RichText\Rich_Text $description text type: a value object, filtered on write
       * @property string $taskable_type type ref: a model class name, stored as a type-ref id
       * @property \App\RSpade\Core\Database\Money\Rsx_Money $budget money: a value object, two decimal places, never a float
       * @property-read int $project_id derived: computed by derive_project_id() from taskable_type, taskable_id, direct_project_id; never assigned
       * @property string $password never exported to the browser
       * @property string $last_seen_at not recorded in revisions
       * @property string $hour_estimate decimal

       A money column reads as Rsx_Money; any other DECIMAL, and a JSON column
       without an array cast, reads as a string (noted decimal / json);
       TINYINT(1) as bool; dates and datetimes as strings.

ENUM COLUMNS

An enum column is a BIGINT whose integer values carry constants, labels and
any custom properties:

    public static $columns = [
        'status_id' => ['enum' => [
            1 => ['constant' => 'STATUS_ACTIVE', 'label' => 'Active', 'order' => 1],
            2 => ['constant' => 'STATUS_INACTIVE', 'label' => 'Inactive', 'order' => 2],
        ]],
        'role_id' => ['enum' => [
            1 => ['constant' => 'ROLE_ADMIN', 'label' => 'Administrator'],
            2 => ['constant' => 'ROLE_USER', 'label' => 'User'],
        ]],
    ];

Each 'constant' becomes a class constant (Model::STATUS_ACTIVE), written into
the model by rsx:constants:regenerate.

Magic Properties (Instance):
- $model->status_id__label - Get label for current enum value
- $model->status_id__constant - Get constant name for current value
- $model->status_id__order - Get sort order for current value

Magic Methods (Static):
- Model::status_id__enum() - Get all enum definitions (sorted by 'order')
- Model::status_id__enum_select() - Get key/label pairs for dropdowns
- Model::status_id__enum_ids() - Get all possible enum values

Enum value properties can include any custom keys (label, order, constant,
color, icon, etc.). All properties are exported to JavaScript via toArray().
The raw map is Model::enum_values('status_id').

Optional 'selectable' property (default true) controls dropdown visibility:
    2 => ['constant' => 'STATUS_ARCHIVED', 'label' => 'Archived', 'selectable' => false]

Full treatment: rsx:man enums.

TEXT TYPE COLUMNS

An enum says what an integer column MEANS; a text type says what KIND of
string a TEXT column holds - plain text, sanitized HTML from a WYSIWYG, or an
application notation such as {{Client_Model:42}} - so that the encoding is
stated once, on the column, and every place that prints, edits, exports or
indexes it asks the value instead of remembering. Without it each call site
independently chooses an escape, a widget and a sanitizer, and when two
disagree the result is markup shown as literal text or user input rendered
unescaped, silently.

    public static $columns = [
        'description' => ['text_type' => Rich_Text::class],
    ];

A declared column is read as a VALUE OBJECT: filtered by the type's sanitizer
on every write, printed on a page by plain interpolation (the type's own
component renders it), edited by whatever widget the type names
(<{Project_Model.editor_component_for('description')} $name="description" />),
reduced by to_plain_text() for a CSV cell or an index, and asked is_empty() -
never === ''.
Used as a string anywhere it THROWS, in PHP and in JavaScript. An undeclared
TEXT column is an ordinary string; declaration is opt-in.

Setting up a rich-text field: the migration column is plain TEXT (LONGTEXT
after normalization); declare it as above; the form uses the editor tag; the
view interpolates it; an endpoint assigns $params['description'] to the column
and validates with is_empty() on the read-back. The shipped Rich_Text type
(rsx/lib/text_types/rich_text/) is the Quill-backed reference. Converting an
EXISTING plain-text column is two acts: a raw-SQL migration that re-encodes the
rows into the type's storage form, then the declaration.

Designing a new type: two required methods, sanitize_encoded() (the sanitizer)
and encode_plain_text() (plain text -> the encoding), plus whatever dedicated
readers the encoding needs, and a JavaScript class of the
same name naming the PRINTER and EDITOR components. The contract, two worked
types and the security design are rsx:man text_types; the how-to is skill
rspade:text-types.

MONEY COLUMNS

A DECIMAL(p,2) column holding an amount of money (p at most 18) is declared
money:

    public static $columns = [
        'budget'        => ['money' => true],
        'hour_estimate' => [],                  // a DECIMAL that is not money
    ];

It reads as an Rsx_Money (or null): an exact, immutable amount that is never a
float, compared and computed only through its methods (equals(), add(),
multiply($factor, $rounding), ...) and printed by plain interpolation
(<%= project.budget %>). Assignment takes an Rsx_Money, a decimal string, an
int of whole units or the {__MONEY} envelope and refuses a float, typed text
and an amount beyond the column's limit (money_limit('col')). It travels to
JavaScript and the external API as {"__MONEY": "1234.56"}, is edited by
<Money_Input>, totalled by sum_money('col') and read from a submission by
Model::money_from_submitted('col', $value). No $casts entry may name it. Every
DECIMAL, FLOAT and DOUBLE column is declared money or not money
(MODEL-DECIMAL-01). The contract is rsx:man money; the how-to is skill
rspade:money.

TYPE REF COLUMNS

A polymorphic reference is the BIGINT pair {relation}_type + {relation}_id.
The _type column is declared a type ref:

    public static $columns = [
        'fileable_type' => ['type_ref' => true],
    ];

It stores a _type_refs integer id and reads and writes as a model class
basename ('Client_Model'), so stock morphTo() / morphMany() work over it. A
morph relation over an undeclared _type column fails the manifest build
(POLY-01). Rsx_Model_Abstract declares the audit type columns
(created_by_type, updated_by_type, deleted_by_type). Full treatment:
rsx:man polymorphic.

NEVER EXPORT COLUMNS

A column that must never leave the server is declared never_export:

    public static $columns = [
        'api_token'     => ['never_export' => true],
        'client_secret' => ['never_export' => true],
    ];

toArray() - the one serializer behind fetch(), relationship and list payloads,
window.rsxapp.user and the external API - unsets every never-exported column
AFTER Laravel has built the array, so nothing (makeVisible(), $visible) can
put one back.

An override can never drop never_export from an inherited entry (see
Inheritance above): a subclass - a class override of a core model included -
only adds secrets. The framework identity models already withhold theirs:
Login_User_Model password and remember_token, Portal_User_Model password and
metadata, User_Model the invite columns.

Which control to use: anything whose disclosure would be a security event (a
password hash, a token, a secret, an open key/value bag) is never_export.
Laravel's $hidden is advisory - makeVisible() removes a column from it - and is
for tidiness only. getAttributes() and attribute reads ($model->password)
bypass both: they are server-side raw access, never a payload.

The same declaration covers the REVISION lane. On a model with $revisions, a
change to a never-exported column is recorded with BOTH sides replaced by
Revision::REDACTED, so a history still says the column changed and the stored
document never holds its value (rsx:man revisions, REDACTED COLUMNS). A secret
therefore needs no revision_exclude; a column carrying both is not recorded at
all.

A column named password, token or secret (or ending _password, _token,
_secret) that is not never_export is flagged by rsx:check
(MODEL-NEVER-EXPORT-01, read from the live schema). A column exported on
purpose is declared in the model's file with its reason:

    // @MODEL-NEVER-EXPORT-01-EXCEPTION display_token - a public badge token

REVISION EXCLUDED COLUMNS

On a model with $revisions, a revision_exclude column is not recorded:

    public static $columns = [
        'view_count' => ['revision_exclude' => true],
    ];

For values that change without anybody changing them: counters, last-seen
stamps, cached aggregates. The column is still stored; it is not a security
control (a secret is never_export). updated_at, the updated_by pair, every
`_`-prefixed system column and every derived column are excluded
automatically. rsx:man revisions.

DERIVED COLUMNS

A derived column is a STORED column whose value a public method of the model
computes, and which nobody assigns:

    public static $columns = [
        'project_id' => ['derived' => 'derive_project_id', 'from' => ['taskable_type', 'taskable_id', 'direct_project_id']],
    ];

    public function derive_project_id(): ?int { ... }

save() computes it on an INSERT and on every UPDATE in which a from column
changed; $record->rederive() recomputes it when what the method reads lives
elsewhere and has moved. An assignment throws:

    Task_Model::project_id is a derived column - Task_Model::derive_project_id()
    computes it from [taskable_type, taskable_id, direct_project_id] on save. It
    is never assigned. Assign its source column(s), or call rederive().

A save that changes only derived columns leaves updated_at and the updated_by
pair untouched and records no revision. The complete contract - when save()
derives, rederive(), the refusals, cross-record dependents, migrations and the
rsx:derived:check / rsx:derived:rebuild commands - is rsx:man derived_columns.

FACT GROUPS

One fact a person edits as one thing is sometimes stored across several
columns, and which column holds it can depend on the record's shape. The
worked case is an activity's "when": an all-day activity keeps its day in
date_start / date_end with the times null, a timed one keeps its day inside
time_start / time_end with date_start null, and its form shows one Date box
either way. Other shapes: a polymorphic type/id pair edited as one field, an
amount stored with the quantity and rate it is the product of.

THE TRAP. Form_Edit finds a conflict per column: another editor's save is a
conflict only with a submission of a field stored in the column that save
changed. When their re-date landed in time_start and the stale submission
sends a Date field stored in date_start, nothing matches - the stale save
moves the activity back to the old day, a 200, no question, no log line.

Declare the columns that are one fact:

    public static $fact_groups = [
        'when' => ['label' => 'Date and time', 'columns' => ['date_start', 'date_end', 'time_start', 'time_end']],
    ];

A change saved to ANY column of a group is a change to the whole group:
Form_Edit treats it as a change to every form field stored in any column of
the group, on the record and on each coupled record, and always asks about it
(rsx:man form_conventions, EDITING A RECORD). The label names the group in the
conflict question. The declaration is in COLUMN terms because it is a fact
about the model, true whichever screen edits it; the endpoint's column-to-field
map says which form field each column stores.

Declare one whenever two or more columns are edited as one thing. There is no
per-model "is this a conflict?" callback, deliberately: a callback that answers
"no" by mistake silently loses an edit, and a declaration is applied the same
way everywhere and can be tested.

Model::fact_groups() reads it, checked the first time it is read against the
table's live columns - every column exists, belongs to one group only, a group
has a label and at least two columns - and throws naming the model otherwise.
The manifest holds code facts only, so a column's existence is checked at first
use, not at build: give every group a test (a save of one column, then a stale
submission of a field stored in another, is asked about).

MASS ASSIGNMENT PREVENTION

Mass assignment is explicitly prohibited. Use explicit field assignment:

    // CORRECT
    $model = new User_Model();
    $model->name = $request->input('name');
    $model->email = $request->input('email');
    $model->save();

    // WRONG - throws MassAssignmentException
    $model = User_Model::create(['name' => 'John', 'email' => 'john@example.com']);
    $model->fill(['name' => 'John']);
    $model->update(['name' => 'John']);

Blocked methods: fill(), forceFill(), create(), firstOrCreate(), firstOrNew(),
updateOrCreate(), update()

EAGER LOADING PREVENTION

All forms of eager loading throw exceptions. Use explicit queries:

    // WRONG - throws exception
    $users = User_Model::with('posts')->get();
    $user->load('posts');

    // CORRECT - explicit queries
    $users = User_Model::all();
    foreach ($users as $user) {
        $posts = Post_Model::where('user_id', $user->id)->get();
    }

Rationale: Prevents recursive loading chains that accidentally cascade across
the entire database. Future optimization will use caching strategies instead.

load(), loadMissing() and loadCount() refuse a RELATION. An empty relation list is
not a load: each returns $this for it.

REFRESHING A RECORD

    $invoice->refresh();

re-reads the row in place and returns the same instance: the attributes become what
the database holds now, and unsaved changes on the instance are discarded. It is the
call for an instance left stale by a write that did not go through it - raw SQL,
DB::table(), ->raw_bulk(), a service that saved its own copy of the row.

Every relation the instance had read, and its detail row (rsx:man detail_tables), is
DROPPED rather than reloaded: the next read of one queries again, so nothing the
instance answers afterwards predates the refresh. A reference the caller took to a
related record before the refresh is that caller's own, and is as stale as it was.

See: php artisan rsx:man rspade (DATABASE PHILOSOPHY section)

AJAX ORM (Model Fetch System)

Models can opt-in to client-side fetching by implementing fetch() with
#[Ajax_Endpoint_Model_Fetch] attribute:

    #[Ajax_Endpoint_Model_Fetch]
    public static function fetch($id)
    {
        // Check authorization
        if (!Session::is_logged_in()) {
            return false;
        }

        // Fetch single record
        $model = static::find($id);
        return $model ?: false;
    }

JavaScript usage:
    const product = await Product_Model.fetch(1);
    console.log(product.status_label);  // Enum properties populated
    console.log(Product_Model.STATUS_ACTIVE);  // Static enum constants

Returns instantiated JS model class with enum properties and optional custom
methods. See: php artisan rsx:man model_fetch

RELATIONSHIPS

Define relationships using #[Relationship] attribute to prevent Laravel from
auto-detecting non-relationship methods:

    #[Relationship]
    public function posts()
    {
        return $this->hasMany(Post_Model::class);
    }

Only methods with #[Relationship] are considered relationships. This prevents
methods like is_active() from being mistaken for relationships.

Note: Eager loading is still blocked. Relationships are supported but must be
loaded with explicit queries.

AUTOMATIC BOOLEAN CASTING

TINYINT(1) columns are automatically cast to boolean without manual $casts
definition. The framework reads the live schema (Rsx_Schema, cached under the
state key) to detect boolean columns at runtime.

Manual $casts entries take precedence over automatic detection.

APPENDED PROPERTIES ($appends)

A computed value that must reach JavaScript, and is not stored, is an APPENDED
PROPERTY: DECLARED, not hand-copied onto a payload. (A computed value that must
be stored - queried, sorted, indexed - is a DERIVED COLUMN instead.) The
declaration is Laravel's $appends plus an accessor per name, and the
accessor DELEGATES to the public method that defines the value:

    COST. An accessor runs on every serialization - a single fetch, a batch
    fetch, any toArray() over a list. One that reads other rows is therefore
    paid once per record; keep such computations to what a single-record view
    needs, and let a list select the columns it wants rather than serialize.

    protected $appends = ['party_id_formatted'];

    public function party_id_formatted()
    {
        return '#PA' . str_pad($this->id, 3, '0', STR_PAD_LEFT);
    }

    public function getPartyIdFormattedAttribute(): string
    {
        return $this->party_id_formatted();
    }

The method is the definition; the property is only its serialization. Delegating is
what keeps the two from drifting - never re-implement the computation in the accessor.

The accessor is one of the two Laravel spellings the naming rule exempts
(get{Property}Attribute / set{Property}Attribute); everything else stays
underscore_case.

WHERE THE VALUE SHOWS UP. Eloquent applies $appends inside parent::toArray(), which
Rsx_Model_Abstract::toArray() calls first, so an appended value rides EVERY payload the
model produces: fetch(), portal_fetch(), an embedded relationship, a list. That is the
difference that matters. A key hand-added inside fetch():

    $data = $party->toArray();
    $data['party_id_formatted'] = $party->party_id_formatted();   // NOT the route

lands on that ONE payload and on none of the others, has to be repeated in the portal
twin, and nothing notices when a sibling model forgets it.

WHAT THE JS SIDE GETS. The model stub generator reads $appends and declares each name on
Base_<Model>_Model.js as a JSDoc @property - a documented, read-only surface an editor
completes and a reader of the stub can see:

     * @property {*} party_id_formatted - appended property (computed by the PHP model); read-only

It is declared as documentation rather than as a real class member on purpose: the ORM
ASSIGNS a fetched record's fields onto the instance, and a class-level getter would
shadow that assignment. An appended property is not a column, so field_length() answers
null for it exactly as it does for any non-varchar, and it gets no enum treatment.

Adding or removing a name changes the stub, so $appends is part of the model metadata
hash that decides when a stub is regenerated.

NAMING. The property name is the method name - no aliasing, at any layer (see NEVER
EXPORT COLUMNS above and the no-field-aliasing convention): one string in PHP, JSON and
JavaScript, so grep finds every usage.

WORKED EXAMPLES. system/app/RSpade/resource/reference_app/models/party_model.php
(party_id_formatted) and App\RSpade\Core\Files\File_Attachment_Model
(is_image / is_video / is_document / can_open_inline).

UTILITY METHODS

Static Methods:
- get_table_static() - Get table name without instantiating model
- getColumns() - Get array of column names for model's table
- hasColumn($column) - Check if column exists
- field_length($column) - Max character length of a varchar/char column, or NULL for
  every other column type. This is the ONE definition of "how long may this field be":
  the lengths a page's JavaScript reads (its bundle's field-length script, behind
  Model.field_length()) are this method's answers, so a server-side length check and
  the client's $max_length cannot drift and app code never mirrors a schema literal in
  a constant.

      $max = Client_Model::field_length('name');   // 255
      Client_Model::field_length('id');            // null - a bigint has no limit

  NULL means "this column has no character limit" - a real answer, never a lookup
  failure. A column the model does not have throws a RuntimeException naming the model
  and the column: answering NULL for a typo'd name would read as "unlimited" and defeat
  the very check being written. Class-Table Inheritance is spanned: a base model's
  detail-table columns are merged into its column map, so a base model answers for its
  detail columns too. A model whose table does not exist in the connected database
  throws too, naming the table and `php artisan migrate`.

  Reads the live schema through Rsx_Schema - one query for the whole database, cached
  under the state key, so a migration is seen with no rebuild (rsx:man migrations).
  Columns whose name starts with a single underscore are SYSTEM columns and are omitted
  from the field-length script - PHP still answers for them, because what a column's length IS and what may be published to
  a client are different questions.
- get_relationships() - Get array of relationship method names, unioned across the
  lineage: this class's #[Relationship] methods plus every manifest-visible ancestor's
  (which is how the framework audit relations created_by / updated_by / deleted_by,
  declared on Rsx_Model_Abstract, reach every model). An override of an ancestor's
  relationship method must redeclare #[Relationship] - see RELATIONSHIP-OVERRIDE-01 in
  `rsx:man code_quality`. The JS model's get_relationships() answers a narrower question:
  only the relationships the browser can FETCH (those also carrying
  #[Ajax_Endpoint_Model_Fetch]) - rsx:man model_fetch.

Instance Methods:
- make_new() - Create new model instance (recommended over new Model())
- get_mass_assignment_example() - Get helpful example code for this model

MODEL ORGANIZATION WITH TRAITS

Large models can be split into domain-specific trait files. This organization
strategy is primarily designed for models, though traits can be used elsewhere
in RSX applications.

Naming Convention:

Trait files should be prefixed with the model name they elaborate on:
    Users_Model -> Users_Model_Authentication (trait for auth methods)
    Users_Model -> Users_Model_Relationships (trait for relationship methods)
    Users_Model -> Users_Model_Permissions (trait for permission logic)

This makes it immediately clear which model a trait belongs to.

Organization Strategy:

Group methods by problem domain within separate trait files:
    - Authentication/authorization logic
    - Query methods for specific use cases
    - Relationship definitions
    - Business logic for specific features
    - Computed properties and accessors

Example Implementation:

    // rsx/models/traits/users_model_authentication.php
    trait Users_Model_Authentication
    {
        public static function find_by_email(string $email)
        {
            return static::where('email', $email)->first();
        }

        public static function find_by_api_token(string $token)
        {
            return static::where('api_token', $token)->first();
        }

        public function verify_password(string $password): bool
        {
            return password_verify($password, $this->password);
        }
    }

    // rsx/models/traits/users_model_relationships.php
    trait Users_Model_Relationships
    {
        #[Relationship]
        public function posts()
        {
            return $this->hasMany(Posts_Model::class);
        }

        #[Relationship]
        public function profile()
        {
            return $this->hasOne(User_Profiles_Model::class);
        }
    }

    // rsx/models/users_model.php
    class Users_Model extends Rsx_Model_Abstract
    {
        use Users_Model_Authentication;
        use Users_Model_Relationships;

        protected $table = 'users';

        public static $columns = [
            'api_token' => ['never_export' => true],
        ];
    }

Manifest Integration:

The manifest system automatically discovers and indexes methods from traits:
- Trait files are loaded before classes during manifest build
- Methods from traits appear in the model's metadata
- IDE helpers correctly locate trait method definitions
- Code quality rules validate trait methods same as class methods

Benefits:

- Keep models focused and maintainable
- Group related functionality by problem domain
- Easier to navigate large models with hundreds of methods
- Clear separation between different aspects of model behavior
- Traits are discovered and validated automatically by manifest

SITE-BASED MULTI-TENANCY

RSpade provides automatic multi-tenant data isolation through model inheritance.

Model Types:

    Rsx_Model_Abstract
        - Base model for global/system-wide data
        - No automatic site scoping
        - Examples: countries, regions, system settings

    Rsx_Site_Model_Abstract
        - Base model for tenant-specific data
        - Automatic site_id scoping on all operations
        - Examples: users, clients, projects, tasks

How It Works:

    Models extending Rsx_Site_Model_Abstract automatically:
    - Filter all queries by current session site_id
    - Set site_id on all new records from session
    - Prevent changing site_id on existing records
    - Prevent cross-site data access (throws fatal error)
    - Require site_id column in database table

    Database Schema:
        CREATE TABLE projects (
            id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY,
            site_id BIGINT NOT NULL,
            name VARCHAR(255) NOT NULL,
            description LONGTEXT,
            INDEX idx_site_id (site_id)
        )

    YOU DECLARE THE site_id COLUMN AND ITS INDEX IN YOUR OWN MIGRATION. Schema
    normalization is database-driven - it walks SHOW TABLES and consults no
    model - so it adds only the columns EVERY table carries: the audit-authorship
    pairs and the timestamps. site_id belongs to one lineage, not to every table,
    so it is the migration's to declare.

Usage:

    class Project_Model extends Rsx_Site_Model_Abstract
    {
        protected $table = 'projects';
    }

    // In controller with session site_id = 1
    $projects = Project_Model::all();
    // SELECT * FROM projects WHERE site_id = 1

    $project = new Project_Model();
    $project->name = 'New Project';
    $project->save();
    // INSERT INTO projects (site_id, name) VALUES (1, 'New Project')

Security Enforcement:

    // Attempt to change site_id - FATAL ERROR
    $project = Project_Model::find(1);  // site_id = 1
    $project->site_id = 2;
    $project->save();
    // FATAL: Attempted to change site_id from 1 to 2. Changing site_id is not allowed.

    // Attempt to save wrong site record - FATAL ERROR
    // (If somehow loaded a record from site 2 while session is site 1)
    $project->save();
    // FATAL: Cross-site saves are not allowed.

Admin Operations (Bypass Site Scoping):

    // Access all sites (admin operations only)
    $all_projects = Project_Model::without_site_scope(function () {
        return Project_Model::all();
    });

    // Query specific site
    $site_2_projects = Project_Model::without_site_scope(function () {
        return Project_Model::where('site_id', 2)->get();
    });

A Site-Scoped Query Needs a Declared Site:

    A site-scoped READ with no site declared THROWS:

        RuntimeException: Site-scoped read of Project_Model with no site declared. ...

    A site is declared by a signed-in staff session bound to a site, a portal
    request (its URL), an API key, Session::set_site_id() (a guest request's
    override, or a command / task / test), Session::impersonate(), or
    Session::set_temporary_site_id(). Nothing else is: a plain #[Task] run, a
    command that named no site, a guest request that declared none. Site 0 (the
    Default site) is a real site and may be declared by name; it is never
    assumed. Session::has_declared_site() answers the question.

    Why it throws rather than reading "site 0": the scope is ANDed with your own
    conditions, never replaced by them. A where('site_id', $n) of your own is
    ADDED to the session's site, not substituted for it:

        Project_Model::where('site_id', 1)->get();
        // SELECT * FROM projects WHERE site_id = 1 AND projects.site_id = <session site>

    With no site declared, every such read used to match nothing and
    Model::find($id) answered NULL, whatever site you named - silently, in the
    shape of a legitimate empty result.

    So code that serves ONE site DECLARES it for the span of the work, and the
    scope then reads that site:

        $prior = Session::has_temporary_site_id() ? Session::get_site_id() : null;
        Session::set_temporary_site_id($site_id);   // writes nothing, creates no session
        try {
            $project = Project_Model::find($id);      // site $site_id
        } finally {
            $prior === null ? Session::clear_temporary_site_id()
                            : Session::set_temporary_site_id($prior);
        }

    Code that means EVERY site - or names its site itself - opts out with
    without_site_scope(fn () => Model::where('site_id', $site_id)->...).
    Naming the site in a scoped query does neither. A realtime #[Emitter] is
    already run with its site declared (rsx:man realtime); a task bound to its
    dispatcher (#[Run_As_Dispatcher]) already runs as the requester's site
    (rsx:man tasks).

    THE DECLARED SITE MUST EXIST. The setters only record a site; the first
    site-scoped read or create of the process confirms that a sites row with
    that id exists (soft-deleted included) and throws when it does not:

        RuntimeException: Site-scoped query of Project_Model: there is no site 1000 (no sites row with that id).

    Creating a record with no site declared still stamps the session's site
    (0, the Default site); only reads require a declaration.

    THE SCOPE GUARDS WRITES TOO. Saving an EXISTING row whose site_id differs
    from the session's site is refused outright, never re-scoped:

        Attempted to save Note_Model with site_id 7 but current session site_id is 0.
        This indicates a serious security issue.

    without_site_scope() suspends the scope for what runs INSIDE its callback -
    the read filter, this save check and the create-time site_id stamp alike
    (on Rsx_Site_Model_Abstract the switch is one flag shared by every model
    beneath it). A row it RETURNED is an ordinary record afterwards: saving it
    outside the callback, under a different ambient site, is refused. So a
    sweep across every tenant writes in one of two ways:

        // A plain change to each row, no per-tenant context needed:
        // write inside the same callback.
        Note_Model::without_site_scope(function () {
            foreach (Note_Model::where('pinned_until', '<', now())->result_set() as $note) {
                $note->pinned_until = null;
                $note->save();
            }
        });

        // Writes that should run AS each tenant (its hooks, its realtime
        // frames, its revisions): read across sites, then declare each row's site.
        $rows = Note_Model::without_site_scope(fn () => Note_Model::where(...)->get());
        foreach ($rows->groupBy('site_id') as $site_id => $site_rows) {
            Session::set_temporary_site_id((int) $site_id);
            try {
                foreach ($site_rows as $note) { ...; $note->save(); }
            } finally {
                Session::clear_temporary_site_id();
            }
        }

    A raw DB::table() / DB::statement() write is checked by NOTHING: no read
    scope narrowed what it touches and no save guard stands in front of it. A
    site-scoped read with no site declared now fails loud; a raw write does not.

    WHICH SETTER IN A TASK. A background task declares its tenant with
    Session::set_temporary_site_id() and clears it in a finally. The permanent
    Session::set_site_id() also works in a virtual session, but a leaked one is
    inherited by whatever the worker runs next, and run INLINE it repoints the
    caller's own session; set_temporary_site_id() is restorable, writes nothing,
    and refuses in an API request and on a frozen #[Run_As_Dispatcher] run,
    where the tenant is not the task's to change. set_site_id() remains the
    call for a command or test declaring its own context, and for a guest
    request.

SITE SCOPING AS AN ADOPTABLE TRAIT (Site_Scoped):

    The implementation lives in the Site_Scoped trait, and
    Rsx_Site_Model_Abstract is a model that adopts it and declares nothing
    else. Extending that class and adopting the trait install the SAME
    controls from the SAME source - there is one tenant boundary, not two.

    Extend Rsx_Site_Model_Abstract when the model is site-scoped from the
    start; that remains the ordinary case and nothing about it changes.

    Adopt the trait directly when a model CANNOT reach that class:

        class User_Profile_Model extends User_Profile_Model_Abstract
        {
            use Site_Scoped;
        }

    The case this exists for is a split core model. An application override of
    one must extend the framework's X_Model_Abstract base DIRECTLY, which fixes
    that base's own parent - so when the framework table is not site-scoped but
    the application added site_id to its copy in its own migration, the override
    has no inheritance slot left to reach Rsx_Site_Model_Abstract with. Before
    the trait the only way out was to re-implement the read scope and the create
    stamp by hand in the override, which is exactly the cloned-machinery drift
    the base/shell split exists to end.

    The adopting model's table MUST have a site_id column - every control names
    it - and the migration that creates the table declares it, for a trait
    adopter and a subclass alike.

    ONE DIFFERENCE WORTH KNOWING. $apply_site_scope is a static the trait
    contributes to whichever class adopts it, so Rsx_Site_Model_Abstract holds
    ONE flag shared by every model beneath it - unchanged from before - while a
    direct adopter holds its own. So without_site_scope() on a direct adopter
    suspends that model alone and never reaches the rest of the family.

Registering Model Hooks (booted() + parent::booted()):

    The site isolation controls (the read scope, the site_id force, the site_id
    validation) are installed by the trait's boot, which Eloquent calls for every
    adopting class before booted() - so they are NOT something an override of
    booted() can drop. A site-scoped model that needs its own model event hooks
    still overrides booted() and still makes parent::booted() its first
    statement, because that is the framework-wide chaining rule:

        class Project_Model extends Rsx_Site_Model_Abstract
        {
            protected static function booted()
            {
                parent::booted();               // installs the site controls
                static::creating(function ($model) {
                    $model->slug = Str::slug($model->name);
                });
            }
        }

    Forgetting parent::booted() is caught at manifest build time by the default
    parent-call chaining rule, PHP-PARENT-CHAIN-01: booted() is a
    chain-mandatory override (it is NOT #[Replaceable]), so an override that
    omits parent::booted() is a fatal manifest-time error until the parent call
    is added. See: php artisan rsx:man code_quality (PARENT-CALL CHAINING
    section).

    That omission used to ALSO drop the site scope silently - a fail-open
    confidentiality defect, Model::find() returning foreign-site rows with no
    exception at runtime - because the protections were installed in
    Rsx_Site_Model_Abstract::booted(). They now ride on the trait boot instead,
    so the tenant boundary no longer depends on anyone remembering to chain.
    Chain anyway: the rule is framework-wide and other bases put real work in
    booted().

    A model that needs no hooks of its own defines no booted() at all and
    inherits the base protections unchanged.

Post-Write Lifecycle Hooks (after_create / after_update / after_delete):

    Every model inherits three no-op template hooks that fire AFTER a write is
    durable - once the save()/delete() has committed (or immediately, for a write
    outside any transaction). Override the ones you need to run side effects off a
    committed model change:

        public function after_create(): void
        public function after_update(array $changed_fields): void
        public function after_delete(): void

    - after_create - the row was INSERTed. $this holds the persisted row (id set).
    - after_update - an existing row was UPDATEd. $changed_fields lists the column
      names that actually changed (array_keys of the dirty set, so it includes
      updated_at); an update that changed nothing does not fire.
    - after_delete - the row was deleted. A SoftDeletes delete fires after_delete
      ONCE (never after_update for the internal deleted_at write). $this still
      holds the deleted row's attributes.

    Commit-gated, rollback-discarded. The hooks are buffered and run on transaction
    COMMIT; a rolled-back write fires NOTHING. That is why they are "after_*" and
    not Eloquent's inline created/updated/deleted events - a hook never runs for a
    change the database rejected.

    A hook that throws never cancels the other hooks of the same commit: every
    one runs, then the first throw surfaces - to the saving code for a write
    outside any transaction, and after a commit as a logged report that never
    fails the committed request (rsx:man site_locks, AFTER THE COMMIT).

    These are #[Replaceable] template hooks (NOT chain-mandatory like booted()): an
    overriding model REPLACES the hook and must NOT call parent::after_*() - the
    base bodies are empty, so there is nothing to chain, and the default parent-call
    rule is annotated off. See: php artisan rsx:man code_quality (PARENT-CALL
    CHAINING - #[Replaceable] is the marker-only opt-out).

    Bulk writes fire these per record. Model::where(...)->update()/->delete() on a
    model that overrides any after_* hook (or has a realtime surface) loads the
    affected rows and runs each through save()/delete(), so the hook fires once per
    row - see: php artisan rsx:man realtime (BULK WRITES). Realtime model-change
    emission is itself wired at this same committed-write layer: a $realtime model
    publishes its change frame off the same path.

Single-Site Applications:

    Even single-site applications use site_id = 1 for all records.
    The architecture is identical - just happens to use only one site.
    Easy upgrade path if multi-tenancy needed later.

How site_id is Determined:

    site_id comes from Rsx_Site_Model_Abstract::get_current_site_id(), which asks
    the EXPERIENCE of the request:

    STAFF request / CLI - the staff session site (Session::get_site_id()):
    - User logs in -> login_user_id set in session
    - User has site memberships -> site_id set in session
    - All queries for site models filtered by this site_id
    - Changing session site_id changes which data is accessible

    PORTAL request - the site the request's URL serves, which the framework
    declares before any application code (Portal_Session::get_site_id()). It is a
    different site from the staff one - the portal sign-in's, on the same one
    browser - and a portal request with no site THROWS rather than scoping to 0.
    See: rsx:man portal.

See: php artisan rsx:man auth (for complete authentication/site selection flow)

RESULT SETS - Rsx_Result_Set

A framework method whose job is "these records" returns ->result_set(), an
Rsx_Result_Set: a handle over the WHOLE set that you foreach like a list, but
which fetches the rows one keyset page at a time.

    // framework side
    public function get_attachments(string $category)
    {
        return File_Attachment_Model::where(...)->result_set();
    }

    // caller side - nothing to call first, nothing to unwrap
    foreach ($record->get_attachments('documents') as $attachment) { ... }

It exists because two rules pull against each other: a function must return EVERY
record it promised (correctness), and the framework must not fall over when that
turns out to be 500,000 rows (memory). Iterating satisfies both. Truncating with a
LIMIT satisfies neither - it silently drops data the caller asked for.

    Interface
        foreach ($set as $record)   the whole set, a page at a time
        $set->count()               SQL COUNT - never walks the set
        $set->is_empty()            an EXISTS check, not a count
        $set->first()               one row, one query
        $set->all()                 materialize to an array (deliberate, explicit)
        $set->map(...) / filter(...) / take(...)   forwarded, and STAY lazy
        $set->query()               the underlying builder (escape hatch)

    It is NOT an array
        No [] indexing, no array_map()/count($x) on the raw value. It IS Countable
        and Traversable, so count($set) and foreach both work.

WHEN NOT TO USE IT

Two cases, both about not over-engineering:

    Known small ceiling. A finite catalog, or a per-record handful. Return the
    Collection; paging machinery for 12 rows is noise.

    Ordered display list. Iteration walks by PRIMARY KEY, so it OVERRIDES any
    orderBy on the query. "The 20 most recent" is a different job - keep the
    ordered query and return rows.

Iteration costs one query per page, so it earns its keep only when the row count is
genuinely unknown.

$unbounded - DECLARING A TABLE THAT GROWS

A model whose row count grows with CUSTOMER ACTIVITY rather than with the codebase
declares it:

    public static $unbounded = true;   // sessions, queues, uploads, request logs

This is a declaration, not a runtime gate - a small, well-narrowed query on such a
model is still perfectly fine. Two things consume it:

    DB-UNBOUNDED-01 (rsx:check) flags a bare ->get()/->pluck() on an $unbounded
    model in FRAMEWORK code. Escape hatches: ->limit(), ->result_set(),
    ->lazyById(), ->chunkById(), ->raw_bulk(), or a file-level
    @DB-UNBOUNDED-01-EXCEPTION - <rationale>.

    rsx.database.result_set_warn_threshold (default 1000) logs ONE warning in
    development and debug mode when any get() actually returns more rows than
    that, naming the count, the model and the call site. It never throws and
    never truncates; it tells you while you are still writing the feature.
    Production never pays for it. Set 0/null to disable.

The two are complements: the declaration is a static claim about a table, the
threshold is what really happened.

WHY THIS EXISTS

A settings page ran an unbounded ->get() and the caller sliced to 20. One login
user had accumulated 62,617 session rows, because every automated browser run
minted a session and nothing expired machine sessions. The page hydrated all
62,617 models, parsed 62,617 user-agent strings, exhausted a 128MB process, and
returned a blank 500 - while saturating the php-fpm pool and making unrelated
endpoints flaky.

Nothing about that code looked wrong. It even had a limit, in the wrong place. The
table simply grew. See the "Do The Whole Job" section of CLAUDE.md.

NAMING CONVENTIONS

Tables:
- Plural snake_case (users, user_logins, product_categories)
- Always include 'id BIGINT NOT NULL AUTO_INCREMENT PRIMARY KEY'

Columns:
- snake_case for all column names
- Foreign keys must suffix with '_id' (user_id, site_id)
- Booleans must prefix with 'is_' (is_active, is_published)
- Timestamps must suffix with '_at' (created_at, updated_at, deleted_at)
- Use BIGINT for all integers, TINYINT(1) for booleans only
- All text columns use UTF-8 (utf8mb4_unicode_ci collation)

REVISION HISTORY

Opt a model into per-write revision recording:

    public static $revisions = true;                      // record every save()/delete()

    public static $columns = [
        'view_count' => ['revision_exclude' => true],     // a column not worth recording
    ];

Instance methods this adds:
- revisions() - every revision recorded for THIS record, newest first
  (Rsx_Result_Set). #[Replaceable] - a model whose `revisions` name means
  something else replaces it outright.
- revisions_including_children() - the same, plus every record declaring this
  one as its #[Revision_Parent], resolved by one indexed query on the root pair.

updated_at, the updated_by pair, every `_`-prefixed system column and every
derived column are excluded automatically. Full treatment: rsx:man revisions.
