RSX_FILE_DISPOSAL(1)          RSpade Manual          RSX_FILE_DISPOSAL(1)

NAME
    file_disposal - time-delayed file disposal: retention window, recovery API,
    scheduled destruction, and orphan sweeps for file attachments

SYNOPSIS
    // Delete = enter the retention window (recoverable), NOT immediate destruction
    $attachment->delete();

    // Recover within the window
    $model->get_deleted_attachments('documents');   // this model's recently-deleted
    File_Attachment_Model::get_deleted_files($fileable, $category);
    $attachment->undelete();                          // restore (throws once destroyed)

    // Out-of-band immediate erasure (GDPR / rollback)
    $attachment->force_destroy();

DESCRIPTION
    Deleting a file attachment never immediately destroys the bytes. RSpade's file
    layer runs a three-state lifecycle:

        live  ->  deleted_at (recoverable)  ->  destroyed_at (tombstone)

    delete() SOFT-deletes the attachment into a RETENTION WINDOW: it stays in the
    database (SoftDeletes; the fileable link is kept) and its deduplicated backing
    blob is preserved, but it drops out of normal queries. It is recoverable via
    undelete() for rsx.files.deleted_retention_days (default 30). After the window,
    the daily disposal task permanently DESTROYS it - stamping destroyed_at (the row
    PERSISTS FOREVER as an audit tombstone, only its claim on the blob released) and
    releasing the blob once no attachment still pins it. A retention of 0 means KEEP
    FOREVER (see KEEP FOREVER below).

    Unlike Laravel, where deleting a model deletes the row, an RSpade file delete is
    always a reversible retention step; permanent destruction is a separate,
    scheduled, hook-gated act. App code should NEVER hard-delete an attachment or a
    blob - delete() means "enter retention"; force_destroy() is the only immediate
    erasure and is reserved for GDPR-style requests and internal rollback.

RETENTION-AWARE REFCOUNT
    The blob store is content-deduplicated: many attachments may share one
    File_Storage_Model blob. A blob is PINNED by any attachment that is LIVE or
    SOFT-DELETED-BUT-NOT-DESTROYED. Only once EVERY attachment referencing a blob is
    destroyed are the bytes released. A recoverable (retained) attachment therefore
    keeps its blob alive - "release the last reference" counts retained references,
    not just live ones. Any refcount query uses
    withTrashed()->whereNull('destroyed_at').

    Every OTHER kind of row that points at a blob pins it too, for as long as the
    row exists: a queued email's part (_email_attachments, until its email row is
    deleted) and a task run's attachment (_task_attachments, until the run's output
    is truncated or the run is purged - rsx:man tasks, RETENTION). Neither has a
    window of its own.

DECLARED BLOB REFERENCES
    The disposal side may release a blob only when NO row references it, so it must
    know every table that can hold one - and that knowledge is DECLARED on the model
    that owns the reference, never listed by hand:

        #[Blob_Reference('file_storage_id')]
        abstract class Email_Attachment_Model_Abstract extends Rsx_Model_Abstract
        {
            use Blob_Referencing;
            ...
        }

        #[Blob_Reference(column: 'file_storage_id', where_null: 'destroyed_at')]

    `column` names the column holding _file_storage.id. `where_null`, when given,
    names a column that must be NULL for the row to count (an attachment's
    destroyed tombstone keeps its row but no longer pins the bytes). Arguments are
    literals - an attribute argument is read by reflection before the autoloader
    is ready, so never a class constant. File_Blob_References::declarations() reads
    them from the manifest; release_blob_if_orphaned() asks every declared table
    (each row counted from every site, soft-deleted or not) and the monthly deep
    sweep excludes every blob any declared table references.

    The Blob_Referencing trait is the WRITE side: its save() holds the blob's read
    lock while a write that sets file_storage_id commits (RACE-PROOF RELEASE). A
    model that declares a reference uses the trait; inside store_blob() /
    store_bytes() the lock is already held and the save is a reentrant hold.

    AN UNDECLARED REFERENCE IS A FAILED HEALTH ROW. rsx:health "Blob References"
    reads every foreign key to _file_storage.id in the live schema and FAILs naming
    each table.column no declaration covers - such a table would let the disposal
    sweeps free bytes it still needs. An application table that stores blobs (a
    model of its own pointing at _file_storage) declares the reference the same
    way; the framework's own declarations are File_Attachment_Model_Abstract (with
    where_null destroyed_at), Email_Attachment_Model_Abstract and
    Task_Attachment_Model_Abstract.

THE CENTRAL BLOB API (File_Storage_Model)
    A consumer stores and reads bytes through the storage row and never by its path,
    so the store's location is the store's business.

        File_Storage_Model::store_blob($temp_path, fn ($storage) => ...)
            THE way bytes enter the store: content-addressed (sha256), deduplicated,
            immutable. The callback writes the referencing row; the blob's read lock
            is held from before the lookup until that row commits.
        File_Storage_Model::store_bytes($bytes, fn ($storage) => ...)
            store_blob() for bytes held in memory (a scratch file is written and
            removed around it).
        $storage->read_bytes()                      the whole contents
        $storage->read_stream()                     an open read stream; the caller
                                                    closes it
        $storage->download_response($file_name, $mime_type = null)
        $storage->inline_response($file_name, $mime_type = null)
                                                    hardened file responses (the same
                                                    headers every file response gets);
                                                    authorizing the caller is the
                                                    caller's job

    Each throws when the bytes are not on disk. A reference recorded OUTSIDE the
    store_blob()/store_bytes() callback has no race protection - record it inside.

RACE-PROOF RELEASE
    A reference can be recorded at any moment, deduplicated onto the very blob a
    disposal pass is releasing. Two mechanisms make that safe.

    The per-blob lock. Every blob has a web-cluster readers-writer lock named
    file_blob:<hash> (File_Blob_Locks; see rsx:man locks).
        READERS  every reference creator. File_Storage_Model::store_blob() takes the
                 read lock BEFORE the storage row is looked up or created and holds it
                 until the reference written in its callback is COMMITTED; the save()
                 of every Blob_Referencing model does the same for any write that
                 sets file_storage_id (a reference to an EXISTING row), and throws if
                 the row was released first.
        WRITERS  release_blob_if_orphaned() and the monthly disk-orphan sweep. Each
                 re-checks every declared reference table (or, for a disk file, the
                 storage row) inside the write lock.
    "Until committed" means: at once when no transaction is open, else at the end
    of the OUTERMOST transaction (commit or rollback). A reference inside an open
    transaction is invisible to every other connection, so a lock released at the
    INSERT would admit a destroyer that cannot see it.

    Delete the row before the file. Inside the write lock the release runs:
        re-check references
        -> transaction: null the DESTROYED tombstones' file_storage_id, delete the
           _file_storage row (its search-index row cascades in the same transaction)
        -> commit
        -> unlink the blob file and purge its rendition + thumbnail caches
    Every declared reference table carries a foreign key to _file_storage that
    refuses the delete (RESTRICT), so a reference that exists after all makes the
    delete FAIL:
    release_blob_if_orphaned() returns false and nothing is unlinked. Only
    destroyed tombstones are un-claimed, so a live reference keeps its claim.

    Inside a caller's open transaction, release_blob_if_orphaned() returns true as
    soon as the row is deleted, but the unlink waits for the OUTERMOST commit
    (DB::afterCommit) and the write lock is held until it has run; a rollback
    restores the row and leaves the file in place. A process that recorded a
    reference to the same blob earlier in that transaction already holds its read
    lock, which the release upgrades to the write lock.

    MAINTENANCE MODE grants cluster locks as no-ops (rsx:man maintenance_mode); the
    row-before-file ordering is then the safety net, on a fleet with nothing else
    running.

RECOVERY API
    File_Attachment_Model::get_deleted_files($fileable = null, $category = null)
        Static. The attachments currently in the retention window (soft-deleted, not
        destroyed), tenant-scoped, optionally narrowed to a fileable owner and/or a
        category. The enumeration a "Recently Deleted" UI is built on.

    $model->get_deleted_attachments(string $category)
        On any Rsx_Model_Abstract: this model's recently-deleted attachments in a
        category (the companion to get_attachment()/get_attachments()).

    $attachment->undelete(): void
        Restore out of the retention window (clears deleted_at). THROWS if the
        attachment has already been permanently destroyed, or if its backing bytes
        are gone.

    $attachment->force_destroy(): void
        Permanently destroy NOW, bypassing BOTH the retention window and the
        destroy.hold gate. Stamps deleted_at + destroyed_at (the tombstone row
        persists) and releases the blob immediately if nothing else pins it. The
        hold gate is skipped, but file.attachment.destroyed DOES fire (the attachment
        is gone either way); a throwing listener is logged and the destruction
        proceeds, unlike the scheduled path. Unaffected by the retention setting.

DESTRUCTION HOOKS (app integration seam)
    The daily destroy pass fires two events per attachment, in the framework event
    vocabulary (see rsx:man event_hooks). Register handlers with #[OnEvent].

    file.attachment.destroy.hold  (a GATE, before stamping)
        Uses the framework gate convention: a listener returns TRUE to PERMIT
        destruction; ANY non-true value HOLDS the attachment (skipped this run,
        re-examined next run). Use for a legal hold, an in-flight operation still
        referencing the blob, an export mid-stream. NOTE: this is the inverse of the
        "return true to hold" phrasing some designs use - here true = allow, matching
        every other RSpade gate (e.g. file.download.authorize).

    file.attachment.destroyed  (an ACTION, after stamping, per attachment)
        Payload = the attachment row. Fired OUTSIDE any blob lock. A
        THROWING listener ABORTS that one attachment's destruction (row left
        un-stamped, retried next run) - destruction never half-happens relative to an
        app integration. Handlers must be idempotent (a retry re-fires).

SCHEDULED TASKS (File_Disposal_Service)
    All #[Exclusive]. Every blob they release or unlink is released under that
    blob's own write lock (RACE-PROOF RELEASE above); there is no pass-wide lock, so
    two passes - or a pass and force_destroy() - serialize only where they touch the
    same blob. All are keyset-paginated for bounded memory over hundreds of
    thousands of rows.

    EVERY PASS SPANS EVERY SITE. Retention is install policy and the blob store is
    deduplicated across the whole install, so each task runs outside the site scope
    (without_site_scope) and a worker's declared site never narrows what it sees. The
    refcount in release_blob_if_orphaned() counts every site's attachments wherever it
    is called from: a blob one tenant released may still be another tenant's file.

    sweep_unclaimed_uploads   #[Schedule('every 6 hours')]
        The CLAIM WINDOW. An upload arrives UNATTACHED and is reachable only by its
        unguessable key until app code claims it with attach_to()/add_to(); this task
        bounds how long that key stays useful. Anything still unattached past
        config('rsx.attachments.unattached_claim_window_hours') (default 24) is
        SOFT-deleted - it enters the ordinary retention window (recoverable via
        undelete(), blob still pinned), never destroyed outright. Never touches:
        attached rows, handler-backed (WP-A) rows, rows already soft-deleted. A
        window of 0 (or null) disables the sweep.

        This is the successor to the bound the retired _file_attachments.session_id
        stamp implied. Claimability is now a property of the attachment (unclaimed +
        same site), so the window is what keeps an abandoned key from lingering
        indefinitely. See rsx:man file_upload (THE CLAIM WINDOW).

    run_daily_disposal   #[Schedule('0 2 * * *')]
        (a) DESTROY pass: attachments with deleted_at older than the retention window
            and destroyed_at NULL -> destroy.hold gate -> destroyed action -> stamp
            destroyed_at. Does not run at all when the retention is 0.
        (b) BLOB-RELEASE pass: for blobs referenced by attachments destroyed within
            rsx.files.disposal_lookback_days (default 60), recompute the
            retention-aware refcount and release at zero (unlink the blob + its
            rendition + thumbnail caches; the search-index row cascades on the storage
            delete). Runs under every retention setting.

    run_monthly_deep_sweep   #[Schedule('0 2 * * 0')] + first-Sunday guard
        Classic cron cannot express "first Sunday", so it fires every Sunday and
        returns early unless the day-of-month is 1..7. Full reconciliation, no time
        window: (a) release every storage blob no declared reference pins;
        (b) stream-walk blob_root() and unlink files older than
        rsx.files.disk_orphan_min_age_days (default 14) that have no storage row (the
        age guard protects a just-written blob whose row commits after the file
        lands); (c) soft-delete stale plain-local unassigned uploads. External (WP-A
        handler-backed) attachments and their bytes are never swept.

    run_monthly_deep_sweep accepts ['force' => true] to bypass the first-Sunday guard
    for a manual or test run: rsx:task:run File_Disposal_Service run_monthly_deep_sweep.
    Note its unassigned-upload pass (c) uses the much older disk_orphan_min_age_days
    bound; the 6-hourly claim-window sweep is the tight one, and the monthly pass is
    the backstop that also reconciles blobs and disk.

KEEP FOREVER
    rsx.files.deleted_retention_days = 0 keeps every deleted attachment recoverable,
    and its blob on disk, indefinitely - for a deployment that must retain deleted
    files for audit. Set it in rsx/resource/config/rsx.php. The same convention as
    rsx.revisions.retention_days.

    - The daily DESTROY pass never runs, so nothing is ever stamped destroyed_at by
      the schedule.
    - Everything else already asks destroyed_at, never a date: the retention-aware
      refcount, the monthly sweep's blob reconciliation, undelete(),
      get_deleted_files() and get_deleted_attachments(). A deleted attachment is
      therefore retained, restorable and pinning its blob for as long as the setting
      holds. The daily task's destroy cutoff is the only place the number is read.
    - force_destroy() still erases at once, and the daily BLOB-RELEASE pass still
      frees the bytes of attachments destroyed that way (once no other attachment
      pins the blob).
    - Stale unattached uploads are still swept (soft-deleted) by the claim-window and
      monthly passes; under keep-forever they then stay in retention forever too.
    - Turning keep-forever OFF later makes the next daily run destroy every
      attachment deleted before the new window, all at once.

    A negative (or non-integer) value is a configuration error: the daily task
    throws naming the key, and destroys nothing.

CONFIG (config('rsx.files.*'))
    deleted_retention_days     30   recoverable window before permanent destruction;
                                    0 = keep forever, negative throws
    disposal_lookback_days     60   blob-release pass window (daily task)
    disk_orphan_min_age_days   14   age guard for the monthly disk / unassigned sweep

CONFIG (config('rsx.attachments.*'))
    unattached_claim_window_hours
                               24   how long an UNATTACHED upload stays claimable
                                    before sweep_unclaimed_uploads soft-deletes it;
                                    0/null disables the sweep

INTERACTIONS / PITFALLS
    - delete() is a SOFT delete. SoftDeletes installs a global scope, so ordinary
      File_Attachment_Model queries exclude retained rows; use withTrashed() to see
      them. Refcount checks MUST use withTrashed()->whereNull('destroyed_at').
    - A destroyed attachment is a TOMBSTONE: the row persists with its metadata, its
      file_storage_id nulled (the FK claim released so the blob's storage row can be
      deleted).
    - A migration that creates attachments via the model must run AFTER the retention
      columns exist - adding SoftDeletes made deleted_at load-bearing at model boot.
    - Rejected uploads (create_from_upload strict reject) use force_destroy(), never a
      plain delete(), so a bad upload never lingers in retention.
    - CLI tools rsx:file:delete and rsx:storage:cleanup are explicit admin erasures:
      they force_destroy() / route through the retention-aware release, not delete().
    - force_destroy() inside an open transaction deletes the storage row at once and
      unlinks the file at the outermost COMMIT; a test that runs inside a rolled-back
      per-test transaction therefore never sees the file disappear.
