    js_decorators - RSX JavaScript decorator system with whitelist validation

SYNOPSIS
    JavaScript decorators on classes and class methods, using the TC39 decorators
    proposal (version 2023-11), with explicit whitelist control

DESCRIPTION
    The RSX framework supports JavaScript decorators on classes and on class
    methods, static and instance alike. They follow the TC39 decorators proposal,
    version 2023-11: a decorator is a function called with (value, context), never
    the (target, key, descriptor) signature of the older proposal.

    Unlike standard JavaScript, RSX requires a decorator to be whitelisted with the
    @decorator marker before it may be applied to a class or a class method.

    Key differences from standard decorators:
    - Standard: Any function can be used as decorator
    - RSX: Only functions marked with @decorator can be used on a class or a method

    Benefits:
    - Prevents accidental decorator misuse
    - Framework validates decorator usage at build time
    - Clear separation between decorator definitions and applications
    - Bundle ordering ensures decorator.js loads first

    The framework's own decorators:
        @route, @layout, @spa, @title, @auth, @spinner_until_ready, @portal_spa
                    class decorators for SPA actions (Core/SPA/Spa_Decorators.js;
                    rsx:man spa)
        @mutex, @mutex('id')
                    method decorator: one call of the method at a time, per
                    instance or per id (Core/Js/Mutex.js)
        @debounce(ms)
                    method decorator: the debounce() of Core/Js/async.js
                    applied to a method

DECORATOR WHITELIST SYSTEM
    Whitelist Requirement:
        A decorator applied to a class, or to a class method - static or instance -
        must be the name of a function or method marked with @decorator.

    Validation:
        Rule JS-DECORATOR-01 checks every class decorator and every method decorator
        against the whitelist when the manifest builds, and a global function carrying
        any decorator other than the @decorator marker fails it. A failure is a
        manifest-build FATAL naming the file, the class, the decorator and - for a
        class decorator - its line and the whitelisted names. The check runs whether
        or not decorators are enabled (rsx.javascript.decorators).

        A decorator is whitelisted under its BARE name. A member-expression decorator
        (@Some_Class.some_method) is recorded under its dotted name, which no
        whitelist entry carries, so it fails on a class and on a method alike: apply
        a static decorator method by its bare name.

        A JSDoc marker in the class's docblock (@Instantiatable) is a comment, not a
        decorator application, and is never checked against the whitelist.

    Bundle Ordering:
        Framework ensures decorator.js loads first in bundles to guarantee
        availability of decorator definitions.

JAVASCRIPT FILE STRUCTURE REQUIREMENTS
    Files Without ES6 Classes:
        JavaScript files that don't contain ES6 classes (utility files)
        may only contain these three types of code:

        1. Function declarations (standard or arrow functions)
        2. Const variables with static values (no function calls)
        3. Decorator definitions (functions marked with @decorator)

        Static values include:
        - Literals (strings, numbers, booleans, null)
        - Binary/unary expressions (e.g., 3 * 365, -100, !false)
        - Static arrays and objects (with literal values)

        NOT allowed:
        - Function calls in const values (e.g., Math.random())
        - let or var declarations at top level
        - Any other code outside the three allowed types

THE DECORATOR SIGNATURE (TC39 2023-11)
    Every decorator is called with two arguments:

        function my_decorator(value, context) { ... }

        value       What is being decorated: the class itself for a class
                    decorator, the method function for a method decorator.
        context     An object describing it:
                      kind            'class' or 'method' (also 'getter',
                                      'setter', 'field', 'accessor')
                      name            the class or method name
                      static          true for a static member
                      private         true for a #private member
                      access          get/has accessors for the member
                      addInitializer  register a function to run when the
                                      class (or instance) is initialized

    The return value REPLACES what was decorated: a class decorator may return a
    replacement class, a method decorator a replacement function. Returning
    nothing (undefined) keeps the original.

    A decorator with arguments is a FACTORY: @route('/contacts') calls
    route('/contacts'), and the function that call returns is the decorator.

    Evaluation order: the decorator expressions are evaluated top to bottom, then
    applied bottom to top - the decorator nearest the declaration runs first.

DEFINING DECORATORS
    Mark the definition with @decorator in its JSDoc. In a file with no ES6 class,
    a bare @decorator line directly above the function works too (the transform
    rewrites it into the JSDoc form).

    Class Decorator (the shape of @route, Core/SPA/Spa_Decorators.js):
        /**
         * @decorator
         * Tag an action with its section.
         */
        function section(section_name) {
            return function (value, context) {
                value._section = section_name;
                return value;
            };
        }

        @section('Billing')
        class Invoices_Index_Action extends Spa_Action { }

    Method Decorator (the shape of @debounce, Core/Js/async.js):
        /**
         * @decorator
         * Log each call of the decorated method.
         */
        function log_calls(label) {
            return function (value, context) {
                if (context.kind !== 'method') {
                    throw new Error(`@log_calls can only be applied to methods, not ${context.kind}`);
                }
                return function (...args) {
                    console.log(`${label}: ${context.name}`, args);
                    return value.apply(this, args);
                };
            };
        }

    Method Decorator Without Arguments (the shape of @mutex, Core/Js/Mutex.js):
        A decorator applied bare (@my_decorator, no parentheses) is called
        directly with (value, context):

        /**
         * @decorator
         */
        function trace(value, context) {
            return function (...args) {
                console.log(`enter ${context.name}`);
                return value.apply(this, args);
            };
        }

    Static Method Of A Class:
        A static method marked @decorator is whitelisted under its method name:

        class My_Decorators {
            @decorator
            static audit(value, context) {
                return value;
            }
        }

    Framework Core Decorator:
        The framework provides the @decorator marker itself in
        /app/RSpade/Core/Js/decorator.js: a function that returns what it is given,
        so @decorator applied to a method is a no-op at run time.

USING DECORATORS
    On A Class:
        @route('/contacts')
        @layout('Frontend_Layout')
        @spa('Frontend_Spa_Controller::index')
        @auth('is_logged_in')
        class Contacts_Index_Action extends Spa_Action { }

    On A Method (static or instance):
        class Contact_Search extends Component {
            @debounce(250)
            async search(term) { ... }

            @mutex
            async save() { ... }

            @log_calls('Contacts')
            static reindex() { ... }
        }

    Multiple Decorators:
        Applied bottom to top - the one nearest the declaration runs first, and
        each receives what the one below it returned:

        class Data_Processor {
            @log_calls('outer')    // Applied second: wraps the debounced method
            @debounce(250)         // Applied first: wraps the original method
            static transform(data) {
                return data.transform();
            }
        }

        @layout is written outermost first for the same reason: each @layout
        prepends its layout, so the first one written ends up first in the chain.

DECORATOR RESTRICTIONS
    Global Function Limitations:
        A global function may carry only the @decorator marker, no other
        decorator.

        /**
         * @decorator
         */
        function valid_global_decorator(value, context) { }   // + Valid - marking as decorator

        @some_other_decorator
        function invalid_global_usage() { }                   // - Invalid - FATAL at build

    Whitelist Validation:
        Only functions/methods marked with @decorator can be used on a class or a
        method.

        function unauthorized_function(value, context) { }    // Not marked

        class My_Class {
            @log_calls('x')
            static valid_usage() { }       // + Valid - whitelisted decorator

            @unauthorized_function
            static invalid_usage() { }     // - Invalid - not whitelisted
        }

        @route('/reports')                 // + Valid - whitelisted decorator
        @rout('/reports/:id')              // - Invalid - FATAL at build, misspelled
        class Reports_Action extends Spa_Action { }

COMMON DECORATOR PATTERNS
    Async Error Logging:
        /**
         * @decorator
         */
        function log_async_errors(value, context) {
            return async function (...args) {
                try {
                    return await value.apply(this, args);
                } catch (error) {
                    console.error(`Error in ${context.name}:`, error);
                    throw error;
                }
            };
        }

    Parameter Validation:
        /**
         * @decorator
         */
        function require_params(value, context) {
            return function (...args) {
                if (args.some(arg => arg === undefined || arg === null)) {
                    throw new Error(`${context.name} requires all parameters to be defined`);
                }
                return value.apply(this, args);
            };
        }

    Per-Instance Setup (addInitializer):
        /**
         * @decorator
         */
        function bound(value, context) {
            context.addInitializer(function () {
                this[context.name] = this[context.name].bind(this);
            });
        }

DECORATOR IMPLEMENTATION DETAILS
    Preserving Method Context:
        A replacement method is a plain function (not an arrow) that calls
        value.apply(this, args), so the method keeps its receiver and arguments.

    Checking What Was Decorated:
        A decorator meant for one kind of declaration checks context.kind and
        throws on any other, as @mutex does - a silent no-op on the wrong kind
        hides the mistake.

    Return Value Handling:
        Decorators can modify return values, but should be careful not to
        break expected return types.

    Error Propagation:
        Decorators should generally allow errors to propagate unless
        specifically designed for error handling.

MANIFEST INTEGRATION
    Build-Time Validation:
        The manifest system validates method decorators during build:
        1. Scans for @decorator markers
        2. Builds whitelist of authorized decorators
        3. Validates every decorator on a class or a class method against the whitelist
        4. Fails the build if an unauthorized decorator is found

    Bundle Processing:
        During bundle compilation decorator.js is placed first, then the other
        non-class files (where decorator functions live), then the class files.

TRANSFORM PIPELINE
    App JS is transpiled to browser-compatible code by the Babel transform server
    (app/RSpade/Core/JsParsers/resource/babel-service.js), then concatenated
    into a shared, non-module bundle scope. Because the bundle scope is shared, a
    decorated class MUST keep its module-scope bare-name binding: other files, jqhtml
    templates, and the SPA registry reference it by bare name, and a missing binding is
    a runtime ReferenceError (a white screen with no build-time signal).

    The Binding Defect:
        Upstream Babel's decorator transform DROPS the module-scope binding of a
        decorated class DECLARATION that has static members. It renames the class to a
        truncated uid and replaces the whole statement with a `new (...)()` expression,
        leaving no binding for the original name. This is a long-standing upstream defect
        (not fixed through Babel 8.0.1).

    The Vendored Fork:
        The framework ships a vendored, patched fork of Babel's decorator transform at
        app/RSpade/Core/JsParsers/resource/babel-plugin-decorators/ (a self-contained
        esbuild bundle with @babel/core externalized). The patch emits
        `var <OriginalName> = <uid>;` at the producer for exactly the dropped-binding
        case, so the bare name is always reachable. See that directory's README.md for
        the patch and regeneration steps. The fork replaces an earlier output-shape
        matcher that appended the binding by pattern-matching Babel's output; that matcher
        broke when @babel/compat-data 7.29.3 moved the destructuring baseline to Safari
        14.1 (preset-env then rewrote the matched shape before the matcher could see it -
        a silent miss producing a white screen).

    Fail-Closed Contract Assertion:
        The transform server records every top-level decorated class declaration before
        transform and, after transform, throws if any such name lost its program-scope
        binding. A dropped binding fails the build loudly (naming the class and file)
        instead of shipping a broken bundle. This checks the CONTRACT, not an output
        shape, so it survives future Babel changes.

    The Class's Own Name:
        The binding is half the contract; the class's own `.name` is the other half,
        because jqhtml and the SPA registry resolve a class BY that name. The transform
        emits `_<hash>_<Name> = <Name>` around a decorated class, so any later step that
        drops the class's own name lets JS infer `.name` from that hashed alias. Strict
        production minification therefore runs with keep_classnames / keep_fnames
        (rsx:man app_mode, STRICT PRODUCTION), and Manifest._define refuses at boot a
        class whose runtime `.name` is not its manifest name.

    Cache Fingerprint:
        Js_Transformer.php folds a toolchain fingerprint (the fork bundle, the transform
        server script, and the @babel/core version) into every transform cache key, so
        swapping any of them invalidates cached transforms automatically. The transform
        server is spawned on demand per build process and shut down at process end (not a
        persistent daemon), so a code change is picked up by the next build.


TROUBLESHOOTING
    Unauthorized Decorator Error:
        Error: "FATAL: Decorator not whitelisted"
        Solution: Add the @decorator marker to the decorator's definition

    Unauthorized Class Decorator Error:
        Error: "FATAL: Class decorator not whitelisted"
        Solution: Correct a misspelled decorator to one the message lists, mark
        your own decorator's definition @decorator, or move a marker such as
        @Instantiatable into the class's docblock comment

    Decorator On A Global Function:
        Error: "FATAL: Global function cannot use decorator"
        Solution: Remove the decorator; a global function carries only @decorator

    A Decorator Written For The Older Proposal:
        Symptom: a TypeError such as "Cannot read properties of undefined (reading
        'value')" when the class is defined - the decorator reads descriptor.value,
        and there is no descriptor in the (value, context) signature.
        Solution: Rewrite it to take (value, context) and return the replacement

    Decorator On The Wrong Kind Of Declaration:
        Error: "@mutex can only be applied to methods" (and the like)
        Solution: Apply it to a method, or check context.kind in your own decorator

    Build-Time Validation Failures:
        Check manifest build output for specific decorator validation errors
        Ensure all used decorators are properly whitelisted

TESTING DECORATORS
    Unit Testing Decorator Logic:
        // Call the decorator with a method and a context, then call the result
        const decorated = require_params(function (a) { return a; }, { kind: 'method', name: 'probe' });
        expect(decorated.call(null, 1)).toBe(1);
        expect(() => decorated.call(null, undefined)).toThrow();

    Integration Testing:
        // Test decorated methods
        class Test_Class {
            @require_params
            static test_method(a) {
                return a;
            }
        }
        expect(Test_Class.test_method('test')).toBe('test');

PERFORMANCE CONSIDERATIONS
    Decorator Overhead:
        Decorators add function call overhead. Use judiciously on
        performance-critical methods.

    Caching Decorators:
        Implement caching carefully to avoid memory leaks with
        dynamic data or large result sets.

    Bundle Size:
        Excessive decorator usage can increase bundle size.
        Consider if simple function calls would be more appropriate.

DECORATOR PARAMETER RESTRICTIONS
    Class Name Identifiers Prohibited (JS-DECORATOR-IDENT-01):
        Decorator parameters MUST NOT use class name identifiers (bare class
        references). The framework cannot guarantee class definition order in
        compiled bundle output, so referencing a class in a decorator parameter
        may fail if that class hasn't been defined yet.

        // WRONG - class identifier as parameter
        @some_decorator(User_Model)
        class My_Action extends Spa_Action { }

        // CORRECT - use string literal instead
        @some_decorator('User_Model')
        class My_Action extends Spa_Action { }

    Why This Matters:
        Bundle compilation orders classes based on inheritance hierarchies
        (extends chains) and other factors, but NOT based on decorator
        parameter dependencies. If Class A's decorator references Class B,
        there's no guarantee Class B will be defined before Class A's
        decorator is evaluated.

    Resolution:
        Pass class names as strings and resolve at runtime if needed:

        // In decorator implementation or consuming code
        const cls = Manifest.get_class_by_name('User_Model');

    Enforcement:
        This restriction is enforced by the JS-DECORATOR-IDENT-01 code quality
        rule, which runs at manifest build time for immediate feedback.
