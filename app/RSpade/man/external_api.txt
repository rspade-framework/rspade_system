EXTERNAL_API(1)                   RSpade Manual                   EXTERNAL_API(1)

NAME
    external_api - attribute-declared external REST API: bearer auth over a
    cookie-less headless Session, declarative param validation, bare-JSON
    responses, auto-generated docs/tester page, and an LLM-readable catalog

SYNOPSIS
    Declaring an endpoint (a static method on an Rsx_Api_Controller_Abstract):
        #[Api_Endpoint('/api/v1/contacts', methods: ['GET'])]
        #[Auth('is_logged_in')]
        #[Api_Param('page', type: 'int', required: false, default: 1)]
        #[Api_Param('search', type: 'string', required: false)]
        public static function list(Request $request, array $params = []) {
            return ['items' => [...], 'meta' => [...]];   // 200 bare JSON
        }

    Calling it:
        curl -H "Authorization: Bearer rsx_live_xxx" \
             https://your.host/api/v1/contacts?page=2

    Response helpers (app-facing):
        return Rsx_Api::created($model);          // 201
        return Rsx_Api::not_found('No such row'); // 404
        return Rsx_Api::validation_error(['email' => 'Invalid']); // 422

    Docs / tester - the APPLICATION routes to it and gates it:
        Rsx_Api_Docs::page($request, My_Bundle::class[, $restrict_to_key])
        Rsx_Api_Docs::openapi_document(): array   (the app builds the response)

    Provisioning a key from a script (see COMMAND LINE, under API KEYS):
        KEY=$(php artisan rsx:api:key:temp --user=1 --expires="2 hours" \
              --scope="/api/v1/*" --read-only \
              --json | jq -r .data.key)
        php artisan rsx:api:openapi --user=1 > openapi.json

    Config / keys / logs:
        config('rsx.api.log_retention_days')   Settings > API Keys   _api_request_log

DESCRIPTION
    TEMPLATE FEATURE - CHECK THE LIVING DOCUMENTATION FIRST
        What follows describes a feature that ships in the TEMPLATE APPLICATION your
        project was forked from (rsx/, your code), not in the framework (system/).
        Your copy may have changed contract, behaviour or shape since - or been
        removed. The current truth is the living file beside the code:

            rsx/app/api/CLAUDE.md
            app skill: none - see rspade:external-api for the framework contract

        Read it before relying on anything below; where it records a DIVERGENCE,
        it wins. This page remains the reference for how the feature was designed
        to work and the conventions it was built to - the shape RSpade expects
        application code to keep.

        This page is MIXED. The framework half - Rsx_Api_Controller_Abstract, the
        #[Api_Endpoint] / #[Api_Param] attributes and the dispatcher - is not
        subject to this notice. The template half - the v1 controllers this
        application ships - is.

    The RSX external API exposes externally-consumable REST endpoints, distinct
    from #[Ajax_Endpoint] (which is a browser-only, cookie-session RPC channel
    with auto-generated JS stubs). An external endpoint is a static method,
    declared with #[Api_Endpoint] plus repeatable #[Api_Param], on a class
    extending Rsx_Api_Controller_Abstract. The manifest discovers it at scan
    time; there is no routes/api.php to maintain.

    Unlike Laravel, which wires an external API through routes/api.php + a guard
    (Sanctum/Passport) + FormRequest validation + API Resources, RSX collapses
    all four onto the endpoint declaration itself:

    - Laravel: route file entry           RSX: #[Api_Endpoint] on the method
    - Laravel: Sanctum/Passport guard     RSX: framework-owned Bearer auth that
                                               establishes a headless Session
    - Laravel: FormRequest rules          RSX: #[Api_Param] specs (also drive docs)
    - Laravel: API Resource / transformer RSX: the model's redacting toArray()

    A request to /api/vN/... is handled by a dedicated Api_Dispatcher branch,
    NOT the main dispatcher: there is no cookie read, no _sessions row, and no
    Set-Cookie on any response. The bearer key resolves to a real user + site,
    and from then on Session:: reports that identity to ordinary controller code
    exactly as a browser session would - so a model's global site scope, an
    endpoint's Permission:: checks, and Rsx::Route() all work unchanged.

DECLARING ENDPOINTS
    A controller:

        namespace Rsx\App\Api\V1;

        class Contacts_Api_Controller extends Rsx_Api_Controller_Abstract {

            /**
             * List contacts for the authenticated site.
             *
             * @api-response {"items": [{"id": 1}], "meta": {"total": 1}}
             */
            #[Api_Endpoint('/api/v1/contacts', methods: ['GET'])]
            #[Auth('is_logged_in')]
            #[Api_Param('page', type: 'int', required: false, default: 1)]
            #[Api_Param('per_page', type: 'int', required: false, default: 20)]
            #[Api_Param('search', type: 'string', required: false)]
            public static function list(Request $request, array $params = []) {
                // $params holds ONLY validated, coerced, declared params.
                return ['items' => [...], 'meta' => [...]];
            }

            #[Api_Endpoint('/api/v1/contacts/:id', methods: ['GET'])]
            #[Auth('is_logged_in')]
            #[Api_Param('id', type: 'int', required: true)]
            public static function get(Request $request, array $params = []) {
                $c = Contact_Model::find($params['id']);
                return $c ?: Rsx_Api::not_found('Contact not found');
            }
        }

    #[Auth(check, ...)]
        MANDATORY on every API endpoint, exactly as on every other
        dispatchable surface - the manifest build FAILS without it (see
        rsx:man auth_gates). API surfaces are STAFF realm: the bearer key
        establishes a staff identity, so the checks are the same
        #[Auth_Check] methods on the app's Permission class that gate the
        web app. Evaluated by Api_Dispatcher AFTER the key authenticates and
        BEFORE the method; a denial is logged and returns 403
        {"error": {"code": "forbidden", "message": "Insufficient
        permissions"}} - distinct from the uniform 401 a bad key gets.

        The template ships 'is_logged_in' on its reference endpoints. It also
        DEFINES can_use_api() (PERM_API_ACCESS) but deliberately does not
        apply it, because keys minted before that permission existed would
        stop working; gating a NEW API surface on can_use_api() is the
        recommended shape when there is no such history to respect.

    #[Api_Endpoint(pattern, methods)]
        pattern   MUST start '/api/vN/' (N = one or more digits) and have a
                  segment after the version. :token placeholders are route
                  params (each REQUIRES a matching #[Api_Param]).
        methods   A non-empty subset of ['GET', 'POST']. No other verb exists
                  on the external API.

    #[Api_Param(name, type, required, default, description, example)]  (repeatable)
        name         The parameter name; matches a :token or a query/body key.
                     Names must be unique within an endpoint.
        type         'string' | 'int' | 'float' | 'bool' | 'file'.
                     Scalars, plus 'file' for a multipart upload part
                     (array/json remains backlogged). A 'file' param is
                     POST-only, can never be a :token, and can never carry a
                     default. See FILE ENDPOINTS.
        required     bool. A required param with no value -> 422.
        default      Value applied when an OPTIONAL param is absent. Declaring
                     BOTH required:true AND a default is a contradiction and
                     throws at scan time.
        description  Human text for the docs page.
        example      Sample value for the docs page and generated code samples.

    Docblock conventions (parsed at scan time):
        - The FIRST paragraph of the method docblock is the endpoint description.
        - @api-hidden           hides the endpoint from the docs page and the
                                LLM catalog (it still routes and works).
        - @api-response {json}  a verbatim example response shown on the card.

    SCAN-TIME ENFORCEMENT (Api_Endpoint_ManifestSupport, fails the manifest
    build with a RuntimeException - loud, immediate, non-bypassable):
        - pattern does not match #^/api/v[0-9]+/# (or has no segment after vN)
        - a verb outside {GET, POST}
        - the class does not extend Rsx_Api_Controller_Abstract
        - a :token with no matching #[Api_Param]
        - duplicate #[Api_Param] names
        - required:true combined with a default
        - a type outside {string, int, float, bool, file}
        - type 'file' on an endpoint that declares GET
        - type 'file' on a :route token
        - type 'file' carrying a default
        - #[FPC], #[Route], #[SPA], or #[Ajax_Endpoint] on the same method
        - a duplicate route pattern
        - API-GET-PURE-01: a write call in a GET-only handler's body (see KEY
          SCOPES)
      The converse guard lives in Route_ManifestSupport: a NON-API #[Route] (or
      an SPA route) under /api/vN/ also throws - the /api/vN namespace is
      reserved for the external API.

    CRITICAL GOTCHA - NEVER put a class constant in an attribute argument:

        #[Api_Param('status', type: 'int', default: My_Model::STATUS_ACTIVE)] // WRONG

    Reflection resolves the attribute's arguments while the manifest is being
    built, BEFORE the autoloader is ready to load My_Model, so the scan dies
    with an obscure class-not-found. Use a literal:

        #[Api_Param('status', type: 'int', default: 1)]                       // RIGHT

    (This is a general RSX attribute rule; it bites hardest here because
    #[Api_Param] naturally invites an enum default.)

PARAMETERS AND VALIDATION
    Api_Param_Validator runs after routing and before the controller. It:
        - REJECTS any key not declared by an #[Api_Param] -> 422 "Unknown parameter"
        - reports a missing required param       -> 422 "This field is required"
        - applies the default for an absent optional param
        - coerces a present value to its declared type; on failure -> 422
          "Expected int" (etc.)
      A 422 body carries per-field messages:
          {"error": {"code": "validation", "message": "Validation failed",
                     "fields": {"page": "Expected int"}}}

    Coercion rules:
        int    matches /^-?\d+$/           float  is_numeric()
        bool   truthy: 1 true yes on       falsy: 0 false no off
        string passthrough

    INPUT PRECEDENCE (highest wins): route params > GET query > body.
    The body is parsed as JSON when Content-Type is application/json,
    multipart/form-data when the request carries an upload, otherwise read as
    form POST. An application/json body that does not parse ->
    400 {"error": {"code": "invalid_json", ...}} (this is distinct from a 422).

    The controller receives $params containing ONLY the validated, coerced,
    declared parameters - nothing else reaches it. The one param that is
    VALIDATED BUT NEVER COERCED is 'file': it arrives as the
    Illuminate\Http\UploadedFile exactly as it was received. A non-file value
    for a 'file' param -> 422 "Expected a single uploaded file part
    (multipart/form-data)"; an UploadedFile offered for a SCALAR param is
    likewise refused, so a temp path can never be smuggled into a string.

RESPONSE CONTRACT
    The endpoint's return value becomes the HTTP response:

        Rsx_Model_Abstract   -> 200, redacting toArray() (see SERIALIZATION)
        Eloquent Collection  -> 200, ordered array of redacted models
        array                -> 200, JSON as-is (recursed: nested models redacted)
        null                 -> 204 No Content (empty body)
        JsonResponse         -> passed through unchanged (the Rsx_Api helpers)
        scalar (int/string)  -> shouldnt_happen() - a bare scalar is never a
                                valid API body; wrap it in an array

    All success responses are BARE JSON with a real HTTP status. There is NO
    {success, data} envelope (this was the pre-epic shape and is gone).

    Rsx_Api response helpers (return JsonResponse; error shape
    {"error": {"code", "message", "fields"?}}):
        Rsx_Api::created($data)                 201, serialized like a return
        Rsx_Api::no_content()                   204
        Rsx_Api::not_found(?$message)           404  code not_found
        Rsx_Api::unauthorized(?$message)        401  code unauthorized
        Rsx_Api::forbidden(?$message)           403  code forbidden
        Rsx_Api::validation_error($fields, ?$message)  422  code validation
        Rsx_Api::error($code, $message, $status, ?$fields)   arbitrary status

SERIALIZATION
    A returned model is serialized with the SAME redacting toArray() the
    fetch() system uses - never a hand-rolled transformer:
        - neverExport columns (password hashes, tokens, ...) are stripped
        - enum columns gain BEM-style magic properties: status_id__label, etc.
        - a __MODEL key identifies the model class
      Never alias enum fields to shorter names; the double-underscore forms are
      the contract (see rsx:man model_fetch, rsx:man enums). Because the model
      does its own redaction, an endpoint may return a model directly without
      worrying about leaking private columns.

AUTHENTICATION
    Authorization: Bearer rsx_... is the ONLY accepted credential. There is no
    X-API-Key header and no api_key query parameter. Auth runs FIRST, before
    any route matching, so every /api/vN/ path returns a UNIFORM 401 for a bad
    or missing key (an attacker cannot probe which endpoints exist):

        no Authorization header      -> 401 {"error": {"code": "auth_required"}}
        invalid / revoked / expired  -> 401 {"error": {"code": "unauthorized"}}

    On success the dispatcher resolves the key's user WITHOUT site scope
    (User_Model::without_site_scope() - there is no site identity yet to scope
    by), then establishes a headless identity:

        Session::_set_api_identity($login_user_id, $site_id, $user_id)

    From that point site scope applies everywhere (the user's own site), and the
    key's last_used_at is touched at most once per 60 seconds (throttled).

    HEADLESS SESSION SEMANTICS. The API identity is a distinct tier consulted
    ahead of the CLI/web tiers in every Session accessor. It is COOKIE-LESS and
    IMMUTABLE for the request:

        Session::is_logged_in()        true
        Session::get_user()            the resolved User_Model (site-specific)
        Session::get_user_id()         the user id
        Session::get_login_user_id()   the login-user id
        Session::get_site_id()         the key's site id
        Session::is_api_request()      true
        Session::get_session_id()      0        (no _sessions row is ever created)
        Session::has_session()         false
        Session::get_csrf_token()      null
        Session::get_session()         THROWS   (shouldnt_happen)
        Session::set_login_user_id(..) THROWS   (identity is immutable in API mode)
        Session::set_site_id(..)       THROWS

    A browser cookie riding along on a tester fetch() is never read and never
    re-set. No API response ever carries Set-Cookie. Calling _set_api_identity()
    twice in one request is a bug and throws.

    get_session_id() being 0 does NOT disable the file-attachment flow. The
    unattached-upload -> claim handshake never keyed on the session id:
    can_user_assign_this_file() asks exactly two questions - is this attachment
    still unclaimed, and is its site_id the current request's site. A bearer
    identity has a real site_id, so the claim succeeds. See FILE ENDPOINTS below
    and rsx:man file_upload.

THE IDENTITY ENDPOINT - GET /api/v1/me
    One of the four endpoints every RSpade API has, shipped by the framework
    rather than written per app (Identity_Api_Controller; the other three are
    the file endpoints below). A client hits it FIRST and OFTEN:
    to check a key at setup, to fail fast on a revoked one, to show "connected
    as" in a UI.

        curl https://host/api/v1/me -H "Authorization: Bearer rsx_live_..."

        {"user_id":1,"email":"...","site_id":1,
         "key":{"name":"...","prefix":"rsx_live_ab12...",
                "expires_at":null,"last_used_at":"...",
                "read_only":false,
                "scopes":"/api/v1/billing/*"}}

    key.read_only is true for a key that may execute GET requests only. A client
    that just took a 403 read_only_key can confirm here that the refusal is the
    KEY's shape rather than a permission it might be granted.

    key.scopes is the key's own canonical scope text, one path pattern per line,
    or null for an unrestricted key. A client that just took a 403
    insufficient_scope can read here exactly what it IS allowed to call, without
    an operator describing the key over chat - and it discloses nothing to
    anyone who does not already hold the key.

    IT REPORTS, IT DOES NOT AUTHORIZE. Reaching it at all IS the validation - an
    absent, malformed, revoked or expired key is a 401 from Api_Dispatcher
    before any of it runs, so a 200 means the key is good. The docs console's
    "Use key" button checks a pasted key against exactly this.

    It is a CONTRACT: path, verb and field names are stable across every install,
    so a client can be written once. Deliberately thin - identity and the key's
    own expiry, nothing else - because it is the endpoint an integration polls,
    and anything expensive here is paid for on every heartbeat. expires_at null
    means NO EXPIRY, not unknown.

FILE ENDPOINTS
    The framework ships THREE file endpoints. They move bytes and report on
    them; they deliberately do NOT attach a file to a record.

        POST /api/v1/files              upload; returns 201 + the attachment key
        GET  /api/v1/files/:key         metadata, URLs, preview/text status
        GET  /api/v1/files/:key/text    extracted text

    UPLOAD is multipart/form-data with a part named by the endpoint's 'file'
    param:

        curl -X POST https://host/api/v1/files \
             -H "Authorization: Bearer rsx_live_..." \
             -F "file=@contract.pdf"

    Optional filename_override stores the file under a different name. The
    response is the file payload: key, id, file_name, file_extension, mime_type,
    file_type, size, width/height, is_animated, duration, has_thumbnail,
    preview_unavailable, and absolute urls{download,inline,thumbnail,preview}.

    The upload gate applies here exactly as it does to POST /_upload: an app with
    no file.upload.authorize handler gets a loud 5xx, not an open endpoint, and a
    handler's refusal is returned verbatim. The size ceiling is checked BEFORE
    the gate (413 file_too_large). site_id is derived server-side; an API key is
    a STAFF credential, so the realm is never the portal.

    THE FILE ARRIVES UNATTACHED, AND THAT IS THE DESIGN. The framework does not
    own "attach this file to that record" - which record, which category and who
    may do it are application policy. The app writes that endpoint itself using
    the returned key:

        $attachment = File_Attachment_Model::find_by_key($params['key']);
        if (!$attachment || !$attachment->can_user_assign_this_file()) { ... }
        $attachment->add_to($record, 'documents');      // add_to = many files
                                                        // attach_to = replace

    can_user_assign_this_file() is STRUCTURAL - unclaimed, and in this tenant. It
    is not a per-user check and never was; authorizing the claim is the app
    endpoint's job. Removing one needs the ownership re-verification
    $record->find_attachment($id_or_key, $category), which returns null unless
    the attachment belongs to THAT record in THAT category.

    Worked example, both halves, in the reference app:
        system/app/RSpade/resource/reference_app/app/api/v1/clients_api_controller.php
        system/app/RSpade/resource/reference_app/app/api/v1/tasks_api_controller.php

    STATUS VOCABULARY. GET /api/v1/files/:key adds preview_status and
    text_status, each one of:

        pending      not converted / not extracted YET - poll
        available    ready
        error        terminal failure; never auto-retried
        unsupported  nothing to convert, or no extractor for this type

    Rendering and extraction are ASYNC, so a document uploaded a second ago is
    normally 'pending'. GET /api/v1/files/:key/text returns 409 with code
    text_pending / text_error / text_unsupported when the text is not available,
    and {key, text, text_status} when it is.

    BYTES ARE FETCHED FROM THE ORDINARY FILE ROUTES, WITH THE SAME KEY. These
    accept Authorization: Bearer in addition to a browser session, so an
    integration needs no cookie:

        /_download/:key          /_inline/:key
        /_thumbnail/preset/...   /_thumbnail/dynamic/...
        /_download_zip/:key      /_preview/pdf/:key

    A bad Bearer on one of these is a 401 - it never degrades to anonymous.
    Read authorization runs the file.thumbnail.authorize and (for bytes)
    file.download.authorize gates; a denial and a missing file are both 404.

API KEYS
    Keys are Api_Key_Model rows on the framework-core _api_keys table. Format
    rsx_{environment}_{random}; only sha256(plaintext) is stored, so the full
    key is shown exactly ONCE at creation:

        ['key' => $plaintext, 'model' => $model] = Api_Key_Model::generate(
            $user_id, 'My integration', 'live', $user_role_id = null,
            $expires_at = null, $scopes = null, $read_only = false
        );  // returns ['key' => 'rsx_live_...', 'model' => Api_Key_Model]

        Api_Key_Model::find_by_key($plaintext)   // sha256 lookup, non-revoked,
                                                 // null if expired
        $key->revoke();  $key->is_valid();  $key->get_user();

    Columns: user_id, name, key_hash, key_prefix ({prefix}{env}_ + first chars,
    for display), user_role_id (RESERVED - see below), scopes (TEXT NULL, the
    key's own scope set - see KEY SCOPES), read_only (TINYINT(1) NOT NULL
    DEFAULT 0 - GET requests only; see READ-ONLY KEYS), last_used_at, expires_at,
    is_revoked, timestamps.

    KEY PREFIX. config('rsx.api.key_prefix'), default 'rsx_', is the leading
    token on newly minted keys: {prefix}{environment}_{random} -> rsx_live_xxx.
    Rename it to your own product's short name. EXISTING KEYS ARE UNAFFECTED -
    lookup is sha256 of the whole key, never the prefix - so changing it can
    never invalidate a key already in service; only newly minted keys differ.

    MANAGEMENT UI. Settings > API Keys - staff create (name required; plaintext
    revealed once), view (name, prefix, scope, created, last used), and revoke
    keys.

    Minting asks for the key's ACCESS on two independent axes. A "Read-only key
    (GET requests only)" checkbox is the VERB axis; below it, Unrestricted
    (scopes NULL - the key carries every permission its holder has) or Scoped is
    the PATH axis, which offers the
    application's named presets, a free-text scope box with the whole grammar
    written out beside it, and a LIVE EFFECTIVE-ACCESS PANEL listing the
    endpoints the current union actually reaches, resolved by the server against
    the real route table (and narrowed to GET verbs while Read-only is ticked, so
    the panel never advertises a call the key would be refused on). The grid
    carries an Access column (Read-only / Read + write) and a Scope column
    (Unrestricted, or a scope count), plus a per-key view of both and of the
    endpoints the key reaches.

    A KEY IS IMMUTABLE AFTER MINT: there is no edit screen and no update
    endpoint, because narrowing a credential already in service would change
    what it can do under the integration holding it, silently and with no
    deploy. To change a key's scope, revoke it and mint a replacement.

    THE PRESETS ARE THE APPLICATION'S, not the framework's - see PRESETS ARE APP
    DATA under KEY SCOPES. The reference implementation is
    system/app/RSpade/resource/reference_app/app/frontend/settings/api_keys/.

    COMMAND LINE. The rsx:api:* namespace exists so a SCRIPT can grant itself
    access to this API and then use it: an importer or an exporter mints a key,
    calls /api/vN with Authorization: Bearer <key> like any other client, and
    exits. There is no privileged CLI channel into the API - the CLI mints a
    credential, and the script then speaks the same HTTP the outside world
    speaks, so it is gated on exactly the surface it will run against.

        php artisan rsx:api:key:create --user=<id|email> [--site=] [--name=]
                                       [--expires=] [--environment=live|test]
                                       [--scope=<rule>]... [--read-only] [--json]
        php artisan rsx:api:key:temp   --user=<id|email> [--site=]
                                       [--expires="1 hour"]
                                       [--environment=live|test]
                                       [--scope=<rule>]... [--read-only] [--json]
        php artisan rsx:api:key:list   --user=<id|email> [--site=] [--all]
                                       [--json]
        php artisan rsx:api:key:delete <id> [--purge] [--force] [--json]
        php artisan rsx:api:openapi    [--user=<id|email>] [--key=<id>]
                                       [--site=] [--compact]

    --user IS REQUIRED wherever it appears without brackets, and is spelled as
    an OPTION because that is how every other framework command spells it
    (rsx:debug, rsx:ajax, rsx:file:list). The requirement is enforced in the
    command, loudly, naming the flag - there is NO default user, because
    defaulting would mint a real key against an identity nobody named.

    It takes a users.id or an email address, resolved WITHOUT the site scope: a
    CLI process has no site context, and refusing to find a user for that reason
    would be an accident of the environment rather than an answer.

    --site DISAMBIGUATES, it does not select. users.id is a global primary key,
    so a numeric --user is already unambiguous and --site is only cross-checked
    against the row it found (a mismatch is refused). users.email is NOT unique
    - one person may hold a users row in several sites - so an email matching in
    more than one site is REFUSED with the candidates listed rather than a
    tenant being guessed. Omitting --site therefore means "infer it from the
    user", and the one case that cannot be inferred fails loud.

    --expires accepts an ISO datetime (2027-01-01) or a relative span ("30
    days", "6 months"). On create there is NO default: a key with no expiry
    lives until it is revoked, which is the right shape for a server-to-server
    integration. An expiry in the past is refused rather than created dead.

    create prints the plaintext ONCE. It is unrecoverable afterwards - only the
    hash reaches the database.

    temp is the same mint with a lifetime that defaults to one hour, matching
    what the docs tester issues. It is the shape a batch job wants: nothing has
    to remember to revoke it, and a job that dies half way leaves a credential
    that stops working by itself. Every key it mints is named "Temporary (CLI)"
    verbatim, in rsx:api:key:list and in Settings > API Keys, so what it is and
    whether it can go are answerable without reading the expiry column.

    --scope IS REPEATABLE, one path pattern per value - a scope set is a list,
    and a list is what a shell can build:

        --scope="/api/v1/contacts/*" \
        --scope="/api/v1/clients/#/view"

    A single value carrying embedded newlines is accepted too, for a script that
    already holds its scopes as text. They are validated and normalized BEFORE
    the mint, so a malformed scope exits with error.code scopes_invalid and
    leaves no key behind. Omitting --scope mints an unrestricted key, exactly as
    before the flag existed.

    list shows state, expiry, last used, created, and a Scope column reading
    'unrestricted' or a scope COUNT (with '(malformed - denies all)' when the
    row carries one that cannot be read) - a listing answers whether a key is
    narrowed at all, and --json carries the full canonical text under "scopes".
    It
    is ACTIVE ONLY by default;
    --all includes revoked and expired keys, which is what "why did this stop
    working" needs. Last-used is the field that answers "is this key still in
    service".

    delete REVOKES by default and keeps the row, because _api_request_log rows
    reference api_key_id: destroying the key would leave every call it ever made
    pointing at nothing, exactly when somebody is working out what it did.
    --purge removes the row outright, for a key created in error. Both prompt
    unless --force. It names the key by ID and not by --user: an id already
    identifies exactly one key across every user and site.

    MINTING IS NOT GATED ON users.is_api_access_enabled. This command runs as
    whoever holds shell access, a strictly higher privilege than any in-app
    permission, and a provisioning script that could not mint for a user it is
    about to enable would be useless. But a key minted for a disabled user is
    rejected at Api_Dispatcher on first use, which reads as "the key is broken",
    so create and temp both WARN and name the column - in the human output and
    as api_access_enabled:false in the JSON.

    THE --json ENVELOPE. Every rsx:api:key:* command takes --json, and under it
    STDOUT carries the JSON document and nothing else - no banner, no table, no
    trailing count - so it pipes straight into jq. One shape, every command:

        {"ok": true,  "command": "rsx:api:key:create", "data": { ... }}
        {"ok": false, "command": "rsx:api:key:create",
         "error": {"code": "user_not_found", "message": "..."}}

    A FAILURE IS STILL JSON, and still exits non-zero. Both halves are required:
    a script cannot parse an English error line, and a script that gets valid
    JSON back with a zero exit code carries on as though nothing happened.

    error.code is machine-stable and never reworded: user_required,
    user_not_found, user_ambiguous, user_site_mismatch, site_invalid,
    site_without_user, expires_invalid, expires_in_past, environment_invalid,
    key_not_found, confirmation_required.

    EXIT CODES are 0 on success and 1 on any handled failure, in both output
    forms. An unhandled fault still bubbles with its stack trace intact.

    delete under --json REQUIRES --force. A confirmation prompt would write a
    question onto the stream the script is parsing and then block forever
    waiting for an answer nobody is there to give, so it refuses with
    confirmation_required instead.

    rsx:api:openapi writes the OpenAPI 3.1 document to stdout, for feeding a
    client generator, a diff against last release's copy, or jq. It is the same
    document /apidocs/openapi.json serves, without a browser or an HTTP round
    trip.

    It has NO --json flag: every other command has a human form and a machine
    form and --json selects between them, while this one has only the machine
    form, and a flag that can only ever be passed is noise. Nor is the envelope
    applied to a successful run - the document IS the payload and has a shape
    generators already read, so wrapping it would mean every consumer unwrapping
    it. ERRORS do use the envelope, and are never mistaken for a document
    because a document has no "ok" key.

    Pretty-printed by default (the common use is reading it or committing it,
    where a one-line file makes every future diff unreadable); --compact for
    piping into something that does not care.

    --user scopes the document to the endpoints that user's #[Auth] gates
    actually admit, via Api_Tester_Key::accessible_targets_for_user() - the same
    fenced identity swap /apidocs uses for an adopted key. Without --user the
    document describes the whole published surface, which is what a public
    openapi.json is. --site on its own is refused: it disambiguates --user and
    scopes nothing by itself.

    --key=<_api_keys id> narrows further, and is the one to generate a client
    from: gates INTERSECTED with that key's own scopes, and with GET alone for a
    READ-ONLY key, so every operation in the document is one the key can
    actually call. It implies its user, so
    --user is redundant with it (naming a different user is refused, as is a
    revoked or expired key, which can reach nothing at all).

    END TO END. A key that grants itself access, uses it, and expires:

        KEY=$(php artisan rsx:api:key:temp --user=importer@example.com \
              --expires="2 hours" --json | jq -r .data.key)

        curl -s -H "Authorization: Bearer $KEY" \
             https://app.example.com/api/v1/clients | jq .

        # nothing to clean up: the key stops working in two hours.
        # to end it sooner, revoke by id:
        # php artisan rsx:api:key:delete <id> --force

    TESTER KEYS. The docs page's tester normally takes a key the developer
    PASTES, created in Settings > API Keys like any other. It can also mint a
    throwaway for itself (Api_Docs_Controller::mint_temporary_key): a live key
    for the signed-in user, named 'API Tester (temporary)', expiring in one
    hour. It is gated on the same Session::has_api_access() the page is, and it
    is the browser twin of rsx:api:key:temp.

    ROLE OVERRIDE - RESERVED, NOT ENFORCED. user_role_id is intended to let a
    key run at a REDUCED role. It is NOT honored: a key always runs at the
    user's actual role. Enforcement is invasive (the permission resolver reads
    role_id off the User_Model directly), so it is backlogged; the column is
    kept in place. Do NOT rely on it to restrict a key.

    NARROWING A KEY IS WHAT scopes IS FOR, and that one IS enforced - see KEY
    SCOPES below. The two are the same request from two angles, and they
    COMPOSE: were the role clamp ever built, effective authority would read

        (the user's permissions, clamped to user_role_id) INTERSECT the scopes

    because the intersection invariant already sits between the permissions and
    the rules. Nothing in the scope engine would move.

KEY SCOPES
    A key otherwise carries its holder's ENTIRE authority: an integration that
    only needs to read contacts can, with the same credential, delete every
    client its owner can delete. Scopes narrow ONE key below its holder without
    touching the holder. The whole meaning lives in Api_Scopes (static, pure -
    no database, no session, no config), and Api_Key_Model stores the text.

    A SCOPE IS A BARE PATH PATTERN, AND IT IS A GRANT. _api_keys.scopes holds
    one per line. There is no keyword, no HTTP method and no deny form:

        /api/v1/contacts/*
        /api/v1/clients/#/view
        /api/?/me

    THE GRAMMAR.

      - a scope starts with '/', and its first two segments are 'api' and a
        VERSION - a 'vN' literal, or '?' or '#';
      - '?', '#' and '*' are the ONLY wildcards, and each occupies a WHOLE
        segment. '/api/v1/foo/bar*', '/api/v1/?_id' and '/api/v1/b#r' are
        REFUSED: a half-segment wildcard reads as a literal and would silently
        match nothing while looking like a working pattern;
      - '?' matches exactly one non-empty segment of any shape;
      - '#' matches exactly one all-digits segment, so '/api/v1/clients/#/view'
        reaches client 42 and not a '/clients/settings/view' that may exist;
      - '*' may appear ONLY as the LAST segment, and matches the prefix itself
        AND everything below it. '/api/v1/files/*' reaches '/api/v1/files',
        '/api/v1/files/abc' and '/api/v1/files/abc/text';
      - every other segment is a LITERAL, compared exactly and CASE-SENSITIVELY
        - which is what RouteResolver itself does, so a scope can never admit a
        path the router would not route;
      - a TRAILING SLASH is meaningless on BOTH sides, and the QUERY STRING is
        not part of a path at all: both are stripped before anything is
        compared. '/api/v1/clients', '/api/v1/clients/' and
        '/api/v1/clients?page=2' are one and the same path, and none of them
        matches '/api/v1/clients/view'.

    Worked examples:

        /api/v1/foo/baz/*   matches /api/v1/foo/baz
                                    /api/v1/foo/baz/x
                                    /api/v1/foo/baz/x/y
                            not     /api/v1/foo
        /api/v1/clients/#/view
                            matches /api/v1/clients/42/view
                            not     /api/v1/clients/settings/view
                            not     /api/v1/clients/42
        /api/?/clients      matches /api/v1/clients  /api/v7/clients
                            not     /api/v1/clients/42
        /api/v1/clients     matches /api/v1/clients  and /api/v1/clients/
                            not     /api/v1/clients/view

    '#' IS ACCEPTED AS THE VERSION SEGMENT even though no 'vN' literal is all
    digits, so it matches nothing there. It is grammar, not a special case:
    every wildcard is legal in every position the grammar allows one.

    THE PATH IS THE SCOPE NAMESPACE, deliberately. There is no derived
    resource:action vocabulary to keep in step with the routes and no
    per-endpoint annotation to forget, so a new endpoint is covered - or not
    covered - by patterns that already exist. It is impossible to ship an
    endpoint that forgot to declare its scope, which is the failure mode every
    annotation-based design carries. And a scope set reads URL-for-URL against
    the /apidocs catalogue. Every scope carries its /api/<version>/ prefix, so a
    v2 rename can never silently re-scope a v1 key.

    NULL IS UNRESTRICTED. A null or blank scopes column leaves the key at its
    holder's full authority. The presence of ANY scope flips the key into
    whitelist mode: DENY BY DEFAULT. There is therefore nothing to write a
    denial for, and no way to write one.

    THE METHOD IS NOT PART OF A SCOPE. GET and POST are indistinguishable to
    this language, and "read-only" is not expressible in it. That is what the
    key's own read_only flag is for - a separate axis, enforced separately; see
    READ-ONLY KEYS below. Ticking two presets is SET UNION, commutative and
    associative, so a mint UI has no ordering to get right and no "which one
    wins" to explain.

    A MALFORMED STORED SCOPE IS IGNORED FOR MATCHING AND STILL COUNTS.

    Every write path validates, so the only way to get one is to edit the column
    by hand. When one is read, it grants nothing - and the key still has a
    registered scope, so it is still deny-by-default and now denies EVERYTHING.
    It FAILS CLOSED, which is the only safe reading of "somebody wrote a rule
    here and it cannot be understood". Each such scope logs one warning per
    request evaluation:

        API key #7: ignoring malformed scope '/api/v1/foo*' - a wildcard must
        be a whole segment: '/api/v1/foo*'

    rsx:api:key:list says so in its Scope column too ('2 scopes (malformed -
    denies all)'), and $key->has_malformed_scopes() is the predicate.

    CREATION AND VALIDATION. One validator, one exception:

        Api_Scopes::validate($scope)   throws Api_Scope_Validation_Exception,
                                       whose MESSAGE is the human-readable rule
                                       that was broken

    Every write path runs it, and the FIRST bad scope refuses the WHOLE set -
    Api_Key_Model::generate(), Api_Key_Model::set_scopes(), the rsx:api:*
    --scope flag, and an application's own mint endpoint. Nothing is written
    when it throws: a scope set that cannot be read must never become a
    credential somebody believes is narrow. Storage is one normalized scope per
    line, duplicates collapsed.

    An application endpoint CATCHES it and answers the form:

        try {
            $scopes = Api_Scopes::canonicalize($text);
        } catch (Api_Scope_Validation_Exception $e) {
            return response_form_error($e->getMessage(), ['scopes' => $e->getMessage()]);
        }

    ONE MATCHER, IN PHP. Api_Scopes::matches() is the only implementation of
    this grammar anywhere in the framework. Anything that previews or narrows -
    the mint modal's effective-access panel, the /apidocs listing - asks a PHP
    endpoint; there is no JavaScript twin, because a second implementation would
    drift and the drift would surface as a key that previews one thing and does
    another.

    INTERSECTION IS THE INVARIANT - SCOPES SUBTRACT ONLY.

        effective authority = the user's LIVE permissions INTERSECT the scopes

    A scope can never grant what the user lacks. This is framework-enforced and
    not optional, because implementing it backwards is privilege escalation
    rather than a misconfiguration. Two corollaries: a user who loses a
    permission narrows every key they hold IMMEDIATELY (scopes are evaluated per
    request against current permissions - never frozen at mint, never cached);
    and a key may be minted with scopes broader than its holder without becoming
    dangerous, because the intersection clamps it.

    PIPELINE POSITION. Api_Dispatcher runs:

        verb gate -> bearer auth -> READ_ONLY -> route match -> SCOPE
        -> param validation -> #[Auth] gates -> controller

    Scope AFTER read_only, because the two answer different questions and the
    integrator must be told which one refused: read_only is about the VERB and
    names no path, a scope is about the PATH and names no verb. So a read-only
    key with no scopes still GETs everything its holder may, and a read-only key
    never reaches a POST handler even when a scope names its path.

    Scope BEFORE validation, so a key that may not reach an endpoint learns
    nothing about its parameters. Scope BEFORE the gates, so a too-narrow key is
    reported as a KEY problem rather than a permissions problem - and the gates
    still run for a key that clears its scope, which is what makes the check
    subtractive.

    DISPATCH IS ROUTE-ONLY, AND THAT IS PART OF THE SCOPE CONTRACT. An external
    API request resolves ONLY against the manifest's declared #[Api_Endpoint]
    route patterns, exact-match, by path. There is deliberately NO by-name
    channel: nothing addresses a handler by controller class plus action name
    the way Rsx::Route('Class::method') addresses a web route or
    /_ajax/Class/method addresses an internal Ajax endpoint, and none may ever
    be added. A scope IS a path pattern, so a second way to address the same
    handler would be a URL no scope was written against - every scoped key in
    existence would reach every endpoint through it. If a handler needs to be
    reachable, it gets a route.

    DENIAL. 403 with its own machine-readable code, distinct from the
    permission 403 the gates produce:

        {"error": {"code": "insufficient_scope",
                   "message": "This API key is not scoped for this endpoint",
                   "required": "/api/v1/clients/:id/delete"}}

    forbidden means "ask your administrator for the permission";
    insufficient_scope means "mint a wider key". An integrator cannot act on the
    two the same way, and without the distinction they are indistinguishable.
    'required' is the matched ROUTE PATTERN, not the request path: it names the
    thing a scope would have to reach, and its ':id' tokens say which segments
    are the caller's to fill in.

    Every scope denial reaches _api_request_log like every other outcome, so
    "why did this call stop working" stays answerable from the log.

    THE WEB BEARER ROUTES ARE CLAMPED TOO. The file-serving web routes
    (/_file/..., /_thumbnail/..., /_download_zip/..., /_preview/pdf/... - see
    FILE ENDPOINTS) accept a Bearer key on a URL that carries no /api/vN/ path
    for a scope to match, and they serve the very bytes GET /api/v1/files/:key
    describes. So Rsx_Api_Bearer::authenticate_web_request() evaluates a scoped
    key against a SYNTHETIC path inside the files subtree - "does any scope
    reach the files subtree" - and answers the same insufficient_scope 403 when
    it does not. Without this the scope would be advisory: a key scoped away
    from files would be refused by the API and handed the same file on
    /_download. That 403 names no 'required' target, because the synthetic path
    is not an endpoint anybody could call.

    API-GET-PURE-01 - A GET ENDPOINT MAY NOT MUTATE. This is the build-time half
    of the read-only guarantee; the runtime half is the key's read_only flag. See
    GET IS FOR READS, POST IS FOR WRITES below for the design rule both enforce.
    Api_Endpoint_ManifestSupport fails the manifest build when a GET-only
    handler's body contains

        ->save(   ->delete(   ->update(   ::create(   ->raw_bulk(
        DB::statement(  DB::insert(  DB::update(  DB::delete(
        Task::dispatch(

    The body is read from source and tokenized, so comments and string literals
    cannot trigger the rule and spacing cannot evade it. ONLY THE HANDLER'S OWN
    BODY IS INSPECTED - a private helper it calls is not followed, which is the
    honest limit of a literal-token rule and the reason the escape exists:

        /**
         * @API-GET-PURE-01-EXCEPTION records a read receipt the caller asked
         * for; no user-visible state changes.
         */

    The RATIONALE IS REQUIRED - a bare tag fails the build, because recording
    that somebody wanted the rule off is not the same as recording a reason.

    PRESETS ARE APP DATA. The framework NEVER names a scope, exactly as
    Auth_Gates never names a permission and leaves the #[Auth_Check] vocabulary
    to the app's Permission class. An application contributes a list of named
    path sets, not annotations scattered across controllers:

        // rsx/resource/config/rsx.php
        'api' => [
            'scope_presets' => [
                ['name' => 'Everything in v1',
                 'description' => 'Every endpoint of API version 1.',
                 'scopes' => "/api/v1/*"],
            ],
        ],

    config('rsx.api.scope_presets') is read by the APPLICATION's key UI and by
    nothing in framework core. The union of the ticked presets is
    order-independent, so the UI has no ordering to get right. The template
    app's presets and its whole mint modal are the worked example, at
    system/app/RSpade/resource/reference_app/app/frontend/settings/api_keys/.

    #[Api_Scope] IS NOT BUILT. An attribute overriding an endpoint's derived
    pattern for matching purposes was considered and declined: if it became the
    norm the path-pattern design would have failed and should be revisited
    rather than papered over.

    THE API OVER SCOPES.

        Api_Scopes::validate($scope)           void; throws
                                               Api_Scope_Validation_Exception
        Api_Scopes::normalize($scope)          trimmed, query string and
                                               trailing slash gone
        Api_Scopes::matches($scope, $path)     one scope, one path
        Api_Scopes::parse_all($stored)         ['valid' => [...],
                                                'malformed' => [text => reason]]
        Api_Scopes::canonicalize($text)        storage form; null when empty;
                                               throws on the first bad scope
        Api_Scopes::count_scopes($stored)      valid + malformed
        Api_Scopes::is_unrestricted($scopes)   null or blank
        Api_Scopes::decide($scopes, $path, $key_id = null)
                                               the dispatcher's question; the
                                               key id turns on the malformed
                                               warning
        Api_Scopes::reaches_route($scopes, $pattern)
                                               does a scope set reach a declared
                                               ROUTE pattern - a route's ':id'
                                               is an OPAQUE segment reached by
                                               '?', by '#' and by any literal,
                                               so this answers "which
                                               endpoints", not "which URLs"

        Api_Catalog::resolve_for_scopes($version, $scopes)

                                               live preview needs.

        $key->is_unrestricted()  $key->get_scope_rules()  $key->set_scopes($t)
        $key->has_malformed_scopes()
        Api_Key_Model::generate(..., $scopes = null)


GET IS FOR READS, POST IS FOR WRITES
    THE DESIGN RULE. A GET endpoint is a READ. Anything that changes application
    data - a create, an update, a delete, a state transition, a send, a queued
    job that will do any of those - is a POST. There is no third verb to reach
    for (the dispatcher accepts GET and POST and nothing else), so this is not a
    style preference about REST: it is the ONLY thing that gives the word "read"
    a meaning anywhere else in this document.

    INCIDENTAL BOOKKEEPING IS FINE. A GET may write the things that are ABOUT
    the request rather than about the data: a request log row, a last-used or
    last-seen stamp, a view counter, a cache fill. The test is whether a caller
    who never made the request could tell: if the only difference is in
    telemetry, the endpoint is still a read. If a record the application's own
    screens show has changed - a status, an owner, a total, a queue entry - it is
    a write, and it belongs on POST.

    TWO HALVES, AND NEITHER IS WORTH ANYTHING ALONE.

      - BUILD TIME, on the HANDLER: API-GET-PURE-01 (see KEY SCOPES above) fails
        the manifest build when a GET-only handler's body carries a write call.
        The handler cannot lie about what it is.
      - RUN TIME, on the CALLER: _api_keys.read_only refuses every non-GET
        request made with that key, with 403 read_only_key. The credential
        cannot be used for anything but reads.

    The flag would be a label rather than a guarantee if a GET could mutate, and
    the build rule would be an academic tidiness exercise if nothing could hand
    out a GET-only credential. Together they add up to a promise an operator can
    make to somebody else: "this key cannot change anything."

    WHAT THE ESCAPE IS FOR. API-GET-PURE-01 reads only the handler's own body and
    matches literal call shapes, so it cannot see a write inside a private helper
    and it cannot tell a bookkeeping write from a real one.
    '@API-GET-PURE-01-EXCEPTION <rationale>' in the method docblock waives it for
    one handler, and the RATIONALE IS REQUIRED - a bare tag fails the build.
    Waive it for the incidental bookkeeping described above, never to let a GET
    perform a user-visible mutation: the rule is the reason a read-only key means
    what it says, so an exception written to get a build green removes that
    meaning for every key in the system.

READ-ONLY KEYS
    A key with _api_keys.read_only = 1 may execute GET requests and nothing else.
    It is the runtime half of the guarantee above, and the answer to the request
    the scope grammar cannot express - a scope is a path pattern with no method
    in it, so "every read endpoint" cannot be written as a scope. (The former
    'Read-only' scope preset was removed for exactly that reason; this flag
    replaces it.)

    THE REFUSAL. Any method other than GET, with any path:

        {"error": {"code": "read_only_key",
                   "message": "This API key is read-only: GET requests only."}}

    403, and no 'required' target: nothing the caller could write in a scope
    would make the request work.

    WHERE IT IS DECIDED. After the bearer key resolves and BEFORE the route is
    matched, so a read-only key learns nothing about which write endpoints exist:
    a POST to a path that does not resolve is refused identically to one that
    does. It is decided before the SCOPES for the same reason the scopes are
    decided before the #[Auth] gates - each refusal must name the thing the
    caller has to change:

        read_only_key       this credential cannot write at all
        insufficient_scope  mint a wider key
        forbidden           ask your administrator for the permission

    THE TWO NARROWINGS COMPOSE and neither implies the other. A read-only key may
    be unrestricted; a scoped key may write. Effective authority is

        the user's LIVE permissions
            INTERSECT the key's scopes
            INTERSECT (read_only ? GET only : every verb)

    SET AT MINT, NEVER CHANGED. Like the scopes, read_only is fixed when the key
    is created: Api_Key_Model::generate(..., $read_only = false) is the only
    writer and there is NO setter. Widening a credential already in service would
    change what it can do under the integration holding it, silently and with no
    deploy. To change a key's access, revoke it and mint a replacement.

    WHERE IT SHOWS.

        Api_Key_Model::generate($user_id, $name, 'live', null, null, $scopes,
                                $read_only = true)
        $key->read_only                          bool (cast)
        GET /api/v1/me                           key.read_only
        rsx:api:key:create --read-only           mint one
        rsx:api:key:temp   --read-only           mint a self-expiring one
        rsx:api:key:list                         an Access column: read-only /
                                                 read+write ('read_only' in
                                                 --json)
        Settings > API Keys                      the mint checkbox, the grid's
                                                 Access column, the view modal
        /apidocs                                 a 'read-only' badge, and a
                                                 listing with the write
                                                 endpoints removed

    THE CONSOLE HIDES WHAT THE KEY CANNOT DO.
    Api_Tester_Key::accessible_targets_for_key() drops every endpoint that
    declares no GET verb, and Api_Catalog::resolve_for_scopes($version, $scopes,
    $include_hidden, $read_only) keeps GET verbs alone - so a console or a
    preview panel drawn for a read-only key never offers a call that would come
    back read_only_key.

    THE WEB BEARER ROUTES NEED NO CLAMP. Every route that accepts a Bearer key
    outside /api/vN (/_download, /_inline, /_thumbnail/*, /_download_zip,
    /_preview/pdf) is declared GET-only, so a read-only key may use all of them
    by definition. A non-GET route adopting that credential would need this gate
    as well as the files-subtree scope clamp.

    A DISABLED WRITER IS NOT THIS. read_only narrows ONE CREDENTIAL;
    users.is_api_access_enabled decides whether an identity may use the API at
    all, and a role or an #[Auth] check decides what a person may do however they
    signed in. Reach for read_only when the HOLDER is trusted and the INTEGRATION
    only needs to read - a reporting job, an export, a dashboard, a key pasted
    into somebody else's tool.

VERSIONING
    Versioning is URL-only (/api/v1/..., /api/v2/...) and EXACT-MATCH at runtime
    - there is NO fallthrough from v2 to v1. A request to a path that does not
    exist at its stated version is a 404 (after auth).

    DOCS DISPLAY RULE (Api_Catalog, the single implementation both the docs page
    and the LLM catalog consume): endpoints are grouped by (verb, path with the
    vN segment stripped). For a selected version V, each group shows the single
    NEWEST endpoint whose version is <= V, at its REAL /api/vN path. So viewing
    "v3" shows a v1 endpoint that was never re-versioned at its v1 path, and the
    v2 revision of another endpoint at its v2 path - the newest each is at or
    below v3. Runtime routing never applies this rule; it is purely how the
    catalog PRESENTS versions.

    Api_Catalog (pure functions over the manifest):
        get_versions()                 distinct versions, descending
        resolve_for_version($v)        the display-rule winners for version $v
        parse_version($pattern)        '/api/vN/...' -> N
        path_key($pattern)             the vN-stripped grouping key

DOCS AND TESTER PAGE
    A developer console - browse endpoints, read parameters, copy a code sample,
    and send a real request. It is NOT bearer-authenticated: it is a page in your
    application, and it is reached at whatever path your application routes to.

    THE APPLICATION OWNS THE ROUTE AND THE GATE. The framework declares no
    route for the console and has no visibility setting: it exists if and only
    if an application routes to it, protected by whatever #[Auth] that route
    carries. That reuses the permission vocabulary an app already has instead of
    inventing a parallel one.

        #[Auth('can_manage_integrations')]
        class Developer_Tools_Controller extends Rsx_Controller_Abstract
        {
            #[Route('/dev/api-reference')]
            public static function api_docs(Request $request, array $params = [])
            {
                return Rsx_Api_Docs::page($request, Developer_Tools_Bundle::class);
            }

            #[Route('/dev/api-reference/openapi.json')]
            public static function api_openapi(Request $request, array $params = [])
            {
                return response()->json(Rsx_Api_Docs::openapi_document(), 200, [
                    'Content-Type' => 'application/json; charset=utf-8',
                    'Content-Disposition' => 'attachment; filename="openapi.json"',
                ], JSON_UNESCAPED_SLASHES | JSON_PRETTY_PRINT);
            }
        }

    Page and document are SEPARATE calls so they can be gated differently - a
    public openapi.json beside a staff-only console is a normal arrangement.

    They are also different KINDS of call. page() renders a RESPONSE;
    openapi_document() returns an ARRAY, and the controller builds the response
    around it. Status, content type and whether the browser renders the JSON
    inline or downloads it are the route's business, not the generator's - the
    reference app serves it as an attachment, because what a developer does with
    the file is feed it to a client generator.

    API ACCESS IS THE GATE THE CONSOLE USUALLY WANTS. A console listing an API
    the viewer may not call is a lie, so the reference app gates both routes on
    Session::has_api_access() (users.is_api_access_enabled) rather than on a
    role - the same predicate Api_Dispatcher applies to a Bearer key, so the
    console cannot drift from what the API will accept. A denial is rendered by
    Error_Screens::unauthorized($request), which sends an unidentified caller to
    the login route and shows an identified one a themed 403. See
    reference_app/app/apidocs/apidocs_controller.php.

    THE BUNDLE IS THE APPLICATION'S TOO, and must include its own directory plus
    app/RSpade/Core/Api. A bundle has to cover the directory of the controller
    that rendered it, so a framework bundle could never serve an app's route. It
    forwards one hook:

        public static function load_rsxapp_data(): array
        {
            return Rsx_Api_Docs::rsxapp_data();
        }

    Worked example, twelve lines including the docblock:
    system/app/RSpade/resource/reference_app/app/apidocs/

    RESTRICTED LISTING. page()'s third argument (default TRUE) lists only the
    endpoints whose #[Auth] gates pass for the API key the viewer supplied,
    scoped to the KEY'S user rather than the viewer's - the console is answering
    "what can this integration do". With no key the sidebar lists NOTHING and
    the landing card says why, because the key IS the question being asked.
    Supplying one calls Api_Docs_Controller::adopt_tester_key and RELOADS: the
    catalog is baked into the page at render, so a key adopted afterwards
    changes nothing until the page is built again.

    Pass false to list every published endpoint. Either way this is about not
    ADVERTISING surfaces a caller cannot use; it is NOT access control, and
    Api_Dispatcher gates every call regardless of what the page showed.

    HOW THE FILTER KNOWS. Auth checks are parameterless and evaluate against the
    current session, so the only way to ask "would this gate pass for the key's
    user" is to become that user for the duration of the question.
    Api_Tester_Key::accessible_targets() establishes the same headless identity
    Api_Dispatcher uses (Session::_set_api_identity), evaluates
    Auth_Gates::can_access per endpoint, and tears the identity down in a
    finally. The identity fence is the whole fence: Auth_Gates evaluates every
    check live, so the answers follow whichever identity is installed at the
    moment of the ask and there is nothing to invalidate around the swap.

    The adopted key is remembered as an ID in session-scoped storage
    (Session::put_value), which the browser never names and therefore cannot
    forge. The PLAINTEXT stays in the browser for the tester's Authorization
    header; it cannot come back from the database, which holds only the hash.

    ONE COMPONENT, NOT AN SPA MODULE. Api_Docs_Console owns the whole page and
    does its own history handling: a sidebar click pushes state and redraws only
    the $redrawable body, and Back/Forward restores the previous endpoint. It is
    mounted by an ordinary #[Route], so Spa's link interception does not apply
    and the console's handler is unambiguous rather than competing with it.

    That is not a workaround. An SPA split rebuilt the header, key bar and
    sidebar on every click (Spa never reuses an action) and lost the class off
    the content element (Spa._clear_container_attributes). Owning the page keeps
    the sidebar's filter text, its scroll position, and the key bar's input.

    COMPONENTS:

        Api_Docs_Console   the page: chrome, navigation, and the body region
        Api_Docs_Header    wordmark (links home), version selector, openapi link
        Api_Docs_Sidebar   resource-grouped nav plus a filter box; filtering is
                           DOM-level, not a re-render, so the focused input is
                           never rebuilt mid-keystroke
        Api_Docs_Home      the landing pane, and the key gate when restricted
        Api_Docs_Catalog   synchronous reader over the baked catalog - there is
                           no loading state anywhere in the UI because there is
                           nothing to wait for
        Api_Key_Bar        paste a key; VALIDATED against /api/v1/me before it is
                           accepted, so a bad key fails here rather than later on
                           some unrelated endpoint. Held in session storage, never
                           persisted. With a key set the input is replaced by the
                           masked key and a Clear button
        Api_Code_Samples   curl / php / js / python / powershell, generated from
                           the catalog. See FILL IN VALUES below
        Api_Tester         the live tester. See WHAT THE TESTER VALIDATES below

    WHAT THE TESTER VALIDATES: path parameters, and nothing else. A URL cannot be
    built without them, so there would be no request to send and no server answer
    to show. Everything else deliberately reaches the server unchecked - a
    required field left blank comes back as the endpoint's own 422, which is the
    thing a tester exists to show, and a second client-side rulebook would drift
    from the real one. An unparseable JSON body is sent too: the dispatcher's 400
    invalid_json is more useful than a message the page invented.

    UNSET MEANS OMITTED. A blank query parameter is not sent as an empty string
    and a blank body field is dropped from the JSON - sending "" would assert a
    value the user never gave, which for an update is the difference between
    "leave this alone" and "clear it".

    FILL IN VALUES (a checkbox in the Code samples tab strip, off by default)
    swaps the samples from documentation to the exact request the tester beside
    them would send: the adopted key, the values typed, unset fields omitted,
    path parameters merged in, updating live as the reader types. It reads
    Api_Tester::current_values() - the same method the Send button uses - so a
    sample can never describe a different request from the one that would be made.

    Off, samples use each param's declared example and the literal {API_KEY}:
    copyable code must not carry a real credential into a file or a chat window.

    A path parameter left blank stays as {name}, marked red with a tooltip,
    rather than being silently invented - a sample that looked runnable and was
    not would be worse than one that says what is missing.

    ESCAPING. Every value in a sample is escaped for the language it lands in
    (api_docs_escaping.js: bash, php, python, powershell, js literals), and URL
    values are escaped TWICE - percent-encoded for the URL, then quoted for the
    language embedding it. Do only the first and a space breaks the command; do
    only the second and the server receives something else. In a shell sample the
    difference is not cosmetic: an unescaped value is a command.

    LAYOUT. The card is two columns above 1850px - reference (verb, parameters,
    example response) left, the things you act on (samples, tester) right - so a
    sample stays readable beside the tester that shaped it. The example response
    also starts expanded at that width, where a collapsed panel is just a click.
        Api_Endpoint_Card  one card per endpoint (description, params, example)
        Api_Params_Table   the #[Api_Param] specs rendered as a table
        Api_Code_Samples   curl / php / js / python / powershell, GENERATED
                           client-side from catalog data (never authored per
                           endpoint), with a {API_KEY} placeholder
        Api_Tester         a live tester: a form built from the param specs (a
                           plain JSON body textarea on POST), firing a native
                           fetch() with the Authorization header ($.ajax is
                           blocked framework-wide; fetch is not) and rendering
                           the status + highlighted JSON response
        Api_Key_Bar        paste a key (the page never mints one); the key is
                           held in Rsx_Storage session scope (never persisted)

    THE OPENAPI DOCUMENT. /apidocs/openapi.json (login-gated) returns
    Api_Openapi::document() - an OpenAPI 3.1 description of every published
    endpoint across every version, served application/json with
    Content-Disposition: inline so a browser renders it in its JSON viewer
    rather than downloading it.

    OpenAPI rather than a house format because everything that consumes an API
    description already speaks it: client generators, Postman/Insomnia, mock
    servers, contract testers, and the LLM/agent toolchains. A bespoke shape has
    to be explained before it can be used.

    Api_Openapi is a PURE PROJECTION of Api_Catalog::get_endpoint_list() and
    invents no facts. Its translation decisions:

        :token -> {token}   OpenAPI templates path params in braces.
        path params         in:path, and required:true (OpenAPI mandates it).
        GET other params    in:query.
        POST other params   a requestBody object. The dispatcher also accepts
                            them as query on POST, but the body is the
                            documented shape and the one the tester sends.
        a 'file' param      the requestBody becomes multipart/form-data and the
                            part is type:string, format:binary. One 'file' param
                            is what makes an endpoint multipart; the PART NAME is
                            the param's own name, never assumed to be 'file'.
        superseded          deprecated:true when a HIGHER version exists for the
                            same verb + path_key. Every version stays listed at
                            its real path, because every version stays callable.
        @api-hidden         omitted entirely.

    Every version is listed; the catalog display rule above is a DOCS-PAGE
    concern and has no equivalent here - paths are paths, and all of them work.

    THE .json PATH. AssetHandler::is_asset_request() claims any *.json path
    BEFORE route dispatch, so a generated document at a natural filename used to
    be unreachable. It is reachable now because the asset seam FALLS THROUGH:
    AssetHandler::try_serve() returns null when the public directories hold no
    such file, and both dispatchers continue to the route table on null. A real
    file still wins, so no asset that resolves today can be shadowed by a route
    added tomorrow, and no route needs registering anywhere for this to work.

    /_compiled/ and /_vendor/ deliberately do NOT fall through - a miss there is
    a build problem, and a route scan would turn a loud failure into a 404.

REQUEST LOGGING
    EVERY API request - success and every failure path - writes one
    _api_request_log row (Api_Request_Log_Model, $realtime_silent = true):

        verb, path, handler (Class::method or null when unmatched),
        status, duration_ms, ip, and nullable api_key_id / user_id / site_id
        (null where unknown, e.g. a 401 before the key resolved).

    WHAT WAS EXCHANGED is recorded alongside what was called:

        request_body            The payload as sent - REDACTED and CAPPED.
        response_error_code     The error envelope's code, NULL on a success.
        response_error_message  The envelope's message.
        response_bytes          Size of the body actually sent.

    "response_error_code IS NULL" is the success predicate; status carries the
    HTTP code for finer filtering.

    THE BODY IS NEVER STORED FOR AN UPLOAD. The test is the REQUEST - files
    present, or a multipart/form-data content type - not the endpoint name, so it
    holds for POST /api/v1/files and for any upload endpoint written later
    without either knowing about the other. It is also null when there was no
    body, which is every GET.

    REDACTION AND CAPS. Values under credential-shaped keys (password, secret,
    token, authorization, api_key, credential, private_key) are replaced with
    [redacted] at any depth. A bare 'key' is deliberately NOT on that list: in
    this API it is the single-use, tenant-scoped attachment key an upload hands
    back, and it is the thing you most need when tracing an attach. Each value is
    capped at 4000 bytes and the whole payload at 25000, both marked
    '...[truncated]' so a truncated value never reads as the value. An
    unparseable JSON body is stored as the text it was - that request 400s, and
    this is where you look to find out why.

    A streamed or file response reports its declared Content-Length as
    response_bytes (0 when it declares none) - the log never buffers a download
    just to measure it.

    PURGING A KEY DESTROYS ITS HISTORY. api_key_id is a foreign key with
    ON DELETE CASCADE, so `rsx:api:key:delete <id> --purge` takes that key's rows
    with it. Revoking does NOT - it sets _api_keys.is_revoked and keeps the row,
    which is the difference between the two operations. Indexes cover the three
    ways the table is read: by key, by ip, and by created_at (date range).

    RETENTION. config('rsx.api.log_retention_days') (default 30) is consumed by
    Api_Cleanup_Service::cleanup_request_log - a #[Task] #[Exclusive]
    #[Schedule('daily at 3am')] that chunk-deletes rows older than the window.
    This is a config value, not an env var (application behavior, not a
    deployment fact).

EXCEPTION HANDLING
    An uncaught Throwable inside an API dispatch is logged as a 500 row, then
    rendered as JSON by Api_Exception_Handler (priority 25, between the Ajax and
    Playwright handlers). It gates on Api_Dispatcher::is_api_dispatch() so it
    ONLY touches API requests (returns null - declines - otherwise), and it
    never emits HTML:

        dev/debug:   {"error": {"code": "internal_error",
                                "message": "<message> (<ExceptionClass>)"}}
        production:  {"error": {"code": "internal_error",
                                "message": "Internal server error"}}

    Do NOT wrap endpoint bodies in blanket try/catch to format errors - let them
    bubble; the handler formats. Catch only genuinely expected failures.

ENVIRONMENT INTERACTIONS AND CAVEATS
    Dev hostname guard. In development mode a web request whose host does not
    match the APP_URL host fatals loudly (Rsx_Env_Hostname_Guard). An external
    API call in dev must therefore use the APP_URL host, or a loopback request
    (localhost / 127.* / ::1), which is exempt.

    CSRF. Not applicable. There is no cookie session to protect, and RSpade's
    VerifyCsrfToken is disabled framework-wide regardless. Bearer auth is the
    entire authentication story.

    FPC (full-page cache). Never applies to an API route - the Api_Dispatcher
    branch exits before any FPC logic, and #[FPC] on an API endpoint throws at
    scan time.

    Main_Abstract::pre_dispatch. Deliberately SKIPPED for API dispatch (the same
    precedent the Portal dispatcher sets). An endpoint's OWN controller
    pre_dispatch(Request, $params) IS honored (a non-null return short-circuits);
    it is the place for per-controller non-auth concerns, never for auth - the
    dispatcher has already authenticated the key AND evaluated the #[Auth]
    gates by the time it runs.

TEMPLATE ENDPOINTS
    The starter template ships three reference API controllers
    (rsx/app/api/v1/) as the working pattern to copy:

        GET  /api/v1/contacts            list (page, per_page, search) -> {items, meta}
        GET  /api/v1/contacts/:id        one record (or 404)
        POST /api/v1/contacts/create     create -> 201
        POST /api/v1/contacts/:id/update present-only update -> 200
        POST /api/v1/contacts/:id/delete soft delete -> 204
        ... and the same five for /api/v1/clients

    Plus the app-owned half of the file story - the three-endpoint attachment
    shape, implemented identically on two record types:

        GET  /api/v1/clients/:id/attachments                     list
        POST /api/v1/clients/:id/attachments/attach              claim a key
        POST /api/v1/clients/:id/attachments/:attachment_id/delete
        ... and the same three for /api/v1/tasks (which also has list + one)

    Clients attach into the SAME category the staff Documents tab reads, so a
    file uploaded over the API shows up in the UI; removing one revokes its
    portal shares before soft-deleting. See FILE ENDPOINTS.

    Notes worth copying: the mutation URLs use explicit action segments
    (/create, /:id/update, /:id/delete) - fitting the GET/POST-only philosophy,
    since there is no PUT/PATCH/DELETE. There is NO manual site_id scoping - the
    models carry a global site scope and the headless identity supplies the site,
    so a cross-site id simply misses the scope and returns 404. Explicit field
    assignment only (never mass assignment). Email/URL fields are validated at
    the endpoint and return validation_error on failure.

    accessors) plus one live-server
    shell script (http/api_auth_and_dispatch.sh) asserting the 401/200/405/404/
    422/400 shapes, that NO response carries Set-Cookie, that a cookie+bearer
    request uses the bearer identity, and that log rows are written. Run:

        php artisan rsx:test --framework            # includes the api concern
        php artisan rsx:test --framework --filter=Api

    Manual curl (over the APP_URL host or loopback; create a key in Settings >
    API Keys first):

        # 200 - list
        curl -H "Authorization: Bearer rsx_live_xxx" \
             https://your.host/api/v1/contacts

        # 401 - no/invalid key (uniform, pre-route)
        curl -i https://your.host/api/v1/contacts

        # 201 - create
        curl -X POST -H "Authorization: Bearer rsx_live_xxx" \
             -H "Content-Type: application/json" \
             -d '{"first_name":"A","last_name":"B","client_id":1,"email":"a@b.co"}' \
             https://your.host/api/v1/contacts/create

        # 422 - undeclared / bad param
        curl -H "Authorization: Bearer rsx_live_xxx" \
             "https://your.host/api/v1/contacts?bogus=1"

RSX VS LARAVEL
    Routing:
        Laravel: declare each route in routes/api.php with a middleware group.
        RSX:     #[Api_Endpoint('/api/vN/...')] on a static method; the manifest
                 discovers it. No route file. /api/vN prefix is enforced.
    Auth:
        Laravel: Sanctum/Passport guard + auth:api middleware; a token model.
        RSX:     framework-owned Bearer auth in the dispatcher; the key resolves
                 to a cookie-less headless Session so ordinary Session:: code and
                 model site-scope work with zero endpoint awareness.
    Validation:
        Laravel: a FormRequest class with rules(), separate from the docs.
        RSX:     #[Api_Param] specs on the method - the SAME declaration drives
                 validation AND the generated docs/tester/samples.
    Serialization:
        Laravel: an API Resource / transformer per model.
        RSX:     the model's redacting toArray() (neverExport + enum labels).
    Docs:
        Laravel: hand-write OpenAPI or bolt on a generator.
        RSX:     /apidocs and /apidocs/openapi.json are generated from the manifest.

TROUBLESHOOTING
    Manifest build fails after adding an endpoint
        Read the RuntimeException - it names the exact rule (bad /api/vN prefix,
        a verb other than GET/POST, a :token with no #[Api_Param], required+
        default, a duplicate name, a conflicting attribute). See SCAN-TIME
        ENFORCEMENT. A cryptic class-not-found from the scan almost always means
        a class CONSTANT in an attribute argument - use a literal (see GOTCHA).

    Every call returns 401 even with a valid key
        The header must be exactly "Authorization: Bearer rsx_...". There is no
        X-API-Key or api_key query param. Confirm the key is not revoked/expired
        (Settings > API Keys).

    A call that used to work now returns 403 insufficient_scope
        The KEY is too narrow, not the user - mint a wider key (or revoke and
        re-mint; keys are immutable after creation). 'required' in the body
        names the route pattern a scope must reach. A plain 403 forbidden is
        the other failure: the user lacks the permission. See KEY SCOPES.

    A scoped key 403s on EVERY endpoint, and the log carries
    "ignoring malformed scope"
        One of its stored scopes does not satisfy the grammar. It grants
        nothing and still counts, so the key is deny-by-default with nothing
        granted - it fails closed. Revoke and re-mint with valid scopes; the
        warning names the text and the rule it broke.

    A file URL (/_file/, /_thumbnail/, /_download_zip/) 403s for a scoped key
        Those routes are clamped against a synthetic path inside the files
        subtree - a key with no scope reaching it is refused there exactly as it
        is on the API. Add /api/v1/files/* to the key.

    The manifest build fails with API-GET-PURE-01
        A GET #[Api_Endpoint] handler's own body contains a write call, and the
        message names which. Move the write to a POST endpoint, or - if the
        write is legitimate bookkeeping - put
        '@API-GET-PURE-01-EXCEPTION <rationale>' in the method docblock. The
        rationale is required; a bare tag still fails.

    A known endpoint returns 404
        Routing is EXACT-MATCH per version - check the vN in the path. A
        cross-site record id also 404s (the global site scope hides it); that is
        correct, not a bug.

    A parameter is "Unknown parameter" (422)
        Undeclared keys are rejected. Add an #[Api_Param] for it, or drop it from
        the request. Precedence is route > GET > body if the same name appears twice.

    The response is 400, not 422
        A 400 invalid_json means the application/json BODY did not parse. A 422
        means a declared param failed validation. They are different failures.

    A model return leaks / omits a field
        Serialization is the model's toArray(): neverExport columns are stripped
        and enum fields appear as status_id__label etc. Adjust the model's
        redaction, not the endpoint.

    Docs page shows nothing / a key does not work in the tester
        /apidocs needs a logged-in staff session (it is not bearer-auth). Paste a
        key into the Api_Key_Bar; create one first at Settings > API Keys. The
        tester fires a native fetch() - a blocked $.ajax error means something
        bypassed it.
