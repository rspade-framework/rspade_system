TWO_FACTOR(1)                    RSpade Manual                    TWO_FACTOR(1)

NAME
    two_factor - second factors and passkey sign-in: TOTP, passkeys, recovery
    codes, passwordless sign-in - for staff and the client portal

SYNOPSIS
    use App\RSpade\Core\TwoFactor\Rsx_Two_Factor;

    # The login function, password stage - nobody is signed in, nothing recorded
    $login_user = RsxAuth::verify_credentials($credentials, record: false);

    if ($login_user === null) {
        Login_History::record_failure($email, Login_History::STATUS_FAILED_PASSWORD);
    }

    if (Rsx_Two_Factor::is_enabled($login_user)) {
        Rsx_Two_Factor::begin_challenge($login_user);   // parks the identity
        return redirect(Rsx::Route('Login_Controller::verify'));
    }

    RsxAuth::login($login_user);                        // no factor: this IS the login
    Login_History::record_success((int) $login_user->id, $email);

    # The application's verification endpoint - the framework does not own it
    $login_user = Rsx_Two_Factor::verify_challenge($params);   // {code} or {assertion}
    return ['redirect' => $destination];

    <%-- The challenge screen, pointed at that endpoint --%>
    <Two_Factor_Challenge $controller="Login_Controller" $method="verify_2fa" />

    # An emailed code: the challenge accepts one, the application delivers it
    Rsx_Two_Factor::begin_challenge($login_user, [Rsx_Two_Factor::ANSWER_ISSUED_CODE]);
    $code = Rsx_Two_Factor::issue_code();      // six digits - send them yourself

    <%-- Enrollment, anywhere a signed-in user can reach --%>
    <Totp_Enrollment />
    <Passkey_Register />

    # PASSWORDLESS: a passkey as the only credential. The app's endpoint again:
    $login_user = Rsx_Two_Factor::verify_passkey_login($params['assertion']);
    return ['redirect' => $destination];

    <Passkey_Sign_In $controller="Login_Controller" $method="passkey_login" />

    # The client portal: the same API over portal users
    use App\RSpade\Core\TwoFactor\Rsx_Portal_Two_Factor;
    Rsx_Portal_Two_Factor::is_enabled($portal_user);
    Rsx_Portal_Two_Factor::verify_passkey_login($params['assertion']);

    # The operator escape hatch
    php artisan rsx:users:2fa:setup  --user=alice@example.com
    php artisan rsx:users:2fa:dump   --user=1
    php artisan rsx:users:2fa:remove --user=1 [--id=7] [--force]
    php artisan rsx:users:2fa:unlock --user=1        # lift an attempt-cap lock

DESCRIPTION
    A second factor proves that the person holding the browser also holds
    something else - a phone running an authenticator app, or an authenticator
    device holding a private key. RSpade owns the whole mechanism: the storage,
    the algorithms, the enrollment ceremonies, the login challenge and its
    brute-force protection. An application supplies one endpoint and one
    screen, because only it knows where a signed-in user should land.

    THREE FACTOR KINDS, one table, one facade:

        TOTP           RFC 6238 six-digit codes from an authenticator app.
        PASSKEY        WebAuthn - a signature from an authenticator, bound to
                       this origin, that no proxy can relay.
        RECOVERY_CODE  Ten single-use codes, minted automatically alongside
                       the first real factor. Never enrolled on its own.

    A PASSKEY IS ALSO A FIRST FACTOR. Beyond answering a second-factor
    challenge, a passkey can sign an identity in ON ITS OWN - no password, no
    email typed - through begin_passkey_login() / verify_passkey_login(). See
    PASSWORDLESS SIGN-IN.

    TWO REALMS, ONE ENGINE. The subsystem is written once
    (Rsx_Two_Factor_Abstract) and bound to each authentication realm by a
    facade with the identical API:

        Rsx_Two_Factor         staff - credentials of a LOGIN IDENTITY
                               (login_users), in _two_factor_credentials
        Rsx_Portal_Two_Factor  client portal - credentials of a PORTAL USER
                               (portal_users), in _portal_two_factor_credentials

    Those two facades are the ONLY classes application code touches. Totp,
    Passkeys, Recovery_Codes and the credential models are implementation
    behind them, and that boundary is what lets the storage shape, the
    WebAuthn library and the encryption of a seed move without a call site
    moving. See THE CLIENT PORTAL REALM for what differs.

    STAFF CREDENTIALS BELONG TO A LOGIN IDENTITY, NOT A SITE USER. They hang
    off login_users, exactly like the password does - a second factor proves
    who is holding the browser, and a users row is an authorization scope
    inside one tenant. Enrolling a phone once per tenant would be wrong.

    THERE IS NO GLOBAL ENABLE SWITCH, deliberately. 2FA is per identity: an
    identity either holds a confirmed factor or it does not, and
    is_enabled($identity) is the whole question. A framework-wide "2FA on"
    flag would have to decide what happens to every account that has not
    enrolled yet, which is a policy only an application can hold. THE
    FRAMEWORK READS NO SUCH COLUMN, and ships no screen that makes a
    signed-in user enroll: requiring a factor is the application's own
    policy and its own screen (see IMPLEMENTING 2FA IN AN APPLICATION).

    Laravel differences: there is no package to install, no service provider,
    no middleware and no fortify-style scaffolding. The tables ship in the
    framework migrations, the endpoints ship force-included in every bundle,
    and the enrollment ceremonies ship as jqhtml components you drop into a
    page.

PICKING METHODS - PREFER PASSKEYS, AND CONSIDER REMOVING TOTP
    The template application ships BOTH modes as a worked example, so that a
    new project can see either one wired end to end. That is a teaching
    decision, not a recommendation.

    IT IS HIGHLY ENCOURAGED TO REMOVE THE TOTP METHOD AND OFFER PASSKEYS ONLY.
    A passkey is phishing-resistant: the authenticator signs a challenge and
    binds the signature to the ORIGIN it was asked from, so a proxy site
    serving a lookalike domain cannot obtain anything it can replay. A TOTP
    code has no such binding - it is a six-digit string the user reads off a
    screen and types wherever they were asked to, which means a phishing page
    can collect it and spend it inside its own validity window. Every other
    property (the encrypted seed, the replay refusal, the throttle) narrows
    that window; none of them closes it.

    KEEP TOTP ONLY WHEN YOUR USER BASE CANNOT USE PLATFORM AUTHENTICATORS -
    shared or locked-down desktops, browsers without WebAuthn, a device
    policy that forbids platform credentials. If that is not your population,
    drop the authenticator-app option from your enrollment screen and offer
    <Passkey_Register /> alone. Nothing in the framework requires both.

HOW IT WORKS
    STORAGE - _two_factor_credentials (staff), _portal_two_factor_credentials
        One row per credential, one table per realm for all three kinds,
        discriminated by the same type_id vocabulary. Owned by login_user_id
        (staff) or portal_user_id (portal), ON DELETE CASCADE - the realm
        boundary IS the table boundary, because a foreign key names one table.
        Three columns mean three things, identically in both tables:

            secret          TOTP: the RFC 6238 seed, ENCRYPTED at rest
                            (Crypt::encryptString).
                            RECOVERY_CODE: the bcrypt hash of one code.
                            PASSKEY: stored public key material - not secret.
            counter         TOTP: the last ACCEPTED timestep (anti-replay).
                            PASSKEY: the authenticator's signature counter
                            (anti-clone).
            credential_key  PASSKEY only: the raw credential id, base64url,
                            globally UNIQUE. Named _key and not _id because
                            SCHEMA-TYPE-01 reserves an _id suffix for
                            integers.

        confirmed_at IS NULL until the enrollment was PROVEN - a live code
        typed, an attestation verified. An unconfirmed row can never satisfy
        a challenge; every read that gates a login filters on it.

        There is no fetch() on the model and there never should be. The
        browser is given metadata only, assembled by list_credentials().

    WHY A SEED IS ENCRYPTED AND A CODE IS HASHED
        A password is verified by hashing the guess, so it never has to be
        recoverable. A TOTP seed is recoverable BY DESIGN - the server has to
        regenerate the same codes the phone does - so there is no one-way
        form of it that still works, and encryption is the strongest
        available posture: a leaked database dump alone does not yield live
        codes. A recovery code IS a password: bcrypt, and the plaintext
        exists exactly once, in the response that shows it.

    TOTP: FIXED PARAMETERS, DRIFT, REPLAY
        SHA1, 6 digits, a 30-second step - the interoperable set, and NOT
        configurable. Authenticator apps read those three from the otpauth://
        URI and several popular ones quietly ignore anything else, so a
        "stronger" choice produces a user whose codes never match. (SHA1
        inside an HMAC is not the broken SHA1; HMAC does not rest on
        collision resistance.)

        DRIFT: one timestep either side of the present one is accepted
        (Totp::DRIFT_STEPS), the value RFC 6238 section 5.2 recommends.
        Widening it multiplies the number of codes live at any instant, which
        is exactly the number an online guesser is up against.

        REPLAY: Totp::verify() returns the accepted TIMESTEP (or false), and
        the caller persists it in counter. A timestep at or below the last
        accepted one is refused outright, so a code that was seen once - over
        a user's shoulder, in a phishing proxy - cannot be spent again inside
        its own window. The confirmation code the user types during
        enrollment is persisted the same way, so it cannot immediately be
        replayed against the login challenge.

    PASSKEYS: RP ID, ATTESTATION, THE COUNTER
        Wrapped around lbuchs/webauthn. The relying party id is the BARE
        HOSTNAME from Rsx::get_hostname() - no scheme, no port, per spec - so
        a passkey enrolled on one host does not work on another. That is
        correct, and worth knowing before somebody reports it as a bug after
        moving environments.

        Attestation is 'none', deliberately: this is a public application,
        not an enterprise issuing hardware, so demanding attestation would
        buy nothing while showing a browser privacy warning and excluding the
        platform authenticators (Windows Hello, iCloud Keychain) most people
        actually have.

        The ceremony CHALLENGE lives in a session value, never in the payload
        - a challenge the client hands back is whatever the client chose. One
        key per realm serves registration and the second-factor assertion (a
        browser is doing one or the other, never both); the PASSWORDLESS
        ceremony parks under its own key, because a login page can offer a
        passkey sign-in while a second-factor ceremony is in flight in the
        same browser. The realms' keys differ too: both realms' values can sit
        on the one session row a browser has.

        THE LOOKUP IS REALM-SCOPED. An assertion is resolved by credential_key
        in the REALM'S OWN TABLE. Staff and portal usually share one relying
        party (one host), so a browser will offer a staff passkey on the
        portal sign-in page - and it is simply unknown there. A portal
        credential can never satisfy a staff challenge, or the reverse.

        THE USER HANDLE IS REALM-PREFIXED FOR THE PORTAL. An authenticator
        files a resident credential under (rpId, user handle) and REPLACES an
        existing one with the same pair, so a staff identity and a portal user
        sharing a numeric id on one host would overwrite each other's passkey.
        Staff handles are the bare login_users id; portal handles are
        'portal-<id>'.

        ANTI-CLONE: an authenticator increments a signature counter on every
        assertion, and one that does not advance means two copies of a key
        that was supposed to be unclonable - refused. Authenticators that
        never implement a counter report zero forever, which the library
        treats as "no counter" rather than as a clone.

        Binary crosses the wire base64url in both directions; Rsx_Two_Factor
        .js converts to and from ArrayBuffers. The fields that are binary:
        create - publicKey.challenge, publicKey.user.id,
        publicKey.excludeCredentials[].id; get - publicKey.challenge,
        publicKey.allowCredentials[].id.

    PASSKEYS: THE CEREMONY TIMEOUT AND THE CHALLENGE WINDOW
        Every ceremony - registration, the second-factor assertion and
        passwordless sign-in, in both realms - is sent publicKey.timeout =
        300000 (Passkeys::CEREMONY_TIMEOUT_SECONDS = 300). It is a browser UI
        HINT - how long the browser keeps its passkey prompt open - and bounds
        no work of ours. The framework must set it: left out, the WebAuthn
        library writes its own 20-second default, and 20 seconds cannot hold
        the CROSS-DEVICE (hybrid / QR) flow - notice the QR code, unlock the
        phone, open its credential provider, scan, Bluetooth tunnel,
        biometric, relay back - which routinely takes 30 to 60 seconds and
        more; the browser abandons first. 300 seconds is the WebAuthn
        specification's recommended default for a ceremony whose
        userVerification is 'required' or 'preferred' (all three are). A
        local authenticator answers in seconds and the prompt closes then.
        The browser may CLAMP the value; it is advice, never a guarantee.

        The server keeps a WebAuthn challenge redeemable for the ceremony
        timeout plus a 60-second round-trip margin
        (Passkeys::challenge_window_seconds() = 360) - DERIVED, not
        configured, so the window can never be shorter than the prompt the
        browser was told to hold open. It is a SECURITY WINDOW like the one
        below: it bounds how long an unanswered challenge stays satisfiable,
        and a confirmation after it answers "That security key request has
        expired. Please try again."

    PASSKEY ENROLLMENT OUTCOMES - WHAT SUPPORT CAN READ
        A browser that gives up on a ceremony tells the server nothing, so
        every staff enrollment writes _login_history rows
        (Login_History::record_passkey_enrollment()), shown on the /_sys
        panel's per-identity Sign-ins tab:

            passkey_enroll_begun      options issued (begin)
            passkey_enrolled          credential stored (confirm)
            passkey_enroll_failed     the confirmation reached the server and
                                      did not verify; failure_reason says why
            passkey_enroll_abandoned  begun and NEVER CONFIRMED: superseded by
                                      a new begin in the same browser, found
                                      expired by the next begin or by the
                                      hourly Session_Values_Cleanup_Service
                                      sweep, or confirmed after the window

        A begin parks a marker session value (PASSKEY_ENROLLMENT_KEY) beside
        the challenge, with the same expiry; whichever of the confirmation,
        the next begin or the sweep claims it records the one outcome, against
        the IP and browser that began the ceremony. An abandoned row's
        failure_reason carries when the ceremony began. A session deleted
        outright takes its marker with it, and that ceremony records no
        outcome beyond its begun row. Nothing here feeds the login throttle -
        an enrollment is not a sign-in attempt. The PORTAL has no login
        history and logs the same outcomes instead:
        Log::info('Portal passkey enrollment', {portal_user_id, email,
        status, reason, ip_address, user_agent}).

        READING "MY PASSKEY WOULD NOT SAVE". A begun row followed by an
        abandoned one, with no failed row, means no confirmation ever reached
        the server: the browser, or the phone's credential provider, declined
        or gave up - the server refused nothing. That is the usual shape of a
        generic browser error shown right after scanning the QR code
        ("Something went wrong"). Not every authenticator app is a general
        passkey provider for arbitrary sites; some hold credentials only for
        their own vendor's accounts, so the user may need a different
        provider on the phone (the platform's own password manager, or one
        that offers passkeys to any site). A failed row, by contrast, is the
        server refusing a response it did receive - read its failure_reason.

    RECOVERY CODES
        Ten codes per set (Recovery_Codes::COUNT), minted automatically the
        first time an identity confirms a real factor, and again by
        regenerate_recovery_codes(). Two hyphenated groups of four from a
        32-symbol alphabet that OMITS 0/O/1/I - these are typed by somebody
        who has just lost their phone.

        CONSUME-ONCE BY DELETION: a spent code's ROW is deleted rather than
        marked, so nothing can match it again and remaining() is a plain
        COUNT. Removing the LAST real factor deletes the recovery codes with
        it - with no factor left they are not a recovery path, they are ten
        bearer tokens that log somebody in with no second step at all.

    THE CHALLENGE STATE MACHINE
        begin_challenge($identity)
            Writes {identity_id, email} to the realm's CHALLENGE_KEY session
            value with an expiry, and then SIGNS THE REALM OUT. The order is load-bearing: put_value() is a writer,
            so it establishes the session row the value hangs off; the logout
            clears the row's IDENTITY but not the row, and _session_values
            hang off it by FK, so the parked value survives.

        WHY IT LOGS OUT. Between a correct password and a correct second
        factor the browser holds a HALF-authenticated state, and the only
        safe representation of half-authenticated is NOT authenticated. A
        session that stayed logged in carrying a "needs 2FA" flag would make
        every route, endpoint and background refresh a place that flag can be
        forgotten - and forgetting it means the second factor was optional.
        Logging out leaves nothing to forget: the pending state is inert data
        only verify_challenge() knows how to redeem.

        challenge_pending()
            {email, email_masked, has_totp, has_passkey, has_recovery_codes},
            or null. An EXPIRED challenge reads as null - get_value() filters
            on the expiry, so "expired" and "never existed" are the same
            answer, which is the only answer a challenge screen needs. The
            address is MASKED (email null) unless the application sets
            rsx.two_factor.challenge_shows_full_email: the page is reachable
            by anyone holding the session cookie. has_recovery_codes = an
            unspent recovery code exists, so the screen may ask for one.

        verify_challenge($input)
            The order of this method is its contract - see THE FACADE.

        abandon_challenge()
            Forget the pending value. Cancel, or done. The challenge_abandon
            endpoint calls it for <Two_Factor_Challenge>'s Cancel.

        A SESSION IS NEVER AUTHENTICATED UNTIL THE SECOND FACTOR PASSES.
        That is the invariant the whole design exists to hold.

    THE SECURITY WINDOW (NOT A TIMEOUT)
        rsx.two_factor.challenge_window_minutes (15) bounds how long a
        passed-password state stays redeemable, and the same window bounds a
        parked TOTP enrollment seed (a WebAuthn ceremony's challenge has its
        own derived window - see PASSKEYS: THE CEREMONY TIMEOUT). It
        bounds no work, cancels nothing, and expiry degrades to a working
        outcome the user can act on ("Your verification window has expired.
        Please sign in again."). What is parked during it is a password that
        has already been proven correct, waiting on a screen that may be
        unattended: long enough to fetch the phone from another room, not
        long enough to leave a proven password redeemable all afternoon.

    THROTTLE INTEGRATION, AND THE ONE-RECORDER RULE
        An unthrottled second factor is a guessing oracle - a million
        six-digit codes with three live at any moment. So:

            1. Login_Throttle::require_not_throttled() is the FIRST statement
               of verify_challenge(). It THROWS Auth_Throttled_Exception
               rather than returning false, and the throw is let through
               untouched: "we did not check" is a different answer from "that
               was wrong", and a login function must be able to say so.
            2. A failed answer is recorded as
               Login_History::record_failure($email, STATUS_FAILED_2FA, null,
               $login_user_id) - and record_failure() ALREADY feeds the
               throttle.
            3. Login_Throttle::record_failure() is therefore NEVER called
               here. Calling both counts one failure twice and halves the
               real budget, and the halving is only ever discovered by a user
               locked out early.

    ATTEMPT CAPS (COUNTS, NOT TIMEOUTS)
        The per-IP throttle alone is not enough: an attacker who holds the
        password rotates addresses. Every wrong answer to a challenge - a TOTP
        code, a recovery code, a passkey assertion - also counts against two
        caps that are independent of IP:

            PER CHALLENGE  rsx.two_factor.challenge_max_failures (5). The
                           answer that reaches it DESTROYS the parked
                           challenge ('Too many incorrect codes. Please sign
                           in again.'); the user re-enters the password,
                           which spends the per-IP budget again. Each
                           begin_challenge() starts its own count at zero.
            PER IDENTITY   rsx.two_factor.identity_max_failures (10) inside
                           identity_failure_window_minutes (60), across every
                           challenge and every address. Once reached, the
                           identity is LOCKED: verify_challenge() refuses it -
                           a correct code included, so the lock is not an
                           oracle - and discards the challenge ('Too many
                           incorrect codes have been entered for this account.
                           Please try again later.'), until the window closes
                           or an operator runs rsx:users:2fa:unlock.

        A correct answer before the cap clears the identity's count. The
        identity window is a SECURITY WINDOW, not a timeout: it bounds the
        guessing RATE (ten guesses an hour), nothing waits on it, and nothing
        fails when it closes. Both counters live in the transient-counter
        store (Rsx_Counter), keyed per realm, so a staff identity and a portal
        user with the same id never share one. Passwordless sign-in
        (verify_passkey_login()) is outside the caps - it has no pending
        identity to count against and is throttled per IP.

        A RECORDED SUCCESS MEANS FULL AUTHENTICATION, AND A SESSION IS SIGNED
        IN ONLY AFTER THE FACTOR. That is why the password stage is
        RsxAuth::verify_credentials($credentials, record: false) - which
        checks the pair, records nothing and signs nobody in - and why
        verify_challenge(), not the password stage, calls RsxAuth::login()
        and Login_History::record_success(). Nothing in _login_history is
        ever a half-authenticated event, and no session is ever authenticated
        before its factor is passed: a request that dies between the password
        and the challenge leaves the visitor signed out.

    ENROLLMENT REFUSES WHILE IMPERSONATING
        Every enrollment path throws when Session::is_impersonating(), and
        the removal endpoint refuses the same way. An administrator viewing
        an account must not be able to attach - or strip - a second factor on
        it: that is an authentication backdoor wearing a support tool's
        clothes, and the account's owner would have no way to see it happen.
        The CLI is the sanctioned exception (see CLI COMMANDS).

THE FACADE
    App\RSpade\Core\TwoFactor\Rsx_Two_Factor          (staff)
    App\RSpade\Core\TwoFactor\Rsx_Portal_Two_Factor   (client portal)

    Both expose exactly this API. Every $identity parameter takes an int id or
    the realm's identity model - a Login_User_Model for Rsx_Two_Factor, a
    Portal_User_Model for Rsx_Portal_Two_Factor - and a model of the OTHER
    realm THROWS (read as an id it would name a different person). Every
    method that returns an identity returns the realm's model.

    READING
        is_enabled($identity): bool
            True when at least one CONFIRMED TOTP or passkey credential
            exists. Recovery codes are EXCLUDED: they are the way back in
            when a factor is lost, and an identity holding only recovery
            codes has no factor to be challenged for. This is the question a
            PASSWORD or FEDERATED sign-in asks; a passwordless sign-in does
            not ask it.

        has_passkey($identity): bool
            Holds a confirmed passkey. Not is_enabled(): an identity with only
            an authenticator app has a second factor and no passkey.

        list_credentials($identity): array
            One row per factor, newest confirmation last:
            {id, type_id, type_id__label, label, confirmed_at, last_used_at}.
            METADATA ONLY, by contract - never a secret, a hash or a public
            key. Its output reaches a browser, and no column on that table
            has any business there.

        recovery_codes_remaining($identity): int
        has_confirmed_totp($identity): bool
        issuer(): string
            config('rsx.two_factor.issuer'), or the hostname when null. A
            colon is stripped - the Key URI Format uses one to separate
            issuer from account.
        challenge_expires_at(): string
            The ISO instant the security window closes. Useful when an app
            parks its own value alongside the challenge (the template parks
            an invite code this way) so it cannot outlive the sign-in.

    ENROLLMENT (the SIGNED-IN identity only; throws while impersonating)
        begin_totp_enrollment(): array
            {secret, otpauth_uri, qr_svg}. The seed is parked in a session
            value, not written to a row - an abandoned enrollment leaves
            nothing behind.
        confirm_totp_enrollment(string $code): array
            Proves a live code, writes the confirmed row, returns the
            plaintext recovery codes (the only time they exist). A wrong code
            throws Two_Factor_Failed_Exception and the parked seed SURVIVES,
            so the retry is the same enrollment.
        begin_passkey_registration(): array
            The navigator.credentials.create() arguments. Records
            passkey_enroll_begun (and passkey_enroll_abandoned for an earlier
            unconfirmed enrollment in this browser) - see PASSKEY ENROLLMENT
            OUTCOMES.
        confirm_passkey_registration(array $attestation, ?string $label): ?array
            Freshly minted recovery codes, or NULL when the identity already
            had a sheet - a user adding a second passkey must not have the
            codes they wrote down silently invalidated. Records
            passkey_enrolled, or passkey_enroll_failed / _abandoned before
            the exception propagates unchanged.
        record_expired_passkey_enrollments(): int
            Framework-internal: the hourly session-values sweep calls it to
            record expired, never-confirmed enrollments as abandoned.
        regenerate_recovery_codes(): array
            Replaces the set. The previous sheet stops working immediately.

    REMOVAL
        remove_credential($identity, int $credential_id): void
            Removes one factor, and the recovery codes with it if it was the
            last. Naming a row that is not this identity's is a NO-OP, not an
            error: a stale settings screen is a race, not an attack.
        remove_all($identity): void
            The administrative unlock, and what an account deletion runs.

    THE CHALLENGE
        begin_challenge($identity, ?array $accepts = null): void
            Parks the identity and SIGNS THE REALM OUT. $accepts names the
            kinds of answer THIS challenge takes - ANSWER_ISSUED_CODE,
            ANSWER_TOTP, ANSWER_PASSKEY, ANSWER_RECOVERY_CODE - and
            verify_challenge() refuses every other kind, a correct one
            included. Null accepts what the identity holds. An explicit list
            is validated BEFORE the sign-out: an unknown kind, an empty list,
            or a list the identity cannot answer (no ANSWER_ISSUED_CODE and
            none of the factors it names) throws InvalidArgumentException.
            Which sign-ins owe a challenge, and which answers satisfy it, is
            the application's policy; the list is how that policy reaches the
            one place it is enforced (ISSUED CODES).
        challenge_pending(): ?array
            {email, email_masked, accepts, has_totp, has_passkey,
            has_recovery_codes, has_issued_code, codes_issued}, or null. accepts
            is what the challenge takes AND the identity can give; the has_*
            flags are the same answer per kind - what the screen may ask for.
            codes_issued counts issue_code() calls.
        issue_code(): string
            Six random digits for the pending challenge, for the APPLICATION
            to deliver. Only a keyed hash is kept; a later code replaces an
            earlier one. Throws Two_Factor_Failed_Exception when nothing is
            pending, RuntimeException when the challenge does not accept
            ANSWER_ISSUED_CODE. See ISSUED CODES.
        pending_identity(): ?identity
            Whom the pending challenge is for - the address a code is sent
            to. SERVER-SIDE ONLY; the browser reads challenge_pending(),
            which masks it.
        challenge_passkey_options(): array
            Refused (Two_Factor_Failed_Exception) when the login function's
            explicit $accepts leaves passkeys out.
        verify_challenge(array $input): identity
            $input is {code: '123456'} or {assertion: {...}}. On success the
            caller is SIGNED IN, last_login is stamped and the success is
            recorded; the method returns the identity. Order:

                1. require_not_throttled()   - throws Auth_Throttled_Exception
                2. the pending identity, or the window has closed
                2b. a LOCKED identity (is_locked()) is refused and its
                   challenge discarded, before anything is tried
                3. only the kinds the challenge ACCEPTS: a passkey assertion
                   when one was offered; otherwise the typed string against
                   the issued code, then every confirmed TOTP credential,
                   and THEN the recovery codes - recovery LAST, so a string
                   that is a live TOTP code never burns a recovery code. An
                   answer of a kind not accepted is a wrong answer
                4. on failure: record the failure ONCE through the realm
                   (staff: Login_History STATUS_FAILED_2FA; portal: the
                   throttle directly), count it once against the challenge
                   and once against the identity, and throw
                   Two_Factor_Failed_Exception('That code is not valid.') -
                   or, when the challenge's cap is reached, destroy the
                   challenge and throw 'Too many incorrect codes. Please sign
                   in again.'
                5. on success: forget the pending value, clear the identity's
                   failure count, sign in through the
                   realm (staff: RsxAuth::login(); portal:
                   Portal_Session::set_portal_user_id()), record the success
                6. an identity the realm will not admit (staff: no enabled
                   site membership; portal: can_login() false, or a portal
                   user of another site) is recorded STATUS_FAILED_DISABLED
                   and fails with the wrong-code message

            A passkey assertion is additionally checked to BELONG to the
            pending identity. Proving the signature came from a credential
            this server issued is not proving whose credential it is;
            without that comparison anyone holding any valid passkey could
            complete anybody else's challenge.
        abandon_challenge(): void

    THE ATTEMPT CAPS
        is_locked(int|identity $identity): bool
            True once the identity has spent identity_max_failures inside the
            window.
        clear_failures(int|identity $identity): void
            Zero the identity's failure count, lifting a lock. What a correct
            answer does on its own, and the operator's release
            (rsx:users:2fa:unlock). Touches no factor.
        challenge_max_failures(): int
        identity_max_failures(): int
        identity_failure_window_seconds(): int
            The configured values; each throws below 1.

    PASSWORDLESS SIGN-IN (anonymous caller; no password, nothing pending)
        begin_passkey_login(): array
            The navigator.credentials.get() arguments for a DISCOVERABLE
            credential: no allowCredentials list (no identity is named), and
            userVerification 'required'. The challenge parks under the realm's
            own passwordless key.
        verify_passkey_login(array $assertion): identity
            Verifies the assertion and SIGNS IN the identity that answered.
            Order, and the same guarantees verify_challenge() gives:

                1. require_not_throttled()   - throws Auth_Throttled_Exception
                2. the assertion verified in the REALM's table, with the UV
                   (user verified) flag REQUIRED; the identity comes from the
                   credential row, never from the client
                3. on failure: recorded ONCE (STATUS_FAILED_PASSKEY) and one
                   sentence whatever went wrong - 'That passkey could not
                   sign you in.' - so nothing says whether a key exists
                4. any pending password-stage challenge is forgotten
                5. the realm signs the identity in, refusing one it will not
                   admit (recorded STATUS_FAILED_DISABLED, same sentence)
                6. the success is recorded

            NO SECOND FACTOR FOLLOWS - see PASSWORDLESS SIGN-IN.

    THE OPERATOR PATH (a shell, not a request - never call from a request)
        cli_setup_totp($identity, ?string $label): array
            {secret, otpauth_uri, recovery_codes}. Writes the row CONFIRMED
            immediately: there is no browser to type a live code into, and
            the operator is already a higher privilege than any identity in
            the application. Refuses when a confirmed TOTP credential exists.
            The recovery set REPLACES whatever the identity held.
        cli_dump_credentials($identity): array
            Every factor WITH the TOTP seeds decrypted, unconfirmed rows
            included. The deliberate opposite of list_credentials(): this
            output reaches a terminal that already holds shell access and the
            encryption key.

    EXCEPTIONS
        Two_Factor_Failed_Exception carries a USER-SAFE message by contract -
        render it as-is. Auth_Throttled_Exception comes from the throttle and
        its message matters most of all. A RuntimeException from the facade
        (nobody signed in, impersonating) is a WIRING MISTAKE and must
        surface loudly.

FRAMEWORK ENDPOINTS AND COMPONENTS
    Rsx_Two_Factor_Controller is the browser's whole view of the subsystem in
    the STAFF realm, and Rsx_Portal_Two_Factor_Controller (#[Auth_Realm
    ('portal')], served on the portal's own Ajax channel) is its portal twin
    - the same endpoints under the same names, over Rsx_Portal_Two_Factor.
    Every method is a thin wrapper over the facade. Both JS stubs are
    FORCE-INCLUDED IN EVERY BUNDLE (like Realtime_Controller), because the
    screens that drive them live in different bundles: the challenge and the
    passkey sign-in are on a login page, enrollment is in a settings SPA, and
    a passkey prompt may be raised from anywhere.

        #[Auth('is_logged_in')]     - the enrollment population
            totp_begin, totp_confirm {code}
            passkey_register_begin, passkey_register_confirm
                                     {attestation, label}
            credentials_list        -> {credentials, recovery_codes_remaining,
                                        is_enabled} - ONE call, so a settings
                                        screen never paints three states that
                                        disagree while they land
            credential_remove {id}  -> the refreshed state; refuses while
                                        impersonating
            recovery_regenerate     -> {recovery_codes}

        #[Auth('public')]           - the half-authenticated population
            challenge_state         -> challenge_pending(): {email,
                                        email_masked, accepts, has_*,
                                        codes_issued} or NULL, which is not
                                        an error
            challenge_abandon       -> null; forgets this session's pending
                                        challenge (Cancel)
            challenge_passkey_options
            passkey_login_options   -> the passwordless get() arguments;
                                        names no identity at all

        The public pair is public in the GATE sense only: between the
        password and the second factor the session is deliberately not logged
        in, so a gate demanding a login could never be satisfied by the very
        screen that exists to produce one. Each answers exclusively from the
        challenge parked on the CALLER'S OWN session, and a caller with
        nothing pending learns nothing.

    WHY VERIFICATION IS NOT HERE. verify_challenge() and
    verify_passkey_login() sign the user in, and where they land afterwards
    is application logic - a captured redirect, a site picker, an
    interstitial the app requires. A framework endpoint would have to guess
    the answer to a question only the app can answer. So the APPLICATION
    owns both verification endpoints, and <Two_Factor_Challenge> and
    <Passkey_Sign_In> are pointed at them.

    THE COMPONENTS PICK THEIR REALM FROM THE PAGE. Rsx_Two_Factor.controller()
    answers Rsx_Portal_Two_Factor_Controller on a portal page
    (Rsx_Portal.is_portal()) and Rsx_Two_Factor_Controller otherwise, and
    every shipped component goes through it - so none of them takes a realm
    argument, and a portal page can never start a staff ceremony.

    <Totp_Enrollment />
        The whole authenticator ceremony: QR code, manual-entry secret, the
        6-digit proof, and the ONE-TIME recovery-code reveal.
        Args:   none - it always enrolls the signed-in identity.
        Events: enrolled - the user acknowledged the code sheet (the factor
                is already live at that point).

    <Passkey_Register />
        An optional key name, the button that raises the browser prompt, and
        the code-sheet reveal when this registration minted one.
        Args:   none.
        Events: registered - fired immediately when no codes came back, or
                when the user acknowledges the sheet that did.
        A browser without WebAuthn gets a plain notice instead of a button
        that cannot work; the host page is expected to still offer TOTP.

    <Two_Factor_Challenge $controller $method [$cancel_url] [$placeholder]
                          [$send_controller $send_method] />
        The login challenge screen.
        Args:   $controller, $method (both REQUIRED) - the application's
                verification endpoint, named the way <Rsx_Form> names one.
                $cancel_url - adds Cancel: challenge_abandon, then navigate
                here (normally the login page). Cancel and Verify then sit
                in a row of their own beneath the box, centred, Cancel
                first. Absent: no Cancel, Verify beside the box.
                $placeholder - replaces the derived placeholder (below).
                $send_controller, $send_method - the application endpoint that
                issues and delivers a code (ISSUED CODES). With them, and a
                challenge accepting an issued code, the screen offers "Send a
                new code" and sends the FIRST code itself when none has been
                issued. Absent: no send link; the host issues the code.
        Posts:  {code: '...'} from the typed answer, or {assertion: {...}}
                from a passkey. To the send endpoint: {}.
        Expects: {redirect: '/somewhere'}, followed with window.location.
                 A response with no redirect throws. The send endpoint may
                 answer anything, or reject with a user-safe message.
        Events: no_challenge - nothing is pending (expired window, direct
                visit). The host page sends the visitor back to /login.

        ONE INPUT FOR EVERY TYPED ANSWER: an issued code, an authenticator
        code and a recovery code go in the same box, because the server
        tries each accepted kind and the user should not have to know which
        kind of string they hold. The box asks only for what the challenge
        accepts and the identity can answer with:

            has_issued_code + has_recovery_codes   "6-digit or recovery code"
            has_issued_code                        "6-digit code"
            has_totp + has_recovery_codes   "Authenticator or recovery code"
            has_totp only                   "6-digit code"
            has_recovery_codes only         "Recovery code"
            none of them (a passkey only)   no box, no Verify - the passkey
                                            button is the answer (a browser
                                            without WebAuthn gets a notice)

        The address shown is email_masked, or email when the application
        set rsx.two_factor.challenge_shows_full_email.

        Every rejection - a wrong code, an expired window, and the THROTTLE
        REFUSAL - is rendered inline as the server's own message. A component
        that only rendered messages it recognised would swallow the most
        important one.

    <Passkey_Sign_In $controller $method [$label] />
        "Sign in with a passkey" for a login page: runs the PASSWORDLESS
        ceremony and posts it to the application's endpoint.
        Args:   $controller, $method (both REQUIRED) - the endpoint;
                $label - the button text (default 'Sign in with a passkey').
        Posts:  {assertion: {id, clientDataJSON, authenticatorData,
                signature}} - the endpoint calls verify_passkey_login() on
                the realm's facade with $params['assertion'].
        Expects: {redirect: '/somewhere'}, followed with window.location.
        Events: signed_in - fired just before the navigation.
        RENDERS NOTHING in a browser without WebAuthn: a login page already
        offers a password, and a button that cannot work is worse than none.
        The root then carries Passkey_Sign_In--unsupported (display: none).
        The "or" divider around it is the page's - wrap both in one block and
        hide the block when nothing in it is visible (PASSWORDLESS SIGN-IN).

        All four components are LAYOUT-NEUTRAL by contract: no card, no
        border, no heading, no width. The host page owns the box.

    Rsx_Two_Factor (JavaScript)
        is_supported(): boolean          - navigator.credentials is present
        controller()                     - the page realm's controller class
        register_passkey(label)          - the create ceremony
        authenticate_passkey()           - the second-factor get ceremony;
                                           RETURNS the assertion rather than
                                           posting it
        sign_in_with_passkey()           - the passwordless get ceremony;
                                           RETURNS the assertion
        A dismissed browser prompt raises NotAllowedError, which is caught
        and answered as NULL. A person changing their mind is not an error
        and must not be reported as one.

IMPLEMENTING 2FA IN AN APPLICATION
    Worked example, complete and release-current:
    system/app/RSpade/resource/reference_app/app/login/login_controller.php
    (the challenge screen is login_verify.blade.php and the settings
    enrollment screen is app/frontend/settings/password_security/).

    1. REWORK THE LOGIN FUNCTION INTO TWO STAGES
        Check the password WITHOUT signing anybody in, then branch on
        is_enabled():

            Rsx_Turnstile::validate($request);   // if you use it - first

            $login_user = null;

            try {
                $login_user = RsxAuth::verify_credentials($credentials, record: false);

                if ($login_user === null) {
                    Login_History::record_failure(
                        $email, Login_History::STATUS_FAILED_PASSWORD
                    );
                }
            } catch (Auth_Throttled_Exception $e) {
                $error = $e->getMessage();   // never "wrong password"
            }

            if ($login_user !== null) {
                // Your own account-state questions go HERE. Nobody is signed
                // in, so a refusal is just an error on the form.

                if (Rsx_Two_Factor::is_enabled($login_user)) {
                    Rsx_Two_Factor::begin_challenge($login_user);
                    return redirect(Rsx::Route('Login_Controller::verify'));
                }

                RsxAuth::login($login_user);
                Login_History::record_success((int) $login_user->id, $email);
                return redirect($this->post_login_destination(...));
            }

        verify_credentials() answers the IDENTITY and touches no session;
        RsxAuth::login() and a passed challenge are the only things that sign
        anybody in. So the order above is the security property: everything
        between the password and the sign-in runs for a visitor who is still
        signed out, and there is nothing to undo on a refusal - no logout()
        to remember.

        With record: false, verify_credentials() writes NOTHING - so the
        password failure above is recorded by YOU, and it is what feeds the
        throttle.

        ANYTHING THE CHALLENGE HAS TO CARRY ACROSS RIDES THE SESSION.
        <Two_Factor_Challenge> posts exactly {code} or {assertion}: there is
        no query string and no place to thread a form field. Park it with
        Session::put_value(..., Rsx_Two_Factor::challenge_expires_at()) BEFORE
        begin_challenge() (put_value() establishes the session row the value
        and the pending identity both hang off) and consume it
        once in the verification endpoint. The template does this with the
        invite code the login form carried.

    2. THE CHALLENGE SCREEN AND ITS ENDPOINT
        A public route that redirects away when nothing is pending:

            #[Route('/login/verify', methods: ['GET'])]
            public static function verify(Request $request, array $params = [])
            {
                if (Rsx_Two_Factor::challenge_pending() === null) {
                    return redirect(Rsx::Route('Login_Controller::index'));
                }

                return rsx_view('Login_Verify');
            }

        Its blade hosts the component:

            <Two_Factor_Challenge $controller="Login_Controller"
                                  $method="verify_2fa" />

        And the endpoint it posts to - #[Auth('public')], because the session
        is deliberately not signed in yet:

            #[Ajax_Endpoint]
            public static function verify_2fa(Request $request, array $params = [])
            {
                try {
                    $login_user = Rsx_Two_Factor::verify_challenge($params);
                } catch (Auth_Throttled_Exception $e) {
                    return response_error(Ajax::ERROR_VALIDATION, $e->getMessage());
                } catch (Two_Factor_Failed_Exception $e) {
                    return response_error(Ajax::ERROR_VALIDATION, $e->getMessage());
                }

                return ['redirect' => static::__post_login_destination(...)];
            }

        Hand $params straight through - it is already {code} or {assertion}.
        Both catches carry a user-safe message; nothing else is caught.

        NEVER SHOW HOW MANY ATTEMPTS REMAIN. "That code is not valid" and the
        form again, every time. A remaining-attempts count tells an attacker
        exactly how much budget is left and when to stop before the identity
        locks - it turns a blind cap into a metered allowance.
        challenge_pending() reports no failure count for the same reason; do
        not add one to your screen.

        WHICH FAILURE IT WAS is $e->reason(), for code - never for display:

            Two_Factor_Failed_Exception::REASON_WINDOW_EXPIRED   nothing is pending
            Two_Factor_Failed_Exception::REASON_WRONG_ANSWER     wrong; try again
            Two_Factor_Failed_Exception::REASON_CHALLENGE_SPENT  wrong, and the last:
                                                                 the challenge is gone
            Two_Factor_Failed_Exception::REASON_IDENTITY_LOCKED  the identity is locked
            Two_Factor_Failed_Exception::REASON_REFUSED          anything else

    2b. TELL THE ACCOUNT OWNER WHEN A CHALLENGE IS EXHAUSTED
        Reaching a challenge means the PASSWORD was right. The caps make
        guessing the second factor slow - six digits against three valid codes
        is 1 in 333,333 a guess, and at ten failures an hour that is roughly 2%
        a month for somebody who never stops - and only being NOTICED makes it
        hopeless. The framework announces the moment and does nothing else
        about it:

            two_factor.challenge.spent           (action) staff
            portal.two_factor.challenge.spent    (action) the client portal

            payload: {identity, email, failures}

        fired when a wrong answer destroys the challenge, just before
        verify_challenge() throws REASON_CHALLENGE_SPENT. The identity travels
        in the payload because the challenge that named it is already gone.
        One handler queues one notice:

            #[OnEvent('two_factor.challenge.spent', priority: 10)]
            public static function notify($data): void
            {
                (new Two_Factor_Challenge_Spent_Email($data['email']))
                    ->to($data['email'])->send();
            }

        The email is the application's (CATEGORY = SECURITY: a required notice
        about the recipient's own account). The identity lock bounds how many
        one account can receive in a window. Worked example:
        system/app/RSpade/resource/reference_app/handlers/Two_Factor_Notice_Handlers.php
        and emails/two_factor_challenge_spent_email.php.

        ONE DESTINATION FUNCTION, TWO CALLERS. The password-only path
        redirects to it and the challenge endpoint returns it as a string; a
        destination computed twice drifts.

        NO TURNSTILE ON THE VERIFICATION ENDPOINT. The component renders no
        widget, so there is no __turnstile field, and the completeness guard
        fires only when a token WAS submitted. The surface is not unguarded:
        it answers only from the caller's own pending challenge and spends
        the brute-force budget as its first statement.

    3. AN ENROLLMENT SCREEN
        Anywhere a signed-in user can reach - the template puts it on
        Settings > Password & Security. Load the state, host the components,
        repaint from the server:

            this.data.two_factor = await Rsx_Two_Factor_Controller
                .credentials_list();

        then open <Totp_Enrollment /> or <Passkey_Register /> in a modal, and
        reload() the screen on its enrolled / registered event. Removal is
        credential_remove({id}), regeneration is recovery_regenerate() - both
        answer the fresh state.

    4. REQUIRING A SECOND FACTOR (OPTIONAL, AND ENTIRELY YOURS)
        The framework decides only whether an identity HAS a factor. It
        does not decide who must have one, it reads no "required" setting,
        and it ships no screen that holds a signed-in user until they
        enroll. The reference application requires nobody to enroll.

        An application that wants the rule writes it as its own sign-in
        step. A user who is past the password is signed in, and what they
        may do is decided by the gates as on any other request; "you still
        have to enroll" is a step the application walks them through, not
        an access level:

            - The login function works out, once, at sign-in, what this
              person still owes (your predicate - a site setting, a role -
              and !Rsx_Two_Factor::is_enabled($login_user)) and parks it
              with Session::put_value().
            - Main::pre_dispatch() redirects a page request to your
              enrollment screen while that value is set, leaving the
              login, enrollment and logout routes alone.
            - The screen hosts <Totp_Enrollment /> and/or
              <Passkey_Register /> and clears the value on their
              enrolled / registered event.

        A rule switched on today therefore reaches each person at their
        NEXT sign-in. Enrollment is refused while impersonating, so the
        step is skipped for an impersonated session. A step the person
        chose to skip for good is a preference variable
        (rsx:man user_preference_variables), not a session value.

ISSUED CODES
    A code the framework MINTS and the application DELIVERS - by email,
    SMS, a phone call - for the pending challenge. It is how an application
    asks for an emailed six-digit code at sign-in, for every identity or
    for some. The full recipe, staff and portal side by side, is
    rsx:man two_factor_codes.

    THE SPLIT. Generating, storing, verifying and rate-limiting a code are
    security work, so the framework does them: random_int digits, only a
    keyed hash kept in the pending challenge (a copy of the session store
    does not reveal them), a later code replacing an earlier one, and the
    same throttle, attempt caps and recording as a TOTP code. Delivering it,
    wording it, capping resends and deciding who owes one are application
    work, so the framework does none of them.

        $accepts = [Rsx_Two_Factor::ANSWER_ISSUED_CODE, Rsx_Two_Factor::ANSWER_PASSKEY];
        Rsx_Two_Factor::begin_challenge($login_user, $accepts);

        # the application's send endpoint (the challenge screen calls it)
        $code = Rsx_Two_Factor::issue_code();
        (new Sign_In_Code_Email($code))->to(Rsx_Two_Factor::pending_identity())->send();

    THE EMAIL is the application's class, declared CATEGORY = SECURITY: it
    reaches an address on the site block list and ignores the recipient
    opt-out, because a person who cannot receive the code cannot reach
    their own account (rsx:man email). The .dev. recipient rules and
    rsx.mail.delivery still apply - in the default 'suppressed' mode the
    code is recorded and never leaves.

    LIFETIME. The code lives exactly as long as its challenge
    (rsx.two_factor.challenge_window_minutes, 15). codes_issued in
    challenge_pending() lets the application cap "Send a new code".

PASSWORDLESS SIGN-IN
    A passkey as the FIRST and only credential: the visitor presses "Sign in
    with a passkey", the authenticator offers the discoverable credential it
    holds for this site, and the identity that owns it is signed in. Every
    passkey this subsystem registers is discoverable (requireResidentKey), so
    any registered passkey can do this with no extra enrollment.

    A PASSWORDLESS SIGN-IN IS COMPLETE; IT OWES NO SECOND FACTOR (framework
    ruling). User verification is REQUIRED on this ceremony - the
    authenticator must have checked a PIN or biometric, and an assertion
    without the UV flag is refused - so the passkey is two factors on its
    own: the device, and what unlocked it. verify_passkey_login() therefore
    signs the identity in outright.

    is_enabled() KEEPS ITS ONE MEANING: "this identity holds a confirmed
    second factor, so a PASSWORD or FEDERATED sign-in owes a challenge". It is
    not asked by a passwordless sign-in. The SSO path reads it unchanged: a
    Google sign-in by an identity holding a passkey still faces the
    challenge (unless rsx.sso.skip_two_factor), and may answer it with that
    same passkey.

    WIRING IT (the reference app's login pages do exactly this):

        #[Ajax_Endpoint]
        public static function passkey_login(Request $request, array $params = [])
        {
            if (!is_array($params['assertion'] ?? null)) {
                return response_error(Ajax::ERROR_VALIDATION, 'That passkey could not sign you in.');
            }

            try {
                $login_user = Rsx_Two_Factor::verify_passkey_login($params['assertion']);
            } catch (Auth_Throttled_Exception | Two_Factor_Failed_Exception $e) {
                return response_error(Ajax::ERROR_VALIDATION, $e->getMessage());
            }

            return ['redirect' => static::post_login_destination((int) $login_user->id, null)];
        }

        <div class="login-alternatives">
            <div class="login-divider"><span>or</span></div>
            <Passkey_Sign_In $controller="Login_Controller" $method="passkey_login" />
        </div>

        // SCSS: hide the block when nothing in it is visible
        .login-alternatives:not(:has(.Passkey_Sign_In:not(.Passkey_Sign_In--unsupported), .Sso_Buttons)) {
            display: none;
        }

    No Turnstile on that endpoint, for the reason there is none on the
    challenge endpoint: the component posts only {assertion}, and the
    endpoint spends the brute-force budget as its first statement.

THE CLIENT PORTAL REALM
    Rsx_Portal_Two_Factor gives portal users (Portal_User_Model) the whole
    subsystem - TOTP, passkeys, recovery codes, the second-factor challenge
    and passwordless sign-in - with the API documented above. Worked example:
    system/app/RSpade/resource/reference_app/portal/auth/Portal_Login_Controller.php
    (the two-stage login, verify_2fa, passkey_login) and
    portal/settings/Portal_Settings_Security.jqhtml (enrollment).

    WHAT DIFFERS FROM THE STAFF REALM:

        storage     _portal_two_factor_credentials, owned by portal_user_id.
                    No site_id: a portal user belongs to one site, so the
                    row is site-scoped through its owner.
        session     Portal_Session. begin_challenge() signs the PORTAL out;
                    a staff login on the same session is untouched.
        admission   a portal user is signed in only when
                    Portal_User_Model::can_login() accepts them (active and
                    verified) AND they belong to the site the application
                    declared (Portal_Session::set_site_id). A credential row
                    names its owner by a global id, so the site check is what
                    keeps one tenant's passkey from signing in on another's
                    portal. A refusal answers like a wrong answer.
        recording   the portal has no login history (_login_history is the
                    staff identity's store): each failure feeds
                    Login_Throttle::record_failure() directly, exactly once,
                    a success records nothing beyond the last_login stamp,
                    and a passkey enrollment outcome is a
                    Log::info('Portal passkey enrollment') line.
        rpId        the portal's HOST (Rsx_Portal_Url::host()) when PORTAL_URL
                    gives the portal a host of its own, otherwise the
                    application's hostname (shared with staff - safe, see
                    PASSKEYS above). A prefix never enters it. A passkey is
                    bound to its rpId, so moving the portal to another host
                    strands the passkeys enrolled under the old one (rsx:man
                    prelaunch_checklist, ENTRY 16).
        user handle 'portal-<id>'.
        endpoints   Rsx_Portal_Two_Factor_Controller.
        impersonation
                    "View as Client" (Portal_Session::is_impersonating())
                    refuses every enrollment and removal: a staff member
                    viewing a client's portal must never be able to enroll a
                    passkey onto that client's account.

    THE PORTAL LOGIN IS TWO-STAGE THE SAME WAY. The portal verifies its own
    password, so the shape is: check the password and can_login(); when
    Rsx_Portal_Two_Factor::is_enabled($portal_user), begin_challenge() and
    redirect to the portal's verify page INSTEAD of set_portal_user_id();
    otherwise sign in as before. The verify page hosts
    <Two_Factor_Challenge $controller="Portal_Login_Controller"
    $method="verify_2fa" />, whose endpoint calls
    Rsx_Portal_Two_Factor::verify_challenge().

    The rsx:users:2fa:* operator commands act on staff login identities only;
    a locked portal user is released with
    Rsx_Portal_Two_Factor::clear_failures($portal_user) from a shell (or by
    the identity window closing).

CLI COMMANDS
    THE BOOTSTRAP AND RECOVERY PATH, and deliberately not a general
    enrollment channel. The web flow can only ever act on the signed-in
    identity, which leaves two situations with no path at all: the first
    account on a fresh box, and a user who has lost both their phone and
    their code sheet. These run as whoever holds shell access, which is
    already a higher privilege than any identity in the application - so the
    impersonation reasoning that governs the web paths does not reach here.

    --user=<id|email> is REQUIRED on all four and resolves against
    login_users. --json wraps the result in the standard
    {"ok": true, "command": ..., "data": {...}} envelope (and a non-zero exit
    with {"ok": false, "error": ...} on failure).

    rsx:users:2fa:setup --user=<id|email> [--json]
        Mints a TOTP seed, writes the credential CONFIRMED, replaces the
        recovery codes, and prints the seed, the otpauth:// URI and the ten
        codes ONCE. A second seed is REFUSED - remove the existing one first,
        or add a second factor from the settings screen.

    rsx:users:2fa:dump --user=<id|email> [--json]
        Every factor, with TOTP seeds DECRYPTED and their provisioning URIs
        rebuilt, unconfirmed rows included. Recovery codes are a COUNT and
        never a list: they are bcrypt hashed and there is nothing to print.

    rsx:users:2fa:remove --user=<id|email> [--id=<credential>] [--force] [--json]
        Removes every factor, or the one named by --id (resolved against
        THIS identity's credentials - a miss is an error, because an operator
        who believes an account is unlocked when it is not is the dangerous
        outcome). Prompts before destroying anything; --force is how a script
        says the intent. --json cannot prompt, so it REQUIRES --force.

    rsx:users:2fa:unlock --user=<id|email> [--json]
        Clears the identity's second-factor failure count
        (Rsx_Two_Factor::clear_failures()), lifting an attempt-cap lock. The
        factors are untouched - remove is the command that takes them away.
        Reports whether the identity was locked ("was_locked" under --json).

CONFIGURATION
    config('rsx.two_factor') - six keys, and there is no seventh:

        'issuer' => null
            The label an authenticator app files the account under. null
            DERIVES it from Rsx::get_hostname(), which is what the user typed
            to get here and is recognisable in a list of twenty accounts in a
            way a product name may not be. A colon is stripped.

        'challenge_window_minutes' => 15
            The SECURITY WINDOW above (the password-passed state and a parked
            TOTP seed; not a WebAuthn challenge). Must be at least 1;
            challenge_expires_at() calls shouldnt_happen() on anything lower
            rather than minting a window that is already closed.

        'challenge_shows_full_email' => false
            true: the challenge state carries the full address (email) and
            <Two_Factor_Challenge> prints it. false: only email_masked - the
            state is answered for whoever holds the session cookie, which on
            an unattended browser need not be who typed the password.

        'challenge_max_failures' => 5
            Wrong answers one parked challenge survives (ATTEMPT CAPS).
            Must be at least 1.

        'identity_max_failures' => 10
            Wrong answers one identity may give inside the identity window,
            across challenges and addresses. Must be at least 1.

        'identity_failure_window_minutes' => 60
            A SECURITY WINDOW (not a timeout): opened by the identity's first
            wrong answer; how long a locked identity stays locked. Must be at
            least 1.

    There is NO enable switch - see DESCRIPTION.

    Dependencies (framework-internal, already installed): lbuchs/webauthn and
    bacon/bacon-qr-code. They are NOT in dependencies.exposed_composer:
    application code talks to Rsx_Two_Factor, not to either library.

NOTES AND GOTCHAS
    - A passkey is bound to the HOSTNAME it was enrolled on. Moving
      environments invalidates it; that is the spec, not a bug.

    - Do not call Login_Throttle::record_failure() alongside a
      STATUS_FAILED_2FA record_failure(). One failure, one recorder.

    - Park anything the challenge must carry BEFORE begin_challenge(), never
      after: the logout clears the identity, and a value written afterwards
      lands on a session the caller has already abandoned.

    - A checkbox that is absent from a POST means OFF. An application policy
      flag written from a form uses the checkbox-absent-means-off idiom, or
      it can never be turned back off.

    - credential_key, not credential_id: it is an opaque string handle minted
      by an authenticator, and SCHEMA-TYPE-01 reserves _id for integers.

    - The recovery-code plaintext exists exactly once. A user who lost the
      sheet regenerates it; an operator's only path is a remove plus
      rsx:users:2fa:setup.

    - Staff and portal credentials are separate: a passkey registered on
      the staff app does not sign anybody in on the portal, and the reverse.
      A person who uses both enrolls a passkey in each.

    - The WebAuthn ceremony timeout is the framework's (300 seconds), not
      configuration: it is sized for the cross-device QR flow, and the
      challenge window is derived from it. A generic browser error right
      after a QR scan, with no failed row on the server, is the browser or
      the phone's provider declining - see PASSKEY ENROLLMENT OUTCOMES.

    - A passwordless assertion must carry the UV flag. An authenticator that
      proves only presence (a bare touch) can answer a second-factor
      challenge but cannot sign anybody in on its own.
