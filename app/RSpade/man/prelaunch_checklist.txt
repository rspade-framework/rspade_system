PRELAUNCH_CHECKLIST(1)            RSpade Manual            PRELAUNCH_CHECKLIST(1)

NAME
    prelaunch_checklist - a curated, in-depth audit of hard-to-lint requirements
    to review and correct in any RSX application before it launches

SYNOPSIS
    php artisan rsx:man prelaunch_checklist

    rsx:prod:enable prints a pointer to this page after sealing a build.

DESCRIPTION
    Some framework requirements cannot be enforced by an rsx:check lint rule -
    either the machinery to recognize the pattern would be too brittle, or the
    requirement is a whole-flow wiring obligation rather than a per-file property.
    This page is the designated home for those requirements: a curated, in-depth
    checklist that should be audited and corrected in ANY RSX application prior to
    launch.

    Each entry discusses one requirement in depth: what to audit, why it matters,
    explicit guidelines, and concrete dos and don'ts. The RSpade LLM creates and
    maintains this file over time, adding an entry whenever a new hard-to-lint
    requirement emerges. It is a valid, sanctioned enforcement channel for
    difficult-to-test framework-required patterns in downstream applications - when
    a lint rule is impractical, "add this to the prelaunch checklist" is a good
    answer.

    This is an ADVISORY audit, not a gate. Nothing here blocks a build. The
    obligation is on the developer to walk the checklist before going live.

HOW TO USE
    Before launching an RSX application:
        1. Read every entry below.
        2. For each entry, perform the described audit against your application.
        3. Correct any divergence, following the entry's guidelines.
        4. Perform the manual walk-throughs where an entry calls for one.

    rsx:prod:enable reminds the operator to do this after it seals a build; the
    reminder is advisory and never blocks the build.

--------------------------------------------------------------------------------

ENTRY 1: LOGIN REDIRECT WIRING (intended-URL threading)

    What to audit
        Whether the application threads the intended-URL ?redirect= parameter
        through its entire login flow using the Login_Redirect API, end to end,
        with no hop dropped and no second validator introduced.

        FIRST: read `php artisan rsx:man login_redirect` IN FULL. That man page is
        the single source of truth for the wiring patterns (capture() at the
        rejection point, params() on every login-flow route hop, hidden_input() in
        every login-flow form, consume() once at each terminal). This audit does
        NOT restate those patterns - it directs you to them and requires you to
        verify each form against them.

        THEN enumerate EVERY auth-flow form in the application - staff AND portal:
        the staff login form and any 2FA / site-selection / invite-acceptance
        forms, and the portal login and invitation-register forms. This audit is
        form-enumeration driven: list all of them, and check EACH one individually
        against the man page's wiring contract. Staff forms use Login_Redirect with
        Rsx::Route and the staff rejection point (Main::pre_dispatch); portal forms
        use the identical calls with Rsx_Portal::Route and Portal_Main::pre_dispatch
        (the class is portal-context aware - it adapts its rules to whichever
        experience the form belongs to). No form in either experience is exempt.

    The wiring contract
        Every page between the auth rejection and the terminal post-login
        destination must merge Login_Redirect::params() into its outbound
        login-flow routes and include Login_Redirect::hidden_input() in its forms;
        the rejection point uses capture(); the terminal destination decision uses
        consume() exactly once.

    Why it matters
        Without this, a user who follows a deep link into a protected page while
        logged out loses their destination at the login 302 and always lands on the
        dashboard - a poor experience for shared/bookmarked deep links. And a
        hand-rolled version invites an open-redirect vulnerability: a naive
        ?redirect= that is not centrally validated can send an authenticated user
        off to an attacker-controlled host. Centralizing every read through the
        Login_Redirect validator is what makes the feature safe; a dropped hop or a
        second validator quietly reintroduces the hazard.

    Dos and don'ts
        DO route every redirect value through the Login_Redirect API (capture /
          params / hidden_input / consume).
        DON'T hand-read $_GET['redirect'] or hand-build the param string. The
          param name is a private constant precisely so nobody types it.
        DON'T write a second validator "just for this one hop". There is exactly
          ONE redirect sanitizer in the codebase; logout uses it too.
        DO let onboarding / welcome flows win over the redirect target. consume()
          supplies the default destination, not an override.
        DON'T let a redirect skip required onboarding, email verification, or
          site selection.
        DON'T stash the intended URL in the server session or browser storage. The
          intended URL is per-navigation state, not per-browser state; a
          session/storage stash is last-write-wins and sends one tab to the URL
          another tab captured (multi-tab correctness - see rsx:man login_redirect,
          STRATEGY).
        DO verify the invalid-value path degrades silently to the default
          destination - no error, no flash, no exception.

    The manual walk (perform before launch)
        1. While logged OUT, visit a protected deep URL (e.g. /settings/onedrive).
        2. Complete the full login flow, including every funnel your app has
           (2FA, site selection, etc.).
        3. Assert you land on the deep URL you originally requested - not the
           dashboard.
        4. Repeat, but tamper the threaded value to a hostile absolute URL:
           follow the flow with ?redirect=https://evil.example present.
        5. Assert you land on the DASHBOARD (the default), never off-host, and
           that no error is shown. Repeat the hostile check with a few more shapes:
           //evil.example, javascript:alert(1), /login (loop).

    The portal manual walk (perform before launch, if the app has a portal)
        The client portal wires the same four calls (Portal_Main::pre_dispatch
        captures; the portal login/register forms carry hidden_input(); the login
        and register controllers consume() at their terminal). Verify it end to
        end, minding prefix mode (portal served under /_portal, no dedicated
        domain - the common dev/single-host layout):
        1. While logged OUT, visit a protected deep portal URL in prefix mode
           (e.g. /_portal/workspace/5).
        2. Assert the 302 goes to /_portal/login?redirect=%2F_portal%2F... and,
           after portal login, you land on the deep URL you requested - not the
           portal dashboard.
        3. Repeat with hostile / cross-context values and assert each degrades to
           the portal dashboard, no error: /login (staff route, cross-context),
           //evil.example (off-host), /_portal/login (loop).
        4. If the portal runs in domain mode, repeat with un-prefixed paths
           (/workspace/5 valid; /login rejected by the portal exclusion list).

    Related follow-ups (framework-side, not app wiring)
        - BACKLOG B-31: when the framework dispatcher's non-Ajax unauthorized
          path redirects to login (instead of throwing), it should call
          Login_Redirect::capture() itself, so apps get intended-URL capture for
          free even if their main.php forgets.

ENTRY 2: reload() CALLS THAT SHOULD BE refresh() (jqhtml widgets)

    What to audit
        Every call to this.reload() in the application's jqhtml components. For
        each one, ask: does this component genuinely need its DOM torn down and
        rebuilt from scratch, or does it merely need fresh data? Unless there is
        an explicit reason the DOM must be reset and started over, refresh() is
        almost always the smarter call.

        Audit mechanically: grep the app's .js and .jqhtml files for ".reload()"
        and justify each occurrence individually.

    The difference (see rsx:man jqhtml, reload()/refresh())
        Both run the identical refetch: reset this.data to on_create() defaults,
        run on_load(), then consider a re-render. The difference is ONLY the
        repaint policy:

            reload()  = refetch + UNCONDITIONAL re-render. Child DOM is destroyed
                        and recreated, DOM handlers must be rebound, and transient
                        UI state is lost - open menus close, scroll position
                        resets, text selection vanishes, the widget visibly blanks
                        to its uninitialized state while data is in flight.
            refresh() = reload(false): the same refetch, but a re-render happens
                        ONLY if this.data's JSON snapshot actually changed. If the
                        server returns identical data, nothing repaints; if it
                        changed, the update lands in place without the
                        disappear-and-reinitialize flash.

    Why it matters
        A widget that reload()s on every notification, poll tick, or tangential
        event visibly strobes: the user watches it blank out and rebuild even when
        nothing changed. On a busy page (realtime subscriptions, periodic
        re-checks) this compounds into constant churn that reads as jank and
        destroys in-progress user interaction (an open dropdown, a half-made text
        selection, a scrolled list). refresh() makes the no-change case free and
        the changed case seamless. This cannot be linted: the two calls are both
        legitimate and only intent distinguishes them - hence a launch audit.

    Rule of thumb
        The SERVER telling you something may have changed -> refresh().
        The USER doing something that must be visibly reflected -> reload().

    Dos and don'ts
        DO use refresh() in every realtime subscription callback
          (this.subscribe(..., () => this.refresh())) - notifications are
          content-free hints and frequently irrelevant to this component's
          payload.
        DO use refresh() for poll-style "check for updates" flows and any
          re-fetch triggered by ambient events rather than direct user action.
        DO keep reload() where this.args changed (filter switched, record id
          swapped) or where the user's own action must land unconditionally -
          the post-save editor pattern (save -> this.reload()) is correct.
        DON'T "fix" a reload() strobe by caching around it or suppressing the
          fetch - that is what refresh()'s snapshot comparison already does.
        DON'T assume the two are interchangeable in the queue: they share one
          debounce queue and a queued reload() outranks a queued refresh(); a
          stray reload() alongside refresh() calls still forces full repaints.
        DO leave a short comment on any reload() that survives the audit for a
          non-obvious reason (why the DOM reset is required), so the next audit
          does not re-litigate it.

    The manual walk (perform before launch)
        1. grep -rn "\.reload()" rsx/ --include=*.js --include=*.jqhtml
        2. For each hit, classify: user-action reflection (keep), args-driven
           re-query (keep), server-hint/poll/subscription callback (switch to
           refresh()), unclear (investigate; default to refresh()).
        3. Open the busiest live page with realtime traffic and watch for widgets
           that visibly blank/rebuild when unrelated records change - each one is
           a missed refresh().

ENTRY 3: NO STATE-CHANGING GET ENDPOINTS (CSRF completeness)

    What to audit
        Whether every GET endpoint in the application is side-effect-free. CSRF
        enforcement (Rsx_Csrf, at the dispatcher POST seam) protects POST ONLY -
        the Origin/Referer check plus the session-gated token both run only for
        POST. A GET that changes state is therefore invisible to it, and is
        trivially triggerable cross-site: an attacker page embeds
        <img src="https://you/that-get-url"> (or a <link>, prefetch, or a
        redirect), the victim's browser fetches it carrying their ambient session
        cookie, and the mutation happens with no token and no Origin barrier.

        Enumerate EVERY GET route - staff #[Route]/#[SPA] AND portal
        #[Portal_Route] (portal routes live in a separate manifest that
        `rsx:routes` does not print). For each, confirm the handler only
        reads/renders/downloads and writes nothing.

    Why it matters
        This is the single invariant that lets CSRF enforcement be POST-only.
        Break it and you have a CSRF hole the framework's protection cannot see.
        The most damaging form is a business-data mutation reachable by GET
        (create/update/delete a record via a plain link) - that must never exist.

    Guidelines
        Every state-changing operation goes through a POST: a #[Ajax_Endpoint]
          (the browser calls Controller.method()) or a POST #[Route] /
          #[Portal_Route]. The automatic CSRF machinery then covers it with no
          extra work.
        A dual-method form route (methods: ['GET','POST']) is fine PROVIDED every
          mutation sits behind an explicit `if ($request->isMethod('POST'))` guard
          and the GET branch only renders the form. Check the guard on each one -
          the template's own auth forms (login, register, password reset,
          request-access) follow exactly this shape.
        Sanctioned exception, one-time-token links: a GET that acts on a
          single-use, unguessable, server-issued token delivered out of band
          (email verification / password-reset / invite-accept links, an
          impersonation handoff token) is acceptable. The token itself is the
          anti-forgery defense - an attacker cannot forge the victim's one-time
          secret - so no ambient cookie is being ridden. Keep such tokens
          cryptographically random and single-use.
        Tolerated low-severity case, logout via GET: /logout (and the portal
          logout / impersonate-stop) change session state on GET - "logout-CSRF."
          The impact is a forced logout (an annoyance, no data loss or
          disclosure), so the framework ships GET logout. If your threat model
          cares, make logout a POST (a small form/button or a Controller.method()
          call); otherwise accepting it is a defensible trade-off. Decide
          deliberately - never let a DATA mutation hide behind "it's just like
          logout."

    Dos and Don'ts
        DON'T ever mutate business data on a GET - no /items/:id/delete,
          /toggle-flag, /mark-read reachable as a GET link. Ever.
        DON'T rely on "the URL is hard to guess" for a mutating GET UNLESS the
          unguessability is a real single-use server-issued token (the exception
          above); a merely-sequential or predictable id is not a defense.
        DO route every write through POST so the automatic CSRF layer covers it.
        DO guard every dual-method route's write path behind
          $request->isMethod('POST').
        DO keep one-time-token GET links single-use and high-entropy.

    The manual walk (perform before launch)
        1. php artisan rsx:routes | grep 'method=GET'          (staff routes)
        2. grep -rn "Portal_Route(" rsx/ | grep -i "GET"       (portal routes)
        3. For each GET handler, confirm it only reads/renders/downloads. Flag any
           that write: business-data writes -> move to POST; session-lifecycle
           (logout / impersonate-stop) -> decide GET-vs-POST per your threat model;
           one-time-token links -> confirm the token is single-use and unguessable.

ENTRY 4: UNBOUNDED QUERY AUDIT (result sets with no ceiling)

    What to audit
        Every database read in your application code (rsx/) that can return more
        than one row. For each, answer: what is the LARGEST number of rows this
        can return, and what enforces that number? If the answer is "however many
        the table happens to hold", it is a defect - however small the table is
        today.

        Search for the shapes that materialize a whole result set:
        `->get()`, `->all()`, `->pluck(...)` without a preceding `->limit()`,
        `Model::all()`, and any `->get()` whose result is then sliced in PHP
        (`array_slice`, `->take(N)`, `foreach` with a counter). A LIMIT applied
        AFTER the fetch is not a limit - the rows were already hydrated.

        Audit the writers too, not just the readers. A read is only as bounded as
        the row growth behind it: rows written per request, per login, per import,
        per cron tick are the ones that grow without anyone noticing.

    Why it matters
        This is the failure mode that took down a live page in this framework's
        own history, and it is worth stating plainly because it is so ordinary.
        A session-list helper ran
        `where(login_user_id)->where(active)->orderBy(last_active)->get()`, then
        the caller sliced to the 20 it wanted to display. Every automated browser
        run had been minting a session row that nothing expired, so one login user
        had accumulated 62,617 of them. The page hydrated all 62,617 models,
        parsed 62,617 user-agent strings, exhausted a 128MB PHP process, and
        returned a blank 500. Secondary damage: those requests occupied every
        php-fpm worker, so unrelated endpoints started failing too.

        Nothing about the code looked wrong. It had a `limit` - in the wrong
        place - and it worked perfectly for a year. The table simply grew.

    Guidelines
        Every multi-row read must land in one of these shapes:

        1. SINGLE ROW - first() / find(), where one row IS the answer. Resolving a
           session from a cookie, a user from an id, a setting by key.

        2. TRUE LIMIT - the semantics genuinely want "the N most recent/top", and
           the LIMIT is in the SQL. Recent activity, latest N sessions, the newest
           notifications. The caller must be asking for N, not for everything.

           NEVER use a LIMIT to quietly truncate data that is all actually needed.
           An export of 125,000 rows must not become "the first 5,000" - that is a
           silent data-loss bug wearing a bound's clothing. That case takes
           shape 3.

        3. PAGINATION / CHUNKED ITERATION - for workloads that legitimately
           process large sets. Keyset ("seek") paging is the durable form:

               $last_id = 0;
               while (true) {
                   $batch = Model::where('...')->where('id', '>', $last_id)
                       ->orderBy('id')->limit(500)->get();
                   if ($batch->isEmpty()) break;
                   foreach ($batch as $row) { $last_id = $row->id; ... }
               }

           Keying on the primary key keeps the walk terminating even when the work
           changes the rows it is walking over. OFFSET paging drifts when rows are
           inserted or deleted mid-walk; prefer keyset for background jobs.

           The framework ships this as ->result_set(), which returns an
           Rsx_Result_Set: foreach it and you reach every record while only one page
           is resident. Framework APIs that hand you records (get_attachments(),
           get_deleted_files(), ...) already return one - foreach and count() work as
           you expect, but it is not an array.

        Two shapes that ARE bounded and need no change:

        4. FINITE CATALOG - the row count is fixed by your codebase or an external
           standard, not by user or machine activity: a settings table with one
           row per declared setting, ISO country/region tables, one row per
           permission. Adding a LIMIT here would truncate a complete answer to
           guard against growth that cannot happen.

        5. BOUNDED BY AN ENFORCED CEILING - something else already caps it (a
           worker-pool limit, a per-form maximum). Note WHERE the ceiling lives;
           if it is only a convention, it is not a ceiling.

        When a set is genuinely unbounded and the caller genuinely needs all of
        it, that is a design signal: give the operation its own paginated endpoint
        or a background job, rather than a lazy accessor that quietly fans out.

    Dos and Don'ts
        DON'T fetch-then-slice. `->get()` followed by `array_slice(..., 0, 20)`
          has already paid the full cost.
        DON'T pluck a large id set into PHP to feed a `whereIn()`. Pass the query
          as a sub-query and let the database keep it: `whereIn('x', $builder)`.
        DON'T assume "this table is small" - write down what BOUNDS it. A table
          that grows one row per request is unbounded no matter its size today.
        DON'T silently truncate. If a cap is exceeded and the caller needs the
          rest, fail loud with a message naming the cap and the alternative;
          a caller handed a partial set has no way to detect it.
        DO put every LIMIT in the SQL.
        DO keyset-chunk background work, and pair it with a heartbeat inside the
          loop if it runs as a #[Task].
        DO give unbounded-growth tables a retention policy at the same time you
          give them a bounded reader - the two problems are the same problem.
          Rows nothing ever deletes are what make readers dangerous.
        DO index the column your bound sorts on. A LIMIT still filesorts the whole
          matched set without a covering index; `(owner_id, active, last_active)`
          turns "20 most recent for this user" into an index-ordered read.
        DO declare `public static $unbounded = true` on every model whose table
          grows with customer activity - see the walk below. NOTHING enforces this
          for you, which is exactly why it is on this checklist.

    The manual walk (perform before launch)
        1. grep -rn -e '->get()' -e '::all()' -e '->pluck(' rsx/ | grep -v resource/
        2. For each hit, state the maximum row count and what enforces it. Assign
           it one of the five shapes above. Anything you cannot assign is a defect.
        3. List the tables your app writes to per-request, per-login, per-import or
           per-cron-tick. For each, name the retention policy that deletes old rows
           and the scheduled task that applies it. A table with no answer will
           eventually produce the failure described above.
        4. For each bounded reader you added, confirm an index supports its
           ORDER BY - otherwise the LIMIT bounds memory but not the scan.
        5. Walk rsx/models/ and confirm every model whose table grows with customer
           activity declares `public static $unbounded = true` next to $table:

               grep -L 'unbounded' rsx/models/*.php

           Each file the grep LISTS is unmarked - decide for each whether it should
           be. Mark logs, audit trails, event and message streams, notifications,
           queues, uploads, and the core business tables that scale with your
           customers. Do NOT mark human-authored low-volume tables (announcements,
           groups, roles), fixtures, join tables you always narrow to one parent, or
           1:1 detail tables. The test is "could a reasonable query here return
           thousands?" - over-marking dilutes the signal until nobody reads it.

           This step is on the checklist because NOTHING catches a missing
           declaration: no exception, no failed build, no lint rule (DB-UNBOUNDED-01
           covers framework code only). It needs a human eye, once, before launch.
           The RSpade template app ships marked examples to copy the shape from.
        6. Skim your development log for [DB-UNBOUNDED] warnings. Each one is a
           query that really did return more rows than expected, with the call site
           named. They are the empirical companion to steps 1-2: step 1 finds what
           LOOKS unbounded, this finds what actually was.

ENTRY 5: PORTAL EXPERIENCE BOUNDARY (the staff facade answering portal questions)

    What to audit
        Every place your application asks "who is the user?", "which tenant is
        this?", or "which session is this?" on a code path a CLIENT PORTAL request
        can reach - and whether it asks the right facade.

        There is ONE session per browser - one `rsx` cookie, one `_sessions` row -
        and TWO sets of PROPERTIES on it, reached through two facades that are not
        interchangeable:

            App\RSpade\Core\Session\Session          the STAFF properties
                                                      (login_user_id, site_id, ...)
            App\RSpade\Core\Portal\Portal_Session    the PORTAL properties
                                                      (portal_user_id,
                                                       portal_site_id, ...)

        Both sets are routinely populated at once - the same human, in the same
        browser, signed into both. So a staff-facade call on a portal path does not
        return null; it returns a REAL staff user, a REAL staff tenant, and
        staff-shaped authorization, on a page that is serving a client. Writes are
        worse still: Session::set_login_user_id(), set_site_id() and logout() act on
        the identity the person is actually using elsewhere.

        This is how the requirement was discovered, in production, downstream.

    Why a lint rule cannot do this
        The rule would have to decide REACHABILITY - can a portal request get here -
        which means whole-call-graph analysis across dispatch, shared transports,
        event handlers and service classes. The framework's three transports
        (/_ajax/:controller/:action, /_ajax/_batch, /_upload) are served on BOTH
        channels by the same handlers, so "this file lives under rsx/app/frontend"
        proves nothing about a gate handler it registers. A file's location, its
        namespace, and its route attributes are all poor proxies for the answer.

    THE ONE RULE
        Fork on the EXPERIENCE OF THE REQUEST:

            Rsx_Portal::is_portal_request()

        NEVER on who happens to be signed in:

            Portal_Session::is_logged_in()          <-- WRONG as an experience test
            Session::is_logged_in()                 <-- WRONG as an experience test

        Identity is not experience, and using identity gets BOTH directions wrong.
        An anonymous portal caller - a public portal page, your invite or register
        flow, a portal tab that logged out - falls into the STAFF branch. And a
        staff caller whose browser is also signed into the portal falls into the
        PORTAL branch. Both identities live on one session, so both mistakes are
        routine rather than exotic.

        A staff-OR-portal disjunction is a different thing and is fine where it is
        genuinely meant - "is anybody signed in" is a real question. What is never
        acceptable is using it to decide WHICH PROPERTIES to read next.

    The manual walk (perform before launch)
        1. Find every staff-facade call in your app and judge its reachability:

               grep -rn "Session::" rsx/ | grep -v "Portal_Session::" \
                   | grep -v "^rsx/resource/"

           For each hit answer one question: can a PORTAL request reach this line?
           Trace the callers - not the file's directory. Give every hit one of:
           staff-only, portal-reachable-and-correct, or portal-reachable-and-WRONG.
           A hit you cannot classify is a defect until proven otherwise.

        2. Grep for the wrong predicate specifically:

               grep -rn "Portal_Session::is_logged_in()" rsx/ | grep -v "rsx/portal/"

           A hit inside your portal tree is usually fine - there the experience is not in
           question. A hit in SHARED code, an event handler, a service, a model, or
           a component backend is the shape to fix.

        3. Audit your gate handlers by hand. These run on both channels and the
           framework hands them a 'user':

               file.upload.authorize        (mandatory - you have one)
               file.thumbnail.authorize
               file.download.authorize

           Confirm each still behaves correctly when 'user' is a Portal_User_Model,
           and when it is null. A handler that type-checks for your staff User_Model
           will silently deny (or silently allow) portal traffic.

        4. Check anything that stamps or scopes by site from portal code: mail sends
           (the site drives the unsubscribe/blocklist lookup, so the wrong site means
           an unsubscribed recipient still gets mailed), attachment claims, and any
           model you write that is not site-scoped.

        5. TEST THE PORTAL IN A BROWSER THAT IS NOT SIGNED INTO THE STAFF APP.
           This is the step everyone skips and it is the one that finds the bugs.
           Use a private window, or a second browser, or clear the `rsx` cookie -
           then walk the portal end to end: log in, upload, download, preview a
           document, use a realtime-backed screen, log out and back in. A
           developer's own browser is usually signed into the staff app, and every
           defect in this entry hides behind that staff identity. Your clients have
           none.

        6. Do NOT use `rsx:debug --portal --portal-user=N` as your only portal test.
           It installs the portal session directly and never runs your login
           controller, so it cannot reproduce anything that happens during a real
           form login. The originating downstream bug hid for eleven development
           phases for exactly this reason. Perform at least one REAL form login.

        7. If you are deploying the portal on a DEDICATED DOMAIN rather than a path
           prefix, treat the whole portal as unverified until you have walked step 5
           on that domain. Domain mode has its own cookie jar and therefore its own
           session row with the staff properties NULL, which means code paths that
           "work" in prefix mode by borrowing the staff identity
           simply return nothing there - a different and much louder set of
           failures, none of which prefix-mode testing will show you.

    Dos and don'ts
        DO   fork on Rsx_Portal::is_portal_request() in any code both experiences
             reach.
        DO   let a portal site resolution FAIL LOUD rather than default to a tenant.
        DO   test in a browser that is NOT signed into the staff app, with a real
             form login.
        DON'T use is_logged_in() (either facade) to decide which facade to use.
        DON'T assume a file under rsx/app/frontend is unreachable from the portal -
             gate handlers, services, models and shared components are not routed.
        DON'T "fix" your Main::init() site declaration by guarding it with
             is_portal_request(). In the current release that line is load-bearing
             for portal site scoping and the guard breaks portal login outright.

ENTRY 6: DATETIME DISPLAY AND DATETIME-vs-DATE COLUMNS (timezone correctness)

    What to audit
        Two related things, both invisible until the wrong person in the wrong
        timezone looks at the screen: (a) whether EVERY rendered date and datetime
        in the application goes through an Rsx_Time / Rsx_Date formatter, and
        (b) whether every DATETIME column actually holds a MOMENT rather than a
        CALENDAR FACT that has been quietly turned into midnight UTC.

        FIRST: read `php artisan rsx:man time` IN FULL. That man page is the single
        source of truth for the two classes, the resolution chain that picks the
        viewer's zone, and which formatter belongs to which value. This audit does
        NOT restate any of it - it directs you there and requires you to verify the
        application against it.

        The rsx:check rule JQHTML-DATETIME-01 already flags a raw *_at / *_date
        value interpolated into a .jqhtml template. Run rsx:check first and clear
        it. Everything below is what that regex CANNOT reach: values formatted in
        PHP, values assembled in JavaScript outside a template, values that leave
        the application entirely (mail, PDF, CSV), and columns whose TYPE is the
        defect.

    Why it matters
        A datetime is stored in UTC and rendered in the viewer's resolved zone
        (user preference -> site default -> config default). Every step of that is
        automatic - as long as display goes through the formatters. Print the
        attribute raw and the user reads a UTC ISO string. Convert it by hand with
        new Date(x).toLocaleDateString() and the user reads the BROWSER's zone
        instead of the one they configured - correct on your laptop, wrong for the
        traveling user and wrong for every shared-workstation tenant.

        The column half is worse, because no formatter can repair it. A calendar
        fact - a birth date, a hire date, an invoice date - is a day, not a moment.
        Store it in a DATETIME column and it becomes midnight UTC; a viewer west of
        UTC then sees the PREVIOUS DAY, forever, in every screen, export and email.
        A due_date at DATETIME-midnight has the same bug with teeth: "due today"
        flips a day early or late depending on where the reader sits.

    Audit A - datetime display beyond the linter's reach
        1. Clear the linter first, and treat its false-positive markers as a list
           to re-verify rather than as settled:

               php artisan rsx:check
               grep -rn "JQHTML-DATETIME-01-EXCEPTION" rsx/

        2. PHP-side string building of a temporal attribute. Any *_at / *_date
           value pushed into a string, a Blade echo, or an array destined for the
           browser, without a formatter:

               grep -rnE '\$[A-Za-z_]+->[a-z0-9_]*(_at|_date)\b' rsx/ \
                 --include='*.php' | grep -v 'Rsx_Time::\|Rsx_Date::'

           Remember MODEL-FETCH-DATE-01: a model's fetch() must NOT pre-format.
           A hit inside fetch() is fixed by REMOVING the formatting and moving it
           to the template - not by wrapping it.

        3. JavaScript outside .jqhtml files - a component .js, an action, a service
           - building display text by concatenation or template literal:

               grep -rnE '[`+].*\b[a-z0-9_]*(_at|_date)\b' rsx/ --include='*.js' \
                 | grep -v 'Rsx_Time\.\|Rsx_Date\.'

        4. Hand-rolled conversion anywhere. Every one of these is wrong on a
           datetime (browser zone, not the user's) and wrong on a DATE string
           (parsed as UTC midnight, renders a day early west of UTC):

               grep -rnE 'new Date\(|toLocale(Date|Time)String|\.slice\(0, ?10\)' \
                 rsx/ --include='*.js' --include='*.jqhtml'

        5. Egress that never renders in a browser at all, and so is never caught by
           looking at pages. EMAIL IS COVERED BY A RULE now - EMAIL-TEMPLATE-01
           flags a raw *_at / *_date read in any blade under an /emails/ directory,
           so clearing rsx:check clears the email half (re-verify every
           @EMAIL-TEMPLATE-01-EXCEPTION marker the same way you re-verify a
           JQHTML-DATETIME-01 one). What no rule reaches is a datetime an email
           class formats - or fails to format - in its own data(), and every other
           export. Walk those by hand:

               grep -rnE '(_at|_date)\b' rsx/emails/*.php
               grep -rniE 'build_csv|Csv.Writer|->download\(|Response::file|pdf' rsx/ \
                 --include='*.php'

           An emailed or exported datetime has no browser to fall back on: it MUST
           be formatted server-side with Rsx_Time / Rsx_Date, in the zone of the
           RECIPIENT, not the zone of the process that generated it.

    Audit B - DATETIME-vs-DATE columns
        1. Enumerate every temporal column in the schema:

               php artisan db:query "SELECT table_name, column_name, data_type \
                 FROM information_schema.columns WHERE table_schema = DATABASE() \
                 AND data_type IN ('datetime','timestamp','date') \
                 ORDER BY table_name, column_name" --table

        2. For EVERY DATETIME / TIMESTAMP column, ask one question: is this value a
           MOMENT (an instant that happened, or will happen, at a point on the
           world's clock) or a CALENDAR FACT (a day that is the same day for every
           reader on earth)?

               MOMENT, correctly DATETIME:
                   created_at, updated_at, deleted_at, completed_at, sent_at,
                   last_login_at, published_at, expires_at

               CALENDAR FACT, WRONG as DATETIME - must be DATE:
                   birth_date    a birthday is not an instant
                   hire_date     the day someone started, in local reality
                   invoice_date  the date printed on the document
                   due_date      the classic day-boundary bug: stored as midnight
                                 UTC, "due today" flips a day for any viewer whose
                                 zone crosses it

           The name is a hint, not the answer. A column named event_at that only
           ever holds a whole day is a calendar fact; a column named report_date
           that records the instant a report ran is a moment. Read what WRITES it.

        3. Flag each wrong column WITH ITS EGRESS PIPELINE. Fixing the column alone
           leaves the value mangled by everything downstream, so for every flagged
           column trace and list:

               - the column       -> a forward-only migration to DATE
               - the model        -> the DATE cast now applies; "YYYY-MM-DD"
                                     replaces the ISO datetime it used to yield
               - fetch()          -> the shape the client receives changes
               - the input        -> a native type="date" input, not
                                     datetime-local (see rsx:man datetime_inputs)
               - the display      -> Rsx_Date.format(...), NOT Rsx_Time.*
               - every other reader - comparisons, sorts, filters, exports,
                                     emails, reports, external API responses

           An LLM performing this audit reports the fields AND the associated
           pipeline for each one. A list of columns with no pipelines is an
           incomplete audit.

    Triage rules (one correct fix per finding)
        A raw datetime printed anywhere
            Wrap it in the formatter matching the column TYPE: Rsx_Time.* for a
            DATETIME, Rsx_Date.format() for a DATE. Never new Date(), never
            toLocaleDateString(), never string slicing.

        A date formatted with Rsx_Time (or a datetime with Rsx_Date)
            Wrong class, not a style choice - the two throw on each other by
            design. Fix the call, and if you cannot tell which class is right, you
            do not yet know the column type: go to Audit B for that column.

        A formatted value coming out of fetch()
            Remove the formatting from fetch() and format at the point of display.
            See MODEL-FETCH-DATE-01.

        A calendar fact in a DATETIME column
            A migration, not a display fix. Do the column AND its whole pipeline in
            one change, and do not leave the display "compensating" for the wrong
            type with an offset - a compensation is a second bug that hides the
            first.

        A genuine false positive (a preformatted value, or a non-temporal name that
        merely ends in _at / _date)
            Mark the line with @JQHTML-DATETIME-01-EXCEPTION and a one-word reason.
            Exception grants need the programmer's approval; never add one on your
            own initiative.

    Dos and don'ts
        DO   let the formatters own every rendered date and datetime. They are the
             only code that knows the viewer's resolved zone.
        DO   pick the class from the COLUMN TYPE: DATETIME -> Rsx_Time,
             DATE -> Rsx_Date.
        DO   format server-side for mail, PDF and exports - in the RECIPIENT's
             zone, not the server's or the sender's.
        DO   fix a wrong column with a migration, and its pipeline with it.
        DON'T use new Date(), toLocaleDateString(), Intl.DateTimeFormat or manual
             offset arithmetic in application code. Every one of them answers a
             different question than the one the user asked.
        DON'T store a calendar fact in a DATETIME column "because it was already
             there". Midnight UTC is not a day.
        DON'T declare $casts with 'date'/'datetime'/'timestamp' to work around a
             typing problem - those are Carbon-backed and blocked by rsx:check.
             The framework casts DATE and DATETIME columns automatically.
        DON'T assume the audit is done because the pages look right in YOUR zone.
             Yours is almost certainly the zone the code was written in.

    The manual walk (perform before launch)
        1. Set your user's timezone preference to a zone far from the server's and
           far from your own - Pacific/Auckland and America/Los_Angeles between
           them expose both directions of the day boundary.
        2. Walk every screen that shows a date or a time: lists, detail pages,
           dashboards, audit/authorship lines, activity feeds, print views.
        3. Assert each value reads in the zone you selected - not UTC, and not your
           browser's zone (change one of the two so they differ, or the test proves
           nothing).
        4. Create a record whose calendar-fact fields are set to a day, then read
           them back with the preference set to a zone WEST of UTC. A day that
           shifts is a DATETIME column that should be a DATE.
        5. Trigger one email and one export containing a datetime, and check the
           delivered artifact - not the screen that queued it.

    Related
        php artisan rsx:man time
        php artisan rsx:man datetime_inputs
        JQHTML-DATETIME-01   template-side display rule (rsx:check)
        MODEL-FETCH-DATE-01  server-side twin - no pre-formatting in fetch()

ENTRY 7: $required ASTERISKS WITH NO SERVER RULE (form validation completeness)

    What to audit
        Whether every $required=true on a <Form_Field> has a real validation rule
        behind it, in the endpoint the enclosing <Rsx_Form>'s $controller and
        $method name.

        FIRST: read `php artisan rsx:man form_conventions` IN FULL. That man page
        is the single source of truth for how a form declares its endpoint, why
        validation is server-only, and what a rejection looks like coming back
        (response_form_error keyed by field). This audit does NOT restate those
        patterns - it directs you to them and requires you to verify each form
        against them.

        THEN enumerate EVERY form in the application - staff AND portal. This
        audit is form-enumeration driven: grep for <Rsx_Form across rsx/, list
        every one, open the endpoint each names, and check each $required field in
        that form individually.

    Why it matters
        $required is PRESENTATION. It draws an asterisk beside the label and
        nothing else - it does not block submission, and there is deliberately no
        client-side check to add, because validation lives on the server exactly
        once. A client check would be a second implementation of the same rule,
        and its real damage is that it MASKS a missing server rule: the form
        appears to enforce the field, so nobody notices the endpoint does not.

        An asterisk with no rule behind it is silent in every way that matters.
        Nothing throws. The field is visibly marked. Manual testing passes,
        because a human fills the field in. The gap surfaces later, when a script,
        an import, or an external API client posts the same endpoint with the
        field blank and the record is written with an empty value that the rest of
        the application assumed could never exist.

    Guidelines
        1. Enumerate the forms: grep for `<Rsx_Form` across rsx/, staff and portal
           alike. Every match is one audit item.
        2. For each form, read its $controller and $method and open that endpoint.
        3. For each $required field in the form, confirm the endpoint has a
           presence check for it, and that the check is written against BLANK, not
           merely against ABSENCE - a submitted-but-empty text input arrives as
           the empty string, not as a missing key.
        4. Confirm the rule is IDENTICAL on create and on edit. A field required
           when a record is added is required when it is changed; a save path that
           validates on one and not the other is the same hole with a narrower
           entrance.
        5. Confirm the rejection is response_form_error keyed by the input's
           $name, so the message lands on the field rather than at the top of the
           form.
        6. Sweep the other direction too: a field the endpoint requires but whose
           <Form_Field> carries no $required is a UI defect. The user is given no
           warning and discovers the requirement by having their submission
           rejected.

    Dos and don'ts
        DO test for blank:
             if (trim($params['title'] ?? '') === '') { ... }
        DON'T add a client-side required check to "help" - validation lives on the
             server once, and the client copy hides the case where the server copy
             is missing.
        DON'T write `if (!empty($params['title'])) { $record->title = ...; }` as a
             stand-in for a required rule. That is not validation; it is "keep the
             old value when the field is blank", it silently accepts the blank
             submission, and on a create it leaves the column at its default.
        DON'T reject with response_error(Ajax::ERROR_VALIDATION, 'message'). That
             is a form-level error with no field to attach to; the user is told
             something is wrong and not which box.
        DO check the portal's forms with the same rigour as the staff app's. A
             portal endpoint is reachable by an external user, which is the
             population least likely to fill a form in the way you expected.

    Related
        php artisan rsx:man form_conventions
    php artisan rsx:man template_app
    php artisan rsx:man email
        php artisan rsx:man external_api    (the other caller that sends blanks)

ENTRY 8: AUTHENTICATION THROTTLE COVERAGE (every credential-checking path, and the
         client IP your proxy actually presents)

    What to audit
        Two things, both silent when wrong.

        FIRST, every path in the application that checks a credential. Enumerate
        them: grep for RsxAuth::attempt, check_password, Hash::check and password_verify
        across rsx/, staff and portal alike, and add every second-factor, backup-code,
        invitation-code and password-reset-token verification you find. For each one,
        confirm it is covered - either it goes through RsxAuth::attempt() (which
        refuses a locked-out address before the lookup), or it calls
        Login_Throttle::require_not_throttled() itself before the check and feeds a
        failure afterwards (Login_Throttle::record_failure(), or a
        Login_History::record_failure() which already does).

        SECOND, what Session::get_client_ip() answers on the DEPLOYED host. It reads
        X-Forwarded-For, then X-Real-IP, then REMOTE_ADDR. Load one page and look at
        the address the framework recorded (a `_sessions` row's ip_address, or a
        deliberate failed login and its "Login failure" log line).

    Why it matters
        The throttle is keyed on the client IP, so a deployment where every request
        presents the SAME address has one shared bucket: ten failures from anywhere
        lock out every user in the world. That is the failure mode to find before
        launch, not after. It happens whenever a reverse proxy, load balancer or CDN
        terminates the connection and the app sees only the proxy's address - and it
        is invisible in development, where every request comes from a different place
        already.

        The mirror image is just as quiet: a credential path that neither goes
        through attempt() nor calls the throttle itself is an unlimited guessing
        oracle sitting beside a protected one. A 6-digit second factor is a million
        guesses inside a 30-second window; an attacker who has the password only
        needs the unthrottled door.

    Guidelines
        1. Enumerate the credential paths as above. One audit item each.
        2. For a path that does NOT use RsxAuth::attempt(), verify the ORDER:
           require_not_throttled() runs BEFORE any lookup, comparison or account-state
           check, so a locked-out address learns nothing at all.
        3. Verify the failure is counted exactly ONCE. Login_History::record_failure()
           already feeds the throttle; pairing it with Login_Throttle::record_failure()
           on the same event counts twice and halves your configured budget.
        4. Verify the refusal is rendered as a message, not as an error page:
           Auth_Throttled_Exception is THROWN, and an uncaught throw on an anonymous
           login form is a 500 for a user who merely typed a password wrong ten times.
        5. Confirm the address the framework sees is the real client's, and that your
           proxy sets X-Forwarded-For (or X-Real-IP). If it does not, the throttle is
           either global or useless.
        6. Review rsx.sessions.login_throttle against how your users actually behave.
           The defaults (10 failures / 15 minutes / 15 minute lockout) suit a normal
           business application; a kiosk or a shared-NAT population may need a larger
           budget, and lowering 'enabled' to false is only correct when something in
           FRONT of the app is doing the same job.

    Dos and don'ts
        DO route a new login flow through RsxAuth::attempt() when you can - coverage
             is then automatic and cannot drift.
        DON'T report a throttled attempt as "invalid email or password". It is not a
             wrong password, and the user whose password is correct will keep retrying.
        DON'T build a second throttle on Login_History::get_failed_attempts_count*().
             Those counts are a statistic; the enforcement is Login_Throttle's, and a
             second one only guarantees two different answers.
        DON'T trust a manual test from your own desk to prove the IP wiring. One
             browser cannot tell a per-IP bucket from a global one.

    Related
        php artisan rsx:man session      (LOGIN THROTTLE)
        php artisan rsx:man auth

ENTRY 9: OUTBOUND EMAIL (the transport, the sender domain, and the dev safety net)

    What to audit
        Whether this installation can actually deliver mail to real people, whether
        receiving servers will believe it, and whether the two development safety
        layers are in the state you intend for production.

        FIRST: read `php artisan rsx:man email` IN FULL - in particular DELIVERY
        MODES AND THE DEV-SITE LAYER and CONFIGURATION. This audit directs you
        there and does not restate it.

        A fresh install is in MAIL_DELIVERY=aiosmtpd - captured into a local Maildir
        and nothing else. That is correct for development and wrong for launch, and
        NOTHING BREAKS to tell you: the queue row says Sent, the catcher file is
        written, and no human ever receives anything.

    Why it matters
        Every failure in this entry is invisible from inside the application. A
        loopback transport looks healthy. A suppressed delivery mode looks healthy.
        A From address on a domain with no SPF record sends successfully and lands
        in a spam folder nobody looks in. The first evidence is a customer saying
        they never got the invitation - and by then the password reset, the receipt
        and the alert never arrived either.

        The dev-site layer is the other direction of the same risk. It is keyed on
        the hostname containing '.dev.', so a staging host named without it has no
        net at all: the first import on that box mails every real address in the
        database.

    The audit
        1. MAIL_DELIVERY=live, EXPLICITLY. It is the ONE value that makes this host
           send mail, and the other three all look healthy while nobody receives
           anything: 'aiosmtpd' (the shipped default) captures into a local Maildir,
           'suppressed' renders and records and hands nothing to a transport, and
           'disabled' freezes the queue entirely. Confirm which one this host is on:

               php artisan rsx:health          # the three Mail rows

           This one value moves THREE things at once: whether mail is handed to a
           transport at all, whether the rsx.mail.transport.* block is even read
           (only 'live' reads it), and whether the dev-site recipient gate engages
           (only 'live' engages it).

        2. MAIL_HOST/MAIL_PORT name the relay or MTA that actually sends for you,
           with MAIL_ENCRYPTION and credentials to match. They are INERT until
           MAIL_DELIVERY=live, so a box that looks configured may not be.

        3. A real MAIL_FROM_ADDRESS on a domain you control, and MAIL_FROM_NAME set
           (or deliberately left empty to use the product name). noreply@example.com
           is the shipped placeholder and must not survive launch.

        4. SPF, DKIM and DMARC published for that domain. The "Mail sender domain"
           health row checks SPF and DMARC and, when rsx.mail.dkim_selector names
           one, the DKIM record too. It WARNs rather than FAILs because the fix is a
           DNS change at a registrar - it is still a launch blocker.

        5. Send a real message to a real mailbox you can open, on the launch host:

               php artisan rsx:mail:test you@your-real-domain.example

           Then READ THE DELIVERED MESSAGE, not the queue row: check the From line,
           the links (they must be absolute and must resolve to the launch host),
           the images, the datetimes, and whether it landed in the inbox or in spam.

        6. The dev-site whitelists and catchall are cleared, or intended. On a
           production hostname they are inert; on any host whose name contains
           '.dev.' they decide who receives mail. Confirm EMAIL_DEV_CATCHALL_ADDRESS,
           EMAIL_DEV_EMAIL_ADDRESS_WHITELIST and EMAIL_DEV_EMAIL_DOMAIN_WHITELIST
           say what you mean on every environment you operate, and that any staging
           box you rely on this net for is actually named with '.dev.'.

        7. Retention is chosen deliberately: rsx.mail.retention_days (default 30)
           deletes whole queue rows - the rendered bodies with them. If a compliance
           or support requirement needs longer, set it before the first month passes.

        8. The stale window is chosen deliberately: rsx.mail.stale_after_days
           (default 2). Any queued message still unsent that long after it was due is
           REFUSED and marked Failed, naming `php artisan rsx:mail:resend <id>`. That
           is what stops a queue nobody noticed was broken from flooding a month of
           stale notices the moment somebody repairs it - the decision to send old
           mail belongs to a human. Raise it only if this application genuinely sends
           mail that is still worth receiving days late; lowering it below a day
           risks refusing mail over a routine relay outage.

        9. Every email class the app ships renders. Walk them:

               php artisan rsx:mail:test you@example.com --email=Welcome_Email

           for each class, and read each delivered message.

        10. The task cron is installed and ticking (the "Task Scheduler Liveness"
           health row). Without it the drain still runs on every send, but a message
           held back by a retry delay or a send_at() waits forever.

    Triage rules (one correct fix per finding)
        MAIL_DELIVERY is not 'live' on a launch host
            Set MAIL_DELIVERY=live, point MAIL_HOST/MAIL_PORT at the real relay, set
            MAIL_ENCRYPTION and credentials, and re-run rsx:mail:test to a real
            mailbox. Do not "test in production" by sending to a colleague from a box
            still in aiosmtpd mode: it proves nothing, because nothing left. Verify
            the "Mail delivery" health row says live via the relay you configured.

        Missing SPF / DMARC / DKIM
            A registrar DNS change, and it propagates - do it days before launch,
            not on the morning.

        Mail arrives but links are broken
            APP_URL on the sending host is wrong, or a template built a URL without
            rsx_absolute_url(). Clear EMAIL-TEMPLATE-01 in rsx:check first.

        A staging host mailing real customers
            The hostname has no '.dev.' in it. Rename it, or accept that the box has
            no recipient net and set MAIL_DELIVERY=suppressed there.

    Dos and don'ts
        DO read the delivered message, in a real mailbox, on the real host.
        DO treat a WARN on the sender-domain row as a blocker. It is the difference
             between "sent" and "read".
        DO check every environment separately. These are .env values, and .env is
             never distributed.
        DON'T assume a green queue means delivered mail. Sent means a transport
             accepted the message; the catcher accepts everything.
        DON'T leave the shipped noreply@example.com in place "for now".
        DON'T rely on the dev-site gate on a host whose name cannot trigger it.

    Related
        php artisan rsx:man email
        php artisan rsx:man config_rsx      (MAIL AND SMS)
        php artisan rsx:man health          (the three Mail rows)
        EMAIL-TEMPLATE-01                   server-side datetimes, absolute URLs

ENTRY 10: LIVING DOCUMENTATION CURRENCY (rsx/**/CLAUDE.md and the app skills)

    What to audit
        Whether every living documentation file this application carries still
        describes the application as it is TODAY: the per-directory CLAUDE.md files
        under rsx/, and the application's own skills under rsx/resource/skills/.

        FIRST: read the framework's LIVING DOCUMENTATION IN rsx/ rule (it is
        always-on knowledge; `rsx:man template_app`, LIVING DOCUMENTATION restates
        the convention). This audit does NOT restate the rule - it enumerates the
        files and holds each one to it.

        This audit is file-enumeration driven. Build the list first:

            find rsx -name CLAUDE.md -not -path '*/resource/*'
            ls rsx/resource/*/CLAUDE.md
            ls rsx/resource/skills/*/SKILL.md

        Every file the three commands print is in scope, and each is read
        INDIVIDUALLY against the directory it documents. There is no sampling: a
        file nobody checked is exactly the file that has been wrong the longest.

        NOT in scope: system/app/RSpade/resource/reference_app/**. Those are the
        pristine template copies that ship inside the framework release; they
        describe the app as it was published, they are read-only, and
        rsx:framework:pull overwrites them whole. Correcting one is meaningless.
        Equally: the framework NEVER edits the files under rsx/ on a pull. Nothing
        upstream will ever fix these for you - which is why they are on this list.

    Why it matters
        A living file is read as current by every LLM session and every developer
        who opens the directory, and nothing breaks when it stops being true. A
        stale WHAT IS HERE inventory sends the next change to a component that was
        renamed a year ago; a HOW TO CUSTOMIZE section naming a seam that no longer
        exists produces code written against a contract nobody implements; a
        DIVERGENCES paragraph describing a divergence you have since abandoned
        actively steers work AWAY from the framework behaviour you went back to.

        Uneven currency is worse than none. A reader who finds one accurate file
        trusts its neighbours, and the wrong one is indistinguishable from the
        right one until the code disagrees.

    The audit
        For each file in the enumeration:

        1. WHAT IS HERE matches `ls` of the directory. Every component, class or
           file group listed still exists under that name; everything present that
           a reader would need to know about is listed. Files added since the last
           edit are the usual finding.

        2. HOW IT IS USED names the real invocation - the current tag names,
           arguments, endpoint names and neighbours. Follow one example from the
           file into the code and confirm it still compiles as written.

        3. HOW TO CUSTOMIZE names seams that EXIST. An "extend this", "override
           that", "delete this directory" instruction is checked against the code,
           not remembered.

        4. RELATED still resolves: every `rsx:man <page>` renders, every skill name
           is a skill that exists (framework skills were renamed when their subject
           moved into the app), every sibling path is a real directory.

        5. Any `## DIVERGENCES FROM FRAMEWORK DOCS` section still describes a REAL
           divergence, one paragraph per divergence. A paragraph whose behaviour the
           framework has since adopted as its own is DELETED - it is no longer a
           divergence, and leaving it in claims a difference that does not exist.
           The template ships no such section; every paragraph in one is a fork's
           own deliberate departure and is re-justified here or removed.

        6. A directory of shipped code this application DELETED has its file deleted
           with it. Grep for the deleted directory's name across rsx/ and remove the
           pointers too.

        7. A directory this application ADDED that is a customization seam - a
           component group, a module, a library of its own - gets a file, in the
           shape the neighbouring files use (WHAT IS HERE / HOW IT IS USED / HOW TO
           CUSTOMIZE / RELATED). A directory with no CLAUDE.md is undocumented; it
           is never "documented elsewhere".

        8. Each app skill's frontmatter `description` still triggers on the work it
           covers: it names symbols, commands and literal error strings that are
           still spelled that way in the code. A skill about a feature you removed
           is deleted; a feature you added that has task vocabulary earns one.

    Triage rules (one correct fix per finding)
        The rule that governs every row below: FIX THE FILE, NEVER THE CODE. This
        audit is a documentation audit. The application is the truth and the file is
        the description of it.

        Stale inventory (files listed that are gone, files present that are absent
        from the list)
            Rewrite WHAT IS HERE from the current `ls`. Do not patch one line - the
            drift is usually broader than the line you noticed.

        A section about code that no longer exists
            Delete the section. There is no deprecation notice and no "used to" in
            a living file; the file describes the present.

        The file contradicts a framework man page or skill
            Decide which way the contradiction runs. If this application is
            DELIBERATELY different, that is a divergence: record it as one short
            paragraph under `## DIVERGENCES FROM FRAMEWORK DOCS` (create the section
            the first time one is needed) naming which framework document says what
            and what this application does instead. If the difference is ACCIDENTAL
            - the app drifted off a convention it meant to keep - that is a CODE
            decision for the developer, made outside this audit. Note it, finish the
            documentation pass, and take the code question separately.

        A file that is thorough but was written for a different directory
            (Usually a copy of a sibling.) Rewrite it against this directory or
            delete it. A confidently wrong file costs more than no file.

        A skill and a CLAUDE.md that disagree
            The skill carries the how-to depth and the CLAUDE.md the inventory; they
            overlap by design and must not conflict. Correct both in one pass -
            they are companions and are updated together.

    Dos and don'ts
        DO read the directory before the file. The `ls` is the source; the file is
          the claim.
        DO update a living file in the SAME pass as the change that made it stale.
          This entry is the safety net for what slipped through, not the mechanism.
        DO delete a file whose directory is gone.
        DON'T edit anything under system/app/RSpade/resource/reference_app/. It is
          overwritten by every framework pull, and it is not your app.
        DON'T "fix" the code to match the documentation. The code is what runs.
        DON'T add a `## DIVERGENCES FROM FRAMEWORK DOCS` section pre-emptively, and
          don't turn it into a changelog: no dates, no history, one paragraph per
          live divergence.
        DON'T leave a directory you added undocumented because "it follows the
          obvious pattern". The reader cannot tell an undocumented directory from an
          uninteresting one.
