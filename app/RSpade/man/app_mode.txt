APP_MODE(3)                 RSX Framework Manual                 APP_MODE(3)

NAME
    app_mode - Application execution modes and the mechanics of a sealed build

SYNOPSIS
    Environment (.env):
        RSX_MODE=development|debug|production

    Mode transitions:
        php artisan rsx:prod:enable [--debug]
        php artisan rsx:prod:disable
        php artisan rsx:mode:set dev|debug|prod

    The build:
        php artisan rsx:build [--force]
        php artisan rsx:clean [--force]
        php artisan rsx:prod:verify

    CDN externals mirror:
        php artisan rsx:cdn_externals:refresh

    DEPLOYING is a separate topic with its own page: rsx:man prod carries the
    deployment recipes, the read-only posture, the administration levers and
    the error catalog. This page is the mechanics underneath them.

DESCRIPTION
    RSpade runs in one of three modes. RSX_MODE (read from the project-root
    .env, and written only by the mode-transition commands) is the SINGLE
    source of truth for the mode. Laravel's app.env and app.debug are DERIVED
    from it in config/app.php; the APP_ENV and APP_DEBUG env keys are not read
    anywhere.

        RSX_MODE       app.env      app.debug
        development    local        true
        debug          local        true    (the sealed DIAGNOSTIC build)
        production     production   false

    development
        The default. Dev mode is production-worthy for low traffic: the
        manifest rebuilds automatically on file changes and bundles compile
        JIT on the web request. Everything is live the instant a file is
        saved. Full debugging: console_debug() works, inline sourcemaps,
        debug info in window.rsxapp.

        A dev box is as important as a prod box. A primary goal of RSpade is
        that development mode runs on a production environment and still
        behaves reliably and securely. The only major differences in a
        sealed build are that it skips the environment checks and dynamic
        source rebuilds (slightly faster), minifies JS (and, in strict
        production, obfuscates the app bundle's strings and drops its
        console.log calls), drops from each
        bundle the jqhtml components nothing it serves names (the component
        shake, rsx:man bundle_api), and suppresses diagnostic dumps on
        errors. Every other feature - CSP enforcement
        included - works identically in every mode. A feature that "only
        breaks in dev" is a broken feature, not a dev-mode allowance.

    debug and production ("prod modes")
        Both are SEALED builds. A sealed build is compiled ONCE by an
        explicit command - rsx:build - and then treated as IMMUTABLE. The
        framework will NOT auto-rebuild the manifest or JIT-compile a bundle
        in a prod mode; if a build artifact is missing it fails loud instead
        of silently degrading to JIT compilation.

        debug is a production-like LOCAL test build: unminified, sourcemaps
        survive, console_debug() still works. Use it to reproduce a
        production-specific issue with readable code.

        production (strict prod) is the fully optimized deployment build:
        minified, sourcemaps gone, console_debug() stripped from the output.

    The word "sealed" is literal: the build writes a seal file that pins the
    exact build on disk, and the framework then refuses to write a build
    artifact from anything but a build (see GUARDS). Two byte-identical
    codebases produce byte-identical build assets (see DETERMINISM CONTRACT),
    which is what makes a sealed build safe to compile once and distribute
    across a cluster.

MODE COMPARISON
    Behavior                    development  debug        production
    --------                    -----------  -----        ----------
    Auto manifest rebuild       Yes          No           No
    Auto bundle JIT compile     Yes          No           No
    Minified output             No           No           Yes
    App strings obfuscated      No           No           Yes
      (rsx.production.obfuscate_strings, default on)
    Unnamed components dropped  No           Yes          Yes
      (the component shake; removed names carried only in debug)
    Inline sourcemaps survive   Yes          Yes          No
    console_debug() in browser  Yes          Yes          No (stripped)
    console.log() in app bundle Yes          Yes          No (stripped)
      (vendor bundle keeps its console.log calls)
    Debug block in window.rsxapp Yes         Yes          No
    window.rsxapp.mode          development  debug        production
    Rsx.is_dev() (JS)           true         false        false
    Rsx.is_debug() (JS)         false        true         false
    Rsx.is_prod() (JS)          false        true         true
    CDN assets                  Mirrored     Mirrored     Mirrored
    Sealed / immutable build    No           Yes          Yes
    Error if artifacts missing  No           Yes          Yes

    In the browser the mode is window.rsxapp.mode, read through the three
    Rsx helpers above - the JS twins of Rsx::is_development(),
    Rsx::is_debug() and Rsx::is_production() (which is likewise true in
    both sealed builds). Strict production alone is
    Rsx.is_prod() && !Rsx.is_debug().

    Note the two things that are NOT true of any mode: nothing merges the
    per-bundle JS/CSS into a single file (bundles are always the vendor/app
    split), and nothing inlines mirrored assets into a bundle. See EXTERNAL
    ASSET MIRRORING and BUNDLE OUTPUT.

THE MODE TRANSITIONS
    rsx:prod:enable [--debug]
        Heal the .env symlink invariant (see ENV FILE INVARIANT), write
        RSX_MODE, then run `rsx:build --force` in a fresh subprocess - which
        boots reading the RSX_MODE just written. Without --debug it builds
        strict production; with --debug it builds the debug variant.

        The build is what produces and seals the assets; this command adds
        nothing to it. `rsx:build --force` on a box already in a prod mode is
        the same operation without the mode write - which is why there is no
        separate "refresh" command.

        A failed build leaves the box unsealed. The message says so, and says
        the box has nothing to serve until the build succeeds.

    rsx:prod:disable
        Heal the .env invariant, remove the seal, write
        RSX_MODE=development, run rsx:clean, restore the DEVELOPMENT composer
        autoloader (a plain, non-authoritative dump - a strict-prod build
        leaves a classmap-authoritative autoloader that must be undone so
        new and renamed classes resolve again), then run rsx:build.
        Idempotent: safe to run on a box already in development.

    rsx:mode:set dev|debug|prod
        Kept for muscle memory. A thin delegator so there is exactly ONE
        implementation of each transition:
            dev, development  -> rsx:prod:disable
            debug             -> rsx:prod:enable --debug
            prod, production  -> rsx:prod:enable

    rsx:prod:verify
        The cluster / CI tool. Requires a seal. Recomputes the sha256 of
        every sealed asset, checks the build_key on disk against the seal,
        and reports OPcache posture (advisory only). Prints a table and
        exits 0 when the build matches the seal, 1 otherwise. (It carries no
        environment-sanity rows: app.env and app.debug derive from RSX_MODE,
        so nothing can disagree with the seal except the mode itself, which
        the drift check already reports.)

    rsx:cdn_externals:refresh
        The ONE expiry for the CDN externals mirror (rsx/resource/.cdn-cache/):
        it delegates the wipe to rsx:clean and the rebuild to rsx:build, so
        every mirrored asset is re-fetched and every bundle recompiled.

THE BUILD
    rsx:build is the only command that produces what the site serves. There
    is no second build path and no build mode.

    In DEVELOPMENT it does what a page would otherwise do for itself on first
    request - the manifest and every bundle - and nothing else. It seals
    nothing.

    In a PROD MODE the pipeline is fixed and complete:

        1. preflight   build/ and tmp/ writable, checked before anything is
                       destroyed. A build that discovers halfway through that
                       it cannot write has already destroyed what it was
                       replacing.
        2. rsx:clean   a build starts from nothing, or it is not
                       reproducible. Spawned as a subprocess carrying the
                       build context.
        3. manifest    the index every later step reads.
        4. externals   every declared external mirrored, so the artifact is
                       self-contained. One console line per download naming
                       the URL; silence for a file already verified present;
                       anything unfetchable FAILS the build.
        5. bundles     every module bundle, minified in strict production.
        6. composer    optimized autoloader; --classmap-authoritative in
                       strict production. This runs BEFORE the Laravel caches
                       because composer's post-autoload-dump hook clears
                       Laravel's compiled files. The discovery step
                       (package:discover) is run IN THIS PROCESS rather than
                       through composer's hook, which would spawn a bare
                       artisan that the seal gate refuses mid-build.
        7. laravel     event and VIEW caches, into build/ (RSX has no
                       route cache: Laravel's route table is empty).
                       Precompiling Blade is what lets a served request read
                       the build tree without writing to it; a template that
                       fails to precompile fails the build.
        8. the seal    written LAST and only on success.

    It refuses without --force when a seal is already present:

        A sealed production build is already present.
          Rebuilding replaces what this box is serving right now.
          Run it deliberately: php artisan rsx:build --force

    rsx:clean owns every wipe: it quiesces the node daemons, empties build/
    and tmp/ (Laravel's caches and compiled views included), flushes the
    Redis caches, sweeps orphaned atomic-write staging directories, and
    recreates the two empty roots. In a prod mode it requires --force.

    Both commands check writability before touching anything and refuse with
    nothing changed.

THE SEAL FILE
    Location:
        build/prod_seal.json

    The seal is the on-disk record of a compiled build. It is JSON:

        {
            "schema": 1,
            "rsx_mode": "production",        // or "debug"
            "build_key": "<manifest hash>",
            "git_commit": "<HEAD sha or null>",
            "created_at": "2026-07-15T...",
            "assets": [
                { "file": "build_key", "sha256": "..." },
                { "file": "bundles/Frontend__app.<hash>.js", "sha256": "..." },
                { "file": "bundle_models/Frontend_Bundle.json", "sha256": "..." },
                { "file": "manifest_index.php", "sha256": "..." }
                // ... every file under bundles/ and bundle_models/ ...
            ]
        }

    Asset paths are recorded relative to the build root, so the seal is
    self-contained and location-independent. The assets list covers
    manifest_index.php, manifest_files.php, the build_key file, every file
    under bundles/ and every file under bundle_models/ (the list of models
    each compiled bundle carries; rsx:man bundle_api).

    is_sealed() is true ONLY when a seal file exists AND the current RSX_MODE
    is a prod mode. That double condition means a leftover seal in a
    development checkout does not accidentally lock anything - dev is never
    sealed.

    created_at, git_commit, and the seal file as a whole are deliberately
    NOT part of any hashed build artifact. They carry the non-deterministic
    build metadata (a timestamp, a machine's git state) that the build
    artifacts intentionally exclude for byte-stability. The seal describes
    the build; it is not itself an input to the build hash.

THE DEBUG VARIANT
    debug is the "readable production" build. Relative to strict production:

        - NOT minified. The shipped JS/CSS is the compiled-but-readable
          source.
        - Inline sourcemaps SURVIVE. There is no separate sourcemap toggle:
          the compiler never adds maps, it only removes the inline
          sourceMappingURL comments carried by the source, and that removal
          happens exclusively inside minification. Since debug does not
          minify, the maps ride along.
        - console_debug() WORKS. The console_debug config block is injected
          into window.rsxapp (so the browser function has its channel
          configuration) and the call sites are NOT stripped from the
          bundle.

    Everything else matches production: it is a sealed, immutable build with
    no auto-rebuild, and external assets are mirrored locally. Build it with
    rsx:prod:enable --debug (or rsx:mode:set debug).

STRICT PRODUCTION
    Strict production is the fully optimized build. Relative to debug:

        - Minified (Terser for JS, cssnano for CSS, via the minify RPC
          server). Class and function NAMES survive minification
          (keep_classnames / keep_fnames): the runtime resolves jqhtml
          components and SPA actions by a class's own .name, so a minifier
          that renamed one would leave every action rendering as an empty
          default component. The browser's class registry
          (Manifest._define) refuses a class whose runtime name is not its
          manifest name, so a rename is a boot failure naming the class,
          never a blank page.
        - Inline sourcemaps are GONE (minification strips the
          sourceMappingURL comments - the "no minify, no maps" truth stated
          above, run forward).
        - App strings are OBFUSCATED (config rsx.production.obfuscate_strings,
          default true; see STRING OBFUSCATION below).
        - console_debug() is neutralized two ways at once:
            1. Call sites are STRIPPED from the compiled output. The minify
               RPC request carries a strip flag (driven by
               Manifest::_should_strip_console_debug()); Terser treats
               console_debug and Debugger.console_debug as pure functions
               (pure_funcs) and deletes the calls.
            2. The console_debug config block is omitted from
               window.rsxapp, so even a call site that survived (there are
               none in app bundles) would no-op at runtime.
        - console.log() call sites are STRIPPED from each bundle's APP
          output by the minifier itself (Terser pure_funcs 'console.log',
          the minify RPC's strip_console_log flag, set for the app output
          only). A dropped call keeps any side-effecting argument -
          console.log(n++) still increments - and a call whose return value
          is used survives. console.error / warn / info are untouched, and
          the VENDOR output keeps its console.log calls. There is no runtime
          check: the calls are simply absent from the shipped file.

STRING OBFUSCATION
    A strict-production step on each bundle's APP JavaScript, run on the
    ORIGINAL SOURCE of each eligible file, before babel; the rewritten copy is
    then babel-transformed where the file is transformed at all, concatenated
    and minified - never the vendor file, never CSS, never a debug or
    development build. Switch: config('rsx.production.obfuscate_strings'),
    default true.

    It deters CASUAL READING of the shipped file and nothing more. Rendered
    text still lands in the DOM, and the dictionary is readable by anyone
    who looks, so business rules and secrets stay server-side - always.

    Eligible files. The MANIFEST draws the boundary, file by file:

        - ES6 class files: a JS file the manifest's JS class index names as
          the file declaring its class;
        - generated MODEL stubs (Base_<Model>) and the generated concrete
          model classes (class X_Model extends Base_X_Model {});
        - compiled jqhtml templates.

    Nothing else is touched: JS files that declare no class, controller/Ajax
    and auth stubs, npm shims, the generated config, manifest, route and
    runner files, CDN and vendor code. Because the pass reads the source, a
    class field is still a field when it is judged (babel later lowers an
    instance field into the constructor), and babel's own injected helpers
    are never touched. A rewritten copy is transformed uncached: the babel
    transform cache only ever holds a source file's own bytes.

    Scope within an eligible file. Only strings lexically inside a FUNCTION
    BODY: methods, getters, setters, constructors, plain functions, arrows
    and template render functions, nested to any depth. The nearest
    enclosing boundary decides, so these stay literal: the top-level
    statements of the file, class field initializers (instance and static,
    e.g. static __MODEL = 'Project_Model'), static blocks, decorators and
    their arguments, member names, extends expressions and parameter lists
    (defaults included).

    Logging first. Before any word is collected, a console.log(...) or
    console_debug(...) call that is a whole statement is REMOVED from the
    eligible file - anywhere in it - so the text it would have logged never
    reaches the dictionary and no printer call is left where the minifier
    would later have dropped the log. An argument that may have an effect is
    kept (console.log(n++) becomes void (n++);, and a string inside a kept
    argument converts like any other); a statement with nothing to keep
    becomes ;. A call whose value is used, and every other console method,
    is left alone. The minifier still strips console.log and console_debug
    from every app file, eligible or not.

    Which strings, within that scope:

        (a) a string with an INNER space - a U+0020 with a non-space
            character before it and after it ('Save changes', '  a b ');
            leading and trailing spaces ride along once an inner one exists;
        (b) EVERY string that is a value in an object literal or an element
            of an array literal (nested literals included), whatever its
            length - a single word and '' included.

    A non-computed object KEY converts only under (a), and then becomes a
    computed key ({[_$$(4,9)]: 1}). A template literal's static parts
    convert under (a) part by part, each rewritten as a ${...} substitution
    so the template evaluates to the identical string; a template that is
    itself an object value or array element converts every non-empty part.
    Never touched: directive prologues ('use strict'), tagged templates,
    import sources. A single word in a function that is not literal data
    ('id', 'click') stays literal.

    Words and dictionary. A converted string is split on exactly one space;
    a word is everything between single spaces (punctuation, tabs and
    newlines included), and leading, trailing or doubled spaces produce
    empty words, so joining with ' ' reproduces the original byte for byte.
    The words of EVERY eligible file in the bundle form ONE dictionary:
    sorted, then shuffled by a PRNG seeded with the sha256 of the sorted
    list - identical input gives byte-identical output (the DETERMINISM
    CONTRACT holds), any change to the word set gives a fresh order.

    Runtime. A generated helper file declares three true globals at the
    top level of the classic app script, so every later script sees them
    and Terser never renames them:

        var _$$SC = [ ...words ];      the dictionary
        function _$$(...indexes)       the indexed words joined by ' '
        function _$$R(index, count)    `count` copies of one index

    It is concatenated DIRECTLY BEFORE the first eligible file in output
    order, so the dictionary exists before any converted string can run.
    Each converted string becomes a call: 'Save your changes' -> _$$(3,55,27).
    A run of three or more identical consecutive indexes - typically the
    empty words a template's indentation splits into - is spread from one
    repeat call: _$$(6,..._$$R(12,40),9).
    A rewritten file keeps every other byte and its line count. When
    nothing in the bundle converts, no helper is emitted and no file
    changes.

    Collisions. An identifier _$$SC, _$$ or _$$R already present in any of a
    bundle's app files or in its vendor JavaScript FAILS the build, naming
    the bundle, the identifier and the file. All three names are reserved: never
    declare them.

    Source: Core/Bundle/resource/string-obfuscation-service.js (the whole
    transform), called once per app compile through
    Minifier::obfuscate_strings(); BundleCompiler::_string_obfuscation_eligible()
    selects the files and _obfuscate_sources() babel-transforms the copies
    (Js_Transformer::transform_derived_copy()).

ENVIRONMENT VALIDATION
    There is none, and there is nothing to validate. app.env and app.debug
    derive from RSX_MODE (see DESCRIPTION), so setting RSX_MODE=production IS
    setting the production environment with debug off.

DETERMINISM CONTRACT
    A sealed build is deterministic: two byte-identical codebases, checked
    out at DIFFERENT paths and built in the SAME mode, produce an IDENTICAL
    build_key and IDENTICAL bundle filenames, byte-for-byte. This is what lets a build be
    compiled once and trusted across a cluster (or cached by CI keyed on the
    build_key), and it is what makes the CI-artifact and container-image
    recipes in rsx:man prod honest.

    How it holds:

    1. File hashing branches on RSX_MODE (_rsx_file_hash_for_build), which
       is the only mode switch there is. In a prod mode the hash is over
       the file's PROJECT-RELATIVE path plus its CONTENT (sha512), never the
       absolute path and never disk timestamps. The same logical file at two
       different checkout locations therefore hashes identically. (The
       development branch still uses a fast project-relative-path + size +
       mtime hash - it only needs to notice local edits, and is deliberately
       not portable. The path is relative there too: base_path() sits above
       symlinks to the application and volatile trees, so an absolute path
       would give one file two identities. That fast hash keys derived
       caches and bundle filenames; it never reaches build_key, which is
       content-derived in every mode - see 2.)

    2. The manifest hash excludes per-file mtime/size. Those still live in
       the cache file (dev change-detection needs them) but are OUT of the
       hashed projection. The prod cache file also drops the "generated"
       timestamp and its comment (that timestamp moved to the seal). The
       top-level SECTION map is ksorted at save, so a cold build and an
       incremental one emit the same sections in the same order rather than
       in the order each happened to produce or inherit them. So the
       manifest index produced by two identical checkouts is byte-stable,
       and build_key (the manifest hash) is content-derived. An mtime change
       alone therefore never moves the key.

    3. The MODE is part of build_key. One tree builds three different
       artifacts (development, debug, production), and the key is what
       identifies the build to the full-page cache and - combined with the
       applied migrations into the STATE key (rsx:man migrations, A MIGRATION
       NEVER REBUILDS) - to the build-scoped RsxCache prefix,
       window.rsxapp.build_key and the development asset cache-buster - so
       the same tree keys differently in each mode, and a
       development build after rsx:prod:disable never answers with the
       sealed build's key. The index records the mode it was built in, and
       a development boot that loads an index recorded under another mode
       discards it and rebuilds in full.

    4. Generated-file keys in the manifest index are LOGICAL, not absolute.
       A generated stub is recorded as tmp/js-stubs/<name>.js whatever
       RSX_TMP_PATH resolves to on the building box, so two boxes with
       different tmp roots produce identical indexes and identical build
       keys.

    5. Bundle filenames are {Bundle}__{app|vendor}.{hash8}.{ext}, where the
       hash8 derives from the same relative-path + content inputs (plus the
       committed lockfile content hashes and npm declarations, already
       deterministic). Minified output is reproducible given the pinned,
       committed node_modules.

    Bonus: because build_key is content-derived and stable across checkouts
    (in one mode),
    the full-page cache keys (fpc:{build_key}:{host}:{...}) are cluster-shareable -
    two nodes on the same build hit the same FPC entries.

GUARDS
    A sealed build is protected by developer GUARDRAILS - not a security
    boundary (see WHAT THE GUARDS DO NOT COVER). They exist to stop a
    developer from accidentally diverging or destroying the build.

    Permission to write the build tree is a property of the PROCESS - the
    BUILD CONTEXT - not of a flag anybody can pass or an environment
    variable. rsx:build declares itself a build context from the first line
    of boot (recognised from argv, so it holds before any handler runs) and
    carries it to every subprocess as a framework-internal flag; rsx:clean
    declares one too, because discarding the tree is its job. A web request,
    a plain artisan command or a tinker session is never a build context.

    The guards:

        Every framework write into build/ passes Rsx_Project_Paths::
        assert_build_writable(). In a prod mode, outside a build context, it
        throws:
            "<context>: '<path>' is a build artifact, and only a build may
            write it."
        It keys on the MODE first, so a seal is not required for it to
        refuse - an unsealed production box is a broken deployment, and
        letting an arbitrary command write into it is how it stays broken.
        A seal ON DISK refuses the write as well, whatever mode the process
        read at boot: the mode is memoized per process, and a web request
        that began under development and is still running after
        rsx:mode:set prod wrote the seal would otherwise compile with
        development semantics into the sealed tree (the refusal says so).
        In development with no seal on disk it is a no-op.

        Manifest::init() refuses to boot in a prod mode when the manifest
        index or the seal is missing:
            "This production build is unsealed. Run: php artisan rsx:build
            --force. See rsx:man prod."
        The exceptions are the commands that repair the box - rsx:build and
        its children, the mode transitions, rsx:clean, rsx:man, and the bare
        introspection invocations.

        rsx:clean and rsx:build refuse without --force in a prod mode.

        Only the build phase may download an external asset into the mirror
        in a prod mode.

    The ONLY sanctioned way to change a sealed build is to run the build
    again (rsx:build --force) or to leave the mode (rsx:prod:disable).

WHAT THE GUARDS DO NOT COVER
    The guards are guardrails, not a security boundary. They intercept the
    framework's OWN write paths. They do NOT (and cannot) stop a developer
    or process that goes around the framework:

        - Raw filesystem meddling: `rm -rf build/`, editing a bundle file by
          hand, `cp` over manifest_index.php. Nothing at the framework layer
          sees these.
        - Direct database writes (DB::table()->update(), raw SQL) or manual
          data changes.

    The analogy is the realtime model layer: model save()/delete() emit
    change notifications, but a raw DB::table() write bypasses the model and
    emits nothing - by design. The seal guards the framework's write
    choke points the same way; go under them and you are on your own.
    rsx:prod:verify is the backstop that DETECTS such drift after the fact
    (recomputed asset hashes will not match the seal).

    The OS-level answer is the read-only posture in rsx:man prod: system/,
    rsx/ and build/ owned by the deploy user and read-only to the web user.

BUNDLE OUTPUT
    Bundles are ALWAYS emitted as a vendor/app split, in every mode:
        build/bundles/{Bundle}__app.{hash8}.{js|css}
        build/bundles/{Bundle}__vendor.{hash8}.{js|css}

    There is no single-file merge. Merging all of a bundle's JS (or CSS)
    into one file is a deferred idea, not a current behavior - do not expect
    a merged app.js/app.css.

    The emission ORDER inside a bundle is a load-bearing contract:
    files are emitted in declared include order, class stubs sit at their
    include position, and aliases are spliced in after the stubs. This
    ordering exists to avoid temporal-dead-zone reference errors in the
    concatenated output.

EXTERNAL ASSET MIRRORING
    THERE IS NO DEVELOPMENT EXCEPTION. Every mode mirrors every external
    asset into the application's own store and serves it from /_vendor/ -
    a development box behaves exactly like a sealed build. What is mirrored:

        - Every bundle cdn_assets entry (Bootstrap, jQuery, ...).
        - Every mirror:true *.externals.php entry.
          See: php artisan rsx:man external_resources
        - Every remote reference INSIDE compiled CSS: a @import url(https://...)
          in application SCSS, an absolute url() for a font or an image, and
          the @font-face files a downloaded stylesheet itself points at. A
          remote @import is spliced in place, recursively, preserving its
          media/supports/layer prelude.

    Left alone: data:, fragment-only, root-relative and relative references.
    (A relative url() in application SCSS is handled by nothing - it resolves
    against the compiled bundle's own URL, as it always did.)

    THE STORE
        rsx/resource/.cdn-cache/, one flat directory of files named
        <md5(url)>_<safe basename>.<ext> and served from
        /_vendor/<that filename>. It is COMMITTED TO GIT - not under a
        volatile tree - so it survives rsx:clean and mode switches, and CI
        builds are reproducible. It is URL-keyed: a present file is by
        definition the right file, nothing expires on its own, and a compile
        only ever ADDS. Commit the files a compile adds; git status shows
        them.

    WHO DOWNLOADS
        Development web requests, any development CLI invocation, and the
        build's own "Mirroring external assets" step. Externals need that
        dedicated step because nothing renders them at build time - the
        client loads them at runtime by identifier.

        IN A PROD MODE ONLY THE BUILD MAY DOWNLOAD. A sealed web request
        never does: a miss THROWS, naming the file, the store directory and
        rsx:build. A miss in development is a 404 naming
        rsx:cdn_externals:refresh (the compile that names the file never ran
        on this box, or the store was emptied).

    FAILING LOUD
        An unfetchable reference FAILS THE COMPILE, naming the URL - a
        stylesheet's references with a JSON failure list. A declared integrity
        hash is verified against the downloaded bytes in every mode and a
        mismatch throws. A production SCSS compile whose postcss pass fails
        now fails too, rather than shipping un-optimized CSS.

    THE ONE EXPIRY
        php artisan rsx:cdn_externals:refresh - empties the store and
        rebuilds, which is what makes the store complete again.

    CSP
        A mirrored asset contributes NOTHING to the policy in any mode: it is
        same-origin, which 'self' already covers. Only mirror:false entries put
        an origin in the header. See: php artisan rsx:man csp

    Mirrored assets are served SEPARATELY via /_vendor/ URLs. They are NOT
    merged or inlined into the compiled bundle files. Cache filenames derive
    from a hash of the URL, so a version bump in a bundle definition creates
    a new cache file and stops referencing the old one - no manual
    invalidation.

WINDOW.RSXAPP ACROSS MODES
    The console_debug config block is injected into window.rsxapp in
    development AND debug (this is what makes browser console_debug() work in
    debug mode). Strict production omits the block entirely.

    ajax_batching is always present but mode-dependent:
        - development: false (direct calls for easier debugging)
        - debug / production: true (batched calls for efficiency)

    Core functionality (user, site, csrf, params, etc.) is present in all
    modes.

ENV FACTS VS INVOCATION FLAGS
    RSX_MODE is a deployment ENVIRONMENT fact and lives in .env. It is NOT
    an invocation parameter. When a mode-transition command spawns the build
    subprocess, it writes RSX_MODE to .env FIRST and also syncs the value
    into the running process (putenv + $_ENV + $_SERVER + the mode cache) so
    the child - which inherits the parent's environment and whose Dotenv
    will not override an already-set var - boots on the correct mode. Without
    that sync an enable launched from a development parent would spawn a
    build that runs unminified and unstripped.

    Per-invocation intent is a --flag, never an env prefix. Do NOT prefix
    invocations with KEY=VALUE. This is an owner ruling; see the CLI
    invocation parameters note in Core/CLAUDE.md.

        WRONG:  SOMETHING=1 php artisan rsx:build
        RIGHT:  php artisan rsx:build --force

ENV FILE PREPARATION (.env.dist -> .env)
    .env is LOCAL configuration and is never distributed. .env.dist at the
    PROJECT ROOT is the tracked, hand-curated canonical defaults, and is the
    only file a missing .env is created from (whole-file, verbatim).
    system/.env.dist NEVER seeds a .env - it feeds the key sync only. A
    project with no root .env.dist refuses to boot in development and names
    the recovery: cp system/.env.dist .env.dist

    On every DEVELOPMENT boot, keys - never values - propagate downhill:

        system/.env.dist  ->  .env.dist  ->  .env

    A key missing from the lower file is appended verbatim under a dated
    marker; a key already present is left exactly as it is, whatever its
    value. Nothing is overwritten, deleted or reordered. Consequently a
    setting is switched off by setting it EMPTY (SOME_FEATURE=): a deleted
    line is a missing key, and the next boot restores it.

    The same pass requires DB_HOST, DB_DATABASE, DB_USERNAME, DB_PASSWORD and
    REDIS_HOST to be PRESENT in .env (the first three non-empty; an empty
    DB_PASSWORD and a passwordless Redis are legal), and mints an APP_KEY when
    there is none - IN DEVELOPMENT ONLY. Outside development an empty APP_KEY
    is refused, because a new key silently invalidates every encrypted value
    and signed cookie made with the one that went missing.

    ENCRYPTED ENV. Laravel's environmentPath() is anchored at the PROJECT ROOT
    (bootstrap/app.php), so env:encrypt, env:decrypt and key:generate all
    operate on the root .env and write .env.encrypted beside it - never inside
    system/, which every framework pull resets and cleans. env:decrypt reaches
    the root through App\RSpade\Commands\Rsx\Env_Decrypt_Command, which
    overrides the stock base_path() output default.

    If .env.encrypted is present and .env is ABSENT, the heal THROWS in every
    mode and names env:decrypt. It never creates a .env from .env.dist over an
    encrypted one: the box would boot looking configured while its real
    configuration sat encrypted one filename away. With both present, .env
    wins and the heal proceeds normally - but .env.encrypted is a snapshot
    that nothing keeps in step, so rsx:health WARNs about one sitting on a
    development box.

    ONE implementation - App\RSpade\Core\Prod\Rsx_Env_Symlink::full_heal() -
    behind rsx:env:heal, both entrypoints pre-boot (via
    bootstrap/rsx_env_heal.php) and the container entrypoint. Development runs
    it on every boot; the cost when nothing has changed is one stat against
    tmp/env_heal.stamp. Outside development it runs only when .env is absent.

ENV FILE INVARIANT (.env SYMLINK HEALER)
    RSX_MODE, and every other configuration key, is read from ONE
    authoritative file: the project-root .env
    (dirname(base_path())/.env; httpdocs/.env in deployed layouts).

    Laravel/Dotenv loads that root file DIRECTLY: bootstrap/app.php calls
    useEnvironmentPath(<project root>), so environmentPath() is the root and
    environmentFilePath() is the root .env.

    system/.env remains, as a SYMLINK to the root .env, because bash readers
    still address it by name (the container entrypoint, the pull script) and
    because the prod-mode env writer (Rsx_Prod_Env) reads/writes only
    base_path('.env'). The invariant is what makes those two spellings one
    file.

    Drift: a deploy or clone frequently MATERIALIZES the symlink into a real
    file. After that the two files diverge, and every writer addressing
    system/.env is writing somewhere Laravel no longer reads. A naive
    re-symlink would instead DISCARD keys that live only in system/.env.

    Healer: rsx:env:heal restores the invariant safely (as part of the full
    env preparation described above).

        php artisan rsx:env:heal            # heal now
        php artisan rsx:env:heal --dry-run  # report SYMLINK drift only

    Merge rule (root is authoritative): keys unique to system/.env are
    APPENDED to the root .env under a dated marker; keys present in BOTH with
    different values keep the ROOT value and REPORT each discarded system/.env
    value; the root file's existing lines are preserved byte-for-byte;
    system/.env is then replaced by a relative symlink (../.env). Before a
    real system/.env is replaced, a 0600 backup is written beside it
    (system/.env.replaced_by_healer; gitignored).

    It runs automatically after every framework pull, at the start of
    rsx:clean, and FIRST in every mode transition so the RSX_MODE write lands
    in the single healed file.

ERROR HANDLING
    In prod modes, missing build artifacts fail loud rather than triggering
    a JIT rebuild. The full error catalog, with remedies, is in rsx:man prod.
    The two most common:

        "This production build is unsealed."
            The manifest index or the seal is missing.
            Fix: php artisan rsx:build --force

        "Bundle 'X' not compiled for production mode"
            A bundle is missing while sealed.
            Fix: php artisan rsx:build --force
