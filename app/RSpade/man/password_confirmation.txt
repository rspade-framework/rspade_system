NAME
    password_confirmation - "confirm it's you" before a sensitive action

SYNOPSIS
    Before a button that adds or removes a way into the account:

        if (!await Password_Confirmation_Modal.require()) return;   // the app's dialog
        await Rsx_Two_Factor_Controller.recovery_regenerate();

    At the top of an endpoint of your own that needs the same protection:

        Rsx_Password_Confirmation::require_confirmed();

    When the user leaves the screen that asked:

        on_stop() { Rsx_Password_Confirmation.clear(); }

DESCRIPTION
    A signed-in session is not proof that the person at the keyboard owns the
    account: a session can be stolen, or a browser left signed in. Whoever holds
    it could register their own passkey, link their own federated account, or
    mint an API key - and a session that would have expired in a week becomes
    permanent access the owner cannot see.

    So the actions that add or remove a way into an account ask for the
    account's password again (or one of its passkeys) first. The user is still
    signed in throughout; the confirmation lasts a few minutes and is given up
    when they leave the screen.

    The FRAMEWORK owns the rule and the check: the confirmation, its lifetime,
    the endpoints that give it, the form that collects it, and the enforcement on
    its own sensitive endpoints. The APPLICATION owns the experience: the dialog,
    how many tries a user gets, which of its own actions are gated, and when the
    confirmation is given up.

    Laravel's password.confirm middleware is the nearest equivalent. RSpade's is
    an Ajax-native session value with an app-owned dialog and no redirect.

WHAT IS GATED
    The framework's own endpoints, staff and portal alike, refuse without a live
    confirmation:

        Rsx_Two_Factor_Controller / Rsx_Portal_Two_Factor_Controller
            totp_begin, totp_confirm, passkey_register_begin,
            passkey_register_confirm, credential_remove, recovery_regenerate
        Rsx_Sso_Controller / Rsx_Portal_Sso_Controller
            link_begin, identity_unlink

    An application gates its own sensitive endpoints the same way (the template
    gates minting an API key). Changing the password is not gated: that form
    already asks for the current password.

    The facades (Rsx_Two_Factor, Rsx_Sso, ...) do not ask. A command, a task or
    server code acting on an identity is not a browser session that could have
    been stolen; the requirement belongs to the web endpoints.

THE CONFIRMATION
    A session value (Session::put_value(), realm-tagged) naming the identity it
    was given for, alive rsx.sessions.password_confirmation_minutes (5) from the
    moment it was given. It is:

        - for ONE identity: another sign-in on the same browser does not hold it;
        - for ONE realm: a staff confirmation is not a portal one;
        - ended by clear(), by the realm's sign-out, and by its expiry;
        - never given or honoured while impersonating - the person acting does
          not hold the account's password.

    The browser holds the same lifetime in memory (Rsx_Password_Confirmation.js)
    so a page knows whether to ask. The server is the authority: a gated endpoint
    reached after expiry refuses with "Your password confirmation has timed out.
    Refresh the page and try again." and the user starts over.

API - PHP (App\RSpade\Core\Confirmation\Rsx_Password_Confirmation)
    Every method answers for the request's experience (staff or portal).

    require_confirmed(): void
        The first statement of a gated endpoint. Throws AjaxFormErrorException -
        an ordinary validation error - while impersonating, and when the identity
        has not confirmed or its confirmation expired (EXPIRED_MESSAGE).

    is_confirmed(): bool
    options(): array            {has_password, has_passkey, confirmed, minutes}
    confirm_password(string $password): bool
    passkey_options(): array    request args for navigator.credentials.get()
    confirm_passkey(array $assertion): bool
    clear(): void
    minutes(): int

    confirm_password() and confirm_passkey() are throttled first, against the
    account (rsx:man session, LOGIN THROTTLE): they throw
    Auth_Throttled_Exception when it is over the limit, and a refused password or
    passkey is recorded as a sign-in failure for the account, which feeds the
    throttle. A passkey confirms only when it is one of the signed-in identity's
    own.

    $force_confirmed_for_tests: set true in a test whose subject is a gated
    ENDPOINT, null afterwards. Nothing else may set it.

API - THE ENDPOINTS (Rsx_Password_Confirmation_Controller)
    #[Auth('is_logged_in')], #[Auth_Realm('any')], in every bundle.

        options()               {has_password, has_passkey, confirmed, minutes}
        verify({password, __turnstile})
                                Turnstile first, then the password.
                                {confirmed: true, expires_in_seconds}
        passkey_options()       request args for the passkey prompt
        verify_passkey({assertion})
                                {confirmed: true, expires_in_seconds}
        clear()                 {cleared: true}

    Every refusal is a form error with a user-safe message.

API - JAVASCRIPT (Rsx_Password_Confirmation)
    status()            'confirmed' or 'required' (STATUS_CONFIRMED /
                        STATUS_REQUIRED), from the in-memory lifetime
    is_confirmed()      true while this page holds a live confirmation
    verify(params)      confirm with {password, __turnstile}; resolves true,
                        rejects with the Ajax error on a refusal
    verify_passkey()    the browser's passkey prompt, then the server; resolves
                        true, false when the user dismissed the prompt, rejects
                        on a refusal
    clear()             give it up here and on the server

THE FORM - <Password_Confirmation_Form>
    An <Rsx_Form> posting to Rsx_Password_Confirmation_Controller::verify: the
    password (a <Password_Input>), <Turnstile_Input /> and <Form_Errors />, plus
    "Use a passkey instead" when the account holds a passkey and the browser can
    run one. What it shows follows options(); an account with neither a password
    nor a passkey gets a notice.

        Event 'confirmed'   the confirmation was given (password or passkey);
                            Rsx_Password_Confirmation.is_confirmed() is now true.
        submit()            submit the password; resolves true when confirmed,
                            false on a refusal it has already rendered.

    Restyle with rules on .Password_Confirmation_Form; the inputs are Bootstrap
    form controls.

THE APPLICATION'S DIALOG
    The framework ships no dialog. The template's is Password_Confirmation_Modal
    (rsx/lib/password_confirmation/), the worked example:

        static async require() {
            if (Rsx_Password_Confirmation.is_confirmed()) return true;
            // Modal.show() hosting <Password_Confirmation_Form>; Confirm calls
            // form.submit(); the form's 'confirmed' event (a passkey) closes it;
            // three refused passwords close it with a notice; resolves true/false.
        }

    Gate a button by awaiting require() before the call, as
    reference_app/app/frontend/settings/password_security/
    settings_password_security_action.js does for every factor action.

    A component that calls a gated endpoint ITSELF (<Passkey_Register>,
    <Totp_Enrollment>, <Sso_Buttons $intent="link">) is shown only after the
    confirmation is given: reference_app/portal/settings/Portal_Settings_Security
    reveals them behind one "Add a sign-in method" button.

    Give the confirmation up when the user leaves: Rsx_Password_Confirmation.clear()
    from the screen's on_stop(). The server's expiry bounds it either way.

CONFIGURATION
    rsx.sessions.password_confirmation_minutes   5
        How long a confirmation lasts. A security window, not an operation
        timeout: its expiry means the password is asked for again.

TROUBLESHOOTING
    "Your password confirmation has timed out. Refresh the page and try again."
        A gated endpoint was called with no live confirmation: the page did not
        ask first (gate the button with the dialog), or the user took longer than
        the configured minutes between confirming and acting.

    The confirmation dialog shows no password field.
        The account has no password (an SSO-only or invited account) - it can
        confirm with a passkey, or not at all here.

    "You're doing that too fast" in the dialog.
        The sign-in rate limit for this account or address (rsx:man session,
        LOGIN THROTTLE).
