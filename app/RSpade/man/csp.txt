NAME
    csp - the framework's Content-Security-Policy: one composed policy per
    realm, derived from declarations

SYNOPSIS
    # system/config/rsx.php (framework defaults; override in rsx/resource/config/rsx.php)
    'csp' => [
        'enabled'            => true,   # emergency kill-switch
        'additional_sources' => [],     # TRANSITIVE origins only
    ],

    # What a staff page carries out of the box:
    Content-Security-Policy: default-src 'self'; script-src 'self'
    'nonce-...'; style-src 'self' 'unsafe-inline'; img-src 'self' data:;
    font-src 'self' data:; connect-src 'self' wss://host ws://host;
    object-src 'none'; base-uri 'self'; frame-ancestors 'self';
    report-uri /_csp-report

    # Triage a blocked resource:
    tail -f storage/logs/csp_violations.log

DESCRIPTION
    A Content-Security-Policy tells the browser what a page is allowed to load
    and execute. It is the single most effective mitigation for cross-site
    scripting: an injected <script> that the policy does not permit simply does
    not run, whatever bug let the markup in.

    RSpade ships one, on every dispatched page, with no wiring. It is COMPOSED,
    not written: the framework's own hardened directives, plus the origins of
    every DECLARED external resource for that realm, plus a per-request nonce
    for the framework's inline scripts. There is no policy string to maintain
    and no middleware to register - and because the external origins derive
    from *.externals.php declarations, the policy cannot drift from the code.
    See: php artisan rsx:man external_resources

    IT ENFORCES. There is one header name and one behavior: a resource the
    policy does not permit is BLOCKED, in every mode, in every install. An
    undeclared external therefore fails visibly the first time somebody loads
    the page, which is the point - a policy nothing enforces protects nothing.
    Every refusal is still reported to /_csp-report, so the violation log is
    the tool you triage a blocked resource with. See TRIAGE.

    ONE POLICY PER REALM, ONE COMPOSER. Staff and portal pages get their own
    composed value from the same class, so a portal-only widget never widens
    the staff policy.

WHAT SHIPS
    Header name        Content-Security-Policy. Always. There is no
                       observe-only mode and no second header name.

    Where it is set    The DISPATCHERS, not Kernel middleware:
                       Dispatcher::__transform_response (staff) and
                       Portal_Dispatcher::__build_response (portal). Every
                       dispatched response funnels through those two points -
                       native routes, SPA bootstraps, error screens, redirects.

    What carries it    HTML responses only. A declared text/html type, or no
                       declared type at all (a plain response($string) has not
                       been prepared yet and will default to text/html; every
                       non-HTML producer in the framework sets its type). A
                       JSON envelope, a download or a rendition carries no
                       policy - a policy governs what a DOCUMENT may load.

    Never overwritten  A response that already carries a Content-Security-
                       Policy keeps it (AssetHandler's static-HTML responses
                       set their own).

    Out of scope       Anything that never reaches an RSX dispatcher: vendor
                       error pages, the ignition development error screen, and
                       any non-dispatcher response. By design, not by accident.

THE COMPOSED DIRECTIVE SET
    Base (Rsx_Csp::_base_directives)

        default-src      'self'
        script-src       'self' 'nonce-{request nonce}'
        style-src        'self' 'unsafe-inline'
        img-src          'self' data:
        font-src         'self' data:
        connect-src      'self'  [+ wss://{host}, + ws://{host} outside strict
                                  production, when realtime is enabled]
        object-src       'none'
        base-uri         'self'
        frame-ancestors  'self'
        report-uri       /_csp-report

    'unsafe-inline' NEVER appears in script-src. Framework inline scripts carry
    the nonce instead.

    NO NONCE IN STYLE-SRC, DELIBERATELY. A nonce present in style-src makes
    browsers IGNORE 'unsafe-inline' - and RSX depends on inline styles
    pervasively (jqhtml, view transitions, every style="" attribute in the
    tree, vendor-injected <style> elements). Adding one would break rendering
    everywhere in exchange for very little: style injection is not script
    execution. So style-src keeps 'unsafe-inline' and no nonce.

    connect-src's websocket entries mirror the client exactly: the canonical
    URL handed to the browser is wss://, and Rsx_Realtime downgrades it to
    ws:// whenever the PAGE itself is plain http (loopback, the rsx:debug
    harness) - possible in every mode except strict production, where http is
    not served. So ws:// is whitelisted outside strict production only.

    Merged in, in this order:

    1. ASSET ORIGINS THIS RESPONSE ACTUALLY EMITTED. In development a bundle's
       cdn_assets load from their own hosts; the emitter declares each one as
       it writes it (Rsx_Bundle_Abstract -> Rsx_Csp::note_asset_origin), so the
       whitelist is EXACTLY what this page loads and never a superset. In a
       sealed build those assets are served from /_vendor (same-origin) and
       contribute nothing.

    2. DECLARED EXTERNAL RESOURCES for the realm
       (Rsx_Externals::csp_hosts_for_realm): each entry's js origins into
       script-src and css origins into style-src - but only while still fetched
       externally, so a mirrored entry drops out of a sealed build's policy -
       plus each entry's own `csp` extras (the frames it opens, the hosts it
       calls), which apply in EVERY mode.

    3. AN EXTERNAL STYLESHEET'S ORIGIN ALSO JOINS font-src, derived rather than
       configured. A webfont stylesheet @font-face's against its own origin as
       a matter of course, and nothing in our code names the font file - so
       without this every icon font would report a violation no declaration
       could fix. An origin already trusted to deliver CSS (which can restyle
       the whole page) is trusted for the fonts that CSS names.

    4. CONFIG rsx.csp.additional_sources, WIDEN-ONLY. Sources are APPENDED;
       they can never replace or remove the framework's hardening, and
       downstream config deep-merges additively on top. A directive the base
       policy did not declare is CREATED seeded with 'self' (it was falling
       back to default-src 'self'; adding one host must not silently narrow the
       page's own same-origin allowance).

       object-src is REFUSED outright, loudly. It is set to 'none' as
       hardening, and appending to "nothing" would loosen it while reading like
       an addition.

    ADDITIONAL_SOURCES IS FOR TRANSITIVE EXTERNALS ONLY. A declared script that
    goes on to load FURTHER scripts from origins the vendor picks at runtime
    (an analytics or tag-manager loader is the classic case) cannot be
    enumerated by any declaration. That is what this key is for. A resource the
    PAGE loads directly belongs in a *.externals.php declaration, where the
    whitelist derives from it automatically.

THE NONCE
    Rsx_Csp::nonce() mints 18 random bytes, base64-encoded, ONCE per request
    and memoizes them. Every framework emitter of an inline <script> stamps the
    same value the header carries:

        - Rsx_Bundle_Abstract's window.rsxapp bootstrap script.
        - Debugger's shutdown-time console echo, which has no Response object
          to read a header from - which is exactly why the nonce is a static
          and not a header lookup.

    IT IS EXPORTED to the browser as window.rsxapp.csp_nonce, and the external
    resource loader stamps it onto every <script>/<link> it appends. Page code
    never reads it: if you find yourself wanting the nonce, you are about to
    hand-inject something that belongs in a declaration.

    _reset_request_state() drops the nonce and the noted asset origins. It is
    the TESTING seam - a PHP test process is one long request, so a test
    asserting nonce stability and one asserting a fresh nonce must be able to
    draw the line themselves.

    FULL PAGE CACHE INTERACTION. An #[FPC] page's HTML is cached by the FPC
    proxy with its baked nonce inside it. On a cache HIT the proxy replays
    status, content type, ETag and body only - it does NOT replay the CSP
    header - so a cached public page is served with no policy at all, and the
    stale nonce in its body is inert. FPC pages are therefore outside the
    policy's coverage today; a public page whose protection matters should not
    be #[FPC], or the proxy must learn to cache and replay the header
    alongside the body.

THE COLLECTOR
    POST /_csp-report, served by Csp_Report_Controller, gate #[Auth('public')]
    (mandatory - the reporter is a browser acting on its own behalf, often on a
    page nobody is logged into) and CSRF-exempt at the Rsx_Csrf::enforce seam.

    It accepts both wire shapes: `application/csp-report`'s single
    {"csp-report": {...}} and the newer Reporting API's list of {type, url,
    body} envelopes. Each report is appended as ONE JSON line to

        storage/logs/csp_violations.log

    with a timestamp and the user agent. json_encode is what makes the line
    format safe - a report is attacker-influenced text and can never emit a raw
    newline.

    IT NEVER ERRORS. Every request answers 204, including a body that is not
    JSON (kept verbatim, truncated, under an `invalid` key). A collector that
    4xx'd would teach browsers to retry; one that threw would fill the
    application log with noise generated by whatever a page happened to load.

    IT REPORTS UNDER ENFORCEMENT. report-uri does not mean "observe": the
    browser blocks the resource AND posts the report. The log is therefore the
    permanent record of what the policy is refusing.

    NO TABLE IN v1. Triage is tail/jq over the file - a report is diagnostic
    exhaust, not application data.

    IT ROTATES WITH EVERYTHING ELSE IN storage/logs. csp_violations.log is an
    ordinary *.log, so the framework's own rotation takes it: generations
    csp_violations.log.1, .2.gz and so on, pruned at the retention edge. Triage
    older than the plain band means reaching for zcat. See rsx:man logrotate.

    DEPLOYMENT NOTE: the path is served by the STAFF dispatcher. With
    prefix-based portal detection a portal page posts here fine
    (/_csp-report is not under the portal prefix). An install serving its
    portal from a SEPARATE DOMAIN would need the same path routed there too.

TRIAGE
    A resource the page needs is blocked. The log is where you find out what
    and why:

        tail -f storage/logs/csp_violations.log

    Keep it open while adding a third-party widget, and read it after any pass
    over the application - one JSON line per refusal, naming the directive, the
    blocked URI and the document. Each line has exactly one correct fix:

      - A resource the page loads ITSELF -> declare it in a *.externals.php
        file and load it with Rsx.load_external().
      - An origin a DECLARED script fetches on its own ->
        rsx.csp.additional_sources.
      - An inline <script> in application markup -> move the code into a
        bundled .js file. Do not reach for the nonce.

    Summarize a log with jq:

        cat storage/logs/csp_violations.log | jq -r \
          '.report | "\(.["effective-directive"]) <- \(.["blocked-uri"])"' \
          | sort | uniq -c | sort -rn

    THE 'unsafe-eval' DECISION GATE. The framework ships NO 'unsafe-eval', and
    that is deliberate: adding it gives back a large part of what CSP is for.
    If triage shows script-src violations naming eval or a Function constructor
    from FRAMEWORK code, STOP and escalate - that is a framework-level
    decision, not an application one.

    JS-EVAL-01 IS THE GATE YOU CAN RUN BEFORE DEPLOYING. `php artisan rsx:check`
    flags eval() and new Function() in bundled JavaScript, so readiness is a
    command rather than a log-watching exercise. The rule matches BOTH
    constructs, because the browser reports them identically as
    `blocked-uri: eval` - a check that caught only eval() would call a page
    clean while it still violated.

    Nearly every instance is one thing: resolving a class from its NAME as a
    string, reached because RSpade classes are top-level `class` declarations
    (lexical bindings), so window['Task_Model'] is undefined and eval() is the
    first thing that appears to work. The supported API is a registry lookup:

        const cls = Manifest.get_class_by_name(name);   // the class, or null

    It executes nothing and cannot throw, so the identifier-guarding regex and
    the try/catch that usually surround an eval() go away with it.

    A dynamic import() needs no wrapper. The babel transform declares
    caller.supportsDynamicImport, so import(url) survives as native syntax;
    new Function('u','return import(u)') was the workaround for an older
    transform that rewrote it into a require() shim, and is now both unnecessary
    and a violation.

    In development the browser's own error is followed by an [RSX CSP] console
    warning naming the directive, the blocked URI and the remedy.

CONFIGURATION
    'csp' => [
        'enabled'            => true,
        'additional_sources' => [],
    ]

    enabled             False emits no header on any response, anywhere.
                        compose() returns null. An EMERGENCY KILL-SWITCH: it
                        deletes the protection, it does not quiet it. There is
                        no observe-only mode to fall back to.

    additional_sources  directive => [sources], merged widen-only. TRANSITIVE
                        externals only; object-src is refused. Downstream
                        config deep-merges additively, so an app's array widens
                        the framework's and never replaces it.

    See: php artisan rsx:man config_rsx

API REFERENCE
    App\RSpade\Core\Csp\Rsx_Csp

    nonce(): string
        This request's nonce, minted once and memoized.

    compose(string $realm): ?array
        ['header' => name, 'value' => policy] or null when disabled.
        $realm is 'staff' or 'portal'.

    apply_to_response($response, string $realm): void
        Stamp a dispatched response, subject to the HTML-only and
        already-has-a-policy rules above. Non-responses are ignored.

    note_asset_origin(string $directive, string $url): void
        Declare an external origin this response actually emitted an asset
        from. Called by the bundle emitter; application code never calls it.

    is_enabled(): bool
        The config read, in one place.

    _reset_request_state(): void
        Testing seam - drops the nonce and noted origins.

    Constants: REPORT_PATH, HEADER_ENFORCE, UNWIDENABLE_DIRECTIVES.

EXAMPLES
    Allowing a transitive origin (the only thing config is for)

        // rsx/resource/config/rsx.php
        'csp' => [
            'additional_sources' => [
                'script-src'  => ['https://www.google-analytics.com'],
                'connect-src' => ['https://www.google-analytics.com',
                                  'https://analytics.google.com'],
                'img-src'     => ['https://www.google-analytics.com'],
            ],
        ],

        The gtag.js SCRIPT URL is not listed here - it is declared in
        rsx/lib/analytics/analytics.externals.php and the policy derives from
        that. Only what gtag.js goes on to fetch at runtime lives in config.

    Reading the violation log

        tail -n 50 storage/logs/csp_violations.log | jq -r \
          '.report | "\(.["effective-directive"]) <- \(.["blocked-uri"]) on \(.["document-uri"])"'

RSX VS LARAVEL
    Laravel ships no Content-Security-Policy and has no opinion about one. The
    conventional approach is a middleware that concatenates a hand-written
    policy string, registered in the HTTP kernel, listing the hosts somebody
    remembered the application uses. It drifts the moment a developer adds a
    widget: the markup changes, the string does not, and the failure is a
    silently broken page in production.

    RSpade composes the policy from facts the framework already knows - the
    declared external resources for the realm, the assets this very response
    emitted, and its own inline scripts, which carry a nonce rather than
    'unsafe-inline'. There is no policy string in application code, and the
    only configuration is the transitive-origin escape hatch (plus an emergency
    kill-switch). The header is set at the DISPATCHER rather than in kernel
    middleware, so an app never registers middleware for it and a framework
    upgrade can improve the policy without touching app code. (app/Http/
    Kernel.php is framework-owned anyway; an app that does need middleware
    of its own declares it in config - rsx:man config_rsx.)

TROUBLESHOOTING
    A resource the page needs is blocked
        Do not edit a header - there is none to edit. Declare the resource:
        php artisan rsx:man external_resources. If it is a transitive load by
        a declared script, add the origin to rsx.csp.additional_sources.

    An inline <script> in a Blade page is blocked
        Move the code into a bundled .js file with a page guard. Application
        inline scripts are not nonce-stamped and never will be - the nonce
        exists for framework-emitted bootstrap markup.

    "Invalid csp.additional_sources directive 'object-src'"
        object-src is hardening set to 'none'; additional_sources can only
        append, which would loosen it. Nothing legitimate needs to widen it.

    A JSON / download response has no policy
        Correct. Only HTML documents carry one.

    An error page has no policy
        If it is an RSX error screen it does. Vendor and ignition error pages
        never reach the dispatcher and are out of scope.

    A public #[FPC] page has no policy
        Also correct today - the FPC proxy replays a cached body without the
        header. See THE NONCE, Full page cache interaction.

    Realtime will not connect
        connect-src covers wss://{APP_URL host} always and ws://{host} outside
        strict production. A host mismatch means APP_URL disagrees with the
        host being browsed - fix APP_URL, not the policy.

    Nothing is being blocked or reported at all
        Confirm csp.enabled is true, that you are looking at a DISPATCHED HTML
        page (view the response headers), and that storage/logs is writable.
