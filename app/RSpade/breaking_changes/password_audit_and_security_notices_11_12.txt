PASSWORD EVENTS: EVERY CHANGE REPORTED WITH ITS CAUSE, RECORDED ON THE USER'S HISTORY, AND ANNOUNCED BY A SECURITY EMAIL
Date: 2026-11-12

IF YOU DO NOTHING: every password change in your application now fires login_user.password.changed / portal_user.password.changed after it commits, but your own change paths state no cause, so the event reports 'unknown' - and with no handler of yours nothing is recorded, no reset link is ended on a change and nobody is told. One case breaks outright: a Login_User_Model or Portal_User_Model override that REDECLARES set_password(string $password) no longer matches the base's signature and fails to load (PHP "Declaration ... must be compatible"); add the second parameter (below).

SUMMARY
    Category 3. A password change is now an EVENT the framework fires from the
    identity model, so an application can audit and announce every change from
    one handler instead of from each controller:

      - the FRAMEWORK gained set_password($plain, $cause), the Password_Change
        cause vocabulary, and the actions login_user.password.changed /
        portal_user.password.changed {identity, cause, actor, audit_session_id,
        ip_address}, fired after the save commits;
      - the REFERENCE APPLICATION records every password change and every
        "Forgot your password?" request as an action-log row (with the address
        it came from) on every site of the identity, shows a user's history -
        what was done TO them as well as what they did - on the User Management
        view page, ends open reset links on ANY change, and mails a SECURITY
        "your password was changed" notice.

    Your /rsx/ receives none of the application half. Port what you want.

WHAT YOU ALREADY HAVE
    - Login_User_Model::set_password(string $password, ?string $cause = null)
      and the same on Portal_User_Model. $cause is a Password_Change::CAUSE_*
      value: self, reset_link, admin, forced_change, cli (unknown is what a
      save reports when none was stated); any other string throws
      InvalidArgumentException. The framework states forced_change (the forced
      change at sign-in) and cli (rsx:users:password:set) itself.
    - The two events. Fired from the model's `updated` hook through
      afterCommit(): inside a transaction they wait for the commit and a
      rollback drops them; creating an identity fires nothing. actor is the
      identity acting on the request (the impersonator while impersonating),
      null for a reset link, the forced change and a command. Store
      audit_session_id to say where a change came from (rsx:man session,
      PASSWORD CHANGES and AUDIT SESSIONS); rsx:man event_hooks lists both.
    - Login_User_Model / Portal_User_Model (likely-overridden): an override
      that EXTENDS the base inherits all of this. An override that redeclares
      set_password() must take the cause and keep the base's behaviour:

          public function set_password(string $password, ?string $cause = null): void
          {
              parent::set_password($password, $cause);
              // your additions
          }

      An override that redeclares booted() already chains parent::booted()
      (PHP-PARENT-CHAIN-01), which is where the event is wired.

WHAT IS MISSING IN YOUR APPLICATION
    - Your change paths do not state a cause, so the event says 'unknown'.
    - Nothing records a password change, or a reset request, against the user.
    - A user's page shows nothing done TO them.
    - Nobody is told their password changed.
    - An open "Forgot your password?" link survives a change made another way
      (only the paths that called invalidate_open_for() themselves ended it).

THE REFERENCE IMPLEMENTATION AND PORTING IT
    Every path below is under system/app/RSpade/resource/reference_app/ (your
    disk, release-current).

    1. STATE THE CAUSE at each place your application changes an existing
       password (one line each):

           // before
           $login_user->set_password($new_password);
           // after
           $login_user->set_password($new_password, Password_Change::CAUSE_SELF);

       self in your Change Password screen, reset_link in your reset-link page,
       admin wherever an administrator sets one. Reference:
           app/frontend/settings/password_security/settings_password_security_controller.php
           app/login/password_reset/password_reset_controller.php
           app/frontend/settings/user_management/settings_user_management_controller.php
           portal/settings/portal_settings_controller.php
           portal/auth/Portal_Password_Reset_Controller.php
       A path that only CREATES an identity (accepting an invitation, the
       portal's register page) needs none.

    2. ONE HANDLER, ONE TASK. The handler ends the identity's open reset links
       on every change (remove the invalidate_open_for() calls your reset-link
       and administrator paths made) and dispatches a task; the task writes
       the rows on every site of the identity (a handler may run under another
       site's lock, and a process holds one site's lock at a time) and queues
       the email:
           handlers/Password_Event_Handlers.php
           services/password_audit_service.php
       The reset REQUEST is the application's own flow, so it fires the
       application events login_user.password.reset_requested /
       portal_user.password.reset_requested with the same payload shape from
       the one place it mints a link (__send_link_if_account() and the portal
       controller's request()).

    3. THE ACTION LOG. A migration adding action_logs.audit_session_id (and an
       actor index), Action_Log::record() stamping it and taking an explicit
       $actor / $audit_session_id, Action_Log_Model::audit_ip_address(), the
       types TYPE_PASSWORD_CHANGED (50, metadata.cause) and
       TYPE_PASSWORD_RESET_REQUESTED (51), their renderers (which print the
       address), and the feed icon bucket 5:
           resource/migrations/2026_11_12_060540_add_audit_session_id_to_action_logs.php
           models/action_log_model.php
           lib/action_log/ (action_log.php, action_log_renderer.php, activity_feed.js)
           app/frontend/dashboard/frontend_dashboard_controller.php (_activity_icon())
       Run php artisan make:migration:safe <name> --path=rsx/resource/migrations
       and copy the SQL. Never store the address on the row: it is read back
       from the audit session.

    4. A USER'S HISTORY. get_user_activity (gated can_view_user_activity on
       top of the user-management gate): rows whose SUBJECT is the user or
       whose ACTOR is their login identity, newest first, with each address
       and its location (Rsx_Geo_Ip::label(), resolved per load, credited with
       <Geo_Ip_Credit />), drawn by a History region on the view page:
           app/frontend/settings/user_management/settings_user_management_controller.php
           app/frontend/settings/user_management/view/

    5. THE NOTICE. Password_Changed_Email (SECURITY): what happened, when,
       from which address, and "If this wasn't you, contact an administrator."
       Sent when the owner chose the password (self, reset_link,
       forced_change) or the cause is unknown; not for admin or cli - that
       person hands the password over, and the owner's forced replacement of
       it sends the notice. SECURITY mail carries no unsubscribe link (the
       framework passes none), so keep rsx.mail.branding.footer_text free of
       notification-preferences wording.
           emails/password_changed_email.php (+ .blade.php)

VERIFICATION
    - php artisan rsx:users:password:set --user=<a test user> --password=<temp>
      --require-reset, then sign in with <temp> and choose a new password: the
      user's page in User Management lists "set from the command line" and
      "chose a new password at sign-in ... from <address>", and
      php artisan rsx:mail:queue shows one Password_Changed_Email to them.
    - Reset Password on a user from User Management: the row appears on that
      user's page AND on yours, naming you, with your address; no email.
