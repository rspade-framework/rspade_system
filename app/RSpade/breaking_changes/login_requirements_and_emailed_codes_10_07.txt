LOGIN REQUIREMENTS AND EMAILED SIGN-IN CODES - PORT THE REFERENCE IMPLEMENTATION
Date: 2026-10-07

IF YOU DO NOTHING: the forced-2FA interstitial your application kept from the template (the users.is_2fa_required redirect in Rsx\Main::pre_dispatch()) stops page loads only - a flagged user with no factor can still call every Ajax endpoint and model fetch - and your application has no way to require an emailed sign-in code.

SUMMARY
    Category 3: two framework features with a template implementation to port.

    LOGIN REQUIREMENTS. A Login_Requirement_Abstract class declares something
    a signed-in user must do before the site is theirs. While it is unmet the
    user is signed in, but every identity reader answers NOT LOGGED IN except
    on the surfaces the requirement lists - so it is a boundary, not a
    redirect. The template's administrator-required second factor is now one.

    EMAILED SIGN-IN CODES. begin_challenge() takes the list of answers a
    challenge accepts, and issue_code() mints a six-digit code the
    application delivers. A new mail and SMS category, SECURITY, reaches an
    address on the site block list. The template uses them for an opt-in
    emailed code on every portal password sign-in.

WHAT YOU ALREADY HAVE
    Arrived automatically in system/, nothing to do:

    - Login_Requirement_Abstract and Login_Requirements (Core/Login), the
      concealment in Session and Portal_Session, the steering in the
      dispatcher and Ajax (error_code requirement_pending, followed by the JS
      Ajax layer), the rsx:health "Login Requirements" row, and the migration
      2026_10_07_210411 (_sessions.login_requirements). With no requirement
      class declared, nothing changes.
    - Rsx_Two_Factor / Rsx_Portal_Two_Factor: begin_challenge($identity,
      ?array $accepts = null) with the ANSWER_* constants, issue_code(),
      pending_identity(), challenge_pending() now carrying accepts,
      has_issued_code and codes_issued. Omitting $accepts behaves as before.
    - <Two_Factor_Challenge $send_controller $send_method>: "Send a new code",
      and the first code sent automatically.
    - The sso.two_factor.accepts / portal.sso.two_factor.accepts resolve hooks.
    - Rsx_Email_Abstract::SECURITY, Rsx_Mail::SECURITY, Rsx_Sms::SECURITY.
    - rsx.two_factor.challenge_window_minutes now defaults to 15 (was 10). An
      application that set it keeps its own value.

WHAT IS MISSING IN YOUR APPLICATION
    1. The forced-2FA policy as a login requirement, replacing the
       pre_dispatch() redirect.
    2. Emailed portal sign-in codes, if you want them.

THE REFERENCE IMPLEMENTATION
    Under system/app/RSpade/resource/reference_app/:

    app/login/two_factor_enrollment_requirement.php
        The administrator-required second factor as a login requirement.
    app/login/login_controller.php
        two_factor_setup() - the requirement's screen.
    main.php
        pre_dispatch() without the forced-2FA redirect.
    app/frontend/settings/user_management/settings_user_management_controller.php
        save_user() - recheck_user() when is_2fa_required changes.
    portal/auth/Portal_Login_Controller.php
        challenge_accepts() (the emailed-code policy), index() (the password
        stage), send_code() (issue and email, capped).
    portal/auth/portal_login_verify.blade.php
        <Two_Factor_Challenge> with the send endpoint.
    emails/portal_sign_in_code_email.php (+ .blade.php)
        The SECURITY email.
    handlers/Portal_Sso_Handlers.php
        two_factor_accepts() - the same policy for a federated sign-in.
    resource/config/rsx.php
        rsx.portal.emailed_sign_in_codes (false).

PORTING IT
    Port into your application's equivalent places; your own login flow,
    navigation and permission model decide the details.

    1. The forced-2FA requirement (only if you kept the template's
       users.is_2fa_required interstitial)

       a. Copy reference_app/app/login/two_factor_enrollment_requirement.php
          into rsx/app/login/. Its is_satisfied() is the condition your
          pre_dispatch() tested; its screen() is your setup route; its
          surfaces() lists the four enrollment endpoints the setup page calls.
          If your setup route is not Login_Controller::two_factor_setup,
          change screen().

       b. Delete the users.is_2fa_required block from Main::pre_dispatch() in
          rsx/main.php (the whole "if (str_starts_with($handler,
          'Rsx\App\Frontend'))" branch, if that was all it did). Keep anything
          else your pre_dispatch() does.

       c. In the edit-user endpoint that writes is_2fa_required
          (reference_app/app/frontend/settings/user_management/
          settings_user_management_controller.php, save_user()), call
          Login_Requirements::recheck_user($user) when the flag changes,
          beside the existing Realtime::push_user_refresh(). Without it a newly
          flagged user is held to the requirement only from their next
          sign-in.

       d. rsx:health shows "Login Requirements: OK 1 staff, 0 portal".

       Note the template dropped its TYPE_PLAYWRIGHT exemption: rsx:debug as a
       flagged user now lands on the setup screen, as the user does.

    2. Emailed portal sign-in codes (optional)

       a. Add the switch to the 'portal' block of rsx/resource/config/rsx.php:
              'emailed_sign_in_codes' => false,
          (reference_app/resource/config/rsx.php carries the comment.)

       b. Copy reference_app/emails/portal_sign_in_code_email.php and
          portal_sign_in_code_email.blade.php into rsx/emails/
          (CATEGORY = SECURITY).

       c. In your portal login controller
          (reference_app/portal/auth/Portal_Login_Controller.php):
          - add MAX_CODES_PER_SIGN_IN, challenge_accepts() and send_code();
          - in index(), replace the "elseif
            (Rsx_Portal_Two_Factor::is_enabled($portal_user))" branch with
            "elseif (($accepts = static::challenge_accepts($portal_user)) !==
            false)" and pass $accepts to begin_challenge().

       d. In the challenge page (reference_app/portal/auth/
          portal_login_verify.blade.php) add
              $send_controller="Portal_Login_Controller" $send_method="send_code"
          to <Two_Factor_Challenge>.

       e. If the portal offers federated sign-in, add two_factor_accepts()
          from reference_app/handlers/Portal_Sso_Handlers.php.

       f. Before turning it on anywhere a real person signs in, set
          rsx.mail.delivery to 'live' and prove it with rsx:mail:test - in the
          default 'suppressed' mode nobody receives a code and nobody can sign
          in.

       The staff login is the same code against Rsx_Two_Factor
       (rsx:man two_factor_codes).

VERIFICATION
    Requirement: flag a test user is_2fa_required with no factor, sign in as
    them, and open any staff page - it lands on the setup screen; a call from
    the browser console to any staff Ajax endpoint answers requirement_pending
    and the page moves to the setup screen. Enroll a factor and any page
    loads. rsx:health "Login Requirements" is OK.

    Emailed codes: with delivery 'live' and the switch on, sign in to the
    portal with a password - the challenge screen appears and a SECURITY email
    with the code arrives (the /_sys mail history shows the row); the code
    signs in; "Send a new code" replaces it; a passkey sign-in skips it.
