## SESSIONS & LOGIN FLOWS

**Always use `Session`** (static facade) — **never Laravel Auth, never `$_SESSION`.** A session is a BROWSER; at most one staff and one portal sign-in are current on it. Readers create nothing: `is_logged_in()`, `has_session()`, `get_user()` (site `User_Model`) / `get_user_id()`, `get_login_user()` / `get_login_user_id()` (cross-site identity), `get_site_id()`, `get_csrf_token()`, `is_impersonating()`, `has_api_access()` (may this identity use the external API — `users.is_api_access_enabled`; JS twin `Permission.has_api_access()`, enforced by `Api_Dispatcher`). Writers: `get_session_id()`, `set_login_user_id($id, $touch_last_login = true)` (null = logout), `logout()`, `set_site_id()`, `begin_impersonation()`/`stop_impersonation()`.

**`get_session_id(): ?int` creates the browser's session for a guest — call it only when you want one; "is there a session?" is `has_session()`.** It is **NULL in a command, a task and a test** (they run a row-less VIRTUAL session), the dispatching browser in a `#[Run_As_Dispatcher]` task, the key's own session on an API request. **A column storing it is NULLABLE and a screen showing it tolerates null.**

**Session values are realm-tagged and short-lived** — `put_value($key, $value, $expires_at = null, $realm = null)` / `get_value()` / `forget_value()`, realm `'staff'` | `'portal'` | `'guest'` (null = the request's experience). A realm's sign-out CLEARS that realm's values; `'guest'` survives. They are for second-factor challenges and small guest preferences, never storage; `put_value()` THROWS with no browser (command, task, API) and all three throw in a `#[Run_As_Dispatcher]` task. `begin_challenge()` signs the realm out first, so park a value AFTER it.

**`get_sessions_for_user()` answers USER SESSIONS** — one entry per browser x account x site (x impersonator), signed in or recently signed out, never another account's sign-ins on that browser — and `terminate_session()`/`terminate_all_other_sessions()` (SELF) and `terminate_*_for_user()` (another user, framework-guarded by `can_admin_role`) take those user-session ids. **A guarded termination REFUSAL THROWS `AjaxUnauthorizedException`; ABSENCE returns false/0** — never conflate them. **A new password saved through the model ends the identity's OTHER sign-ins by itself** (this browser and API-key sessions spared; `SIGN_OUT_PASSWORD_CHANGED`) — never terminate beside it. A screen lists a bounded window (the template: 3 months).

**A sign-in has a lifetime, and the framework enforces it** — `rsx.sessions.staff` / `.portal`: `max_length_minutes` (7 days, from the sign-in; the limit that bounds a hijacked session) and `max_idle_minutes` (8 hours, from the last PAGE VIEW — a rendered page or an SPA navigation, never an Ajax or API call), `0` = none. Checked on every request: a page navigation past a limit signs out and redirects with a flash; Ajax keeps working for `ajax_grace_minutes` (2h) so an open form can still save, then answers `session_expired`; an hourly sweep signs out the ones nobody comes back to. A browser unused `unused_session_days` (30) is made inactive. **Never implement "Remember Me" or a timeout of your own.** The app's one job is the dialog: `Rsx.set_session_expired_handler(fn)`; unregistered, the page reloads. Every sign-in and sign-out ROTATES the browser's session and CSRF tokens in place. **Two ids, two jobs:** browser-scoped state of your own keys on `get_session_id()` with `FOREIGN KEY ... REFERENCES _sessions (id) ON DELETE CASCADE` (the one reference an app makes to a system table); **a record of what somebody did stores `Session::get_audit_session_id()`** — a permanent row per user session x site x address x user agent (null in a command or a plain task); `Audit_Session::join($query, 'table.audit_session_id')` adds `audit_ip_address`, `audit_user_agent`, … to a query of your own. Skills `rspade:session-auth`, `rspade:audit-session`; `rsx:man session` (BASIC, then ADVANCED).

**Brute-force throttling is the framework's and is ON by default**: `Login_Throttle` counts FAILURES per client IP (`rsx.sessions.login_throttle`; the IP is `Session::get_client_ip()` = `$request->ip()`, and X-Forwarded-For is believed only from loopback and `rsx.http.trusted_proxies` (`TRUSTED_PROXIES` in `.env`, comma-separated) — **a box behind a load balancer must list it**, or every visitor shares one budget), `RsxAuth::verify_credentials()` refuses a locked-out address as its FIRST statement by THROWING `Auth_Throttled_Exception` ("You're doing that too fast"), and `Login_History::record_failure()` feeds it — so a login function CATCHES that exception and renders its message, never reporting it as a wrong password, and a path that verifies its own password calls `require_not_throttled()` + `record_failure()` itself. A caller with no client IP (CLI, tasks) is never throttled.

**A staff login is TWO calls: `RsxAuth::verify_credentials($credentials)` checks the pair and answers the identity or null - it signs NOBODY in and touches no session - and `RsxAuth::login($identity)` is the only way into a session.** Whatever a sign-in still owes (a second factor, your own account-state question) runs BETWEEN them, with the visitor still signed out, so a request that dies part-way leaves them out and a refusal has no session to undo. **Its second thrown refusal is `Auth_Password_Reset_Required_Exception`** (`->identity`): a correct password on an identity flagged `password_reset_required` (set by the app or `rsx:users:force_password_reset`, cleared by the framework when the password changes; recorded as a row even under `record: false`) - catch it beside `Auth_Throttled_Exception`; it refuses the password door only, never a passkey or SSO sign-in. `verify_credentials()` records the login outcome itself — never call `Login_History::record_success()` beside it, or you record twice (`record: false` when the check is not yet a login, and then you record). Account state (`status_id`/`is_activated`/`is_verified`) is **APPLICATION vocabulary**: `verify_credentials()` checks a live identity plus the password and nothing else, so enforce your statuses in your own login function and in `Main::pre_dispatch()` (`init()` is bootstrap and cannot eject anybody), which runs for bearer-key calls too — `/api/vN` and the file-serving routes alike (non-null = 403 `account_refused`; branch on `Session::is_api_request()` before `logout()`). **`users.is_enabled` and `sites.is_enabled` are the exception and are the FRAMEWORK's** — a membership is usable only when both are on (`User_Model::is_active()` / the `->active()` scope, which a site picker lists with); an identity with no such membership fails `verify_credentials()` exactly like a wrong password (recorded `STATUS_FAILED_DISABLED`), `RsxAuth::login()` returns false for it so the 2FA, SSO and dev-auth doors close too, and `Session::enforce_enabled_membership()` ends a live session whose membership or site was disabled or deleted before the gates run (site 0 can never be disabled); **delete your own `is_enabled` checks.**

**`Rsx_Two_Factor` is the framework's second factor** (TOTP + passkeys + recovery codes on the LOGIN identity), opt-in **per identity with no global switch** — `is_enabled($login_user)` is the whole question. A login function becomes two-stage: `verify_credentials($credentials, record: false)`, then `begin_challenge($identity)`, which parks the pending identity — **nobody is signed in and nothing is authenticated until the factor passes**, and `verify_challenge()` is what logs in, stamps `last_login` and records the outcome (it is throttle-first and writes `STATUS_FAILED_2FA`, which already feeds the throttle — never count it twice; per-challenge and per-identity attempt caps sit beside it, a locked identity is released with `rsx:users:2fa:unlock`; a failure's `reason()` is a `REASON_*` constant for code, a challenge destroyed by wrong answers fires `two_factor.challenge.spent` / `portal.two_factor.challenge.spent` `{identity, email, failures}` so the app can tell the account owner, and a challenge screen NEVER shows attempts remaining). **The verification ENDPOINT stays the app's** (the destination is application logic); `<Two_Factor_Challenge $controller $method>` posts to it. Enrollment and removal act on the signed-in identity only and **refuse while impersonating**; the operator escape hatch is `rsx:users:2fa:*`. **What a challenge accepts is the login function's policy and is ENFORCED**: `begin_challenge($identity, $accepts)` (`ANSWER_ISSUED_CODE`/`_TOTP`/`_PASSKEY`/`_RECOVERY_CODE`; null = what the identity holds), and an **emailed six-digit code** is `issue_code()` (framework mints ONE live code per identity - a resend re-sends the same digits until it expires - stores it encrypted, verifies, caps) delivered by the app's own `CATEGORY = SECURITY` email - `rsx:man two_factor_codes`. **A browser that passed may be TRUSTED** for a per-realm window (`rsx.two_factor.trusted_device_days`, both 0 = off): the verify endpoint calls `trust_this_device($identity)` (throws unless that identity passed in this request), the login function asks `device_is_trusted($identity, $earned_by)` before challenging - the framework never skips a challenge itself. **A passkey is also a FIRST factor**: `begin_passkey_login()` / `verify_passkey_login()` behind `<Passkey_Sign_In $controller $method>` (the endpoint again the app's) sign in with no password, user verification required, and **owe no second factor** — `is_enabled()` still means "a password or SSO sign-in owes a challenge". **`Rsx_Portal_Two_Factor` is the identical API for portal users** (own table; a staff credential never signs in on the portal), and the shipped components pick the realm from the page. Skill `rspade:two-factor`.

**A step a signed-in user still owes is APPLICATION code.** Enrolling a factor, accepting terms, an onboarding wizard: the login function works out what is outstanding once, at sign-in, and parks it with `Session::put_value()`; `Main::pre_dispatch()` redirects page requests to the step's screen while it is set. The user is signed in throughout - an outstanding step is not an access level, and the framework ships no forced-enrollment screen and reads no "2FA required" setting.

**Preference variables** - `$user->get_variable($key, $default)` / `set_variable()` / `forget_variable()` / `has_variable()` on `User_Model` (this site's record), `Login_User_Model` (the identity, across sites) and `Portal_User_Model`: a key/value store for a step skipped, a prompt dismissed, "do not show this again". Never in the record's payload, no expiry. **A preference every account has for life (dark mode, timezone) is a COLUMN; a value that should die with the browser session is `Session::put_value()`.** `rsx:man user_preference_variables`.

**`Rsx_Sso` is the framework's federated sign-in** (Google, Microsoft, Facebook, Apple, X built in; a sixth is a `socialiteproviders` package plus an `rsx.sso.custom` block) — **a provider is live because its `enabled` config flag is true and for no other reason**, and one enabled with a missing credential THROWS naming the literal `.env` keys. **The framework owns the CEREMONY** (state, PKCE, the token exchange, the throttle, `STATUS_FAILED_SSO` recorded exactly once) **and the app owns the POLICY**, through hooks that all FAIL CLOSED: **`sso.identity.unlinked`** (resolve; return a destination URL or null — all-declined is "No account is connected to this sign-in."), `sso.login.authorize` (gate; a STRING denies and is shown), `sso.two_factor.verify_url` (resolve; REQUIRED once any identity holds a factor), `sso.login.destination` / `sso.link.destination`. A proven-but-unconnected identity is parked as `Rsx_Sso::pending()` — **half-authenticated, nothing is logged in** — and redeemed with `link_pending()` / `consume_pending_and_login()`. **NEVER match an unverified provider email onto a local account** (account takeover); a provider sign-in still faces the local 2FA unless `rsx.sso.skip_two_factor`; linking refuses while impersonating. Buttons are `<Sso_Buttons />` (renders NOTHING when nothing is enabled; the "or" divider is the page's job). **`Rsx_Portal_Sso` is the client-portal realm** — same API, off until `rsx.sso.portal_enabled`, its own ceremony URLs (a second redirect URI per console) and its own `portal.sso.*` hooks, never the staff ones. Skill `rspade:sso`; `rsx:man sso`.

**CSRF is framework-handled** on every internal transport (Ajax, uploads, `@csrf`), portal included — never hand-roll one. **Never hand-roll `?redirect=` handling** either: `Login_Redirect` (`capture()`/`params()`/`hidden_input()`/`consume()`, PHP and an identical JS mirror) is the ONE redirect sanitizer, staff/portal aware, degrading silently on hostile input.

**The INITIAL USER is `login_users` id 1 AND `users` id 1, by contract** - created only by `Rsx_Initial_User::create()` (first-run screen, the `RSPADE_DEFAULT_*` post-migrate step, the test-baseline seed), which assigns the id explicitly and fires **`user.initial.created`** `{user, login_user, site_id, source}`. **An app attaches its founder's own rows in an `#[OnEvent]` handler - NEVER in a migration keyed to user id 1** (a migration runs at a fixed point in history and never runs for the test baseline, where this event fires too). Skill `rspade:event-hooks`; `rsx:man initial_user`.

**Turnstile is built in — do NOT install a captcha package.** `<Turnstile_Input />` renders a real hidden `__turnstile` field that is ALWAYS submitted (sentinel `'inactive'` while the feature is off), so the endpoint calls `Rsx_Turnstile::validate($request[, $params])` as the **FIRST statement of the POST branch** — before any credential or email work, so it gates enumeration too. Submitting the field without validating it throws "Turnstile implementation incomplete"; fix it, never silence it.

Skills: `rspade:session-auth` (references `csrf`, `login-redirect`) for login pages, device-session screens, admin termination, impersonation, lifecycle windows and the concurrent cap; `rspade:turnstile`, `rspade:two-factor`, `rspade:sso`. Details: `rsx:man session`, `rsx:man turnstile`, `rsx:man two_factor`, `rsx:man sso`.
