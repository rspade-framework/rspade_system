## BACKGROUND WORK (TASKS, LOCKS, SUBPROCESSES)

Background work is a `public static` Service method (a class extending `Rsx_Service_Abstract`, in `/rsx/services/`) marked `#[Task]`, taking `(Task_Instance $task, array $params = [])` and optionally `#[Schedule('every 5 minutes')]`. **A MAINTENANCE task - anything running daily or less often (a retention purge, a cleanup, a sweep) - is `#[Schedule('maintenance')]` (or `'maintenance weekly on <day>'` / `'maintenance monthly'`) PLUS `#[Exclusive('maintenance')]`, never a hard-coded `'daily at 3am'`, and reports what it is doing (`status()` per phase, `progress_count()`, a `stdout()` line of what it changed, a `summary()`)**: the window opens at `rsx.tasks.maintenance_hour` (default 2am, server timezone) and its tasks run one at a time. **Every execution is a run, and every run is a `_tasks` row (`Task_Run_Model`)** - dispatched, scheduled or inline. `$id = Task::dispatch('Service', 'method', $params)` enqueues, spawns a worker when due and returns the run id; `Task::internal()` runs in-process and returns the settled row. **A dispatched run executes as NOBODY** in a blank virtual session (no identity, no site, `get_session_id()` null - right for system work), and every run ends with the process blanked again. **So a plain run has no site, and a site-scoped READ there THROWS** (`Site-scoped read of X_Model with no site declared`) - the scope is ANDed with any `where('site_id', $n)` of your own, so naming the site in the query never overrides it. A system task that serves ONE tenant (a per-site sweep, a sync engine) DECLARES it for the span of the work - `Session::set_temporary_site_id($site_id)` (writes nothing, refuses where the declaration is not the task's to make), cleared in a `finally`, never the permanent `set_site_id()` (a leaked one repoints whatever the process runs next, and an inline caller's own session); `#[Emitter]`s are declared by the engine. **A task whose subject is EVERY tenant reads with `Model::without_site_scope()` - a READ bypass for the rows it returns, not a licence to save them later: `save()` of an existing row whose `site_id` is not the ambient one is REFUSED** ("serious security issue"), so write inside the same `without_site_scope()` callback, or group the rows by `site_id` and declare each group around its writes. A raw `DB::` write is checked by nothing. **A task that is the asynchronous stand-in for a user's Ajax endpoint MUST declare `#[Run_As_Dispatcher]`**: it runs BOUND to the dispatching sign-in, FROZEN - identity, site, realm, timezone and audit session are the requester's even after that browser signs out, `get_session_id()` is the requester's browser, and every identity setter and session value throws; refused (FAILED, nothing run) when the account or site was disabled since, and never scheduled; run INLINE it acts as whoever is acting in the caller (by hand `rsx:task:run <Service> <method> --user=<id|email> --site=<id>`, in a test `__acting_as_user()`), and with nobody acting it is refused (`rsx:man tasks`, RUNNING AS THE DISPATCHER). Workers claim `#[Run_As_Dispatcher]` runs first, then other on-demand runs, then scheduled ones, oldest first within each. A task REPORTS through `$task`: `status()`, `progress()`/`progress_count()` (each re-estimates the ETA from the pace so far; `eta()` is only for a task that reports no progress), `state()`, the queue (`queue_push()`/`queue_push_many()`/`queue_pop()`/`queue_remove()`/`queue_clear()` - one row per item, advanced on EVERY item: it is what shows a run moving or stuck), `message()`, `stdout()`/`stderr()` (echo is stdout), `attach_file()`/`attach_bytes()`, `summary()`. **Design every task for its watchers**: use each report that describes its work, ONE progress indicator and only when progress is measurable, `heartbeat()` + `is_stop_requested()` on every item of a loop. **A task has no limit on how long it runs so long as it keeps reporting; a worker-run task that reports NOTHING for 30 minutes (`rsx.tasks.silent_timeout`) is killed** - so a task expected to run long ("render a preview of everything in the system") must report its status as it goes, heartbeat/progress on every item, or it will be killed after 30 minutes without a report; **an attachment is only for a file the initiator of a user-started run is waiting to take (an export) or a debug artifact** - results that belong to the application go in its own tables. **The return value is the RETURN CODE: `null`/`true`/`0` succeed, `false` or an integer fail - a task never returns data** (an array is a failed run). Outside code acts on a run: `request_stop()` (**cooperative** - only a task that checks `$task->is_stop_requested()` stops), `force_stop($grace)` / `force_kill()` (carried out by kill workers on the target's host; a run inside a web request is never signalled), `cancel()`, `rerun()`. **A PENDING run says what it is waiting for** - `waiting: {reason, text, lock, held_by_task_id}` on `to_status_array()`, derived at read time and never stored (`scheduled for ...`, `waiting for exclusive lock "group" (held by task #N)`, `waiting for a free worker (2 of 3 busy)`); `Rsx_Task.waiting_text(status)` in JS. **`php artisan rsx:tasks:disable [--reason=] [--grace=]` / `rsx:tasks:enable` turn the task system off and on** (a database switch, one fact for every host; the first half of a server replacement): disable stops what is running - asked, then killed after the grace - and returns once this host's runs have settled; **while disabled, every task - dispatched or inline - queues, nothing runs until `rsx:tasks:enable`, and an inline caller (`Task::internal()`, `rsx:task:run`, a `#[Command]`) waits for its answer**; `Task::is_enabled()` / `Task::disabled_state()` read it. Pools `on_demand`, `scheduled`, `kill` (`rsx.tasks.pools`). One cron entry drives everything: `* * * * * php artisan rsx:task:process`. **A PHP script OUTSIDE the application boots the whole shell with `$app = require '<project>/system/script.php';` and nothing else** - same pre-boot guards, same manifest, same site: `rsx:man scripting`. **A script that writes many rows calls `Task::spawn_workers(false)` right after it** - every save, mail or upload that dispatches would otherwise start a worker process whenever a pool has room; off, dispatch only queues and the cron tick drains it.

**The task gates DENY BY DEFAULT**: nobody but a developer sees or controls a run until the app registers `task.view.authorize` / `task.view.scope` / `task.control.authorize` handlers (portal: `portal.task.*`). **Grant least privilege, like an AWS `policy.json`**: only the user types, the specific tasks (`'Service::method'`, normally on runs the viewer started) and the actions a screen was built for - and re-check the grants with every new or changed task. Through them the browser reads with `Rsx_Task` and shows a run with the Core widgets `<Task_Status_Badge>`, `<Task_Report>`, `<Task_Report_Browser>`, `<Task_Output>`.

**An artisan command in RSpade is a `#[Task]` with a name.** An application writes NO command classes (all of `system/` is framework property) — it adds `#[Command('prefix:name', 'Description')]` beside the `#[Task]`, and the manifest-discovered declaration IS the command: `php artisan myapp:import` is `rsx:task:run <Service> <method>` under a friendlier name. **The task's stdout is the command's stdout, its stderr (each `status()` change included) the command's stderr, and its return code the exit code**; `-q` silences stderr. Skill `rspade:task-commands`; `rsx:man task_commands`.

**KEY: tasks run concurrently and UNGUARDED.** No automatic application lock exists anywhere — multiple workers run at once, and a task shares tables with web requests and other tasks. **A `#[Task]` must never assume it is the only writer.** `#[Exclusive]` (identity: the method) and `#[Debounce(seconds)]` (the method + its params; the delay is optional, a bare `#[Debounce]` has none) guard **ONE identity against itself** (at most one running + one pending), never a shared table against other writers — use a lock for that. **`#[Exclusive('group')]` serializes several TASKS against each other**: one running across the group, pending still one per method, and a run waiting on its group holds no worker slot; it is REPEATABLE, and a task naming several groups runs only while it holds all their locks, taken together or not at all (no lock is reserved for a waiting run - workers start the most overdue run whose locks are all free); **a due `#[Schedule]` is a call like `dispatch()`**, so a tick during the task's own run (an on-demand one included) becomes its one pending follow-up, debounced like any other; the two markers may sit TOGETHER - `#[Debounce]` beside `#[Exclusive('group')]` queues per method + params and runs under the group's lock, beside a bare `#[Exclusive]` it is `#[Debounce]` alone — never take a lock inside the task body for this. **You never add a timeout to your own task**; the silence limit is infrastructure, and a task that should hand its worker back mid-job does so itself with `$task->run_again_in($seconds)` (its own `#[Schedule]`'s next run; `Task::set_next_run($service, $method, $iso)` from outside - both throw without a `#[Schedule]`, and the cadence resumes after that run).

**Locks**: `RsxLocks::named_write_lock($name)` / `named_read_lock()` for a critical section, `site_write_lock($site_id)` / `site_read_lock()` per tenant, `system_lock($name)` for a this-box-only resource, plus `upgrade_lock()` and counting semaphores. **Always release in a `finally`** (`RsxLocks::release_lock($token)`). **A lock is held until you release it or your process dies** — no lease, no TTL, no renewal; `$timeout` is a WAIT budget only and defaults to wait-forever.

**MANDATE: spawn `php artisan` ONLY through `Rsx_Artisan`** (`App\RSpade\Core\Console\Rsx_Artisan`) — never `passthru`/`exec_safe`/`shell_exec`/`system`/`popen`/`proc_open` with an artisan command line.

`Rsx_Artisan::passthru($cmd)` streams, `run($cmd, $args, $output)` captures, `dispatch_detached($cmd)` is fire-and-forget.

**Why it is a mandate: a subprocess is a different lockd connection, so it queues behind locks its own PARENT holds while the parent blocks in `waitpid` — a permanent hang the deadlock detector structurally cannot see.** Command name and argv tokens stay SEPARATE. In-process `Artisan::call()` needs none of this. Enforced by `ARTISAN-SPAWN-01`.

Skills: `rspade:background-tasks` (reporting, the return contract, lifecycle control, gates and widgets, `#[Schedule]` phrases, the pools, abandonment retry), `rspade:task-commands` (`#[Command]`, the console output contract, the build-time FATALs), `rspade:locks-and-subprocesses` (cluster vs system locks, semaphores, FIFO/deadlock refusal, lock groups). Details: `rsx:man tasks`, `rsx:man task_commands`, `rsx:man locks`.
