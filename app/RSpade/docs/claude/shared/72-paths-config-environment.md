## PATHS, CONFIG & ENVIRONMENT

**Laravel runs FROM `system/`, so `base_path()` resolves to `<project>/system` — not the project root.** Never join a project-logical path onto it: `base_path('storage/...')` lands inside the framework tree, where nothing lives, and reserve `base_path()` for framework-internal locations.

**THREE VOLATILE TREES, one level ABOVE the Laravel base path, and `App\RSpade\Core\Paths\Rsx_Project_Paths` is their SINGLE OWNER**: `<project>/build` (everything `rsx:build` produces — the manifest index, bundles, Laravel's route/event/package caches, compiled Blade, the seal), `<project>/tmp` (every derived cache and runtime scratch — the generated JS stubs, node sockets, npm scratch, staging, thumbnails, renditions — and **what Laravel calls its storage path**, so `storage_path()` lands here), `<project>/storage` (uploads, `storage/app`, logs, plus `storage/state` for the maintenance flag, flock files and updater markers). `build/` and `tmp/` are gitignored and regenerated on demand; `storage/` is the tree to back up. **Durable files never go through `storage_path()`** — that is the disposable tree; use a `Storage` disk or `Rsx_Project_Paths::app_dir()`. The two links `tmp/logs` and `tmp/app` are what keep those two lazy spellings persistent.

**Never write one of those paths as a literal** — `build_root()`/`tmp_root()`/`storage_root()`/`state_root()`, the joiners `build_path()`/`tmp_path()`/`storage_path()`/`state_path()`, and a named method per entry (`bundles_dir()`, `seal_file()`, `logs_dir()`, `flock_dir()`, …) are the whole API. `PATH-OWNER-01` flags a literal, a `storage_path()` with a literal argument, and `rsx_project_file_path()`/`base_path()` handed one. **The reason is that `tmp/` and `storage/` are RELOCATABLE** in `.env` (`RSX_TMP_PATH`, `RSX_STORAGE_PATH`; an absolute path or one relative to the PROJECT ROOT; `storage/state` follows the storage root and is not independently overridable), so a literal addresses nothing on a box that moved one. **`build/` is FIXED at `<project>/build`** — it is deployed and made read-only beside `system/` and `rsx/` — and a literal for it is still a finding, because the owner is the one spelling. `rsx_project_file_path()` survives as the inverse — resolve a key you were HANDED, never a literal you wrote. **A `./`-prefixed string is WORKING-DIRECTORY relative and addresses nothing a subprocess can rely on**; a resource file is reached with `__DIR__` or `base_path('rsx/...')`.

**Project layout**: `rsx/` is your code (`app/` modules, `models/`, `lib/`, `services/`, `handlers/`, `public/`, `resource/`, `theme/`); `system/` is the framework. **Path-agnostic rules**: ANY directory named **`resource/`** is framework-ignored (exception: `/rsx/resource/config/`); ANY directory named **`public/`** is web-accessible and framework-ignored. **Classes are found by NAME, not path** — no imports, no manual namespaces.

**Config is two-tier**: framework `/system/config/rsx.php` (**never modify**) + user `/rsx/resource/config/rsx.php`, deep-merged. **`system/app/Http/Kernel.php` is framework-OWNED** (hard-synced by every framework update, tamper-gated against local edits) — an app's own HTTP middleware is declared in `config('rsx.middleware.global')` (append-only: it runs AFTER the framework stack, around every request - there is no Laravel router, so no route middleware groups or aliases). **Use `env()` ONLY for deployment-specific values** (`DB_PASSWORD`, `REDIS_HOST`); application behavior belongs in a config file, under version control.

**`APP_URL` in `.env` is the single hostname source, and outside development it MUST be https** — http throws at boot in debug and production. **Development also accepts http**, so a local container with no TLS in front runs as-is (`APP_URL=http://localhost:8080`; include the port when it is not the scheme default), and a guard fatals loudly when the browsed host disagrees. On a host that has TLS write the literal `APP_URL=https://$HOSTNAME` — unquoted, no braces, the only spelling phpdotenv passes through. `Rsx::get_hostname()` and `is_dev_site()` (contains `.dev.`, gating outbound email/SMS to whitelisted recipients or a catchall) both derive from it. **There is no hostname-derived "debug site" concept** - login credential auto-fill is the boolean `RSPADE_LOGIN_AUTOFILL`, off unless a developer turned it on.

**`.env` is LOCAL configuration and is never distributed; `.env.dist` at the project root is the TRACKED canonical defaults.** A missing `.env` is created from it whole-file, and **keys propagate downhill on every development boot — `.env.dist` -> `.env`, a key MISSING below is appended — while values are never touched.** So **to remove a setting set it EMPTY: a deleted line comes back on the next boot**, and **any NEW config key must be added to `.env.dist`** with a sensible default or an empty string, never a secret. One implementation, `php artisan rsx:env:heal`.

**Laravel's `environmentPath()` IS the project root** — `env:encrypt`, `env:decrypt` and `key:generate` all operate there, never inside `system/`. **`system/.env` remains a SYMLINK to the project-root `.env` for the bash readers that address it by name; the root file is authoritative.** A deploy or clone can materialize it into a real file, at which point writes to that path go somewhere Laravel no longer reads — `rsx:env:heal [--dry-run]` repairs it and reports every discarded value.

Skill `rspade:environment-config` (config recipes, hostname-guard diagnosis, `.env` drift repair, path-helper selection). Details: `rsx:man config_rsx`, `rsx:man storage_directories`.
