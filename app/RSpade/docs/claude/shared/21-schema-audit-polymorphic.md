## SCHEMA, AUDIT AUTHORSHIP & POLYMORPHIC REFERENCES

**Migrations are forward-only, with no rollbacks: deterministic transformations against known state.** Raw SQL through `DB::statement()`; the Schema builder is prohibited. Create one with `php artisan make:migration:safe <name>`, apply with `php artisan migrate` (which snapshots the database first and auto-rolls-back the run on failure — but ONLY in the RSpade DEV container against a LOCAL database host; anywhere else, the prod container included, it runs bare and prints every reason protection is off). **`migrate --dump-rollback`** protects a production or external-database run with a gzipped mysqldump instead: restored on failure, and an interrupted run's leftovers are recovered by the next migrate automatically, or refused when ambiguous (`--abandon-dump-rollback` accepts the database as it stands) - `rsx:man migrations`, DUMP ROLLBACK.

**`migrate` is fine to run whenever schema work needs it** — expected and encouraged after creating or changing a migration; treat it as one command (press the button), not "heavy machinery." **Always run `migrate` with its FULL output — never pipe it through `| tail`/`| head`, grep it, or truncate it in any way**: the snapshot/rollback narrative IS the diagnostic, and a truncated run hides which step failed. A migrate CANCELLED mid-run leaves its snapshot behind — `php artisan migrate:restore` performs the same restore a failed run performs automatically. **`migrate` rebuilds nothing, in any mode**: a build holds code facts only, and a table's columns are read from the database at run time (`Rsx_Schema`), cached under the STATE key - the build's code key combined with the applied migrations - so a migration moves that key and every process sees the new schema, on a sealed box included. `migrate` also purges the cached schema state before and after every run.

**A fresh database restores the shipped schema cache before migrating**: with NO TABLES AT ALL and `rsx/resource/db/schema_cache.sql.gz` present, `migrate` streams it in (plus `uploads_cache.tar.gz` into the blob store) and then **continues with the ordinary run** — a PRE-MIGRATE step, not a replacement, so migrations newer than the cache apply on top exactly as always. **A stale cache is therefore never a bug, and you NEVER regenerate it on your own initiative** — `rsx:db:rebuild_provision_cache_snapshot` is a destructive, operator-requested command (skill `rspade:migrations`).

**No defensive coding in a migration.** No `IF EXISTS`, no `information_schema` queries, no fallbacks. **Know the current state, write the exact transformation.** Failures fail loud — the snapshot rollback is what handles recovery.

### System tables are private

**A `_`-prefixed TABLE belongs to the RSpade core, schema included, and application code in `rsx/` never touches one directly** — no `DB::table('_sessions')`, no raw SQL or join that names one, no query that depends on one of its columns. The two sanctioned contacts: a `FOREIGN KEY ... REFERENCES _sessions (id) ON DELETE CASCADE` on a table of BROWSER-scoped state (its `session_id` nullable when a command or task may write the row), and joins made FOR you by a framework call (`Audit_Session::join()`). Reach what it holds through the interface the framework publishes for that feature (`Session::get_sessions_for_user()`, `Login_History::get_history_for_user()`, `Session::get_audit_session()`, `$record->revisions()`, `Task_Run_Model::find_page()`, …). **A system table's schema is not a contract**: columns move, split and disappear between releases with no notice, and only the published interfaces stay stable. **When an interface does not give you what you need, submit a change request to RSpade to extend it — never query the table yourself.** `rsx:man database_schema_architecture`.

### Audit authorship

Every table carries a polymorphic PAIR per audit column — `created_by_id`+`created_by_type`, `updated_by_id`+`updated_by_type` (both BIGINT), plus `deleted_by_*` where rows soft-delete — because RSpade has three identity models (`User_Model`, `Portal_User_Model`, `Login_User_Model`) and a bare integer could not say which one it meant. **`Rsx_Model_Abstract::save()` stamps it automatically** — no trait, no wiring — and **an explicitly assigned pair always wins** (the pair is ONE unit: set one half and you must set both). Read it back with `$record->created_by` / `get_created_by_author()`.

**Migrations never declare the audit columns** — the schema-hygiene pass adds them to every table. **Never reference them positionally (`AFTER updated_by`) or by a pre-pair name.**

**An actor model** (anything an audit pair can point at) extends `Rsx_Site_Actor_Model_Abstract` when its table has `site_id` and `Rsx_Actor_Model_Abstract` when it does not, which supplies the mandated `SoftDeletes` and forces `get_printed_name()` + `get_view_profile_url()`. **An actor must never be hard-deleted** — every audit column naming it would dangle. `ACTOR-01` is a manifest-build FATAL on both counts.

### Polymorphic type references

**A polymorphic reference is ALWAYS the pair `{relation}_type` + `{relation}_id`, both BIGINT** — the `_type` stores a type-ref integer id (**never a VARCHAR class name**) and is declared in the owning model's `$type_ref_columns`; the relation itself is stock Eloquent (`morphTo()` etc., read as a property). **Two parallel nullable FKs is the forbidden shape**; a single-target reference is a plain FK, not a pair; a `type_id` ENUM column is a different concept entirely. **Simple names only**: `class_basename($model)`, never `get_class($model)`. `POLY-01` (manifest-build FATAL) rejects the Laravel string-morph pattern.

Skills: `rspade:migrations`, `rspade:actors-and-authorship` (stamp matrix, `<Record_Author>`, writing an actor), `rspade:polymorphic` (boundaries, half-set pairs, pivot morphs). Details: `rsx:man model_normalization`, `rsx:man polymorphic`.
