## DISTRIBUTION & PUBLISHING

**`bin/publish` cuts a production release - NEVER a test step** (skill `rspade:publishing-a-release`). **We AUTHOR the consumer**: downstream, `system/` is a git submodule hard-reset to each release (`reset --hard` + `clean -fdx`), so ALL of `system/` is overwritten and a downstream change lives in `rsx/` (class override). **Durable "make the environment correct" behavior is a script in `system/bin/environment_updates/`** (self-detecting, idempotent, silent; its CLAUDE.md), never an edit to the updater - `framework-pull-upstream.sh.dist` is authoritative and lags one pull (`rsx:man framework_pull_mechanics`). **`rsx/resource/CLAUDE.dist.md` is the starter's CLAUDE.md - a TEMPLATE EXAMPLE of how an end developer uses their own CLAUDE.md, not an index of the app: keep edits to it minimal** (the template's behavior is inferred from conventions and its own comments). `rsx/resource/skills/` ships too.

**THE RSPADE IMAGES are published to GitHub Container Registry by `bash system/bin/publish_docker_images`** (framework-author only, stripped from the release): `ghcr.io/rspade-framework/rspade-server-dev`, `rspade-server-prod`, `rspade-docconvert`, each one tag covering linux/amd64 + linux/arm64 (arm64 built here under QEMU, however long it takes). **The version is automatic** - the UTC build date `YYYY.MM.DD`, `.N` when that tag exists - recorded in the image as `image_version=` in `/opt/rspade/image.conf`; all three push under the version tag first, then `latest` moves to them, then the script verifies both tags and both architectures. **A NEW VERSION IS A FROM-SCRATCH BUILD** (owner mandate): the script empties the Docker build cache and pulls the base image before the first build, so every version carries current package updates; **only a RESUME of an interrupted version may use the cache** (`docs.dev/docker_images/publish_state.conf` records the version in progress; a resume skips already-pushed images and refuses if the Docker sources changed; `--fresh` abandons it) - never work around this with a cached build of a new version. **THE MINIMUM IMAGE VERSION** (the image version a framework checkout requires; inside the container an older image is FATAL, outside it nothing is checked, and the framework authors' box skips it) **is bumped ONLY when the framework starts to DEPEND on something new in the container** - a service added, or a service changed in a way framework code interacts with. Never for an image-only improvement (package updates, security floors, sizing, a Node bump the checkout does not need), never arbitrarily, never "to be safe". **When a change you make would require a bump, STOP and tell the owner what the framework now depends on and why an older image breaks; bump only on their approval**, then: publish the image first, set the minimum to that published version (never above the newest published one - `bin/publish` refuses), and ship a `breaking_changes` document telling downstream to pull the image and recreate the container. **Node and npm are exact pins** (`NODE_VERSION`/`NPM_VERSION` in the Dockerfile); a bump gets a local test build (`build.sh dev`) and a framework suite run on that image before any publish. **NEVER publish an image on your own initiative**: when a change to `resource/docker/` needs a new image, TELL THE OWNER and push only on their go-ahead. Credentials and registry notes: `/root/CLAUDE.md`.
